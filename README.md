# Learning Hub — Interview Prep Knowledge Base

A growing set of deep, self-paced study resources for ML / AI-engineering interviews.
Each subject is a **self-contained static mini-site** — styled HTML, hand-written inline
SVG diagrams, runnable code, interactive widgets, an interview Q&A bank, and a progress
tracker that saves in your browser.

**Classical ML and LangGraph are structured differently** from the other subjects: **one part per
level** (17 and 12 parts respectively), and — following the RAG pattern — **every topic section ends
with its own interview Q&A box**, tagged by question type (`Conceptual`, `Gotcha`, `Debug`,
`System design`, `Deep dive`, `Trap`). That is why their Q&A counts are an order of magnitude above
the others: the questions live *with* the concept rather than only in a bank at the end. Each still
has a final consolidated, shuffled drill ([CML Part 17](https://subhasish-saha.github.io/Data-Science-Learning-Hub/cml/CML_Part17_QABank.html),
[LangGraph Part 12](https://subhasish-saha.github.io/Data-Science-Learning-Hub/langgraph/LangGraph_Part12_QABank.html)).

**Interactive widgets** (Classical ML and LangGraph) are self-contained `<canvas>` + vanilla-JS
components defined inside each content fragment, styled by the `.wdg` CSS block that
`build_cml.py` / `build_lg.py` inject before `</style>`. They compute for real in the browser rather
than replaying a recorded animation — least-squares fits, coordinate-descent Lasso, Lloyd
iterations, PAVA isotonic regression and exact AUC/PSI on the ML side; a ReAct trace stepper, a
reducer playground, cost and latency models, a trajectory scorer and a drill deck on the LangGraph
side. Each is wrapped in an IIFE with unique element IDs so it keeps working after being
concatenated into the `*_Complete.html` file.

## Reading it locally

Opening the files directly works (`open index.html`), but a local server avoids any
`file://` quirks:

```bash
git clone https://github.com/Subhasish-Saha/Data-Science-Learning-Hub.git
cd Data-Science-Learning-Hub
python3 -m http.server 8000
# then open http://localhost:8000/
```

Local progress is stored under the same localStorage keys as the live site, but the two
origins are separate — `localhost` progress does not appear on the GitHub Pages URL.

## Progress tracking

Each subject keeps its own progress-tracker localStorage key so they never collide:

| Subject | Key |
|---|---|
| Python for Data Science | `pyPrepStatus_v1` |
| RAG | `ragPrepStatus_v1` |
| Classical ML | `cmlPrepStatus_v1` (+ `cmlDrill_v1` for the Q&A drill marks) |
| NLP | `nlpPrepStatus_v1` |
| LangChain | `lcPrepStatus_v1` |
| LangGraph | `lgPrepStatus_v1` |

A subject's tracker is shared between its individual part files and its `Complete` edition in the
same browser, so marking a topic done in one shows up in the other.

**Progress is per-device.** The tracker writes to each browser's local storage, so phone and laptop
track separately — there is no cross-device sync (that would need a backend).

## Regenerating a combined file

After editing any part, rebuild that subject's stitched `Complete` file:

```bash
cd python    && python3 stitch_py.py   # Python       (12 parts)
cd rag       && python3 stitch.py      # RAG          (6 parts)
cd cml       && python3 stitch_cml.py  # Classical ML (17 parts)
cd nlp       && python3 stitch_nlp.py  # NLP          (7 parts)
cd langchain && python3 stitch_lc.py   # LangChain    (6 parts)
cd langgraph && python3 stitch_lg.py   # LangGraph    (12 parts)
```

Each subject is generated from a Markdown blueprint in `rag_learning/` (one level per `##` heading,
one tracker row per `- [ ]` checkbox), so the tracker can always be regenerated from the blueprint
with that subject's `build_*.py`. Where a subject has an `insert.py`, that is the tool that splices a
content fragment into a shell at the `<!--CONTENT_INSERT-->` marker and validates tag balance and
anchors before writing.

## Adding a new subject

1. Create a folder, e.g. `mlops/`, and put its pages inside with an `mlops/index.html` landing page.
2. Copy an existing subject's `build_*.py` / `stitch_*.py` pair and point them at the new blueprint;
   give the new subject **its own localStorage key** so its tracker can't collide with the others.
3. Add a card for it on the hub `index.html` (copy a `.card.soon` block, point its `href` at
   `mlops/index.html`, and switch the badge to `Live`).
4. Add it to the tables at the top of this README.

That's it — no other wiring. Keeping each subject self-contained means they never interfere
