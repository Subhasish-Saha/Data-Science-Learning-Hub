Part 6 of 12 · Tools & Agent Capabilities

The interface between the model and the world Tool definition and binding, designing a schema and docstring the model can actually use, error handling that lets the agent recover, tool selection under a large catalogue, sandboxing destructive operations, the Model Context Protocol, and LangChain's middleware layer.

Tool design is a prompt-engineering problem wearing an API-design costume, and this is where most real agent failures actually live — not in the graph. Three ideas carry the part. A tool's docstring and schema are prompt: the model chooses tools by reading them, so an ambiguous description is a bug in the model's decision-making. Errors should be returned to the model, not raised, because an agent that receives “invalid date format, expected YYYY-MM-DD” can fix itself, while an exception just ends the run. And too many tools degrades selection — past roughly 15–20 the model starts confusing them, which is what tool retrieval and namespacing exist to fix.

6.1 What a tool is ⭐

A tool is three things at once: a Python function, a JSON schema sent to the model, and a piece of prompt. Most tool bugs come from forgetting the third.

What the model receives is the name, the docstring, and the argument schema with its field descriptions. It never sees the body. So the function body determines what happens; the name, docstring and schema determine whether and how it gets called — and those are the parts you tune when tool selection goes wrong.

Binding and the ToolNode

model.bind_tools([...]) attaches the schemas to the model so it can emit tool calls. ToolNode (or create_agent) is what executes them: it reads tool_calls off the last message, runs each one — in parallel when there are several — and appends a ToolMessage per call id. Binding without executing gives you a model that proposes tool calls nobody runs, which is a surprisingly common first bug.

Likely interview questions
CoreWhat does the model actually see when you give it a tool?

Three things: the name, the docstring (the description), and the JSON schema of the arguments including every field description. It never sees the implementation.

The consequence that matters: those three artefacts are prompt. If the model calls the wrong tool, or passes a badly-formed argument, the fix is almost never in the function body — it's in the name, the description, or the schema. And they cost tokens on every single request, which is why a catalogue of 60 tools is both a selection problem and a cost problem.

CodingWhat's the difference between binding tools and executing them?

bind_tools attaches schemas to the model so its responses may contain tool_calls. Execution is separate: something has to read those calls, run the matching functions, and append a ToolMessage for each tool_call_id. In LangGraph that's ToolNode, or it's handled for you inside create_agent.

Two details worth adding: a single response can contain several tool calls, and ToolNode runs them concurrently; and every tool call must get a matching ToolMessage before the next model call, or the provider rejects the request as malformed.

6.2 Designing a tool the LLM can use ⭐⭐

This is where real agent quality is won or lost — far more than in the graph. A tool designed for a human developer is usually a bad tool for a model.

PrincipleBadGood
Name says the actionprocess_datasearch_customer_orders
Description says when, not just what“Searches orders.”“Find a customer's past orders by email or id. Use before answering questions about order history or refunds.”
Say when not to use it—“Do not use for shipment tracking — use track_shipment.”
Closed value setsstatus: strstatus: Literal["open","shipped","cancelled"]
Few, flat argumentsOne nested config object2–4 scalar arguments
Return text the model can read{"c":1,"d":[...]}Formatted lines with labels and ids
Return “nothing found” explicitly[]“No orders found for that email in the last 12 months.”

Granularity: the most consequential choice

Too coarse — one database_query(sql) tool — and you've delegated the hard part to the model and opened a large safety hole. Too fine — forty single-purpose tools — and selection degrades and your prompt is mostly schemas. The useful heuristic: one tool per user-meaningful action, with the parameters a human would need to specify. get_order(order_id), search_orders(email, status), refund_order(order_id, amount, reason) — not one orders(op, payload) and not fifteen variants of get.

The test that catches most bad tools

Show the tool's name, description and schema — and nothing else — to a competent colleague who doesn't know the codebase, and ask them when they'd call it and with what. If they hesitate, the model will too. That five-minute test finds more agent bugs than any amount of prompt tuning.

Likely interview questions
Very commonWhat makes a good tool for an LLM?

Start with the framing: the tool's interface is prompt, so design it for a reader who has no other context.

Concretely: a name that states the action; a description that says when to use it and when not to, naming the alternative tool; closed types (Literal/enum) wherever the value set is finite; few, flat, scalar arguments rather than one nested config object; a return value formatted for reading, with ids so the model can cite or chain; and an explicit empty result — “no orders found for that email” rather than [], because an empty list gives the model nothing to reason about and it tends to retry.

Then the test: hand a colleague only the name, description and schema and ask when they'd call it. Their hesitation predicts the model's.

DesignHow granular should tools be?

One tool per user-meaningful action, with the arguments a person would naturally specify.

Too coarse — a single execute_sql(query) — pushes the hard part onto the model, makes failures opaque, and hands it an enormous capability surface. Too fine — forty near-identical tools — degrades selection accuracy and fills the prompt with schemas you pay for on every call.

The signals: if the model regularly needs three calls to do one obvious thing, your tools are too fine; if one tool's arguments encode a mini-language (op, payload, mode), it's too coarse. And prefer splitting by risk as well as by function — a read tool and a write tool should be separate even if they hit the same table, so you can gate one and not the other.

DebugThe agent keeps passing a malformed argument. How do you fix it?

Fix it in the schema, not the prompt. In order: use a Literal or enum if the value set is closed — the model then literally cannot emit anything else under constrained decoding. Add format instructions in the field description (“ISO date, YYYY-MM-DD”) since the description is what it reads. Add numeric constraints (ge/le). Give a default so the model can omit it.

And make the failure recoverable: return a corrective error string from the tool — “invalid date '03/04/2026'; expected YYYY-MM-DD” — rather than raising. The model reads that and retries correctly, which turns a hard failure into a self-healing one.

6.3 Tool errors and retries ⭐

The default instinct — raise on failure — is usually wrong for an agent. An exception ends the run; a well-worded error message lets the model fix itself.

Retries multiply

Three retries inside the tool, times three at the node's RetryPolicy, times an agent loop that tries the tool again after seeing the error, is 27 calls to a struggling dependency — the classic accidental self-DDoS. Pick one layer to own transient retries, use exponential backoff with jitter, and make the other layers pass through.

Likely interview questions
Very commonShould a tool raise an exception or return an error message?

Depends on who can fix it, and that framing is the answer.

Return a message when the model can act on it: bad arguments, no results, ambiguous input. “Invalid date '03/04/2026'; expected YYYY-MM-DD” lets the agent self-correct on the next iteration, turning a failure into a recoverable step. Retry inside the tool for transient infrastructure errors — 429s, timeouts — with backoff and jitter, because the model can't do anything useful with a rate limit. Raise for genuine infrastructure failures you want the node's RetryPolicy or your alerting to handle, and for permanent errors like invalid credentials where retrying is pointless and harmful.

Never return a raw stack trace: it wastes tokens, leaks internals, and gives the model nothing actionable.

System designHow do you stop retries from amplifying?

Decide one owner per failure class and make the other layers transparent. Typically: transient network errors are owned by the tool (3 attempts, exponential backoff with jitter); node-level RetryPolicy is reserved for errors the tool deliberately raised; and the agent loop is bounded so it can't keep re-calling a broken tool indefinitely.

On top of that: a circuit breaker per dependency, so after N consecutive failures the tool returns “this service is currently unavailable” immediately instead of waiting on timeouts; a global timeout for the whole run; and metrics on retry counts per tool, because silent retry amplification shows up as latency long before it shows up as errors.

CodingHow do you configure retries on a node?

builder.add_node("fetch", fetch, retry_policy=RetryPolicy(max_attempts=3)), optionally with a retry_on predicate so you only retry the exception types that are actually transient — retrying a ValueError from your own validation just wastes time.

Two things to say alongside it: retries re-execute the node, so the idempotency requirement from durable execution applies here too; and a node-level retry doesn't help with a model that's making a bad decision — it only helps with flaky infrastructure. Confusing the two leads to retrying your way around a prompt problem.

6.4 Tool choice and too many tools ⭐

Selection accuracy degrades as the catalogue grows, and the degradation is driven more by similarity between tools than by raw count.

InteractiveTool-catalogue selection simulator

An illustrative model, not a benchmark: accuracy falls with catalogue size and falls much faster when descriptions overlap. Tool retrieval fixes both problems at once by only ever showing the model a small, relevant subset — at the cost of a retrieval step that can itself miss the right tool.

What to do as the catalogue grows

Merge tools that overlap — two tools the model confuses are usually one tool with a parameter. Namespace by domain so names disambiguate (github_create_issue vs jira_create_issue). Route first: a cheap classifier picks a domain, and the agent for that domain sees only its own tools. Tool retrieval: embed the tool descriptions and bind only the top-k relevant to this request. And tool_choice when you need to force behaviour — "auto", "any" (must call something), "none", or a named tool.

Likely interview questions
Very commonYour agent has 50 tools and picks the wrong one. What do you do?

First, note the real cause: degradation is driven more by similarity between tools than by count. Fifty clearly-distinct tools work better than twelve that overlap.

Then, in order of effort: merge overlapping tools — the ones being confused are usually one tool with a parameter. Sharpen descriptions with explicit “use this when… do NOT use this for X, use y_tool” lines. Namespace by domain so names disambiguate. Route first — a cheap classifier picks a domain and the sub-agent for that domain sees only its 6 tools, which also cuts prompt cost. Tool retrieval — embed descriptions, bind only the top-k for this request.

And mention the cost angle: 50 schemas is a fixed per-request token bill before any conversation history, so shrinking the visible set helps latency and cost as well as accuracy.

CodingWhat is tool_choice and when would you set it?

It forces the model's tool-calling behaviour: "auto" (default — call one if useful), "any"/"required" (must call some tool), "none" (must answer in text), or a specific tool name.

Uses: forcing a specific tool on the first step of a pipeline where retrieval is mandatory; "any" when the model keeps answering from parametric knowledge instead of looking things up; "none" for a final synthesis turn where you want prose, not another tool call.

The caution: forcing a call when none is appropriate produces a fabricated call with invented arguments, because the model must emit something. Use it for a specific step, not as a global setting.

DesignHow does tool retrieval work, and what's the risk?

Embed each tool's name and description; at request time, embed the user's query (or the current state) and retrieve the top-k most similar tools; bind only those to the model for this call. The catalogue can then be arbitrarily large while the model only ever sees, say, eight schemas.

The risk is that you've added a retrieval failure mode in front of a selection failure mode: if the right tool isn't in the top-k, the model can't call it and will confidently do something else instead. Mitigations: always include a small set of always-on tools (search, clarify, finish); use a generous k; retrieve on the current step's intent rather than only the original question, since what the agent needs changes mid-run; and log retrieval misses so you can see the failure rather than infer it from bad answers.

6.5 Dangerous tools and sandboxing ⭐

The model will eventually try something you didn't anticipate — through confusion, or because someone engineered the input to make it. Your defence has to be structural, not persuasive.

LayerMechanismDefeated by
1 · CapabilityRead-only credentials; no delete grant at allNothing — the ability doesn't exist
2 · ValidationParse and allow-list the request in the toolA gap in your parser
3 · Approvalinterrupt before the actionApproval fatigue
4 · SandboxContainer with no network, tight timeout, quotasEscape vulnerabilities (rare, real)
5 · Prompt“Never delete anything”Any sufficiently unusual input

Read that table top-down: security lives at layer 1, and the prompt at layer 5 is a UX improvement that reduces how often you exercise the real controls. A candidate who answers “how do you stop the agent dropping a table” with “I'd tell it not to” has failed the question; the answer is “the credentials it runs under cannot drop tables”.

Likely interview questions
System designHow do you give an agent database access safely?

Capability first. The agent connects with a role that has SELECT on specific views and nothing else — no write, no DDL, no access to other schemas. That makes “drop the table” impossible rather than discouraged.

Then defence in depth: parse the SQL with a real parser (not a regex) and reject anything that isn't a SELECT; allow-list tables; wrap the query with a LIMIT and a statement timeout; expose views rather than base tables so column-level exposure is deliberate; and log every query with the thread and user for audit.

Better still where it fits: don't hand it raw SQL at all. Offer parameterised tools — get_orders(customer_id, since) — so the query shapes are ones you wrote. Raw SQL is a last resort for genuinely open-ended analytics, and then only against a read replica.

Very commonHow do you prevent an agent from doing something destructive?

Layered, and explicitly not in the prompt. 1. Capability — don't grant the permission; the agent's credentials should make the destructive action impossible. 2. Validation — inside the tool, parse and allow-list what's being asked. 3. Approval — an interrupt before any irreversible action, with the proposed action shown to a human. 4. Sandbox — for code execution, an ephemeral container with no network, a CPU/memory quota and a hard timeout. 5. Reversibility — prefer soft deletes, staged changes and undo paths so a mistake is recoverable.

The prompt is layer 5 in importance: useful for reducing how often you hit the other controls, worthless as a control itself, because any instruction in the context can be overridden by other content in the context.

DesignThe agent needs to run arbitrary user code. How?

In an isolated, ephemeral sandbox, never in your process. Concretely: a container or micro-VM per execution, no network egress by default, read-only filesystem except one scratch directory, CPU/memory limits, a hard wall-clock timeout, no credentials or environment variables from the host, and destruction after the run.

Then bound the blast radius further: cap output size (a program printing 500 MB will otherwise take out your logging), rate-limit executions per thread, and log the code alongside the run for audit. Use a managed code-execution service if one is available — this is a category where rolling your own isolation is a poor use of risk budget.

Worth saying plainly: “we sanitise the code with a prompt” is not an answer. Isolation is the control.

6.6 MCP — the Model Context Protocol ⭐

MCP standardises how tools are exposed to models, the way LSP standardised how language features are exposed to editors. It is the clearest example of an integration layer that actually settled.

The problem it solves

Without a standard, connecting m agent frameworks to n tool providers is m × n bespoke integrations. With a protocol it's m + n: each framework implements a client once, each provider implements a server once. An MCP server exposes tools (callable functions), resources (readable context) and prompts (reusable templates) over stdio for local processes or HTTP/SSE for remote ones.

A third-party MCP server is code you're trusting

Its tool descriptions go straight into your prompt — a malicious or compromised server can inject instructions there. Its tools run with whatever access you granted. And a server can change its tool set between connections. Treat MCP servers like dependencies: pin them, review them, run untrusted ones sandboxed with least privilege, and don't wire an unvetted server into an agent that holds real credentials.

Likely interview questions
ModernWhat is MCP and why does it matter?

The Model Context Protocol — an open standard for how applications expose tools, resources and prompt templates to LLM clients. Analogy that lands: it's LSP for tools. Before LSP, every editor needed a bespoke integration with every language; after it, each side implements the protocol once.

The value is turning an m × n integration problem into m + n. A vendor writes one MCP server and it works with any MCP-capable agent; a framework writes one client and gets the whole server ecosystem. It runs over stdio for local processes and HTTP/SSE for remote ones.

In LangGraph you consume it with langchain-mcp-adapters, which turns MCP tools into ordinary LangChain tools — so from the graph's perspective nothing is special about them. And as of 2026 it's the clearest case of a layer that actually standardised, which is worth saying because most agent protocols haven't.

DesignWhat are the security implications of using third-party MCP servers?

Three, and they're specific. Prompt injection via tool descriptions: the server controls text that goes directly into your model's context, so a malicious server can inject instructions. Capability grants: its tools execute with whatever access you gave the process — a filesystem server pointed at / is a filesystem server with root's reach. Mutable tool sets: a server can present different tools on a later connection, so what you reviewed isn't necessarily what runs.

Controls: treat servers as dependencies — pin versions, review the source, prefer first-party or well-known ones; run them sandboxed with least privilege (scoped directories, scoped tokens, no ambient credentials); consider pinning or reviewing the tool list at startup and alerting on change; and keep destructive MCP tools behind the same approval gates you'd apply to your own.

ConceptualWould you build your internal tools as MCP servers?

Sometimes. Yes when the tools have multiple consumers — several agents, an IDE assistant, a desktop client — because then you get the m + n benefit and a single place to maintain the interface. Yes when a team wants to own and version its tool surface independently of the agent teams.

No when there's exactly one consumer: a plain @tool function in the same repo is simpler, faster (no transport hop), easier to test, and easier to debug. Adding a protocol boundary to a single-consumer integration is architecture for its own sake.

The useful rule: MCP is for crossing an ownership boundary. If there's no boundary, don't manufacture one.

6.7 The middleware layer

LangChain 1.x middleware is a composable place to put the cross-cutting behaviour that used to be copy-pasted into every agent: trimming, guardrails, retries, approval, logging.

HookRunsTypical use
before_modelBefore each model callTrim or summarise history, inject retrieved memories
after_modelAfter the responseGuardrails, PII redaction, logging, cost accounting
before_tool / after_toolAround tool executionApproval gates, argument validation, result truncation
wrap_model_callAround the callModel fallback, retries, per-request model selection

Middleware matters because these concerns are the same in every agent you'll build, and because they're the concerns most likely to be forgotten. Prebuilt pieces cover the common cases — summarisation, human-in-the-loop, PII redaction — and a custom middleware is a small class implementing the hooks you need. The mental model: create_agent is the loop; middleware is everything you'd otherwise wrap around it.

Likely interview questions
ModernWhat is agent middleware, and what did it replace?

A composable hook layer around the agent loop in LangChain 1.x — before_model, after_model, before_tool, after_tool, and wrap_model_call — where cross-cutting behaviour lives.

It replaces two older approaches: callbacks, which could observe but not easily modify the flow, and copy-pasted wrapper code, where every team reimplemented history trimming, guardrails and retry logic slightly differently. The wins are that these concerns become reusable and testable in isolation, and that the list of middleware attached to an agent is a readable summary of its non-functional behaviour.

DesignMiddleware or a custom graph node?

Middleware for concerns that are cross-cutting and apply on every iteration of the loop: trimming history before each model call, redacting PII from every response, enforcing a token budget, falling back to another model on error, gating every tool call of a certain class. These would otherwise appear in a dozen places.

A node for anything that is a step in the domain logic — retrieve, classify, draft, validate — because it belongs in the graph where it's visible, individually checkpointed, and can be routed around.

The test: would it appear in the flowchart you'd draw for a colleague? If yes, it's a node. If it's the kind of thing you'd mention in a footnote about how the system behaves, it's middleware.
