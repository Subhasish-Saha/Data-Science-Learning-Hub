Level 5 · Tools & Agent Capabilities

Giving the agent hands

An agent without tools is a chatbot. Tool design is most of the quality — the docstring is literally the prompt that drives selection — and the modern API (create_agent) hides the ReAct loop you should still be able to hand-write.

3.1 Defining tools — the docstring is the prompt

The model never sees your implementation. It sees the tool's name, description (the docstring), and argument schema — and picks from those alone. Vague docstrings are the #1 cause of wrong tool selection.

  • Prefer few, well-scoped tools over many overlapping ones — overlap is what makes the model dither.
  • Say what the tool is not for; negative guidance disambiguates better than more adjectives.
  • Return strings or JSON-serialisable objects, and keep outputs small — every tool result re-enters the context window.

3.2 Wiring the ReAct loop by hand

Build this once yourself. It's six lines, it demystifies every prebuilt agent, and interviewers ask you to draw it.

3.3 create_agent — the current API

The same loop, prebuilt. Note the deprecation: create_react_agent from langgraph.prebuilt still runs but emits LangGraphDeprecatedSinceV10. The current entry point lives in langchain.agents.

create_agent's headline addition is a middleware system: composable hooks that run before/after the model call and before/after tool execution — for logging, guardrails, retries, and summarization — without rewriting the graph.

When asked how you'd add summarization, guardrails, retries, or logging to an existing agent, the current answer is middleware — composable hooks around the model and tool calls — not "I'd restructure the graph." Naming the built-ins (summarization, model-retry, moderation) shows you're on 1.1+ rather than quoting 1.0 docs.

3.4 Advanced tool topics

Five things that separate a demo agent from one that survives real traffic.

  • Parallel tool calls — a model can emit several calls at once; ToolNode executes them concurrently. Big latency win for independent lookups.
  • Tool errors — never let an exception crash the graph. Return a ToolMessage describing the failure so the model can read it and retry or change approach.
  • InjectedState / InjectedStore — pass graph state or the Store into a tool without exposing it to the LLM (it won't appear in the tool schema the model sees).
  • Tool-call review — gate sensitive tools behind HITL (Part 2 §2.11): interrupt before execution and let a human approve the arguments.
  • Structured output vs tool calling — use structured output when you want data in a shape; use tools when you want an action performed.

3.5 Model Context Protocol (MCP)

An open standard (from Anthropic) for connecting models to tools and data sources — replacing the bespoke wrapper you'd otherwise write per integration.

Likely interview questions
ToolsHow does the model decide which tool to call, and how do you improve that?

It sees only the tool name, description/docstring, and argument schema — never your implementation — and selects via the provider's function-calling mechanism. Improve it by: writing precise docstrings that state both what the tool is for and what it isn't; using typed Pydantic schemas with per-field descriptions; keeping the toolset small and non-overlapping (overlap causes dithering); giving tools distinct, unambiguous names; and few-shot examples in the system prompt for tricky cases. If selection is still wrong, that's a prompt-engineering problem in the docstring, not a model problem.

ToolsA tool throws an exception. What should happen?

It should become a ToolMessage the model can read — not an unhandled crash. Catch the exception inside the tool (or configure ToolNode's error handling) and return a clear, actionable message: what failed, and whether retrying is sensible. The model then adapts — retries with different args, tries another tool, or reports the failure to the user. Crashing the graph loses the whole run; a readable error keeps the agent's recovery loop intact. Guard against infinite retry with an attempt counter.

ModernWhat is MCP and why does it matter?

Model Context Protocol — an open, provider-neutral standard (originating at Anthropic) for exposing tools and data sources to LLM applications over a client–server interface. Your agent is the client; services like a filesystem, Postgres, Slack, or Drive run MCP servers. It matters because it kills the N×M integration problem: instead of writing a bespoke wrapper per tool per framework, any MCP-speaking client can use any MCP server. Transports are stdio (local) and HTTP/SSE (remote); langchain-mcp-adapters converts MCP tools into LangChain tools, and LangGraph can also expose an agent as an MCP server.

Level 6 · RAG and Advanced RAG

The RAG ladder, built as graphs

Retrieval is the most common agent capability, and its variants are a graded interview ladder: naive → agentic → corrective → self-reflective. Each rung adds one node to the graph — which is exactly how to explain them.

Deep on retrieval itself? The RAG subject covers chunking, hybrid search, rerankers, and evaluation in full. Here we focus on how each variant is wired in LangGraph.

3.6 Baseline RAG

Six stages: Load → Split → Embed → Store → Retrieve → Generate. The first four are offline; the last two run per query.

  • Loaders: PyPDFLoader, WebBaseLoader, DirectoryLoader
  • Splitting: RecursiveCharacterTextSplitter — chunk size and overlap both matter
  • Vector stores: FAISS (local), Chroma, Pinecone, pgvector
  • Retriever config: k, MMR, metadata filtering, score thresholds

3.7 RAG as a step vs RAG as a tool = Agentic RAG

One design decision separates naive RAG from agentic RAG: is retrieval a fixed pipeline stage, or a tool the model chooses to call?

3.8 Corrective RAG (CRAG)

Adds one node — a grader after retrieval — that asks "do these documents actually answer the question?" and takes corrective action when they don't.

3.9 Self-RAG

Where CRAG grades the retrieval, Self-RAG grades the generation — twice: is it grounded in the context, and does it actually answer the question?

3.10 The full RAG ladder

Interviewers ask you to "explain the ladder." Here it is as one table — each rung adds a specific node and solves a specific failure.

RungWhat it addsFailure it fixes
Naive RAGRetrieve → generate, always— (baseline; ungrounded LLM)

Also worth naming: HyDE (embed a hypothetical answer), parent-document / small-to-big, reranking with a cross-encoder, hybrid search (BM25 + dense), GraphRAG, and contextual retrieval — all covered in depth in the RAG subject.

3.11 Interview focus

Likely interview questions
RAG ⭐Naive RAG vs Agentic RAG vs CRAG vs Self-RAG — explain the ladder.

Naive: every query goes retrieve → generate. Simple, but it retrieves for "hi", can't choose a source, and generates from bad chunks. Agentic: the retriever becomes a tool, so the model decides whether to retrieve, which source (docs / SQL / web), and can retrieve repeatedly — it's the ReAct loop. CRAG: adds a grader after retrieval that scores document relevance and triggers a correction (query rewrite or web search) when they're insufficient. Self-RAG: adds reflection after generation — one grader for groundedness (are claims supported by context?) and one for answer relevance — regenerating or re-retrieving on failure. Each rung adds a node and costs latency, so climb only as far as your failure modes require, and bound every retry loop.

DebuggingYour RAG system returns confident wrong answers. Debug it.

Localise before fixing. First, log and read the retrieved chunks for the failing queries: if the right chunk isn't there, it's a retrieval bug (chunking too big/small, embedding truncation, missing exact-term matching → add hybrid search); if it is there, the bug moved to generation. For generation, check the prompt actually instructs "answer only from context" and that temperature is low. Then add the structural fixes: a CRAG-style relevance grader so bad retrievals don't reach the generator, a groundedness check (Self-RAG) so unsupported claims are caught, and an abstention path so the system says "I don't know" instead of inventing. Finally, measure — faithfulness and context-relevance metrics on a fixed eval set — so you know the fix worked.

DesignWhy wrap a retriever as a tool instead of making it a graph step?

Because retrieval isn't always the right move. As a fixed step, every query pays retrieval latency and cost — including greetings and pure-reasoning questions — and the pipeline can only ever consult one source, once. As a tool, the model decides if to retrieve, which source to use (PDF retriever vs SQL vs web), and can retrieve again after reading the first results (multi-hop). The cost is non-determinism: the model might skip retrieval when it shouldn't, so you evaluate tool-choice accuracy as part of trajectory eval (Part 4).
