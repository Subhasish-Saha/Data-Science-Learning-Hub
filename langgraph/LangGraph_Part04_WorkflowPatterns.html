Part 4 of 12 · Workflow Patterns

The six shapes almost every system is made of Prompt chaining, parallelisation (sectioning and voting), routing, orchestrator-worker, evaluator-optimizer loops, and the agent loop — each with the LangGraph construct that implements it and the failure mode that kills it.

Anthropic's Building Effective Agents put names to a small set of shapes, and interviewers now use those names as shared vocabulary — so being able to say “that's an orchestrator-worker with an evaluator gate” is worth a surprising amount. The section that matters most is the last one: choosing. Every pattern here trades determinism for flexibility, and the senior move is to pick the least flexible pattern that solves the problem, because determinism is what makes a system testable, debuggable and cheap. An evaluator-optimizer loop with no iteration cap is the most common way to turn a working demo into a runaway bill.

4.1 Prompt chaining

The simplest pattern: decompose a task into a fixed sequence of calls, where each step's output feeds the next. Boring, deterministic, and correct far more often than people expect.

Why splitting one prompt into three helps

A single prompt asking the model to research, outline, draft and edit does all four badly, because attention is split and there's no point at which any one sub-task gets the model's full effort. Chaining gives each step a focused instruction and a clean context. It also gives you something a monolithic prompt can't: a place to put a gate. Between step 2 and step 3 you can validate, filter, retry that step alone, or stop early — none of which is possible inside one generation.

Likely interview questions
ConceptualWhy split one prompt into a chain of three?

Three reasons. Focus: each call gets one job and a clean context, which measurably improves quality over a prompt that asks for four things at once. Gates: you can validate, filter or branch between steps — impossible inside a single generation. Observability and cost control: you can see which step failed, retry only that step, and use a cheap model for the mechanical steps and an expensive one for the hard step.

The cost: more round trips, so higher latency. If quality is already fine with one call, chaining is over-engineering — the pattern earns its keep when a step needs to be checked or when different steps want different models.

DesignWhere would you put a gate in a chain, and what should it check?

Immediately after any step whose failure would waste the remaining steps or produce a confidently wrong result. The check should be deterministic wherever possible — schema validation, a length or format check, a regex, “did retrieval return anything at all” — because a deterministic gate is free, instant and testable.

Use an LLM gate only for judgements that genuinely need one (relevance, tone, factual grounding), and when you do, use with_structured_output so the gate returns a typed verdict rather than prose. And give the gate an escape: retry the failed step at most k times, then either continue with a flag or fail cleanly — never loop unbounded.

4.2 Parallelisation ⭐

Two distinct patterns share this name, and conflating them is a common slip. Sectioning splits a task into independent parts; voting runs the same task several times and aggregates.

SectioningVoting
What runs in parallelDifferent sub-tasksThe same task, repeated
WhyLatency — n steps in one step's timeReliability — reduce variance
AggregationConcatenate / synthesiseMajority vote, best-of-n, or a judge
CostSame total tokens, less wall-clockn× the tokens for one answer
ExampleResearch six companies at onceThree independent safety checks; any flag blocks

Sectioning is nearly always worth it when the parts are independent — you're spending the same tokens in less time. Voting is a deliberate purchase of reliability with money: three-way self-consistency on a hard classification is a real accuracy gain, and it costs exactly 3×. Use it where the error is expensive, not everywhere.

“Independent” has to be true

Sectioning only works if the sections genuinely don't depend on each other. If section 3 needs section 1's finding, running them in parallel produces a section 3 written in ignorance — which reads fine and is wrong. Where there are dependencies, use waves: parallelise within a wave, sequence between waves.

Likely interview questions
ConceptualWhat are the two kinds of parallelisation?

Sectioning — split a task into independent sub-tasks and run them concurrently, then synthesise. You buy latency: the same total tokens in roughly one step's wall-clock. Voting — run the same task several times (different temperatures, prompts or models) and aggregate by majority, best-of-n, or a judge. You buy reliability, and you pay n× the tokens for one answer.

Both are implemented the same way in LangGraph — a fan-out into one superstep with a reducer on the shared channel — but they're chosen for opposite reasons, and mixing up which one you're doing leads to paying 3× for a latency win you didn't get.

System designWhen is voting worth 3× the cost?

When the cost of an error clearly exceeds the cost of two extra calls, and the errors are at least partly independent. Good cases: safety and moderation checks where a false negative is serious and you take the union of flags; a high-stakes classification feeding an irreversible action; extraction from a noisy document where you can take the modal value per field.

Bad cases: creative generation, where there's no ground truth to vote on; anything where the model's errors are systematic, since three runs of the same model with the same blind spot vote unanimously for the same wrong answer — which is why diversity (different prompts or different models) matters more than raw repetition. And always compare against the cheaper alternative: one call to a stronger model is often better than three to a weak one.

CodingHow do you implement each in LangGraph?

Sectioning with known parts: several add_edge("plan", worker) calls, so all workers activate in the same superstep. Sectioning with dynamic parts: a conditional edge returning [Send("worker", {...}) for ...]. Voting: fan out to the same node n times with Send, varying a seed or prompt in the payload.

In all three cases the result channel needs a reducer — Annotated[list, operator.add] — and a downstream node performs the aggregation. Two production notes: make the workers async or the parallelism is only notional, and cap the fan-out width so a runaway plan can't launch hundreds of concurrent calls into a rate limit.

4.3 Routing ⭐

Classify the input, send it to a specialist handler. It is the highest value-per-unit-complexity pattern in the whole catalogue, and it is very often the correct answer to a question that sounded like it needed an agent.

Why routing beats one big prompt

A single prompt that must handle billing, technical support and account changes carries instructions for all three, most of which are irrelevant to any given request — that's wasted context and diluted attention. Routing gives each branch a focused prompt, its own tools, and its own model tier. Billing questions can go to a cheap model with the pricing table; technical escalations to a strong model with the diagnostics tools. You also get per-branch metrics, which is what lets you find out that one category is quietly performing badly.

Always have a fallback branch

Two things will happen in production: an input that fits none of your categories, and a low-confidence classification. Both need a general handler — never let the router pick the nearest wrong specialist. Returning a confidence score alongside the label, and routing below a threshold to the fallback, costs nothing and prevents the worst routing failures.

Likely interview questions
DesignHow do you build a reliable router?

Five things. Structured output with a Literal so the model can't invent a category. A confidence score in the same schema, with a threshold below which you route to a general fallback. An explicit fallback branch for inputs that fit nothing. A cheap fast model — classification is easy and the router is on every request's critical path. And a labelled dataset, because a router is a classifier and you should be able to state its accuracy and see its confusion matrix.

The last point is what separates a real answer from a plausible one: routing is the one agentic pattern that's trivially evaluable, so there's no excuse for not measuring it.

DebugYour router sends 30% of requests to the wrong branch. What do you do?

Get the confusion matrix first — “30% wrong” is uninformative; “billing is being misread as account 80% of the time” tells you what to fix. Then, in order: are the categories genuinely distinguishable? Frequently two categories overlap semantically and the fix is to merge them or add a disambiguating question rather than to tune the prompt. Are the category descriptions in the schema clear, with examples of edge cases? Would few-shot examples of the confusable pairs help? Is the model too small for the distinctions you're asking for?

And check the cheap structural fix: if two categories route to handlers that behave almost identically, the misclassification may not matter — measure the downstream impact before optimising the classifier.

ConceptualRouter or agent — how do you tell which a problem needs?

Ask whether one decision is enough. If the input can be classified and handed to a handler that completes the job, it's a router: one call, bounded, testable, cheap. If choosing the right handler itself requires looking things up — check the customer's plan, then their ticket history, then whether the bug is known — and the number and order of lookups depends on what you find, then the control flow is dynamic and you need a tool-calling loop.

The practical test: can you draw the complete decision tree? If yes, build the tree. If the tree's depth depends on runtime data, build the agent.

4.4 Orchestrator-worker ⭐

A planner decides what needs doing and dispatches workers to do it. The distinguishing feature versus plain parallelisation is that the number and nature of the subtasks is decided at runtime.

The three failure modes are worth memorising because they're what an interviewer probes: the orchestrator produces too many subtasks (cap the width); the subtasks overlap, so you pay three times for the same research and the synthesiser has to dedupe; and the subtasks don't cover the question, which no amount of good worker output can fix. All three are prompt-and-validation problems at the orchestrator, not worker problems.

Likely interview questions
ConceptualHow is orchestrator-worker different from parallelisation?

In parallelisation the branches are fixed at design time — you wrote three edges to three nodes. In orchestrator-worker an LLM decides at runtime how many subtasks there are and what they are, and identical workers are dispatched dynamically with Send.

That's a real difference in kind, not degree: it means the graph's shape depends on the input, you can't enumerate the execution paths, and you now own new failure modes — too many subtasks, overlapping subtasks, and subtasks that don't cover the question. Parallelisation has none of those, which is why you should prefer it when the decomposition is knowable.

DebugYour orchestrator generates overlapping subtasks and you're paying three times for the same work. Fix it.

Attack it at the orchestrator, in this order. Constrain the schema: make it return a list of subtasks with an explicit instruction that they must be non-overlapping and collectively exhaustive, and require a one-line scope per subtask so overlap is visible. Cap the count in the schema (max_length) and in code. Add a validation node between plan and dispatch that dedupes near-identical subtasks — cheap string or embedding similarity is usually enough. Cache at the tool layer, so even if two workers issue the same search, you pay once.

And measure it: log the number of workers and the total cost per request, because “the orchestrator got chatty” is a regression that's invisible without that metric.

System designDesign a document-generation system with this pattern.

Orchestrator: one call with structured output producing sections: list[{title, brief, target_words}], capped at say 12. Validate: dedupe overlapping sections, check total length against the target. Dispatch: conditional edge returning one Send("write_section", s) per section, so all sections write concurrently in a single superstep. Collect: each worker returns {"sections": [{"idx": i, "text": ...}]} into an operator.add channel — note the index, because concurrent write order isn't guaranteed and you need to restore document order. Synthesise: sort by index, then a final pass for transitions and consistent voice.

Extras that show production thinking: a checkpointer so a 12-section document survives a crash without regenerating everything; an interrupt after the outline so a human can approve the structure before you spend twelve calls on it; and per-worker error capture so one failed section doesn't lose the other eleven.

4.5 Evaluator-optimizer loops ⭐

Generate, evaluate, revise, repeat. The most powerful pattern here and the one most likely to produce a runaway bill, because its natural termination condition is “when the critic is happy” and the critic may never be.

The four guards

GuardImplementationPrevents
Hard iteration capCounter in state, checked first in the routerInfinite loops
Score thresholdStructured critic returning a numeric scoreEndless polishing of adequate work
Keep the best draftbest_draft/best_score channelsReturning a worse round-4 draft than round-2
Improvement floorStop if score gain < εPaying for cosmetic rewrites

The best version of this pattern gives the evaluator something objective to look at: unit test results, a linter, a schema validation, a retrieval check against sources. Code generation is the canonical fit precisely because “the tests pass” is a real signal, not an opinion. When the evaluator is just the same model asked whether it likes the output, expect much smaller gains — see §2.5.

InteractivePattern cost & latency simulator

Latency assumes perfect concurrency where the pattern allows it; cost counts every call regardless. Note how orchestrator-worker and evaluator-optimizer cost roughly the same but differ enormously in wall-clock — the fan-out spends its calls simultaneously, the loop spends them in sequence.

Likely interview questions
DesignHow do you stop an evaluator-optimizer loop from running forever?

Four guards, and you want all of them. A hard iteration cap in state, checked before the quality condition in the routing function. A score threshold so “good enough” is a defined number from a structured critic, not a vibe. Keep the best draft in its own channel and return that rather than the last one, because quality genuinely degrades on over-revision. An improvement floor: stop when the score gain between rounds is below ε, since you're paying for cosmetic edits at that point.

Plus recursion_limit on the config as a backstop — but treat hitting it as a bug, not a design.

ConceptualWhat makes a good evaluator?

Access to something the generator didn't have. Test results, compiler output, a schema validation error, retrieved sources to check claims against — objective signals produce real improvements. An evaluator that is the same model re-reading the same context with “is this good?” shares the generator's blind spots and mostly produces hedging.

Beyond that: explicit checkable criteria rather than a global quality judgement; structured output so you get a numeric score and a list of specific issues, not prose; and the issues fed back into the generator's prompt so the revision is targeted. If you can make the evaluator a tool call rather than a judgement — run the tests, validate the JSON — do that instead.

GotchaYour loop's output gets worse after round two. What's happening?

Over-revision. A critic asked to find issues will always find issues, so each round the generator makes changes that address increasingly marginal critiques, often damaging things that were fine. Text gets hedged and bloated; code accumulates defensive branches.

Three fixes: track and return the best-scoring draft, not the final one — this alone makes degradation harmless; give the critic an explicit “accept” option and a rubric where a good draft genuinely scores well, rather than a prompt that implies something must be wrong; and stop on marginal improvement. Two rounds is usually the sweet spot, and it's worth measuring rather than assuming.

4.6 The agent loop as a pattern

Listed last among the patterns deliberately: the agent loop is the most flexible shape and therefore the one you reach for when the others don't fit — not first.

As a pattern it is simply: model decides → tool executes → observation returns → repeat until no tool call. What distinguishes it from everything above is that the sequence and count of steps are not in your code. The other six patterns all have a shape you drew; this one's shape is drawn at runtime by the model.

In LangGraph it's two nodes and one conditional edge, or one line with create_agent. The engineering is not in building the loop — it's in the bounds you put around it: iteration cap, budget cap, tool gates, and a trace you can read afterwards.

Patterns compose

Real systems are rarely one pattern. A production research system is typically router → orchestrator-worker → evaluator gate → agent loop for the one branch that genuinely needs open-ended tool use. Recognising the composition — and keeping the agentic part as small as possible — is the design skill being tested.

Likely interview questions
DesignCan you mix patterns in one system?

You almost always should — real systems are compositions. A representative shape: a router classifies the request; simple categories go to a single call; one category goes to an orchestrator-worker fan-out for parallel research; its output passes an evaluator gate; and only the genuinely open-ended branch runs an agent loop.

The principle is to keep the agentic part as small as possible. Every request that can be answered by a deterministic branch should be, so the expensive, unpredictable path handles only the cases that need it. That's also what makes the system evaluable: you can measure the router's accuracy, the workers' coverage, and the agent branch separately.

ConceptualWhere does the engineering effort go in an agent loop?

Not into the loop — that's two nodes and an edge, or one create_agent call. It goes into the bounds and the surroundings: tool design (descriptions, schemas, error strings the model can recover from), the iteration and budget caps, approval gates on destructive tools, context management as history grows, and tracing good enough to reconstruct why the model chose what it chose.

A candidate who describes building the loop is describing the easy 10%. A candidate who describes the caps, the gates, the tool ergonomics and the trace is describing the part that determines whether it works in production.

4.7 Choosing a pattern ⭐⭐

The section that actually gets tested. Given a scenario, name the pattern and justify it in two sentences — and be willing to name the simplest one.

ScenarioPatternThe one-line justification
Classify and hand off support ticketsRouterOne bounded decision; testable against labels
Translate, then localise, then check toneChainFixed sequence, each step needs a focused prompt
Summarise 40 documentsParallel sectioningIndependent work; buy latency at the same token cost
Moderate content for four policy typesVoting / parallel checksErrors are expensive; take the union of flags
Write a report whose sections depend on the topicOrchestrator-workerDecomposition isn't knowable until you see the topic
Generate code that must pass testsEvaluator-optimizerThere's an objective signal to iterate against
Debug a production incident from logs and metricsAgent loopEach finding changes what to look at next
Extract five fields from an invoiceSingle callStructured output; no orchestration needed at all
The selection heuristic, in one question

Can you draw the control flow before the program runs? If yes → chain, router, parallel or orchestrator-worker, in ascending order of how late the shape is decided. If no → an agent loop, kept as small as you can make it. Everything else is detail.

Likely interview questions
System design“Summarise these 40 documents into one brief.” What's your design?

Parallel sectioning with a reduce — map-reduce, essentially. Fan out one summariser per document with Send, each writing into an operator.add channel, then a synthesis node produces the brief. Latency is roughly one summarisation plus one synthesis rather than 40 sequential calls.

The details that show experience: cap concurrency (batch in waves of ~10) because 40 simultaneous calls will hit a rate limit; if 40 summaries don't fit the synthesiser's context, add a hierarchical reduce — summarise groups of 8, then summarise the summaries; keep document ids alongside each summary so the brief can cite sources; and attach a checkpointer, so a failure at document 37 doesn't discard 36 completed summaries.

System design“Our support bot should handle refunds.” Which pattern?

A router into a small tool-calling agent, with an approval gate on the refund itself.

Concretely: classify the request; the refund branch runs an agent with read-only tools (order lookup, policy retrieval, prior refunds) so it can gather what it needs in a dynamic number of steps; the refund tool itself is behind an interrupt that surfaces the proposed amount and reason to a human — or auto-approves below a threshold under an explicit policy.

What earns the point: recognising that the investigation is genuinely agentic (you don't know in advance how many lookups it takes) while the action must be gated, and that the gate is enforced in the tool layer rather than by prompting the model to be careful.

ConceptualWhat's your default when you're unsure?

The simplest pattern that could work, plus measurement. Start with a single call or a router, build a small golden dataset, measure, and only add structure where the data shows a specific failure. Complexity added speculatively is complexity you'll never be able to justify removing.

This matters as an interview answer because the failure mode being tested is over-engineering. “I'd start with one call and see where it breaks” is a stronger answer than a multi-agent architecture diagram — and if the interviewer wants the complex design, they'll push, at which point you can produce it.
