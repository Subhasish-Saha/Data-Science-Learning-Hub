Level 3 · Workflow Patterns

Four shapes, endlessly recombined

Every agentic system is these four patterns glued together: sequential, parallel, conditional, and iterative — plus deferred nodes as the synchronisation trick. Build each twice: once with a non-LLM toy so you see the mechanics, once with an LLM.

2.1 Sequential (prompt chaining)

A linear graph where each node enriches state. The simplest pattern, and the right default whenever the steps are known.

Practice ladder: a BMI calculator with no LLM at all (so you see pure state mechanics) → an outline generator → a blog writer that chains outline → draft → polish.

2.2 Parallel (fan-out / fan-in)

Multiple independent nodes in one superstep. This is where reducers stop being theory — parallel branches must return partial updates into a reduced key.

Drop the Annotated[..., operator.add] and this graph raises InvalidUpdateError the moment two evaluators finish in the same superstep — the single most common beginner failure.

2.3 Conditional (branching)

A router function plus add_conditional_edges. The trick that makes it reliable: force the classification into a closed set with Literal in a Pydantic schema.

Practice: a quadratic solver branching on the discriminant (no LLM — pure mechanics), then a customer-review bot routing on sentiment with an extra diagnosis sub-step for negative reviews.

2.4 Iterative (cycles)

Loop back to an earlier node instead of hitting END. This is what makes LangGraph a graph rather than a chain — and it's where runaway agents come from if you don't bound it.

The canonical shape is evaluator–optimizer: generate → critique → regenerate until the critic passes. Always bound the loop with a counter in state, and know the framework-level backstop:

Common pitfall · the counter you forgot to increment

A cycle whose counter is read but never incremented (or is stored on a key that gets overwritten) loops until GraphRecursionError — burning tokens the whole way. recursion_limit is a safety net, not a design: it stops the process but gives you no partial answer and no graceful degradation. Bound the loop semantically and keep the limit.

2.5 Deferred nodes (synchronisation barriers)

A subtle but interview-worthy primitive: defer=True makes a node wait until all upstream paths complete — solving parallel branches of unequal length.

Likely interview questions
MechanicsHow do you prevent an infinite loop in a cyclic graph?

Two independent guards. Semantic: keep an iteration counter in state, increment it in the loop body, and have the router exit at a max (plus an exit on success). Framework: recursion_limit (default 25) raises GraphRecursionError past N supersteps — a safety net, not a design. Also give the loop a meaningful stop condition (a critic that can actually pass) and return the best-so-far result on exhaustion rather than failing hard.

MechanicsWhat is a deferred node and what problem does it solve?

A node declared with defer=True runs only after all upstream paths reach it, instead of firing when the first one arrives. It solves parallel branches of unequal length: without it, an aggregator downstream of a 1-hop branch and a 3-hop branch executes early on partial data. It's the clean way to build a synchronisation barrier for map-reduce fan-in, consensus voting, or multi-agent collaboration.

Level 4 · State, Persistence & Memory

Where junior and senior candidates separate

Persistence is what turns a script into a product: conversations that survive a restart, agents you can pause for human approval, runs you can rewind and debug. It also contains the single most reliable discriminator question in LangGraph interviews — checkpointer vs Store.

2.6 Checkpointers — short-term, thread-scoped memory

A checkpointer snapshots the entire state after every superstep. That one mechanism gives you conversation memory, crash recovery, time travel, and human-in-the-loop — they're all the same feature.

  • thread_id isolates conversations — User A's memory never bleeds into User B's.
  • Dev → InMemorySaver. Prod → SqliteSaver or PostgresSaver (async variants: AsyncSqliteSaver, AsyncPostgresSaver).
  • No checkpointer = no memory, no HITL, no time travel. No thread_id = the checkpointer silently does nothing useful.

2.7 Inspecting state & time travel

Because every superstep is a checkpoint, you can read the state at any point, edit it, rewind to a past checkpoint, and fork a different branch from there. This is the debugging superpower for non-deterministic agents.

Primary use is debugging: an agent took a bad turn at step 7, so you rewind to step 6, change one value, and replay to see whether your fix actually helps — without re-running the expensive earlier steps.

2.8 The Store — long-term, cross-thread memory ⭐

The classic interview discriminator. A checkpointer gives within-thread memory keyed by thread_id; a Store gives cross-thread memory keyed by namespace (usually user_id). Confusing them is the most common telling mistake.

2.9 The long-term memory pipeline

Having a Store isn't having memory — you need a pipeline that decides what is worth remembering, and gets it back into the prompt at the right moment.

2.10 Context window management

Conversations grow; context windows don't. Three strategies, and interviewers like to hear you compare them rather than name one.

StrategyToken efficiencyContext lossComplexity
Trimming (trim_messages)HighHigh — drops old turns wholesaleLow
Deletion (RemoveMessage)ModerateTargeted — you choose what goesLow–Med
SummarizationHighLow — meaning preservedMed–High

start_on/end_on matter more than they look: cutting between an assistant tool-call and its ToolMessage leaves an orphaned call that many providers reject outright.

2.11 Human-in-the-loop

Pause the graph, show a human the pending action, resume with their decision. The modern mechanism is interrupt() — and it only works because checkpointing already gives you durable pause/resume.

2.12 Interview focus — the Level-4 checkpoint

You should be able to explain the difference between a checkpointer and a store in one sentence each, without hesitating. Here are the questions this level generates.

Likely interview questions
Trap ⭐Checkpointer vs Store — what's the difference?

A checkpointer persists the graph's state after every superstep, scoped to a thread_id — it's within-conversation memory, and it's what enables resume, time travel, and HITL. A Store is a separate key-value (optionally vector-indexed) service scoped to a namespace, usually user_id — it's cross-conversation memory. Rule of thumb: "what happened in this chat?" → checkpointer; "what do I know about this user?" → Store. User preferences go in the Store, because thread state dies with the thread. You typically compile with both.

StateHow does thread_id work, and what breaks without it?

thread_id (passed in config["configurable"]) is the key the checkpointer stores state under — it partitions conversations so User A's history never leaks into User B's, and so a returning user resumes their own thread. Without it the checkpointer has nothing to key on: you effectively get no useful memory, every invocation looks like a fresh conversation, and HITL/time travel can't target a run. It fails silently, which is what makes it a good interview question.

StateHow would you manage a conversation that exceeds the context window?

Three strategies with different trade-offs. Trimming (trim_messages) keeps the last N tokens — cheapest, but loses old context wholesale; mind start_on/end_on so you don't orphan a tool call. Deletion (RemoveMessage with the add_messages reducer) surgically drops specific messages — targeted, needs real message ids. Summarization folds old turns into a running summary — best meaning-per-token, but costs an extra LLM call and can drift. In production I'd summarize older history and keep recent turns verbatim, plus push durable facts into the Store so they survive independently of the transcript.

HITLinterrupt() vs interrupt_before — which and why?

interrupt() is dynamic: called inside a node, it can pause conditionally (only for high-value orders, say), and it passes a payload to the human describing what's pending. interrupt_before=["node"] is static, decided at compile time, and always pauses before that node. Prefer interrupt() for production approval gates — conditional pausing and a structured payload — and use interrupt_before for debugging or blanket gates. Both require a checkpointer, and you resume both with Command(resume=…).

DebuggingWhat is time travel and when have you used it?

Because every superstep is checkpointed, you can list history with get_state_history(), replay from any past checkpoint_id, or fork — patch state at a past checkpoint and run a different branch forward. The main use is debugging non-deterministic agents: rather than re-running an expensive 10-step trajectory hoping to reproduce a bug, you rewind to the step before it went wrong, change one value, and replay. It's also how you A/B two prompts from an identical mid-run state.
