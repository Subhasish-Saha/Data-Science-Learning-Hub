Why LangGraph exists at all State as a typed channel set, checkpointers and what a checkpoint contains, threads and thread_id, time travel, interrupt-based human-in-the-loop, context-window management, the cross-thread Store, and durable execution across crashes.

If you had to justify LangGraph over a plain while loop in one sentence, it would be this part. Persistence is the feature — a checkpointer turns an agent from a function call into a resumable process, and everything valuable follows: human-in-the-loop approval that can wait three days, crash recovery that resumes mid-graph rather than restarting, and time travel for debugging. The distinction interviewers probe hardest is checkpointer versus store: the checkpointer is within-thread execution state, the store is cross-thread long-term memory, and conflating them is the tell that someone has only done tutorials.

5.1 What state actually is ⭐

Three different things get called “memory” in agent systems, and interviewers separate candidates by whether they keep them distinct.

A fourth thing sometimes gets called memory too — the context window, i.e. what you actually send to the model on this call. It is not a storage layer at all; it's a selection from the layers above. Keeping that distinction is what makes §5.6 make sense.

Likely interview questions
Very commonExplain the difference between state, checkpointer and store.

State is the live set of channel values during an invocation — messages, retrieved docs, counters. Without a checkpointer it exists only in memory for the duration of the call.

The checkpointer persists a snapshot of state per superstep, per thread. Its scope is one conversation, keyed by thread_id. It's what gives you resume, human-in-the-loop, crash recovery and time travel.

The store is cross-thread long-term memory: namespaced key-value (often with semantic search) holding user preferences, learned facts and profile data that should be available in every future conversation. You read and write it explicitly from nodes.

The sentence that settles it: the checkpointer remembers this conversation; the store remembers this user.

Gotcha“My agent doesn't remember what the user told it last week.” Diagnose.

Almost certainly a layer confusion: they're relying on the checkpointer, which is per-thread. Last week's conversation is a different thread_id, so its state is intact but invisible to this one.

The fix is a store: during (or after) a conversation, extract durable facts and write them to a namespace like ("memories", user_id); at the start of each run, retrieve relevant memories and inject them into the prompt. Two design points to add: extraction should be selective — writing every utterance to the store gives you a slow, noisy retrieval problem — and you need a policy for updating or invalidating facts, because “the user's favourite airline is X” can stop being true.

The alternative non-answer worth ruling out: reusing one thread_id forever so all history is in one thread. That technically works and then fails, because the thread grows without bound and every turn re-sends more history.

5.2 Checkpointers ⭐⭐

The checkpointer is the feature. Everything that makes LangGraph worth using over a loop is downstream of one design decision: state is written to durable storage at every superstep barrier.

What a checkpoint contains

FieldWhat it holdsWhy it's needed
Channel valuesEvery state channel at this barrierThe data itself
nextWhich node(s) run nextResuming needs the program counter, not just the data
Pending writesWrites from nodes that completed before a failureSo a partial superstep doesn't re-run completed work
MetadataStep number, source, parent checkpoint idTime travel and forking
Tasks / interruptsAny active interrupt payloadKnowing what the graph is waiting for

The field people forget is next. A checkpoint is not just a data snapshot — it's a resumable continuation, which is why you can restore it in a different process next week and the graph picks up mid-flow rather than at the start.

ImplementationUseNotes
InMemorySaverTests, notebooksLost on restart — never production
SqliteSaver / AsyncSqliteSaverLocal apps, single-processReal persistence, no server; poor concurrency
PostgresSaver / AsyncPostgresSaverProduction defaultCall .setup() once to create tables; connection-pool it
Redis / customLatency-sensitive or bespokeImplement BaseCheckpointSaver
Checkpoints are a data-retention surface

Everything in state is written to your database at every superstep — including whatever the user pasted into the chat and whatever a tool returned. That means PII, secrets and tool payloads are now persisted, subject to your retention policy and any deletion requests. Two consequences: never put credentials in state, and have an actual TTL/deletion story for old threads before you ship.

Likely interview questions
Very commonWhat does a checkpointer actually do, and what does a checkpoint contain?

It persists a snapshot of the graph's state at every superstep barrier, keyed by thread_id and checkpoint id.

A checkpoint contains: all channel values; the next field saying which nodes run next; any pending writes from nodes that completed before a failure; metadata including the step number and parent checkpoint id; and any active interrupt. The next field is the one candidates forget and it's the important one — a checkpoint is a resumable continuation, not just a data dump, which is why you can restore it in a different process days later.

What it unlocks, all from the same mechanism: pause/resume, human-in-the-loop, crash recovery, time travel, and forking a conversation from any past point.

System designWhich checkpointer would you use in production, and what do you watch?

Postgres — AsyncPostgresSaver in an async service — because you need durability, concurrent access from multiple app instances, and operational tooling you already have. Call .setup() once at deploy to create the tables, and put it behind a connection pool.

What to watch: write volume, since it's one write per superstep per run and a chatty graph multiplies that; state size, because large objects in channels are re-serialised every superstep — keep blobs external and store references; growth and retention, so you need a TTL or archival job for old threads, plus a deletion path for data-subject requests; and latency, since the checkpoint write is on the critical path of every superstep.

SQLite is fine for a local or single-process app; InMemorySaver is for tests only.

GotchaWhat happens if you compile a graph with no checkpointer?

It runs perfectly well — and silently loses every capability that depends on persistence. No thread memory (each invoke starts fresh, so a chatbot has no history), no interrupt/resume (calling interrupt raises), no get_state or get_state_history, no crash recovery, no time travel.

The reason it's a gotcha is that nothing warns you: a stateless one-shot pipeline is a legitimate use, so LangGraph can't treat the absence as an error. If you're building a conversational or long-running graph and it “doesn't remember”, the missing checkpointer and the missing thread_id are the first two things to check.

5.3 Threads and thread_id ⭐

A thread is a conversation. The thread_id is the key that ties a sequence of invocations to a shared, persisted history — and getting it wrong produces two opposite, equally confusing bugs.

MistakeSymptomFix
New thread_id every requestAmnesia — no history at allDerive it from the conversation, not the request
One thread_id per user, foreverContext bloat, cost growth, topic bleedOne thread per conversation; use the store for durable facts
Reusing a thread_id across usersCross-user data leakNamespace it: f"{tenant}:{user}:{conv}"
Guessable idsAnother user can read a threadOpaque UUIDs, plus an authorisation check server-side
Likely interview questions
CoreWhat is a thread, and where does thread_id come from?

A thread is one conversation — the sequence of checkpoints sharing a thread_id. Passing the same id in config["configurable"] across invocations makes them continue the same state; passing a different one starts fresh.

It comes from your application's model of a conversation, not from the framework: the chat session id, the ticket id, the workflow instance id. The rule is one thread per conversation — not per request (amnesia) and not per user forever (unbounded growth).

Production detail: namespace it, e.g. f"{tenant_id}:{user_id}:{conversation_id}", and treat it as a capability — always verify server-side that the authenticated user owns the thread they're asking for, because a thread id is a key to someone's conversation history.

System designHow do you handle multi-tenancy with threads?

Three layers, and you want all three. Namespaced ids so a thread key encodes the tenant. Authorisation on every request — resolve the tenant from the authenticated session, never from a client-supplied field, and check ownership before invoking. Storage isolation proportionate to the requirement: a tenant column with row-level security for most cases, separate schemas or databases where contractual isolation is required.

Also worth naming: per-tenant rate and cost limits so one tenant can't exhaust shared capacity, and per-tenant retention/deletion, because “delete this customer's data” must reach the checkpoint tables, not just your application tables.

DebugTwo users are seeing each other's messages. What happened?

They're sharing a thread_id. The usual causes: a hardcoded id left over from development ("thread_id": "1" in a demo that shipped); an id derived from something non-unique like a session name or a date; or the id coming from a client-supplied parameter with no server-side ownership check, which is the security version of the bug.

Fix immediately by deriving the id server-side from the authenticated user plus a conversation identifier, and add an authorisation check before every invoke. Then treat it as an incident: the checkpoint tables now contain cross-contaminated history that has to be found and purged.

5.4 Time travel and state editing

Because every superstep is checkpointed, you can rewind to any past point, change the state there, and run forward again — creating a branch rather than destroying history.

Three practical uses. Debugging: reproduce a failure by replaying from the checkpoint just before it, as many times as you like. What-if analysis: change one field and see how the run differs. Correction in production: an agent picked a wrong branch — rewind, fix the state, continue, without losing the work before the mistake. Note that update_state writes a new checkpoint whose parent is the one you targeted, so the original path remains in the history.

Replay is not a simulation

Replaying from a checkpoint re-executes the nodes, which means real LLM calls, real tool calls, real side effects. Time travel is not a dry run. If a node in the replayed range sends an email, replaying sends the email again — which is the same idempotency requirement durable execution imposes, arriving from a different direction.

Likely interview questions
ConceptualWhat is time travel and what's it for?

Because every superstep writes a checkpoint, get_state_history() gives you the full sequence, and you can resume from any of them by passing that checkpoint's config back into invoke. update_state lets you modify the state at that point first, which creates a fork — a new checkpoint whose parent is the one you targeted — leaving the original branch intact.

Three uses: debugging (replay deterministically from just before a failure, repeatedly); what-if analysis (change one field, compare outcomes); and production correction (an agent took a wrong turn — rewind, fix, continue, keeping everything it got right).

The caveat to volunteer: replay re-executes nodes for real — real model calls, real side effects. It's not a simulation.

CodingHow do you edit an agent's state mid-run?

graph.update_state(config, {"channel": value}). The update goes through each channel's reducer, which matters: on an add_messages channel, passing a message with an existing id replaces it, and passing a RemoveMessage deletes it, whereas a fresh message appends. You can also pass as_node="some_node" to make the update look as though that node produced it, which controls what the graph considers to run next.

The main use in practice is human-in-the-loop editing — a reviewer corrects a drafted tool call or removes a bad message before resuming. Do it through update_state, never by writing to the checkpoint store directly.

5.5 Human-in-the-loop ⭐⭐

The single most valuable production capability LangGraph offers. An agent that can pause mid-execution, wait indefinitely for a human, and then continue exactly where it stopped.

The node re-runs from the top on resume

interrupt() works by raising; on resume, LangGraph re-executes the whole node and the interrupt() call returns the resume value instead of raising. So anything before the interrupt in that function runs twice. Keep interrupt nodes tiny — do the expensive or side-effecting work in a separate node after the gate, never above the interrupt call.

The four HITL shapes

Approve/reject a proposed action. Edit — return a modified payload, e.g. a corrected tool argument or a reduced refund amount. Provide input — the agent asks a clarifying question and waits. Review and continue — a checkpoint for oversight where the human usually just says “proceed”. All four are the same mechanism with a different payload contract.

Likely interview questions
Very commonHow does human-in-the-loop work in LangGraph?

A node calls interrupt(payload). That raises a special exception which LangGraph catches: it checkpoints the state with next pointing at this node and surfaces the payload to the caller. The invocation returns — no process, connection or memory is held, so the graph can wait indefinitely.

Later, possibly days later and in a different process, you invoke the same thread_id with Command(resume=decision). LangGraph restores the checkpoint, re-runs that node, and this time interrupt() returns the decision instead of raising, so execution continues.

The gotcha to volunteer: because the node re-runs from the top, keep interrupt nodes small and put side effects after the gate. And it requires a checkpointer — interrupt without one raises.

System designDesign an approval gate for a refund agent.

Graph: investigate (read-only tools) → propose refund → approve node with interrupt → execute refund → notify. Policy: auto-approve under a threshold (say £20) with an audit record; interrupt between £20 and £500; require a second approver above that.

Payload: everything the human needs to decide without opening another system — amount, customer, order, reason, the agent's evidence, and prior refunds for this customer. Resume contract: {"approved": bool, "amount": optional, "note": str}, so a reviewer can approve a reduced amount rather than only yes/no.

Operations: the pending thread goes into a review queue with the thread_id; a timeout job auto-rejects after N days and notifies; the refund execution node is idempotent with an idempotency key, because it can be re-run on resume or after a crash; and every decision is written to an audit log with the approver's identity.

Gotchainterrupt() versus interrupt_before — what's the difference?

interrupt_before=["node"] at compile time is a static breakpoint: the graph always stops before that node, regardless of state. It's a debugging and inspection tool, and it can't carry a payload.

interrupt(payload) inside a node is dynamic: it fires only when your code decides to call it (so you can gate on the refund amount), and it carries a structured payload to the human and receives a structured decision back via Command(resume=...).

For product features — approval, editing, clarifying questions — use dynamic interrupt. Use interrupt_before for debugging and for coarse “always let a human see this stage” checkpoints.

DesignHow do you handle a human who never responds?

Treat the pending interrupt as a queue item with a deadline, because LangGraph itself will wait forever — that's the design. Concretely: when you interrupt, write a row (thread id, action, payload, created_at, assignee) to a review queue; run a scheduled job that finds items past their SLA and either escalates to another approver, sends a reminder, or resumes the thread with a default decision — usually reject, since the safe default for an irreversible action is not to do it.

Also expose the queue to operators, and make the timeout policy per-action rather than global: a £5 refund can auto-approve after a day, a £5,000 one should never auto-approve.

5.6 Short-term memory and the context window ⭐

The message list grows without bound; the context window does not. Every long conversation eventually needs a policy, and there are only four of them.

InteractiveContext strategy comparator

Four policies on the same conversation. “Fits” is about the window; “recall” is a rough measure of how much of the early conversation is still reachable. Summarisation is the only strategy that keeps both — at the cost of an extra LLM call and lossy compression.

The four policies

PolicyMechanismLoses
Do nothingSend everythingNothing — until it overflows or the bill does
Trimtrim_messages keeping the last k tokensThe beginning of the conversation, entirely
Summarise + recentSummarise old turns, keep the last k verbatimDetail, but not the thread of the conversation
RAG over historyEmbed past turns, retrieve the relevant onesContinuity — retrieval is by relevance, not recency

Two mechanical points that matter when you implement any of these. First, never break the tool-call pairing: if you trim away an assistant message containing a tool call but keep its ToolMessage (or vice versa), most providers reject the request outright. trim_messages has options for this — use them. Second, always keep the system message, which is why every trimming helper has an explicit flag for it.

Likely interview questions
Very commonA conversation exceeds the context window. What do you do?

Four options, in increasing sophistication. Trim to the last k tokens with trim_messages — free and instant, but the beginning is simply gone. Summarise + recent: when history exceeds a threshold, summarise the older turns into a single system-level message and keep the last k verbatim; one extra LLM call, and it preserves the thread of the conversation. RAG over history: embed past turns and retrieve the relevant ones — good for very long histories where relevance beats recency, but it loses continuity. Structured extraction: pull durable facts out into a store and drop the raw turns.

The production default is summary + last k, often combined with a store for facts that must persist across conversations. And two implementation traps: keep the system message, and never split a tool call from its ToolMessage — providers reject that outright.

CodingHow do you actually delete messages from state?

Return a RemoveMessage(id=...) for each message you want gone — the add_messages reducer understands it and removes the matching message. A summarisation node typically returns a list of RemoveMessage for the old turns plus one new summary message, all in a single update.

You can't do it by returning a shorter list, because add_messages appends; returning fewer messages adds nothing and removes nothing. And doing it by mutating state["messages"] in place is the bug from §3.3 — it bypasses the reducer and the checkpointer.

GotchaYour provider starts rejecting requests after you added trimming. Why?

You've almost certainly orphaned a tool call. Providers require that an assistant message containing tool_calls is followed by a ToolMessage for each call id, and a naive “keep the last 10 messages” window can cut between them — leaving either a tool call with no result or a result with no call. Both are protocol violations and produce a 400, not a degraded answer.

Fix by trimming on conversation boundaries rather than message counts: trim_messages supports start_on="human" and include_system=True for exactly this. The same rule applies to summarisation — summarise whole exchanges, not arbitrary message ranges.

5.7 Long-term memory and the Store ⭐⭐

The store is what makes an agent feel like it knows you. It is also where most teams over-build: writing everything, retrieving noise, and never invalidating anything.

What to store, and what not to

TypeExampleWorth storing?
Stable preferences“prefers metric units”, “works in EU timezone”Yes — high value, rarely changes
Profile factsRole, team, systems they ownYes — but needs an update path
Past outcomes“this fix worked for their setup”Yes, with a timestamp
Every utteranceRaw conversation logsNo — that's a search index, not memory
Volatile facts“is currently on call”No — fetch live, don't remember
Memory that is never invalidated becomes a liability

“The user's manager is Alice” is true until it isn't, and a confidently-retrieved stale fact is worse than no memory, because the agent asserts it. Every memory needs a timestamp, a way to be superseded (write the new fact and mark the old one inactive, don't silently accumulate both), and ideally a source so a human can adjudicate a contradiction.

Likely interview questions
Very commonWhat is the Store and how does it differ from the checkpointer?

The store is cross-thread, long-lived memory: a namespaced key-value store, usually with vector search over the values, that you read and write explicitly from nodes. Namespaces scope it — ("memories", user_id), ("policies", org_id).

The checkpointer is within-thread and automatic: it snapshots the whole graph state every superstep so one conversation can be resumed. The store is cross-thread and manual: nothing goes into it unless a node decides to put it there.

The clean summary: checkpointer = this conversation, automatic, whole state. Store = this user, deliberate, selected facts. They're complementary, and you'll normally compile with both.

System designDesign memory for an assistant used daily for a year.

Three tiers. Working memory: the message list in state, trimmed to a summary plus the last k turns. Episodic: per-conversation summaries written to the store at the end of each thread, so “what did we decide last Tuesday?” is answerable. Semantic: extracted durable facts and preferences in ("memories", user_id) with embeddings for retrieval.

Write path: a background extraction step at conversation end, not on every message — cheaper and less noisy. Deduplicate against existing memories before writing, and when a new fact contradicts an old one, supersede rather than append. Read path: retrieve top-k relevant memories at the start of a run and inject them into the system prompt, with a hard cap on how many tokens memory may consume.

Governance: timestamps and sources on every memory, a TTL for classes of fact that go stale, a user-visible “what do you remember about me” view, and deletion that actually reaches the store. That last point is usually what distinguishes a designed system from a demo.

GotchaWhat goes wrong when you store too much?

Retrieval quality collapses. If every utterance is a memory, top-k retrieval returns five vaguely-related fragments instead of the one fact that mattered, and the model is now reasoning over noise. You also pay for embedding and storing content that will never be useful, and you accumulate contradictions — three versions of the user's job title, all retrievable, none marked current.

The principle: memory is a curated summary, not a log. If you want full history search, build a search index over transcripts and expose it as a tool; keep the memory store small, high-signal and maintained.

5.8 Durability and crash recovery ⭐

Durable execution means a run survives the process that started it. It is the reason agents can take hours — and it imposes one hard requirement on your code.

durability modeWhen state is persistedTrade
"exit"Only when the run finishes or interruptsFastest; a crash loses the whole run
"async"Written concurrently with the next superstepGood default — near-full safety, little latency cost
"sync"Committed before the next superstep startsStrongest guarantee; a write on the critical path

The hard requirement: idempotency

Because a superstep can be re-executed after a crash, any node with a side effect must be safe to run twice. This is not an operational nicety — it is a structural consequence of the durability model, and it changes how you write nodes: side-effecting work goes in its own small node, carries an idempotency key derived from something stable in state (not a random UUID generated inside the node), and the external system must honour that key.

Likely interview questions
Very commonWhat happens if the process dies mid-run?

With a checkpointer, the last completed superstep is durable. On restart you invoke the same thread_id with None as input, and LangGraph restores that checkpoint — including next and any pending writes from nodes that had completed within the failed superstep — and continues. You lose at most one superstep of work, not the run.

Then state the requirement that falls out of it: the nodes in that superstep re-execute, so any side effect must be idempotent. And name the durability setting: "async" is the sensible default, "sync" when losing a superstep is unacceptable, "exit" only for throwaway runs.

System designHow do you make a node that sends an email safe under durable execution?

Three layers. Isolate it — the send goes in its own node with nothing else in it, so the re-run surface is as small as possible. Idempotency key — derive it deterministically from state (f"notify-{order_id}-{stage}"), never from a UUID generated inside the node, and pass it to the provider so a duplicate send is deduplicated on their side. Record the result in state — write the message id back, and check for it at the top of the node so a re-run short-circuits.

If the provider has no idempotency support, keep your own sent-log table keyed by that same deterministic key and check it transactionally. And where the action is expensive or irreversible, put an interrupt in front of it as well — belt and braces.

ConceptualWhich durability mode would you pick, and why?

"async" as the default: the checkpoint write happens concurrently with the next superstep, so you get near-full crash protection without putting a database round trip on the critical path of every step.

"sync" when losing even one superstep is unacceptable — a node performed an external side effect and the record of it must be committed before anything else runs. "exit" only for short, cheap, side-effect-free runs where restarting from scratch is genuinely fine; it's the fastest but a crash discards everything.

The trade in one line: you're choosing how much work you're willing to redo against how much latency you'll pay per superstep.
