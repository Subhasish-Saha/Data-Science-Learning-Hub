1.1 The Python you actually need

LangGraph is a small library sitting on top of a few Python features you may have skimmed. Four of them are load-bearing, and every one of them shows up in an interview as “walk me through this code”.

The four that matter

FeatureWhere it shows up in LangGraphIf you don't know it
TypedDictThe default state schema — class State(TypedDict)You can't read any graph definition
Annotated[T, meta]Attaches a reducer to a channelReducers look like magic syntax
Decorators@tool, @task, @entrypointYou can't explain what @tool generates
async/awaitainvoke, astream, parallel node executionYour “parallel” graph runs serially

Generators and streaming

Every graph.stream(...) call returns a generator, not a list. That is why you write for chunk in graph.stream(...) and why nothing executes until you start iterating. The async form, astream, is an async generator consumed with async for. If you have never written a generator, streaming will feel arbitrary; if you have, it's obvious that a partially-consumed stream means a partially-executed graph.

The one-line summary of a node

A node is a function that takes the whole state and returns a partial update. Not the new state — a dict of the channels it wants to change. Everything else in LangGraph follows from that sentence.

Likely interview questions
ConceptualWhat does a LangGraph node return, and why does that matter?

It returns a partial update — a dict containing only the channels it wants to change — not a whole new state object. LangGraph then merges that update into the state using each channel's reducer. This matters for three reasons: nodes stay small and composable because they don't need to know about channels they don't touch; parallel nodes can each return their own slice and the reducers merge them at the superstep barrier; and a returned key that isn't in the schema is either ignored or raises, depending on the schema type, which is a common silent-bug source.

CodingWhat does Annotated[list[str], add] actually do at runtime?

Annotated is a typing construct that carries arbitrary metadata alongside a type — at runtime the type is still list[str], and the extra argument is retrievable via typing.get_type_hints(..., include_extras=True). LangGraph reads that metadata when it builds the graph and registers add as the channel's reducer. So it's not special syntax — it's ordinary Python metadata that LangGraph inspects. Without it, the channel uses the default reducer, which is overwrite.

GotchaWhy does graph.stream() sometimes appear to do nothing?

Because it returns a generator. Calling it schedules nothing; execution only advances as you iterate. If you write result = graph.stream(inputs) and never loop over result, the graph never runs. Similarly, breaking out of the loop early leaves the graph partially executed — which, with a checkpointer attached, means a persisted half-finished thread you can later resume. That is a feature, but it surprises people.

1.2 Typing, TypedDict and Pydantic ⭐

You have three choices for a state schema. The interview question is not “which is best” — it's “when would you pay for validation, and what does it cost you?”

The rule of thumb

TypedDict for internal state, Pydantic for boundaries. The graph's own state is written by your own nodes, which you control — validation there mostly buys you protection against your own typos, at a per-superstep cost. The places where validation genuinely earns its keep are the boundaries: the input schema of the graph (which may come from an untrusted HTTP request), and tool arguments and structured output, which are generated by an LLM and therefore genuinely untrusted. Many production graphs use a Pydantic input_schema and a TypedDict internal state.

TypedDict is not checked at runtime

TypedDict is a static typing construct. At runtime your state is a plain dict, and returning {"quesiton": "..."} with a typo does not raise — with the default schema handling, an unknown key is rejected by the channel machinery in current versions, but a wrongly typed value for a known key sails straight through. Nothing but mypy or a Pydantic schema will catch {"count": "five"}.

Input, output and private channels

A graph can declare three schemas. StateGraph(State, input_schema=In, output_schema=Out) means callers pass only In, receive only Out, and everything else in State is internal scratch space that never leaves the graph. This is how you keep intermediate reasoning, raw retrieved chunks and tool traces out of the API response — a genuinely useful production pattern and a good thing to mention unprompted.

Likely interview questions
Very commonTypedDict or Pydantic for your state schema — how do you choose?

TypedDict by default; Pydantic at the boundaries. TypedDict is the LangGraph default, is a plain dict at runtime, has zero validation overhead, and makes partial updates natural. Pydantic gives you runtime validation and coercion, but LangGraph validates on every state update, so you pay that cost once per superstep for the life of the run — and it makes checkpoint serialisation heavier.

Where Pydantic clearly wins: the graph's input_schema when input comes from an untrusted caller, and anywhere an LLM produces the data — tool arguments and structured output — because that's genuinely unvalidated input. A common production shape is a Pydantic input schema and a TypedDict internal state.

GotchaDoes TypedDict catch a wrong type at runtime?

No. TypedDict is a static-analysis construct only; at runtime the state is a plain dict. Returning {"count": "five"} from a node where count: int will not raise — it just puts a string in your state and blows up somewhere downstream, far from the cause. The only ways to catch that are a type checker in CI, or a Pydantic state model.

DesignHow do you keep internal scratch data out of the graph's response?

Declare separate schemas: StateGraph(State, input_schema=In, output_schema=Out). The internal State can carry raw retrieved documents, tool traces, scratchpad reasoning and retry counters; the caller only ever supplies In and only ever receives the channels in Out. This matters for API hygiene, for payload size, and for not leaking intermediate reasoning or raw source documents to a client.

ConceptualWhy does state have to be a schema at all — why not just a dict?

Because LangGraph needs to know the channels in advance to do three things: attach a reducer to each one, decide how to merge concurrent writes at a superstep barrier, and serialise the state into a checkpoint. A free-form dict has no reducer attachment point and no stable serialisation contract. The schema is what turns “a dict passed between functions” into “a set of typed channels with merge semantics and persistence” — which is the whole difference between a graph and a chain of function calls.

1.3 Async, concurrency and the event loop ⭐

Agents are almost entirely I/O wait. Async is not an optimisation here — it is the difference between a parallel fan-out that takes 2 seconds and the identical code taking 20.

Why async, specifically

An agent's wall-clock time is dominated by waiting: for the model, for a vector store, for an HTTP tool. That is I/O-bound work, which is exactly what asyncio is for. A single event loop can hold hundreds of in-flight LLM calls, because while one is waiting on the network the loop runs another. Threads would also work, but with far more memory per unit of concurrency; processes are for CPU-bound work, which agents essentially never are.

One blocking call poisons the whole loop

An async def node that calls requests.get(), a synchronous DB driver, or time.sleep() blocks the entire event loop — not just its own task. Every other concurrent node in that superstep stalls behind it. Fixes: use an async client (httpx.AsyncClient, asyncpg), or push the blocking call to a thread with await asyncio.to_thread(fn, ...).

Mixing sync and async in one graph

LangGraph lets you define sync and async nodes in the same graph, but the invocation style decides what happens. Call graph.ainvoke() and sync nodes are run in a thread pool — safe, but each one occupies a thread. Call graph.invoke() on a graph containing async nodes and LangGraph will run an event loop for you, but you lose the concurrency benefit for anything outside the graph. Pick one style and be consistent; production graphs should be async end to end, because that is what lets one process serve many concurrent users.

Likely interview questions
Very commonWhy does async matter so much for agents specifically?

Because an agent is almost entirely I/O wait — LLM calls, vector search, HTTP tools. Under async, one event loop keeps hundreds of those waits in flight simultaneously with almost no per-task memory. Concretely: three 2-second tool calls run sequentially take 6 seconds; awaited concurrently they take 2. Threads would give the same concurrency at much higher memory cost per task, and processes are for CPU-bound work, which agents essentially never are. Async is also what makes one server process able to serve many concurrent conversations.

DebugYour parallel fan-out isn't any faster than the sequential version. What do you check?

In order:

1. Is anything actually parallel? Nodes only run concurrently if they're in the same superstep — multiple edges out of one node, or a Send fan-out. If node B has an edge from A and node C has an edge from B, they're sequential by construction.

2. Are you calling the async entrypoint? invoke on async nodes doesn't get you loop concurrency.

3. Is a node blocking the loop? This is the usual answer — an async def node calling requests, a sync DB driver, or time.sleep. Wrap it in asyncio.to_thread or switch to an async client.

4. Rate limits. If the provider is throttling you, the calls are serialising server-side and no amount of client concurrency helps.

CodingYou must call a synchronous vendor SDK inside an async node. What do you do?

result = await asyncio.to_thread(sdk.call, arg). That runs the blocking function in the default thread pool executor and yields control back to the event loop while it runs, so other tasks keep progressing. Two caveats worth stating: the thread pool is bounded, so a large fan-out of blocking calls will queue; and the SDK must be thread-safe. The better long-term fix is an async client, but to_thread is the correct immediate answer.

1.4 The LLM substrate

Tokens, the context window, temperature, and the mechanics of tool calling. You need these not as trivia but because every agent design constraint traces back to one of them.

The four numbers that constrain every design

QuantityTypical 2026 scaleThe design constraint it creates
Context window200k–1M tokensLong agent runs still overflow it — hence trimming, summarisation, memory
Output token limit4k–64kLong generations must be chunked across nodes
Cost per tokenInput ≪ outputRe-sending history each turn is the dominant cost in a long agent loop
Latency~1–10 s per callAn agent with 8 sequential tool calls is a 30-second experience

Why the agent loop is quadratic in cost

This is the single most useful mechanical fact in the whole subject. On each iteration of an agent loop you re-send the entire message history — because the model is stateless. Turn 1 sends 1 unit, turn 2 sends 2, turn 10 sends 10. Total tokens over n turns is O(n²), not O(n). That is why a 20-step agent costs vastly more than 20× a single call, why prompt caching matters so much, and why message trimming is a cost lever rather than a nicety.

Tool calling is a protocol, not intelligence

Mechanically: you send the model a list of tool schemas (name, description, JSON-schema parameters). If it decides to use one, its response contains a structured tool_call block with a name, an argument object and a call id — it does not execute anything. Your code runs the function and sends the result back as a ToolMessage carrying that same id. The model then continues. Every agent framework, LangGraph included, is a loop around that exchange.

Likely interview questions
Very commonExplain what actually happens when a model “calls a tool”.

The model never executes anything. You pass tool schemas in the request — name, description, JSON-schema parameters. The model's response may contain a structured tool_call: a tool name, an arguments object, and a unique call id. Your runtime parses that, executes the matching function, and appends a ToolMessage containing the result and the same call id back into the message list. Then you call the model again with the extended history and it continues.

Two consequences worth adding: the model chooses tools purely by reading their descriptions and schemas, so those are prompt; and because your code is the executor, all authorisation and safety enforcement lives on your side, never in the model's judgement.

System designWhy does an agent loop cost more than the number of turns suggests?

Because the model is stateless, so every turn re-sends the full accumulated history. Turn 1 sends 1 unit of context, turn 10 sends 10 — total input tokens over n turns is O(n²). A 20-step agent is not 20× a single call, it's closer to 200×.

The levers: prompt caching on the stable prefix (system prompt + tool schemas + early history) typically cuts the charged rate for that prefix by around 90%; message trimming or summarisation to bound history length; a hard iteration cap; and model cascading, using a cheap model for routing and tool-selection steps and a strong one only for synthesis.

ConceptualContext windows are a million tokens now — is memory management still a problem?

Yes, for three reasons that have nothing to do with whether the content fits. Cost: you're billed per token every turn, and a million-token context in a loop is ruinous. Latency: time-to-first-token scales with prompt length. Quality: attention degrades over very long contexts — the “lost in the middle” effect means a relevant fact buried at position 400,000 is often effectively invisible, so a focused 8k context frequently beats an unfocused 500k one. Bigger windows raised the ceiling; they did not remove the incentive to be selective. That selection discipline is what people now call context engineering.

1.5 Structured output ⭐

Half of agent engineering is getting the model to emit something your code can branch on. There are three mechanisms with very different reliability, and knowing which one your provider is actually using is a senior signal.

Three mechanisms, ranked

MechanismHow it worksReliability
Constrained decodingThe sampler is masked so only tokens valid under the schema can be emittedGuaranteed to parse — the grammar makes invalid output unreachable
Tool-calling coercionYour schema is presented as a tool the model must call; arguments are the outputVery high — the provider validates against the schema
Prompt-and-parse“Reply in JSON”, then json.loadsWeakest — markdown fences, prose preambles, trailing commas

In LangChain, model.with_structured_output(Schema) picks the best available mechanism for the provider and returns a validated object. Passing method="json_schema" requests strict constrained decoding where supported.

Field descriptions are prompt, not documentation

The schema — including every Field(description=...) and the class docstring — is serialised into the request and read by the model. A vague description produces vague values. Write them as instructions to the model, not as comments for your teammates, and use Literal rather than str whenever the value set is closed.

The remaining failure mode is semantic, not syntactic: the schema guarantees you get a valid urgency between 1 and 5, but not that it's the right number. Constrained decoding solves parsing; it does not solve judgement. That distinction is worth making explicitly in an interview.

Likely interview questions
Very commonHow do you reliably get JSON out of an LLM?

Three mechanisms, in descending reliability. Constrained decoding — the provider masks the sampler with a grammar derived from your JSON schema, so invalid tokens are literally unreachable and the output is guaranteed to parse. Tool-calling coercion — your schema is presented as a tool the model is forced to call, and the arguments are the output; the provider validates it. Prompt-and-parse — “reply in JSON” plus json.loads, which is the weakest and fails on markdown fences and prose preambles.

Use with_structured_output(Schema), which selects the best mechanism the provider supports. And say the important caveat: none of this guarantees the values are correct, only that they're well-formed.

DesignWhat makes a good Pydantic schema for LLM output?

Treat it as prompt. Concretely: use Literal or an enum for any closed value set so the model can't invent a category; write a Field(description=...) on every field phrased as an instruction; put a docstring on the class explaining the task, because it's serialised too; use numeric constraints (ge/le) rather than hoping; keep it flat and shallow, since deeply nested schemas degrade accuracy; and add a short reason or rationale field before the decision field so the model reasons before committing — field order in the schema is generation order.

GotchaConstrained decoding guarantees valid JSON. What can still go wrong?

Everything semantic. You are guaranteed a syntactically valid object matching the schema; you are not guaranteed the right object. The model can pick a plausible-but-wrong enum value, hallucinate a confident urgency: 5, or fill a required field with a fabricated value precisely because the grammar forbids omitting it. There's also a subtler cost: heavy constraint can degrade quality, since the model is forced down token paths it wouldn't otherwise choose. Validation belongs downstream too — check the values against reality, don't just trust that they parsed.

1.6 The LangChain layer in 2026 ⭐

“What's the difference between LangChain and LangGraph?” is asked in the first five minutes of most interviews. It is a layering question, and the wrong framing — treating them as competitors — is an instant tell.

What changed in the 1.x era

Old (0.x)Current (1.x, 2026)Why
AgentExecutor, initialize_agentcreate_agent from langchainThe old executors were opaque loops with no persistence or interruption
langgraph.prebuilt.create_react_agentcreate_agent (same idea, new home)Consolidated into LangChain 1.x; the LangGraph name is deprecated
Memory classes (ConversationBufferMemory)Checkpointers + the StoreMemory became a runtime concern, not a chain wrapper
Ad-hoc callbacks for behaviour injectionMiddleware around the agent loopA composable place to put trimming, guardrails, retries, HITL
Versions as of this guide

LangGraph 1.2.11 and LangChain 1.3.15 (both released 11 Aug 2026), Python ≥ 3.10. Recent additions worth knowing: trace_policy on add_node for per-node tracing control, and a typed v3 stream_events return with native projections. Don't over-index on patch numbers in an interview — knowing that create_agent superseded AgentExecutor matters far more.

Likely interview questions
Very commonWhat is the difference between LangChain and LangGraph?

They're layers, not alternatives. LangChain provides the abstractions — a standard message format, tool schemas, model wrappers, output parsers, the Runnable interface — so your code isn't coupled to one provider's SDK. LangGraph is the orchestration runtime: a state machine with typed channels, reducers, supersteps, checkpointed persistence, interrupts and streaming.

The clinching detail: LangChain's own create_agent is built on LangGraph. So it isn't a choice between them — you use LangChain's abstractions, and you use LangGraph when you need control over the control flow, or need persistence, human-in-the-loop or durable execution. The honest one-liner: LangChain gives you the pieces; LangGraph decides when each piece runs and remembers what happened.

ModernSomeone shows you code using AgentExecutor. What do you say?

That it's the 0.x-era API and is deprecated — along with initialize_agent and langgraph.prebuilt.create_react_agent. The current equivalent is create_agent from langchain, which builds a LangGraph graph under the hood.

Then explain why it changed, which is the part that scores: AgentExecutor was an opaque while loop. You couldn't inspect intermediate state, pause for human approval, resume after a crash, stream internal steps meaningfully, or modify the control flow without forking it. create_agent returns a real graph, so you get checkpointing, interrupts, time travel and streaming for free — and you can drop down to a raw StateGraph when the default loop isn't the shape you need.

DesignWhen would you use create_agent versus building a StateGraph by hand?

create_agent when your problem genuinely is the standard loop — model, optional tool calls, repeat until done — and you want middleware, structured output and checkpointing without wiring them. It's a real graph, so you can still attach a checkpointer, interrupt it and stream it.

A hand-built StateGraph when the control flow is yours: fixed multi-stage pipelines, parallel fan-out with Send, evaluator-optimizer loops with custom exit conditions, multi-agent supervision, or any state shape beyond a message list. Rule of thumb: start with create_agent, drop to StateGraph when you find yourself fighting the loop. Building a custom graph to reproduce the default ReAct loop is wasted effort — and so is bending create_agent into a shape it wasn't meant to take.

ConceptualWhere does LangSmith fit, and is it required?

It's an observability and evaluation sidecar that spans the whole stack: traces of every LLM call, tool call and node transition; datasets; evaluators; and human feedback collection. It is not required — LangGraph runs perfectly without it, and it's framework-agnostic, so you can trace non-LangChain code too. But for anything non-trivial in production it's close to essential, because a multi-step non-deterministic program is genuinely undebuggable from logs alone. If you don't want a vendor, the substitute is OpenTelemetry-based tracing; the requirement is tracing, not that specific product.

2.1 The capability ladder ⭐⭐

There are five rungs between “one LLM call” and “an agent”. Every rung buys flexibility and pays for it in determinism, latency, cost and debuggability. The senior instinct is to climb no higher than the problem forces you.

The dividing line

Everything below rung 5 has a control flow you can draw before the program runs. At rung 5 you cannot: the model decides what to do next, so the set of possible execution paths is only bounded by your iteration cap. That is the entire trade. An agent can handle inputs you never anticipated; it can also take a path you never anticipated, and you will find out in production.

The one-sentence distinction

A workflow's control flow is written by a developer; an agent's control flow is decided by an LLM at runtime. Everything else — tools, memory, loops — appears on both sides of the line.

Likely interview questions
Very commonWhat is the difference between a workflow and an agent?

Who decides the control flow. In a workflow, a developer wrote the path at build time — the branches, loops and parallel steps are all in the code, and an LLM may fill in content or pick between known options, but it can't invent a new route. In an agent, the LLM decides at runtime what to do next, typically by choosing tools in a loop, so the execution path isn't known until the run happens.

The trade follows directly: workflows are predictable, testable, cheap to reason about, and bounded in cost; agents handle open-ended inputs but have an unbounded path space, variable cost and latency, and failure modes you can't enumerate in advance. Adding the ladder — call, chain, router, workflow, agent — shows you think in gradations rather than a binary.

ConceptualIs a router an agent?

No — it's the rung below. A router lets the LLM make one bounded decision: pick one of N branches the developer defined. The path space is exactly N, every branch is enumerable and testable, and cost is predictable. An agent's decision is unbounded and repeated: it chooses and then chooses again based on what it observed, so the number of possible paths grows with the iteration limit. A router is a classifier with a nice API; an agent is a loop with judgement in it.

System designWhat actually gets worse as you climb the ladder?

Four things, and being able to list them is the point. Testability: you can enumerate a workflow's paths; you cannot enumerate an agent's. Cost predictability: a workflow's token spend is roughly fixed per request, an agent's is a distribution with a long tail. Latency: each extra LLM decision adds a round trip, and they're sequential. Debuggability: when a workflow breaks you know which node; when an agent breaks you have to reconstruct a trajectory and work out why it chose what it chose.

What gets better is exactly one thing: the ability to handle inputs you didn't anticipate. If you don't have those inputs, you're paying four costs for no benefit.

2.2 Anatomy of an agent

Strip away the frameworks and every agent is the same four components wrapped in a loop. Being able to draw it from memory is worth more than knowing any specific API.

The component people forget is termination. Everything else is present in every tutorial; the stopping condition is what the tutorial leaves at its default and production reveals as inadequate. In practice you need at least three simultaneously: natural termination (the model returns no tool call), a hard iteration cap, and a budget cap on tokens or wall-clock. Without the second and third, a confused agent will happily loop until your bill notices.

Likely interview questions
CoreDraw the anatomy of an agent from memory.

A model at the centre, reading three inputs — instructions (system prompt, role, constraints), memory (the message history for this run plus any long-term facts retrieved), and a tool catalogue (schemas, not implementations). Its output is one of two things: a tool call, which your runtime executes and appends the result of as an observation before looping back to the model; or a final answer, which exits.

Guarding the loop is termination: natural (no tool call), a hard iteration cap, and a budget cap. Naming termination as a first-class component rather than an afterthought is the part that reads as production experience.

GotchaHow does an agent know when it's finished?

Primarily by omission: the model returns a response with no tool call in it, and the runtime interprets that as “done”. That's the default in create_agent and in the standard ReAct loop.

The reason it's a gotcha is that this is a fragile signal. A confused model can keep calling tools forever, alternate between two tools indefinitely, or call the same search repeatedly with slightly different queries. So production agents add: a hard recursion_limit, a token or cost budget checked between iterations, a wall-clock timeout, and sometimes an explicit finish tool so termination is a positive decision rather than an absence.

DesignWhere does the “scratchpad” live in a modern agent?

In the message list itself. Older frameworks kept a separate string scratchpad that was formatted into the prompt; the modern shape is that each assistant turn containing a tool call, and each corresponding ToolMessage, is the scratchpad. That's why MessagesState with an add_messages reducer is the default state for an agent — the accumulating message list is simultaneously the memory, the scratchpad and the trace.

The consequence is the cost curve: the scratchpad is re-sent to the model every turn, which is exactly why the loop's token spend is quadratic and why trimming and summarisation are cost levers.

2.3 ReAct and its descendants ⭐

ReAct — Reason + Act — is the pattern everyone names. The interesting part is what has changed since the 2022 paper, because the version you'd implement today looks quite different from the one people describe.

So the honest 2026 answer to “do you use ReAct?” is: the loop, yes; the text format, no. The paper's contribution was the insight that interleaving reasoning with acting beats doing either alone — reasoning-only agents hallucinate facts they could have looked up, action-only agents flail without a plan. That insight survived; the string protocol did not.

InteractiveReAct trace stepper — watch the context grow

Likely interview questions
Very commonExplain ReAct.

Reason + Act: interleave reasoning steps with tool actions, so the model thinks about what it needs, takes an action, observes the result, and thinks again. The 2022 paper's contribution was showing that this beats either half alone — chain-of-thought without tools hallucinates facts it could have looked up, and tool use without reasoning flails at tool selection.

The part that gets you credit: say what's changed. The original used a parsed text protocol (Thought:/Action:/Observation:) that was brittle — regex parsing was the dominant failure mode. Modern implementations use native structured tool calls, so there's no parsing, and support parallel tool calls in a single response. The loop survived; the string format didn't.

ModernIs ReAct still state of the art?

As a protocol, no; as a loop shape, it's still the default. What's moved on: reasoning is now native — reasoning models produce internal thinking without a text scaffold, so you don't prompt for Thought:. Tool calls are structured and can be issued in parallel, which the original's one-action-at-a-time format couldn't express. And the loop is usually wrapped in things ReAct never specified: persistence, interruption, reflection passes, budget caps.

The honest framing is that ReAct named a pattern that turned out to be right, and the industry absorbed it so thoroughly that it stopped being a technique and became the baseline. Descendants worth naming: Plan-and-Execute (plan up front, then execute, fewer LLM calls), Reflexion (add a self-critique step and retry), and Tree-of-Thoughts (branch and evaluate multiple reasoning paths — powerful but expensive and rarely worth it in production).

DebugYour ReAct agent keeps calling the same tool with nearly identical arguments. Why, and what do you do?

Almost always one of four causes. The observation isn't informative — the tool returned an empty result or an opaque error, so the model has no new information and retries with a nudge. The tool description is ambiguous, so the model isn't sure it used it correctly. The result was truncated and the model thinks it's missing something. Or the goal isn't achievable with the available tools and the model has nothing better to do.

Fixes in order: make tool results explicit — return “no results found for X” rather than []; return actionable error strings the model can correct against; sharpen the tool description; add a loop detector that inspects recent tool calls and injects a message when it sees repetition; and always have a recursion_limit so it terminates regardless.

2.4 Planning and decomposition

Should the agent plan first, or figure it out as it goes? The answer depends on whether the steps are knowable in advance — and that's a property of the task, not a preference.

Plan-and-ExecuteReAct (interleaved)
ShapeOne planning call produces a step list; a cheap executor runs each stepDecide one step at a time, informed by the last observation
LLM callsFewer — planning is amortised across stepsOne decision call per step
AdaptabilityPoor — a stale plan keeps executing after reality divergesHigh — every step sees the latest evidence
ParallelismEasy — independent plan steps fan out with SendHard — the next step depends on the last
Best whenSteps are knowable up front and mostly independentEach step's result changes what's sensible next

The pragmatic middle is re-planning: produce a plan, execute a step, then let a re-planner revise the remaining steps in light of what happened. You pay one extra call per step but keep both the parallelism of planning and the adaptability of ReAct. A close cousin is plan caching — for a task type you see repeatedly, the plan is nearly always the same, so store it and skip the planning call entirely, which quietly converts your agent back into a workflow for the common case.

A plan is a hypothesis, not a contract

The failure mode of Plan-and-Execute is an agent that dutifully executes steps 3 through 7 of a plan that step 2 already invalidated. If you use planning, you need either a re-planning step or an explicit validity check before each step — otherwise you've built something less adaptive than a hand-written workflow, at higher cost.

Likely interview questions
DesignPlan-and-Execute or ReAct — how do you choose?

Ask one question: are the steps knowable before you start? If yes — “research these six companies and produce a comparison” — plan first. You get fewer LLM calls because planning is amortised, and the independent steps can run in parallel with Send, which is often a 5× latency win. If no — “debug why this job is failing” — interleave, because each observation changes what's sensible next and a plan written in ignorance is worthless.

Then add the middle option: plan with re-planning, where a re-planner revises remaining steps after each execution. It costs one extra call per step but keeps parallelism and adaptability, and it's what most serious systems converge on.

GotchaWhat's the specific failure mode of Plan-and-Execute?

Stale-plan execution. The plan is generated once, before any evidence exists. If step 2 reveals that the whole premise was wrong — the data source is empty, the customer doesn't exist, the API changed — steps 3 through 7 execute anyway, burning tokens on work that can't be useful, and often producing a confident wrong answer built on nothing.

Guards: a re-planning node after each step; an explicit validity check before executing each step; and making the executor able to signal “this step is no longer applicable” back to the planner rather than only succeeding or failing.

System designHow would you make a research agent 5× faster?

Turn the sequential loop into a plan-then-fan-out. Concretely: one planning call decomposes the question into k independent sub-questions; a conditional edge returns [Send("research", {"sub_q": q}) for q in sub_questions], so all k researchers run in the same superstep, concurrently; each writes into a channel with an operator.add reducer; a synthesis node reads the merged findings.

Wall clock goes from k × step-time to roughly one step-time plus planning and synthesis. Three caveats to mention: you need async end-to-end or the fan-out serialises; you'll hit provider rate limits before you hit any framework limit, so bound the fan-out width; and the sub-questions must be genuinely independent — if question 3 needs question 1's answer, you need two waves, not one.

2.5 Reflection and self-critique

Have the model check its own work and try again. It genuinely helps — for a specific class of task — and it is also the pattern most likely to produce an infinite loop and a large bill.

When reflection actually helps

It helps when the critic has access to something the generator didn't — an external signal. Test results, a compiler error, a schema validation failure, retrieved documents to check claims against: these are real information, and a revision informed by them is genuinely better. It helps far less when the critic is the same model looking at the same context with a different prompt, because the model's blind spots are correlated between the two calls. “Are you sure?” produces a hedge, not an insight.

Likely interview questions
ConceptualDoes self-critique actually improve output?

It depends entirely on whether the critic has new information. When the critique is grounded in an external signal — unit tests that failed, a compiler error, a JSON-schema validation error, retrieved documents to check claims against — reflection works well, because the revision is responding to evidence.

When it's the same model re-reading its own output with an “are you sure?” prompt, gains are small and sometimes negative: the model's errors and its blind spots are correlated across the two calls, so it tends to either rubber-stamp or make confident cosmetic edits. Research on unaided self-correction has repeatedly found this. The design implication is concrete: give the critic a tool or a signal, not just an opinion.

GotchaWhat breaks in a reflection loop?

Non-termination, in three flavours. The critic is never satisfied and the loop runs to your recursion limit. The generator oscillates between two drafts, each fixing what the other broke. Or quality genuinely degrades with iteration — over-revised text often gets worse after round two.

Every reflection loop therefore needs: a hard iteration cap with a forced-accept branch; a score threshold so “good enough” is defined rather than aspirational; ideally keeping the best draft seen so far rather than the last one, so degradation can't cost you; and a critic prompted with explicit, checkable criteria instead of “is this good?”.

DesignHow do you implement reflection in LangGraph?

Two nodes and a conditional edge. generate writes a draft to state; critique uses with_structured_output to return {score: int, issues: list[str], accept: bool}; a conditional edge from critique returns "generate" or END.

The details that matter: keep an iterations counter in state and increment it in the generator, with the conditional edge checking iterations >= MAX before it checks the score; store best_draft and best_score alongside the current one so you return the best rather than the last; and feed the critique text back into the generator's prompt so the revision is targeted. Set recursion_limit on the config as a final backstop — it's a safety net, not the design.

2.6 Autonomy versus control ⭐

Autonomy is not a binary and not a virtue. It is a dial, and where you set it should be a function of blast radius, not of how impressive the demo looks.

LevelThe model decides…Appropriate when
L0 · FixedNothing about flow — it generates content onlyThe process is known and compliance matters
L1 · RoutingWhich of N known branchesInput types vary, handling is standard
L2 · Tool selectionWhich tools to call, in what orderRead-only tools; wrong choices are cheap
L3 · Gated actionWhat to do — but a human approves before it happensWrites, spends, sends — irreversible effects
L4 · Full autonomyEverything, including when it's doneSandboxed, reversible, low-value-per-error

The useful reframing: set autonomy per action, not per agent. One agent can read freely at L2, draft at L2, and require approval at L3 for the single tool that sends an email. That is a far better design than choosing a single autonomy level for the whole system, and it's what interrupt exists to express.

The blast-radius question

For every tool, ask: if the model calls this wrongly, what's the worst outcome, and can we undo it? Reversible and cheap → let it run. Irreversible or expensive → gate it behind approval. That single question generates your entire autonomy policy, and it's a much better answer than “we'd add a guardrail prompt”.

Likely interview questions
System designHow much autonomy would you give a production agent?

Reframe it: autonomy is set per action, not per agent, and the deciding question is blast radius — if this call is wrong, how bad is it and can we undo it?

Concretely, in one support agent: reading the knowledge base and querying order history are free (wrong answers are cheap and reversible); drafting a reply is free; issuing a refund, sending the email, or modifying a record requires an interrupt and human approval. Above some value threshold you might require a second approver.

The additional point that lands well: gating is enforced in your tool layer, not in the prompt. The model can be talked out of a prompt instruction; it cannot be talked past a code path that requires an approval token.

ConceptualIsn't a heavily gated agent just a workflow with extra steps?

Sometimes, and noticing that is a good sign — but not always. The distinction is where the flexibility lives. A gated agent still chooses which tools to use and in what order, and it handles inputs you didn't enumerate; the gate only constrains the small number of actions with real-world consequences. That's genuinely different from a workflow where the path is fixed.

That said, if you find that every meaningful action is gated and the sequence is always the same, you have discovered that your problem was a workflow all along — and you should rewrite it as one. That realisation is worth acting on, not defending against.

DesignWhere do you enforce a “never do X” rule?

In code, in the tool layer — never only in the prompt. A system-prompt rule is a strong suggestion that a sufficiently unusual input, or a deliberate injection, can override. A check inside the tool function, or a wrapper that refuses before dispatch, cannot be argued with.

The layered version, best to state in full: capability limits first (the agent's DB credentials are read-only, so “never DROP a table” is enforced by permissions rather than intent); validation in the tool second (parse the SQL, reject anything that isn't a SELECT); approval gates third for the actions that survive; and the prompt last, as a hint that reduces how often you hit the other three. The prompt is UX; the code is the control.

2.7 When NOT to build an agent ⭐⭐

The highest-scoring answer in most agentic-AI interviews is a well-argued no. Candidates who reach for an agent by default are demonstrating exactly the instinct that produces expensive, unreliable production systems.

The four disqualifiers

If…Then build…Because
The steps are always the sameA chain or workflowYou're paying an LLM to rediscover a sequence you already know
Latency budget is under a secondA single call, or no LLMEach agent iteration is a round trip; 5 steps is 5–20 s
Errors are expensive and hard to detectA gated workflow, or a humanNon-determinism plus high stakes is the worst combination
You can't evaluate the outputNothing yet — build the eval firstAn agent you can't measure will silently degrade

There is a fifth, less often stated: if a well-written SQL query, a regex, or a lookup table solves it, do that. A surprising share of “agent” projects are deterministic data problems wearing a chat interface. Saying this out loud in an interview signals that you optimise for the business outcome rather than for using the interesting technology.

The interview trap

You'll be given a scenario that sounds agentic — “classify incoming tickets and route them” — and the expected answer is a router, not an agent. If you launch into supervisor architectures and tool catalogues for a problem one structured-output call solves, you've failed the judgement test regardless of how good the rest of the answer is.

Likely interview questions
Very commonWhen would you not build an agent?

Four clear cases. The steps are knowable in advance — then encode them; paying an LLM to rediscover a fixed sequence on every request adds cost, latency and failure modes for nothing. The latency budget is tight — each iteration is a round trip, so a five-step agent is a 5–20 second experience and no amount of engineering fixes that. Errors are expensive and hard to detect — non-determinism plus high stakes is the worst combination; use a gated workflow or a human. You have no way to evaluate the output — an unmeasurable agent degrades silently, so build the eval before the agent.

And the fifth: if SQL, a regex or a lookup table solves it, do that. The honest default is that most problems that look agentic are workflows, and most that look like they need multi-agent need one agent.

System design“We want an agent that classifies support tickets and routes them.” Design it.

Push back first, then design. That's not an agent — it's a single classification call. One LLM call with with_structured_output returning a Literal category plus a confidence, then a deterministic route. One model call, ~500 ms, fully testable against a labelled dataset, trivially cheap, and you can measure accuracy directly.

Then show where it would become an agent: if routing requires looking things up — checking the customer's plan, their open tickets, whether the reported bug is known — and the number and order of those lookups depends on what you find, then you have genuine dynamic control flow and an agent (or at minimum a tool-calling loop) is justified. Volunteering the boundary condition is what makes this a strong answer rather than a contrarian one.

ConceptualHow do you justify agent cost to a sceptical stakeholder?

By making the comparison concrete rather than architectural. Establish the baseline: what does the task cost today in human minutes, and what's the error rate? Then measure the agent on the same terms — cost per successful completion, not cost per call, because failed runs and retries are part of the price. Include the tail: p95 cost and latency, since agent spend is a distribution with a long right tail, and a stakeholder surprised by that tail will lose trust in the whole project.

And be willing to conclude against the agent. “We measured it; a workflow gets 94% of the value at 20% of the cost, so we shipped the workflow” is a stronger answer than any defence of the agent.

ConceptualWhat's actually changed in agent engineering over the last two years?

And the industry got more conservative — the 2023 enthusiasm for fully autonomous multi-agent swarms gave way to the observation that most production value comes from one well-instrumented agent with well-designed tools and tight gates.

The meta-point: the trend is toward less autonomy and more engineering, which is the opposite of what the early hype predicted.

ConceptualHow do you evaluate a claim like “our agent scores 78% on this benchmark”?

With three questions. What's the task distribution? Most agent benchmarks are narrow — a single domain, a fixed tool set — and performance rarely transfers. Is there contamination? Public benchmarks leak into training data, and a model that has seen the test set is not being evaluated. What was the cost and latency? A score achieved with 50 model calls and a tree search is not comparable to one achieved in three calls, and almost no leaderboard reports that.

The practical conclusion: benchmarks are useful for ruling out candidates, not for selecting one. The only number that matters is performance on your data with your tools, which is why you build a small golden dataset before you pick a model.

3.1 Why a graph at all ⭐

You can write an agent as a while loop in forty lines. The question every interviewer is really asking is: what do you get by writing it as a graph instead?

What the loop cannot do

Pause for human approval, resume tomorrowImpossible — the stack is gone when the process endsinterrupt + checkpointer
Resume after a crash mid-runRestart from scratch, re-running side effectsResume from the last completed node

Every row reduces to one root cause: a while loop's state lives on the call stack, and the call stack is not persistable. A graph's state lives in an explicit, serialisable object that the runtime owns, so it can be written to a database between steps. Once that's true, pause/resume, crash recovery, inspection and time travel all become available at once. They are not six features — they are one feature, seen from six angles.

Be willing to say the loop is fine

If you don't need persistence, interruption, streaming or parallelism, the loop really is fine — and saying so is a stronger answer than defending the framework. The graph earns its complexity precisely when the run is long enough, valuable enough, or interruptible enough that losing it matters.

Likely interview questions
Very commonWhy use LangGraph instead of just writing a loop?

Because a loop's state lives on the call stack, and a call stack can't be persisted. Everything LangGraph gives you follows from moving state into an explicit serialisable object the runtime owns and checkpoints between steps: you can pause for human approval and resume days later in a different process; resume after a crash from the last completed node instead of re-running side effects; inspect the exact state at any past step and even fork from it; parallelise branches with declared merge semantics instead of hand-rolled gather; and stream intermediate progress without callback plumbing.

Then be honest about the boundary: for a short, stateless tool-calling loop with no persistence requirement, a plain loop is genuinely simpler and easier to debug. LangGraph earns its cost when the run is long, valuable, or interruptible.

ConceptualWhat kind of graph is a LangGraph graph?

A directed graph with cycles allowed — deliberately not a DAG, because agent loops are cycles by nature and a DAG framework can't express “call a tool and go back to the model”. Execution follows the Pregel model from bulk-synchronous parallel computing: rounds called supersteps, where all active nodes in a round execute (potentially in parallel), all their writes are applied at a barrier, and then the next round's active set is determined.

Being able to say “it's Pregel-style BSP, not a DAG scheduler” is a strong signal, because it explains parallel write conflicts, reducers and checkpoint boundaries in one stroke.

3.2 StateGraph and the state schema ⭐⭐

The state schema is the most consequential design decision in a LangGraph application. Get it right and nodes stay small; get it wrong and you'll be threading data through channels that shouldn't exist.

State is a set of channels, not an object

The mental model that makes everything else click: your state is not one blob that nodes overwrite. It is a collection of independent named channels, each with its own reducer and its own write history. When a node returns {"docs": [...]}, it writes to the docs channel and touches nothing else. When two parallel nodes both write to docs, the channel's reducer decides how to combine them. Checkpointing snapshots all channels together.

Designing the schema

Three questions per field. Who writes it? If more than one node can write it concurrently, it needs a non-default reducer. Does it accumulate or replace? Accumulate → add-style reducer; replace → default. Does the caller need it? If not, keep it out of output_schema. A schema with fifteen fields is usually three schemas wearing a trench coat — consider subgraphs with their own state.

Likely interview questions
CoreWhat is state in LangGraph, and what does “channel” mean?

State is a typed set of independent named channels, declared by a schema (usually a TypedDict). Each channel has its own reducer — a function (current, update) -> new that decides how a node's write is merged in. The default reducer is overwrite.

“Channel” matters because it's the unit of everything: nodes write to channels not to state; parallel writes are resolved per channel by that channel's reducer; a checkpoint is a snapshot of all channels; and stream_mode="updates" reports per-channel writes. Thinking of state as one mutable object rather than a set of channels is the root of most confusion about parallel updates.

DesignHow do you decide what belongs in state?

Put in state anything that (a) must survive across nodes, (b) must be checkpointed for resume, or (c) is written by more than one node. Keep out of state: things derivable on demand, large blobs better referenced by id (put the S3 key in state, not the 40 MB PDF), and anything secret — state is persisted, so credentials in state are credentials in your database.

Two refinements worth volunteering: use input_schema/output_schema so internal scratch channels never leave the graph; and if the schema is growing past roughly eight fields, that's a signal to factor part of it into a subgraph with its own private state rather than widening the parent.

GotchaWhere should you not put large objects?

In state, if you have a checkpointer. Every superstep serialises the full state to the checkpoint store, so a 40 MB dataframe in a channel means a 40 MB write per superstep — plus the same cost on every resume and every get_state. It will look like the model is slow when it's actually the serialiser.

Store the artifact externally and put a reference in state: an S3 key, a row id, a cache key. The same applies to raw retrieved documents in a RAG graph — keep the text if it's small, but consider passing ids plus a lightweight summary and re-fetching in the node that needs the full text.

3.3 Nodes ⭐

A node is a function from state to a partial update. Everything interesting about nodes is a consequence of taking that definition seriously.

Signatures and what nodes receive

The minimal node takes state and returns a dict. It can also take a second argument for runtime context — the config carrying thread_id, user identity, and anything you passed at invocation. A node can be sync or async; it can be a plain function, another graph, or any Runnable. Node names default to the function's name and must be unique.

Never mutate the state you were given

state["docs"].append(x); return {} is a bug even when it appears to work. It bypasses the reducer, so parallel merges are wrong; it bypasses the checkpointer's change detection; and it makes the node non-replayable, which breaks time travel and durable resume. Always return a new value and let the reducer apply it.

Nodes should be replayable

With durable execution, a node may be executed more than once — after a crash, on resume, or during time travel. That makes idempotency a design property of nodes, not an ops concern: a node that charges a card must be safe to run twice. In practice this means side-effecting work goes in its own small node with an idempotency key, kept separate from the reasoning around it.

Likely interview questions
GotchaWhat happens if a node mutates the incoming state directly?

You get bugs that are hard to trace. Mutating state["docs"] in place bypasses the reducer, so if two nodes do it concurrently the merge semantics you declared never run and one write is silently lost or interleaved. It also bypasses the checkpointer's notion of what changed, so the persisted state may not match what your code thinks it did. And it makes the node non-replayable — re-running it during resume or time travel applies the mutation twice.

The rule: nodes are pure with respect to state. Read it, return a new partial update, let the runtime apply it.

DesignHow big should a node be?

Sized by checkpoint boundaries and side effects, not by lines of code. A checkpoint is written after each superstep, so node boundaries are your resume points: if a node does five things and fails on the fourth, resume re-runs all five. So put each side effect in its own node — that's the real rule.

Beyond that: split when you want a human-in-the-loop gate between two operations, when parts could run in parallel, or when you want distinct retry policies. Don't split for aesthetics — every node boundary costs a checkpoint write, and a graph with forty trivial nodes is slower and harder to read than one with eight meaningful ones.

ConceptualCan a node return nothing?

Yes — returning None or {} means “no state change”, and it's perfectly valid for a node that only performs a side effect like logging or emitting a metric. The graph still advances and a checkpoint is still written.

Two related points: returning a key that isn't in the schema is an error rather than a silent no-op in current versions, which is a useful guard against typos; and if you want a node to both update state and decide where to go next, return a Command instead of a plain dict.

3.4 Edges and conditional edges ⭐

Edges are the control flow. There are three kinds, and the difference between a normal edge and a conditional edge is exactly the difference between a workflow and an agent.

KindWritten asSemantics

Keeping the router deterministic makes the branch testable in isolation, which is one of the most practical testing wins available in a LangGraph codebase.

The mapping dict in add_conditional_edges is optional if your function returns node names directly — but supply it anyway. It's what lets LangGraph draw the possible edges in the rendered graph, and without it the visualisation shows a node with no visible outgoing edges, which makes reviews and debugging harder.

Likely interview questions
CoreHow do you create a loop in LangGraph?

A conditional edge that can point backwards. The canonical agent loop: model → should_continue → {"tools": "tools", "finish": END}, plus a normal edge tools → model. That cycle runs until should_continue returns the exit branch.

Two things to add. First, the routing function is ordinary Python — no LLM call — which is what makes the branch unit-testable. Second, always bound the loop: check an iteration counter in the router before the model-driven condition, and set recursion_limit on the config as a backstop (the default is 25 supersteps, and hitting it raises GraphRecursionError).

CodingCan a conditional edge return more than one destination?

Yes. Return a list of node names and all of them run in the next superstep, concurrently — that's static fan-out chosen at runtime. Return a list of Send objects and you get dynamic fan-out where each branch also receives its own private input state, which is how map-reduce is expressed.

The important consequence: as soon as more than one branch can write the same channel, that channel needs a reducer, or you'll get an InvalidUpdateError at the superstep barrier.

DebugYour graph raises GraphRecursionError. What's your process?

Don't start by raising the limit — that usually converts a fast failure into an expensive one. Diagnose first.

1. Look at the trajectory. Print stream_mode="updates" or open the LangSmith trace and read the node sequence; a cycle is usually obvious within a few steps. 2. Is the exit condition reachable? Often the router checks something no node ever sets — a counter that's never incremented, or a flag written to the wrong channel. 3. Is the model looping? The same tool called repeatedly with near-identical arguments usually means uninformative tool results; fix the tool's return value, not the limit. 4. Is the counter increment being lost? With a fan-out, two branches each writing count + 1 to an overwrite channel results in one increment, not two.

Only raise recursion_limit once you've confirmed the graph legitimately needs more supersteps than the default 25.

3.5 Reducers ⭐⭐

A reducer is a two-argument function that says how a write is merged into a channel. It is the single most misunderstood concept in LangGraph, and the source of the most common production bug: disappearing messages.

The default is overwrite

Declare messages: list and the channel's reducer is “replace the old value with the new one”. So a node returning {"messages": [ai_msg]} throws away the entire conversation and leaves one message. Declare messages: Annotated[list, add_messages] and the same return appends instead. Nothing else changes — one annotation is the difference between a working chatbot and one with amnesia.

InteractiveReducer playground — two parallel nodes, one channel

Both branches run in the same superstep and both write to the same channel. The reducer is the only thing deciding what the state looks like afterwards — and with the default, one of the two writes raises rather than silently winning, because LangGraph refuses to guess.

Likely interview questions
Very commonWhat is a reducer and why does LangGraph need them?

A reducer is a function (current_value, update) -> new_value attached to a state channel, declared with Annotated[T, reducer]. It decides how a node's write is merged into that channel. The default is overwrite.

LangGraph needs them for two reasons. Sequentially, most agent state accumulates — messages, documents, findings — and overwriting is the wrong semantics. Concurrently, when several nodes in the same superstep write the same channel, something has to decide how to combine the writes, and a reducer is that declaration. Without one, LangGraph refuses to guess and raises InvalidUpdateError.

The framing that lands: a reducer is how you declare merge semantics up front, instead of resolving conflicts ad hoc at runtime.

DebugYour chatbot only ever remembers the last message. What's wrong?

The messages channel has no reducer, so it's using the default overwrite. Each node returning {"messages": [new_msg]} replaces the whole list with a single-element list.

Fix: messages: Annotated[list, add_messages], or just use the built-in MessagesState. This is the single most common LangGraph bug and it's worth being able to diagnose it from the symptom in one sentence.

Two adjacent causes worth ruling out if the annotation is already there: a node returning the whole message list instead of just the new messages (which duplicates history, the opposite symptom), and a missing or wrong thread_id, which means every turn starts a fresh conversation even though the reducer is correct.

Deep diveWhat does add_messages do that operator.add doesn't?

operator.add is plain list concatenation. add_messages is message-aware: it assigns ids to messages that lack them; de-duplicates and replaces by id, so re-sending a message with an existing id edits history rather than appending a duplicate; understands RemoveMessage, which is how trimming and summarisation actually delete history; and coerces dicts and strings into proper message objects.

The replace-by-id behaviour is the one people miss, and it's what makes editable history, redaction of a tool result, and message deletion possible at all.

CodingWrite a custom reducer, and say what makes a good one.

def keep_best(cur: float, new: float) -> float: return max(cur, new), then score: Annotated[float, keep_best]. Or dedup-preserving concat: lambda a, b: a + [x for x in b if x not in a].

What makes it good: it must be pure (no side effects, no I/O — it runs inside the state machinery), it must not mutate its arguments, it should be associative where possible because the order of concurrent writes isn't guaranteed, and it must handle the initial call where the current value may be the channel's default. A reducer that assumes cur is non-empty will fail on the first write.

3.6 The superstep model ⭐⭐

LangGraph executes in rounds, not step by step. Once you understand supersteps, parallel-write conflicts, reducer necessity and checkpoint boundaries all stop being separate topics.

The three rules

1. All nodes active in a superstep execute together, potentially in parallel. 2. Their writes are buffered and applied at the barrier, through the reducers, all at once. 3. A checkpoint is written per superstep, and the next superstep's active set is whichever nodes the completed nodes' edges point to. The consequence that trips people up: a node cannot see a sibling's write, because at the time it runs, that write hasn't been applied.

Counters and parallel branches don't mix

Three parallel nodes each returning {"count": state["count"] + 1} to an overwrite channel raise a conflict; give it a reducer of max and you get +1, not +3, because all three read the same pre-barrier value. To count parallel completions, use Annotated[int, operator.add] and have each node return {"count": 1} — the reducer does the summing.

Likely interview questions
Deep diveWhat is a superstep, and why does LangGraph work this way?

A superstep is one round of execution in the Pregel / bulk-synchronous-parallel model. All nodes active in the round run together, their state writes are buffered rather than applied immediately, and at the end of the round a barrier applies every write through its channel's reducer at once. Then a checkpoint is written and the next round's active set is computed from the edges.

Why: it makes concurrency deterministic in its merge semantics. Nodes can't race on shared state because none of them can observe another's write mid-round — there's exactly one place where state changes, and it's governed by reducers you declared. It also gives a natural, consistent point to checkpoint: the barrier.

The practical corollaries: parallel siblings never see each other's writes; concurrent writes to one channel need a reducer; and resume granularity is the superstep, not the individual node.

GotchaThree parallel nodes each do count + 1. What is count afterwards?

With the default overwrite reducer: an InvalidUpdateError, because three concurrent writes to one overwrite channel are ambiguous. With a max or last-write-wins reducer: 1, not 3 — all three nodes read the same pre-barrier value of count, so all three compute the same result.

The correct pattern is to let the reducer do the arithmetic: declare count: Annotated[int, operator.add] and have each node return {"count": 1}. Then the barrier sums the three writes and you get 3. This generalises — in a fan-out, nodes should return their contribution, not the computed new total.

ConceptualHow often is a checkpoint written?

Once per superstep, at the barrier — not once per node. So if five nodes run concurrently in one superstep, that's one checkpoint containing all five merged writes.

Two consequences. Resume granularity is the superstep: after a crash you re-enter at the start of the superstep that hadn't completed, and every node in it re-runs — which is exactly why side-effecting nodes must be idempotent. And checkpoint cost scales with state size times superstep count, which is why a large object in state is expensive: you pay to serialise it on every round, not once.

3.7 Send and the map-reduce pattern ⭐

Send answers a question static edges can't: what if you don't know how many branches you need until the graph is already running?

The three things that make Send different

Dynamic width — the number of branches comes from state at runtime, not from the graph definition. Private input state — each worker receives the dict you pass, not the parent state, so write_section sees {"subtopic": ...} and nothing else; that isolation is what keeps a 50-way fan-out from carrying 50 copies of a large parent state. Automatic join — all the sends run in one superstep and the graph continues to the next node once they've all completed and their writes have been merged.

Three ways a Send fan-out goes wrong

No reducer on the channel the workers write → InvalidUpdateError at the barrier. Unbounded width → 500 sub-questions means 500 concurrent LLM calls and an immediate rate-limit wall; cap it. Sync nodes → the fan-out is concurrent in the graph's model but serialised in wall-clock time if the nodes block.

Likely interview questions
Very commonWhat is Send and when do you need it?

Send(node_name, state) is returned from a conditional-edge function to dispatch a branch dynamically. You need it whenever the number of parallel branches isn't known until runtime — a planner produced n sub-questions, a query returned n rows, a document split into n sections.

Three properties to name. The width is dynamic, unlike static fan-out where every edge is in the graph definition. Each worker gets its own private input state — the dict you pass in the Send, not the parent state — which both isolates workers and keeps large parent state from being copied n times. And there's an implicit join: all sends run in one superstep, and the graph advances once they've all completed and merged.

Requirement to state unprompted: the channel the workers write must have a reducer, because by construction there are concurrent writes.

CodingWrite a map-reduce in LangGraph.

Three nodes and one conditional edge. Map: a plan node produces subtopics: list[str]. A conditional edge returns [Send("worker", {"subtopic": s}) for s in state["subtopics"]]. Reduce: the worker returns {"sections": [text]} into a channel declared Annotated[list[str], operator.add], and a compile node downstream reads the merged list.

Production details worth adding: cap the width (subtopics[:MAX]) so a runaway planner can't launch 500 concurrent calls; make workers async or the concurrency is notional; and decide what happens if one worker fails — by default the superstep fails, so if partial results are acceptable, catch inside the worker and return a sentinel like {"sections": [], "errors": [msg]} instead of raising.

GotchaWhat does a Send worker actually receive as its state?

Exactly the dict you passed in the Send — not the parent graph's state. This surprises people: a worker that tries to read state["messages"] will find it missing unless you explicitly included it.

That's deliberate and useful: it isolates workers, keeps them independently testable, and avoids copying a large parent state into every branch. If a worker genuinely needs shared context, pass it explicitly in the Send payload — and if the payload is getting big, that's a hint to pass an id and let the worker fetch what it needs.

Normally a node updates state and an edge decides where to go. Command lets one return value do both — which is exactly what agent handoffs need.

Likely interview questions
CoreCommand versus a conditional edge — when do you use which?

Command when the node computes the routing decision as part of its work, so splitting it into a node plus a router would mean either re-deriving the decision or stashing it in state purely to hand it to the router. The canonical case is a supervisor or an agent handoff: “record my message and transfer to the researcher” is one atomic act.

Conditional edge when the routing rule is separable from the node's work, when several nodes share the same rule, or when you want the branch to be visible in the rendered graph and unit-testable on its own.

And the case where only Command works: routing from a subgraph to a node in the parent, via Command(goto=..., graph=Command.PARENT).

DesignHow do you implement an agent handoff with Command?

Make the handoff a tool whose implementation returns a Command. The agent calls transfer_to_researcher(); the tool returns Command(goto="researcher", update={"messages": [ToolMessage("transferring…", tool_call_id=id)]}, graph=Command.PARENT).

Why this shape is good: the handoff appears in the model's tool catalogue, so it's a first-class decision the model makes with a described purpose; the ToolMessage keeps the message history well-formed (an assistant tool call with no matching tool result breaks most providers); and graph=Command.PARENT lets a tool called inside one agent's subgraph move control to a sibling agent in the parent graph. This is exactly how the swarm pattern is built.

GotchaWhy does your graph diagram show a supervisor node with no outgoing edges?

Because it routes with Command and you didn't annotate the return type. LangGraph infers drawable edges from the type annotation -> Command[Literal["a", "b", "__end__"]]; without it, the runtime routing still works but the compiler has no way to know the possible destinations, so nothing is drawn.

It matters more than aesthetics: the diagram is what you show in a design review, and a graph whose picture doesn't match its behaviour is a documentation bug waiting to mislead someone.

3.9 Subgraphs

A compiled graph is a Runnable, so it can be a node in another graph. That's the whole mechanism — the interesting part is how state crosses the boundary.

Two ways to attach

Shared schema: if the subgraph's state schema shares channel names with the parent, you can add it directly — builder.add_node("sub", subgraph) — and matching channels flow through automatically. Different schema: wrap it in a function that translates in and out, which is the more common and more maintainable choice because it makes the contract explicit:

Checkpointing and streaming across the boundary

A subgraph inherits the parent's checkpointer — you don't (and shouldn't) compile it with its own, or you'll get two persistence layers writing to different places. Its checkpoints are namespaced under the parent's thread, so get_state on the parent can reach into subgraph state with subgraphs=True. Streaming works the same way: pass subgraphs=True to stream or the inner nodes' events won't surface.

Likely interview questions
DesignWhen would you use a subgraph?

Three genuine reasons. Reuse — the same retrieval-and-grade pipeline is needed by several parent graphs. Encapsulation — a multi-agent system where each agent is its own graph with its own private state, so the parent's schema stays small. Team boundaries — different people own different subgraphs with an agreed interface.

And the reason not to: pure aesthetics. A subgraph adds an indirection layer to debugging (you need subgraphs=True to see inside when streaming or inspecting state) and a schema-translation boundary to maintain. If it's just a group of three nodes that always run together, leave them in the parent.

GotchaHow does state pass between parent and subgraph?

Two modes. If the schemas share channel names, you can add the compiled subgraph directly as a node and those channels flow in and out automatically — convenient, but it couples the two schemas invisibly. If they don't, you wrap the subgraph in a function that maps parent state to subgraph input and maps the result back to a parent update. The wrapper is usually the better choice because the contract is written down.

Two details people miss: the subgraph inherits the parent's checkpointer and its checkpoints are namespaced under the parent thread, so don't give it its own; and to see the subgraph's internals you must pass subgraphs=True to stream or get_state, otherwise it looks like a single opaque node.

compile() is where the graph stops being editable and starts being runnable — and it's where you attach the things that turn a graph into a product.

At invocation you pass a config rather than a graph option: configurable carries the thread_id and anything your nodes need per-run; recursion_limit caps supersteps (default 25); durability selects how aggressively checkpoints are persisted. Likely interview questions
CoreWhat does compile() do?

It freezes the builder into an immutable, executable Runnable, and it's where you attach runtime infrastructure: the checkpointer, the store, static interrupt_before/interrupt_after breakpoints, and a name for traces.

It also validates the graph — unreachable nodes, edges pointing at names that don't exist, no path from START. Those become errors at compile time rather than surprises at runtime, which is why compiling in a unit test is a cheap structural check even without running anything.

The division to state clearly: compile-time is infrastructure, invocation-time is per-request — thread_id, user context and recursion_limit go in the config on each call, not into compile().

DebugWhat's recursion_limit, and what should you set it to?

It caps the number of supersteps in a single invocation; default 25; exceeding it raises GraphRecursionError. Note it counts supersteps, not LLM calls or tool calls — a fan-out of ten workers is one superstep, and one agent iteration (model, then tools) is two.

Set it from the graph's expected depth with headroom: if your agent should finish in at most eight iterations, that's roughly 16–18 supersteps, so 25 is fine and 40 is generous. Deliberately keep it low enough to fail fast — it's a safety net against runaway loops and cost, not a target. And treat hitting it as a bug to diagnose rather than a number to raise.

CodingHow do you pass per-request data like a user id into nodes?

Through the config's configurable dict at invocation: {"configurable": {"thread_id": tid, "user_id": uid}}. Nodes access it via the runtime/config argument in their signature. This is the right channel for anything that varies per request but isn't conceptually part of the conversation state — user identity, tenant, feature flags, a request id for correlation.

Two rules worth stating: don't put per-request identity in state, because state is persisted in the checkpoint and you'd be freezing a user id into a thread's history; and don't put secrets in either — configs are frequently logged and state is definitely persisted.

4.1 Prompt chaining

The simplest pattern: decompose a task into a fixed sequence of calls, where each step's output feeds the next. Boring, deterministic, and correct far more often than people expect.

Why splitting one prompt into three helps

A single prompt asking the model to research, outline, draft and edit does all four badly, because attention is split and there's no point at which any one sub-task gets the model's full effort. Chaining gives each step a focused instruction and a clean context. It also gives you something a monolithic prompt can't: a place to put a gate. Between step 2 and step 3 you can validate, filter, retry that step alone, or stop early — none of which is possible inside one generation.

Likely interview questions
ConceptualWhy split one prompt into a chain of three?

Three reasons. Focus: each call gets one job and a clean context, which measurably improves quality over a prompt that asks for four things at once. Gates: you can validate, filter or branch between steps — impossible inside a single generation. Observability and cost control: you can see which step failed, retry only that step, and use a cheap model for the mechanical steps and an expensive one for the hard step.

The cost: more round trips, so higher latency. If quality is already fine with one call, chaining is over-engineering — the pattern earns its keep when a step needs to be checked or when different steps want different models.

DesignWhere would you put a gate in a chain, and what should it check?

Immediately after any step whose failure would waste the remaining steps or produce a confidently wrong result. The check should be deterministic wherever possible — schema validation, a length or format check, a regex, “did retrieval return anything at all” — because a deterministic gate is free, instant and testable.

Use an LLM gate only for judgements that genuinely need one (relevance, tone, factual grounding), and when you do, use with_structured_output so the gate returns a typed verdict rather than prose. And give the gate an escape: retry the failed step at most k times, then either continue with a flag or fail cleanly — never loop unbounded.

4.2 Parallelisation ⭐

Two distinct patterns share this name, and conflating them is a common slip. Sectioning splits a task into independent parts; voting runs the same task several times and aggregates.

SectioningVoting
What runs in parallelDifferent sub-tasksThe same task, repeated
WhyLatency — n steps in one step's timeReliability — reduce variance
AggregationConcatenate / synthesiseMajority vote, best-of-n, or a judge

Sectioning is nearly always worth it when the parts are independent — you're spending the same tokens in less time. Voting is a deliberate purchase of reliability with money: three-way self-consistency on a hard classification is a real accuracy gain, and it costs exactly 3×. Use it where the error is expensive, not everywhere.

“Independent” has to be true

Sectioning only works if the sections genuinely don't depend on each other. If section 3 needs section 1's finding, running them in parallel produces a section 3 written in ignorance — which reads fine and is wrong. Where there are dependencies, use waves: parallelise within a wave, sequence between waves.

Likely interview questions
ConceptualWhat are the two kinds of parallelisation?

Sectioning — split a task into independent sub-tasks and run them concurrently, then synthesise. You buy latency: the same total tokens in roughly one step's wall-clock. Voting — run the same task several times (different temperatures, prompts or models) and aggregate by majority, best-of-n, or a judge. You buy reliability, and you pay n× the tokens for one answer.

Both are implemented the same way in LangGraph — a fan-out into one superstep with a reducer on the shared channel — but they're chosen for opposite reasons, and mixing up which one you're doing leads to paying 3× for a latency win you didn't get.

System designWhen is voting worth 3× the cost?

When the cost of an error clearly exceeds the cost of two extra calls, and the errors are at least partly independent. Good cases: safety and moderation checks where a false negative is serious and you take the union of flags; a high-stakes classification feeding an irreversible action; extraction from a noisy document where you can take the modal value per field.

Bad cases: creative generation, where there's no ground truth to vote on; anything where the model's errors are systematic, since three runs of the same model with the same blind spot vote unanimously for the same wrong answer — which is why diversity (different prompts or different models) matters more than raw repetition. And always compare against the cheaper alternative: one call to a stronger model is often better than three to a weak one.

CodingHow do you implement each in LangGraph?

Sectioning with known parts: several add_edge("plan", worker) calls, so all workers activate in the same superstep. Sectioning with dynamic parts: a conditional edge returning [Send("worker", {...}) for ...]. Voting: fan out to the same node n times with Send, varying a seed or prompt in the payload.

In all three cases the result channel needs a reducer — Annotated[list, operator.add] — and a downstream node performs the aggregation. Two production notes: make the workers async or the parallelism is only notional, and cap the fan-out width so a runaway plan can't launch hundreds of concurrent calls into a rate limit.

4.3 Routing ⭐

Classify the input, send it to a specialist handler. It is the highest value-per-unit-complexity pattern in the whole catalogue, and it is very often the correct answer to a question that sounded like it needed an agent.

Why routing beats one big prompt

A single prompt that must handle billing, technical support and account changes carries instructions for all three, most of which are irrelevant to any given request — that's wasted context and diluted attention. Routing gives each branch a focused prompt, its own tools, and its own model tier. Billing questions can go to a cheap model with the pricing table; technical escalations to a strong model with the diagnostics tools. You also get per-branch metrics, which is what lets you find out that one category is quietly performing badly.

Always have a fallback branch

Two things will happen in production: an input that fits none of your categories, and a low-confidence classification. Both need a general handler — never let the router pick the nearest wrong specialist. Returning a confidence score alongside the label, and routing below a threshold to the fallback, costs nothing and prevents the worst routing failures.

Likely interview questions
DesignHow do you build a reliable router?

Five things. Structured output with a Literal so the model can't invent a category. A confidence score in the same schema, with a threshold below which you route to a general fallback. An explicit fallback branch for inputs that fit nothing. A cheap fast model — classification is easy and the router is on every request's critical path. And a labelled dataset, because a router is a classifier and you should be able to state its accuracy and see its confusion matrix.

The last point is what separates a real answer from a plausible one: routing is the one agentic pattern that's trivially evaluable, so there's no excuse for not measuring it.

DebugYour router sends 30% of requests to the wrong branch. What do you do?

Get the confusion matrix first — “30% wrong” is uninformative; “billing is being misread as account 80% of the time” tells you what to fix. Then, in order: are the categories genuinely distinguishable? Frequently two categories overlap semantically and the fix is to merge them or add a disambiguating question rather than to tune the prompt. Are the category descriptions in the schema clear, with examples of edge cases? Would few-shot examples of the confusable pairs help? Is the model too small for the distinctions you're asking for?

And check the cheap structural fix: if two categories route to handlers that behave almost identically, the misclassification may not matter — measure the downstream impact before optimising the classifier.

ConceptualRouter or agent — how do you tell which a problem needs?

Ask whether one decision is enough. If the input can be classified and handed to a handler that completes the job, it's a router: one call, bounded, testable, cheap. If choosing the right handler itself requires looking things up — check the customer's plan, then their ticket history, then whether the bug is known — and the number and order of lookups depends on what you find, then the control flow is dynamic and you need a tool-calling loop.

The practical test: can you draw the complete decision tree? If yes, build the tree. If the tree's depth depends on runtime data, build the agent.

4.4 Orchestrator-worker ⭐

A planner decides what needs doing and dispatches workers to do it. The distinguishing feature versus plain parallelisation is that the number and nature of the subtasks is decided at runtime.

The three failure modes are worth memorising because they're what an interviewer probes: the orchestrator produces too many subtasks (cap the width); the subtasks overlap, so you pay three times for the same research and the synthesiser has to dedupe; and the subtasks don't cover the question, which no amount of good worker output can fix. All three are prompt-and-validation problems at the orchestrator, not worker problems.

Likely interview questions
ConceptualHow is orchestrator-worker different from parallelisation?

In parallelisation the branches are fixed at design time — you wrote three edges to three nodes. In orchestrator-worker an LLM decides at runtime how many subtasks there are and what they are, and identical workers are dispatched dynamically with Send.

That's a real difference in kind, not degree: it means the graph's shape depends on the input, you can't enumerate the execution paths, and you now own new failure modes — too many subtasks, overlapping subtasks, and subtasks that don't cover the question. Parallelisation has none of those, which is why you should prefer it when the decomposition is knowable.

DebugYour orchestrator generates overlapping subtasks and you're paying three times for the same work. Fix it.

Attack it at the orchestrator, in this order. Constrain the schema: make it return a list of subtasks with an explicit instruction that they must be non-overlapping and collectively exhaustive, and require a one-line scope per subtask so overlap is visible. Cap the count in the schema (max_length) and in code. Add a validation node between plan and dispatch that dedupes near-identical subtasks — cheap string or embedding similarity is usually enough. Cache at the tool layer, so even if two workers issue the same search, you pay once.

And measure it: log the number of workers and the total cost per request, because “the orchestrator got chatty” is a regression that's invisible without that metric.

System designDesign a document-generation system with this pattern.

Orchestrator: one call with structured output producing sections: list[{title, brief, target_words}], capped at say 12. Validate: dedupe overlapping sections, check total length against the target. Dispatch: conditional edge returning one Send("write_section", s) per section, so all sections write concurrently in a single superstep. Collect: each worker returns {"sections": [{"idx": i, "text": ...}]} into an operator.add channel — note the index, because concurrent write order isn't guaranteed and you need to restore document order. Synthesise: sort by index, then a final pass for transitions and consistent voice.

Extras that show production thinking: a checkpointer so a 12-section document survives a crash without regenerating everything; an interrupt after the outline so a human can approve the structure before you spend twelve calls on it; and per-worker error capture so one failed section doesn't lose the other eleven.

4.5 Evaluator-optimizer loops ⭐

Generate, evaluate, revise, repeat. The most powerful pattern here and the one most likely to produce a runaway bill, because its natural termination condition is “when the critic is happy” and the critic may never be.

The four guards

The best version of this pattern gives the evaluator something objective to look at: unit test results, a linter, a schema validation, a retrieval check against sources. Code generation is the canonical fit precisely because “the tests pass” is a real signal, not an opinion. Likely interview questions
DesignHow do you stop an evaluator-optimizer loop from running forever?

Four guards, and you want all of them. A hard iteration cap in state, checked before the quality condition in the routing function. A score threshold so “good enough” is a defined number from a structured critic, not a vibe. Keep the best draft in its own channel and return that rather than the last one, because quality genuinely degrades on over-revision. An improvement floor: stop when the score gain between rounds is below ε, since you're paying for cosmetic edits at that point.

Plus recursion_limit on the config as a backstop — but treat hitting it as a bug, not a design.

ConceptualWhat makes a good evaluator?

Access to something the generator didn't have. Test results, compiler output, a schema validation error, retrieved sources to check claims against — objective signals produce real improvements. An evaluator that is the same model re-reading the same context with “is this good?” shares the generator's blind spots and mostly produces hedging.

Beyond that: explicit checkable criteria rather than a global quality judgement; structured output so you get a numeric score and a list of specific issues, not prose; and the issues fed back into the generator's prompt so the revision is targeted. If you can make the evaluator a tool call rather than a judgement — run the tests, validate the JSON — do that instead.

GotchaYour loop's output gets worse after round two. What's happening?

Over-revision. A critic asked to find issues will always find issues, so each round the generator makes changes that address increasingly marginal critiques, often damaging things that were fine. Text gets hedged and bloated; code accumulates defensive branches.

Three fixes: track and return the best-scoring draft, not the final one — this alone makes degradation harmless; give the critic an explicit “accept” option and a rubric where a good draft genuinely scores well, rather than a prompt that implies something must be wrong; and stop on marginal improvement. Two rounds is usually the sweet spot, and it's worth measuring rather than assuming.

4.6 The agent loop as a pattern

Listed last among the patterns deliberately: the agent loop is the most flexible shape and therefore the one you reach for when the others don't fit — not first.

As a pattern it is simply: model decides → tool executes → observation returns → repeat until no tool call. What distinguishes it from everything above is that the sequence and count of steps are not in your code. The other six patterns all have a shape you drew; this one's shape is drawn at runtime by the model.

In LangGraph it's two nodes and one conditional edge, or one line with create_agent. The engineering is not in building the loop — it's in the bounds you put around it: iteration cap, budget cap, tool gates, and a trace you can read afterwards.

Patterns compose

Real systems are rarely one pattern. A production research system is typically router → orchestrator-worker → evaluator gate → agent loop for the one branch that genuinely needs open-ended tool use. Recognising the composition — and keeping the agentic part as small as possible — is the design skill being tested.

Likely interview questions
DesignCan you mix patterns in one system?

You almost always should — real systems are compositions. A representative shape: a router classifies the request; simple categories go to a single call; one category goes to an orchestrator-worker fan-out for parallel research; its output passes an evaluator gate; and only the genuinely open-ended branch runs an agent loop.

The principle is to keep the agentic part as small as possible. Every request that can be answered by a deterministic branch should be, so the expensive, unpredictable path handles only the cases that need it. That's also what makes the system evaluable: you can measure the router's accuracy, the workers' coverage, and the agent branch separately.

ConceptualWhere does the engineering effort go in an agent loop?

Not into the loop — that's two nodes and an edge, or one create_agent call. It goes into the bounds and the surroundings: tool design (descriptions, schemas, error strings the model can recover from), the iteration and budget caps, approval gates on destructive tools, context management as history grows, and tracing good enough to reconstruct why the model chose what it chose.

A candidate who describes building the loop is describing the easy 10%. A candidate who describes the caps, the gates, the tool ergonomics and the trace is describing the part that determines whether it works in production.

5.1 What state actually is ⭐

Three different things get called “memory” in agent systems, and interviewers separate candidates by whether they keep them distinct.

A fourth thing sometimes gets called memory too — the context window, i.e. what you actually send to the model on this call. It is not a storage layer at all; it's a selection from the layers above. Keeping that distinction is what makes §5.6 make sense.

Likely interview questions
Very commonExplain the difference between state, checkpointer and store.

State is the live set of channel values during an invocation — messages, retrieved docs, counters. Without a checkpointer it exists only in memory for the duration of the call.

The checkpointer persists a snapshot of state per superstep, per thread. Its scope is one conversation, keyed by thread_id. It's what gives you resume, human-in-the-loop, crash recovery and time travel.

The store is cross-thread long-term memory: namespaced key-value (often with semantic search) holding user preferences, learned facts and profile data that should be available in every future conversation. You read and write it explicitly from nodes.

The sentence that settles it: the checkpointer remembers this conversation; the store remembers this user.

Gotcha“My agent doesn't remember what the user told it last week.” Diagnose.

Almost certainly a layer confusion: they're relying on the checkpointer, which is per-thread. Last week's conversation is a different thread_id, so its state is intact but invisible to this one.

The fix is a store: during (or after) a conversation, extract durable facts and write them to a namespace like ("memories", user_id); at the start of each run, retrieve relevant memories and inject them into the prompt. Two design points to add: extraction should be selective — writing every utterance to the store gives you a slow, noisy retrieval problem — and you need a policy for updating or invalidating facts, because “the user's favourite airline is X” can stop being true.

The alternative non-answer worth ruling out: reusing one thread_id forever so all history is in one thread. That technically works and then fails, because the thread grows without bound and every turn re-sends more history.

5.2 Checkpointers ⭐⭐

The checkpointer is the feature. Everything that makes LangGraph worth using over a loop is downstream of one design decision: state is written to durable storage at every superstep barrier.

Two consequences: never put credentials in state, and have an actual TTL/deletion story for old threads before you ship.

Likely interview questions
Very commonWhat does a checkpointer actually do, and what does a checkpoint contain?

It persists a snapshot of the graph's state at every superstep barrier, keyed by thread_id and checkpoint id.

A checkpoint contains: all channel values; the next field saying which nodes run next; any pending writes from nodes that completed before a failure; metadata including the step number and parent checkpoint id; and any active interrupt. The next field is the one candidates forget and it's the important one — a checkpoint is a resumable continuation, not just a data dump, which is why you can restore it in a different process days later.

What it unlocks, all from the same mechanism: pause/resume, human-in-the-loop, crash recovery, time travel, and forking a conversation from any past point.

System designWhich checkpointer would you use in production, and what do you watch?

Postgres — AsyncPostgresSaver in an async service — because you need durability, concurrent access from multiple app instances, and operational tooling you already have. Call .setup() once at deploy to create the tables, and put it behind a connection pool.

What to watch: write volume, since it's one write per superstep per run and a chatty graph multiplies that; state size, because large objects in channels are re-serialised every superstep — keep blobs external and store references; growth and retention, so you need a TTL or archival job for old threads, plus a deletion path for data-subject requests; and latency, since the checkpoint write is on the critical path of every superstep.

SQLite is fine for a local or single-process app; InMemorySaver is for tests only.

GotchaWhat happens if you compile a graph with no checkpointer?

It runs perfectly well — and silently loses every capability that depends on persistence. No thread memory (each invoke starts fresh, so a chatbot has no history), no interrupt/resume (calling interrupt raises), no get_state or get_state_history, no crash recovery, no time travel.

The reason it's a gotcha is that nothing warns you: a stateless one-shot pipeline is a legitimate use, so LangGraph can't treat the absence as an error. If you're building a conversational or long-running graph and it “doesn't remember”, the missing checkpointer and the missing thread_id are the first two things to check.

5.3 Threads and thread_id ⭐

A thread is a conversation. The thread_id is the key that ties a sequence of invocations to a shared, persisted history — and getting it wrong produces two opposite, equally confusing bugs.

Likely interview questions
CoreWhat is a thread, and where does thread_id come from?

A thread is one conversation — the sequence of checkpoints sharing a thread_id. Passing the same id in config["configurable"] across invocations makes them continue the same state; passing a different one starts fresh.

It comes from your application's model of a conversation, not from the framework: the chat session id, the ticket id, the workflow instance id. The rule is one thread per conversation — not per request (amnesia) and not per user forever (unbounded growth).

Production detail: namespace it, e.g. f"{tenant_id}:{user_id}:{conversation_id}", and treat it as a capability — always verify server-side that the authenticated user owns the thread they're asking for, because a thread id is a key to someone's conversation history.

System designHow do you handle multi-tenancy with threads?

Three layers, and you want all three. Namespaced ids so a thread key encodes the tenant. Authorisation on every request — resolve the tenant from the authenticated session, never from a client-supplied field, and check ownership before invoking. Storage isolation proportionate to the requirement: a tenant column with row-level security for most cases, separate schemas or databases where contractual isolation is required.

Also worth naming: per-tenant rate and cost limits so one tenant can't exhaust shared capacity, and per-tenant retention/deletion, because “delete this customer's data” must reach the checkpoint tables, not just your application tables.

DebugTwo users are seeing each other's messages. What happened?

They're sharing a thread_id. The usual causes: a hardcoded id left over from development ("thread_id": "1" in a demo that shipped); an id derived from something non-unique like a session name or a date; or the id coming from a client-supplied parameter with no server-side ownership check, which is the security version of the bug.

Fix immediately by deriving the id server-side from the authenticated user plus a conversation identifier, and add an authorisation check before every invoke. Then treat it as an incident: the checkpoint tables now contain cross-contaminated history that has to be found and purged.

5.4 Time travel and state editing

Because every superstep is checkpointed, you can rewind to any past point, change the state there, and run forward again — creating a branch rather than destroying history.

Three practical uses. Debugging: reproduce a failure by replaying from the checkpoint just before it, as many times as you like. What-if analysis: change one field and see how the run differs. Correction in production: an agent picked a wrong branch — rewind, fix the state, continue, without losing the work before the mistake. Note that update_state writes a new checkpoint whose parent is the one you targeted, so the original path remains in the history.

Replay is not a simulation

Replaying from a checkpoint re-executes the nodes, which means real LLM calls, real tool calls, real side effects. Time travel is not a dry run. If a node in the replayed range sends an email, replaying sends the email again — which is the same idempotency requirement durable execution imposes, arriving from a different direction.

Likely interview questions
ConceptualWhat is time travel and what's it for?

Because every superstep writes a checkpoint, get_state_history() gives you the full sequence, and you can resume from any of them by passing that checkpoint's config back into invoke. update_state lets you modify the state at that point first, which creates a fork — a new checkpoint whose parent is the one you targeted — leaving the original branch intact.

Three uses: debugging (replay deterministically from just before a failure, repeatedly); what-if analysis (change one field, compare outcomes); and production correction (an agent took a wrong turn — rewind, fix, continue, keeping everything it got right).

The caveat to volunteer: replay re-executes nodes for real — real model calls, real side effects. It's not a simulation.

CodingHow do you edit an agent's state mid-run?

graph.update_state(config, {"channel": value}). The update goes through each channel's reducer, which matters: on an add_messages channel, passing a message with an existing id replaces it, and passing a RemoveMessage deletes it, whereas a fresh message appends. You can also pass as_node="some_node" to make the update look as though that node produced it, which controls what the graph considers to run next.

The main use in practice is human-in-the-loop editing — a reviewer corrects a drafted tool call or removes a bad message before resuming. Do it through update_state, never by writing to the checkpoint store directly.

5.5 Human-in-the-loop ⭐⭐

The single most valuable production capability LangGraph offers. An agent that can pause mid-execution, wait indefinitely for a human, and then continue exactly where it stopped.

The node re-runs from the top on resume

interrupt() works by raising; on resume, LangGraph re-executes the whole node and the interrupt() call returns the resume value instead of raising. So anything before the interrupt in that function runs twice. Keep interrupt nodes tiny — do the expensive or side-effecting work in a separate node after the gate, never above the interrupt call.

The four HITL shapes

Approve/reject a proposed action. Edit — return a modified payload, e.g. a corrected tool argument or a reduced refund amount. Provide input — the agent asks a clarifying question and waits. Review and continue — a checkpoint for oversight where the human usually just says “proceed”. All four are the same mechanism with a different payload contract.

Likely interview questions
Very commonHow does human-in-the-loop work in LangGraph?

A node calls interrupt(payload). That raises a special exception which LangGraph catches: it checkpoints the state with next pointing at this node and surfaces the payload to the caller. The invocation returns — no process, connection or memory is held, so the graph can wait indefinitely.

Later, possibly days later and in a different process, you invoke the same thread_id with Command(resume=decision). LangGraph restores the checkpoint, re-runs that node, and this time interrupt() returns the decision instead of raising, so execution continues.

The gotcha to volunteer: because the node re-runs from the top, keep interrupt nodes small and put side effects after the gate. And it requires a checkpointer — interrupt without one raises.

System designDesign an approval gate for a refund agent.

Graph: investigate (read-only tools) → propose refund → approve node with interrupt → execute refund → notify. Policy: auto-approve under a threshold (say £20) with an audit record; interrupt between £20 and £500; require a second approver above that.

Payload: everything the human needs to decide without opening another system — amount, customer, order, reason, the agent's evidence, and prior refunds for this customer. Resume contract: {"approved": bool, "amount": optional, "note": str}, so a reviewer can approve a reduced amount rather than only yes/no.

Operations: the pending thread goes into a review queue with the thread_id; a timeout job auto-rejects after N days and notifies; the refund execution node is idempotent with an idempotency key, because it can be re-run on resume or after a crash; and every decision is written to an audit log with the approver's identity.

Gotchainterrupt() versus interrupt_before — what's the difference?

interrupt_before=["node"] at compile time is a static breakpoint: the graph always stops before that node, regardless of state. It's a debugging and inspection tool, and it can't carry a payload.

interrupt(payload) inside a node is dynamic: it fires only when your code decides to call it (so you can gate on the refund amount), and it carries a structured payload to the human and receives a structured decision back via Command(resume=...).

For product features — approval, editing, clarifying questions — use dynamic interrupt. Use interrupt_before for debugging and for coarse “always let a human see this stage” checkpoints.

DesignHow do you handle a human who never responds?

Treat the pending interrupt as a queue item with a deadline, because LangGraph itself will wait forever — that's the design. Concretely: when you interrupt, write a row (thread id, action, payload, created_at, assignee) to a review queue; run a scheduled job that finds items past their SLA and either escalates to another approver, sends a reminder, or resumes the thread with a default decision — usually reject, since the safe default for an irreversible action is not to do it.

Also expose the queue to operators, and make the timeout policy per-action rather than global: a £5 refund can auto-approve after a day, a £5,000 one should never auto-approve.

5.6 Short-term memory and the context window ⭐

The message list grows without bound; the context window does not. Every long conversation eventually needs a policy, and there are only four of them.

InteractiveContext strategy comparator

Four policies on the same conversation. “Fits” is about the window; “recall” is a rough measure of how much of the early conversation is still reachable. Summarisation is the only strategy that keeps both — at the cost of an extra LLM call and lossy compression.

The four policies

PolicyMechanismLoses

Two mechanical points that matter when you implement any of these. First, never break the tool-call pairing: if you trim away an assistant message containing a tool call but keep its ToolMessage (or vice versa), most providers reject the request outright. trim_messages has options for this — use them. Second, always keep the system message, which is why every trimming helper has an explicit flag for it.

Likely interview questions
Very commonA conversation exceeds the context window. What do you do?

Four options, in increasing sophistication. Trim to the last k tokens with trim_messages — free and instant, but the beginning is simply gone. Summarise + recent: when history exceeds a threshold, summarise the older turns into a single system-level message and keep the last k verbatim; one extra LLM call, and it preserves the thread of the conversation. RAG over history: embed past turns and retrieve the relevant ones — good for very long histories where relevance beats recency, but it loses continuity. Structured extraction: pull durable facts out into a store and drop the raw turns.

The production default is summary + last k, often combined with a store for facts that must persist across conversations. And two implementation traps: keep the system message, and never split a tool call from its ToolMessage — providers reject that outright.

CodingHow do you actually delete messages from state?

Return a RemoveMessage(id=...) for each message you want gone — the add_messages reducer understands it and removes the matching message. A summarisation node typically returns a list of RemoveMessage for the old turns plus one new summary message, all in a single update.

You can't do it by returning a shorter list, because add_messages appends; returning fewer messages adds nothing and removes nothing. And doing it by mutating state["messages"] in place is the bug from §3.3 — it bypasses the reducer and the checkpointer.

GotchaYour provider starts rejecting requests after you added trimming. Why?

You've almost certainly orphaned a tool call. Providers require that an assistant message containing tool_calls is followed by a ToolMessage for each call id, and a naive “keep the last 10 messages” window can cut between them — leaving either a tool call with no result or a result with no call. Both are protocol violations and produce a 400, not a degraded answer.

Fix by trimming on conversation boundaries rather than message counts: trim_messages supports start_on="human" and include_system=True for exactly this. The same rule applies to summarisation — summarise whole exchanges, not arbitrary message ranges.

5.7 Long-term memory and the Store ⭐⭐

The store is what makes an agent feel like it knows you. It is also where most teams over-build: writing everything, retrieving noise, and never invalidating anything.

What to store, and what not to

TypeExampleWorth storing?
Stable preferences“prefers metric units”, “works in EU timezone”Yes — high value, rarely changes
Profile factsRole, team, systems they ownYes — but needs an update path
Past outcomes“this fix worked for their setup”Yes, with a timestamp
Every utteranceRaw conversation logsNo — that's a search index, not memory
Volatile facts“is currently on call”No — fetch live, don't remember
Memory that is never invalidated becomes a liability

“The user's manager is Alice” is true until it isn't, and a confidently-retrieved stale fact is worse than no memory, because the agent asserts it. Every memory needs a timestamp, a way to be superseded (write the new fact and mark the old one inactive, don't silently accumulate both), and ideally a source so a human can adjudicate a contradiction.

Likely interview questions
Very commonWhat is the Store and how does it differ from the checkpointer?

The store is cross-thread, long-lived memory: a namespaced key-value store, usually with vector search over the values, that you read and write explicitly from nodes. Namespaces scope it — ("memories", user_id), ("policies", org_id).

The checkpointer is within-thread and automatic: it snapshots the whole graph state every superstep so one conversation can be resumed. The store is cross-thread and manual: nothing goes into it unless a node decides to put it there.

The clean summary: checkpointer = this conversation, automatic, whole state. Store = this user, deliberate, selected facts. They're complementary, and you'll normally compile with both.

System designDesign memory for an assistant used daily for a year.

Three tiers. Working memory: the message list in state, trimmed to a summary plus the last k turns. Episodic: per-conversation summaries written to the store at the end of each thread, so “what did we decide last Tuesday?” is answerable. Semantic: extracted durable facts and preferences in ("memories", user_id) with embeddings for retrieval.

Write path: a background extraction step at conversation end, not on every message — cheaper and less noisy. Deduplicate against existing memories before writing, and when a new fact contradicts an old one, supersede rather than append. Read path: retrieve top-k relevant memories at the start of a run and inject them into the system prompt, with a hard cap on how many tokens memory may consume.

Governance: timestamps and sources on every memory, a TTL for classes of fact that go stale, a user-visible “what do you remember about me” view, and deletion that actually reaches the store. That last point is usually what distinguishes a designed system from a demo.

GotchaWhat goes wrong when you store too much?

Retrieval quality collapses. If every utterance is a memory, top-k retrieval returns five vaguely-related fragments instead of the one fact that mattered, and the model is now reasoning over noise. You also pay for embedding and storing content that will never be useful, and you accumulate contradictions — three versions of the user's job title, all retrievable, none marked current.

The principle: memory is a curated summary, not a log. If you want full history search, build a search index over transcripts and expose it as a tool; keep the memory store small, high-signal and maintained.

5.8 Durability and crash recovery ⭐

Durable execution means a run survives the process that started it. It is the reason agents can take hours — and it imposes one hard requirement on your code.

durability modeWhen state is persistedTrade
"exit"Only when the run finishes or interruptsFastest; a crash loses the whole run
"async"Written concurrently with the next superstepGood default — near-full safety, little latency cost
"sync"Committed before the next superstep startsStrongest guarantee; a write on the critical path

The hard requirement: idempotency

Because a superstep can be re-executed after a crash, any node with a side effect must be safe to run twice. This is not an operational nicety — it is a structural consequence of the durability model, and it changes how you write nodes: side-effecting work goes in its own small node, carries an idempotency key derived from something stable in state (not a random UUID generated inside the node), and the external system must honour that key.

Likely interview questions
Very commonWhat happens if the process dies mid-run?

With a checkpointer, the last completed superstep is durable. On restart you invoke the same thread_id with None as input, and LangGraph restores that checkpoint — including next and any pending writes from nodes that had completed within the failed superstep — and continues. You lose at most one superstep of work, not the run.

Then state the requirement that falls out of it: the nodes in that superstep re-execute, so any side effect must be idempotent. And name the durability setting: "async" is the sensible default, "sync" when losing a superstep is unacceptable, "exit" only for throwaway runs.

System designHow do you make a node that sends an email safe under durable execution?

Three layers. Isolate it — the send goes in its own node with nothing else in it, so the re-run surface is as small as possible. Idempotency key — derive it deterministically from state (f"notify-{order_id}-{stage}"), never from a UUID generated inside the node, and pass it to the provider so a duplicate send is deduplicated on their side. Record the result in state — write the message id back, and check for it at the top of the node so a re-run short-circuits.

If the provider has no idempotency support, keep your own sent-log table keyed by that same deterministic key and check it transactionally. And where the action is expensive or irreversible, put an interrupt in front of it as well — belt and braces.

ConceptualWhich durability mode would you pick, and why?

"async" as the default: the checkpoint write happens concurrently with the next superstep, so you get near-full crash protection without putting a database round trip on the critical path of every step.

"sync" when losing even one superstep is unacceptable — a node performed an external side effect and the record of it must be committed before anything else runs. "exit" only for short, cheap, side-effect-free runs where restarting from scratch is genuinely fine; it's the fastest but a crash discards everything.

The trade in one line: you're choosing how much work you're willing to redo against how much latency you'll pay per superstep.

6.1 What a tool is ⭐

A tool is three things at once: a Python function, a JSON schema sent to the model, and a piece of prompt. Most tool bugs come from forgetting the third.

What the model receives is the name, the docstring, and the argument schema with its field descriptions. It never sees the body. So the function body determines what happens; the name, docstring and schema determine whether and how it gets called — and those are the parts you tune when tool selection goes wrong.

Binding and the ToolNode

model.bind_tools([...]) attaches the schemas to the model so it can emit tool calls. ToolNode (or create_agent) is what executes them: it reads tool_calls off the last message, runs each one — in parallel when there are several — and appends a ToolMessage per call id. Binding without executing gives you a model that proposes tool calls nobody runs, which is a surprisingly common first bug.

Likely interview questions
CoreWhat does the model actually see when you give it a tool?

Three things: the name, the docstring (the description), and the JSON schema of the arguments including every field description. It never sees the implementation.

The consequence that matters: those three artefacts are prompt. If the model calls the wrong tool, or passes a badly-formed argument, the fix is almost never in the function body — it's in the name, the description, or the schema. And they cost tokens on every single request, which is why a catalogue of 60 tools is both a selection problem and a cost problem.

CodingWhat's the difference between binding tools and executing them?

bind_tools attaches schemas to the model so its responses may contain tool_calls. Execution is separate: something has to read those calls, run the matching functions, and append a ToolMessage for each tool_call_id. In LangGraph that's ToolNode, or it's handled for you inside create_agent.

Two details worth adding: a single response can contain several tool calls, and ToolNode runs them concurrently; and every tool call must get a matching ToolMessage before the next model call, or the provider rejects the request as malformed.

6.2 Designing a tool the LLM can use ⭐⭐

This is where real agent quality is won or lost — far more than in the graph. A tool designed for a human developer is usually a bad tool for a model.

Granularity: the most consequential choice

Too coarse — one database_query(sql) tool — and you've delegated the hard part to the model and opened a large safety hole. Too fine — forty single-purpose tools — and selection degrades and your prompt is mostly schemas. The useful heuristic: one tool per user-meaningful action, with the parameters a human would need to specify. get_order(order_id), search_orders(email, status), refund_order(order_id, amount, reason) — not one orders(op, payload) and not fifteen variants of get.

The test that catches most bad tools

Show the tool's name, description and schema — and nothing else — to a competent colleague who doesn't know the codebase, and ask them when they'd call it and with what. If they hesitate, the model will too. That five-minute test finds more agent bugs than any amount of prompt tuning.

Likely interview questions
Very commonWhat makes a good tool for an LLM?

Start with the framing: the tool's interface is prompt, so design it for a reader who has no other context.

Concretely: a name that states the action; a description that says when to use it and when not to, naming the alternative tool; closed types (Literal/enum) wherever the value set is finite; few, flat, scalar arguments rather than one nested config object; a return value formatted for reading, with ids so the model can cite or chain; and an explicit empty result — “no orders found for that email” rather than [], because an empty list gives the model nothing to reason about and it tends to retry.

Then the test: hand a colleague only the name, description and schema and ask when they'd call it. Their hesitation predicts the model's.

DesignHow granular should tools be?

One tool per user-meaningful action, with the arguments a person would naturally specify.

Too coarse — a single execute_sql(query) — pushes the hard part onto the model, makes failures opaque, and hands it an enormous capability surface. Too fine — forty near-identical tools — degrades selection accuracy and fills the prompt with schemas you pay for on every call.

The signals: if the model regularly needs three calls to do one obvious thing, your tools are too fine; if one tool's arguments encode a mini-language (op, payload, mode), it's too coarse. And prefer splitting by risk as well as by function — a read tool and a write tool should be separate even if they hit the same table, so you can gate one and not the other.

DebugThe agent keeps passing a malformed argument. How do you fix it?

Fix it in the schema, not the prompt. In order: use a Literal or enum if the value set is closed — the model then literally cannot emit anything else under constrained decoding. Add format instructions in the field description (“ISO date, YYYY-MM-DD”) since the description is what it reads. Add numeric constraints (ge/le). Give a default so the model can omit it.

And make the failure recoverable: return a corrective error string from the tool — “invalid date '03/04/2026'; expected YYYY-MM-DD” — rather than raising. The model reads that and retries correctly, which turns a hard failure into a self-healing one.

6.3 Tool errors and retries ⭐

The default instinct — raise on failure — is usually wrong for an agent. An exception ends the run; a well-worded error message lets the model fix itself.

Retries multiply

Three retries inside the tool, times three at the node's RetryPolicy, times an agent loop that tries the tool again after seeing the error, is 27 calls to a struggling dependency — the classic accidental self-DDoS. Pick one layer to own transient retries, use exponential backoff with jitter, and make the other layers pass through.

Likely interview questions
Very commonShould a tool raise an exception or return an error message?

Depends on who can fix it, and that framing is the answer.

Return a message when the model can act on it: bad arguments, no results, ambiguous input. “Invalid date '03/04/2026'; expected YYYY-MM-DD” lets the agent self-correct on the next iteration, turning a failure into a recoverable step. Retry inside the tool for transient infrastructure errors — 429s, timeouts — with backoff and jitter, because the model can't do anything useful with a rate limit. Raise for genuine infrastructure failures you want the node's RetryPolicy or your alerting to handle, and for permanent errors like invalid credentials where retrying is pointless and harmful.

Never return a raw stack trace: it wastes tokens, leaks internals, and gives the model nothing actionable.

System designHow do you stop retries from amplifying?

Decide one owner per failure class and make the other layers transparent. Typically: transient network errors are owned by the tool (3 attempts, exponential backoff with jitter); node-level RetryPolicy is reserved for errors the tool deliberately raised; and the agent loop is bounded so it can't keep re-calling a broken tool indefinitely.

On top of that: a circuit breaker per dependency, so after N consecutive failures the tool returns “this service is currently unavailable” immediately instead of waiting on timeouts; a global timeout for the whole run; and metrics on retry counts per tool, because silent retry amplification shows up as latency long before it shows up as errors.

CodingHow do you configure retries on a node?

builder.add_node("fetch", fetch, retry_policy=RetryPolicy(max_attempts=3)), optionally with a retry_on predicate so you only retry the exception types that are actually transient — retrying a ValueError from your own validation just wastes time.

Two things to say alongside it: retries re-execute the node, so the idempotency requirement from durable execution applies here too; and a node-level retry doesn't help with a model that's making a bad decision — it only helps with flaky infrastructure. Confusing the two leads to retrying your way around a prompt problem.

6.4 Tool choice and too many tools ⭐

Selection accuracy degrades as the catalogue grows, and the degradation is driven more by similarity between tools than by raw count.

InteractiveTool-catalogue selection simulator

An illustrative model, not a benchmark: accuracy falls with catalogue size and falls much faster when descriptions overlap. Tool retrieval fixes both problems at once by only ever showing the model a small, relevant subset — at the cost of a retrieval step that can itself miss the right tool.

What to do as the catalogue grows

Merge tools that overlap — two tools the model confuses are usually one tool with a parameter. Namespace by domain so names disambiguate (github_create_issue vs jira_create_issue). Route first: a cheap classifier picks a domain, and the agent for that domain sees only its own tools. Tool retrieval: embed the tool descriptions and bind only the top-k relevant to this request. And tool_choice when you need to force behaviour — "auto", "any" (must call something), "none", or a named tool.

Likely interview questions
Very commonYour agent has 50 tools and picks the wrong one. What do you do?

First, note the real cause: degradation is driven more by similarity between tools than by count. Fifty clearly-distinct tools work better than twelve that overlap.

Then, in order of effort: merge overlapping tools — the ones being confused are usually one tool with a parameter. Sharpen descriptions with explicit “use this when… do NOT use this for X, use y_tool” lines. Namespace by domain so names disambiguate. Route first — a cheap classifier picks a domain and the sub-agent for that domain sees only its 6 tools, which also cuts prompt cost. Tool retrieval — embed descriptions, bind only the top-k for this request.

And mention the cost angle: 50 schemas is a fixed per-request token bill before any conversation history, so shrinking the visible set helps latency and cost as well as accuracy.

CodingWhat is tool_choice and when would you set it?

It forces the model's tool-calling behaviour: "auto" (default — call one if useful), "any"/"required" (must call some tool), "none" (must answer in text), or a specific tool name.

Uses: forcing a specific tool on the first step of a pipeline where retrieval is mandatory; "any" when the model keeps answering from parametric knowledge instead of looking things up; "none" for a final synthesis turn where you want prose, not another tool call.

The caution: forcing a call when none is appropriate produces a fabricated call with invented arguments, because the model must emit something. Use it for a specific step, not as a global setting.

DesignHow does tool retrieval work, and what's the risk?

Embed each tool's name and description; at request time, embed the user's query (or the current state) and retrieve the top-k most similar tools; bind only those to the model for this call. The catalogue can then be arbitrarily large while the model only ever sees, say, eight schemas.

The risk is that you've added a retrieval failure mode in front of a selection failure mode: if the right tool isn't in the top-k, the model can't call it and will confidently do something else instead. Mitigations: always include a small set of always-on tools (search, clarify, finish); use a generous k; retrieve on the current step's intent rather than only the original question, since what the agent needs changes mid-run; and log retrieval misses so you can see the failure rather than infer it from bad answers.

The model will eventually try something you didn't anticipate — through confusion, or because someone engineered the input to make it. Your defence has to be structural, not persuasive.

Likely interview questions
System designHow do you give an agent database access safely?

Capability first. The agent connects with a role that has SELECT on specific views and nothing else — no write, no DDL, no access to other schemas. That makes “drop the table” impossible rather than discouraged.

Then defence in depth: parse the SQL with a real parser (not a regex) and reject anything that isn't a SELECT; allow-list tables; wrap the query with a LIMIT and a statement timeout; expose views rather than base tables so column-level exposure is deliberate; and log every query with the thread and user for audit.

Better still where it fits: don't hand it raw SQL at all. Offer parameterised tools — get_orders(customer_id, since) — so the query shapes are ones you wrote. Raw SQL is a last resort for genuinely open-ended analytics, and then only against a read replica.

Very commonHow do you prevent an agent from doing something destructive?

Layered, and explicitly not in the prompt. 1. Capability — don't grant the permission; the agent's credentials should make the destructive action impossible. 2. Validation — inside the tool, parse and allow-list what's being asked. 3. Approval — an interrupt before any irreversible action, with the proposed action shown to a human. 4. Sandbox — for code execution, an ephemeral container with no network, a CPU/memory quota and a hard timeout. 5. Reversibility — prefer soft deletes, staged changes and undo paths so a mistake is recoverable.

The prompt is layer 5 in importance: useful for reducing how often you hit the other controls, worthless as a control itself, because any instruction in the context can be overridden by other content in the context.

DesignThe agent needs to run arbitrary user code. How?

In an isolated, ephemeral sandbox, never in your process. Concretely: a container or micro-VM per execution, no network egress by default, read-only filesystem except one scratch directory, CPU/memory limits, a hard wall-clock timeout, no credentials or environment variables from the host, and destruction after the run.

Then bound the blast radius further: cap output size (a program printing 500 MB will otherwise take out your logging), rate-limit executions per thread, and log the code alongside the run for audit. Use a managed code-execution service if one is available — this is a category where rolling your own isolation is a poor use of risk budget.

Worth saying plainly: “we sanitise the code with a prompt” is not an answer. Isolation is the control.

6.6 MCP — the Model Context Protocol ⭐

MCP standardises how tools are exposed to models, the way LSP standardised how language features are exposed to editors. It is the clearest example of an integration layer that actually settled.

The problem it solves

Without a standard, connecting m agent frameworks to n tool providers is m × n bespoke integrations. With a protocol it's m + n: each framework implements a client once, each provider implements a server once. An MCP server exposes tools (callable functions), resources (readable context) and prompts (reusable templates) over stdio for local processes or HTTP/SSE for remote ones.

A third-party MCP server is code you're trusting

Its tool descriptions go straight into your prompt — a malicious or compromised server can inject instructions there. Its tools run with whatever access you granted. And a server can change its tool set between connections. Treat MCP servers like dependencies: pin them, review them, run untrusted ones sandboxed with least privilege, and don't wire an unvetted server into an agent that holds real credentials.

Likely interview questions
ModernWhat is MCP and why does it matter?

The Model Context Protocol — an open standard for how applications expose tools, resources and prompt templates to LLM clients. Analogy that lands: it's LSP for tools. Before LSP, every editor needed a bespoke integration with every language; after it, each side implements the protocol once.

The value is turning an m × n integration problem into m + n. A vendor writes one MCP server and it works with any MCP-capable agent; a framework writes one client and gets the whole server ecosystem. It runs over stdio for local processes and HTTP/SSE for remote ones.

In LangGraph you consume it with langchain-mcp-adapters, which turns MCP tools into ordinary LangChain tools — so from the graph's perspective nothing is special about them. And as of 2026 it's the clearest case of a layer that actually standardised, which is worth saying because most agent protocols haven't.

DesignWhat are the security implications of using third-party MCP servers?

Three, and they're specific. Prompt injection via tool descriptions: the server controls text that goes directly into your model's context, so a malicious server can inject instructions. Capability grants: its tools execute with whatever access you gave the process — a filesystem server pointed at / is a filesystem server with root's reach. Mutable tool sets: a server can present different tools on a later connection, so what you reviewed isn't necessarily what runs.

Controls: treat servers as dependencies — pin versions, review the source, prefer first-party or well-known ones; run them sandboxed with least privilege (scoped directories, scoped tokens, no ambient credentials); consider pinning or reviewing the tool list at startup and alerting on change; and keep destructive MCP tools behind the same approval gates you'd apply to your own.

ConceptualWould you build your internal tools as MCP servers?

Sometimes. Yes when the tools have multiple consumers — several agents, an IDE assistant, a desktop client — because then you get the m + n benefit and a single place to maintain the interface. Yes when a team wants to own and version its tool surface independently of the agent teams.

No when there's exactly one consumer: a plain @tool function in the same repo is simpler, faster (no transport hop), easier to test, and easier to debug. Adding a protocol boundary to a single-consumer integration is architecture for its own sake.

The useful rule: MCP is for crossing an ownership boundary. If there's no boundary, don't manufacture one.

7.1 Why RAG is a tool, not a stage ⭐

One framing shift explains everything in this part: in a pipeline, retrieval always happens; in an agent, retrieval is something the model decides to do.

What the agent gains: it can skip retrieval for questions that don't need it, rewrite the query into something the index can actually match, retrieve several times from different sources, and react to poor results by trying again. What you lose is the guarantee that retrieval happened at all — which is why evaluation gets harder, and why §7.6 exists.

Scope note

This part covers retrieval inside an agent. The retrieval internals — chunking, embeddings, hybrid search, rerankers, index choice, evaluation metrics — belong to the RAG subject, which goes far deeper. Interviews for agentic roles usually test the orchestration side covered here, and expect competence rather than depth on the internals.

Likely interview questions
Very commonWhat's the difference between RAG and agentic RAG?

Who decides whether and how to retrieve. In classic RAG, retrieval is a fixed pipeline stage — every query is embedded, the top-k chunks are fetched, and they're stuffed into the prompt, whether or not that helps. In agentic RAG, retrieval is a tool the model chooses to call.

That buys four things: skipping retrieval when the question doesn't need it (“summarise what you just told me”); query rewriting, so the search string is one the index can match rather than the user's raw phrasing; multiple retrievals, possibly from different sources, for multi-part questions; and reaction — if the results are poor, try a different query or a different source.

The costs: higher latency and token spend, non-deterministic behaviour, and much harder evaluation, because a bad answer might come from bad retrieval, a bad query, or good retrieval the model ignored.

DesignWhen is plain pipeline RAG the better choice?

When the question shape is predictable and retrieval is always the right move — a documentation Q&A bot, a policy lookup, a “search our knowledge base” feature. In those cases the agent's flexibility buys nothing and costs an extra round trip per request plus unpredictable behaviour.

The tell is the same as everywhere else in this subject: can you draw the flow in advance? If retrieval always happens exactly once with a query you can construct deterministically, build the pipeline. Add the agent when you observe real cases the pipeline handles badly — multi-hop questions, questions needing a different source, questions that don't need retrieval at all — rather than in anticipation of them.

7.2 The retrieval ladder ⭐

Enough of the retrieval stack to be credible: what each rung adds, and roughly what it costs. You should be able to name the rung you'd add next and why.

RungWhat it addsCost
1 · Dense vector searchSemantic matching — finds paraphrasesEmbedding + ANN index
2 · Hybrid (BM25 + dense)Exact terms: error codes, product names, IDsSecond index; fusion (usually RRF)
3 · RerankingCross-encoder reorders top-50 → top-5; biggest single quality win+100–300 ms, per-query model call
4 · Query transformationRewrite, decompose, HyDE, multi-query+1 LLM call before retrieval
5 · Metadata filteringRestrict by date, tenant, doc type, permissionsRequires clean metadata at ingest

The order matters. Hybrid then reranking is where most of the improvement lives, and both are cheap to add. Query transformation is what an agent gives you for free — the model rewriting its own query is rung 4. And rung 5 is not optional in any multi-tenant system: permission filtering must happen in the retrieval query, not by asking the model to ignore documents it shouldn't have seen.

Likely interview questions
RetrievalYour retrieval quality is poor. What do you try, in order?

Measure first — build a small set of questions with known-correct documents and compute recall@k. Without that you're guessing, and most “retrieval” problems turn out to be generation problems or vice versa.

Then, in order of value per unit effort: hybrid search (add BM25 alongside dense and fuse with RRF) — it fixes the single most common failure, exact terms like error codes and product names that embeddings blur. Reranking with a cross-encoder over the top ~50 — usually the largest single quality jump. Chunking review — chunks too small lose context, too large dilute the embedding; contextual chunking (prepending a document-level summary to each chunk) helps a lot. Query transformation — rewrite or decompose. Metadata filters to cut the candidate set.

And check the unglamorous causes: is the content even in the index, is ingestion up to date, are permissions filtering out the right document?

ConceptualWhy does hybrid search beat dense alone?

Because the two methods fail on different things. Dense embeddings capture semantics, so they find paraphrases — but they blur exact tokens, which means an error code like ERR_4021, a product SKU or a rare proper noun can be represented almost identically to its neighbours. BM25 is the opposite: it nails exact and rare terms and completely misses paraphrase.

Fusing them — typically with reciprocal rank fusion, which needs no score calibration between the two systems — gets both. In practice the wins show up exactly where users are most annoyed: searching for a specific identifier they copied out of an error message.

System designHow do you enforce document permissions in RAG?

In the retrieval query, as a hard filter, using the caller's identity resolved server-side. Every chunk carries the ACL metadata it inherited at ingest; the search is issued with a filter on that metadata; documents the user can't see are never retrieved and therefore never reach the model.

What not to do, and why: post-filtering after retrieval means you fetched the content into your process and it may already be in a trace or a log; and asking the model to ignore unauthorised documents is not access control at all — the content is in the context, and anything in the context can leak into the answer.

Two extras that matter: permissions change, so re-check at query time rather than trusting an index built last week; and be careful with caches and summaries, which can carry restricted content across a boundary the raw index would have blocked.

7.3 Agentic RAG ⭐⭐

The concrete pattern: retrieval as a tool, a grading step, and a bounded retry loop. This is the design most interviewers are fishing for when they ask you to “improve our RAG”.

The three decisions that define the pattern

Whether to retrieve — a router or the model's own tool choice. Whether the results are good enough — a grading step, which is what turns naive RAG into corrective RAG. What to do when they aren't — rewrite the query, try a different source, ask the user, or answer honestly that you don't know. That last option is the one systems most often omit, and its absence is why so many RAG bots hallucinate rather than decline.

The retrieval loop that never converges

If the answer simply isn't in the corpus, the grader will keep saying “not relevant” and the rewriter will keep producing variations forever. Cap attempts at two or three, and make the fallback branch a first-class outcome — “I couldn't find this in our documentation; here's what I did find, and here's who to ask” is a good answer, not a failure.

Likely interview questions
System designDesign an agentic RAG system for an internal knowledge base.

Graph: route (does this need retrieval at all?) → retrieve (hybrid + rerank, filtered by the user's permissions) → grade (structured: relevant? why not? better query?) → conditional: generate if relevant, rewrite → retrieve if not and attempts < 2, fallback otherwise → verify (are the claims grounded in the retrieved text?) → answer with citations.

State: messages, docs with ids, attempts counter, and the graded verdict. Guards: attempt cap checked before the quality condition; a fallback branch that says “not in the knowledge base” rather than improvising.

Production concerns to volunteer: permission filtering inside the retrieval query, not after; citations back to chunk ids so users can verify; a checkpointer so a slow multi-hop question survives a restart; caching on the retrieval tool since the same questions recur; and an eval set of question/expected-document pairs so you can measure recall separately from answer quality.

DebugYour agent retrieves good documents and still answers wrongly. Where's the bug?

Retrieval isn't the problem, so look downstream. In order: are the documents actually in the prompt? Check the trace — truncation, a trimming middleware, or a state channel that got overwritten will silently drop them. Position: with many chunks, content in the middle gets attended to less; rerank so the best is first and cut k. Conflict: retrieved content that contradicts the model's parametric knowledge often loses — the prompt must say explicitly to prefer the provided sources and to say when they disagree. Prompt framing: if it doesn't instruct “answer only from the context; if it isn't there, say so”, the model will helpfully fill gaps. Chunk boundaries: the right document, cut so the crucial sentence is in the neighbouring chunk.

The systematic version of this answer: instrument the two halves separately — retrieval recall against known-correct docs, and grounded-answer accuracy given gold documents. Whichever number is bad tells you where to work.

DesignShould the query rewrite happen before or after the first retrieval?

Both, for different reasons. A rewrite before the first retrieval fixes predictable mismatches — resolving pronouns and references from the conversation (“what about the second one?” is unsearchable), expanding acronyms, and translating conversational phrasing into index vocabulary. That's cheap and nearly always worth it in a multi-turn system.

A rewrite after a failed retrieval is corrective: now you have evidence about why it failed, and the grader can suggest a specific better query. That's more targeted but costs a wasted retrieval first.

Practical shape: always do the cheap conversational rewrite up front, and reserve the corrective rewrite for the grading loop, capped at two attempts.

Two named papers that come up constantly. They solve adjacent problems and they're often confused, so being precise about the difference is an easy differentiator.

In practice most production systems implement a simplified hybrid: grade the retrieved documents (CRAG's idea), and check the generated answer against them before returning it (Self-RAG's grounding check). Likely interview questions
ModernExplain CRAG and Self-RAG, and how they differ.

CRAG (Corrective RAG) adds a lightweight retrieval evaluator that grades the retrieved documents into three buckets: correct (use them), incorrect (discard and fall back to web search), ambiguous (combine both). It targets one failure: retrieval returned rubbish and the generator used it anyway.

Self-RAG trains the model to emit reflection tokens at several decision points: should I retrieve for this query at all? is this passage relevant? is my statement supported by it? is the response useful? It targets two failures — unnecessary retrieval, and ungrounded generation.

The crisp difference: CRAG grades the retrieval; Self-RAG makes the model reflect on both the need for retrieval and the grounding of its own output. And the practical note: most teams implement the ideas — a grading node and a grounding check — as ordinary structured-output calls in a graph, rather than the papers' full training setups.

DesignHow would you implement a CRAG-style grader cheaply?

A small, fast model with structured output over the top-k documents: {relevant: bool, confidence: float, missing: str}. Grade the set rather than each document individually — one call, not k calls — unless you specifically want per-document filtering.

Cheaper still, and worth trying first: use the reranker's score as the grade. If the top reranked document scores below a calibrated threshold, treat the retrieval as failed. That costs nothing extra because you were reranking anyway, and it's more consistent than an LLM judgement.

Then the fallback ladder: rewrite the query and retry (capped), broaden to another source or the web, and finally decline. Log which branch fired — the rate of “retrieval graded bad” is one of the most useful health metrics a RAG system can have.

GotchaWhat's the risk of falling back to web search when retrieval fails?

You've silently changed the trust level of the answer. An internal knowledge base is curated and authoritative; the open web is neither. An agent that quietly substitutes a web result for a policy document can give a confidently wrong answer about your policy based on someone else's blog post.

Controls: label the source in the answer so the user knows it's external; restrict the fallback to question types where public information is legitimate (general technical questions, yes; “what is our refund policy”, no); allow-list domains; and for internal-policy questions make the fallback “I couldn't find this internally” rather than a web search at all.

7.5 Grounding and citation

Retrieving the right documents doesn't guarantee the answer reflects them. Grounding is a separate property, and it needs its own check.

Three levels of citation

Document-level — “sources: doc A, doc B”. Easy, and nearly useless for verification: the user still has to read both. Chunk-level — each claim links to the chunk it came from. Requires the model to emit chunk ids inline, which structured output makes reliable. Span-level — highlight the supporting sentence. Best UX, hardest to get right; often done by post-hoc matching of the claim against the source text rather than by asking the model.

The verification step is separate from citation: after generating, ask a cheap model “is every claim in this answer supported by the provided sources?” with structured output listing unsupported claims. That's Self-RAG's grounding check as one extra call, and it's one of the highest-value additions to a production RAG system — especially because you can make its failures visible rather than silent, by flagging or removing unsupported sentences.

Likely interview questions
DesignHow do you make an agent cite its sources reliably?

Give it ids to cite and make citation part of the output schema. Concretely: format retrieved chunks with explicit markers ([doc-17]) in the context; use with_structured_output with a schema like {answer: str, citations: list[{claim: str, chunk_id: str}]} so citations aren't optional prose the model may forget; then validate that every cited id actually exists in what you retrieved — models do invent plausible ids.

Add a grounding check as a separate step: a cheap model comparing each claim against its cited chunk, returning any unsupported claims. Flag or strip those rather than shipping them. And render citations as links back to the source in the UI, because a citation nobody can follow doesn't build trust.

ConceptualRetrieval was correct but the answer is hallucinated. Is that a RAG failure?

It's a grounding failure, not a retrieval failure, and separating those is the point of the question. Retrieval succeeded; generation didn't stay faithful to what it was given.

Causes and fixes: the prompt didn't instruct the model to answer only from context and to say when the context is insufficient; too many chunks so the relevant one is buried (rerank and cut k); a conflict between retrieved content and the model's parametric knowledge, where the prompt must state which wins; or a question the context genuinely doesn't answer, where the model helpfully improvises rather than declining.

The structural fix is a separate grounding verification step — you cannot fix this by hoping the generator behaves, and you can measure it independently of retrieval metrics.

In a pipeline you can measure recall@k directly. In an agent the query changes between attempts, retrieval may happen several times or not at all, and the final answer depends on a chain of decisions. You need to instrument the pieces separately.

Likely interview questions
System designHow do you evaluate an agentic RAG system?

Decompose it — end-to-end accuracy alone is undiagnostic. Measure at least four things separately.

Decision correctness: on questions that need retrieval, did it retrieve; on those that don't, did it skip? Groundedness: an LLM judge checking each claim against the retrieved text. Answer correctness: judged against a reference.

Plus operational metrics — retrieval calls per question, p95 latency and cost — because a system that quietly makes five retrieval calls per answer is a regression even if accuracy held.

DebugRecall@k is 95% but users complain the answers are wrong. What now?

The retrieval half is healthy, so the problem is between the retrieved documents and the final answer. Check, in order:

Groundedness — run a judge over recent traces; if claims aren't supported by the retrieved text, it's a generation-prompt problem. Context assembly — are all retrieved docs actually reaching the model, or is trimming, truncation or a state overwrite dropping them? Ranking within k — recall@10 being high doesn't mean the right document is first; measure MRR or recall@3 and rerank. Question/answer mismatch — for multi-hop questions, each hop's document may be retrievable while the model fails to combine them. The eval set itself — a 95% recall on questions that don't resemble real traffic is a measurement of the wrong thing; sample actual user queries.

8.1 When multi-agent earns its cost ⭐⭐

The most valuable thing you can say about multi-agent architectures is when not to build one. The honest default in 2026 is that one well-instrumented agent with good tools beats three agents passing messages.

The three cases where it genuinely pays

CaseWhat makes it realThe test
Separable expertiseDifferent prompts, different tools, different modelsWould the system prompts actually differ, or just say “you are the X agent”?
Context pressureOne agent's context can't hold the whole jobAre you actually near the window, or is it aesthetic?
Organisational boundariesDifferent teams own, deploy and version different agentsIs there a real ownership boundary, or one team drawing boxes?

Notice what's absent: “the task has several steps” is not a reason — that's a workflow. “It feels more modular” is not a reason — nodes are already modular. And “the tasks are different in kind” is usually satisfied by different tools on one agent, which costs nothing extra.

What every extra agent costs you

An extra LLM call per hop (latency and tokens, sequentially); context loss at every boundary, because the receiving agent sees a summary rather than the full history; a new failure mode — agents ping-ponging or each assuming the other did the work; and a harder trace, since debugging now means reconstructing a conversation between programs. Three agents is not 3× the complexity, it's closer to 3² — the interactions are the hard part.

Likely interview questions
Very commonWhen would you use a multi-agent architecture?

Lead with restraint: most of the time I wouldn't — one agent with well-designed tools handles the majority of what people reach for multi-agent to do, at a fraction of the latency, cost and debugging burden.

Three cases where it earns its keep. Genuinely separable expertise — the sub-agents need materially different system prompts, tool sets, and possibly different models; a “research agent” and a “writing agent” whose prompts differ only in the first sentence don't qualify. Context pressure — the work genuinely doesn't fit one context window, so splitting is a compression strategy. Organisational boundaries — different teams own, version and deploy different agents, and the seam is a real one.

Then name the costs: an extra LLM call per hop, context loss at every boundary, coordination failure modes, and traces that are much harder to read.

DesignSomeone proposes five agents for a document pipeline: research, outline, write, edit, format. What do you say?

That's a workflow, not a multi-agent system — the steps are known, fixed and sequential, so encode them as five nodes in one graph. You get the same modularity, and you keep a single state, one trace, no handoff protocol, and no coordination failures. Nodes can even use different models and prompts, which is most of what people actually want from “separate agents”.

Then find the part that is agentic, if any: the research step, where the number and order of searches depends on what's found, is a genuine agent loop. So the answer is usually “a workflow with one agentic node”, plus a parallel fan-out for section writing.

Volunteering the distinction — separate agents versus separate nodes — is what makes this a strong answer rather than a contrarian one.

ConceptualWhat's the difference between a multi-agent system and a graph with several nodes?

Autonomy at the boundary. In a multi-node graph, you wrote the edges — control moves where the graph says. In a multi-agent system, each agent has its own loop, its own prompt, its own tools, and the transfer of control is itself a decision an LLM makes (a supervisor routing, or an agent calling a handoff tool).

The practical implication is which failure modes you own. A multi-node graph can't ping-pong, can't lose context at a boundary you didn't define, and can't have two components each assume the other did the work. A multi-agent system can do all three, which is why the bar for choosing it should be high.

8.2 Supervisor ⭐

One coordinator decides which specialist runs next; specialists report back to it. The most common architecture, and the easiest to reason about — because control always returns to one place.

StrengthWeakness
One place holds the plan — easy to reason about and auditThe supervisor is a bottleneck: every hop costs a supervisor call
Adding a specialist is a local changeLatency is 2 × hops model calls, all sequential
Termination is centralised and easy to boundThe supervisor must summarise well or context is lost each hop
Likely interview questions
CoreDescribe the supervisor pattern and how you'd implement it.

A coordinator agent decides which specialist runs next; each specialist does its work and returns control to the supervisor, which decides again, until it decides to finish.

Implementation: the supervisor is a node returning Command(goto=chosen, update={...}) — with the return type annotated Command[Literal[...]] so the graph can be drawn — driven by a structured-output call returning {next, instruction}. Each specialist has a normal edge back to supervisor.

Two things to add that show experience: bound the hops with a counter checked before the model call, because a supervisor can bounce between two specialists indefinitely; and be deliberate about what each specialist sees — passing the whole message history is simple but expensive and noisy, while passing a summary risks losing detail. That choice is the supervisor pattern's main design decision.

DesignWhat's the main weakness of a supervisor, and how do you mitigate it?

It's a sequential bottleneck. Every transition costs a supervisor LLM call, so n specialist steps means roughly 2n model calls, all sequential — latency adds up fast and the supervisor's own context grows with every hop.

Mitigations: let the supervisor dispatch several specialists in parallel when the subtasks are independent, by returning multiple Sends instead of one goto; use a cheap fast model for the supervisor, since routing is an easy task; let specialists hand off directly for common adjacent pairs (a swarm edge inside a supervisor architecture); and cap hops so a degenerate loop is bounded.

8.3 Swarm and handoffs ⭐

No coordinator. Each agent can transfer control directly to another by calling a handoff tool. Lower latency, and considerably harder to keep under control.

Three details in that snippet are the ones interviewers look for. graph=Command.PARENT — without it you can only route inside the current subgraph. The ToolMessage — every tool call needs a matching result or the provider rejects the next request. And active_agent in state — with a checkpointer, that's what lets the conversation resume with the right agent tomorrow rather than restarting at the entry point.

Swarms ping-pong

Agent A decides this is really B's problem; B decides it's really A's. Without a coordinator there's nothing to notice. Guards: a hop counter with a hard cap; recording the handoff history in state and refusing a transfer back to an agent that just handed off; requiring a reason string, which measurably reduces reflexive transfers; and a default agent that must resolve or escalate rather than transfer.

InteractiveArchitecture comparator — topology, latency, cost

Model calls counted sequentially; a supervisor pays one routing call per hop, a swarm pays a handoff tool call instead (cheaper, but with no central place to bound the loop), and a hierarchy pays two levels of routing. The single-agent row is the baseline you should always compute before choosing anything else.

Likely interview questions
CoreSupervisor or swarm — how do you choose?

Supervisor when you want control: one place holds the plan, termination is centralised and easy to bound, the trace is linear and auditable, and adding a specialist is a local change. The cost is a routing call per hop, so it's slower and pricier.

Swarm when you want directness: agents hand off to each other via tools, so there's no coordinator round trip, which suits customer-support-style flows where triage transfers to a specialist who mostly finishes the job. The cost is that nothing is watching — no central place to detect ping-pong or enforce a hop budget.

My default is supervisor, because the debuggability is worth the extra calls, and I'd add direct handoff edges for the two or three transitions that are common and obviously one-directional. With a swarm, I'd insist on a hop cap and handoff history in state from day one.

CodingHow is a handoff actually implemented?

As a tool whose implementation returns a Command. The agent calls transfer_to_billing(reason=...); the tool returns Command(goto="billing", graph=Command.PARENT, update={...}).

Three details that matter. graph=Command.PARENT, because the tool executes inside the calling agent's subgraph and without it you can only route within that subgraph. A ToolMessage in the update carrying the same tool_call_id, because an assistant tool call with no matching result is a protocol error at the next model call. And active_agent written into state, so that with a checkpointer the conversation resumes with the correct agent rather than at the entry point.

Making the handoff a tool rather than an edge is deliberate: it appears in the model's catalogue with a description, so “when should I transfer” becomes a documented decision rather than an implicit one.

DebugTwo agents keep transferring the conversation back and forth. Fix it.

Immediate stop: a hop counter in state with an operator.add reducer, checked before any handoff; past the cap, route to a default agent that must resolve or escalate to a human.

Then fix the cause. Keep a handoff history in state and refuse a transfer back to the agent that just handed off. Require a reason argument on the handoff tool — being forced to articulate why measurably reduces reflexive transfers. Sharpen the handoff tool descriptions with explicit “transfer only if…” conditions, and check whether the two agents' scopes genuinely overlap, in which case merge them. Finally, make sure the receiving agent gets enough context: ping-pong is often two agents each concluding “I don't have what I need for this” because the handoff dropped the history.

8.4 Hierarchical teams

Supervisors of supervisors. Occasionally the right answer at genuine scale, and much more often a sign that someone enjoyed drawing the org chart.

The structure: a top-level lead routes to team supervisors, each of which routes to its own specialists. Each team is a subgraph with its own state, so the top level's context stays small. That's the real benefit — context isolation at scale — and it's why the pattern appears in systems with, say, twenty specialists where a flat supervisor's prompt would list twenty options and its history would accumulate all of their outputs.

The cost is bluntly arithmetic: two levels of routing before any work happens, so a single specialist step costs three model calls before the specialist even starts. Adopt it when a flat supervisor is demonstrably struggling — not in anticipation.

Likely interview questions
DesignWhen is a hierarchy actually justified?

When a flat supervisor is measurably failing — its routing accuracy has dropped because it's choosing between twenty specialists, or its context has grown unmanageable because every specialist's output accumulates in one message list. Both are real problems at scale, and hierarchy solves them by context isolation: each team is a subgraph with its own state, so the lead only ever sees team-level summaries.

It's not justified by organisational aesthetics. The cost is two routing calls before any work starts, plus a second layer of context loss at the team boundary. If you can't point at a specific metric a flat supervisor is failing on, you're paying that for nothing.

CodingHow do you build a hierarchy in LangGraph?

Each team is a compiled subgraph containing its own supervisor and specialists, added as a node in the top-level graph. The top-level lead routes between team nodes with Command; each team subgraph internally routes among its own members and returns a result to the parent.

Details worth stating: subgraphs inherit the parent's checkpointer and are namespaced under the parent thread, so don't compile them with their own; pass subgraphs=True to stream and get_state or the inner steps are invisible; and translate state explicitly at the boundary — a wrapper function mapping parent state to team input and back — rather than letting the two schemas share channel names by accident.

8.5 Shared state versus message passing ⭐

The most consequential decision in a multi-agent design, and the one candidates most often skip: what exactly does the next agent see?

Shared stateMessage passing
MechanismAll agents read/write the same channelsEach agent gets a constructed input; returns a result
ContextFull — nothing is lostOnly what you chose to pass
Token costGrows with every agent's outputBounded by the handoff payload
CouplingHigh — a schema change touches every agentLow — agents are independently testable
Failure modeContext bloat; agents distracted by irrelevant historyLost context — the receiver lacks something it needed

The pragmatic answer is usually hybrid: a shared messages channel so the conversation is coherent and auditable, plus private working channels per agent that others never see. That gives you a single readable trace without every agent's scratchpad polluting every other agent's context. When you do pass summaries instead of history, make the summary a structured artefact — findings, sources, open questions — rather than free prose, because prose summaries lose exactly the details the next agent needs.

Likely interview questions
DesignShould agents share state or pass messages?

Hybrid, in practice. A shared messages channel keeps the conversation coherent and gives you one readable trace; private per-agent channels keep each agent's scratchpad out of everyone else's context.

The trade if you go pure either way: full shared state means nothing is lost but every agent pays tokens for every other agent's output and gets distracted by irrelevant history, and a schema change touches everything. Pure message passing keeps agents decoupled and independently testable, but you must decide exactly what to pass — and the classic failure is a receiving agent missing a detail the sender didn't think to include.

When you do pass a summary, make it structured — {findings, sources, open_questions, confidence} — rather than prose. Free-text summaries lose precisely the specifics the next agent needs.

DebugThe writer agent keeps missing details the researcher found. Why?

Context loss at the handoff, almost certainly. Either the researcher's output is being summarised before the writer sees it, or the writer receives only the last message rather than the findings channel.

Diagnose by reading the trace and looking at the exact input to the writer's first model call — not what you think it receives. Then fix by structuring the handoff: the researcher writes to a typed findings channel (claims with sources and confidence), and the writer reads that channel directly rather than inferring from conversation text.

Also consider whether the split is worth it at all: if the writer needs everything the researcher found, the boundary is providing no context savings and you may be better off with one agent that does both.

Likely interview questions
System designWhat goes wrong in multi-agent systems, and how do you guard against it?

Six, with guards. Ping-pong — agents transferring back and forth; guard with a hop cap, handoff history, and a default agent that must resolve or escalate. Diffusion of responsibility — each assumes another did the work; guard with explicit ownership in the task payload and a completion check before finishing. Context loss at handoffs — guard with structured handoff artefacts rather than prose summaries. Cost explosion — guard with a per-run token budget checked between hops, not just an iteration cap. Conflicting writes to shared channels — guard with reducers or private per-agent channels. Untraceable failures — guard with per-agent spans so you can attribute a bad answer to a specific step.

And the meta-guard: always build and measure the single-agent baseline first, so the complexity is a decision with a number behind it.

DebugYour multi-agent system costs 12× what you estimated. Where do you look?

Get the per-agent, per-run token breakdown from traces first — the answer is almost always visible there and rarely where people guess.

Common causes: full history passed to every agent, so each hop re-sends everything before it, making cost quadratic in hops rather than linear. Supervisor overhead — a routing call per hop that you didn't count. Ping-pong inflating the hop count. Redundant work — two agents independently doing the same retrieval because neither can see the other's results. No prompt caching, so the stable system prompt and tool schemas are billed at full rate every call.

Fixes in order of impact: pass structured summaries instead of full history at boundaries; enable prompt caching; cap hops; cache the tool layer so duplicate retrievals are free; and re-run the single-agent baseline to check whether the architecture is buying anything at all.

ConceptualHow do you debug a multi-agent system?

Trajectory first, per-agent spans second. Read the sequence of agents and handoffs before looking at any individual output — most failures are coordination failures, and they're only visible at that level: an unnecessary transfer, a loop, a specialist invoked with the wrong task.

Then per agent: what was its exact input (not what you assume it receives), what did it output, how long and how much did it cost. Tag every span with the agent name so you can attribute.

Two techniques that help specifically here: replay from a checkpoint just before the suspect handoff, so you can iterate on one boundary without re-running everything; and test agents in isolation with recorded inputs, which separates “this agent is bad at its job” from “this agent was given a bad task”. Those two failures look identical end-to-end and have completely different fixes.

9.1 Why agents need tracing ⭐

A conventional service fails at a line of code. An agent fails at a decision — and no log line records why a model chose one tool over another.

The last row is the one that matters. Debugging an agent means reconstructing what the model could see when it decided, and that means capturing the full inputs and outputs of every model call — which is precisely what a trace is and a log is not. Likely interview questions
Very commonWhy can't you debug an agent with logs?

Because an agent's failures are decision failures, and a log line records an event, not the context that produced it. To understand why the model called the wrong tool you need the exact prompt it saw at that step — system prompt, tool schemas, full message history, retrieved documents — and nobody logs that, because it's kilobytes per step and useless in aggregate.

A trace captures it natively: a tree of spans where every model call records its complete input and output, its token counts and its latency. That turns “it gave a bad answer” into “at step 4 it had the right documents in context and ignored them”, which is a fixable statement.

Add the operational point: traces also give you per-step cost and latency attribution, which logs can't, and which you need the first time someone asks why a request took 14 seconds.

ConceptualIs LangSmith required? What if you can't use it?

Not required — the requirement is tracing, not a specific product. LangSmith is the LangChain-native option (one environment variable and it captures everything, plus datasets, evaluators and feedback collection), and it's framework-agnostic so it isn't a lock-in.

If you're in an environment where prompts and responses cannot leave your network, self-host — which is the actual constraint behind most “can we use LangSmith” questions, and worth naming.

What you must have either way: full inputs and outputs per model call, a span tree that reflects the graph structure, token and latency per span, and the ability to attach feedback to a run.

9.2 Traces, runs and spans ⭐

Three words used loosely everywhere. In LangSmith's model: a run is one unit of work, runs nest into a tree, and the whole tree for one request is a trace.

Practical things to attach: tags for environment and version so you can filter; metadata for user, tenant and thread id so you can find a specific complaint; and a stable run name per node. LangGraph 1.2.11 also exposes trace_policy on add_node, which lets you turn down tracing for hot, uninteresting nodes without disabling it globally.

Likely interview questions
CoreWalk me through how you'd read an agent trace.

Top-down, four passes. First the trajectory: the sequence of nodes and tool calls. Most failures are visible here — a tool that shouldn't have been called, a loop, a retrieval that never happened.

Second, timings: find the span that owns the latency. It's usually one model call, and often the final one because its input is the whole accumulated history.

Third, tokens: look for the input counts growing across turns, which tells you whether prompt caching or trimming would pay.

Fourth, open the suspect model span and read its exact input — the full prompt including tool schemas, history and retrieved documents. That's where you find out whether the model made a bad decision or was given bad information, which are completely different bugs.

DesignWhat metadata do you attach to traces, and why?

Identifiers so you can find a specific run when someone complains: user id (or a hash), tenant, thread_id, request id. Versioning so you can compare before and after a change: app version, prompt version, model name. Environment tags to keep dev noise out of production dashboards. Business context where it exists — plan tier, feature flag, experiment arm — because that's how you find out a regression only affects one segment.

The caveat to state: traces capture full prompts and outputs, so they contain whatever the user typed. Treat the trace store as a PII surface — redact where required, set retention, and control access to it the way you would a database of conversations.

9.3 What to evaluate in an agent ⭐⭐

The independence is the point. An agent can produce the right answer via six unnecessary tool calls (trajectory bad, response good) — that's the version that breaks next month when one of those tools changes. Three sources, in this order. Hand-written seeds — twenty cases covering the main flows, a few known failures and a couple of edge cases. Start here today rather than waiting for something better. Production traffic — sample real queries, especially ones with negative feedback, and label them; these are far better test cases than anything invented. Synthetic generation from your documents or schemas for coverage of areas real traffic hasn't reached yet, treated as a supplement rather than the core.

Two disciplines that matter more than the source: every production bug becomes a test case before it's fixed, which is how the set stays relevant; and keep a held-out slice you don't tune against, because a dataset you've optimised on for six months stops measuring anything.

ConceptualWhy isn't “the answer was right” enough?

Because it doesn't tell you why, and in a non-deterministic multi-step system the “why” is what predicts tomorrow's behaviour. An agent that reached the right answer through six unnecessary tool calls is right today and broken the moment one of those tools changes, gets slower, or starts costing more. An agent that got there by ignoring the retrieved documents and using parametric knowledge is right on questions it happens to know and confidently wrong on the rest.

Trajectory and step-level evaluation surface both. They're also what makes a failure diagnosable — “response accuracy fell 8 points, trajectory match fell 30” points straight at tool selection, whereas “accuracy fell” starts a week of guessing.

9.4 Trajectory evaluation ⭐

Comparing the sequence of steps an agent took against the sequence it should have taken. The technique that most clearly separates people who have run agents in production from people who haven't.

InteractiveTrajectory scorer — four matching strategies

The golden path is lookup_order → check_policy → issue_refund → notify. Notice that exact match fails on a harmless extra step while superset passes a wandering run that burned four extra calls — which is exactly why you pick the matcher deliberately and usually pair it with a step-count budget.

Likely interview questions
Deep diveWhat is trajectory evaluation and how do you score it?

Comparing the sequence of steps an agent actually took against the sequence it should have taken, rather than only judging the final answer.

Four matchers, increasingly permissive. Exact match — same tools, same order, same count; usually too strict, since a harmless duplicate call fails. In-order subsequence — the golden steps appear in order, extras allowed; a good default when order genuinely matters. Any-order set — the right tools were used, order irrelevant; correct when the steps are genuinely independent. Superset — the golden steps happened, anything else is tolerated; the most permissive and the most dangerous.

Pick the matcher by asking whether order and extra calls actually matter for that task, and always report the extra-step count and precision alongside the verdict — otherwise a wandering run that burned four extra calls passes silently.

DesignWhere does the golden trajectory come from?

Three sources. Hand-authored by whoever knows the domain — for a refund flow, “look up the order, check the policy, then issue” is a business rule, not an opinion, and it should be written down anyway. Harvested from good runs — take traces that were rated highly, extract the tool sequence, review and promote them. Derived from constraints rather than a full path: often you don't need the whole sequence, just assertions like “check_policy must appear before issue_refund” or “delete_* must never appear”.

That last form is underrated: partial-order constraints are cheaper to maintain than full golden paths, survive refactors better, and encode the things you actually care about — safety ordering and forbidden actions.

GotchaIsn't trajectory evaluation too brittle? Agents legitimately vary.

Exact matching is, which is why it's rarely the right matcher. The fix isn't to abandon trajectory evaluation, it's to evaluate the properties you actually care about: required steps present, forbidden steps absent, safety ordering respected, step count within budget. Those are stable across legitimate variation and still catch the failures that matter.

The second answer is to track the distribution rather than pass/fail per run. “Median 4 tool calls, p95 7” is a health metric; when it moves to “median 6, p95 14” you have a regression, even though no single run was “wrong”. That framing handles non-determinism honestly instead of pretending it away.

9.5 LLM-as-judge and its bias controls ⭐

Using a model to grade outputs is unavoidable for open-ended tasks and unreliable if you do it naively. The bias controls are the whole answer.

BiasWhat happensControl
PositionIn pairwise comparison, the first option wins more oftenRun both orders; count only consistent verdicts
VerbosityLonger answers score higher regardless of qualityRubric that penalises padding; control for length
Self-preferenceA model rates its own family's output higherJudge with a different model than the generator
LeniencyEverything gets 4/5; no discriminationBinary or 3-point scales with anchored definitions
FormatConfident, well-formatted answers score higherRubric focused on factual criteria only

Two structural fixes beat all of the individual controls. Prefer pairwise comparison to absolute scoring — models are far better at “which of these is better” than at “rate this 1–5”. And validate the judge against human labels on a sample: if the judge disagrees with your reviewers 30% of the time, its numbers aren't measuring what you think, and no amount of prompt tuning downstream will fix that.

Use a judge only where you must

If a deterministic check exists — exact match, schema validation, does the SQL run, does the cited chunk id exist, did the tests pass — use it. It's free, instant, perfectly consistent and needs no validation. Reserve the judge for genuinely subjective dimensions like helpfulness, tone and groundedness.

Likely interview questions
Very commonHow do you make LLM-as-judge reliable?

Six controls, and naming the biases by name is what makes the answer land.

Pairwise over absolute — models compare much better than they score, so ask “which is better” rather than “rate 1–5”. Swap the order and count only consistent verdicts, to defeat position bias. Anchored rubrics — define what each level means with examples, and use a 3-point scale rather than 10, to defeat leniency. A different model than the generator, to defeat self-preference. Structured output with the reasoning field before the score, so it reasons before committing. Validate against human labels on a sample and report the agreement rate — if it's 70%, the judge's numbers aren't measuring what you think.

And the framing: use a judge only where a deterministic check can't work.

DesignWrite a good judge prompt for “is this answer grounded?”

Make it a per-claim check rather than a global judgement, with structured output: give it the sources and the answer, ask it to extract each factual claim, mark each as supported / contradicted / not_found, and cite the supporting span for anything marked supported. The overall verdict is then computed in code from the claim list, not asked for directly.

Why this shape: a global “is it grounded, 1–5” invites leniency and gives you nothing to act on. Per-claim output is auditable, produces a natural score (fraction supported), and hands you the specific unsupported sentences — which you can then flag in the UI or strip.

Two additions: instruct it that absence of evidence is not contradiction, since conflating those inflates the failure rate; and put the reasoning field before the verdict in the schema.

GotchaYour judge scores 4.2/5 on everything. What's wrong?

Leniency bias plus an unanchored scale. A 1–5 scale with no definitions collapses to “4 unless something is obviously broken”, and a metric with no variance can't detect a regression — which is worse than having no metric, because it looks like coverage.

Fixes: switch to binary or 3-point with explicit anchored definitions and an example of each level; make the criteria specific and checkable (“does it cite a source for every numeric claim”) rather than global quality; move to pairwise comparison against a baseline answer, which produces discrimination automatically; and sanity-check the judge by feeding it deliberately bad answers — if they also score 4, the judge is broken, not your system.

9.6 Datasets and regression gates ⭐

Evaluation only changes behaviour when it can block a merge. A dashboard nobody looks at is a cost centre; a CI gate is a control.

Set thresholds relative to the current main branch, not to absolute ideals — “no more than 2 points below main” is enforceable from day one, whereas “95% accuracy” either blocks everything or nothing. Gate on cost and latency too, because the easiest way to raise quality is to spend more, and an unwatched budget makes that invisible.

Likely interview questions
System designHow do you stop prompt changes from silently regressing quality?

A dataset-backed eval gate in CI. Every PR that touches a prompt, a tool, a model version or the graph runs the golden dataset and reports scores against the main branch; thresholds block the merge.

The details that make it work: relative thresholds (“no more than 2 points below main”) rather than absolute ideals, so the gate is enforceable from day one; gate on cost and latency too, since spending more is the easiest way to buy quality and you want that visible; version the dataset so results are comparable over time; and keep the run cheap enough to tolerate — a few dozen examples, with the full set nightly, or nobody will run it.

Plus the cultural half: every production failure becomes a dataset entry before it's fixed. That's what keeps the gate meaningful rather than measuring last quarter's problems.

GotchaYour eval scores are noisy run to run. What do you do?

First accept the cause: agents are non-deterministic, so some variance is real and shouldn't be engineered away.

Reduce what you can: set temperature 0 for eval runs; fix seeds where the provider supports it; and stub external tools with recorded responses so the world isn't changing underneath you.

Then measure honestly: run each example several times and report mean with a confidence interval, not one number; increase dataset size, since noise falls with N; and set thresholds outside the noise band — if run-to-run variance is ±3 points, a 2-point gate is a coin flip that will erode trust in the gate.

And if one specific example flips constantly, that's usually informative rather than noise: it's a genuinely ambiguous case, and it belongs in a separate bucket you inspect rather than in the pass/fail count.

9.7 Online evaluation and feedback

Offline evals measure what you thought to test. Production measures what users actually do — and it's the only source of the failures you didn't imagine.

SignalCost to collectWhat it tells you
Thumbs up/downTrivialSparse, biased to the annoyed — still valuable
Implicit signalsFreeRetries, rephrasing, abandonment, escalation to a human
Online judges on a sampleSmall LLM spendContinuous groundedness/quality on real traffic
Operational metricsFreeLoop rate, tool error rate, p95 cost and latency

Implicit signals are the underrated ones. A user rephrasing the same question, escalating to a human, or abandoning mid-conversation is a stronger negative signal than a thumbs-down and costs nothing to capture. Route those runs into a review queue, label them, and they become tomorrow's dataset entries — which closes the loop between production and CI.

Likely interview questions
System designHow do you know your agent is degrading in production?

Layer four signals and alert on the leading ones.

Operational metrics first, because they move before quality does: p95 latency and cost per request, tool error rate, average tool calls per run, recursion-limit hits. A rising call count usually precedes a visible quality drop. Implicit user signals: retry rate, rephrasing, escalation to a human, abandonment. Explicit feedback, sparse but real. Online judges on a sampled percentage of traffic for groundedness and quality — expensive at 100%, cheap at 2%.

Then close the loop: negative-signal runs go to a review queue, get labelled, and become dataset entries. And re-run the offline eval on a schedule as well as per PR, because the world changes even when your code doesn't — model providers update, indexes drift, and upstream APIs change their responses.

DesignHow would you A/B test a prompt change?

Assign by a stable hash of the user or conversation id, not per request — otherwise a user gets different behaviour mid-conversation, which corrupts both the experience and the measurement. Tag every trace with the arm so all your metrics can be sliced by it.

Measure the full picture, not just quality: task success or feedback rate, escalation rate, cost per request, p95 latency. A variant that wins on quality and costs 60% more may still be the wrong choice, and you want that trade visible rather than discovered later.

Two disciplines: pre-register the primary metric and the minimum effect you care about, so you don't fish through slices afterwards; and run the offline eval on both arms first — if the change fails the golden dataset, don't spend production traffic finding that out.

Likely interview questions
System designHow would you deploy a LangGraph agent?

GotchaWhy is serverless awkward for agents?

Three reasons. Execution time limits — a multi-step agent can run for minutes, and many platforms cap well below that; the workaround (return immediately, process in a queue) means you weren't really doing request-scoped work anyway. Cold starts — importing the LLM and framework stack plus establishing DB connections adds meaningful latency to a p99 that's already poor. Connection pooling — every invocation opening its own Postgres connection to the checkpointer exhausts the database, so you need a pooler in front.

And the structural one: interrupts. If a run can be pending for three days waiting for approval, the compute model has to be “persist and resume later” regardless of platform — which is exactly what LangGraph's checkpointing gives you, and exactly what a request-scoped mental model fights.

10.2 Streaming ⭐⭐

An agent that takes twelve seconds and shows nothing feels broken. Streaming is a product requirement, and LangGraph gives you several modes because “stream” means different things at different layers.

Likely interview questions
Very commonWhat streaming modes does LangGraph have, and which do you use?

Five: "values" (full state after each superstep), "updates" (only what each node changed), "messages" (LLM tokens as generated, with metadata), "custom" (whatever a node writes to the stream writer), and "debug".

Two details worth volunteering: filter messages by langgraph_node so you only stream the user-facing node's tokens rather than every internal call; and pass subgraphs=True or anything inside a subgraph is invisible, which is the most common “my streaming stopped working” cause.

DesignHow do you stream an agent that thinks for 30 seconds before answering?

Stream the process, not just the product. Users tolerate long waits when they can see progress and it looks purposeful.

Concretely: emit a step label from updates as each node starts (“looking up your order…”, “checking the refund policy…”); use custom events for counted work (“analysed 7 of 20 documents”); show tool calls in a collapsible “working” panel, which also builds trust because the user can see what it consulted; then stream the final answer's tokens.

And treat the wait as a latency bug too: parallelise independent steps, use a fast model for the early routing calls, and show a first partial result if one exists. The best fix for a 30-second agent is usually a 12-second agent.

DebugStreaming works locally but not through your API. What's wrong?

Almost always buffering somewhere in the chain, not LangGraph. Check, in order: the web framework — you must return a streaming response and yield, not build a list; a reverse proxy buffering responses (nginx needs proxy_buffering off or the X-Accel-Buffering: no header); gzip compression middleware, which buffers to compress; and the client, where fetch without a streaming reader silently waits for completion.

Then the LangGraph-specific causes: using invoke instead of astream; a sync node blocking the event loop so nothing else can be emitted; and missing subgraphs=True when the streaming node lives inside a subgraph.

10.3 Durability and idempotency ⭐⭐

Covered mechanically in §5.8; here it's a production discipline. Durable execution means your nodes will be re-run, and that is a design constraint on every side effect in the system.

The re-execution checklist

Node does…Safe to re-run?Make it safe by…
Reads / queries / retrievalYesNothing — though caching saves money
LLM callYes, but costs againCache by input hash if the run is expensive
Sends an email / messageNoProvider idempotency key from stable state
Charges / transfers moneyNoIdempotency key + record the result in state and check it
Creates a recordNo — duplicatesDeterministic id, or upsert on a natural key
Appends to a log/queueNo — duplicatesDedup key consumers can honour

The key must be derived from state, not generated in the node. f"charge-{order_id}" is stable across re-runs; uuid4() is a new key every time and defeats the entire mechanism. That single distinction is the most common bug in this area.

Likely interview questions
Very commonWhy does durable execution force you to think about idempotency?

Because recovery works at the superstep level: after a crash, every node in the incomplete superstep runs again. The same is true when you resume from an interrupt (the interrupted node re-executes from the top) and when you replay during time travel.

So “this node runs exactly once” is not something the runtime can promise — at-least-once is the contract. Any node with an external side effect must therefore be safe to execute twice, which changes how you write code: keep each side effect in its own small node, derive an idempotency key from stable state rather than generating one inside the node, record the result back into state and short-circuit if it's already there, and make sure the external system actually honours the key.

DebugA customer was charged twice. Walk me through the investigation.

Get the thread's checkpoint history first — it's the authoritative record. Look for a superstep that ran twice: a crash and resume, an interrupt resume where the charge sat above the interrupt() call in the same node, a node-level retry after a timeout where the charge actually succeeded, or a replay during debugging that hit production credentials.

Then check the key: was an idempotency key sent at all, and was it derived from stable state or generated in the node? A uuid4() per execution defeats the provider's dedup entirely and is the single most common cause.

Fixes: stable key, record charge_id in state and short-circuit on re-entry, move the charge below any interrupt and into its own node, and add an alert on duplicate charges per order so the next occurrence is detected rather than reported by a customer.

10.4 Timeouts, retries and error handlers ⭐

Three layers can time out and three can retry. Deciding who owns what — before you need it — is the difference between graceful degradation and a cascade.

LayerTimeoutRetryOwns
HTTP client in a toolPer-request, shortYes — transient networkFlaky dependencies
Model clientPer-callYes — 429/503, with backoffProvider throttling
Node RetryPolicy—Yes — raised exceptionsWhole-step failure
Whole runYes — a hard budgetNoNot letting one request run forever

Two rules keep this sane. Inner timeouts must be shorter than outer ones, or the outer one fires first and you lose the specific error. And degrade rather than fail where you can: a node whose optional enrichment tool is down should return partial results with a flag, not kill the run — that's what error-handler branches in the graph are for.

Likely interview questions
System designDesign the timeout and retry strategy for an agent.

Nested, with each layer shorter than the one above it. Tool HTTP calls get a short per-request timeout (say 10 s) and own transient network retries with exponential backoff and jitter, capped at 3. The model client gets its own per-call timeout and retries 429/503 with backoff. Node RetryPolicy handles exceptions the tool deliberately raised, with a retry_on predicate so you don't retry your own validation errors. And the whole run has a hard wall-clock budget — nothing should be able to run forever.

Then the two rules: one owner per failure class, so retries don't multiply into 27 calls to a struggling service; and degrade rather than fail — if an optional enrichment tool is down, return partial results with a flag and let the agent proceed, rather than killing a run the user is waiting on.

Add a circuit breaker per dependency so a hard-down service fails fast instead of consuming your timeout budget on every call.

DesignHow do you handle a node that fails permanently?

Route around it in the graph rather than letting the exception escape. Catch inside the node, write an error marker into state, and use a conditional edge to a fallback branch: use a cached or default value, try an alternative provider, degrade to a partial answer, or escalate to a human via interrupt.

What makes this good rather than just defensive: the failure becomes visible in state and in the trace instead of a stack trace, the user gets a useful partial result with an honest caveat, and the run's checkpoint records what happened so it can be inspected or resumed after you fix the dependency.

Reserve hard failure for cases where continuing would be wrong — a payment step that can't verify its own outcome should stop, not guess.

DesignHow do you enforce a hard cost ceiling per request?

Track spend in state and check it between supersteps. Deep diveHow does prompt caching work, and what breaks it?

Providers can cache the model's internal state for a prefix of your prompt. On a later request whose prompt starts with byte-identical content, the cached prefix is reused and billed at a large discount — typically around 10% of the normal input rate — with a lower time-to-first-token as a bonus.

What breaks it: anything that changes the prefix. A timestamp or request id in the system prompt; reordering tool definitions between calls; inserting retrieved documents before the static instructions; changing the model or its parameters. Caches also expire, typically in minutes, so low-traffic endpoints see fewer hits.

The design rule: order your prompt most-static to most-dynamic — system prompt, then tool schemas, then long-lived context, then conversation history, then the current turn. That's exactly the layout an agent loop wants anyway, which is why caching pairs so well with agents.

The trap answer

“We'd add a guardrail prompt telling it to ignore instructions in retrieved content.” That's a mitigation, not a control — it reduces frequency and provides no guarantee, because to the model the injected text and your instruction are the same kind of thing. Likely interview questions
Very commonHow do you defend an agent against prompt injection?

Start with the framing: for agents this is a privilege problem, not a content problem. Detection heuristics and guardrail prompts are useful as defence in depth — they reduce frequency. They are not the control.

System designAn agent reads customer emails and can send replies. What's your threat model?

Every incoming email is attacker-controlled input that enters the model's context, so the primary threat is indirect injection driving the send tool.

Design accordingly: the reply tool can only reply to the original sender — no arbitrary recipient, no CC, no forwarding; that alone removes exfiltration-by-email. Scope reads so the agent can only see the thread it's handling, not the whole mailbox. Gate replies above a risk threshold behind human approval, and gate anything involving account changes unconditionally. Strip HTML, hidden text and images before the content reaches the model, since injections often hide there. Rate-limit sends per thread and per hour to bound a compromise.

Then detection as defence in depth: flag emails containing instruction-like patterns for review, and alert on anomalous tool-use sequences. And log everything with the thread id, because you will eventually need to reconstruct what happened.

DesignWhere do secrets live in an agent system?

Not in state and not in the prompt. State is serialised into checkpoints, so anything there is persisted in your database and visible to anyone who can read a thread; the prompt is captured in traces.

Correct places: environment or a secret manager, read by the tool implementation at call time; per-user credentials fetched from a vault keyed by the authenticated user; and short-lived scoped tokens rather than long-lived keys wherever the provider supports it.

Two extras: redact traces, because tool inputs and outputs are captured verbatim and an access token in a tool argument ends up in your observability store; and remember the model should never need a secret — it asks for an action, your code supplies the credentials. If the model has to pass an API key as a tool argument, the tool is designed wrong.

10.8 Multi-tenancy and scale

One agent serving ten thousand users is mostly an ordinary systems problem — with three agent-specific twists.

Isolation. Namespaced thread ids, tenant resolved server-side from the authenticated session, ownership checked before every invoke, and row-level security or separate schemas in the checkpoint store. Retrieval filters must carry the tenant too — a leak through the vector index is still a leak.

Fairness. Agent workloads are extremely uneven: one user's research question can cost a hundred times another's greeting. Per-tenant rate limits and token budgets are both needed, because a request-count limit doesn't stop one tenant consuming the whole model quota.

Capacity. Your real ceiling is usually the provider's rate limit, not your CPU. Design for it: a queue with per-tenant fairness, backpressure that degrades gracefully rather than erroring, and — where it fits — batching or a fallback provider. Scale the app tier on concurrent runs, and watch the checkpointer's write throughput, which is one write per superstep per run and grows faster than request count.

System designScale this agent to 10,000 concurrent users.

The bottleneck is almost certainly the model provider's rate limit, not your infrastructure — say that first, because it reframes the whole answer.

Architecture: async service, horizontally scaled and stateless (all state is in the checkpointer, so any pod can serve any thread); Postgres with connection pooling for checkpoints, watching write throughput since it's one write per superstep per run; a queue with per-tenant fairness in front of model calls, with backpressure that degrades rather than errors.

Agent-specific concerns: per-tenant token budgets as well as request limits, because agent cost per request varies by orders of magnitude; graceful degradation under load — shrink the iteration cap, drop to a cheaper model, disable optional enrichment; and caching (prompt caching plus tool-result caching) which raises effective throughput against a fixed provider quota.

And the honest note: check whether every request needs the agent. Routing the common cases to a cheap deterministic path is often the cheapest way to scale.

DesignHow do you stop one tenant from starving the others?

Limit on two dimensions, because agents make request counts a poor proxy for consumption. A per-tenant request rate limit is table stakes; a per-tenant token or cost budget per window is what actually protects capacity, since one research question can cost a hundred times a greeting.

Then fair queueing: a per-tenant queue with round-robin or weighted service rather than a single FIFO, so a burst from one tenant delays only itself. Add a per-run cap so no single request can consume an unbounded share, and separate the queue for long-running background work from interactive traffic so a batch job can't add seconds to everyone's chat latency.

Make it visible: expose per-tenant consumption, and return an explicit “you've reached your limit” rather than a timeout, so the failure is diagnosable by the customer rather than by you.

You can't unit-test a model, but you can test almost everything around it — and most agent bugs live in the “around it”.

Likely interview questions
Very commonHow do you test a non-deterministic agent?

By splitting deterministic parts from statistical ones — and noting that most of the system is deterministic.

Ordinary unit tests for routing functions (they're plain Python over state — craft a state, assert the branch), reducers (including the empty-channel and concurrent-write cases), tools (mocked dependencies, and the error paths especially), and graph structure (compile and assert nodes, edges, reachability). Stubbed-model tests for nodes that call an LLM: inject a fake model returning a fixed response or a fixed tool call, and assert the state transition and routing. That makes the whole graph testable end-to-end deterministically.

Statistical evaluation only for the genuinely non-deterministic part: a golden dataset with trajectory and judge evaluators, run in CI with relative thresholds.

CodingHow do you test a node that calls a model?

Inject the model rather than importing it. Build nodes as factories or classes taking the model as a parameter, so tests can pass a fake that returns a canned AIMessage — with a specific tool_calls payload when you want to exercise the tool branch.

Then assert the things you actually control: the partial update the node returned, the branch the router chose given that output, and that the tool was invoked with the expected arguments. You're testing your logic, not the model's.

Two complements: record-and-replay real model responses as fixtures, which keeps tests realistic without network calls (refresh them periodically or they encode a model version you no longer use); and keep a small set of live tests, run on a schedule rather than per commit, so you find out when a provider's behaviour changes underneath you.

10.10 Rollout and incident response

Agent changes are riskier than code changes because the blast radius is behavioural and often invisible until someone complains. The mitigations are the familiar ones, applied to prompts and models as well as code.

Rollout. Version prompts and model choices as configuration, not code constants, so they can be changed without a deploy — and, critically, rolled back in seconds. Canary to a small traffic slice with per-arm metrics. Keep the previous model version pinned and available: providers deprecate, and “the model changed underneath us” is a real incident category.

Incidents. The agent-specific runbook items are: a kill switch that routes traffic to a deterministic fallback or a human queue; the ability to disable individual tools without a deploy, since one misbehaving tool is a common cause; a cost circuit breaker that trips on spend rate, because a runaway agent is a financial incident and not only a quality one; and a way to find and inspect affected threads, which is what the trace metadata from §9.2 is for.

Likely interview questions
System designYour agent starts behaving badly in production at 2 a.m. What's the runbook?

Contain, diagnose, fix — in that order.

Contain: hit the kill switch — route to a deterministic fallback or a human queue — or roll back the prompt/model config, which should be a config change rather than a deploy. If it's one tool misbehaving, disable that tool. If it's a cost incident, the spend circuit breaker should already have tripped; if it hasn't, cap iterations globally.

Diagnose: pull recent traces and compare against traces from before the change. Look at trajectories first — a new tool being called, a loop, a retrieval returning nothing. Check what changed: your deploy, a prompt edit, a model version update on the provider's side, or an upstream API's response format.

Fix and follow up: add the failing cases to the golden dataset before fixing, so the fix is verified and the regression can't recur silently. And check whether affected threads need remediation — with checkpoints you can find them, inspect them, and in some cases resume them correctly.

DesignHow do you roll out a model upgrade safely?

Offline first, then canary. Run the golden dataset against the new model and compare quality, trajectory match, cost and latency — a newer model is often better and different, and the differences show up as changed tool-selection behaviour more than as wrong answers.

Then canary a small traffic slice with the arm tagged on every trace, and watch the same four metrics plus implicit user signals (retries, escalations). Ramp slowly, keep the old model pinned and one config change away, and don't ramp during a period when nobody is watching.

Two agent-specific traps: prompt caching resets when the model changes, so early costs and latency will look worse than steady state; and prompts tuned against the old model may be over-fitted to it — a regression on the new model can mean your prompt is doing work the new model doesn't need, not that the model is worse.

11.1 Long-horizon agents ⭐

Agents that run for hours, days or weeks. Everything that is merely annoying in a 30-second agent becomes structural here — and LangGraph's persistence model is why it's the framework people reach for.

ProblemAt 30 secondsAt 3 weeks

Crash recoveryRetry the requestMandatory — the process will restart several times
Goal driftRareCommon — periodically re-read the objective
CostCentsReal money — needs a running budget, not a per-request cap

The world changingDoesn'tFacts gathered on day 1 may be false by day 10

The design that follows: externalise the plan into state or a store rather than keeping it in the message history, since history will be summarised away; work in bounded episodes — each waking period does a chunk of work and writes a durable summary; re-anchor to the original objective at the start of each episode; and put human checkpoints at milestones using interrupt, so a three-week run doesn't discover on day 20 that day 3 went wrong.

Likely interview questions
System designDesign an agent that runs a marketing campaign over six weeks.

Episodic, not continuous. A scheduled trigger wakes the graph — daily, or on an event — and each episode does a bounded chunk of work then writes a durable summary and exits. The graph is checkpointed throughout, so it survives restarts, deploys and long gaps.

State design: the plan and objective live in explicit channels (and the store), not in the message history, because history will be summarised away. Each episode re-reads the objective and the plan, does its work, updates progress, and appends a compact episode summary.

Oversight: interrupt at milestones — approve the plan, approve the first send, approve anything above a spend threshold — so a six-week run can't quietly go wrong for five of them. A running budget in state, checked each episode, not just a per-request cap.

Freshness: facts gathered in week 1 may be stale by week 4, so timestamp what's stored and re-verify anything load-bearing before acting on it. This is where LangGraph's persistence genuinely has no substitute — the alternative is building the same checkpoint-and-resume machinery yourself.

GotchaWhat is goal drift and how do you prevent it?

Over a long run the agent gradually optimises for something adjacent to the original objective — the goal was “increase qualified leads”, and twenty episodes later it's tuning email open rates because that's what its recent context is about. It happens because the objective sits at the start of a history that keeps getting summarised, while recent tactical detail dominates the context.

Prevention: keep the objective in a dedicated state channel that is never summarised and is re-injected verbatim into every episode's prompt. Define success criteria as checkable conditions rather than prose. Add a periodic alignment check — a cheap call asking “does the current plan still serve this objective?”. And put a human review at milestones, since drift is much easier for a person to spot than for the drifting agent to self-diagnose.

11.2 Computer use and browser agents

Agents that operate a GUI — screenshot in, click and keystroke out. Genuinely useful where no API exists, and considerably less reliable than any tool-based alternative.

The loop is the familiar one with a different observation space: screenshot → model identifies the target and emits a coordinate or an accessibility-tree action → the action is executed → new screenshot. The failure modes are specific: ambiguous targets (three buttons labelled “Continue”), timing (acting before the page settled), drift (the UI changed and every hardcoded expectation broke), and cost — screenshots are large images, so every step is an expensive multimodal call.

The judgement to express: prefer an API, then a structured DOM/accessibility tree, then pixels. Computer use is the last resort for systems that genuinely have no programmatic surface — legacy internal tools, third-party portals — and where it's used, it should be sandboxed, gated on destructive actions, and monitored, because a mis-click has real consequences and no schema stops it.

Likely interview questions
DesignWhen would you use a browser agent instead of an API?

Only when there is no API — a legacy internal system, a third-party portal with no integration, a workflow spanning several systems that can't be joined any other way.

The preference order is API → structured DOM or accessibility tree → raw pixels, and you should move down it reluctantly. Each step down costs reliability (no schema, no error codes, no idempotency), cost (screenshots are expensive multimodal inputs on every step), and speed.

Where you do use one: pin it to the accessibility tree rather than coordinates where possible, gate destructive clicks behind approval, run it in a sandboxed browser with scoped credentials, and expect maintenance — a UI change is a silent breakage with no deprecation notice.

ConceptualWhy are computer-use agents unreliable?

Because the observation is a picture, not a structured state, so every step involves perception that can be wrong in ways a schema would have prevented. Specific modes: ambiguity — several visually similar targets, and nothing distinguishes them semantically; timing — acting before an async render completes, which produces a click on whatever was there a moment ago; drift — the UI changes and there's no contract to break loudly; and compounding error, since a single wrong click puts the agent in a state its subsequent reasoning doesn't account for.

The mitigations are honest but partial: verify after each action (screenshot and confirm the expected change happened), prefer accessibility-tree targets over coordinates, keep episodes short with checkpoints so recovery doesn't mean restarting, and gate anything irreversible.

11.3 Agent protocols — MCP, A2A, AG-UI ⭐

Three layers people conflate. Be precise about which problem each one solves, and honest about which have actually settled.

ProtocolConnectsStatus in 2026
MCPAgent ↔ tools and dataSettled — broad adoption, the de-facto tool interface
A2AAgent ↔ agent, across organisationsEmerging; real momentum, not yet universal
AG-UIAgent ↔ user interface (streaming, state, HITL)Early; the problem is real, the standard isn't fixed

The reason to hold a view here: interviewers use protocol questions to check whether you distinguish what has actually been adopted from what has been announced. The defensible position is that MCP won its layer and you should build against it; A2A addresses a genuine problem (cross-organisational agent interoperability) that most teams don't have yet; and the UI layer is still being fought over, so building directly on LangGraph's streaming modes is a reasonable choice today.

Likely interview questions
ModernMCP, A2A, AG-UI — what does each solve?

Different layers, not competitors. MCP connects an agent to tools and data — the m × n → m + n integration argument, and the one layer that has genuinely standardised. A2A connects agents to other agents, typically across organisational boundaries: capability discovery, task delegation, negotiated exchange. AG-UI connects an agent to a user interface — streaming tokens and steps, shared state, human-in-the-loop prompts.

Then the honest status assessment, which is the part being tested: MCP is settled and worth building against; A2A solves a real problem that most teams don't have yet, and it hasn't converged; the UI layer is early enough that building on your framework's streaming primitives is a defensible choice. Saying “all three are the future” is weaker than saying which one you'd actually adopt this quarter and why.

ConceptualDo we need an agent-to-agent protocol at all?

Within one organisation, usually not — you control both agents, so a shared graph, a function call or an internal RPC is simpler, faster and easier to debug than a negotiation protocol. Adding one internally is manufacturing a boundary that doesn't exist.

Across organisations, yes, and that's the real motivation: my agent needs to discover what your agent can do, delegate a task, and track it, without either of us having integrated with the other in advance. That's a genuine m × n problem and it's exactly what MCP solved one layer down.

The open questions are why it hasn't settled: authentication and authorisation between autonomous agents, liability when a delegated task goes wrong, payment, and trust in capability claims. Those are harder than the wire format, which is why the protocol layer is moving slower than the enthusiasm.

11.4 Self-improving agents

An agent that gets better from its own experience. Several mechanisms are real and useful; the version people imagine — an agent rewriting its own code unsupervised — is not something you should ship.

MechanismWhat improvesReality
Memory of outcomesRecalls what worked for similar casesWorks today — write outcomes to the store, retrieve on similar queries
Few-shot from successesPrompt improves as good examples accumulateWorks; needs curation or it drifts
Automated prompt optimisationPrompt tuned against an eval setReal, and entirely dependent on the eval set's quality
Learned tool selectionRouting improves from logged outcomesWorks — it's a classifier trained on your traces
Self-modifying codeThe agent rewrites itselfResearch. Do not put this in production

The common requirement across the workable ones is a reliable outcome signal. Without knowing which runs succeeded, “learning from experience” is just accumulating unlabelled history — and an agent that learns from its own unvalidated outputs will confidently reinforce its own mistakes. Get the feedback loop from §9.7 working first; self-improvement is downstream of evaluation, not a substitute for it.

Likely interview questions
ConceptualCan agents learn from their mistakes?

Yes, through mechanisms you build — not by themselves. The workable ones: writing outcomes to a store and retrieving relevant past cases (“last time this customer's issue was X, the fix was Y”); accumulating successful examples as few-shot prompts; automated prompt optimisation against an eval set; and training a small routing classifier on logged trajectories and outcomes.

The prerequisite is a reliable outcome signal. Without knowing which runs actually succeeded, the agent is accumulating unlabelled history and will reinforce its own errors as readily as its successes. So the honest ordering is: evaluation and feedback collection first, then self-improvement on top of it.

And the boundary: an agent modifying its own code or prompts unsupervised in production is a research topic, not an engineering practice — the failure mode is silent, compounding and hard to roll back.

DesignHow would you build an agent that learns user preferences?

Explicit extraction into a store, with governance. After a conversation, a background step extracts candidate preferences (“prefers concise answers”, “works in metric units”, “owns the payments service”) with a confidence and a source; dedupe against existing memories; write to ("preferences", user_id). At the start of each run, retrieve the relevant ones and inject them into the system prompt with a token cap.

What makes it work rather than degrade: extract selectively, since storing everything makes retrieval noisy; supersede rather than accumulate when a new preference contradicts an old one; timestamp everything, because preferences go stale; and make it visible and editable — a “what I remember about you” view where the user can correct or delete entries, which is both a trust feature and a genuine quality mechanism, since users will fix errors you'd never have detected.

11.5 Context engineering ⭐⭐

The reframing that has replaced “prompt engineering” as the central discipline. Once you see agent design this way, memory, RAG, tool selection and message trimming stop being separate topics.

The definition

Context engineering is deciding, for every LLM call, exactly what occupies the finite context window. Not the wording of a prompt — the composition of everything sent: system instructions, tool schemas, retrieved documents, conversation history, memories, and the current input. Every token is a choice, and every token you include crowds out one you didn't.

ComponentGoverned byThe lever
System instructionsPrompt designKeep stable — it's the cacheable prefix
Tool schemasCatalogue sizeNamespacing, routing, tool retrieval (§6.4)
Retrieved documentsRetrieval qualityRerank and cut k — fewer, better (§7.2)
Conversation historyTrimming policySummary + last k (§5.6)
Long-term memoriesStore curationSelective extraction; hard token cap (§5.7)
Current inputThe userRewrite for the index; strip boilerplate

The four operations, worth naming as a set: write (persist outside the window — the store, a scratchpad file), select (retrieve only what this call needs), compress (summarise, trim, truncate results), and isolate (give sub-agents or subgraphs their own contexts so their scratchpads don't pollute the main one). Almost every technique in this subject is one of those four.

A bigger window did not remove the problem

Million-token windows changed the constraint from “does it fit” to “should it be there”. Cost scales with tokens on every turn, time-to-first-token scales with input length, and attention degrades over long contexts — so a focused 8k context routinely beats an unfocused 500k one. Selection is now a quality technique, not just a capacity workaround.

Likely interview questions
ModernWhat is context engineering, and how is it different from prompt engineering?

Prompt engineering is about the wording of instructions. Context engineering is about the composition of the whole context window for every call: which instructions, which tool schemas, which retrieved documents, how much history, which memories, in what order.

The shift matters because in an agent, the prompt is assembled dynamically at every step and it's the assembly — not the phrasing — that determines behaviour. Four operations cover it: write (persist outside the window), select (retrieve only what this call needs), compress (summarise and trim), and isolate (sub-agents get their own contexts).

The unifying insight worth stating: memory management, RAG, tool selection and history trimming are not four topics, they're four instances of one problem — a finite window and a budget for what goes in it. Framing them that way is a strong senior signal.

Deep diveHow do you decide what goes into the context for a given call?

Work backwards from the decision the model has to make at that step, and include only what's needed for it.

Practically: a token budget per component — say 20% instructions and tools, 30% retrieved content, 40% history, 10% memories — enforced in code rather than hoped for. Rank within each component and cut, rather than including everything that fits: five well-reranked chunks beat twenty mediocre ones, and fewer is often better, not just cheaper. Order most-static to most-dynamic so prompt caching works and the important recent content sits near the end where attention is strongest. And isolate — if a sub-task needs a large working context, give it a subgraph with its own state so that context never enters the main thread.

Then measure it: log token composition per call. Teams are routinely surprised to find tool schemas or stale history consuming most of their window.

Toward standardisation at the boundaries: MCP settled the tool layer, and the agent-to-agent and UI layers are being contested now. ConceptualWhat's the most overrated idea in agentic AI right now?

Multi-agent as a default architecture. 12.1 Conceptual foundations

The opening five minutes. These get asked almost regardless of the role, and a crisp answer sets the tone for everything after.

Drill
Very commonWhat is an agent?

A system where an LLM decides the control flow at runtime — typically by choosing tools in a loop until it decides it's done. Four components: instructions, memory, tools, and a termination condition; the loop is model → tool call → observation → model.

The distinguishing feature versus everything simpler is that the execution path isn't known before the run. That's what buys flexibility and what costs predictability, testability and bounded cost.

Very commonWalk me through the capability ladder.

Single call → chain → router → workflow → agent. Each rung adds flexibility and subtracts determinism. The line that matters is between workflow and agent: a workflow's control flow is written by a developer; an agent's is decided by an LLM at runtime.

The point of naming the ladder is that it makes “do we need an agent?” a question with five answers rather than two, and the right answer is usually the lowest rung that solves the problem.

Very commonWhen would you not build an agent?

When the steps are knowable in advance (encode them); when the latency budget is under a second or two (each iteration is a round trip); when errors are expensive and hard to detect (non-determinism plus stakes is the worst pairing); and when you have no way to evaluate the output (build the eval first).

Plus: if SQL, a regex or a lookup table solves it, do that. Most problems that look agentic are workflows.

Very commonExplain ReAct, and say what's changed since the paper.

Reason + Act — interleave reasoning with tool actions so the model thinks, acts, observes, and thinks again. It beat reasoning-only (which hallucinates lookupable facts) and action-only (which flails at tool choice).

What's changed: the text protocol (Thought:/Action:/Observation:) is gone, replaced by native structured tool calls, which killed the regex-parsing failure mode and added parallel tool calls. Reasoning is native in reasoning models. The loop survived; the format didn't.

ConceptualDoes self-critique actually improve output?

Only when the critic has information the generator didn't — test results, a compiler error, a schema validation failure, sources to check against. Same-model self-review with “are you sure?” shares the generator's blind spots and produces hedging more than insight.

Design implication: give the critic a tool or a signal, not just an opinion. And bound the loop — cap iterations, keep the best draft, stop on marginal improvement.

DesignPlan-and-Execute or ReAct?

Ask whether the steps are knowable up front. Yes → plan, because planning amortises across steps and independent steps can run in parallel. No → interleave, because each observation changes what's sensible next.

The middle option most serious systems land on is plan with re-planning: revise remaining steps after each execution, which keeps parallelism and adaptability at the cost of one extra call per step. Name the Plan-and-Execute failure mode: stale-plan execution after step 2 invalidated the premise.

System designHow much autonomy would you give a production agent?

Reframe it as per action, not per agent, decided by blast radius: if this call is wrong, how bad is it and can we undo it? Reads and drafts are free; writes, spends and sends are gated behind an interrupt.

And enforcement lives in the tool layer, not the prompt — the model can be talked out of an instruction, not past a code path requiring an approval token.

ModernWhy LangGraph over CrewAI, AutoGen or a provider SDK?

The axis is control over control flow, plus durability. CrewAI and AutoGen give high-level abstractions — fast to start, awkward when you need a specific flow. Provider SDKs give a clean loop tied to one vendor. LangGraph is low-level and durable: explicit graph, no hidden flow, plus checkpointing for resume, HITL, time travel and crash recovery.

Finish honestly: for a simple tool-calling agent with no persistence requirement, a plain SDK loop is easier to debug and a perfectly good choice.

12.2 LangGraph mechanics

The part where an interviewer finds out whether you've used it or read about it. Be able to write these on a whiteboard.

Drill
CoreWhat is a node, and what does it return?

A function from state to a partial update — a dict of only the channels it wants to change, not a new state object. LangGraph merges it through each channel's reducer.

Consequences: nodes stay small and composable; parallel nodes each return their slice and reducers merge at the barrier; and never mutate the incoming state, because that bypasses the reducer and the checkpointer and makes the node non-replayable.

CoreHow do you create a loop, and how do you bound it?

A conditional edge that can point backwards: model → should_continue → {"tools": "tools", "finish": END} plus tools → model. The routing function is plain Python, which is why it's unit-testable.

Bound it by checking an iteration counter before the model-driven condition, and set recursion_limit (default 25 supersteps) as a backstop. Treat hitting the limit as a bug to diagnose, not a number to raise.

Deep diveWhy is LangGraph's execution model Pregel-style rather than a DAG scheduler?

Because agent loops are cycles, and a DAG framework can't express “call a tool then go back to the model”. Pregel/BSP gives cycles plus deterministic merge semantics: rounds, buffered writes, a barrier that applies everything through reducers, then the next round's active set.

That single model explains parallel-write conflicts, why reducers exist, why a node can't see a sibling's write, and why checkpoints land where they do.

CodingCan a conditional edge return several destinations?

Yes. A list of node names activates all of them in the next superstep (static fan-out chosen at runtime). A list of Send objects gives dynamic fan-out where each branch also carries its own private input state.

Either way, any channel more than one branch writes now needs a reducer, or you get InvalidUpdateError at the barrier.

CodingWhat does a Send worker receive as its state?

Exactly the dict you passed — not the parent state. A worker reading state["messages"] will find it missing unless you included it.

That's deliberate: it isolates workers, keeps them testable, and avoids copying a large parent state into every branch. If the payload is getting big, pass an id and let the worker fetch.

CodingWrite a custom reducer and say what makes it correct.

def keep_best(cur, new): return max(cur, new), used as score: Annotated[float, keep_best].

Correctness properties: pure (no I/O — it runs inside the state machinery), doesn't mutate its arguments, associative where possible because concurrent write order isn't guaranteed, and handles the initial call where the current value is the channel default. A reducer assuming a non-empty cur fails on the first write.

CoreWhat does compile() do?

Freezes the builder into an immutable Runnable and attaches infrastructure: checkpointer, store, static interrupt_before/interrupt_after, and a name for traces. It also validates — unreachable nodes, edges to non-existent names, no path from START.

The division: compile-time is infrastructure; invocation-time config carries thread_id, user context and recursion_limit.

DesignWhen would you use a subgraph, and what breaks?

For reuse, encapsulation (multi-agent with private state), or team ownership boundaries. Not for aesthetics — it adds a translation boundary and an indirection layer to debugging.

What breaks if you forget: a subgraph inherits the parent's checkpointer and is namespaced under the parent thread, so don't compile it with its own; and you must pass subgraphs=True to stream or get_state or the internals are invisible.

DebugYou get GraphRecursionError. Process?

Don't raise the limit first. Read the trajectory (stream_mode="updates" or the trace) — a cycle is usually obvious. Check the exit condition is reachable: often the router tests something no node ever sets. Check whether the model is looping on an uninformative tool result. Check whether a fan-out is losing a counter increment because the channel overwrites.

Only raise recursion_limit once you've confirmed the graph legitimately needs more supersteps.

DebugYour parallel fan-out isn't faster. Why?

Four checks: is anything actually in the same superstep (sequential edges aren't parallel); are you calling the async entrypoint; is a node blocking the event loop with a sync client (the usual answer — wrap in asyncio.to_thread or use an async client); and are you hitting provider rate limits, in which case the calls are serialising server-side.

12.3 State and memory

The layer confusion here — checkpointer versus store — is the single most probed misunderstanding in the subject.

Drill
Very commonExplain state, checkpointer and store.

State = live channel values during an invocation. Checkpointer = per-superstep, per-thread snapshots, giving resume, HITL, crash recovery and time travel. Store = cross-thread namespaced memory you read and write explicitly.

The settling sentence: the checkpointer remembers this conversation; the store remembers this user.

DesignTypedDict or Pydantic for state?

TypedDict by default — it's the LangGraph default, a plain dict at runtime, zero validation overhead. Pydantic at the boundaries: the graph's input_schema when input is untrusted, and anywhere an LLM produces data (tool args, structured output).

The cost to name: LangGraph validates Pydantic state on every state update, so you pay per superstep, and checkpoint serialisation gets heavier.

DesignHow do you decide what belongs in state?

In: anything that must survive across nodes, be checkpointed for resume, or is written by more than one node. Out: derivable values, large blobs (put an S3 key or row id instead — state is re-serialised every superstep), and anything secret, because state is persisted.

If the schema passes about eight fields, that's a signal to factor part into a subgraph with private state rather than widening the parent.

GotchaWhy shouldn't you put a large dataframe in state?

Because every superstep serialises the full state to the checkpoint store. A 40 MB object means a 40 MB write per superstep, plus the same cost on every resume and get_state. It looks like model latency and is actually the serialiser.

Store it externally, put a reference in state.

CoreWhat's a thread, and where does thread_id come from?

One conversation — the checkpoints sharing that id. It comes from your application's model of a conversation (chat session, ticket, workflow instance), not from the framework. One thread per conversation: not per request (amnesia), not per user forever (unbounded growth).

Namespace it (tenant:user:conv) and always verify ownership server-side — a thread id is a key to someone's history.

DebugTwo users see each other's messages. What happened?

Shared thread_id: a hardcoded demo value, an id derived from something non-unique, or — the security version — a client-supplied id with no server-side ownership check.

Fix by deriving it server-side from the authenticated user plus a conversation identifier and checking ownership before invoke. Then treat it as an incident: the checkpoint tables now hold cross-contaminated history.

CodingHow do you delete messages from state?

Return RemoveMessage(id=...) for each — add_messages understands it. A summarisation node returns a list of RemoveMessage plus one new summary message in a single update.

You can't do it by returning a shorter list (the reducer appends), and you mustn't do it by mutating state["messages"].

GotchaYour provider starts rejecting requests after you added trimming. Why?

Orphaned tool calls. An assistant message with tool_calls must be followed by a ToolMessage per call id; a naive last-N window cuts between them and the provider returns a 400.

Trim on conversation boundaries — trim_messages with start_on="human" and include_system=True.

System designDesign memory for an assistant used daily for a year.

Three tiers: working (message list, summary + last k), episodic (per-conversation summaries in the store), semantic (extracted durable facts with embeddings).

Write path: extract at conversation end, not per message; dedupe; supersede contradictions rather than appending. Read path: top-k relevant memories injected with a hard token cap. Governance: timestamps, sources, TTLs, a user-visible “what I remember” view, and deletion that reaches the store.

GotchaWhat goes wrong if you store too much long-term memory?

Retrieval quality collapses — top-k returns vaguely-related fragments instead of the one fact that mattered — and you accumulate contradictions with no current-version marker.

Memory is a curated summary, not a log. If you want full history search, build a search index over transcripts and expose it as a tool.

12.4 HITL and durability

The capabilities that justify the framework. Expect these in any interview for a role shipping agents that touch real systems.

Drill
Very commonHow does interrupt work, mechanically?

It raises. LangGraph catches it, checkpoints the state with next pointing at this node, and surfaces the payload to the caller; the invocation returns and nothing is held in memory. Later, Command(resume=decision) on the same thread restores the checkpoint, re-runs the node, and this time interrupt() returns the decision.

Requires a checkpointer. And keep the node small, because everything above the interrupt executes twice.

Gotchainterrupt() vs interrupt_before?

interrupt_before is a static compile-time breakpoint — always stops, no payload, good for debugging. interrupt() is dynamic — fires only when your code decides, carries a structured payload out and a decision back.

Product features (approval, editing, clarifying questions) use dynamic interrupts.

DesignWhat are the four HITL shapes?

Approve/reject a proposed action; edit — return a modified payload such as a corrected tool argument or reduced amount; provide input — the agent asks a clarifying question; review and continue — an oversight checkpoint.

All four are the same mechanism with a different payload contract, which is worth saying because it means you design the contract, not the plumbing.

DesignWhat if the human never responds?

LangGraph waits forever by design, so you own the deadline. Write the pending interrupt into a review queue with an SLA; a scheduled job escalates, reminds, or resumes with a default decision — usually reject, since the safe default for an irreversible action is not to do it.

Make the timeout policy per-action: a £5 refund can auto-approve after a day; a £5,000 one never should.

ConceptualWhat is time travel, and what's the caveat?

get_state_history() gives every checkpoint; resume from any by passing its config; update_state first to fork with a modification, leaving the original branch intact. Uses: deterministic debugging, what-if analysis, correcting a wrong turn in production.

The caveat: replay re-executes nodes for real — real model calls, real side effects. It's not a simulation.

Very commonWhich durability mode, and why?

"async" as the default — the checkpoint write happens concurrently with the next superstep, so near-full crash protection without a DB round trip on the critical path. "sync" when losing one superstep is unacceptable. "exit" only for short, cheap, side-effect-free runs.

The trade: how much work you'll redo versus how much latency you'll pay per superstep.

System designMake an email-sending node safe under durable execution.

Isolate it in its own node; derive an idempotency key from stable state (f"notify-{order_id}-{stage}", never uuid4()); pass it to the provider; record the returned message id in state and short-circuit on re-entry.

If the provider has no idempotency support, keep your own sent-log keyed by the same value. For expensive or irreversible actions, add an interrupt in front too.

DebugA customer was charged twice. Investigate.

Read the thread's checkpoint history for a superstep that ran twice: a crash-and-resume, an interrupt resume where the charge sat above the interrupt() call, a node retry after a timeout that actually succeeded, or a debug replay against production.

Then check whether an idempotency key was sent and whether it was derived from stable state — a per-execution UUID defeats provider dedup entirely and is the usual cause.

12.5 Tools and MCP

Where most real agent failures live. Interviewers who have shipped agents spend a lot of time here.

Drill
CoreWhat does the model see when you give it a tool?

Name, docstring, and the JSON schema of the arguments including every field description. Never the implementation.

So those three artefacts are prompt: when the model picks the wrong tool or passes a bad argument, the fix is in the name, description or schema. They also cost tokens on every request.

Very commonWhat makes a good tool?

Action-stating name; description that says when and when not to use it, naming the alternative; Literal/enum for closed value sets; few flat scalar arguments; a readable return with ids; an explicit “nothing found” message instead of [].

The test: show only the name, description and schema to a colleague and ask when they'd call it. Their hesitation predicts the model's.

DesignHow granular should tools be?

One tool per user-meaningful action, with the arguments a person would specify. Too coarse (execute_sql) pushes the hard part onto the model and opens a safety hole; too fine degrades selection and fills the prompt with schemas.

Also split by risk: a read tool and a write tool should be separate even against the same table, so you can gate one.

DebugThe agent keeps passing a malformed argument.

Fix the schema, not the prompt: Literal/enum for closed sets, format instructions in the field description, numeric constraints, sensible defaults.

Then make failure recoverable — return “invalid date '03/04/2026'; expected YYYY-MM-DD” rather than raising, so the loop self-corrects.

CodingWhat is tool_choice and when do you set it?

Forces behaviour: "auto", "any"/"required", "none", or a named tool. Uses: mandatory retrieval on the first step; "any" when the model keeps answering from parametric knowledge; "none" for a final prose turn.

Caution: forcing a call when none is appropriate produces a fabricated call with invented arguments. Use it per step, not globally.

DesignHow does tool retrieval work and what's the risk?

Embed tool descriptions; at request time retrieve the top-k relevant and bind only those. The catalogue can be huge while the model sees eight schemas.

The risk: a retrieval failure in front of a selection failure — if the right tool isn't in the top-k, the model confidently does something else. Mitigate with always-on tools, a generous k, retrieving on the current step's intent rather than the original question, and logging misses.

System designHow do you give an agent database access safely?

Capability first: a role with SELECT on specific views and nothing else. Then parse the SQL with a real parser and reject non-SELECT, allow-list tables, wrap with LIMIT and a statement timeout, expose views not base tables, log every query.

Better where it fits: don't hand it raw SQL — offer parameterised tools whose query shapes you wrote.

ModernWhat is MCP, and would you build internal tools as MCP servers?

An open standard for exposing tools, resources and prompts to LLM clients — LSP for tools; m × n becomes m + n. Consumed in LangGraph via langchain-mcp-adapters, which yields ordinary LangChain tools.

Internally: yes when there are multiple consumers or a real ownership boundary; no for a single consumer, where a plain @tool is simpler and faster. MCP is for crossing an ownership boundary.

DesignSecurity implications of third-party MCP servers?

Three: prompt injection via tool descriptions, since the server controls text entering your context; capability grants, since its tools run with whatever access you gave; and mutable tool sets between connections.

Treat them as dependencies: pin and review, run sandboxed with least privilege, alert on tool-list changes, and gate destructive MCP tools like your own.

ModernWhat is agent middleware, and when do you use it over a node?

Hooks around the agent loop — before_model, after_model, before_tool, after_tool, wrap_model_call — replacing callbacks and copy-pasted wrapper code.

Middleware for cross-cutting concerns applying every iteration (trimming, guardrails, budgets, model fallback). A node for anything that's a step in the domain logic. The test: would it appear in the flowchart you'd draw for a colleague? If yes, it's a node.

12.6 RAG in agents

Expect competence rather than depth here unless the role is RAG-specific — but the orchestration questions come up constantly.

Drill
Very commonRAG versus agentic RAG?

Who decides whether and how to retrieve. Pipeline: always once, with the raw query. Agentic: a tool the model may skip, rewrite, repeat, or point at a different source, and react to poor results.

Costs: latency, tokens, non-determinism, and much harder evaluation — a bad answer could be bad retrieval, bad query formulation, or good retrieval the model ignored.

RetrievalRetrieval quality is poor. What do you try, in order?

Measure first with a golden question→document set and recall@k. Then: hybrid (BM25 + dense, fused with RRF) — fixes exact-term failures like error codes; reranking a top-50 with a cross-encoder — usually the biggest single jump; chunking review, including contextual chunking; query transformation; metadata filters.

And check the unglamorous causes: is the content indexed, is ingestion current, are permissions filtering the right doc out?

ConceptualWhy does hybrid search beat dense alone?

They fail on different things. Dense finds paraphrase but blurs exact tokens — error codes, SKUs, rare proper nouns. BM25 nails those and misses paraphrase. RRF fuses them without needing score calibration.

The wins land exactly where users are most annoyed: searching for an identifier copied out of an error message.

System designEnforce document permissions in RAG.

As a hard filter inside the retrieval query, using identity resolved server-side. Chunks carry ACL metadata from ingest; unauthorised documents are never retrieved.

Not post-filtering (the content already entered your process and possibly your traces), and definitely not asking the model to ignore them. Re-check at query time since permissions change, and watch caches and summaries, which can carry restricted content across a boundary.

ModernCRAG and Self-RAG — the precise difference.

CRAG grades the retrieval: correct / incorrect / ambiguous, falling back to web search when documents are poor. Self-RAG makes the model reflect at several points: should I retrieve at all, is this passage relevant, is my statement supported, is the response useful.

Most production systems implement a simplified hybrid — a grading node plus a grounding check — as two structured-output calls rather than the papers' training setups.

DebugRetrieval is good but the answer is wrong. Where's the bug?

Downstream of retrieval. Check whether the docs are actually in the prompt (truncation, trimming, an overwritten channel); position, since middle-of-context content is attended to less — rerank and cut k; conflict with parametric knowledge, which the prompt must resolve explicitly; prompt framing (“answer only from context; say when it isn't there”); and chunk boundaries putting the crucial sentence in the neighbouring chunk.

Systematically: measure retrieval recall and grounded-answer accuracy given gold documents, separately.

System designHow do you evaluate an agentic RAG system?

Decompose: retrieval recall (did any retrieval call fetch the known-correct docs?), decision correctness (did it retrieve when it should and skip when it shouldn't?), groundedness (judge each claim against retrieved text), answer correctness, plus retrieval calls per question and p95 cost.

End-to-end accuracy alone is undiagnostic — “recall unchanged, groundedness down 12” is actionable; “62% success” is not.

DesignHow do you make an agent cite sources reliably?

Give it ids to cite ([doc-17] markers in the context), make citations part of the output schema rather than optional prose, then validate that cited ids exist — models invent plausible ones.

Add a separate grounding check listing unsupported claims, and flag or strip them. Render citations as followable links, or they build no trust.

12.7 Multi-agent

The section where restraint scores highest. Lead with when not to, then show you can build it properly.

Drill
Very commonWhen is multi-agent worth it?

Three cases: genuinely separable expertise (materially different prompts, tools, possibly models), context pressure (the work doesn't fit one window), and organisational boundaries (different teams own and deploy them).

Not worth it for “the task has several steps” (that's a workflow) or “it feels modular” (nodes are already modular). Costs: an extra call per hop, context loss at every boundary, coordination failures, harder traces.

ConceptualMulti-agent system versus a graph with several nodes?

Autonomy at the boundary. In a multi-node graph you wrote the edges. In a multi-agent system each agent has its own loop and prompt, and the transfer of control is itself an LLM decision.

Which is why the failure modes differ: a multi-node graph can't ping-pong, can't lose context at an undefined boundary, and can't have two components each assume the other did the work.

CoreDescribe the supervisor pattern and its weakness.

A coordinator picks the next specialist via structured output and Command(goto=...); specialists have normal edges back. Annotate the return type Command[Literal[...]] so the graph is drawable, and bound hops with a counter checked before the model call.

Weakness: a sequential bottleneck — roughly 2n calls for n steps. Mitigate with parallel dispatch via multiple Sends, a cheap model for routing, and direct handoffs for common adjacent pairs.

CodingHow is a handoff implemented?

A tool returning a Command: Command(goto="billing", graph=Command.PARENT, update={...}).

Three details: graph=Command.PARENT to escape the calling agent's subgraph; a ToolMessage with the matching tool_call_id or the next model call is malformed; and active_agent in state so a checkpointed conversation resumes with the right agent.

DebugTwo agents keep transferring back and forth.

Stop it with a hop counter (add-reducer) checked before any handoff, routing past the cap to a default agent that must resolve or escalate.

Then fix the cause: handoff history in state refusing an immediate return; a required reason argument (articulating why measurably reduces reflexive transfers); sharper “transfer only if…” descriptions; merging agents whose scopes overlap; and checking the handoff carries enough context, since ping-pong is often two agents each lacking what they need.

DesignShared state or message passing between agents?

Hybrid: a shared messages channel for coherence and one readable trace, plus private per-agent channels so scratchpads don't pollute everyone's context.

Pure shared state loses nothing but costs tokens and distracts; pure message passing decouples but risks the receiver missing something. When passing summaries, make them structured — findings, sources, open questions — because prose loses exactly the specifics the next agent needs.

System designName the multi-agent failure modes and their guards.

Ping-pong → hop cap, handoff history, default agent. Diffusion of responsibility → explicit ownership in the task payload, completion check. Context loss → structured handoff artefacts. Cost explosion → per-run token budget between hops. Conflicting writes → reducers or private channels. Untraceable failures → per-agent spans.

Meta-guard: always build and measure the single-agent baseline first.

DebugHow do you debug a multi-agent system?

Trajectory first — the sequence of agents and handoffs, because most failures are coordination failures visible only at that level. Then per-agent spans: exact input, output, latency, cost.

Two techniques specific to this: replay from a checkpoint just before the suspect handoff so you can iterate on one boundary; and test agents in isolation with recorded inputs, which separates “bad at its job” from “given a bad task” — identical end-to-end, completely different fixes.

12.8 Evaluation and observability

The area where senior candidates most reliably separate themselves, because it's the part most people skip.

Drill
Very commonWhy can't you debug an agent with logs?

Agent failures are decision failures, and understanding one requires the exact prompt the model saw — system prompt, tool schemas, full history, retrieved docs. Nobody logs that; a trace captures it natively, along with per-span tokens and latency.

That turns “it gave a bad answer” into “at step 4 it had the right documents and ignored them”.

Very commonHow do you evaluate an agent?

Four independent dimensions: final response, trajectory, single step, and cost/latency. They fail independently — right answer via an absurd route is the version that breaks next month.

Run them as a versioned dataset in CI with relative thresholds against main, and grow the dataset from production failures.

Deep diveWhat is trajectory evaluation and how do you score it?

Comparing the tool-call sequence to a golden path. Matchers: exact (usually too strict — a duplicate call fails), in-order subsequence (good default), any-order set (when steps are independent), superset (most permissive, most dangerous).

Always report the extra-step count and precision alongside, or a wandering run that burned four extra calls passes silently.

DesignWhere does the golden trajectory come from?

Hand-authored from domain rules (“check policy before issuing a refund” is a business rule you should have written down anyway); harvested from highly-rated runs; or expressed as partial-order constraints rather than a full path.

That last form is underrated — “check_policy before issue_refund”, “delete_* never appears” — cheaper to maintain, survives refactors, and encodes what you actually care about.

GotchaIsn't trajectory evaluation too brittle?

Exact matching is, which is why it's rarely the right matcher. Evaluate the properties instead: required steps present, forbidden steps absent, safety ordering respected, step count within budget.

And track the distribution rather than pass/fail per run — “median 4 tool calls, p95 7” moving to “median 6, p95 14” is a regression even though no single run was wrong.

Very commonHow do you make LLM-as-judge reliable?

Name the biases and the controls: position → swap order, count only consistent verdicts; verbosity → rubric penalising padding; self-preference → judge with a different model; leniency → anchored 3-point scales, not 1–10; format → factual criteria only.

Structurally: pairwise beats absolute, reasoning field before the score, and validate against human labels — a judge agreeing with reviewers 70% of the time isn't measuring what you think.

GotchaYour judge scores 4.2/5 on everything.

Leniency plus an unanchored scale. A metric with no variance can't detect a regression, which is worse than no metric because it looks like coverage.

Switch to binary or 3-point with anchored definitions, make criteria specific and checkable, move to pairwise against a baseline, and sanity-check by feeding it deliberately bad answers.

System designHow do you stop prompt changes from silently regressing quality?

A dataset-backed eval gate in CI on any PR touching a prompt, tool, model version or the graph. Relative thresholds against main (“no more than 2 points below”) rather than absolute ideals; gate on cost and latency too; version the dataset; keep the run cheap enough that people tolerate it.

Plus the cultural half: every production failure becomes a dataset entry before it's fixed.

GotchaEval scores are noisy run to run.

Reduce what you can — temperature 0, fixed seeds, stubbed tools with recorded responses. Then measure honestly: several runs per example with a confidence interval, a bigger dataset, and thresholds outside the noise band.

If one specific example flips constantly it's usually informative, not noise — it's genuinely ambiguous and belongs in a separate bucket you inspect.

System designHow do you know your agent is degrading in production?

Four layers, alerting on the leading ones: operational metrics (p95 latency and cost, tool error rate, tool calls per run, recursion-limit hits) — these move before quality does; implicit user signals (retries, rephrasing, escalation, abandonment); explicit feedback; online judges on a small traffic sample.

Close the loop: negative-signal runs go to a review queue, get labelled, and become dataset entries. And re-run offline evals on a schedule, because the world changes even when your code doesn't.

12.9 Production and cost

Where a senior interview spends most of its time. Concrete numbers and named mechanisms beat architectural vocabulary.

Drill
System designHow would you deploy a LangGraph agent?

Async service in a container, Postgres (AsyncPostgresSaver, pooled) for checkpoints, background worker for long runs — return a thread_id immediately and stream or poll.

Don't forget: resume endpoints for HITL, graceful shutdown (durable execution makes it cheap), secrets outside state, and retention for checkpoint tables. Mention LangGraph Platform as the managed alternative when that infrastructure is the work.

Very commonWhat streaming modes are there and which do you use?

values, updates, messages, custom, debug. Production combination: updates + messages + custom — progress labels, the typing effect, and domain progress respectively.

Two details: filter messages by langgraph_node so you don't stream a router's deliberation as the answer; and pass subgraphs=True or inner nodes are invisible.

DebugStreaming works locally but not through your API.

Buffering somewhere in the chain: the framework (must return a streaming response and yield), a reverse proxy (proxy_buffering off / X-Accel-Buffering: no), gzip middleware, or a client not using a streaming reader.

Then LangGraph-side: using invoke instead of astream, a sync node blocking the loop, or missing subgraphs=True.

Very commonYour agent costs 10× the estimate.

Measure per-step from traces first. Then: prompt caching on the stable prefix (usually the biggest win), iteration cap (bounds the tail), model cascade (cheap model for routing/grading), trim or summarise history (the quadratic term), cache tool results, shrink the catalogue.

Then the structural question: does it need to be an agent? Routing common cases to a deterministic path often beats all the tuning.

Deep diveHow does prompt caching work and what breaks it?

Providers cache internal state for a prefix; a later request whose prompt starts byte-identically reuses it at roughly 10% of the input rate, with faster time-to-first-token.

Broken by anything that changes the prefix: a timestamp in the system prompt, reordered tool definitions, retrieved docs placed before static instructions, a model change. Design rule: order the prompt most-static to most-dynamic.

DesignEnforce a hard cost ceiling per request.

Accumulate token usage into an operator.add channel after each model call (middleware's after_model is a clean place), and have a routing function check the total against the budget before continuing, diverting to a “finish with what we have” branch.

Plus per-tenant daily budgets, alerts on p95 cost not the mean, and recursion_limit as a coarse backstop. Degrade rather than abort.

System designYour agent takes 15 seconds. Get it under 5.

Break down the traces — it's almost always sequential model calls. Then parallelise independent steps, downgrade routing and grading to a small fast model, remove iterations by improving tool descriptions and returns, shorten prompts (TTFT scales with input), and prefetch highly likely retrievals.

Then the perceptual half: stream progress and tokens — a 6-second run showing its work beats a 4-second blank screen.

Debugp50 is 2 s, p95 is 20 s.

Bimodal — find the long runs in traces. Usual causes: a subset of queries triggering many more iterations, retry/backoff after 429s, one slow dependency on a branch, very long conversations, or cold starts and pool exhaustion.

Always-right fixes: cap iterations and alert on p95. If the long path is legitimate, make it visibly asynchronous rather than holding a request open.

Very commonHow do you defend against prompt injection?

Frame it as a privilege problem. The dangerous form is indirect — instructions planted in content your agent retrieves — and to the model it's indistinguishable from your instructions, so detection is unreliable by construction.

Assume it succeeds: least-privilege tools (no arbitrary HTTP, no send-to-any-recipient, credentials scoped to the end user), approval gates on outbound actions, treat all tool output as untrusted data, egress controls, escape output before rendering. Guardrail prompts are defence in depth, not a control.

DesignWhere do secrets live?

Not in state (persisted in checkpoints) and not in the prompt (captured in traces). They live in a secret manager, read by the tool implementation at call time, ideally as short-lived scoped tokens.

Also redact traces, since tool arguments are captured verbatim. And note the model should never need a secret — it requests an action, your code supplies credentials.

System designScale to 10,000 concurrent users.

Lead with: the bottleneck is the provider's rate limit, not your infrastructure. Then: stateless horizontally-scaled async pods (state lives in the checkpointer), pooled Postgres with an eye on write throughput, a queue with per-tenant fairness and graceful backpressure.

Agent-specific: per-tenant token budgets as well as request limits, degradation under load (smaller iteration cap, cheaper model, drop optional enrichment), and caching to raise effective throughput against a fixed quota.

Very commonHow do you test a non-deterministic agent?

Most of the system is deterministic: unit-test routing functions (plain Python over state), reducers (including empty and concurrent cases), tools (with error paths), and graph structure (compile and assert reachability). Stub the model to make LLM nodes deterministic. Only end-to-end needs statistical evaluation.

Saying “you can't really test agents” misses five sixths of the work — and most agent bugs are graph bugs, not model bugs.

System designYour agent misbehaves at 2 a.m. Runbook?

Contain: kill switch to a deterministic fallback or human queue; roll back prompt/model config (config, not deploy); disable the offending tool; check the spend circuit breaker.

Diagnose: recent traces versus pre-change traces, trajectories first. What changed — your deploy, a prompt edit, a provider model update, an upstream API?

Follow up: add the failing cases to the golden dataset before fixing, and use checkpoints to find and remediate affected threads.

12.10 Frontier and senior signal

Positions, not facts. The goal is to show you've thought about the open questions and can hold a view under pushback.

Drill
ModernWhat is context engineering?

Deciding what occupies the finite context window on every call — the composition, not the wording. Four operations: write (persist outside), select (retrieve only what's needed), compress (summarise, trim), isolate (sub-agents get their own contexts).

The unifying claim: memory management, RAG, tool selection and history trimming are four instances of one problem, not four topics.

ConceptualMillion-token windows — is memory management obsolete?

No. Cost scales with tokens on every turn; latency (TTFT) scales with input length; and attention degrades over long contexts, so a focused 8k context routinely beats an unfocused 500k one.

Bigger windows raised the ceiling and turned selection from a capacity workaround into a quality technique.

System designDesign an agent that runs for six weeks.

Episodic: a scheduled trigger wakes the graph, does a bounded chunk of work, writes a durable summary, exits. Plan and objective in dedicated state channels (never summarised away), re-read each episode. interrupt at milestones. A running budget in state. Timestamps on gathered facts, re-verified before acting.

This is where LangGraph's persistence has no real substitute — the alternative is building checkpoint-and-resume yourself.

GotchaWhat is goal drift?

Over a long run the agent optimises for something adjacent to the objective, because the objective sits at the start of a history that keeps getting summarised while recent tactical detail dominates.

Prevent with a dedicated never-summarised objective channel re-injected each episode, checkable success criteria, a periodic alignment check, and human review at milestones — drift is far easier for a person to spot than for the drifting agent.

ModernMCP, A2A, AG-UI — what does each solve, and which has settled?

MCP: agent ↔ tools/data — settled, build against it. A2A: agent ↔ agent across organisations — real problem, not yet converged, and most teams don't have it. AG-UI: agent ↔ user interface — early; building on your framework's streaming primitives is defensible today.

The signal being tested is whether you distinguish adopted from announced.

ConceptualCan agents learn from their mistakes?

Through mechanisms you build: outcomes written to a store and retrieved for similar cases; successful examples accumulated as few-shot; prompt optimisation against an eval set; a routing classifier trained on logged trajectories.

The prerequisite is a reliable outcome signal — without it you're accumulating unlabelled history and reinforcing errors. Self-improvement is downstream of evaluation, not a substitute. And self-modifying code in production is research, not practice.

Conceptual“Frameworks will be obsolete when models get good enough.”

Disagree, specifically: a better model improves decisions; it doesn't provide persistence, resumability, HITL or observability. A perfect reasoner still can't pause three days and resume in another process, or be inspected at step 4 of a failed run.

Concede where it has force: the orchestration scaffolding does shrink — fewer reflection loops, less prompt hand-holding — so the framework's centre of gravity moves toward durable execution and observability. And if you need none of those, a plain SDK loop is right today.

ConceptualWhat's the most overrated idea in agentic AI right now?

Multi-agent as a default architecture. The org-chart metaphor is intuitive and mostly wrong; most three-agent systems work better as one agent or a workflow with one agentic node. Runner-up: benchmark scores as evidence of production readiness.

Underrated, since the question invites it: tool design — unglamorous, where most real failures live, and an afternoon rewriting descriptions and return values routinely beats a week of architecture.

12.11 The trap questions ⭐⭐

Agentic-AI interviews are lost on a small number of confidently-wrong answers. Each of these has an obvious answer that is wrong, and a correct answer that sounds less impressive.

Traps — the answer that sounds good and isn't
Trap 1“Design an agent to classify and route support tickets.”

Trap: designing a multi-agent triage system. Correct: that's not an agent — it's one classification call with structured output and a deterministic route. ~500 ms, testable against labels, trivially cheap.

Then show the boundary: it becomes agentic if routing requires lookups whose number and order depend on what you find. Volunteering the boundary is what makes this a strong answer rather than a contrarian one.

Trap 2“How do you stop prompt injection?”

Trap: “a guardrail prompt telling it to ignore instructions in retrieved content.” Correct: it's a privilege problem. Injected text is indistinguishable from your instructions, so assume it succeeds and constrain what it can achieve — least-privilege tools, approval gates on outbound actions, egress controls, scoped credentials.

Guardrail prompts reduce frequency. They are not a control.

Trap 3“Should we use multi-agent for this?”

Trap: yes, with an architecture diagram. Correct: usually no. Ask whether the sub-agents would have materially different prompts and tools, whether there's real context pressure, and whether an ownership boundary exists. If not, one agent with good tools wins on every axis.

The clincher: “I'd build the single-agent baseline first and measure it.”

Trap 4“The checkpointer gives you memory, right?”

Trap: agreeing. Correct: it gives within-thread persistence. Cross-conversation memory is the store. Conflating them is the tell that someone has only done tutorials.

The distinguishing sentence: the checkpointer remembers this conversation; the store remembers this user.

Trap 5“Three parallel nodes each increment a counter. What's the result?”

Trap: “3”. Correct: with the default overwrite reducer it raises InvalidUpdateError; with a max or last-write reducer it's 1, because all three read the same pre-barrier value.

To count parallel completions, use Annotated[int, operator.add] and have each node return {"count": 1} — in a fan-out, nodes return their contribution, not the computed total.

Trap 6“Just increase recursion_limit — the graph needs more steps.”

Trap: raising it. Correct: hitting the limit is almost always a bug — an unreachable exit condition, a model looping on uninformative tool results, or a lost counter increment in a fan-out. Raising it converts a fast failure into an expensive one.

Diagnose from the trajectory first; raise the limit only after confirming the graph legitimately needs more supersteps.

Trap 7“Context windows are huge now, so we don't need RAG or memory management.”

Trap: agreeing. Correct: three reasons that have nothing to do with fitting — cost per token every turn, latency scaling with input length, and attention degradation over long contexts. A focused 8k context routinely beats an unfocused 500k one.

Big windows made selection a quality technique rather than a capacity workaround.

Trap 8“We'll add a retry so the flaky tool stops failing.”

Trap: adding retries at every layer. Correct: retries multiply — 3 in the tool × 3 at the node × an agent loop retrying = 27 calls to a struggling dependency, a self-inflicted DDoS.

Pick one owner per failure class, use backoff with jitter, add a circuit breaker, and note that retries don't fix a model making a bad decision.

Trap 9“The agent's answer was correct, so the run was fine.”

Trap: accepting it. Correct: a right answer via six unnecessary tool calls is right today and broken the moment one of those tools changes. A right answer from parametric knowledge instead of the retrieved documents is right by luck.

Trajectory and step-level evaluation exist precisely to catch answers that are correct for the wrong reasons.

Trap 10“Put the API key in state so the tool can use it.”

Trap: doing it. Correct: state is serialised into checkpoints, so that key is now in your database, in every state snapshot, and readable by anyone who can read a thread. Prompts and tool arguments are also captured in traces.

Secrets live in a secret manager, read by the tool implementation at call time. The model never needs one — it requests an action; your code supplies credentials.

Trap 11“We use AgentExecutor — that's the standard way, isn't it?”

Trap: agreeing, or dismissing it as merely “old”. Correct: it's the deprecated 0.x API, along with initialize_agent and langgraph.prebuilt.create_react_agent; the current one is create_agent.

Then say why it changed: AgentExecutor was an opaque loop with no inspectable state, no interruption, no resume, no time travel. create_agent returns a real graph, so all of that comes free.

Trap 12“Time travel lets you safely test what would have happened.”

Trap: treating replay as a simulation. Correct: replay re-executes nodes for real — real model calls, real tool calls, real side effects. Replaying a range containing a send or a charge does it again.

Same idempotency requirement as crash recovery, arriving from a different direction.

12.12 System design scenarios

Six full scenarios. Practise them out loud with a whiteboard: state schema, graph shape, guards, then operations.

The structure that works for every one of these

1. Clarify scope and non-goals. 2. Say what the simplest thing that could work is — and why it isn't enough here. 3. State schema and graph shape. 4. Guards: iteration cap, budget, approval gates, fallbacks. 5. Operations: persistence, streaming, tracing, evaluation. 6. What you'd measure and what would make you change the design.

Scenarios
System design1 · Customer support triage agent

Shape: router (cheap model, Literal + confidence, fallback branch) → per-category handler. The refund/billing branch is a tool-calling agent with read-only tools (order lookup, policy retrieval, prior refunds); the action tool is gated.

State: messages (add_messages), category, confidence, customer_id, iterations. Thread per conversation, namespaced by tenant.

Guards: confidence threshold → general handler; iteration cap; interrupt on refunds above a threshold with a full decision payload; escalation-to-human branch.

Ops: Postgres checkpointer, streaming updates + messages, traces tagged with category and tenant, golden dataset of labelled tickets with router accuracy as its own metric.

System design2 · Research assistant with parallel search and reflection

Shape: plan (decompose into ≤8 sub-questions) → conditional edge returning one Send per sub-question → researcher workers writing to findings: Annotated[list, add] → synthesise → critique (structured: score + gaps) → conditional: accept, or one more targeted research wave.

Why this shape: the fan-out turns n sequential researches into one superstep, which is the main latency win; the reflection loop is bounded at two rounds with best-draft retention.

Guards: cap fan-out width; async workers; per-worker error capture so one failure doesn't lose the rest; overall token budget.

Ops: checkpointer so a long research run survives a restart; custom stream events for “4 of 8 complete”; citations carried through with source ids.

System design3 · SQL analytics agent

Shape: schema-retrieval node (only the relevant tables, not the whole catalogue) → generate SQL with structured output → validate (parse with a real parser, reject non-SELECT, allow-list tables, inject LIMIT) → execute against a read-only replica with a statement timeout → interpret results → optional retry on error with the error text fed back.

Security is the answer here: capability first (read-only role on specific views), then parsing, then limits, then logging every query with user and thread.

Guards: row and byte caps on results (a 2M-row result destroys your context and your bill); retry cap of 2; refuse rather than guess when the schema doesn't support the question.

System design4 · Code review agent

Shape: fetch diff → fan out one reviewer per file (or per concern: correctness, security, tests) via Send → merge findings with an add-reducer → dedupe and rank → verify each finding against the actual code (a second pass that tries to refute it) → post.

The design point: the verification pass is what makes it usable — unverified LLM review findings have a high false-positive rate, and false positives are what get a review bot turned off.

Tools: read file, read symbol definition, run tests, search the repo. All read-only; posting is the only write and it's rate-limited.

Eval: golden PRs with known issues; measure recall on real bugs and false-positive rate, because the second is what determines adoption.

System design5 · Multi-tenant chatbot at 10k users

Isolation: thread ids namespaced tenant:user:conv, tenant resolved server-side from the session, ownership checked before every invoke, row-level security on checkpoint tables, tenant filters inside retrieval queries.

Capacity: the provider rate limit is the ceiling. Stateless async pods, pooled Postgres, a queue with per-tenant fair scheduling, backpressure that degrades rather than errors.

Fairness: per-tenant request limits and token budgets, because agent cost per request varies by orders of magnitude.

Cost: prompt caching, a cheap model for routing, trimming policy, tool-result caching. Retention: TTL on old threads plus a deletion path that reaches the checkpoint store.

System design6 · Long-running campaign agent (weeks)

Episodic execution: a scheduled trigger wakes the graph; each episode re-reads the objective and plan from dedicated state channels, does bounded work, writes a durable summary, exits.

Why not continuous: processes restart, deploys happen, and a six-week in-memory run is a fiction. Checkpointing makes episodes the natural unit.

Oversight: interrupt at milestones (approve the plan, approve the first send, approve spend above a threshold), with a review queue and SLA-based escalation.

Drift and staleness: objective channel never summarised; periodic alignment check; timestamps on gathered facts with re-verification before acting; a running budget in state, not a per-request cap.

12.13 Coding exercises

Whiteboard-sized tasks. If you can write these from memory you can write anything they'll ask.

Write these out
Coding1 · A minimal ReAct agent, by hand

Two nodes, one conditional edge, one cycle. MessagesState; an agent node calling model.bind_tools(tools); a ToolNode; should_continue checking the iteration cap first and then last.tool_calls; add_edge("tools", "agent"). Compile with a checkpointer.

The details that score: the cap check before the tool-call check, and knowing that create_agent does exactly this so you'd only hand-roll it when you need to change the loop.

Coding2 · Map-reduce with Send

plan produces subtopics; a conditional edge returns [Send("worker", {"subtopic": s}) for s in state["subtopics"][:MAX]]; workers return {"sections": [{"idx": i, "text": ...}]} into an operator.add channel; compile sorts by index.

Score points for: the index (concurrent write order isn't guaranteed), the width cap, async workers, and per-worker error capture returning a sentinel instead of raising.

Coding3 · An approval gate

A tiny node calling interrupt({...}) with everything the reviewer needs; a resume contract of {"approved": bool, "amount": optional, "note": str}; the actual action in a separate downstream node.

Say why the action isn't in the interrupt node: the node re-runs from the top on resume.

Coding4 · A bounded reflection loop

generate → critique (structured: score, issues, accept) → conditional edge checking iterations >= MAX first, then the score threshold. Channels: draft, best_draft, best_score, iterations.

Return best_draft, not the last one — quality degrades on over-revision, and this makes that harmless.

Coding5 · A custom reducer with dedup

def merge_docs(cur, new): seen = {d["id"] for d in cur}; return cur + [d for d in new if d["id"] not in seen], used as docs: Annotated[list[dict], merge_docs].

Mention: pure, non-mutating, handles an empty cur, and is order-insensitive enough for concurrent writes.

Coding6 · A safe SQL tool

Parse with sqlglot, reject anything that isn't a SELECT, allow-list tables, wrap in SELECT * FROM (...) LIMIT n, execute on a read-only pool with a timeout, and return a corrective string rather than raising on rejection so the model can fix its query.

Say the important part out loud: the read-only credential is the control; the parsing is defence in depth.

Coding7 · A supervisor with Command

def supervisor(state) -> Command[Literal["researcher","writer","__end__"]], hop cap checked first, structured decision {next, instruction}, returning Command(goto=..., update={...}); specialists have normal edges back.

Explain the return-type annotation: it's what lets the compiled graph be drawn correctly.

Coding8 · Trim history without breaking tool pairs

trim_messages(messages, max_tokens=N, strategy="last", token_counter=model, include_system=True, start_on="human"), applied in a before_model middleware or a node returning RemoveMessages.

The point to make: start_on="human" is what prevents orphaning a tool call from its ToolMessage, which providers reject outright.

Likely follow-ups
Practical“Walk me through a project you built.”

Structure it as: the problem, the simplest thing you tried first, what failed and how you knew, what you changed, and what you measured. Land on a number — latency, cost per request, accuracy on your eval set.

Then volunteer a limitation and what you'd do next. Interviewers are calibrating whether you can evaluate your own work; a candidate with no criticisms of their project reads as someone who never measured it.

Practical“What was the hardest bug?”

Self-test
DebugCover the table. Given “the graph runs but nothing is persisted”, what are your three checks?

1. Was the graph compiled with a checkpointer at all? Without one, it runs perfectly and silently keeps nothing. 2. Is a thread_id being passed in config["configurable"], and is it stable across turns? 3. Is the checkpointer an InMemorySaver that looked fine in a notebook and is lost on restart in production?

If all three pass, check durability — "exit" only persists at the end of a run.

DebugGiven “findings from parallel workers are missing”, what's your first hypothesis?

The channel has no reducer — either you're getting an InvalidUpdateError you've swallowed somewhere, or the channel overwrites and only one worker's write survives. Fix with Annotated[list, operator.add].

Second hypothesis: the workers are writing to a channel name that isn't in the parent schema, or a Send worker is reading state it was never given.

CodingWhich of these is set at compile time and which at invocation?

Compile: checkpointer, store, interrupt_before/interrupt_after, name. Invocation: thread_id and any per-request context in configurable, recursion_limit, durability.

The principle: compile-time is infrastructure, invocation-time is per-request. Putting a thread_id into compile() is a category error that shows up as every user sharing one conversation.

ModernWhat's new in LangGraph 1.2.x worth mentioning?

trace_policy on add_node (1.2.11) for per-node tracing control — useful for turning down noise from hot, uninteresting nodes without disabling tracing globally. And a typed v3 stream_events return with native projections (1.2.10).

Don't over-index on patch numbers in an interview — knowing that create_agent superseded AgentExecutor and that memory moved from chain wrappers to checkpointers and stores matters far more than any release note.
