Foundations & Core Primitives
Agentic ladder, agent anatomy, state, reducers, Command, Send
API currency · read this first

LangChain and LangGraph hit 1.0 LTS in October 2025. The single biggest source of tutorial confusion right now:

AgentExecutor, initialize_agent, and langgraph.prebuilt.create_react_agent are all deprecated. The current prebuilt entry point is from langchain.agents import create_agent, which runs on the LangGraph runtime. LangGraph is the runtime; LangChain is the batteries-included layer on top — "LangGraph vs LangChain" is a layering question, not a rivalry. All LangChain packages require Python 3.10+. Any tutorial from 2023–24 using AgentExecutor is teaching deprecated syntax.

Level 0 + 1 · Foundations

What makes a system agentic

Conceptual ground first — the typing features LangGraph leans on, the capability ladder from traditional AI to agents, what an agent is actually made of, the canonical architectures, and the senior-signal answer: when not to build one.

1.1 Prerequisites & the typing that matters

Skip the Python basics if you're comfortable — but do not skip the typing section. LangGraph encodes its most important behaviour in type annotations, and one annotation causes more bugs than everything else combined.

You need: functions/decorators/closures, async/await and asyncio.gather, generators and yield (streaming depends on them), Pydantic v2 (BaseModel, validation, model_dump()), and env management (venv/uv + python-dotenv). On the LLM side: tokens and context windows, temperature/top-p, the chat roles (system / user / assistant / tool), embeddings and cosine similarity, function/tool calling at the API level, structured output and JSON mode, and why grounding reduces hallucination.

Why Annotated matters

This one distinction drives LangGraph's entire state-merging model:

A plain key is overwritten by whatever a node returns. An Annotated[T, reducer] key is merged by calling reducer(current, update). That's the whole mechanism — and §1.9 shows why getting it wrong raises an error rather than silently doing the wrong thing.

1.2 The AI capability ladder

Interviewers open here almost every time. The ladder positions agentic AI against everything that came before it — and the one-liner at the top of this section is what they're listening for.

Interview tip · the one-liner to memorise

"GenAI is a capability; Agentic AI is a behaviour." The same model powers both — what changes is whether the system is handed a prompt or a goal, and who decides the intermediate steps.

1.3 Anatomy of an agent

Six behavioural characteristics, five architectural components. Being able to name both — and map a system you've built onto them — is the fastest way to sound like you've shipped agents rather than read about them.

The six characteristics

  • Autonomy — acts without step-by-step prompting
  • Goal-orientation — a persistent objective drives all actions
  • Planning — decomposes goals, generates candidate plans, selects one
  • Reasoning — chooses tools, handles errors, evaluates results
  • Adaptability — pivots when a strategy fails
  • Context awareness — uses memory to know where it is

1.4 Canonical agent architectures

Six shapes cover almost every agentic system you'll be asked to design. Know each one's loop, and what it costs.

Read the primary sources for two of these: ReAct (Yao et al.) and Reflexion (Shinn et al.) — they're among the most-cited references in interview loops.

1.5 When not to build an agent

The answer interviewers respect most. Enthusiasm for agents is cheap; judgment about when they're the wrong tool is the senior signal.

Agents add latency (multiple LLM round-trips), cost (3–10× the tokens), and non-determinism (the same input can take a different path). If the task is deterministic and the steps are known in advance, write a workflow — or plain code — not an agent. Reach for agency only when the path genuinely can't be enumerated ahead of time.

1.6 The framework landscape

Be ready to defend a choice with tradeoffs, not name-drop. The question is rarely "which is best" — it's "why did you pick that one for this problem."

FrameworkModelPick it when
LangGraphGraph-based, explicit stateMaximal control, durability, HITL — the production/enterprise default

AutoGenConversational multi-agentAgents that talk to each other (Microsoft)
OpenAI Agents SDKProvider-nativeAll-in on OpenAI, minimal glue
Pydantic AI / MastraType-first / TypeScriptStrong typing; TS-native stacks
The framing that fails · "LangGraph vs LangChain"

They are layers, not rivals. LangGraph is the runtime — the graph engine, state, checkpointing, streaming. LangChain is the batteries-included layer on top: model wrappers, tools, and create_agent, which itself runs on the LangGraph runtime. Answering "LangGraph is better" reveals you've misunderstood the stack. Say instead: "You use both — LangChain for components and the prebuilt agent, and you drop down to a hand-built StateGraph when you need control the prebuilt doesn't give you."

Likely interview questions
ConceptualWhat distinguishes an agent from a workflow?

Who decides the control flow. In a workflow, the developer fixes the sequence of steps up front — the LLM fills in content but never chooses what runs next. In an agent, the LLM decides: which tool to call, whether to loop, when it's done. That autonomy buys adaptability to paths you couldn't enumerate, at the cost of latency, tokens, and non-determinism. You'd deliberately choose a workflow whenever the steps are knowable — it's cheaper, faster, testable, and debuggable.

ConceptualWhat's the difference between LangChain and LangGraph in 2026?

They're layers of one stack, not competitors. LangGraph is the low-level runtime: a graph engine with explicit state, reducers, checkpointing, streaming, and durability. LangChain is the higher-level library — model/tool abstractions and the prebuilt create_agent, which is built on the LangGraph runtime. Use create_agent for the common ReAct-style case and drop to a hand-built StateGraph when you need custom control flow, multi-agent topologies, or bespoke state.

GotchaWhen is an agent the wrong solution?

When the path is deterministic and enumerable. Agents add latency (many LLM round-trips), cost (3–10× tokens), and non-determinism that makes testing and debugging hard. If you can write the steps down, write a workflow or plain code — you get speed, reproducibility, and far easier evaluation. Reserve agency for genuinely open-ended tasks (research, multi-hop investigation, unpredictable tool sequences). A candidate who says "use an agent for everything" is signalling inexperience.

ConceptualExplain ReAct. Where does it break down?

ReAct interleaves Thought → Action → Observation in a loop: the model reasons about what it needs, calls a tool, reads the result, and repeats until it can answer. It's the default single-agent pattern and maps directly onto a two-node LangGraph cycle (agent ⇄ tools). It breaks down on long horizons — it can wander, repeat tool calls, or loop without converging; context grows with every observation until it overflows; and errors compound because each step conditions on the last. Mitigations: bound iterations, add a planner (plan-and-execute) or a critic (reflection), compress observations, and evaluate the trajectory rather than just the final answer.

Level 2 · LangGraph Core Primitives

The foundation everything sits on

Master this completely — every pattern, memory feature, and multi-agent topology in Parts 2–5 is these six primitives recombined: state, nodes, reducers, edges, Command, and Send.

1.7 Your first graph & the mental model

A LangGraph graph is a flowchart where nodes are ordinary Python functions and edges are control flow. The whole framework follows from that plus one rule: nodes return partial state updates.

The mental model — five rules

  • A graph is a flowchart: nodes are Python functions, edges are control flow.
  • Nodes return partial state updates — a dict of only the keys they changed, never the whole state.
  • START and END are sentinels, never executed as nodes.
  • Execution happens in rounds called supersteps (the Pregel model, from Google).
  • Two nodes reachable from the same source in one step run in parallel.

1.8 State schemas

State is the single object every node reads from and writes to. You define its shape with a schema — and you can expose a narrow public interface while keeping internals private.

Three schema options: TypedDict (most common, no runtime validation), Pydantic BaseModel (runtime validation, slower), or a dataclass. Beyond the shape, you can separate what callers send, what they get back, and what only flows between nodes:

This matters in production: your graph's public contract stays stable while you refactor internals freely, and you don't leak scratchpads, raw tool output, or intermediate reasoning to the caller.

1.9 Reducers ⭐

The most-asked LangGraph interview topic, and the source of more bugs than anything else. A reducer tells LangGraph how to merge a node's write into existing state.

A custom reducer is just a function (current, update) -> merged:

Common pitfall · returning the whole state from a parallel node

A node must return only the keys it changed. Returning the entire state object from a node that runs in parallel means it "writes" every key — including ones the sibling branch is also writing — which trips InvalidUpdateError on keys you never intended to touch. Return partial dicts, always.

Likely interview questions
CoreWhat is a reducer and why does it exist?

A reducer is a function (current, update) → merged attached to a state key via Annotated[T, reducer]. It tells LangGraph how to combine a node's write with the existing value instead of overwriting it. It exists because nodes return partial updates and, in a superstep, several nodes may write the same key — LangGraph needs explicit merge semantics rather than guessing. Common ones: operator.add (concatenate), add_messages (append + dedupe by id), or any custom function.

TrapWhat happens when two parallel nodes write the same key without a reducer?

InvalidUpdateError — it does not silently merge and it is not "last write wins." LangGraph deliberately refuses to guess. The naive answers ("it merges" / "last one wins") are exactly what this question is designed to catch. Fix by declaring a reducer on that key, or by having the branches write to different keys.

MechanicsWhat's special about add_messages?

It's the purpose-built reducer for chat history. It appends new messages, dedupes by message id (so re-emitting a message updates rather than duplicates it), and understands RemoveMessage for deleting specific messages from history — which is how you implement targeted context trimming (Part 2, §2.10). Note RemoveMessage needs a real message id to match.

MechanicsExplain supersteps.

LangGraph executes in discrete rounds (the Pregel model). In each superstep, every node scheduled for that round runs — potentially in parallel — reading the state as it stood at the start of the round. Their partial updates are merged into state (applying reducers) at the end of the round, and the next round is scheduled. That's why parallel siblings can't see each other's writes, why the merge is where reducers apply, and why a checkpointer snapshots state once per superstep.

1.10 Edges & conditional routing

Edges are control flow. Static edges always fire; conditional edges call a router function that returns the name of the next node — not data. That distinction trips people up constantly.

The path_map is optional if the router returns node names directly, but it's good practice: it documents the possible destinations and lets the router return semantic labels decoupled from node naming. Typing the router with Literal[...] also lets LangGraph draw the correct edges in the visualisation.

1.11 The Command primitive

A node normally returns a state update, and a separate conditional edge decides where to go next. Command collapses both into one return value — update and routing together.

Command has two other important uses: navigating to a node in a parent graph with graph=Command.PARENT (the mechanism behind multi-agent handoffs, Part 4), and resuming after an interrupt with Command(resume=...) (the HITL pattern, Part 2).

1.12 The Send API — dynamic fan-out

Static edges require you to know the branches at build time. Send is for when you only learn at runtime how many parallel branches you need — the canonical map-reduce in LangGraph.

Likely interview questions
MechanicsSend vs conditional edges — when do you need Send?

A conditional edge picks which of a fixed, build-time-known set of nodes runs next. Send spawns N parallel instances of a node where N is only known at runtime, and — crucially — each instance receives its own payload rather than the shared graph state. Use Send for map-reduce: one worker per search result, per document section, per sub-question. Results merge back via a reducer on the target key.

MechanicsWhat does Command let you do that a conditional edge can't?

Return a state update and a routing decision together from inside the node, instead of splitting them across a node plus a separate router function. It also does two things edges can't: navigate to a node in a parent graph (graph=Command.PARENT) — the basis of multi-agent handoffs — and resume a paused graph after an interrupt() via Command(resume=value).

1.13 Interview focus — the Level-2 checkpoint

You should be able to explain, without notes: nodes vs edges, partial updates, supersteps, why reducers exist, when Send beats a static fan-out, and what Command replaces. Here's the consolidation.

Four workflow patterns, checkpointers, Store, HITL
Level 3 · Workflow Patterns

Four shapes, endlessly recombined

Every agentic system is these four patterns glued together: sequential, parallel, conditional, and iterative — plus deferred nodes as the synchronisation trick. Build each twice: once with a non-LLM toy so you see the mechanics, once with an LLM.

2.1 Sequential (prompt chaining)

A linear graph where each node enriches state. The simplest pattern, and the right default whenever the steps are known.

Practice ladder: a BMI calculator with no LLM at all (so you see pure state mechanics) → an outline generator → a blog writer that chains outline → draft → polish.

2.2 Parallel (fan-out / fan-in)

Multiple independent nodes in one superstep. This is where reducers stop being theory — parallel branches must return partial updates into a reduced key.

Drop the Annotated[..., operator.add] and this graph raises InvalidUpdateError the moment two evaluators finish in the same superstep — the single most common beginner failure.

2.3 Conditional (branching)

A router function plus add_conditional_edges. The trick that makes it reliable: force the classification into a closed set with Literal in a Pydantic schema.

Practice: a quadratic solver branching on the discriminant (no LLM — pure mechanics), then a customer-review bot routing on sentiment with an extra diagnosis sub-step for negative reviews.

2.4 Iterative (cycles)

Loop back to an earlier node instead of hitting END. This is what makes LangGraph a graph rather than a chain — and it's where runaway agents come from if you don't bound it.

The canonical shape is evaluator–optimizer: generate → critique → regenerate until the critic passes. Always bound the loop with a counter in state, and know the framework-level backstop:

Common pitfall · the counter you forgot to increment

A cycle whose counter is read but never incremented (or is stored on a key that gets overwritten) loops until GraphRecursionError — burning tokens the whole way. recursion_limit is a safety net, not a design: it stops the process but gives you no partial answer and no graceful degradation. Bound the loop semantically and keep the limit.

2.5 Deferred nodes (synchronisation barriers)

A subtle but interview-worthy primitive: defer=True makes a node wait until all upstream paths complete — solving parallel branches of unequal length.

Likely interview questions
MechanicsHow do you prevent an infinite loop in a cyclic graph?

Two independent guards. Semantic: keep an iteration counter in state, increment it in the loop body, and have the router exit at a max (plus an exit on success). Framework: recursion_limit (default 25) raises GraphRecursionError past N supersteps — a safety net, not a design. Also give the loop a meaningful stop condition (a critic that can actually pass) and return the best-so-far result on exhaustion rather than failing hard.

MechanicsWhat is a deferred node and what problem does it solve?

A node declared with defer=True runs only after all upstream paths reach it, instead of firing when the first one arrives. It solves parallel branches of unequal length: without it, an aggregator downstream of a 1-hop branch and a 3-hop branch executes early on partial data. It's the clean way to build a synchronisation barrier for map-reduce fan-in, consensus voting, or multi-agent collaboration.

Level 4 · State, Persistence & Memory

Where junior and senior candidates separate

Persistence is what turns a script into a product: conversations that survive a restart, agents you can pause for human approval, runs you can rewind and debug. It also contains the single most reliable discriminator question in LangGraph interviews — checkpointer vs Store.

2.6 Checkpointers — short-term, thread-scoped memory

A checkpointer snapshots the entire state after every superstep. That one mechanism gives you conversation memory, crash recovery, time travel, and human-in-the-loop — they're all the same feature.

  • thread_id isolates conversations — User A's memory never bleeds into User B's.
  • Dev → InMemorySaver. Prod → SqliteSaver or PostgresSaver (async variants: AsyncSqliteSaver, AsyncPostgresSaver).
  • No checkpointer = no memory, no HITL, no time travel. No thread_id = the checkpointer silently does nothing useful.

2.7 Inspecting state & time travel

Because every superstep is a checkpoint, you can read the state at any point, edit it, rewind to a past checkpoint, and fork a different branch from there. This is the debugging superpower for non-deterministic agents.

Primary use is debugging: an agent took a bad turn at step 7, so you rewind to step 6, change one value, and replay to see whether your fix actually helps — without re-running the expensive earlier steps.

2.8 The Store — long-term, cross-thread memory ⭐

The classic interview discriminator. A checkpointer gives within-thread memory keyed by thread_id; a Store gives cross-thread memory keyed by namespace (usually user_id). Confusing them is the most common telling mistake.

2.9 The long-term memory pipeline

Having a Store isn't having memory — you need a pipeline that decides what is worth remembering, and gets it back into the prompt at the right moment.

2.10 Context window management

Conversations grow; context windows don't. Three strategies, and interviewers like to hear you compare them rather than name one.

StrategyToken efficiencyContext lossComplexity
Trimming (trim_messages)HighHigh — drops old turns wholesaleLow
Deletion (RemoveMessage)ModerateTargeted — you choose what goesLow–Med
SummarizationHighLow — meaning preservedMed–High

start_on/end_on matter more than they look: cutting between an assistant tool-call and its ToolMessage leaves an orphaned call that many providers reject outright.

2.11 Human-in-the-loop

Pause the graph, show a human the pending action, resume with their decision. The modern mechanism is interrupt() — and it only works because checkpointing already gives you durable pause/resume.

2.12 Interview focus — the Level-4 checkpoint

You should be able to explain the difference between a checkpointer and a store in one sentence each, without hesitating. Here are the questions this level generates.

Likely interview questions
Trap ⭐Checkpointer vs Store — what's the difference?

A checkpointer persists the graph's state after every superstep, scoped to a thread_id — it's within-conversation memory, and it's what enables resume, time travel, and HITL. A Store is a separate key-value (optionally vector-indexed) service scoped to a namespace, usually user_id — it's cross-conversation memory. Rule of thumb: "what happened in this chat?" → checkpointer; "what do I know about this user?" → Store. User preferences go in the Store, because thread state dies with the thread. You typically compile with both.

StateHow does thread_id work, and what breaks without it?

thread_id (passed in config["configurable"]) is the key the checkpointer stores state under — it partitions conversations so User A's history never leaks into User B's, and so a returning user resumes their own thread. Without it the checkpointer has nothing to key on: you effectively get no useful memory, every invocation looks like a fresh conversation, and HITL/time travel can't target a run. It fails silently, which is what makes it a good interview question.

StateHow would you manage a conversation that exceeds the context window?

Three strategies with different trade-offs. Trimming (trim_messages) keeps the last N tokens — cheapest, but loses old context wholesale; mind start_on/end_on so you don't orphan a tool call. Deletion (RemoveMessage with the add_messages reducer) surgically drops specific messages — targeted, needs real message ids. Summarization folds old turns into a running summary — best meaning-per-token, but costs an extra LLM call and can drift. In production I'd summarize older history and keep recent turns verbatim, plus push durable facts into the Store so they survive independently of the transcript.

HITLinterrupt() vs interrupt_before — which and why?

interrupt() is dynamic: called inside a node, it can pause conditionally (only for high-value orders, say), and it passes a payload to the human describing what's pending. interrupt_before=["node"] is static, decided at compile time, and always pauses before that node. Prefer interrupt() for production approval gates — conditional pausing and a structured payload — and use interrupt_before for debugging or blanket gates. Both require a checkpointer, and you resume both with Command(resume=…).

DebuggingWhat is time travel and when have you used it?

Because every superstep is checkpointed, you can list history with get_state_history(), replay from any past checkpoint_id, or fork — patch state at a past checkpoint and run a different branch forward. The main use is debugging non-deterministic agents: rather than re-running an expensive 10-step trajectory hoping to reproduce a bug, you rewind to the step before it went wrong, change one value, and replay. It's also how you A/B two prompts from an identical mid-run state.

Level 5 · Tools & Agent Capabilities

Giving the agent hands

An agent without tools is a chatbot. Tool design is most of the quality — the docstring is literally the prompt that drives selection — and the modern API (create_agent) hides the ReAct loop you should still be able to hand-write.

3.1 Defining tools — the docstring is the prompt

The model never sees your implementation. It sees the tool's name, description (the docstring), and argument schema — and picks from those alone. Vague docstrings are the #1 cause of wrong tool selection.

  • Prefer few, well-scoped tools over many overlapping ones — overlap is what makes the model dither.
  • Say what the tool is not for; negative guidance disambiguates better than more adjectives.
  • Return strings or JSON-serialisable objects, and keep outputs small — every tool result re-enters the context window.

3.2 Wiring the ReAct loop by hand

Build this once yourself. It's six lines, it demystifies every prebuilt agent, and interviewers ask you to draw it.

3.3 create_agent — the current API

The same loop, prebuilt. Note the deprecation: create_react_agent from langgraph.prebuilt still runs but emits LangGraphDeprecatedSinceV10. The current entry point lives in langchain.agents.

create_agent's headline addition is a middleware system: composable hooks that run before/after the model call and before/after tool execution — for logging, guardrails, retries, and summarization — without rewriting the graph.

3.4 Advanced tool topics

Five things that separate a demo agent from one that survives real traffic.

  • Parallel tool calls — a model can emit several calls at once; ToolNode executes them concurrently. Big latency win for independent lookups.
  • Tool errors — never let an exception crash the graph. Return a ToolMessage describing the failure so the model can read it and retry or change approach.
  • InjectedState / InjectedStore — pass graph state or the Store into a tool without exposing it to the LLM (it won't appear in the tool schema the model sees).
  • Tool-call review — gate sensitive tools behind HITL (Part 2 §2.11): interrupt before execution and let a human approve the arguments.
  • Structured output vs tool calling — use structured output when you want data in a shape; use tools when you want an action performed.

3.5 Model Context Protocol (MCP)

An open standard (from Anthropic) for connecting models to tools and data sources — replacing the bespoke wrapper you'd otherwise write per integration.

Likely interview questions
ToolsHow does the model decide which tool to call, and how do you improve that?

It sees only the tool name, description/docstring, and argument schema — never your implementation — and selects via the provider's function-calling mechanism. Improve it by: writing precise docstrings that state both what the tool is for and what it isn't; using typed Pydantic schemas with per-field descriptions; keeping the toolset small and non-overlapping (overlap causes dithering); giving tools distinct, unambiguous names; and few-shot examples in the system prompt for tricky cases. If selection is still wrong, that's a prompt-engineering problem in the docstring, not a model problem.

ToolsA tool throws an exception. What should happen?

It should become a ToolMessage the model can read — not an unhandled crash. Catch the exception inside the tool (or configure ToolNode's error handling) and return a clear, actionable message: what failed, and whether retrying is sensible. The model then adapts — retries with different args, tries another tool, or reports the failure to the user. Crashing the graph loses the whole run; a readable error keeps the agent's recovery loop intact. Guard against infinite retry with an attempt counter.

ModernWhat is MCP and why does it matter?

Model Context Protocol — an open, provider-neutral standard (originating at Anthropic) for exposing tools and data sources to LLM applications over a client–server interface. Your agent is the client; services like a filesystem, Postgres, Slack, or Drive run MCP servers. It matters because it kills the N×M integration problem: instead of writing a bespoke wrapper per tool per framework, any MCP-speaking client can use any MCP server. Transports are stdio (local) and HTTP/SSE (remote); langchain-mcp-adapters converts MCP tools into LangChain tools, and LangGraph can also expose an agent as an MCP server.

Level 6 · RAG and Advanced RAG

The RAG ladder, built as graphs

Retrieval is the most common agent capability, and its variants are a graded interview ladder: naive → agentic → corrective → self-reflective. Each rung adds one node to the graph — which is exactly how to explain them.

Deep on retrieval itself? The RAG subject covers chunking, hybrid search, rerankers, and evaluation in full. Here we focus on how each variant is wired in LangGraph.

3.6 Baseline RAG

Six stages: Load → Split → Embed → Store → Retrieve → Generate. The first four are offline; the last two run per query.

  • Loaders: PyPDFLoader, WebBaseLoader, DirectoryLoader
  • Splitting: RecursiveCharacterTextSplitter — chunk size and overlap both matter
  • Vector stores: FAISS (local), Chroma, Pinecone, pgvector
  • Retriever config: k, MMR, metadata filtering, score thresholds

3.7 RAG as a step vs RAG as a tool = Agentic RAG

One design decision separates naive RAG from agentic RAG: is retrieval a fixed pipeline stage, or a tool the model chooses to call?

3.8 Corrective RAG (CRAG)

Adds one node — a grader after retrieval — that asks "do these documents actually answer the question?" and takes corrective action when they don't.

3.9 Self-RAG

Where CRAG grades the retrieval, Self-RAG grades the generation — twice: is it grounded in the context, and does it actually answer the question?

3.10 The full RAG ladder

Interviewers ask you to "explain the ladder." Here it is as one table — each rung adds a specific node and solves a specific failure.

RungWhat it addsFailure it fixes
Naive RAGRetrieve → generate, always— (baseline; ungrounded LLM)
Agentic RAGRetriever wrapped as a toolRetrieving when pointless; can't pick a source; can't re-retrieve
CRAGGrader after retrieval + fallbackPlausible-but-wrong chunks used anyway
Self-RAGGraders after generation (grounded? relevant?)Hallucinated or off-target answers
Adaptive RAGRouter on query complexitySpending multi-hop effort on trivial queries

Also worth naming: HyDE (embed a hypothetical answer), parent-document / small-to-big, reranking with a cross-encoder, hybrid search (BM25 + dense), GraphRAG, and contextual retrieval — all covered in depth in the RAG subject.

3.11 Interview focus

Likely interview questions
RAG ⭐Naive RAG vs Agentic RAG vs CRAG vs Self-RAG — explain the ladder.

Naive: every query goes retrieve → generate. Simple, but it retrieves for "hi", can't choose a source, and generates from bad chunks. Agentic: the retriever becomes a tool, so the model decides whether to retrieve, which source (docs / SQL / web), and can retrieve repeatedly — it's the ReAct loop. CRAG: adds a grader after retrieval that scores document relevance and triggers a correction (query rewrite or web search) when they're insufficient. Self-RAG: adds reflection after generation — one grader for groundedness (are claims supported by context?) and one for answer relevance — regenerating or re-retrieving on failure. Each rung adds a node and costs latency, so climb only as far as your failure modes require, and bound every retry loop.

DebuggingYour RAG system returns confident wrong answers. Debug it.

Localise before fixing. First, log and read the retrieved chunks for the failing queries: if the right chunk isn't there, it's a retrieval bug (chunking too big/small, embedding truncation, missing exact-term matching → add hybrid search); if it is there, the bug moved to generation. For generation, check the prompt actually instructs "answer only from context" and that temperature is low. Then add the structural fixes: a CRAG-style relevance grader so bad retrievals don't reach the generator, a groundedness check (Self-RAG) so unsupported claims are caught, and an abstention path so the system says "I don't know" instead of inventing. Finally, measure — faithfulness and context-relevance metrics on a fixed eval set — so you know the fix worked.

DesignWhy wrap a retriever as a tool instead of making it a graph step?

Because retrieval isn't always the right move. As a fixed step, every query pays retrieval latency and cost — including greetings and pure-reasoning questions — and the pipeline can only ever consult one source, once. As a tool, the model decides if to retrieve, which source to use (PDF retriever vs SQL vs web), and can retrieve again after reading the first results (multi-hop). The cost is non-determinism: the model might skip retrieval when it shouldn't, so you evaluate tool-choice accuracy as part of trajectory eval (Part 4).

Level 7 · Multi-Agent Architectures

When one agent isn't enough

Multi-agent isn't automatically better — it's a way to manage context and specialisation. Know the five topologies, when each fits, and the two mechanisms that implement them: subgraphs and handoffs.

4.1 The five topologies

Pick by how much structure the flow has. Supervisor is the most common production choice; network is the most expensive.

PatternShapeUse when
NetworkEvery agent can call every agentExploratory, flow genuinely unclear
Supervisor ★Central router delegates to specialistsMost common production choice
Supervisor-as-toolsSub-agents exposed to the supervisor as toolsClean and simple — reuses tool-calling
HierarchicalSupervisors of supervisorsLarge teams of agents

4.2 Subgraphs

Compile a graph and use it as a node in a parent graph. This is how you reuse an approval loop or a research module across projects — and how big agent systems stay comprehensible.

Checkpointing propagates from parent to subgraph automatically — you don't compile the child with its own checkpointer. To stream from inside a subgraph, pass subgraphs=True to the stream call (Part 5 §5.5).

4.3 Handoffs & context isolation

A handoff is one agent transferring control — and some amount of context — to another. Deciding how much context transfers is the real design question.

Interview tip · context isolation is why you go multi-agent

The strongest justification for multi-agent isn't "specialisation" — it's context management. A single agent doing research + writing + review accumulates every tool result in one exploding context window. Giving each sub-agent its own scratchpad, and passing only a compressed summary on handoff, keeps each context small and focused. Say that and you're answering at a systems level, not a buzzword level.

4.4 The orchestrator–worker capstone shape

This one diagram combines almost everything in Parts 1–4: dynamic fan-out, a reducer, a critique loop, and a human gate. It's the canonical "build me a report writer" answer.

Likely interview questions
DesignWhen would you go multi-agent instead of one agent with many tools?

Primarily for context isolation and specialisation. One agent with 20 tools has a bloated tool schema (worse selection) and one context window accumulating every observation. Splitting into sub-agents gives each a small, focused toolset and its own scratchpad, with only a compressed summary crossing the handoff. Also: different sub-agents can use different models (cheap for classification, strong for synthesis) and be developed/tested independently. The cost is coordination overhead, more tokens on handoffs, and harder debugging — so don't reach for it until a single agent is actually straining.

MechanicsHow do subgraphs work, and does checkpointing carry over?

You compile a graph and add it as a node in a parent. If the schemas match, add the compiled object directly; if not, wrap it in a function that translates state in and out. Checkpointing propagates automatically from parent to subgraph — you don't give the child its own checkpointer. Subgraphs are how you reuse modules (an approval loop, a research pipeline) and how you keep large systems readable; for streaming from inside one, pass subgraphs=True.

Level 8 · Observability & Evaluation (LangSmith)

The round that fails the most candidates

Interviewers report this is where most people come apart. Everyone can build an agent; far fewer can say how they'd know it works, catch a regression before it ships, or evaluate a trajectory rather than a final answer. Do not skip this level.

4.5 Tracing setup

Tracing is automatic for LangChain/LangGraph — three env vars and every run is captured. Arbitrary functions need one decorator.

4.6 Runs, traces & spans

A run is one unit of work; a trace is the whole tree for one request. For LangGraph specifically, the trace shows each superstep — which is what makes it so good at catching state bugs.

4.7 Datasets & evaluators

A dataset is curated inputs (plus reference outputs) you test against. The highest-value ones are built from production traces you flagged as interesting, not invented in a vacuum.

  • Heuristic / code-based — exact match, JSON validity, regex. Cheap and deterministic.
  • LLM-as-judge — correctness, groundedness, helpfulness (mind the biases — see the RAG subject §4.6).
  • Pairwise — A/B between two versions.
  • Human annotation — via annotation queues, for the cases that matter most.

Two modes worth naming: online evaluation (evaluators running against live production traffic) and regression testing (comparing experiments across prompt or model changes — the CI gate).

4.8 Agent-specific evaluation ⭐

The senior-level differentiator. Final-answer accuracy is not enough for agents — you must evaluate the trajectory: the sequence of steps taken to get there.

Golden trajectories are reference paths a correct run should follow. Match them with varying strictness: exact, in-order (the right steps, extra ones allowed), any-order, or superset. And know the common agent failure taxonomy: wrong tool, malformed args, infinite loop, premature stop, context overflow.

4.9 Interview focus & adjacent tooling

Know the ecosystem by name: LangSmith Prompt Hub (versioned prompts decoupled from code), LangGraph Studio (visual debugger — step through and edit state), and the alternatives: Langfuse, Arize Phoenix, W&B Weave, and the OpenTelemetry GenAI conventions.

The evaluation round
Eval ⭐How do you evaluate an agent?

On two axes. Outcome: is the final answer correct/grounded/helpful — via heuristic checks, LLM-as-judge, or human annotation on a curated dataset. Trajectory: did it get there sensibly — right tools, right arguments, right order, no loops, no premature stop — scored against golden trajectories with a chosen strictness (exact / in-order / any-order / superset). Treat cost and step count as first-class metrics. Build datasets from real production traces you flagged, run evaluators offline as a CI regression gate and online against live traffic, and track a failure taxonomy (wrong tool, malformed args, infinite loop, early stop, context overflow) so improvements are targeted.

Eval ⭐Why isn't final-answer accuracy sufficient? What is a golden trajectory?

Because two runs can produce the same correct answer via wildly different paths — one in 3 efficient steps, one after 40 flailing tool calls costing 14× more and 10× the latency. The second is unshippable, and outcome-only evaluation scores them identically. It also hides why a failure happened. A golden trajectory is a reference path — the tool sequence a correct run should follow — that you compare actual runs against, so you can score step-level tool choice and argument correctness, not just the destination.

EvalHow do you catch a regression before it ships?

Make evaluation a CI gate. Keep a versioned LangSmith dataset (seeded from production traces, including known-hard and previously-broken cases), run the evaluator suite on every prompt/model/graph change, and compare the experiment against the previous baseline — failing the build if key metrics (correctness, groundedness, trajectory match, cost, p95 latency) regress beyond a threshold. Pair that with pairwise comparison for subjective quality, and shadow/canary deployment before full rollout. Pin the judge model version so scores stay comparable across runs.

Level 9 · Production Engineering

Surviving contact with production

Durability, idempotency, retries, caching, streaming, deployment, cost, security, testing. This level contains the single strongest senior answer in the whole subject — the one about side effects (§5.2).

5.1 Durability & failure recovery

Checkpointing isn't free — every write costs latency. Durability modes let you trade write frequency against performance.

ModePersistsTrade-off
"exit"Only at the end of the runFastest · least safe — a crash loses everything
"async"In the backgroundBalanced — small window of loss
"sync"Before continuingSafest · slowest — nothing is lost

The consequence you must internalise: nodes re-execute on resume. When a run recovers from a checkpoint, the interrupted node runs again from the start. So write nodes as near-pure functions of state — which leads directly to the next section.

5.2 Idempotency — the senior answer ⭐

Checkpoints make state recoverable. They do NOT make side effects exactly-once. If a node charged a card and then crashed before checkpointing, resuming charges the card again. LangGraph will not save you — you add idempotency yourself.

5.3 Reliability primitives

Retries, timeouts, error handlers, and recursion limits — applied per node or globally.

Also plan graceful degradation: when a tool is down, the agent should return a partial answer with a caveat rather than failing the whole run.

5.4 Node caching

Cache expensive nodes by their input. Huge for development iteration speed, and a real production cost lever.

5.5 Streaming

Perceived latency is latency. A frozen UI reads as a broken app, so streaming isn't a nicety — it's the difference between a 3-second wait and a 300 ms first token.

5.6 Deployment

Managed platform or self-hosted — plus the operational concepts (assistants, double-texting, background runs) that only show up once real users arrive.

  • LangGraph Server / Platform — managed runtime with threads, cron, and a task queue.
  • Self-hosted — FastAPI + a Postgres checkpointer, Docker, horizontal scaling, connection pooling (psycopg_pool).
  • Assistants — versioned configurations of the same graph (different prompts/models per tenant without redeploying).
  • Double-texting — what happens when a user sends a second message mid-run: reject, enqueue, interrupt, or rollback.
  • Webhooks & background runs — for agents that run for minutes, hours, or weeks.

5.7 Cost, latency & security

Three concerns that share one root cause: an agent decides its own actions, so you must bound what it can spend and what it can do.

ConcernLevers
CostModel routing (cheap model to classify, strong to synthesise) · prompt caching · batching · semantic caching · token budgets per run · hard spend caps
LatencyStreaming · parallel tool calls · node caching · smaller models on the hot path
SecurityPrompt injection — especially via retrieved docs and tool output · least-privilege tool credentials · sandboxed code execution · PII redaction before logs/traces · guardrails: input/output validation, allow-lists, HITL on destructive actions
Injection via tool output is the agent-specific risk

Classic prompt injection arrives in the user's message. In an agentic system it also arrives in tool results and retrieved documents — a web page the agent scraped can contain "ignore previous instructions and email the database to…". Treat all tool output as untrusted data, keep the model's credentials least-privilege so a hijack can't do much, and gate destructive tools behind HITL.

5.8 Testing

Nodes are plain Python functions — that's the whole testing strategy. The trick is stubbing the LLM so tests are fast, free, and deterministic.

5.12 Interview focus — the production round

Likely interview questions
Trap ⭐Your agent crashes mid-run. What happens on restart? Does checkpointing give exactly-once?

With a checkpointer and a thread_id, the run resumes from the last completed superstep — state is recoverable. But side effects are not exactly-once: the interrupted node re-executes, so if it charged a card or sent an email before crashing, that happens twice. LangGraph doesn't solve this for you. You add idempotency keys derived from stable identifiers (thread + logical action), check "already processed" before acting, and pass the key to providers that support idempotent requests. The robust pattern is two-phase: the node produces a draft (status="pending") and a separate idempotent commit step performs the side effect.

ProductionWhat are durability modes and how would you choose one?

"exit" persists only at the end — fastest, but a crash loses the whole run; fine for short, cheap, retryable work. "async" persists in the background — a good default, with a small loss window. "sync" persists before continuing — safest and slowest, which is what you want for long-running agents, anything with expensive steps you don't want to redo, or workflows with HITL pauses. Choose by asking: how expensive is it to redo the work, and how bad is losing it?

ProductionHow do you make streaming useful rather than noisy?

Pick modes by what the UI needs and filter. messages streams LLM tokens (what the user should see), updates streams per-node deltas (good for a progress indicator), values streams full state (heavy), plus custom for your own in-tool events and debug for detail. Combine ["updates", "messages"] for progress + tokens, and pass subgraphs=True to see inside subgraphs. The classic bug: piping raw tool-call JSON into the UI, which looks broken — filter to AIMessage content.

SecurityHow do you secure an agent that can call tools?

Assume the model can be hijacked and limit the blast radius. Treat all tool output and retrieved documents as untrusted input (that's where agentic prompt injection arrives), give tools least-privilege credentials so a compromised run can't do much, sandbox any code execution, redact PII before it reaches logs and traces, validate inputs/outputs with allow-lists, and put HITL approval gates on destructive or irreversible actions. Combine with hard spend caps and recursion limits so a runaway loop is bounded financially as well as logically.

TestingHow do you test a LangGraph agent?

Three layers. Unit: nodes are plain functions — call them with a state dict and assert on the partial update, no framework needed. Integration: run full graph paths with a stubbed LLM (a fake chat model returning scripted messages/tool calls) so tests are deterministic, fast, and free — this is the key trick. Regression: LangSmith datasets with outcome and trajectory evaluators, run in CI to gate prompt/model changes. Add explicit tests for the failure paths too: tool errors, interrupts/resume, and recursion limits.

Interview Q&A Bank

Answer out loud, then compare

Written answers aren't enough — 2026 hiring reports are explicit that candidates fail on explaining trajectory evaluation out loud, designing tool schemas live, and defending framework choices under pushback. Cover the answer, respond aloud, then expand and compare.

6.1 Conceptual

Conceptual · 6 questions
CoreWhat distinguishes an agent from a workflow? When would you deliberately choose a workflow?

Who controls the flow. In a workflow the developer fixes the steps; the LLM fills in content. In an agent the LLM decides what to do next — which tool, whether to loop, when to stop. Choose a workflow deliberately whenever the path is enumerable: it's cheaper, faster, deterministic, testable, and debuggable. Agents buy adaptability to unpredictable paths at the cost of latency, tokens, and non-determinism. (§1.5)

CoreExplain ReAct. Where does it break down?

Interleaved Thought → Action → Observation until the model can answer — a two-node LangGraph cycle (agent ⇄ tools). It breaks on long horizons: the agent wanders or repeats calls, context grows with every observation until it overflows, and errors compound step to step. Mitigate with iteration caps, a planner (plan-and-execute) or critic (reflection), observation compression, and trajectory evaluation. (§1.4, §3.2)

CoreWhy is LangGraph a graph rather than a chain?

Because agentic control flow needs cycles, branches, and parallelism — a chain is a straight line. Agents loop (retry, refine, re-retrieve), branch (route by classification), and fan out (research N topics at once). A graph expresses all three natively, plus it gives explicit state with defined merge semantics, and a natural checkpoint boundary (the superstep) for persistence, resume, and HITL. (§1.7)

CoreLangChain vs LangGraph in 2026?

Layers, not rivals. LangGraph is the runtime — graph engine, state, checkpointing, streaming, durability. LangChain is the batteries-included layer on top — model/tool abstractions and create_agent, which runs on the LangGraph runtime. Use the prebuilt for standard ReAct agents; drop to a hand-built StateGraph for custom control flow, multi-agent topologies, or bespoke state. (§1.6)

CoreWalk me through an agentic system you built end to end.

Structure it: problem & why agentic (the path couldn't be enumerated) → state design (what keys, which reducers) → graph shape (nodes, routing, loops, and their bounds) → tools (schemas and why those) → memory (checkpointer for threads, Store for user facts) → HITL (what's gated and why) → observability & eval (traces, dataset, trajectory metrics, CI gate) → production (durability, idempotency, cost controls) → results and what you'd change. Naming a concrete failure you hit and fixed is what makes it credible.

CoreWhen is an agent the wrong solution?

When steps are known (write a workflow), when latency is tight (each loop is an LLM round-trip), when determinism is required (audit/compliance paths), when the task is a single classification or transformation, or when a cheaper tool fits — a SQL query beats an agent for "total revenue by region." Also when you can't evaluate it: shipping an agent you can't measure is how teams end up with expensive, unfixable systems. (§1.5)

6.2 LangGraph mechanics

Mechanics · 7 questions
Core ⭐What is a reducer and why does it exist?

A function (current, update) → merged attached to a state key via Annotated[T, reducer], telling LangGraph how to combine a node's write with the existing value instead of overwriting. It exists because nodes return partial updates and multiple nodes in one superstep may write the same key — the framework needs explicit merge semantics rather than guessing. (§1.9)

Trap ⭐Two parallel nodes write the same key with no reducer — what happens?

InvalidUpdateError. Not "it merges," not "last write wins." LangGraph refuses to guess. Fix with a reducer on that key, or write to different keys. (§1.9)

MechanicsSend vs conditional edges?

A conditional edge picks among a fixed, build-time-known set of next nodes. Send spawns N parallel instances where N is only known at runtime, each with its own payload rather than the shared state — the map-reduce primitive. Results merge back via a reducer. (§1.12)

MechanicsWhat does Command let you do that a conditional edge can't?

Return a state update and a routing hop together from inside the node. Plus two things edges can't do: navigate into a parent graph (graph=Command.PARENT — the multi-agent handoff mechanism) and resume a paused graph via Command(resume=value). (§1.11)

MechanicsExplain supersteps.

Execution rounds (the Pregel model). Each superstep runs all currently-scheduled nodes — possibly in parallel — against the state as it stood at the round's start; their partial updates are merged (applying reducers) at the round's end, then the next round is scheduled. That's why parallel siblings can't see each other's writes, why reducers apply at the boundary, and why checkpoints happen once per superstep. (§1.7)

MechanicsHow do you prevent an infinite loop in a cyclic graph?

Two guards. Semantic: an iteration counter in state, incremented in the loop, with the router exiting at a max (and on success). Framework: recursion_limit raising GraphRecursionError — a safety net, not a design. Return the best-so-far result on exhaustion rather than failing hard. (§2.4)

MechanicsWhat is a deferred node and what problem does it solve?

defer=True makes a node wait until all upstream paths reach it. It solves parallel branches of unequal length — without it an aggregator fires when the first (short) branch arrives, on partial data. Ideal for map-reduce fan-in, consensus voting, and multi-agent collaboration. (§2.5)

6.3 State & memory

State & memory · 5 questions
Trap ⭐Checkpointer vs Store?

Checkpointer = within-thread memory, keyed by thread_id, snapshotting state every superstep; enables resume, time travel, HITL. Store = cross-thread memory, keyed by namespace (usually user_id), optionally vector-indexed for semantic search. "What happened in this chat?" → checkpointer. "What do I know about this user?" → Store. User preferences go in the Store — thread state dies with the thread. Compile with both. (§2.8)

StateHow does thread_id work, and what breaks without it?

It's the key the checkpointer stores state under, passed in config["configurable"]. It partitions conversations so users don't see each other's history and returning users resume their own thread. Without it you get no useful memory, every call looks fresh, and HITL/time travel have nothing to target — and it fails silently. (§2.6)

StateManaging a conversation that exceeds the context window — compare three strategies.

Trimming (trim_messages): high token efficiency, high context loss, low complexity — watch start_on/end_on so you don't orphan a tool call. Deletion (RemoveMessage): targeted, moderate efficiency, needs real message ids. Summarization: high efficiency and low context loss, but costs an LLM call and can drift. Production answer: summarize old turns, keep recent ones verbatim, and push durable facts to the Store so they survive independently. (§2.10)

DesignDesign a long-term memory system for a personal assistant.

Four stages. Extraction: an LLM pulls durable facts from conversational noise (background or hot-path). Storage: write to a Store namespaced by user_id, vector-indexed, typed as semantic (facts) / episodic (past events) / procedural (learned instructions). Retrieval: semantic search at session start or per turn. Injection: splice retrieved facts into the system prompt. Add: deduplication and conflict resolution when facts change, TTLs for stale ones, and user-visible controls to view/delete memories. Trade-off to name: hot-path writes are immediate but add latency; background writes are async but eventually consistent. (§2.9)

DebuggingWhat is time travel and when have you used it?

Every superstep is a checkpoint, so you can list history, replay from a past checkpoint_id, or fork — patch state at a past checkpoint and run a different branch. Main use is debugging non-deterministic agents: instead of re-running an expensive trajectory hoping to reproduce a bug, rewind to just before it went wrong, change one value, and replay. Also useful for A/B-ing two prompts from an identical mid-run state. (§2.7)

6.4 HITL & production

HITL & production · 5 questions
HITLHow do you implement an approval gate before a destructive action?

Compile with a checkpointer, then call interrupt({...}) inside a gate node before the destructive step, passing a payload describing the pending action. The graph pauses and durably checkpoints; you read pending interrupts via graph.get_state(config).tasks[0].interrupts, show them to a human, and resume with graph.invoke(Command(resume="yes"), config). Make the gate conditional (only high-value/irreversible actions), and pair it with idempotency so the resumed run can't double-execute. (§2.11, §5.2)

HITLinterrupt() vs interrupt_before?

interrupt() is dynamic — inside a node, can pause conditionally, and passes a structured payload to the human. interrupt_before=["node"] is static, set at compile time, and always pauses. Prefer interrupt() in production; use interrupt_before for debugging or blanket gates. Both need a checkpointer; both resume with Command(resume=…). (§2.11)

Trap ⭐Your agent crashes mid-run. What happens on restart?

It resumes from the last completed superstep — state is recoverable. But the interrupted node re-executes, so any side effect it already performed happens again. Checkpointing gives you recoverable state, not exactly-once effects. (§5.1–5.2)

Trap ⭐How do you ensure a resumed run doesn't send the same email twice?

Idempotency keys. Derive a stable key from the thread + logical action (e.g. thread-42:send:order-9), check "already processed" before acting, and pass the key to providers that support idempotent requests. Better still, two-phase it: the node produces a draft (status="pending") and a separate, idempotent commit step performs the send. Write nodes as near-pure functions of state so replay is safe by construction. (§5.2)

ProductionWhat are durability modes and how would you choose one?

"exit" (persist at the end — fastest, least safe), "async" (background — balanced default), "sync" (before continuing — safest, slowest). Choose by how expensive the work is to redo and how costly it is to lose: short cheap runs can use exit; long agents with expensive steps or HITL pauses want sync. (§5.1)

6.5 Tools & RAG

Tools & RAG · 5 questions
ToolsHow does the model decide which tool to call? How do you improve that?

From the tool name, docstring, and argument schema only. Improve by writing precise docstrings stating what the tool is and isn't for, typed Pydantic schemas with per-field descriptions, few non-overlapping tools with distinct names, and few-shot examples for ambiguous cases. Wrong selection is a docstring problem, not a model problem. (§3.1)

ToolsA tool throws an exception. What should happen?

It becomes a ToolMessage the model can read — never an unhandled crash. Return a clear, actionable failure message so the agent can retry with different args, try another tool, or report honestly. Guard against infinite retry with an attempt counter. (§3.4)

ModernWhat is MCP and why does it matter?

Model Context Protocol — an open client–server standard for exposing tools and data to LLM apps. Your agent is the client; filesystem/Postgres/Slack/Drive run servers. It kills the N×M integration problem: any MCP client can use any MCP server, instead of a bespoke wrapper per tool per framework. Transports: stdio (local), HTTP/SSE (remote). langchain-mcp-adapters converts them to LangChain tools; LangGraph can also expose an agent as an MCP server. (§3.5)

RAG ⭐Naive vs Agentic vs CRAG vs Self-RAG — explain the ladder.

Naive: always retrieve → generate. Agentic: retriever as a tool — the model decides if/which/how many times, and can route between sources. CRAG: a grader after retrieval scores document relevance and triggers correction (rewrite or web search). Self-RAG: graders after generation — groundedness and answer relevance — regenerating or re-retrieving on failure. Each rung adds a node and latency; climb only as far as your failure modes require, and bound the loops. (§3.10)

DebuggingYour RAG system returns confident wrong answers. Debug it.

Localise first: log and read the retrieved chunks. Missing right chunk → retrieval bug (chunk size, truncation, need hybrid search for exact terms). Right chunk present but bad answer → generation (prompt not enforcing "only from context", temperature too high). Then add structure: a CRAG relevance grader before generation, a groundedness check after it, and an abstention path so it says "I don't know." Finally measure faithfulness/context-relevance on a fixed set to confirm the fix. (§3.11)

6.6 Evaluation

Evaluation · 4 questions
Eval ⭐How do you evaluate an agent?

Outcome and trajectory. Outcome: correctness/groundedness/helpfulness via heuristics, LLM-judge, or human annotation on a curated dataset. Trajectory: right tools, right args, right order, no loops or premature stops — scored against golden trajectories (exact / in-order / any-order / superset). Treat cost and step count as first-class metrics. Build datasets from flagged production traces; run offline as a CI gate and online against live traffic; track a failure taxonomy. (§4.8)

Eval ⭐What is a golden trajectory? Why isn't final-answer accuracy sufficient?

A golden trajectory is the reference tool sequence a correct run should follow. Final-answer accuracy is insufficient because two runs can produce the same right answer via wildly different paths — 3 efficient steps vs 40 flailing calls at 14× the cost. Outcome-only scoring rates them equally, and hides why failures happen. A correct answer after 40 tool calls is a failure. (§4.8)

EvalHow do you catch a regression before it ships?

Evaluation as a CI gate: a versioned dataset (seeded from production traces plus known-hard and previously-broken cases), the evaluator suite run on every prompt/model/graph change, compared against the prior baseline, failing the build if correctness, groundedness, trajectory match, cost, or p95 latency regress. Then shadow/canary before full rollout. Pin the judge model version so scores stay comparable. (§4.9)

EvalWhat does a LangSmith trace show you for a LangGraph run specifically?

Each superstep as a span, which conditional branches were taken, how many times loops ran, and — the killer feature — how state mutates node by node. That state-diff view is how you spot a dropped or overwritten key (the reducer bugs from §1.9) without adding print statements. Plus the usual per-span latency, token counts, cost, errors, and filterable tags/metadata. (§4.6)

6.7 The trap questions ⭐

Specifically designed to separate people who've read about LangGraph from people who've shipped it. Each has a naive answer that sounds right — and is wrong.

The traps, expanded
Trap 1"LangGraph vs LangChain — which is better?"

Reject the premise politely: they're layers, not rivals. LangGraph is the runtime (graph engine, state, checkpointing, streaming); LangChain is the batteries-included layer whose create_agent runs on that runtime. You use both — prebuilt for standard cases, hand-built StateGraph when you need control.

Trap 2"What happens with concurrent writes to one state key?"

InvalidUpdateError unless a reducer is defined. It does not silently merge and it is not last-write-wins — LangGraph deliberately refuses to guess merge semantics.

Trap 3"Checkpointer or Store for user preferences?"

Store. The checkpointer is thread-scoped — preferences saved there vanish when the user starts a new conversation. The Store is namespaced by user and survives across all threads.

Trap 4"Checkpointing gives you exactly-once execution, right?"

No. State is recoverable; side effects are not idempotent. A node re-executes on resume, so a charge or email can fire twice. You add idempotency keys yourself, and ideally separate producing a draft from committing the effect.

Trap 5"Is create_react_agent the standard?"

Deprecated in LangGraph v1. It still runs but emits LangGraphDeprecatedSinceV10. The current entry point is from langchain.agents import create_agent, which adds a middleware system. Also deprecated: AgentExecutor, initialize_agent.

Trap 6"How do you eval an agent?"

Not "check the final answer." Trajectory evaluation — golden paths, step-level tool-choice and argument accuracy, trajectory match strictness, and cost/step-count as first-class metrics. A correct answer after 40 tool calls is a failure.

Trap 7"Just use an agent for everything?"

No — agents add latency, cost, and non-determinism. Use a workflow when the path is known. Reach for agency only when the steps genuinely can't be enumerated in advance.

6.8 System design scenarios

Whiteboard these and say the tradeoffs out loud. A reusable structure: clarify → state design → graph shape → tools → memory → HITL → eval → production concerns.

Six scenarios
DesignCustomer support triage agent

Classify intent → RAG the knowledge base → draft a reply → HITL approve → escalate on low confidence. Graph: classifier node with Literal-constrained output routing to specialist paths; retrieval as a tool so trivial intents skip it; a confidence check routing to human escalation. Checkpoints: a Postgres checkpointer keyed by conversation thread_id, plus a Store for customer history across tickets. HITL: interrupt() before sending any customer-facing reply (or only for low-confidence/refund cases). Eval set: historical tickets with known correct resolutions — measure intent-classification accuracy, retrieval relevance, draft quality (LLM-judge + human sample), and escalation precision/recall. Production: idempotent send, PII redaction before traces, cost caps.

DesignResearch assistant

Decompose the question → parallel web search via Send → synthesise with citations → reflect and re-search on gaps. Graph: planner emits one Send per sub-question; workers write into an Annotated[list, operator.add] findings key; a deferred aggregator waits for all; a reflection node checks coverage and can loop back (bounded). Tradeoffs: parallelism cuts wall-clock but multiplies token spend; cap the fan-out width. Cite by carrying source URLs in the findings payloads. Evaluate with trajectory metrics — did it search the right sub-questions? — plus citation-grounding checks.

DesignSQL analytics agent — how do you prevent DROP TABLE?

Defence in depth, not prompt-begging. Database layer: connect as a read-only role — the strongest guarantee, because it holds even if the model is fully hijacked. Query layer: allow only SELECT, reject multi-statement input, enforce row limits and statement timeouts, and dry-run/EXPLAIN before executing. Graph layer: a validation node between generation and execution; HITL approval for anything unusual. Schema handling: retrieve only relevant tables into the prompt rather than dumping the whole schema. Flow: NL → SQL → validate → dry-run → execute → interpret.

DesignCode review agent — tool design is the whole game

Read a diff → run tests → propose fixes → iterate. The quality lives in the tool schemas: get_diff(pr_id), read_file(path, line_range) (bounded output!), run_tests(pattern), post_comment(path, line, body). Keep outputs small — a whole repo won't fit in context, so tools must support targeted reads. Bound the iterate loop, gate post_comment behind HITL initially, and evaluate on a corpus of PRs with known issues (did it find the real bug, and how many irrelevant comments did it leave?).

DesignMulti-tenant chatbot at 10k concurrent users

Checkpointer: Postgres with connection pooling (psycopg_pool) and async variants; namespace thread_id by tenant. Isolation: per-tenant namespaces in the Store, and tenant-scoped filters on any retrieval — never rely on the prompt. Scale: stateless graph workers behind a load balancer (state lives in Postgres), horizontal autoscaling, background runs for long tasks. Cost: model routing (cheap classifier, strong synthesiser), semantic caching, per-tenant token budgets and hard caps. Ops: double-texting strategy, durability "async", and per-tenant observability so one noisy tenant is diagnosable.

DesignLong-running campaign agent (runs for weeks)

Durability: "sync" mode with a Postgres checkpointer — you cannot afford to lose weeks of state. Idempotency is non-negotiable: every external action (email sent, ad spend) needs a key so a resume can't duplicate it. HITL: interrupt() for approval gates that may sit pending for days — the durable pause is exactly the feature. Scheduling: cron/background runs rather than a held-open request; webhooks to resume. Observability: traces spanning a month need aggregation — track per-step cost, cumulative spend against a cap, and alert on stalls. Also plan for version drift: the graph may be redeployed mid-run, so version your assistants.
