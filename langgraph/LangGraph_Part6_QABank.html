6.1 Conceptual

Conceptual · 6 questions
CoreWhat distinguishes an agent from a workflow? When would you deliberately choose a workflow?

Who controls the flow. In a workflow the developer fixes the steps; the LLM fills in content. In an agent the LLM decides what to do next — which tool, whether to loop, when to stop. Choose a workflow deliberately whenever the path is enumerable: it's cheaper, faster, deterministic, testable, and debuggable. Agents buy adaptability to unpredictable paths at the cost of latency, tokens, and non-determinism. (§1.5)

CoreExplain ReAct. Where does it break down?

Interleaved Thought → Action → Observation until the model can answer — a two-node LangGraph cycle (agent ⇄ tools). It breaks on long horizons: the agent wanders or repeats calls, context grows with every observation until it overflows, and errors compound step to step. Mitigate with iteration caps, a planner (plan-and-execute) or critic (reflection), observation compression, and trajectory evaluation. (§1.4, §3.2)

CoreWhy is LangGraph a graph rather than a chain?

Because agentic control flow needs cycles, branches, and parallelism — a chain is a straight line. Agents loop (retry, refine, re-retrieve), branch (route by classification), and fan out (research N topics at once). A graph expresses all three natively, plus it gives explicit state with defined merge semantics, and a natural checkpoint boundary (the superstep) for persistence, resume, and HITL. (§1.7)

CoreLangChain vs LangGraph in 2026?

Layers, not rivals. LangGraph is the runtime — graph engine, state, checkpointing, streaming, durability. LangChain is the batteries-included layer on top — model/tool abstractions and create_agent, which runs on the LangGraph runtime. Use the prebuilt for standard ReAct agents; drop to a hand-built StateGraph for custom control flow, multi-agent topologies, or bespoke state. (§1.6)

CoreWalk me through an agentic system you built end to end.

Structure it: problem & why agentic (the path couldn't be enumerated) → state design (what keys, which reducers) → graph shape (nodes, routing, loops, and their bounds) → tools (schemas and why those) → memory (checkpointer for threads, Store for user facts) → HITL (what's gated and why) → observability & eval (traces, dataset, trajectory metrics, CI gate) → production (durability, idempotency, cost controls) → results and what you'd change. Naming a concrete failure you hit and fixed is what makes it credible.

CoreWhen is an agent the wrong solution?

When steps are known (write a workflow), when latency is tight (each loop is an LLM round-trip), when determinism is required (audit/compliance paths), when the task is a single classification or transformation, or when a cheaper tool fits — a SQL query beats an agent for "total revenue by region." Also when you can't evaluate it: shipping an agent you can't measure is how teams end up with expensive, unfixable systems. (§1.5)

6.2 LangGraph mechanics

Mechanics · 7 questions
Core ⭐What is a reducer and why does it exist?

A function (current, update) → merged attached to a state key via Annotated[T, reducer], telling LangGraph how to combine a node's write with the existing value instead of overwriting. It exists because nodes return partial updates and multiple nodes in one superstep may write the same key — the framework needs explicit merge semantics rather than guessing. (§1.9)

Trap ⭐Two parallel nodes write the same key with no reducer — what happens?

InvalidUpdateError. Not "it merges," not "last write wins." LangGraph refuses to guess. Fix with a reducer on that key, or write to different keys. (§1.9)

MechanicsSend vs conditional edges?

A conditional edge picks among a fixed, build-time-known set of next nodes. Send spawns N parallel instances where N is only known at runtime, each with its own payload rather than the shared state — the map-reduce primitive. Results merge back via a reducer. (§1.12)

MechanicsWhat does Command let you do that a conditional edge can't?

Return a state update and a routing hop together from inside the node. Plus two things edges can't do: navigate into a parent graph (graph=Command.PARENT — the multi-agent handoff mechanism) and resume a paused graph via Command(resume=value). (§1.11)

MechanicsExplain supersteps.

Execution rounds (the Pregel model). Each superstep runs all currently-scheduled nodes — possibly in parallel — against the state as it stood at the round's start; their partial updates are merged (applying reducers) at the round's end, then the next round is scheduled. That's why parallel siblings can't see each other's writes, why reducers apply at the boundary, and why checkpoints happen once per superstep. (§1.7)

MechanicsHow do you prevent an infinite loop in a cyclic graph?

Two guards. Semantic: an iteration counter in state, incremented in the loop, with the router exiting at a max (and on success). Framework: recursion_limit raising GraphRecursionError — a safety net, not a design. Return the best-so-far result on exhaustion rather than failing hard. (§2.4)

MechanicsWhat is a deferred node and what problem does it solve?

defer=True makes a node wait until all upstream paths reach it. It solves parallel branches of unequal length — without it an aggregator fires when the first (short) branch arrives, on partial data. Ideal for map-reduce fan-in, consensus voting, and multi-agent collaboration. (§2.5)

6.3 State & memory

State & memory · 5 questions
Trap ⭐Checkpointer vs Store?

Checkpointer = within-thread memory, keyed by thread_id, snapshotting state every superstep; enables resume, time travel, HITL. Store = cross-thread memory, keyed by namespace (usually user_id), optionally vector-indexed for semantic search. "What happened in this chat?" → checkpointer. "What do I know about this user?" → Store. User preferences go in the Store — thread state dies with the thread. Compile with both. (§2.8)

StateHow does thread_id work, and what breaks without it?

It's the key the checkpointer stores state under, passed in config["configurable"]. It partitions conversations so users don't see each other's history and returning users resume their own thread. Without it you get no useful memory, every call looks fresh, and HITL/time travel have nothing to target — and it fails silently. (§2.6)

StateManaging a conversation that exceeds the context window — compare three strategies.

Trimming (trim_messages): high token efficiency, high context loss, low complexity — watch start_on/end_on so you don't orphan a tool call. Deletion (RemoveMessage): targeted, moderate efficiency, needs real message ids. Summarization: high efficiency and low context loss, but costs an LLM call and can drift. Production answer: summarize old turns, keep recent ones verbatim, and push durable facts to the Store so they survive independently. (§2.10)

DesignDesign a long-term memory system for a personal assistant.

Four stages. Extraction: an LLM pulls durable facts from conversational noise (background or hot-path). Storage: write to a Store namespaced by user_id, vector-indexed, typed as semantic (facts) / episodic (past events) / procedural (learned instructions). Retrieval: semantic search at session start or per turn. Injection: splice retrieved facts into the system prompt. Add: deduplication and conflict resolution when facts change, TTLs for stale ones, and user-visible controls to view/delete memories. Trade-off to name: hot-path writes are immediate but add latency; background writes are async but eventually consistent. (§2.9)

DebuggingWhat is time travel and when have you used it?

Every superstep is a checkpoint, so you can list history, replay from a past checkpoint_id, or fork — patch state at a past checkpoint and run a different branch. Main use is debugging non-deterministic agents: instead of re-running an expensive trajectory hoping to reproduce a bug, rewind to just before it went wrong, change one value, and replay. Also useful for A/B-ing two prompts from an identical mid-run state. (§2.7)

6.4 HITL & production

HITL & production · 5 questions
HITLHow do you implement an approval gate before a destructive action?

Compile with a checkpointer, then call interrupt({...}) inside a gate node before the destructive step, passing a payload describing the pending action. The graph pauses and durably checkpoints; you read pending interrupts via graph.get_state(config).tasks[0].interrupts, show them to a human, and resume with graph.invoke(Command(resume="yes"), config). Make the gate conditional (only high-value/irreversible actions), and pair it with idempotency so the resumed run can't double-execute. (§2.11, §5.2)

HITLinterrupt() vs interrupt_before?

interrupt() is dynamic — inside a node, can pause conditionally, and passes a structured payload to the human. interrupt_before=["node"] is static, set at compile time, and always pauses. Prefer interrupt() in production; use interrupt_before for debugging or blanket gates. Both need a checkpointer; both resume with Command(resume=…). (§2.11)

Trap ⭐Your agent crashes mid-run. What happens on restart?

It resumes from the last completed superstep — state is recoverable. But the interrupted node re-executes, so any side effect it already performed happens again. Checkpointing gives you recoverable state, not exactly-once effects. (§5.1–5.2)

Trap ⭐How do you ensure a resumed run doesn't send the same email twice?

Idempotency keys. Derive a stable key from the thread + logical action (e.g. thread-42:send:order-9), check "already processed" before acting, and pass the key to providers that support idempotent requests. Better still, two-phase it: the node produces a draft (status="pending") and a separate, idempotent commit step performs the send. Write nodes as near-pure functions of state so replay is safe by construction. (§5.2)

Current ⭐What did LangGraph 1.2 add for fault tolerance?

Three things, all per-node. Timeouts: TimeoutPolicy(run_timeout=…, idle_timeout=…) — a hard wall-clock cap per attempt, and an idle cap that resets on progress signals (catches stalled streams); either raises a retriable NodeTimeoutError. Error handlers: error_handler= runs after retries are exhausted with a NodeError, enabling graceful degradation and Saga-style compensation via Command(goto="compensate"). set_node_defaults(): apply retry/timeout/cache/error-handler to every node at once — per-node values still win, defaults apply at compile(), and they are not inherited by subgraphs. (§5.3)

CurrentWhat is DeltaChannel and when would you use it?

A LangGraph 1.2 (beta) channel type that stores incremental deltas instead of the full value on each checkpoint, cutting write overhead for long-running threads with growing state. Use snapshot_frequency to periodically write a full snapshot so replay doesn't fold an unbounded delta chain. Reach for it when checkpoint cost — not model latency — dominates a long thread. (§5.1)

ProductionWhat are durability modes and how would you choose one?

"exit" (persist at the end — fastest, least safe), "async" (background — balanced default), "sync" (before continuing — safest, slowest). Choose by how expensive the work is to redo and how costly it is to lose: short cheap runs can use exit; long agents with expensive steps or HITL pauses want sync. (§5.1)

6.5 Tools & RAG

Tools & RAG · 5 questions
ToolsHow does the model decide which tool to call? How do you improve that?

From the tool name, docstring, and argument schema only. Improve by writing precise docstrings stating what the tool is and isn't for, typed Pydantic schemas with per-field descriptions, few non-overlapping tools with distinct names, and few-shot examples for ambiguous cases. Wrong selection is a docstring problem, not a model problem. (§3.1)

ToolsA tool throws an exception. What should happen?

It becomes a ToolMessage the model can read — never an unhandled crash. Return a clear, actionable failure message so the agent can retry with different args, try another tool, or report honestly. Guard against infinite retry with an attempt counter. (§3.4)

ModernWhat is MCP and why does it matter?

Model Context Protocol — an open client–server standard for exposing tools and data to LLM apps. Your agent is the client; filesystem/Postgres/Slack/Drive run servers. It kills the N×M integration problem: any MCP client can use any MCP server, instead of a bespoke wrapper per tool per framework. Transports: stdio (local), HTTP/SSE (remote). langchain-mcp-adapters converts them to LangChain tools; LangGraph can also expose an agent as an MCP server. (§3.5)

RAG ⭐Naive vs Agentic vs CRAG vs Self-RAG — explain the ladder.

Naive: always retrieve → generate. Agentic: retriever as a tool — the model decides if/which/how many times, and can route between sources. CRAG: a grader after retrieval scores document relevance and triggers correction (rewrite or web search). Self-RAG: graders after generation — groundedness and answer relevance — regenerating or re-retrieving on failure. Each rung adds a node and latency; climb only as far as your failure modes require, and bound the loops. (§3.10)

DebuggingYour RAG system returns confident wrong answers. Debug it.

Localise first: log and read the retrieved chunks. Missing right chunk → retrieval bug (chunk size, truncation, need hybrid search for exact terms). Right chunk present but bad answer → generation (prompt not enforcing "only from context", temperature too high). Then add structure: a CRAG relevance grader before generation, a groundedness check after it, and an abstention path so it says "I don't know." Finally measure faithfulness/context-relevance on a fixed set to confirm the fix. (§3.11)

6.6 Evaluation

Evaluation · 4 questions
Eval ⭐How do you evaluate an agent?

Outcome and trajectory. Outcome: correctness/groundedness/helpfulness via heuristics, LLM-judge, or human annotation on a curated dataset. Trajectory: right tools, right args, right order, no loops or premature stops — scored against golden trajectories (exact / in-order / any-order / superset). Treat cost and step count as first-class metrics. Build datasets from flagged production traces; run offline as a CI gate and online against live traffic; track a failure taxonomy. (§4.8)

Eval ⭐What is a golden trajectory? Why isn't final-answer accuracy sufficient?

A golden trajectory is the reference tool sequence a correct run should follow. Final-answer accuracy is insufficient because two runs can produce the same right answer via wildly different paths — 3 efficient steps vs 40 flailing calls at 14× the cost. Outcome-only scoring rates them equally, and hides why failures happen. A correct answer after 40 tool calls is a failure. (§4.8)

EvalHow do you catch a regression before it ships?

Evaluation as a CI gate: a versioned dataset (seeded from production traces plus known-hard and previously-broken cases), the evaluator suite run on every prompt/model/graph change, compared against the prior baseline, failing the build if correctness, groundedness, trajectory match, cost, or p95 latency regress. Then shadow/canary before full rollout. Pin the judge model version so scores stay comparable. (§4.9)

EvalWhat does a LangSmith trace show you for a LangGraph run specifically?

Each superstep as a span, which conditional branches were taken, how many times loops ran, and — the killer feature — how state mutates node by node. That state-diff view is how you spot a dropped or overwritten key (the reducer bugs from §1.9) without adding print statements. Plus the usual per-span latency, token counts, cost, errors, and filterable tags/metadata. (§4.6)

6.7 The trap questions ⭐

Specifically designed to separate people who've read about LangGraph from people who've shipped it. Each has a naive answer that sounds right — and is wrong.

The traps, expanded
Trap 1"LangGraph vs LangChain — which is better?"

Reject the premise politely: they're layers, not rivals. LangGraph is the runtime (graph engine, state, checkpointing, streaming); LangChain is the batteries-included layer whose create_agent runs on that runtime. You use both — prebuilt for standard cases, hand-built StateGraph when you need control.

Trap 2"What happens with concurrent writes to one state key?"

InvalidUpdateError unless a reducer is defined. It does not silently merge and it is not last-write-wins — LangGraph deliberately refuses to guess merge semantics.

Trap 3"Checkpointer or Store for user preferences?"

Store. The checkpointer is thread-scoped — preferences saved there vanish when the user starts a new conversation. The Store is namespaced by user and survives across all threads.

Trap 4"Checkpointing gives you exactly-once execution, right?"

No. State is recoverable; side effects are not idempotent. A node re-executes on resume, so a charge or email can fire twice. You add idempotency keys yourself, and ideally separate producing a draft from committing the effect.

Trap 5"Is create_react_agent the standard?"

Deprecated in LangGraph v1. It still runs but emits LangGraphDeprecatedSinceV10. The current entry point is from langchain.agents import create_agent, which adds a middleware system. Also deprecated: AgentExecutor, initialize_agent.

Trap 6"How do you eval an agent?"

Not "check the final answer." Trajectory evaluation — golden paths, step-level tool-choice and argument accuracy, trajectory match strictness, and cost/step-count as first-class metrics. A correct answer after 40 tool calls is a failure.

Trap 7"Just use an agent for everything?"

No — agents add latency, cost, and non-determinism. Use a workflow when the path is known. Reach for agency only when the steps genuinely can't be enumerated in advance.

6.8 System design scenarios

Whiteboard these and say the tradeoffs out loud. A reusable structure: clarify → state design → graph shape → tools → memory → HITL → eval → production concerns.

Six scenarios
DesignCustomer support triage agent

Classify intent → RAG the knowledge base → draft a reply → HITL approve → escalate on low confidence. Graph: classifier node with Literal-constrained output routing to specialist paths; retrieval as a tool so trivial intents skip it; a confidence check routing to human escalation. Checkpoints: a Postgres checkpointer keyed by conversation thread_id, plus a Store for customer history across tickets. HITL: interrupt() before sending any customer-facing reply (or only for low-confidence/refund cases). Eval set: historical tickets with known correct resolutions — measure intent-classification accuracy, retrieval relevance, draft quality (LLM-judge + human sample), and escalation precision/recall. Production: idempotent send, PII redaction before traces, cost caps.

DesignResearch assistant

Decompose the question → parallel web search via Send → synthesise with citations → reflect and re-search on gaps. Graph: planner emits one Send per sub-question; workers write into an Annotated[list, operator.add] findings key; a deferred aggregator waits for all; a reflection node checks coverage and can loop back (bounded). Tradeoffs: parallelism cuts wall-clock but multiplies token spend; cap the fan-out width. Cite by carrying source URLs in the findings payloads. Evaluate with trajectory metrics — did it search the right sub-questions? — plus citation-grounding checks.

DesignSQL analytics agent — how do you prevent DROP TABLE?

Defence in depth, not prompt-begging. Database layer: connect as a read-only role — the strongest guarantee, because it holds even if the model is fully hijacked. Query layer: allow only SELECT, reject multi-statement input, enforce row limits and statement timeouts, and dry-run/EXPLAIN before executing. Graph layer: a validation node between generation and execution; HITL approval for anything unusual. Schema handling: retrieve only relevant tables into the prompt rather than dumping the whole schema. Flow: NL → SQL → validate → dry-run → execute → interpret.

DesignCode review agent — tool design is the whole game

Read a diff → run tests → propose fixes → iterate. The quality lives in the tool schemas: get_diff(pr_id), read_file(path, line_range) (bounded output!), run_tests(pattern), post_comment(path, line, body). Keep outputs small — a whole repo won't fit in context, so tools must support targeted reads. Bound the iterate loop, gate post_comment behind HITL initially, and evaluate on a corpus of PRs with known issues (did it find the real bug, and how many irrelevant comments did it leave?).

DesignMulti-tenant chatbot at 10k concurrent users

Checkpointer: Postgres with connection pooling (psycopg_pool) and async variants; namespace thread_id by tenant. Isolation: per-tenant namespaces in the Store, and tenant-scoped filters on any retrieval — never rely on the prompt. Scale: stateless graph workers behind a load balancer (state lives in Postgres), horizontal autoscaling, background runs for long tasks. Cost: model routing (cheap classifier, strong synthesiser), semantic caching, per-tenant token budgets and hard caps. Ops: double-texting strategy, durability "async", and per-tenant observability so one noisy tenant is diagnosable.

DesignLong-running campaign agent (runs for weeks)

Durability: "sync" mode with a Postgres checkpointer — you cannot afford to lose weeks of state. Idempotency is non-negotiable: every external action (email sent, ad spend) needs a key so a resume can't duplicate it. HITL: interrupt() for approval gates that may sit pending for days — the durable pause is exactly the feature. Scheduling: cron/background runs rather than a held-open request; webhooks to resume. Observability: traces spanning a month need aggregation — track per-step cost, cumulative spend against a cap, and alert on stalls. Also plan for version drift: the graph may be redeployed mid-run, so version your assistants.

Last-minute review. Every one of these is a real bug people ship.
