Level 7 · Multi-Agent Architectures

When one agent isn't enough

Multi-agent isn't automatically better — it's a way to manage context and specialisation. Know the five topologies, when each fits, and the two mechanisms that implement them: subgraphs and handoffs.

4.1 The five topologies

Pick by how much structure the flow has. Supervisor is the most common production choice; network is the most expensive.

PatternShapeUse when
NetworkEvery agent can call every agentExploratory, flow genuinely unclear
Supervisor ★Central router delegates to specialistsMost common production choice
Supervisor-as-toolsSub-agents exposed to the supervisor as toolsClean and simple — reuses tool-calling
HierarchicalSupervisors of supervisorsLarge teams of agents
Custom / handoffExplicit Command(goto=…) between peersKnown, bespoke flow

4.2 Subgraphs

Compile a graph and use it as a node in a parent graph. This is how you reuse an approval loop or a research module across projects — and how big agent systems stay comprehensible.

Checkpointing propagates from parent to subgraph automatically — you don't compile the child with its own checkpointer. To stream from inside a subgraph, pass subgraphs=True to the stream call (Part 5 §5.5).

4.3 Handoffs & context isolation

A handoff is one agent transferring control — and some amount of context — to another. Deciding how much context transfers is the real design question.

Interview tip · context isolation is why you go multi-agent

The strongest justification for multi-agent isn't "specialisation" — it's context management. A single agent doing research + writing + review accumulates every tool result in one exploding context window. Giving each sub-agent its own scratchpad, and passing only a compressed summary on handoff, keeps each context small and focused. Say that and you're answering at a systems level, not a buzzword level.

4.4 The orchestrator–worker capstone shape

This one diagram combines almost everything in Parts 1–4: dynamic fan-out, a reducer, a critique loop, and a human gate. It's the canonical "build me a report writer" answer.

Likely interview questions
DesignWhen would you go multi-agent instead of one agent with many tools?

Primarily for context isolation and specialisation. One agent with 20 tools has a bloated tool schema (worse selection) and one context window accumulating every observation. Splitting into sub-agents gives each a small, focused toolset and its own scratchpad, with only a compressed summary crossing the handoff. Also: different sub-agents can use different models (cheap for classification, strong for synthesis) and be developed/tested independently. The cost is coordination overhead, more tokens on handoffs, and harder debugging — so don't reach for it until a single agent is actually straining.

MechanicsHow do subgraphs work, and does checkpointing carry over?

You compile a graph and add it as a node in a parent. If the schemas match, add the compiled object directly; if not, wrap it in a function that translates state in and out. Checkpointing propagates automatically from parent to subgraph — you don't give the child its own checkpointer. Subgraphs are how you reuse modules (an approval loop, a research pipeline) and how you keep large systems readable; for streaming from inside one, pass subgraphs=True.

Level 8 · Observability & Evaluation (LangSmith)

The round that fails the most candidates

Interviewers report this is where most people come apart. Everyone can build an agent; far fewer can say how they'd know it works, catch a regression before it ships, or evaluate a trajectory rather than a final answer. Do not skip this level.

4.5 Tracing setup

Tracing is automatic for LangChain/LangGraph — three env vars and every run is captured. Arbitrary functions need one decorator.

4.6 Runs, traces & spans

A run is one unit of work; a trace is the whole tree for one request. For LangGraph specifically, the trace shows each superstep — which is what makes it so good at catching state bugs.

4.7 Datasets & evaluators

A dataset is curated inputs (plus reference outputs) you test against. The highest-value ones are built from production traces you flagged as interesting, not invented in a vacuum.

  • Heuristic / code-based — exact match, JSON validity, regex. Cheap and deterministic.
  • LLM-as-judge — correctness, groundedness, helpfulness (mind the biases — see the RAG subject §4.6).
  • Pairwise — A/B between two versions.
  • Human annotation — via annotation queues, for the cases that matter most.

Two modes worth naming: online evaluation (evaluators running against live production traffic) and regression testing (comparing experiments across prompt or model changes — the CI gate).

4.8 Agent-specific evaluation ⭐

The senior-level differentiator. Final-answer accuracy is not enough for agents — you must evaluate the trajectory: the sequence of steps taken to get there.

Golden trajectories are reference paths a correct run should follow. Match them with varying strictness: exact, in-order (the right steps, extra ones allowed), any-order, or superset. And know the common agent failure taxonomy: wrong tool, malformed args, infinite loop, premature stop, context overflow.

4.9 Interview focus & adjacent tooling

Know the ecosystem by name: LangSmith Prompt Hub (versioned prompts decoupled from code), LangGraph Studio (visual debugger — step through and edit state), and the alternatives: Langfuse, Arize Phoenix, W&B Weave, and the OpenTelemetry GenAI conventions.

The evaluation round
Eval ⭐How do you evaluate an agent?

On two axes. Outcome: is the final answer correct/grounded/helpful — via heuristic checks, LLM-as-judge, or human annotation on a curated dataset. Trajectory: did it get there sensibly — right tools, right arguments, right order, no loops, no premature stop — scored against golden trajectories with a chosen strictness (exact / in-order / any-order / superset). Treat cost and step count as first-class metrics. Build datasets from real production traces you flagged, run evaluators offline as a CI regression gate and online against live traffic, and track a failure taxonomy (wrong tool, malformed args, infinite loop, early stop, context overflow) so improvements are targeted.

Eval ⭐Why isn't final-answer accuracy sufficient? What is a golden trajectory?

Because two runs can produce the same correct answer via wildly different paths — one in 3 efficient steps, one after 40 flailing tool calls costing 14× more and 10× the latency. The second is unshippable, and outcome-only evaluation scores them identically. It also hides why a failure happened. A golden trajectory is a reference path — the tool sequence a correct run should follow — that you compare actual runs against, so you can score step-level tool choice and argument correctness, not just the destination.

EvalHow do you catch a regression before it ships?

Make evaluation a CI gate. Keep a versioned LangSmith dataset (seeded from production traces, including known-hard and previously-broken cases), run the evaluator suite on every prompt/model/graph change, and compare the experiment against the previous baseline — failing the build if key metrics (correctness, groundedness, trajectory match, cost, p95 latency) regress beyond a threshold. Pair that with pairwise comparison for subjective quality, and shadow/canary deployment before full rollout. Pin the judge model version so scores stay comparable across runs.
