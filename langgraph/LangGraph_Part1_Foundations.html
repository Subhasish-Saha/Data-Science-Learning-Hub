Level 0 + 1 · Foundations

What makes a system agentic

Conceptual ground first — the typing features LangGraph leans on, the capability ladder from traditional AI to agents, what an agent is actually made of, the canonical architectures, and the senior-signal answer: when not to build one.

1.1 Prerequisites & the typing that matters

Skip the Python basics if you're comfortable — but do not skip the typing section. LangGraph encodes its most important behaviour in type annotations, and one annotation causes more bugs than everything else combined.

You need: functions/decorators/closures, async/await and asyncio.gather, generators and yield (streaming depends on them), Pydantic v2 (BaseModel, validation, model_dump()), and env management (venv/uv + python-dotenv). On the LLM side: tokens and context windows, temperature/top-p, the chat roles (system / user / assistant / tool), embeddings and cosine similarity, function/tool calling at the API level, structured output and JSON mode, and why grounding reduces hallucination.

Why Annotated matters

This one distinction drives LangGraph's entire state-merging model:

A plain key is overwritten by whatever a node returns. An Annotated[T, reducer] key is merged by calling reducer(current, update). That's the whole mechanism — and §1.9 shows why getting it wrong raises an error rather than silently doing the wrong thing.

1.2 The AI capability ladder

Interviewers open here almost every time. The ladder positions agentic AI against everything that came before it — and the one-liner at the top of this section is what they're listening for.

Interview tip · the one-liner to memorise

"GenAI is a capability; Agentic AI is a behaviour." The same model powers both — what changes is whether the system is handed a prompt or a goal, and who decides the intermediate steps.

1.3 Anatomy of an agent

Six behavioural characteristics, five architectural components. Being able to name both — and map a system you've built onto them — is the fastest way to sound like you've shipped agents rather than read about them.

The six characteristics

  • Autonomy — acts without step-by-step prompting
  • Goal-orientation — a persistent objective drives all actions
  • Planning — decomposes goals, generates candidate plans, selects one
  • Reasoning — chooses tools, handles errors, evaluates results
  • Adaptability — pivots when a strategy fails
  • Context awareness — uses memory to know where it is

1.4 Canonical agent architectures

Six shapes cover almost every agentic system you'll be asked to design. Know each one's loop, and what it costs.

Read the primary sources for two of these: ReAct (Yao et al.) and Reflexion (Shinn et al.) — they're among the most-cited references in interview loops.

1.5 When not to build an agent

The answer interviewers respect most. Enthusiasm for agents is cheap; judgment about when they're the wrong tool is the senior signal.

Agents add latency (multiple LLM round-trips), cost (3–10× the tokens), and non-determinism (the same input can take a different path). If the task is deterministic and the steps are known in advance, write a workflow — or plain code — not an agent. Reach for agency only when the path genuinely can't be enumerated ahead of time.

1.6 The framework landscape

Be ready to defend a choice with tradeoffs, not name-drop. The question is rarely "which is best" — it's "why did you pick that one for this problem."

The framing that fails · "LangGraph vs LangChain"

They are layers, not rivals. LangGraph is the runtime — the graph engine, state, checkpointing, streaming. LangChain is the batteries-included layer on top: model wrappers, tools, and create_agent, which itself runs on the LangGraph runtime. Answering "LangGraph is better" reveals you've misunderstood the stack. Say instead: "You use both — LangChain for components and the prebuilt agent, and you drop down to a hand-built StateGraph when you need control the prebuilt doesn't give you."

Likely interview questions
ConceptualWhat distinguishes an agent from a workflow?

Who decides the control flow. In a workflow, the developer fixes the sequence of steps up front — the LLM fills in content but never chooses what runs next. In an agent, the LLM decides: which tool to call, whether to loop, when it's done. That autonomy buys adaptability to paths you couldn't enumerate, at the cost of latency, tokens, and non-determinism. You'd deliberately choose a workflow whenever the steps are knowable — it's cheaper, faster, testable, and debuggable.

ConceptualWhat's the difference between LangChain and LangGraph in 2026?

They're layers of one stack, not competitors. LangGraph is the low-level runtime: a graph engine with explicit state, reducers, checkpointing, streaming, and durability. LangChain is the higher-level library — model/tool abstractions and the prebuilt create_agent, which is built on the LangGraph runtime. Use create_agent for the common ReAct-style case and drop to a hand-built StateGraph when you need custom control flow, multi-agent topologies, or bespoke state.

GotchaWhen is an agent the wrong solution?

When the path is deterministic and enumerable. Agents add latency (many LLM round-trips), cost (3–10× tokens), and non-determinism that makes testing and debugging hard. If you can write the steps down, write a workflow or plain code — you get speed, reproducibility, and far easier evaluation. Reserve agency for genuinely open-ended tasks (research, multi-hop investigation, unpredictable tool sequences). A candidate who says "use an agent for everything" is signalling inexperience.

ConceptualExplain ReAct. Where does it break down?

ReAct interleaves Thought → Action → Observation in a loop: the model reasons about what it needs, calls a tool, reads the result, and repeats until it can answer. It's the default single-agent pattern and maps directly onto a two-node LangGraph cycle (agent ⇄ tools). It breaks down on long horizons — it can wander, repeat tool calls, or loop without converging; context grows with every observation until it overflows; and errors compound because each step conditions on the last. Mitigations: bound iterations, add a planner (plan-and-execute) or a critic (reflection), compress observations, and evaluate the trajectory rather than just the final answer.

Level 2 · LangGraph Core Primitives

The foundation everything sits on

Master this completely — every pattern, memory feature, and multi-agent topology in Parts 2–5 is these six primitives recombined: state, nodes, reducers, edges, Command, and Send.

1.7 Your first graph & the mental model

A LangGraph graph is a flowchart where nodes are ordinary Python functions and edges are control flow. The whole framework follows from that plus one rule: nodes return partial state updates.

The mental model — five rules

  • A graph is a flowchart: nodes are Python functions, edges are control flow.
  • Nodes return partial state updates — a dict of only the keys they changed, never the whole state.
  • START and END are sentinels, never executed as nodes.
  • Execution happens in rounds called supersteps (the Pregel model, from Google).
  • Two nodes reachable from the same source in one step run in parallel.

1.8 State schemas

State is the single object every node reads from and writes to. You define its shape with a schema — and you can expose a narrow public interface while keeping internals private.

Three schema options: TypedDict (most common, no runtime validation), Pydantic BaseModel (runtime validation, slower), or a dataclass. Beyond the shape, you can separate what callers send, what they get back, and what only flows between nodes:

1.9 Reducers ⭐

The most-asked LangGraph interview topic, and the source of more bugs than anything else. A reducer tells LangGraph how to merge a node's write into existing state.

A custom reducer is just a function (current, update) -> merged:

Common pitfall · returning the whole state from a parallel node

A node must return only the keys it changed. Returning the entire state object from a node that runs in parallel means it "writes" every key — including ones the sibling branch is also writing — which trips InvalidUpdateError on keys you never intended to touch. Return partial dicts, always.

Likely interview questions
CoreWhat is a reducer and why does it exist?

A reducer is a function (current, update) → merged attached to a state key via Annotated[T, reducer]. It tells LangGraph how to combine a node's write with the existing value instead of overwriting it. It exists because nodes return partial updates and, in a superstep, several nodes may write the same key — LangGraph needs explicit merge semantics rather than guessing. Common ones: operator.add (concatenate), add_messages (append + dedupe by id), or any custom function.

TrapWhat happens when two parallel nodes write the same key without a reducer?

InvalidUpdateError — it does not silently merge and it is not "last write wins." LangGraph deliberately refuses to guess. The naive answers ("it merges" / "last one wins") are exactly what this question is designed to catch. Fix by declaring a reducer on that key, or by having the branches write to different keys.

MechanicsWhat's special about add_messages?

It's the purpose-built reducer for chat history. It appends new messages, dedupes by message id (so re-emitting a message updates rather than duplicates it), and understands RemoveMessage for deleting specific messages from history — which is how you implement targeted context trimming (Part 2, §2.10). Note RemoveMessage needs a real message id to match.

MechanicsExplain supersteps.

LangGraph executes in discrete rounds (the Pregel model). In each superstep, every node scheduled for that round runs — potentially in parallel — reading the state as it stood at the start of the round. Their partial updates are merged into state (applying reducers) at the end of the round, and the next round is scheduled. That's why parallel siblings can't see each other's writes, why the merge is where reducers apply, and why a checkpointer snapshots state once per superstep.

1.10 Edges & conditional routing

Edges are control flow. Static edges always fire; conditional edges call a router function that returns the name of the next node — not data. That distinction trips people up constantly.

The path_map is optional if the router returns node names directly, but it's good practice: it documents the possible destinations and lets the router return semantic labels decoupled from node naming. Typing the router with Literal[...] also lets LangGraph draw the correct edges in the visualisation.

1.11 The Command primitive

A node normally returns a state update, and a separate conditional edge decides where to go next. Command collapses both into one return value — update and routing together.

Command has two other important uses: navigating to a node in a parent graph with graph=Command.PARENT (the mechanism behind multi-agent handoffs, Part 4), and resuming after an interrupt with Command(resume=...) (the HITL pattern, Part 2).

1.12 The Send API — dynamic fan-out

Static edges require you to know the branches at build time. Send is for when you only learn at runtime how many parallel branches you need — the canonical map-reduce in LangGraph.

Likely interview questions
MechanicsSend vs conditional edges — when do you need Send?

A conditional edge picks which of a fixed, build-time-known set of nodes runs next. Send spawns N parallel instances of a node where N is only known at runtime, and — crucially — each instance receives its own payload rather than the shared graph state. Use Send for map-reduce: one worker per search result, per document section, per sub-question. Results merge back via a reducer on the target key.

MechanicsWhat does Command let you do that a conditional edge can't?

Return a state update and a routing decision together from inside the node, instead of splitting them across a node plus a separate router function. It also does two things edges can't: navigate to a node in a parent graph (graph=Command.PARENT) — the basis of multi-agent handoffs — and resume a paused graph after an interrupt() via Command(resume=value).

1.13 Interview focus — the Level-2 checkpoint

You should be able to explain, without notes: nodes vs edges, partial updates, supersteps, why reducers exist, when Send beats a static fan-out, and what Command replaces. Here's the consolidation.
