Part 7 of 17 · Decision Trees

The building block of everything that wins Recursive binary splitting step by step, Gini versus entropy versus information gain (and the honest answer), variance reduction for regression, every complexity hyperparameter and what it actually controls, pre- and post-pruning, the three failure modes worth drawing — and the feature-importance trap.

A single decision tree is the weakest model in this guide and the most important one to understand, because every model in Part 8 is made of these. If you cannot compute an information gain by hand, the ensembles conversation will not go well. Two things here are disproportionately examined. The first is the greedy, locally-optimal nature of the algorithm — it never revisits an earlier split, which is why the tree it builds is not the globally optimal tree. The second is the feature-importance trap: the default feature_importances_ is biased toward high-cardinality and continuous features and is computed on training data, and knowing that is one of the most reliable senior filters in the subject.

7.1 How a tree is built ⭐⭐

Everything in Part 8 is made of these. If you cannot compute an information gain by hand, the ensembles conversation will not go well.

interactive Find the split — Gini, entropy and information gain, live
—parent impurity
—left child
—right child
—information gain

Everything is computed exactly: Gini = 1 − Σpᵢ², Entropy = −Σpᵢ log₂ pᵢ, and gain = H(parent) − Σ(nᵢ/n)·H(childᵢ). Drag the threshold and watch the gain curve; the tree's algorithm simply evaluates every candidate threshold on every feature and takes the maximum. Switch criteria and notice how little the chosen split moves — which is the honest answer to “Gini or entropy?”

The algorithm, precisely

  1. At the current node, for every feature and every candidate threshold, split the rows into left and right.
  2. Compute the weighted child impurity Σ(nᵢ/n)·H(childᵢ) and subtract it from the parent's impurity to get the gain.
  3. Take the split with the highest gain. If no split beats the stopping criteria, make this node a leaf and predict the majority class (or the mean).
  4. Recurse on each child, with only that child's rows.

Two properties fall straight out of that description and are constantly asked about. It is greedy — it takes the best split now and never revisits it, so the tree it produces is not the globally optimal tree (finding that is NP-hard). And it is axis-aligned — every split is a threshold on a single feature, which is why a diagonal boundary costs a staircase of splits (§7.6).

Likely interview questions
Very commonHow does a decision tree choose a split?

Greedily and exhaustively. At each node it scans every feature and every candidate threshold, computes the impurity decrease H(parent) − Σ(nᵢ/n)H(childᵢ), and takes the maximum — then recurses on each child with only that child's rows, stopping when a criterion is hit. Two properties to volunteer: it's greedy, so it never revisits an earlier split and the resulting tree isn't globally optimal (that's NP-hard); and it's axis-aligned, so every boundary is a threshold on one feature at a time.

Deep diveWhat are the "candidate thresholds", and how many are there?

For a continuous feature, the candidates are the midpoints between consecutive distinct sorted values — at most n−1 per feature, so the naive split search is O(n·p) per node after sorting. That cost is why modern implementations use histogram binning: LightGBM, XGBoost's hist method and sklearn's HistGradientBoosting pre-bin each feature into ~256 buckets and only consider bin boundaries, which turns the per-node cost into O(bins·p) and is the single biggest reason those libraries are fast (§8.6).

ConceptualWhy is the tree not globally optimal?

Because the algorithm is greedy: it picks the split with the highest immediate gain and never reconsiders. A split with modest gain now might enable two excellent splits below it, and the greedy algorithm will never find that path — the horizon effect. Finding the globally optimal tree is NP-hard, so exhaustive search isn't an option at any realistic size. In practice it matters less than it sounds, because ensembles make individual trees' myopia irrelevant — which is a large part of why we ensemble rather than trying to build one perfect tree.

7.2 Split criteria ⭐

Gini, entropy, information gain and gain ratio — with the honest answer about which to use.

CriterionFormulaRange (binary)Notes
Gini impurity1 − Σpᵢ²0 to 0.5Probability that two randomly drawn items from the node have different labels. sklearn's default; cheaper, no logarithm
Entropy−Σpᵢ log₂ pᵢ0 to 1Bits needed to encode the class. Penalises impure nodes slightly more aggressively
Information gainH(parent) − Σ(nᵢ/n)H(childᵢ)—The reduction, using either measure. This is what's maximised
Gain ratioIG / SplitInfo—C4.5's correction for the high-cardinality bias — normalises by how many ways the split partitions the data
Log loss / deviance−Σ y log p—Available in sklearn as criterion='log_loss'; equivalent to entropy for classification

Gini is the first-order Taylor approximation of entropy around the uniform distribution, which is why they behave so similarly — a fact worth knowing if someone pushes on the difference.

Gini or entropy? The honest answer

They almost always choose the same splits and produce trees of nearly identical accuracy — empirical studies put the disagreement at around 2% of splits. Gini is cheaper (no logarithm) and is sklearn's default; entropy penalises impure nodes marginally more. Saying “in practice it doesn't matter — I'd spend the tuning budget on max_depth and min_samples_leaf instead” is a better answer than inventing a difference, and it's what an experienced practitioner would actually say.

Likely interview questions
Very commonGini vs entropy — does it matter?

Almost never. Gini = 1 − Σpᵢ² is the probability two random items from the node have different labels; entropy = −Σpᵢlog₂pᵢ is the bits needed to encode the class. They pick the same split roughly 98% of the time — Gini is in fact the first-order Taylor approximation of entropy near uniform. Gini is cheaper (no logarithm) and is the default. The right answer is that it doesn't matter and the tuning budget belongs on depth and leaf size instead.

Deep diveWhat is gain ratio and what problem does it solve?

Plain information gain is biased toward high-cardinality features: a feature with a unique value per row splits the data into perfectly pure singleton nodes and scores maximum gain, while being useless. C4.5's gain ratio divides the gain by SplitInfo — the entropy of the partition sizes themselves — which penalises splits that shatter the data into many small pieces. Modern implementations mostly handle this differently: binary splits only, plus min_samples_leaf. But the underlying bias never fully goes away, and it's the root cause of the feature-importance trap in §7.7.

7.3 Regression trees

Same algorithm, different impurity — and one consequence that decides whether you can use trees on a trending time series at all.

For regression the criterion is variance reduction: the impurity of a node is its MSE about the node mean, and the split maximises MSE(parent) − Σ(nᵢ/n)·MSE(childᵢ). The leaf predicts the mean of its rows. Swap in MAE and the leaf predicts the median — the same mean-vs-median distinction as §4.1, and sklearn exposes it as criterion='absolute_error' (much slower, because the median can't be updated incrementally the way a mean can).

A regression tree outputs a step function — and cannot extrapolate

Because every prediction is a leaf mean, the output is piecewise constant: it can never produce a value outside the range of the training target, and beyond the training range of a feature it simply returns the nearest leaf's constant. For a trending series that is fatal — a model trained on 2024 data will predict 2024 levels forever. The fixes are to detrend/difference first, model the residual with a tree and add the trend back, or use a hybrid with a linear component. This is the single most important practical limitation of tree models (§10.5).

Likely interview questions
ConceptualHow does a regression tree differ from a classification tree?

Only in the impurity measure and the leaf prediction. Classification uses Gini or entropy and predicts the majority class; regression uses variance / MSE reduction and predicts the leaf mean. Switch the criterion to absolute error and the leaf predicts the median instead — the same mean-vs-median choice as any other loss, and much slower to fit because medians can't be updated incrementally. Everything else — greedy search, axis-aligned splits, recursion — is identical.

Gotcha⭐ Can a decision tree extrapolate?

No. Every prediction is a leaf constant, so the output is bounded by the range of the training target and is flat beyond the training range of any feature. A tree trained on house prices from £100k–£500k will never predict £800k, and a tree trained on a rising time series will predict the last level forever. That makes tree models a poor fit for trending targets without preprocessing — detrend or difference first, model the residual, add the trend back — or use a hybrid with a linear component. It's the main structural reason a linear model can still beat a GBM on a forecasting problem.

7.4 Controlling complexity ⭐

A fully-grown tree has near-zero training error and enormous variance. Every hyperparameter here is a way of stopping that — and each controls a genuinely different thing.

ParameterStops growth when…Notes
max_depthThe node is d levels downThe blunt, effective knob — tune it first. Caps interactions at depth d
min_samples_splitA node has too few rows to consider splittingPrevents splits on tiny samples
min_samples_leafA split would leave a child below the minimumUsually the most useful — it bounds the variance of every prediction, because no leaf estimate is based on fewer than that many rows
max_leaf_nodesThe tree hits a leaf budgetGrows best-first rather than depth-first — the same idea as LightGBM's leaf-wise growth (§8.6)
min_impurity_decreaseThe best split's gain is below a thresholdDirect control on the gain shown in the §7.1 widget
max_features—Considers a random subset of features per split. Mostly a Random Forest device (§8.3), but it also regularizes a single tree
ccp_alpha—Post-pruning by cost-complexity — see §7.5
class_weight—Re-weights impurity calculations; how you make a tree cost-sensitive
Depth caps interaction order

A useful reframing: a tree of depth d can express interactions among at most d features on any single path. max_depth=1 (a stump) is a purely additive model with no interactions at all; max_depth=3 allows three-way interactions. That's why boosting with shallow trees works so well — you're fitting an additive model of low-order interactions, which is a good inductive bias for tabular data and is the connection to GAMs (§14.2).

Likely interview questions
PracticalWhich tree hyperparameter would you tune first, and why?

max_depth for a single tree — it's the bluntest and most effective control, and it has a clean interpretation: depth d caps the interaction order at d. Then min_samples_leaf, which I'd argue is actually the more useful one on noisy data because it bounds the variance of every leaf estimate rather than just the shape of the tree. For a Random Forest the priority inverts: leave depth unbounded and control the model with min_samples_leaf and max_features, because the averaging handles the variance (§8.3).

ConceptualWhat's the difference between min_samples_split and min_samples_leaf?

min_samples_split is a precondition on the parent: don't even consider splitting a node with fewer than this many rows. min_samples_leaf is a constraint on the children: reject any split that would leave a child below the minimum. The second is stronger and more useful, because a node with 100 rows passes min_samples_split=20 and can still produce a 99/1 split whose tiny leaf is pure noise — exactly what min_samples_leaf prevents. If I could set only one, it'd be min_samples_leaf.

7.5 Pruning

Pre-pruning is cheap and myopic; post-pruning is principled and slower. The distinction is a standard question with a satisfying answer.

Why this section is really about Part 8

A single tree needs careful pruning because its variance is enormous. The insight behind ensembles is that you can instead let trees stay high-variance and average that variance away — which is why in a Random Forest you often leave max_depth=None entirely and control the model with min_samples_leaf and max_features. Pruning matters most in exactly the case where you're shipping a single tree for interpretability.

Likely interview questions
ConceptualPre-pruning vs post-pruning — which is better?

Pre-pruning (early stopping via depth, leaf size, minimum gain) is fast and needs one pass, but it's myopic: a split with poor immediate gain might be the only route to two excellent splits below it, and you'll never find out. Post-pruning (cost-complexity, ccp_alpha) grows the full tree then removes subtrees that don't justify their leaves, so it sees the whole picture — at the cost of building a large tree first. Post-pruning is generally better for a single tree; pre-pruning is what everyone actually uses inside ensembles, because there the myopia is averaged away.

PracticalHow do you choose ccp_alpha?

Use cost_complexity_pruning_path, which returns the finite sequence of α values at which the pruned tree changes — because the pruning path is a nested sequence, there are only so many distinct trees. Then cross-validate over just those α values and pick the best, or apply the one-standard-error rule and take the smallest tree within one SE of the optimum. That's a cheaper and better-posed search than tuning max_depth over an arbitrary grid, and it's a nice thing to know because most people have never used it.

7.6 Strengths and failure modes ⭐

Three failure modes worth being able to draw, and a strengths list that explains why trees became the base learner for everything in Part 8.

Likely interview questions
Very commonWhy is a single deep tree high-variance?

Because splits are chosen greedily and hierarchically: moving a handful of rows can flip the root split, and everything below it then changes completely. A fully-grown tree also drives training error to near zero by isolating individual points, so it's fitting noise by construction. That instability is exactly the property bagging exploits — average many high-variance, low-bias trees and the variance falls while the bias stays put (§8.2).

ConceptualWhat are the strengths of trees that made them the base of every winning tabular model?

No scaling, because splits use rank order. Mixed types handled natively. Interactions captured automatically — you don't have to specify them, which is exactly what linear models need feature engineering for. Missing values handled by a learned default direction. Robust to feature outliers, since an extreme value is just "the largest". And interpretable at small depth. The weakness — high variance — is precisely the one that averaging fixes, which is why bagging and boosting on trees works so well while bagging on, say, linear models buys almost nothing.

GotchaWhy do trees struggle with a diagonal decision boundary?

Because every split is axis-aligned — a threshold on one feature — so a diagonal boundary must be approximated by a staircase, which costs many splits and therefore lots of data and depth. The giveaway in practice is a tree that needs surprising depth on what looks like a simple problem. Two fixes: rotate the feature space (a PCA or a learned linear combination can make the boundary axis-aligned), or engineer the combination directly — if you know the boundary is roughly x₁ + x₂ = c, giving the model x₁ + x₂ as a feature turns many splits into one. Oblique-split trees exist but are rarely used in practice.

7.7 The feature-importance trap ⭐⭐

One of the most reliable senior filters in the whole subject. Quoting feature_importances_ without qualification is a specific, recognisable tell.

The default feature_importances_ on a sklearn tree or forest is mean decrease in impurity (MDI): for each feature, the total impurity reduction it produced across all splits, weighted by the rows reaching those nodes. It is free — it was computed while fitting — and it has two documented biases.

Bias 1 Cardinality — it favours features with many distinct values
Mechanism
A continuous or high-cardinality feature offers many more candidate split points, so it has more chances to reduce impurity by luck. A binary feature offers one.
Demonstration
Add a column of pure random noise with many distinct values to any dataset and it will rank as an important feature. Everyone should run this once — it takes four lines and permanently changes how you read an importance plot.
Bias 2 It is computed on training data
Mechanism
MDI measures impurity reduction achieved while fitting, so a feature the model overfitted to scores highly — even if it contributes nothing out of sample.
Consequence
The importances describe how the model was built, not what actually predicts. Those are different questions and the distinction is the whole point of §14.3.
And permutation importance is not a free lunch either

Permutation importance on held-out data is the right default — it measures the actual metric drop when a column is shuffled, on data the model didn't train on. But it has its own failure: with correlated features, permuting one leaves its information available through the other, so both look unimportant while jointly being essential. It also evaluates the model on unrealistic rows created by the shuffle. Three methods, three different questions — which is exactly the framing §14.3 develops.

Likely interview questions
Very common⭐ Why is impurity-based feature importance misleading? What do you use instead?

Mean decrease in impurity has two documented biases. It favours high-cardinality and continuous features, because more candidate split points means more chances to reduce impurity by luck — add a column of pure noise with many distinct values and it will rank as important. And it's computed on training data, so it rewards features the model overfitted to. It describes how the model was built, not what actually predicts. Use permutation importance on held-out data instead, which measures the real metric drop when a feature is shuffled — then state its own caveat: correlated features mask each other, so both can look unimportant while jointly being essential.

DebugYour top feature by importance is the customer ID. What's happening?

Two possibilities, and I'd check both. The MDI bias: an ID has thousands of distinct values, so it offers thousands of split points and accumulates impurity reduction by chance — it can rank high while being useless. Genuine leakage: IDs are often assigned sequentially, so an ID encodes time, and if the target rate drifted over time the model has learned a temporal shortcut that will not generalise forward one day. The test that distinguishes them: compute permutation importance on held-out data — if it's ~zero, it's the cardinality bias; if it's large, it's leakage. Either way, drop the ID.

ConceptualIs feature importance a causal statement?

No, and this is the most consequential misuse. Importance measures how much the model uses a feature, which reflects predictive association — including through proxies, confounders and consequences of the target. num_collection_calls is enormously important for predicting default and reducing collection calls will not reduce default. If someone intends to act on the explanation, they need a causal design, not an importance ranking (§16.4). What importance is good for: debugging, sanity-checking, leakage detection, and generating hypotheses worth testing properly.
