Part 1 of 17 · What ML Actually Is

The questions asked before any model exists What machine learning actually trades away, the five learning paradigms and where real problems fall, the difference between predicting, explaining and deciding, the lifecycle, how to frame a target — and the senior answer: when not to use ML at all.

This part contains no algorithms, and it is where a surprising number of interviews are decided. Every question here is really the same question: do you understand what you are buying and what you are giving up? ML trades explicit, auditable rules for examples plus a loss function — a good trade when the rule is genuinely unknown, and a terrible one when it isn't. The three highest-value habits in this part are naming the task type before proposing anything, separating prediction from inference from decision (they are three different projects with three different methods), and always reporting baselines. Each topic ends with the interview questions it answers.

1.1 Rules vs examples — what ML actually trades ⭐

Machine learning replaces explicit rules with examples plus a loss function. Every other property of ML systems — including all of their failure modes — follows from that single substitution.

When you write a rule, you own the logic. You can read it, test it clause by clause, explain it to a regulator, and change it on a Tuesday afternoon. When you fit a model, you no longer own the logic — you own the data, the loss, and the evaluation, and the logic is inferred from those three things. That is a genuinely good trade when the rule is complex, unknown, or changes faster than you could rewrite it. It is a terrible trade when the rule is simple, known and stable.

What you give up, concretely

PropertyHand-written ruleFitted model
Where the logic livesIn code you wroteIn parameters inferred from data
AuditabilityRead itApproximate it post-hoc (Part 14)
Behaviour on new inputsDefined by the ruleUnknown — this is the whole reason validation exists
Failure modeYou wrote the wrong ruleYou collected the wrong data, or chose the wrong loss, or measured the wrong thing
Cost to changeEdit and deployRetrain, revalidate, redeploy, re-monitor
Scales withYour understandingYour data

Two axes that get asked as follow-ups

Online vs batch learning. Batch learning fits on a fixed dataset and is redeployed on a schedule; online learning updates continuously from a stream. Almost all production classical ML is batch-trained and served online — meaning the model is refitted nightly or weekly but answers requests in real time. Saying “we'd use online learning to keep it fresh” is usually the wrong answer, because continuous updating makes incidents unreproducible, is hard to validate, and is vulnerable to feedback loops (§15.7).

Transductive vs inductive. Inductive learning produces a function that generalises to rows you have never seen — this is what almost everything in this guide does. Transductive learning only produces labels for a specific known set of unlabelled rows, with no reusable function: label propagation and some graph methods work this way. The distinction matters the moment someone asks “how do you score a new customer?” and your method has no answer.

The framing that makes you sound senior

When asked “what is machine learning?”, most candidates define it. Better: define it as a trade. “It's learning a function from examples instead of specifying it — you trade explicit, auditable rules for data, a loss function and an evaluation procedure. That's the right trade when the rule is genuinely unknown or too complex to write, and the wrong one otherwise, which is why the first question I ask on any project is whether a rule would do.”

Likely interview questions
ConceptualWhat is machine learning, in one or two sentences?

Learning a function from examples plus a loss function, instead of specifying that function as explicit rules. The trade is that you stop owning the logic and start owning the data, the loss and the evaluation — which is why validation and monitoring are structural requirements rather than nice-to-haves. Define it as a trade rather than a category and the rest of the interview follows more naturally.

ConceptualOnline vs batch learning — which would you use in production and why?

Almost always batch-trained, online-served: refit on a schedule, answer requests in real time. True online learning updates from a stream, which sounds attractive but makes incidents unreproducible, is very hard to validate before it affects users, and amplifies feedback loops — a fraud model that learns continuously from its own accepted transactions drifts in a direction nobody chose (§15.7). Online learning earns its place with genuinely non-stationary, high-volume, low-stakes problems (ad ranking, some recommendations), not with credit or claims.

GotchaTransductive vs inductive — why would anyone care?

Inductive learning gives you a reusable function that scores rows you have never seen; transductive learning gives you labels for a specific fixed set and nothing more. Label propagation over a graph is transductive: add a new node and you re-run the whole thing. It matters the moment the system has to score a new customer at request time — a transductive method has no answer to that, and discovering it after choosing the method is expensive.

1.2 The five learning paradigms

Naming the paradigm is the first move in any design answer, because it determines what data you need, what it costs, and what could possibly go wrong.

ParadigmYou supplyIt learnsReal problemThe hard part
SupervisedFeatures + labelsf: x → yCredit default, claim severity, churn, fraudGetting labels, and getting them at the right time
UnsupervisedFeatures onlyStructure — clusters, components, densitySegmentation, anomaly detection, compressionEvaluation — there is no ground truth to score against
Semi-supervisedFew labels + much unlabelled dataf: x → y, propagatedFraud where only confirmed cases are labelledConfirmation bias — the model reinforces its own errors
Self-supervisedUnlabelled data + a pretext taskRepresentationsAll modern pretraining; increasingly tabular too (§16.1)Designing a pretext task whose solution is useful
ReinforcementAn environment + a rewardA policy π: s → aBidding, inventory, routing, pricing under feedbackYou need an environment — and reward design is notoriously fragile

The distinctions that trip people up

Self-supervised is not unsupervised. Both start from unlabelled data, but self-supervised learning manufactures labels from the data itself — mask a token and predict it, corrupt a column and reconstruct it — and then trains with ordinary supervised machinery. The output is a representation, not a clustering. That distinction matters in 2026 because it is the mechanism behind tabular foundation models (§16.1).

Semi-supervised is not “just use the unlabelled data”. Its methods — self-training, label propagation, co-training — all rest on an assumption (that the decision boundary lies in a low-density region, or that the data has cluster structure aligned with the labels). When that assumption fails, pseudo-labelling makes things actively worse because the model trains on its own confident mistakes.

Reinforcement learning needs an environment, and you probably don't have one. The most common bad answer in a case interview is proposing RL for a problem where you can only observe historical logs of a policy you did not control. That is offline RL or, more usefully, a causal inference problem (§16.4) — and framing it that way instead is a strong signal.

Likely interview questions
Very commonSupervised vs unsupervised vs reinforcement learning — with a real example of each.

Supervised: features plus labels → a mapping. Predicting credit default from application data. Unsupervised: features only → structure. Customer segmentation, or anomaly detection where you have no confirmed anomalies. Reinforcement: an environment and a reward → a policy. Real-time bid optimisation, inventory replenishment. Add for credit: self-supervised (a pretext task manufactures the labels — the basis of all pretraining) and semi-supervised (a few labels plus lots of unlabelled data, which is the realistic fraud situation).

GotchaIs self-supervised learning just unsupervised learning with a new name?

No. Both start from unlabelled data, but self-supervised learning creates labels from the data itself via a pretext task — mask and predict, corrupt and reconstruct — then trains with ordinary supervised machinery. The output is a representation you then fine-tune, not a clustering or density estimate. It matters on tabular data now because it is the mechanism behind TabPFN-style models (§16.1), which are pretrained on synthetic data and applied in-context.

DesignA stakeholder asks for reinforcement learning to optimise pricing. How do you respond?

Ask what environment we would train in. RL needs to interact — take an action, observe the consequence, repeat — and if all we have is a log of prices someone else set, we have observational data from an unknown policy, not an environment. That is either offline RL (hard, data-hungry, easy to get wrong) or, far more usefully, a causal inference problem: estimating price elasticity with confounding by the historical pricing policy (§16.4). Proposing a geo experiment or a DML approach instead is the stronger answer, and it is usually also the cheaper one.

ConceptualWhen does semi-supervised learning hurt rather than help?

When its underlying assumption fails — that the decision boundary lies in a low-density region, or that cluster structure aligns with the labels. Pseudo-labelling then trains the model on its own confident mistakes, which reinforces them: the classic confirmation-bias failure. Guard against it by holding out a clean, human-labelled validation set that never receives pseudo-labels, and by adding pseudo-labels gradually with a confidence threshold rather than all at once.

1.3 Prediction vs inference vs decision ⭐

Three different projects, three different methods, three different ways to be wrong — and they are constantly conflated, including by the people commissioning the work.

“We want to understand churn” is not a specification. It could mean any of three things, and each one changes the model, the validation, the metric and the deliverable.

How to tell which one you're being asked for

Listen for the verb. “Predict”, “score”, “flag”, “rank” ⇒ prediction. “Understand”, “explain”, “which factors drive”, “how much does X affect Y” ⇒ inference. “Who should we target / offer / approve / intervene on” ⇒ decision. Then say which one you heard, out loud, and confirm it — because if the stakeholder wanted a decision and you deliver a prediction, the project will be judged a failure for reasons nobody will be able to articulate.

Feature importance is not a cause

A model can be highly accurate while assigning importance to a feature that has no causal effect at all — it may be a proxy, a collider, or a consequence of the target. “num_support_tickets is the top driver of churn, so let's reduce support tickets” is an inference claim made from a prediction model, and it is usually wrong. If someone will act on the explanation, you need a causal design, not a SHAP plot (Part 14, §16.4).

Likely interview questions
Very commonWhat's the difference between prediction and inference, and why does it matter?

Prediction asks “what will happen?” and is judged on out-of-sample accuracy; correlation is sufficient because you never intervene. Inference asks “why?” or “how much does X affect Y?” and is judged on identifiability and correct uncertainty; it needs assumptions to hold and often prefers a simpler, well-specified model over a more accurate one. It matters because the methods diverge: a GBM with SHAP is excellent for the first and inadmissible as evidence for the second. And there is a third — decision — which needs a causal quantity, not either of the first two.

GotchaYour churn model is 0.88 AUC. The business wants to know what causes churn. What do you say?

That the model is not evidence of causes and I'd be misleading them if I read it that way. A predictive model happily uses proxies, consequences of the target, and features that are only correlated through a confounder — num_collection_calls predicts default beautifully and reducing collection calls will not reduce default. To answer “what causes churn” I'd need a causal design: an experiment where possible, or an identification strategy with the assumptions stated (§16.4). What I can offer immediately from the predictive model is a hypothesis list worth testing, which is genuinely useful as long as it is labelled as that.

DesignHow do you tell which of the three a stakeholder is actually asking for?

Ask what happens the day after the model ships — specifically, what action does someone take, and on which rows? If nobody acts and the output is a report, it's inference. If a system consumes the score and treats rows differently, it's prediction feeding a decision, and then I need to know the action's cost and whether it plausibly changes the outcome — which is what turns it into an uplift problem. Listening for the verb helps too: “predict/score/flag” vs “understand/explain” vs “target/offer/approve”.

1.4 The ML lifecycle

The loop is not linear, it closes, and the box everyone practises is the smallest one in it.

The three things to write down before any fit()

  • The target metric — and specifically, the metric at the operating point you will deploy, not a threshold-free summary (Part 12).
  • The baseline it must beat — including the existing business rule, which is the real bar (§1.6).
  • The decision it feeds — because if you cannot state the decision, you cannot choose the metric, and you will optimise something arbitrary.

Interviewers who ask “how would you know the project succeeded?” are checking whether you do this. The answer they want is not a metric name; it is evidence that success was defined before the modelling started.

Likely interview questions
ConceptualWalk me through the ML lifecycle. Where does the time actually go?

Problem framing → data collection → EDA and deciding the split → feature engineering → baseline then model → validation → deployment → monitoring → retraining, which loops back into re-framing. The time goes overwhelmingly into data and validation, not modelling — the modelling box is the one everyone practises and the smallest one in the loop. Two things worth adding unprompted: the loop closes (monitoring changes the problem definition, not just the weights), and the offline metric is a proxy whose link to the business outcome is an assumption you test.

DesignHow would you know the project succeeded?

By having defined it beforehand: a target metric measured at the deployed operating point, a baseline it must beat (including the current business rule), and the decision it feeds. Then success is the business quantity that decision moves — cases prevented, hours saved, margin protected — measured against that baseline, ideally with an experiment. And an operational half: is it monitored, is it maintainable, can it be rolled back, does the team trust it.

GotchaWhat is the offline/online metric gap?

Your offline metric is a proxy for a business outcome, and the mapping is an assumption. A model with better AUC can lose an A/B test — because the improvement was in a score region users never see, because the score distribution shifted under a fixed threshold, or because the business metric depends on something you never optimised (diversity, latency, fairness of exposure). Manage it by stating the assumed link explicitly, validating it against historical launches, and shipping through shadow → canary → A/B with guardrails (§15.7–15.8).

1.5 Framing a problem correctly ⭐

Choosing the target variable is the highest-leverage decision in the whole project, and the one most often made in thirty seconds.

Take “predict churn”. It is not a specification. Churn could be a cancelled subscription, ninety days of inactivity, a downgrade, or a support ticket asking how to close an account. Each definition produces a different label, a different base rate, a different model — and, crucially, a different set of customers you would act on.

The five decisions inside “the target”

DecisionThe questionConsequence of getting it wrong
DefinitionWhat event exactly counts?You optimise for something the business does not care about
Unit of predictionCustomer? Session? Transaction? Customer-month?Determines your splitting strategy — get it wrong and you get group leakage (§3.6)
HorizonWithin 30 days? 90? Ever?“Ever” is unlearnable and unactionable; too short and the base rate collapses
Decision windowHow long does the team need to act?A prediction that arrives after the action window is worthless
Data latencyWhen does each feature actually become available?You build features from data that will not exist at prediction time — temporal leakage

The same business problem, framed four ways

FramingTargetWhat it buysWhat it costs
ClassificationWill this customer churn in 30 days?Simple, calibratable, thresholdableLoses timing information entirely
Regression / survivalWhen will they churn?Timing for the intervention calendar; handles censoring (§10.3)Harder to evaluate and to explain
RankingWho are the top 500 at risk?Matches a fixed outreach capacity exactlyScores stop being probabilities, so expected value breaks
Uplift / CATEWho will churn only if we do nothing?The correct target for a retention offerNeeds experimental data; harder to validate (§16.5)
Cost asymmetry, in the units the business uses

“What does a false positive cost versus a false negative?” is the question that turns a metric argument into a business conversation. A wrongly-blocked legitimate payment costs a lost sale plus a support contact; a missed fraud costs the transaction value plus a chargeback fee plus scheme penalties. Once those are numbers, the threshold (§12.7) stops being a matter of taste and becomes arithmetic — and you can defend it to someone who does not know what a threshold is.

Likely interview questions
Very common⭐ How do you choose the target variable and prediction horizon for a churn model?

Work backwards from the decision. Ask what action the model triggers and how long that action needs — if retention needs 30 days to run a campaign, the target is “churns within 30 days”, not “ever churns”. Then define churn concretely (cancellation? 90 days inactive? downgrade?) and check the base rate under each definition, because that determines whether the problem is even learnable. Pin the unit of prediction — customer, or customer-month — because it fixes your splitting strategy. Add a data-latency gap so every feature is knowable at prediction time. And close with the framing caveat: if the decision is who gets a retention offer, churn is the wrong target and you want uplift.

DesignWhy does the unit of prediction matter so much?

Because it determines the split, and the split determines whether any number you report is meaningful. If the unit is a transaction but rows are nested inside customers, a random split puts the same customer on both sides — the model learns to recognise the customer rather than the pattern, and validation looks excellent right up until it meets a new customer. It also determines what a “positive” means (one churned customer, or twelve churned customer-months?) and therefore the base rate and the metric.

DesignSame business problem, four framings — when would you pick each?

Classification when a yes/no decision at a threshold is enough and you want calibrated probabilities. Survival when timing matters and some customers simply have not churned yet — censoring makes binary labels biased. Ranking when capacity is fixed ("we can call 500 people"), though you then lose probability semantics. Uplift when you are choosing who to treat rather than who to watch. Saying “these are four different targets, and the right one depends on the action” is worth more than any one of them.

GotchaWhat's wrong with defining churn as "ever cancels"?

Three things. It is unactionable — you cannot intervene on an event with no time bound. It is unlearnable in practice, because the features that predict a cancellation next week are different from those predicting one in three years, and the model averages them into mush. And it creates a censoring problem: customers still active are labelled 0 when they may simply not have churned yet, which biases the model toward whatever tenure distribution your snapshot happens to have.

1.6 Baselines you must always report

A model without a baseline is an unfalsifiable claim. Reporting baselines is nearly free, and forgetting them is one of the most visible junior tells there is.

interactive What does your model actually have to beat?
—majority-class accuracy
—your model's accuracy
—accuracy gained
—AP vs base-rate AP

All computed from 4,000 simulated rows. Drag the base rate to 3% and watch the majority-class baseline hit 97% accuracy while your model gains almost nothing on that metric — even though its average precision is many times the baseline. This is the accuracy trap in §12.1, encountered before you have written any model code, which is exactly when it should be encountered.

The five baselines, and what each one tells you

BaselineWhat it isWhat it tells you
Majority / meanAlways predict the majority class or the training meanThe floor. On a 99:1 problem it scores 99% accuracy — which is the whole argument of §12.1
Previous valueNaive or seasonal-naive forecastThe one that embarrasses time-series models most often (§10.6)
The existing ruleWhatever the business does todayThe real bar. If you can't beat it, the project's value is negative
Random-but-calibratedPredict the base rate for everyoneAnchors intuition for log loss and Brier — and it is the correct AP baseline
Strong simple modelLogistic regression or a small GBM on obvious featuresUsually reaches 90–95% of the final performance in 2% of the effort
The finding is allowed to be “don't ship it”

If the complex model doesn't beat those baselines by a margin that justifies its serving cost, its retraining cost and its risk, that is the result — report it. Candidates who volunteer this are describing a real project; candidates who can't imagine it are describing a tutorial. The corollary is that a strong simple baseline should be built first, not last, because it also tells you whether the problem is learnable at all before you spend three weeks on features.

Likely interview questions
Very commonWhat baselines would you report before any model?

Majority class or mean; the previous value / seasonal-naive for time series; the existing business rule, which is the real bar; a random-but-calibrated predictor to anchor log loss and to give the correct average-precision baseline; and a strong simple model — logistic regression or a small GBM on obvious features. Then the sentence that matters: if the complex model doesn't beat these by enough to justify its cost and risk, that is the finding, and I'd report it.

GotchaWhy is "the existing business rule" the most important baseline?

Because it is what the model actually replaces, so it is what the project's value is measured against. Beating a majority-class baseline proves nothing if the current hand-written rule already beats it by more. It is also the baseline most often skipped, because it takes work to reconstruct and it sometimes produces an uncomfortable answer — which is precisely why an interviewer asking about it is testing your honesty as much as your method.

ConceptualWhat's the right baseline for average precision?

The base rate — a random ranker achieves an average precision equal to the positive class proportion, not 0.5. That is why an AP of 0.30 can be excellent (on a 2% base rate it is 15× lift) or poor (on a 40% base rate it is worse than random). Always report AP alongside the base rate, or report lift over it, otherwise the number is uninterpretable. Contrast with ROC-AUC, whose random baseline is always 0.5 regardless of imbalance — which is precisely the flattery described in §12.3.

1.7 When not to use ML ⭐⭐

The strongest senior signal in this entire part, and it takes one sentence: most candidates answer “when you don't have data”, and the full answer has four branches — three of which are about consequences rather than data volume.

Two more reasons to say no that candidates rarely mention

The feedback loop makes evaluation impossible. If the model's decisions determine the data you will next observe, and you have no exploration traffic, you cannot measure whether it works (§15.7). Shipping into that situation is shipping something you can never evaluate.

The cost of being wrong is not symmetric with the cost of being right. If a correct prediction saves £5 and an incorrect one costs £5,000, you need precision so high that a rule with a human reviewer will usually beat an ML system on expected value — and will be defensible in a way the model is not.

How to deliver this in an interview

Do not wait to be asked. When given a case, spend the first thirty seconds on it: “Before designing this — is there a rule that would do? Do we have labels, or a path to them? Is an unexplainable error acceptable here? And is there enough data for the effect size we're chasing? Assuming yes to all four, here's how I'd approach it…” It costs half a minute and it reframes you from someone who builds models into someone who decides whether to.

Likely interview questions
Very common⭐ When would you not use machine learning?

Four branches. (1) The rule is stable and writable — ship the rule; it's auditable, free, and never drifts. (2) You have no labels and no path to getting them — reframe as unsupervised, buy labels, or instrument now and model later. (3) An unexplainable error is unacceptable — use a deterministic system, or ML with a human in the loop. (4) The data is too small for the effect size you're chasing — a GLM, a statistical estimate or a lookup table will beat an under-trained model. Two more worth adding: when a feedback loop makes evaluation impossible without exploration traffic, and when cost asymmetry is so extreme that a rule plus a human reviewer wins on expected value.

DesignGive a concrete example where a rule beats a model.

“Flag every transaction above £10,000 to a payee first seen today.” It is auditable, instant, has no training data requirement, cannot drift, and a compliance officer can sign it off. A model might catch marginally more, but it would need labels, monitoring, retraining, an explanation layer and a fairness review — and the regulator would still ask why a specific transaction was flagged. In regulated screening the rule is often the correct engineering answer, with ML used to rank the alert queue the rule generates rather than to replace it.

Gotcha“We don't have labels but we have lots of data — can't we just use unsupervised learning?”

Sometimes, but check what you'd do with the output. Unsupervised methods give you structure, not answers, and you cannot evaluate them against the thing you actually care about — a clustering that looks beautiful may have nothing to do with churn. If the goal is genuinely exploratory (segmentation for a marketing team to interpret), it's fine. If the goal is a prediction, unsupervised learning is a way of postponing the labelling problem, not solving it. The better answer is often: label 500 rows properly, use active learning to spend the next 500 well (§10.1), and get a supervised baseline you can actually measure.

DesignHow does cost asymmetry change the build-or-rule decision?

It changes the precision you need, which changes whether any achievable model is viable. If a correct catch saves £5 and a false positive costs £5,000, the break-even precision is above 99.9% — no model on a noisy problem will hit that, so the viable design is a high-recall cheap filter plus human review, where the ML system's job is to rank the queue rather than to decide. Working that arithmetic out loud, before proposing an architecture, is one of the clearest senior signals available in a case interview.
