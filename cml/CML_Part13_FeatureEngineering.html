A model can only use structure you expose, which is why on tabular data feature engineering routinely beats model choice. But the two ideas that make this part senior-level are less obvious than that. The first is that you usually select features not for accuracy but for latency, acquisition cost, drift surface, interpretability and maintenance — and being able to say “I dropped features that improved accuracy because they cost more than they were worth” is a genuinely strong answer. The second is point-in-time correctness: reconstructing what a feature's value was at prediction time rather than what it is now, which is simultaneously a feature-store design problem and the deepest form of the leakage question from Part 3.

13.1 Why feature engineering still matters ⭐

A model can only use structure you expose. On tabular data that single sentence explains why feature work routinely beats model choice — even in 2026.

The counter-argument you'll hear is “deep learning does automatic feature extraction”, and it's true for images, audio and text — modalities with strong local structure that a convolution or attention layer can exploit. Tabular data has no such structure: columns have no spatial or sequential relationship, so there's nothing for an architecture to discover generically. The structure is semantic — that debt and income should be divided, that a timestamp implies a business calendar — and semantics come from you.

Likely interview questions
ConceptualDoesn't deep learning make feature engineering obsolete?

For images, audio and text — largely yes, because those modalities have strong local structure (spatial, spectral, sequential) that convolutions and attention exploit generically. Tabular data has no such structure: columns have no inherent adjacency, so there's nothing for an architecture to discover from the geometry. The structure that matters is semantic — that debt should be divided by income, that a timestamp implies a business calendar — and that comes from domain knowledge. Even tabular foundation models (§16.1) benefit from well-constructed features; they change the modelling baseline, not the value of exposing real structure.

13.2 Numeric features ⭐

Ratios, differences and group aggregates carry most of the value. Transformations matter mainly for linear models.

TechniqueExampleWhy it helps
Ratiosdebt/income, amount/avg_amount_30dOften more predictive than either input — it encodes a comparison the model would otherwise have to learn from a 2-D interaction
Differencesnow − last_login, price − category_medianRecency and deviation-from-normal are the two most reusable signals in tabular ML
Group aggregatesmean / max / std / count per customer, merchant, dayGives a row context it doesn't have alone — and is the most common source of temporal leakage (§3.7)
Transformationslog, sqrt, Box-Cox / Yeo-JohnsonTames skew for linear models; does nothing for trees
BinningUniform, quantile, supervised (tree-based)Injects non-linearity into a linear model; usually loses information for a GBM
Clipping / winsorizingCap at the 1st/99th percentileBounds the influence of extremes without deleting rows
Interactions & splinesPolynomialFeatures, SplineTransformerHow a linear model gets what a tree gets for free
The fraud-features answer, organised

Structure it as entity × window × statistic. Transaction-level: amount, currency, hour (cyclically encoded), channel, merchant category, is-the-country-new. Card/customer aggregates over 1h / 24h / 7d / 30d: count, sum, max, std, distinct merchants, distinct countries, velocity (count this hour ÷ average hourly count). Deviation features: amount ÷ customer's 30-day median, geo-distance since last transaction ÷ elapsed time. Merchant-side: cross-fitted chargeback rate, relationship age. Graph-ish: cards seen on this device. Then close with the constraint that makes it real: every one of these must be computable inside the ~150 ms budget and must be point-in-time correct.

Likely interview questions
Very common⭐ Walk me through feature engineering for a transaction fraud model.

Organise by entity × window × statistic. Transaction: amount, hour (cyclically encoded), channel, merchant category, is-new-country. Card/customer aggregates over 1h/24h/7d/30d: count, sum, max, std, distinct merchants, distinct countries, velocity ratios. Deviation: amount ÷ 30-day median, geo-distance ÷ elapsed time. Merchant: cross-fitted chargeback rate, relationship age. Device/graph: cards per device. Then the constraints that make it a real answer: every feature must fit the ~150 ms budget and be point-in-time correct, and aggregates must never be computed over the full history at training time.

ConceptualWhy does a ratio like debt/income beat giving the model both columns?

Because a ratio is a multiplicative interaction, and neither a linear model nor a shallow tree gets there cheaply. A linear model literally cannot represent a ratio without you constructing it. A tree can approximate it, but only with a staircase of axis-aligned splits — it needs many splits and therefore many rows to learn what one column states directly (§7.6). Providing it is pure inductive bias: you're telling the model something true about the domain that it would otherwise have to discover from data it may not have enough of.

GotchaWhen does binning a continuous feature help, and when does it hurt?

Helps for linear models, where it's a cheap way to capture non-linearity without specifying its shape — and in regulated settings, where binned "scorecard" features are easier to explain and to constrain. Hurts for trees and GBMs, which already choose their own thresholds optimally: pre-binning throws away resolution and can only lose information. It also creates discontinuities at bin edges that are hard to defend ("£49,999 and £50,001 get different treatment"). If I want non-linearity in a linear model, I'd usually prefer splines, which are smooth and don't have edge artefacts.

13.3 Datetime features ⭐

The one people get wrong most often, and the fix is a single line of trigonometry.

interactive Why cyclical encoding — 23:00 and 00:00 are one hour apart
—distance, raw integer
—distance, sin/cos
—true clock distance (h)

Both distances computed exactly. The raw integer encoding says 23:00 and 00:00 are the furthest apart pair on the clock; the sin/cos encoding says they're adjacent, which is the truth. This matters for every distance- and linear-based model — and even for trees, which would otherwise need two separate splits to express “late night”.

Likely interview questions
Very commonHow do you encode a datetime? Why cyclical encoding?

Extract components (hour, day-of-week, day-of-month, month, week-of-year), add domain flags (holiday, business day, days-to-next-holiday), and add time-since-last-event recency features, which are consistently among the strongest in churn and fraud. Use cyclical encoding — sin(2πh/24) and cos(2πh/24) — because on a raw integer scale 23 and 0 are the furthest apart values when they're actually one hour apart. Two traps: be explicit about timezone/DST, and never feed the raw absolute timestamp, or the model memorises a period rather than a pattern.

GotchaDo trees need cyclical encoding?

Less than linear or distance-based models, but it still helps. A tree can express "hour ≥ 22 or hour ≤ 5" — but only with two separate splits on different branches, so it needs more depth and more data to learn what one sin/cos pair states directly. Giving it both the raw integer and the cyclical pair costs two columns and lets it choose. The models where cyclical encoding is essential rather than helpful are anything using a distance (kNN, k-means, RBF-SVM) or a linear coefficient, where hour 23 and hour 0 would otherwise be maximally far apart.

DebuggingYour model works in backtest and degrades every month after deployment. What datetime mistake might explain it?

Most likely you fed absolute time — a raw timestamp, an epoch integer, or a monotonically increasing ID that proxies for it. The model then learns "recent rows behave like X", which is true within the training window and meaningless beyond it: every prediction after deployment is an extrapolation past the largest value the tree ever saw, so it just returns the last leaf (§7.3). The fix is to use relative time features (time-since-event, day-of-week, seasonality) and never the absolute index, and to validate with a time-based split which would have caught it before launch.

13.4 Text & geospatial on a tabular row

Two modalities that show up as columns in an otherwise-tabular problem, each with a standard ladder of options.

ModalityCheapMiddleExpensive
TextLength, word count, has-keyword flags, punctuation ratio, is-all-capsTF-IDF + TruncatedSVD to a few dozen dimsSentence embeddings — but a 384-dim block among 20 tabular columns usually needs reduction to be useful to a GBM. See the NLP guide
GeospatialCountry, region, postcode prefixDistance to points of interest; geohash prefixes at several precisionsCluster the coordinates and use cluster ID + distance-to-centroid; spatial joins to demographic data
Raw latitude and longitude are bad features

A tree splitting on latitude carves the world into horizontal bands, which almost never matches anything real, and it cannot express “near this city” without many splits. Better: distance to relevant points (city centre, nearest branch, nearest competitor), geohash prefixes at a few precisions (which give hierarchical categorical regions), or cluster IDs from k-means on coordinates. And note that postcode is a proxy for protected attributes in many jurisdictions (§14.8), so its use needs a fairness review rather than just a performance check.

Likely interview questions
DesignYou have a free-text description column in an otherwise tabular problem. What do you do?

Ladder up only as far as the value justifies. Start cheap: length, word count, keyword flags, punctuation/caps ratios — these often capture most of the signal in short operational text and cost nothing. Then TF-IDF plus TruncatedSVD down to 20–50 dimensions, which plays well with a GBM. Only then embeddings, and if I use them I'd reduce dimensionality first, because a 384-dim dense block alongside 20 tabular columns will dominate the split search and dilute the tabular signal. Whatever I choose gets fitted inside the pipeline — a TF-IDF vocabulary is learned from data, so fitting it before the split is contamination (§3.7).

GotchaWhy are raw latitude and longitude poor features?

Because axis-aligned splits on lat/long carve the map into rectangles that almost never correspond to anything meaningful, and expressing "within 5km of this city" needs many splits. Better representations: distance to relevant points of interest (which encodes the actual mechanism), geohash prefixes at several precisions (hierarchical categorical regions the model can use directly), or cluster IDs from clustering the coordinates plus distance to the centroid. And a governance point: postcode and fine-grained location are strong proxies for protected attributes, so their use needs a fairness review, not just a performance check.

13.5 Feature selection ⭐

The interesting question is not how to select but why — and the honest answer is usually not accuracy.

Selection is part of the model

Choosing features by looking at the whole dataset — including validation rows — and then cross-validating is textbook train-test contamination. The selection has already seen the labels it will be scored against, so the CV score is optimistic, sometimes dramatically so when p ≫ n. Feature selection must be fitted inside the CV loop, exactly like a scaler or an imputer, which in practice means it lives in the Pipeline.

Likely interview questions
Very commonFilter vs wrapper vs embedded feature selection.

Filter scores each feature independently of any model (correlation, chi², ANOVA F, mutual information) — fast and scalable, but blind to interactions, so a feature useless alone but valuable in combination gets dropped. Wrapper repeatedly refits a model on subsets (forward/backward, RFE/RFECV) — accounts for the actual model and interactions, but is expensive and can overfit the selection itself. Embedded gets selection as a by-product of fitting (L1, tree importances, boosting gain) — the practical default, but it inherits the model's biases (§7.7). Whichever I use: it's fitted inside the CV loop.

Very commonWhy would you drop features that improve accuracy?

Because accuracy isn't the only cost. Each feature carries serving latency (a fetch, a join), acquisition cost (a paid third-party call), drift and monitoring surface, leakage risk, maintenance burden, and sometimes regulatory exposure as a proxy for a protected attribute. A feature worth 0.002 AUC and £0.30 per prediction is a bad trade at any volume. Being able to make that argument explicitly — and to have actually done it — is one of the clearest signals of production experience.

Deep diveWhat is Boruta and when would you use it?

Boruta is an all-relevant selection method rather than a minimal-optimal one. It creates shadow features — random shuffles of each real column — trains a Random Forest, and keeps any feature whose importance significantly exceeds the best shadow feature's, repeating with statistical tests. The distinction matters: most methods find a minimal set sufficient for prediction, which arbitrarily drops one of every correlated pair. Boruta finds every feature carrying signal, which is what you want for understanding the problem or for downstream causal work — not necessarily for building the leanest production model.

13.6 Pipelines in production ⭐

The Pipeline is not a convenience — it is the unit that makes leakage structurally impossible and makes training and serving the same code.

PracticeWhy
ColumnTransformer + PipelineThe unit of everything learned from data — refitted per fold, serialised as one object
Custom transformersBaseEstimator + TransformerMixin; implement get_feature_names_out so downstream explanations stay readable
set_output(transform="pandas")Keeps column names through the pipeline — essential for SHAP and for debugging
handle_unknownServe-time categories will include levels not seen in training. Decide the behaviour explicitly rather than crashing
Feature versioningChanging a feature's definition silently invalidates every model trained on the old one — version the definition, not just the code
Latency budget per featureWhat can be computed inline at request time versus precomputed and looked up (§15.3)
Likely interview questions
PracticalWhy put everything in a Pipeline rather than transforming the data first?

Three reasons. Correctness: cross-validation refits the whole pipeline per fold, so scalers, imputers, encoders and selectors are fitted on training data only — leakage becomes structurally impossible rather than a discipline you have to remember (§3.7). Deployment: the pipeline serialises as one object, so serving applies exactly the transforms that training used — no second implementation to drift (§15.4). Tuning: preprocessing hyperparameters (imputation strategy, encoder settings, n_components) become searchable alongside model hyperparameters, which is often where the real gains are.

DesignWhat happens when a categorical level appears at serve time that wasn't in training?

Whatever you decided in advance — and if you didn't decide, it throws and takes down the endpoint. Options: handle_unknown='ignore' (all-zeros one-hot, i.e. treated as the baseline), 'infrequent_if_exist' (mapped to the rare-category bucket, which is usually the most sensible), or an explicit unknown level created at training time by grouping rare categories. I'd also monitor the unknown rate as a data-quality signal — a spike means an upstream vocabulary changed, which is one of the most common production incidents (§15.5).

13.7 Feature stores & point-in-time correctness ⭐⭐

The deepest form of the leakage question: reconstructing what a feature's value was at prediction time, rather than what it is now.

Likely interview questions
Very common⭐ What is a feature store and what problem does point-in-time correctness solve?

A feature store is a shared, versioned system for computing, storing and serving features so that training and inference use the same definitions. Point-in-time correctness is the hard part it exists for: when you build a training row for March, the feature values must be the values that existed in March, not today's. Joining today's lifetime_spend onto a March label leaks six months of the future into the row — CV looks great, production doesn't. The mechanism is an as-of join against a time-versioned feature history. The sibling problem it solves is training/serving skew: one code path instead of two implementations that silently diverge.

DesignDo you always need a feature store?

No — it's infrastructure, and infrastructure has a cost. You need one when: multiple models share features, features are computed from streams, you have genuine real-time serving with precomputed aggregates, or point-in-time correctness is hard to get right by hand. You don't need one for a single batch-scored model whose features come from one warehouse query — there, a well-tested shared transformation module and a disciplined as-of join do the same job for a fraction of the complexity. The principles (one definition, point-in-time joins, versioning) are non-negotiable; the product is optional.

Deep diveHow would you implement a point-in-time join yourself?

Keep feature values in an event-sourced table with a validity timestamp: (entity_id, feature_name, value, valid_from), appending rather than updating. Then the training join is an as-of join — for each label row with timestamp t, take the most recent feature row with valid_from ≤ t − latency, where latency accounts for how long the value takes to become observable (a value stamped at t but only landing in the warehouse at t+2h is not available at t). Pandas has merge_asof; in SQL it's a lateral join or a window function. The subtle part is that latency, not just the timestamp — which is exactly what the purge/embargo gap encodes in validation (§10.6).
