15.1 The architecture ⭐

One rule dominates this whole level: the same feature code must serve training and inference. Almost every production ML incident traces back to a violation of it.

Likely interview questions
System design⭐ Walk me through deploying a model end to end.

Frame the decision and metric → build the offline pipeline with point-in-time-correct features → validate with a split that mimics production → choose a threshold from cost or capacity → package the whole pipeline (not just the estimator) and register it with a version and lineage → deploy in shadow to check latency and stability → canary at a few percent with guardrails → A/B test against the incumbent → full rollout with a rollback path → monitor data quality, drift, prediction distribution and eventually performance → define retraining triggers and write the runbook. The two markers of a good answer: one feature code path for training and serving, and a rollback plus an on-call playbook.

DesignWhat do you log at inference time, and why?

The full input feature vector, the raw score, the applied threshold, the final decision, the model version, and a request ID that ties back to the business event. The inputs matter most: when someone disputes a decision months later, or you're diagnosing a drift alert, reconstructing the feature vector from the warehouse gives you today's values, not what the model saw — and the difference is exactly the bug you're hunting. Input logs are also what let you compute training/serving skew (§15.4) and replay traffic against a candidate model. It's cheap, and its absence turns solvable incidents into unsolvable ones.

15.2 Batch vs real-time ⭐

One question decides it: do the features exist before the request arrives?

BatchReal-timeStreaming
When it runsOn a scheduleOn requestContinuously as events arrive
ServingPrecomputed to a key-value store — prediction is an O(1) lookupFetch features, transform, predict inlineUpdate features as events land; predict on demand
RequiresAll features knowable in advanceFeatures that only exist at request timeEvent infrastructure
Cost & complexityLowestHigher — latency budget, scaling, cold startsHighest
StalenessUp to one cycleNoneSeconds
ExampleNightly churn scores for a CRMPayment fraud, ad rankingVelocity features for fraud
Most real systems are hybrid — and that's the good answer

Precompute the expensive, slow-moving parts (customer 30-day aggregates, embeddings, segment membership) into a key-value store; compute only the genuinely request-time features inline (this transaction's amount, this session's clicks); join them at serving time. You get most of real-time's freshness at most of batch's cost and simplicity. Saying “hybrid, and here's the split” is a better answer than picking one.

Likely interview questions
System designBatch vs real-time serving — how do you decide?

One question: do the features exist before the request arrives? If yes, precompute on a schedule and write to a key-value store — prediction becomes an O(1) lookup, which is cheaper, more stable and far easier to monitor. If a feature only exists at request time (this transaction's amount, this session's behaviour), you need real-time. Secondary considerations: acceptable staleness, model cost, and the p99 budget. Most real systems are hybrid — precomputed aggregates joined with a few live features — and describing the split is a better answer than choosing one.

15.3 Serving & latency ⭐

Latency budgets are decomposed, not asserted — and you report p95/p99, not p50.

Likely interview questions
System designYou have a 150 ms end-to-end budget. How do you spend it?

Decompose it: network (~15 ms), feature fetch (usually the bottleneck — 60 ms if it's a remote store), transform (~20 ms), predict (~18 ms, and often the smallest piece), post-process (~12 ms), and keep headroom for tail latency. Then optimise in cost order: precompute what you can, cache, batch the fetches into one round trip, drop features that don't earn their fetch cost, then shrink the model, then change the serving format. And budget on p95/p99, not p50 — a p50 of 40 ms with a p99 of 900 ms means thousands of users an hour waiting a second.

PracticalWould you pickle a model for production?

It works, and I'd do it with eyes open. Three issues: it's version-coupled (unpickling with a different sklearn version can fail or, worse, silently misbehave), it's an arbitrary-code-execution vector if the file is ever untrusted, and it's Python-only. Alternatives: ONNX for a portable graph with usually faster inference, at the cost of an export step that doesn't cover every estimator; or the model's native format (Booster.save_model for XGBoost/LightGBM), which is my usual choice for GBMs because it's stable across wrapper versions. Whatever I use, the deps get pinned and there's a golden-prediction test that would catch a silent change (§15.9).

15.4 Training/serving skew ⭐⭐

The same feature computed two slightly different ways in two codebases — with nothing to alert you, because both systems individually “work”.

Skew sourceConcrete exampleDetection
Different implementationsTraining computes a 30-day mean in SQL; serving reimplements it in Python with a subtly different windowLog serving features and compare distributions against training
Different null handlingSQL AVG ignores nulls; pandas mean() does too, but the denominator differs from a hand-written sum/countSame
Timezone / boundary“Yesterday” means UTC in the warehouse and local time in the serviceCompare per-hour distributions
Data freshnessTraining used a complete day; serving sees a partial one because the ETL hasn't finishedMonitor feature completeness by hour
Schema driftAn upstream column changed type or units, only one side updatedSchema tests on both paths
Point-in-time incorrectnessTraining joined today's value onto a historical row (§13.7)The worst case — it can't be seen from serving logs at all
Why the fix is architectural, not procedural

“Be careful to implement it the same way” is not a fix — it's a hope, and it fails the first time someone changes one side. The fix is to make two implementations impossible: one shared library imported by both paths, a feature store both paths read from, or a batch job whose output the API simply looks up. Then add a skew check that logs serving features and compares their distribution against training, so if it does happen you find out in a dashboard rather than in a post-mortem.

Likely interview questions
Very common⭐ What is training/serving skew and how do you prevent it?

The training pipeline and the serving path compute the same feature differently — a different window, null handling, timezone, or rounding — so the model sees a distribution it was never trained on, and nothing alerts because both systems are individually working. Prevent it architecturally: one shared code path (a library, a feature store, or a batch job whose output the API reads), because "be careful to implement it the same way" fails the first time someone changes one side. Then add a skew check comparing logged serving features against the training distribution. Its worse sibling is point-in-time incorrectness, which serving logs can't reveal at all.

DebuggingOffline AUC 0.85, production performance clearly worse, no drift alerts. What do you check?

Skew, because drift monitors compare production to production and won't catch a training/serving mismatch. Concretely: log the actual serving feature vectors and compare each feature's distribution against the training data — a shifted mean, a different null rate, or a different cardinality on one feature usually falls out immediately. Also check feature completeness by hour (a partial-day ETL gives serving a different picture than training had), and replay a sample of production requests through the training pipeline to see whether the scores match. If the scores differ for identical inputs, it's skew; if they match, look at threshold, base rate, or label definition instead.

15.5 Monitoring & drift ⭐⭐

The highest-value idea in production ML is a negative one: not every drift alert warrants a retrain.

PSI is computed exactly as Σ (aᵢ − eᵢ)·ln(aᵢ/eᵢ) over 10 quantile bins of the reference distribution, and KS as the maximum gap between the empirical CDFs. The third slider is the one that isn't in the formula: a large PSI on an unimportant feature is not an incident, and a small PSI on the feature carrying half your signal might be.

Likely interview questions
Very common⭐ How do you detect drift when labels arrive 60 days late?

Layered proxies. Input: per-feature PSI (<0.1 stable, 0.1–0.2 moderate, >0.2 significant), KS/chi-square, Jensen-Shannon and Wasserstein as smoother alternatives to KL on noisy production data — weighted by feature importance. Output: the prediction distribution and mean predicted probability, which move immediately and need no labels. Behavioural: override rate, abstention rate, analyst agreement, downstream conversion. Partial labels: any fast-resolving subset. Data quality: schema, nulls, ranges, cardinality — which in practice catches more incidents than drift statistics do. And the discipline: confirm a metric actually moved before retraining.

Very commonData drift vs concept drift — how do the responses differ?

Data/covariate drift is P(x) moving with P(y|x) stable — a new segment or channel. The model may still be valid; you might reweight, retrain on recent data, or do nothing. Concept drift is P(y|x) changing — fraudsters adapt, a recession redefines risk — and only retraining helps, possibly with new features or a new target definition. There's a third worth naming: prior/label drift, where the base rate moves, which shifts precision at a fixed threshold and is usually fixed by re-thresholding rather than retraining. Practical difference: covariate and prior drift are detectable without labels; concept drift generally is not.

DebuggingPSI = 0.35 on one feature. Do you retrain?

Not yet. PSI > 0.2 means the distribution changed significantly — it does not mean the model got worse. First: how important is that feature? A big shift on a feature contributing 1% of the signal is a log entry, not an incident. Second: did a metric actually move? Score the recent window against whatever labels have arrived, watch the prediction distribution and the override rate. Third: why did it shift — an upstream pipeline change or a genuine population change? Those have different fixes. Retraining on drifted-but-harmless data costs you churn, reproducibility and possibly performance. Not every drift alert warrants a retrain, and alert fatigue kills monitoring programmes faster than missed drift does.

15.6 Retraining triggers ⭐

Three triggers, in preference order — and one trade-off nobody mentions until it bites them.

TriggerWhen it worksRisk
Performance-triggeredLabels arrive in time to measure — the idealBy the time you can measure it, you've already been degraded for the label-delay period
Drift-triggeredThe proxy when labels are slow, with a confirmation step (§15.5)False alarms — retraining on harmless drift costs churn and reproducibility
ScheduledThe boring default that mostly worksRetrains when nothing changed; misses fast degradation between cycles
Data-volume triggered“Every 100k new labelled rows”Decouples from calendar, which suits irregular businesses
Event-triggeredA known regime change — a product launch, a policy changeRequires someone to remember to trigger it
The staleness-vs-churn trade-off

Retraining constantly sounds obviously good and isn't. Every retrain changes predictions for the same inputs, which means a customer declined today might be approved tomorrow for no reason anyone can explain; incidents become unreproducible because the model that made the decision no longer exists; and downstream thresholds calibrated to the old score distribution silently stop meaning what they meant. Against that, staleness costs accuracy. The resolution: retrain on a defensible cadence, gate every retrain behind champion/challenger comparison and a golden-set regression suite, and version every model so any past decision can be reproduced.

Likely interview questions
Very commonWhen do you retrain? What triggers it?

Three triggers in preference order: performance-triggered when labels arrive in time, drift-triggered as the proxy when they don't (with a confirmation step so you don't retrain on noise), and scheduled as the boring default that mostly works. The trade-off to name is staleness vs churn: retraining constantly makes predictions change under users for no visible reason, makes incidents unreproducible, and silently invalidates downstream thresholds calibrated to the old score distribution. So I'd gate every retrain behind champion/challenger comparison and a golden-set regression suite, and version every model so past decisions stay reproducible.

DesignRetrain on all history, or a rolling window?

Depends on whether the relationship is stable. If P(y|x) is stable and only the input mix moves, use all history — more data is better and old rows are still valid. If there's genuine concept drift, old data is actively misleading and a rolling window (or exponentially decaying sample weights, §8.9) is right. The empirical way to decide: backtest both — train on all-history and on a window, evaluate on the most recent period, and see which wins. Sample weighting is often the best of both, since it downweights rather than discarding, and the decay rate becomes a tunable parameter rather than an arbitrary cutoff.

15.7 Deployment & the feedback loop ⭐

The ladder from shadow to full rollout — and the problem that makes fraud and credit systems genuinely hard.

Likely interview questions
Very common⭐ What is the feedback-loop problem in a fraud or credit model?

The model's decisions determine the data it will be trained on next. A fraud model never observes whether the transactions it blocked were really fraud; a credit model never sees how rejected applicants would have performed (the reject inference problem). The training set becomes systematically censored, the model grows confident about a shrinking slice of the world, and offline evaluation cannot detect it because the missing data is missing from evaluation too. Mitigations: hold out a small exploration/control slice that bypasses the model, use propensity weighting on the observed data, and model the blocked population explicitly rather than dropping it.

DesignWhy bother with shadow mode if you're going to canary anyway?

Because they answer different questions and shadow is free. Shadow answers "does this survive production?" — real latency on real feature fetches, real malformed inputs, real memory at peak traffic, real distribution of missing values — none of which offline testing reproduces, and all of which are cheaper to discover when the model affects nothing. Canary answers "does it break anything when it actually decides?" — which risks real customers. Running shadow for a week catches most operational failures before any user is exposed, and it also gives you a score-distribution comparison against the incumbent, which is the best early warning that something is subtly wrong.

15.8 A/B testing a model ⭐

The statistics are standard. What makes it an ML question is everything that can invalidate the test.

Design decisionGet it rightWhat goes wrong
Randomisation unitRandomise the unit the effect acts on — usually the user, not the requestPer-request randomisation lets one user see both variants, diluting the effect and breaking independence
Sample sizeCompute it up front from the MDE, baseline rate and powerUnderpowered tests read as “no effect” when the effect exists
Primary vs guardrailOne primary metric; guardrails on latency, revenue, complaints, fairnessPicking the winning metric after the fact is p-hacking
PeekingFix the duration, or use a proper sequential testChecking daily and stopping at significance badly inflates the false-positive rate
Novelty / primacyRun at least one full business cycleEarly lift that decays; or early loss from users adapting
Network effectsCluster/geo randomisationTreatment leaks to control through the marketplace, biasing everything toward zero
Sample-ratio mismatchCheck the actual split matches the intended oneA 50/50 split that arrives 52/48 signals an assignment bug that invalidates everything
Variance reductionCUPED using pre-period dataNot using it just means a longer, more expensive test
The offline-to-online gap, stated before someone asks

Your offline metric is a proxy. A model with better AUC can lose an A/B test because it improved ranking in a region users never see, because it shifted the score distribution and the fixed threshold now behaves differently, or because the business metric depends on something the model doesn't optimise (diversity, latency, fairness of exposure). Say explicitly: “I'd confirm that the offline metric actually moves the online objective — ideally by checking historical launches — before trusting it as a launch criterion.”

Likely interview questions
System designHow do you A/B test a model? What could invalidate the test?

Randomise at the unit the effect acts on (usually the user, not the request), compute the sample size up front from the MDE and power, declare one primary metric plus guardrails (latency, revenue, complaints, fairness), and fix the duration. Invalidators: peeking and stopping at significance; novelty and primacy effects; network effects leaking treatment into control (use cluster/geo randomisation); sample-ratio mismatch, which signals an assignment bug; and choosing the winning metric after the fact. Use CUPED with pre-period data to cut variance. And state the offline-to-online gap explicitly rather than assuming better AUC means a better outcome.

Deep diveWhat is CUPED and why does it help?

Controlled-experiment Using Pre-Experiment Data. Much of the variance in an outcome metric is explained by the same user's pre-period behaviour — a heavy spender before the test is a heavy spender during it. CUPED regresses the outcome on that pre-period covariate and analyses the residual, which removes that predictable variance without biasing the treatment effect (the covariate is pre-treatment, so it can't be affected by the assignment). The practical payoff is large: variance reductions of 30–50% are common, which means the same test reaches significance in roughly half the time — or detects an effect half the size for the same duration.

GotchaYour A/B test shows treatment winning overall but losing on both mobile and desktop. What's happening?

Simpson's paradox (§2.5), and in an A/B test it almost always indicates a bug rather than a real effect — specifically a sample-ratio mismatch, where the treatment group received a different mix of mobile and desktop users than control. That means randomisation didn't work as intended, which invalidates the whole test rather than just this cut. I'd check the actual assignment ratios per segment against the intended split with a chi-square test, look for a bug in the assignment logic or in how exposure is logged, and not ship on the aggregate result until it's resolved.

15.9 Engineering hygiene

The unglamorous section that separates a system from a notebook. Interviewers ask it as “how do you make an ML pipeline reproducible?”

PracticeConcretely
Data-schema testsTypes, ranges, allowed categories, null rates, row-count bounds — run on every batch, fail loudly
Pipeline invariantsDoes fit then transform equal fit_transform? Are outputs deterministic given a seed? Does it reject unseen categories gracefully?
Golden-prediction testsA fixed set of inputs with expected outputs, checked in CI — the single cheapest way to catch a silent regression
No-network unit testsTests must not depend on a live warehouse; fixture the data
ReproducibilityPinned dependencies (a lockfile), seeded randomness, data snapshots or versioned datasets, captured environment, and lineage from a prediction back to a model, a dataset and a commit
Config over codeHyperparameters, feature lists and thresholds in versioned config, not scattered literals
Experiment trackingEvery run's params, metrics, artefacts and data version recorded automatically
DocumentationModel card, stated assumptions, known limitations, a retraining runbook and an on-call playbook — “the model is returning nulls, now what?”
Reproducibility is more than random_state

“Set the seed” is the 2018 answer. The 2026 answer is: pinned dependencies, a versioned data snapshot, captured environment, config-as-code, recorded lineage, and golden-prediction tests — because what actually breaks reproducibility is a library minor-version bump changing a default, or the upstream table having been backfilled since you trained. Seeds only control the randomness you own.

Likely interview questions
Very commonHow do you make an ML pipeline reproducible?

"Set the seed" is the 2018 answer. The full one: pinned dependencies (a lockfile, not a range), versioned data snapshots (DVC/lakeFS-style, or an immutable partition), captured environment, config-as-code for hyperparameters and thresholds, recorded lineage from a prediction back to a model, dataset and commit, experiment tracking, and golden-prediction tests in CI. What actually breaks reproducibility in practice is a library minor version changing a default, or the upstream table being backfilled after you trained — seeds only control the randomness you own.

PracticalWhat tests would you write for an ML pipeline?

Data-schema tests on every batch (types, ranges, allowed categories, null rates, row counts) — these catch more production incidents than model monitoring does. Pipeline invariants: fit-then-transform equals fit_transform; output is deterministic given a seed; unseen categories don't crash. Golden-prediction tests: a fixed set of inputs with expected outputs, checked in CI — the cheapest possible guard against a silent regression from a library bump. No-network unit tests with fixtured data so the suite runs anywhere. And a smoke test that trains on a tiny sample end-to-end, so a broken pipeline fails in seconds rather than after an hour of training.
