8.1 Split-apply-combine ⭐⭐

groupby is three steps, and naming them is the answer: split rows into groups, apply a function to each, combine the results.

Run itgroupby.pyidle
⌘/Ctrl + Enter 

          
Expected: de 9.0, fr 5.0, uk 21.0 (sorted by key — groupby sorts by default). The named aggregation gives one clean row per region with five columns. Two keys produce a MultiIndex Series, and as_index=False flattens the keys back into columns, which is usually what you want before a merge. The lambda column arrives named <lambda_0>, which is why named aggregation is preferable.

        


        

          
Likely interview questions

          

            
Very commonExplain groupby.
              
Split-apply-combine. Split rows into groups by one or more keys; apply a function to each group; combine the results into a new object, with the group keys becoming the index.
The part worth adding is that groupby itself is lazy — it returns a GroupBy object that has done almost no work. Nothing computes until you call agg, transform, apply or a direct method like .sum(). That's why you can chain a column selection in between and only the needed column is processed.
Then the practical shape: prefer named aggregation — .agg(total=("rev","sum"), n=("rev","size")) — because it produces flat, readable column names instead of a MultiIndex you then have to flatten.

            

            
Codingcount vs size vs nunique?
              
size counts all rows in the group, including missing values, and returns a single Series. count counts non-null values, per column. nunique counts distinct values.
The distinction matters constantly: “how many orders did this customer place” is size; “how many had a recorded discount” is count on that column; “how many distinct products” is nunique. Using count where you meant size silently under-reports whenever there are nulls, which is a quiet correctness bug rather than an error.

            

          

        

      


      

        
8.2 agg vs transform vs apply ⭐⭐

        
The one-line answer that immediately signals fluency: agg reduces, transform preserves shape, apply is the flexible slow path.


        

          
choose By the shape you need out

          
agg
One row per group. Returns a scalar per group. Fast — dispatches to a C implementation for named functions like "sum".

          
transform
Same rows as the input, with the group's result broadcast back to every member. This is how you add a group statistic as a column.

          
apply
Anything. Receives the whole sub-frame, can return a scalar, Series or frame. Flexible and slow — a Python call per group.

          
filter
Keeps or drops whole groups by a predicate. Easy to confuse with row filtering.

        


        

          
Run itagg_transform_apply.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: agg gives 2 values, transform gives 5 — the shape difference in one line. The augmented frame shows the four idioms you'll actually use: group mean as a column, percent-of-group, rank within group, and demeaning. filter keeps only group b (sum 30 > 15), dropping all of a. The benchmark shows agg("mean") typically 5–30× faster than the equivalent apply, with identical results.

        


        

          
Likely interview questions

          

            
Very commonagg vs transform vs apply?
              
Shape is the deciding factor. agg reduces each group to a scalar, so you get one row per group. transform returns a value per input row, broadcasting the group result back, so the output has the same index as the input. apply receives the whole sub-frame and can return anything.
Then the practical rule: use transform when you want to add a group statistic as a column — df["grp_mean"] = df.groupby("g")["v"].transform("mean") — because it aligns automatically. Use agg for summary tables. Use apply only when the operation genuinely needs multiple columns of the group at once.
And the performance note: agg/transform with a named string function ("mean", "sum") dispatch to a Cython implementation, while apply and lambdas run Python per group — typically 5–30× slower. So .agg("mean") beats .apply(lambda s: s.mean()) for the identical result.

            

            
CodingAdd a column with each row's percentage of its group total.
              
df["pct"] = df["val"] / df.groupby("grp")["val"].transform("sum").
This is the canonical transform use case, and it's worth explaining why the alternatives are worse. With agg you'd get a 2-row result that you then have to merge or map back — more code, an extra join, and a chance of misalignment. With apply you'd be running Python per group for no benefit. transform broadcasts the group total to every member row automatically and aligns on the index.
The same pattern covers most within-group feature engineering: rank within group, deviation from group mean, share of group, group-wise z-score, and group-wise forward-fill.

            

            
GotchaWhat's the difference between groupby().filter() and boolean masking?
              
groupby().filter(fn) evaluates the predicate per group and keeps or drops every row of that group together. Boolean masking evaluates per row.
So df.groupby("user").filter(lambda g: len(g) >= 5) keeps all rows for users with at least five records, and drops all rows for the rest — you cannot express that with a row mask without first computing a group size. Conversely df[df["val"] > 10] keeps individual qualifying rows regardless of their group.
The idiom worth knowing as an alternative: df[df.groupby("user")["val"].transform("size") >= 5] does the same thing with transform, and is usually faster than filter because it avoids the per-group Python call.

            

          

        

      


      

        
8.3 groupby gotchas ⭐

        
Three defaults that silently change your results: NaN keys are dropped, categoricals produce unobserved combinations, and the output is sorted.


        

          
Run itgroupby_gotchas.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the input totals 15, but the default groupby accounts for only 9 — the two NaN-key rows are silently dropped. dropna=False recovers them. With categoricals, observed=False emits a row for the unused category z (value 0), and with two categorical keys it produces 9 rows from 2 input rows — the full cross-product, which on real categorical columns can be an accidental explosion. sort=False preserves ['z', 'a'].

        


        

          
Likely interview questions

          

            
GotchaYour group totals don't add up to the overall total. Why?
              
groupby drops rows with a missing key by default (dropna=True). Any row whose grouping column is NaN vanishes from the output entirely, with no warning — so the group sums are legitimately less than the column sum.
Fixes: pass dropna=False to get an explicit NaN group; or, better for a pipeline, fillna("UNKNOWN") on the key first so the missing category is a first-class value you can see and report on.
The habit that catches it generally: after any aggregation, assert that the total is conserved — assert result.sum() == df["val"].sum(). It's one line and it turns a silent under-count into an immediate failure. Silent row loss is the most dangerous class of pandas bug because the output still looks plausible.

            

            
GotchaYou grouped by a categorical and got far more rows than groups.
              
observed=False — historically the default — emits a row for every declared category, not just the ones present in the data. With a single key that's mildly annoying; with two or three categorical keys it produces the full cross-product of all category levels, which can be thousands of empty rows and a large memory spike.
Pass observed=True to get only the combinations that actually occur. The behaviour does have a legitimate use — guaranteeing a complete grid for a report or a pivot where you want zeros for absent combinations — but it should be a deliberate choice.
Worth pairing with: the same “empty category” issue makes value_counts() on a categorical report zeros, and appending an unseen value to a categorical column gives NaN rather than adding a category (§7.3).

            

          

        

      


      

        
8.4 merge: the five joins ⭐⭐

        
Same semantics as SQL. The interview value is knowing which rows each how keeps, and — more importantly — how to verify the result.


        

          

            
howKeepsUse when

            
              
innerOnly matching keys (default)You need both sides present

              
leftAll left rows; NaN where no matchEnriching a primary table — the common case

              
rightAll right rowsRare — usually write it as a left join the other way round

              
outerUnion of keysReconciling two sources; finding what's in one and not the other

              
crossEvery combinationDeliberate grids — parameter sweeps, date × entity scaffolds

            
          

        


        

          
Run itmerges.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: inner keeps 2 rows, left keeps 3 (with one NaN tier for customer z), right keeps 3, outer keeps 4. The indicator=True column shows both for a and b, left_only for z, right_only for c — which is exactly how you reconcile two sources. And validate="many_to_one" raises MergeError on the duplicated right key rather than silently doubling rows.

        


        

          
Likely interview questions

          

            
Very commonDifference between merge, join and concat?
              
merge is the SQL-style join: match on columns (or index), with a how parameter. It's the general tool and what you should reach for.
join is a convenience method that merges on the index by default. a.join(b) is roughly a.merge(b, left_index=True, right_index=True, how="left") — note the default is left, unlike merge's inner, which trips people up.
concat doesn't join at all — it stacks. axis=0 appends rows (aligning columns by name), axis=1 appends columns (aligning rows by index). Use it to combine chunks of the same shape, not to enrich one table with another.
The rule: matching on keys → merge; stacking like-shaped pieces → concat; index-to-index convenience → join.

            

            
PracticalHow do you verify a join did what you intended?
              
Four checks, and volunteering them is what distinguishes someone who has been burned by a join.
1. validate= — declare the cardinality you expect ("one_to_one", "many_to_one", "one_to_many") and pandas raises if it's violated. This is the single highest-value argument in merge and almost nobody uses it.
2. Assert the row count. For a left join enriching a table, assert len(out) == len(left). If it grew, your right side had duplicate keys.
3. indicator=True then inspect _merge.value_counts() — how many matched, how many are left-only. An unexpectedly large left_only count usually means a dtype mismatch or whitespace in the keys (§7.7).
4. Check null rates on the newly-added columns before and after.

            

          

        

      


      

        
8.5 Joins that explode ⭐⭐

        
The bug that has cost real companies real money: a many-to-many join silently multiplying rows, so every downstream sum is inflated and nothing errors.


        

          
Run itexplosion.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: orders total 60 over 3 rows; after the join there are 4 rows and a total of 90 — a 50% overstatement with no error and no warning. validate="many_to_one" raises MergeError: Merge keys are not unique in right dataset, and the row-count assertion also catches it. Both fixes restore the total to 60: dedupe the lookup, or aggregate the right side to one row per key first.

        


        

          
          Why this one is dangerous
          
It produces plausible wrong numbers, not a crash. Revenue is up 50%, which looks like a good quarter rather than a bug, so it can reach a dashboard and then a decision before anyone checks. Make validate= and a row-count assertion habitual on every join — they cost one line each.

        


        

          
Likely interview questions

          

            
DebugYour row count went from 1M to 4M after a join. What happened and how do you fix it?
              
A many-to-many match. The join key is duplicated on one or both sides, so pandas produces the cross-product for each key — m left rows × n right rows per key. Every downstream sum, count and average is now wrong, and nothing raised.
Diagnose: right["key"].is_unique, or right["key"].duplicated().sum(). Add indicator=True to see the match breakdown.
Fix depending on intent. If the duplicates are genuine data-quality noise, drop_duplicates(subset="key") — but decide which row wins, with a sort, rather than taking an arbitrary one. If the right side legitimately has multiple rows per key, aggregate it first to one row per key. If the many-to-many is genuinely what you want, keep it but make it explicit and re-check your aggregations.
Prevent: validate="many_to_one" plus assert len(out) == len(left) on every enrichment join.

            

            
PracticalYour left join produced far more NaNs than expected.
              
The keys aren't matching, and it's almost never a logic error — it's a data-hygiene one. In order of likelihood:
dtype mismatch — int64 on one side, float64 or str on the other (§7.3), so 1 never equals 1.0 or "1". Whitespace or case — "UK " vs "UK"; check with repr(), which makes trailing spaces visible. Leading zeros stripped by a CSV read on one side only. Different granularity — you're joining a daily table to a monthly one.
Diagnostic recipe: compare dtypes; look at set(left_keys) - set(right_keys) for a handful of examples; and use indicator=True to quantify how many rows are left_only. Fix at the source by normalising key columns — strip, casefold, cast to a declared dtype — as a documented step before any join.

            

          

        

      


      

        
8.6 merge_asof and point-in-time joins ⭐

        
Joining on “the most recent value at or before this timestamp”. This is how you build features without leaking the future, and knowing it exists is a real differentiator.


        

          
Run itasof.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the backward join pairs the 10:00:03 trade with the 10:00:00 quote (10.0), 10:00:07 with 10:00:05 (10.5), and 10:00:12 with 10:00:10 (11.0) — each trade gets the most recent prior price. The forward direction instead pairs each trade with a future quote, which is textbook leakage. The 2-second tolerance turns the 10:00:03→10:00:00 match into NaN because the quote is 3 seconds stale.

        


        

          
Likely interview questions

          

            
DesignHow do you join a fact table to a slowly-changing dimension without leaking?
              
pd.merge_asof with direction="backward" — for each fact row, take the most recent dimension record at or before its timestamp. That's a point-in-time join, and it's the correct way to build features that only use information available when the event happened.
The details that matter: both frames must be sorted on the join key or the result is silently wrong; use by= to match within an entity (per customer, per symbol); and use tolerance= so an unreasonably stale match becomes NaN rather than a misleading value.
Why it's the right answer rather than a plain merge: joining on a naive key gives every fact row the current dimension value, which encodes information from after the event. The model then looks excellent in backtest and fails in production — the classic leakage failure (§10.7).

            

          

        

      


      

        
8.7 Wide, long, and the MultiIndex ⭐

        
Reshaping between one-row-per-observation (long, tidy) and one-row-per-entity (wide). Every pipeline does this, and pivot versus pivot_table is a reliable question.


        

          
Run itreshape.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: melt turns 2 rows × 2 month columns into 4 long rows; pivot reverses it. The key contrast: pivot raises Index contains duplicate entries, cannot reshape on duplicate index/column pairs, while pivot_table aggregates them (giving 10 for the summed pair). Then stack/unstack round-trip, and the MultiIndex selection idioms — xs, tuple .loc, and slice(None) for a cross-section on the inner level.

        


        

          
Likely interview questions

          

            
Very commonpivot vs pivot_table?
              
pivot is a pure reshape: it requires the index/column pairs to be unique and raises if they aren't. pivot_table aggregates, so duplicates are combined by aggfunc (mean by default).
The practical implication: if pivot raises “Index contains duplicate entries”, that error is useful information — your data has more than one record per cell and you need to decide what that means. Reaching straight for pivot_table silently averages them, which may be right or may hide a duplicate-record bug.
So: use pivot when the data should be unique, precisely so it fails loudly if it isn't. Use pivot_table when aggregation is genuinely what you want — and then pass aggfunc explicitly rather than relying on the mean default.

            

            
ConceptualWide or long — which should you store?
              
Long (tidy) for storage and processing; wide for presentation and modelling.
Long — one row per observation, with the variable name in a column — is easier to extend (a new month is new rows, not a schema change), plays well with groupby, and is how databases and Parquet files naturally store event data. Wide is what a human wants to read and what a model wants as a feature matrix.
melt goes wide→long and pivot/pivot_table goes long→wide, so treat the wide form as a view you materialise at the end of a pipeline rather than the thing you keep. The tell that you've got it backwards: a schema migration every time a new period arrives.

            

          

        

      


      

        
8.8 Time series ⭐

        
A datetime index unlocks resampling, partial-string slicing and time-aware windows. The trap is timezones.


        

          
Run ittimeseries.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: partial-string slicing returns [2, 3, 4] (inclusive, like all label slicing) and s["2026-01"] selects the whole month. resample("3D").sum() buckets into 3-day windows. The .dt accessor adds day name, ISO week and a weekend flag. Comparing a naive to an aware timestamp raises TypeError: Cannot compare tz-naive and tz-aware timestamps — the bug that motivates “store UTC, convert at the edges”.

        


        

          
Likely interview questions

          

            
Codingresample vs groupby?
              
resample is a groupby, specialised for a datetime index: it groups into regular time bins. The differences that matter are that it produces a complete, evenly-spaced set of bins — including empty ones, which groupby would omit — and it understands frequency strings and calendar semantics like month-end.
So df.resample("ME").sum() gives a row for every month in the range even if some had no data, which is what you want for a chart or a time-series model. df.groupby(df.index.month).sum() would silently skip empty months and would also collapse different years together.
Also worth knowing: resample both downsamples (aggregate) and upsamples (then ffill/interpolate to fill), and Grouper(freq=...) lets you combine a time bin with other grouping keys in one groupby.

            

            
GotchaWhat's the timezone trap?
              
Mixing naive and aware timestamps. A tz-naive timestamp has no offset; a tz-aware one does. Comparing or subtracting one from the other raises TypeError, and — worse — concatenating frames where one side is naive can silently produce an object column that stops behaving like a datetime.
The discipline: store everything in UTC, convert to local only for display. tz_localize attaches a timezone to a naive timestamp; tz_convert changes an aware one. Getting those two confused shifts your data by hours.
Then the DST edge cases, which are the ones that actually cause incidents: on a spring-forward day some local times don't exist and on autumn-back some are ambiguous, so tz_localize raises unless you pass nonexistent= and ambiguous=. Daily aggregates in local time also have 23- and 25-hour days, which quietly breaks any “per hour” average.

            

          

        

      


      

        
8.9 Windows and lag features without leakage ⭐⭐

        
Where a pandas question becomes a machine-learning question. A rolling mean computed without shifting includes the current row — so your feature contains its own target.


        

          
Run itwindows.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: for the third row (sales 14), roll3_LEAKY is 12.0 — the mean of 10, 12 and 14 itself — while roll3_safe is 11.0, using only prior days. That one-column difference is the whole lesson. The per-group version shows the correct ordering: groupby → shift → rolling. And the last pair shows a count-based window ignoring the 18-day gap while rolling("3D") correctly isolates the 20th.

        


        

          
Likely interview questions

          

            
DesignHow do you build a rolling-average feature without leakage?
              
.shift(1) before .rolling(). By default rolling(3) includes the current row, so a “past 3 days average” feature actually contains today's value — and if you're predicting today's value, the feature contains the target. The model scores brilliantly in backtest and fails in production.
Correct form: df["sales"].shift(1).rolling(3).mean() — shift first so the window sees only prior rows.
For panel data the order matters too: sort by entity and time, group by entity, then shift, then roll — df.groupby("user")["v"].transform(lambda s: s.shift(1).rolling(3).mean()). Rolling across the whole frame without grouping bleeds one user's history into another's features.
And use rolling("3D") rather than rolling(3) when the series has gaps, so the window is three days rather than three rows.

            

            
Codingrolling vs expanding vs ewm?
              
rolling(n) — a fixed-width window; older observations drop out entirely. Use when only recent history is relevant.
expanding() — everything from the start up to now, so the window grows. Use for cumulative statistics like a running mean or a to-date total.
ewm() — exponentially weighted; all history contributes but with geometrically decaying weight, controlled by alpha, span or halflife. Use when recent data matters more but you don't want a hard cutoff, and it's smoother than a rolling mean because there's no abrupt drop-out.
All three take min_periods, which controls the warm-up: by default rolling(3) gives NaN for the first two rows, and min_periods=1 fills them with partial windows. Whether that's right depends on whether a partial window is meaningful for your feature — silently accepting the default is how you get a model that can't score the first rows of every new entity.

            

          

        

      


      

        
8.10 SQL → pandas ⭐

        
Interviewers often ask the same question twice, once in each language. Having the mapping ready is cheap, and knowing when to stay in SQL is the better answer.


        

          

            
SQLpandas

            
              
SELECT a, bdf[["a", "b"]]

              
WHERE x > 5 AND y = 'z'df.query("x > 5 and y == 'z'")

              
GROUP BY g + aggregatesdf.groupby("g").agg(...)

              
HAVING sum(v) > 10aggregate first, then filter the result

              
ORDER BY a DESC, bdf.sort_values(["a","b"], ascending=[False, True])

              
LEFT JOIN … ON kdf.merge(o, on="k", how="left")

              
ROW_NUMBER() OVER (PARTITION BY g ORDER BY t)df.groupby("g")["t"].rank(method="first")

              
SUM(v) OVER (PARTITION BY g)df.groupby("g")["v"].transform("sum")

              
LAG(v) OVER (PARTITION BY g ORDER BY t)df.sort_values("t").groupby("g")["v"].shift(1)

              
COUNT(DISTINCT x)df["x"].nunique()

              
UNION ALLpd.concat([a, b], ignore_index=True)

            
          

        


        

          
Run itsql_to_pandas.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the GROUP BY + HAVING keeps both regions (uk 40, de 45). The window-function block adds row_num, group total, previous value, running total and percent-of-group — the five window operations that cover most SQL translations. Top-1-per-region returns the 30.0 uk row and the 25.0 de row.

        


        

          
Likely interview questions

          

            
CodingTranslate ROW_NUMBER() OVER (PARTITION BY g ORDER BY t).
              
df.sort_values(["g","t"]).groupby("g").cumcount() + 1, or df.groupby("g")["t"].rank(method="first").astype(int).
The distinction worth drawing, because it's the follow-up: rank(method="first") mirrors ROW_NUMBER (arbitrary but distinct ranks for ties), method="min" mirrors RANK (ties share the low rank, gaps after), and method="dense" mirrors DENSE_RANK (ties share, no gaps). Getting the tie semantics right is usually the actual point of the question.
And the general mapping to state: SQL window functions correspond to groupby().transform(), shift(), rank() and cumsum() — all the ones that preserve row count, which is exactly what a window function does.

            

            
DesignWould you do this in SQL or pandas?
              
SQL wherever the data lives in a database — push filtering, joining and aggregation to the engine so you move less data over the wire, and let the query planner and indexes do their job. Pulling a hundred million rows into pandas to group them is the classic mistake.
pandas for what SQL is awkward at: iterative and exploratory work, complex reshaping, anything feeding directly into scikit-learn, and custom Python logic that isn't expressible as a UDF.
The 2026 answer that shows range: for a large local file, DuckDB lets you write SQL directly against a DataFrame or a Parquet file, out-of-core and multi-threaded, so the choice isn't binary any more. And Polars gives you a lazy, query-optimised DataFrame API. Naming these — and saying you'd benchmark rather than assume — is stronger than defending either tool.
