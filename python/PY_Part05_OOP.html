5.1 Classes and the instance dict

An instance is mostly a dictionary with a type pointer. Attribute lookup walks instance → class → base classes, and knowing that order explains almost every OOP surprise.

Run itinstances.pyidle
⌘/Ctrl + Enter 

          
Expected: the instance dicts hold only name; library lives on the class and is the same object for both. Assigning a.library creates an instance attribute that shadows the class one — b and Model are untouched — and del a.library reveals the class attribute again. The two describe calls show a bound method is the same code object with self supplied.

        


        

          
Likely interview questions

          

            
ConceptualWhat is self, and why is it explicit?
              
self is just the first parameter, holding the instance. A method is an ordinary function stored on the class; accessing it through an instance creates a bound method that passes the instance automatically, so a.describe() is Model.describe(a).
It's explicit because Python's design favours no hidden magic — and because it makes several things natural that are awkward elsewhere: you can call the unbound function directly, pass a bound method as a callback and have it carry its instance, and define methods outside the class body then attach them.
The corollary worth adding: the name self is a convention, not a keyword — but never rename it, because every tool and reader assumes it.

            

            
Deep diveHow does Python find an attribute?
              
Roughly: data descriptors on the type → the instance __dict__ → the type and its MRO → __getattr__ as a last resort. The practically important part is that the instance dict comes before the class, which is why assigning a.library = x shadows a class attribute for that instance only.
The exception people trip over: @property is a data descriptor, so it takes precedence over the instance dict. That's exactly why a property can intercept assignment and validate it — otherwise obj.x = 5 would simply write to the instance dict and bypass your setter.

            

          

        

      


      

        
5.2 Class vs instance attributes ⭐⭐

        
The OOP twin of the mutable-default-argument trap from §1.5. A mutable class attribute is shared by every instance, and it is asked precisely because it tests whether Part 1 landed.


        

          
Run itshared_state.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: both a.history and b.history print ['a-1', 'b-1'] — one shared list. Fixed keeps them separate. The Counter block shows why immutable class attributes are safe: self.total += 1 reads the class value then rebinds on the instance, so e.total is 2 while f.total and Counter.total stay 0. And dataclasses raise mutable default … is not allowed outright, which is the language protecting you from exactly this.

        


        

          
Likely interview questions

          

            
Very commonWhat's wrong with a mutable class attribute?
              
It's created once, when the class body executes, and shared by every instance — so self.history.append(x) mutates state visible to all of them. Structurally identical to the mutable default argument in §1.5: one object, many users.
Fix: initialise mutable state in __init__ (self.history = []), or in a dataclass use field(default_factory=list).
The refinement that shows real understanding: an immutable class attribute is fine, because you can't mutate it — self.total += 1 rebinds on the instance, silently creating an instance attribute and leaving the class value untouched. That asymmetry surprises people, and it's the reason class-level constants are idiomatic while class-level lists are a bug.

            

            
PracticalWhen is a class attribute the right choice?
              
For things that genuinely belong to the class, not the instance, and are immutable: constants (SUPPORTED_FORMATS = ("csv", "parquet") — note the tuple), default configuration values, a version string, or a registry populated deliberately at class-definition time.
Also for shared caches where sharing is the point, though then you want it to be explicit — a leading underscore and a comment — because a reader's default assumption is per-instance.
The test: would two instances ever want different values? If yes, it belongs in __init__. If no, and it's immutable, the class body is the right home and saves memory across many instances.

            

          

        

      


      

        
5.3 Properties ⭐

        
A property turns attribute access into a method call, which lets you validate on assignment or compute on read — without changing a single call site.


        

          
Run itproperties.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: test: 0.25 | train: 0.75, then 0.3 0.7, then a ValueError for 1.5 and an AttributeError for the read-only train_size. The last line shows the real storage is _test_size — test_size is not in the instance dict at all, because the property on the class intercepts both read and write.

        


        

          
Likely interview questions

          

            
Very commonWhat is @property for?
              
It makes a method look like an attribute, so you can add behaviour to attribute access without breaking callers. Two main uses: validation on assignment via a setter, and computed values that are always consistent because there's no stored copy to go stale.
The design argument is the one to give: in Java you'd write getters and setters from the start defensively. In Python you start with a plain attribute and promote it to a property later if you need validation — the call sites don't change, because obj.x works either way. So properties are what let you avoid speculative getters.
Read-only is the default: define only the getter and assignment raises AttributeError. And note it's a data descriptor, so it takes priority over the instance dict — that's the mechanism, not a detail.

            

            
PracticalProperty or plain method?
              
Use a property when it reads conceptually as a value and is cheap — df.shape, model.n_features, split.train_size. Use a method when it's an action, takes arguments, is expensive, or can raise for reasons unrelated to bad input.
The rule that prevents the common mistake: a property should be cheap and side-effect free. Hiding a database query or a five-second computation behind attribute access is unkind — a reader sees obj.total and assumes it's free, then puts it in a loop. If it's expensive but stable, functools.cached_property is the honest middle ground.

            

          

        

      


      

        
5.4 staticmethod vs classmethod ⭐

        
Both live on a class and neither takes self. The difference is whether they receive the class — and the useful application is alternative constructors.


        

          
compare Three kinds of callable on a class

          
instance
Receives self. Needs the instance's data. The default.

          
classmethod
Receives cls. Use for alternative constructors (from_csv, from_dict) — and it inherits correctly, returning the subclass.

          
staticmethod
Receives nothing. A plain function namespaced under the class. Use when it belongs conceptually but touches no state.

        


        

          
Run itmethods.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: three parsed rows and len: 3; True False from the static method. The key line: TimedDataset.from_csv_text(...) returns a TimedDataset with .loaded set — because the classmethod called cls(...). The Bad version returns a plain Dataset, which is exactly the inheritance bug cls prevents.

        


        

          
Likely interview questions

          

            
Very commonstaticmethod vs classmethod vs instance method?
              
Instance method takes self and uses the instance's data. classmethod takes cls — the class itself — and is used for anything that needs to construct or inspect the class. staticmethod takes neither; it's a function grouped under the class for organisation.
The killer use case for classmethod is alternative constructors: Dataset.from_csv, Dataset.from_dict. Because it calls cls(...) rather than the hardcoded class name, it returns the correct subclass when inherited — which a staticmethod or a hardcoded constructor cannot do. That's the detail that shows you've used it rather than read about it.
Real examples to cite: dict.fromkeys, datetime.fromisoformat, pd.DataFrame.from_records.

            

          

        

      


      

        
5.5 Dunder methods ⭐

        
Implementing the right dunder makes your object work with Python's built-in syntax. Six are worth knowing; the rest you look up.

Likely interview questions

          

            
Very common__repr__ vs __str__?
              
__repr__ is for developers — unambiguous, ideally valid Python that would recreate the object, and it's what the REPL, debuggers, and containers show (printing a list of objects calls repr on each element, not str). __str__ is for users — readable, possibly lossy.
The practical rule: always implement __repr__; add __str__ only when the human-facing form genuinely differs. str() falls back to __repr__, so one good __repr__ covers both.
Why it earns its keep: the default <Foo object at 0x7f…> is useless in a log, a pytest failure message, or a list of results. A five-line __repr__ saves hours of debugging, which is why it's the one dunder worth writing reflexively.

            

            
GotchaYou defined __eq__ and now your object won't go in a set. Why?
              
Because defining __eq__ makes Python set __hash__ = None, so the class becomes unhashable. That's deliberate: the contract from §1.4 says equal objects must hash equally, and Python can't infer a correct hash from your equality logic, so rather than let you violate the contract silently it removes hashing.
Fix: define __hash__ over the same fields __eq__ uses — hash((self.a, self.b)). Only do this if those fields are effectively immutable; hashing on mutable state means an object can get lost inside a set after you change it.
Which is exactly why @dataclass(frozen=True) generates both and plain @dataclass generates only __eq__ — the library is encoding the same rule.

            

            
Deep diveWhat does returning NotImplemented from __eq__ do?
              
It tells Python “I don't know how to compare with this type”, so Python tries the reflected operation on the other operand (other.__eq__(self)), and if that also declines, falls back to identity comparison — giving False rather than an error.
This is why you return NotImplemented instead of False for unknown types: returning False claims the objects are definitively unequal and prevents the other type from offering a sensible answer. It matters when comparing against a subclass or a compatible type from another library.
Note it's NotImplemented (the singleton), not NotImplementedError (the exception) — a classic confusion, and returning the exception class by mistake makes every comparison truthy.

            

          

        

      


      

        
5.6 Dataclasses ⭐⭐

        
One decorator generates __init__, __repr__ and __eq__ from annotations. For config objects and records this is the modern default.

The frozen Point is hashable and set-compatible, and assigning to it raises FrozenInstanceError. Finally kw_only rejects positional arguments.

        


        

          
Likely interview questions

          

            
Very commonWhat does @dataclass give you?
              
Generated __init__, __repr__ and __eq__ from the class's annotations — replacing the boilerplate you'd otherwise write for every record type.
Then the options that matter: frozen=True makes instances immutable and generates __hash__, so they work as dict keys and set members. slots=True drops the per-instance dict for a real memory win at scale. kw_only=True forces named arguments, which is what you want for a wide config. field(default_factory=...) for mutable defaults — and dataclasses refuse a bare mutable default, which is the language preventing §1.5's bug. __post_init__ for validation and derived fields.
Where it fits: config objects, records, small value types — anything that's mostly data. What it isn't: a replacement for a class with real behaviour, and it does not validate types at runtime (see the next question).

            

            
GotchaDoes a dataclass validate types?
              
No. @dataclass class C: x: int will accept C("hello") without complaint — annotations are metadata used to generate methods, not to enforce anything at runtime (§3.8).
If you need enforcement: use Pydantic, which reads the same annotations and validates and coerces on construction; add checks in __post_init__ for the handful of invariants you care about; or run a static type checker in CI, which catches it before runtime.
The practical division worth stating: dataclass for internal objects you construct yourself, Pydantic at boundaries where the data comes from JSON, a request, a config file, or a user — the same argument as TypedDict-versus-Pydantic in §5.7.

Likely interview questions

          

            
Designdataclass vs NamedTuple vs TypedDict vs Pydantic?
              
dataclass is the default for internal records and configs: mutable by choice, supports methods and defaults, and frozen=True/slots=True when you want immutability or memory.
NamedTuple when you want an immutable row that's also a tuple — unpackable, sortable, indexable, and cheap. Good for coordinates, small fixed records, and anything you'll zip or feed to code expecting tuples.
TypedDict when the data is already a dict — a parsed JSON row — and you want annotations without changing the runtime type. Purely a static-checking aid.
Pydantic at boundaries: API requests, config files, anything untrusted, because it's the only one that validates and coerces at runtime.
The one-line rule: dataclass inside, Pydantic at the edges, NamedTuple when it should behave like a tuple, TypedDict when it must stay a dict.

            

            
PracticalWhy not just use dicts for everything?
              
Because dicts have no contract. Four concrete costs: typos are silent (row["scroe"] is a runtime KeyError at best, a .get() returning None at worst); no autocomplete or type checking, so refactoring a field name means grepping strings; no place for behaviour, so helpers drift into unrelated modules; and memory — a dict per row is 3–4× a slotted dataclass, which matters at a million rows.
Where dicts genuinely win: keys are actually dynamic and unknown at write time, or you're passing straight through to JSON and adding a model buys nothing.
The pragmatic position: parse untrusted dicts into typed objects once, at the boundary, then work with the typed objects. That's the same argument as validating a schema at the edge of a pipeline rather than checking columns in every function.

            

          

        

      


      

        
5.8 Inheritance, MRO and composition ⭐

        
Python resolves multiple inheritance with a linearisation called the MRO. Knowing it exists matters; knowing to prefer composition matters more.


        

          
Run itmro.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the MRO is ['Job', 'LogMixin', 'CacheMixin', 'Base', 'object'] and run returns all four names — CacheMixin included, even though Job called super() once. That's the key insight: super() means “next in the MRO”, not “my parent”. The diamond prints D B C A with A exactly once. The composition version needs none of this reasoning.

        


        

          
Likely interview questions

          

            
Deep diveWhat is the MRO and what does super() actually do?
              
The Method Resolution Order is the linearised sequence of classes Python searches for an attribute, computed by the C3 linearisation algorithm. It guarantees each class appears once, subclasses precede their bases, and the order you listed the bases is respected.
The correction that scores: super() does not mean “my parent class” — it means “the next class in the MRO of type(self)”. So in a diamond, a single super().__init__() chain visits every class exactly once, which is why the shared base isn't initialised twice.
That's what makes cooperative multiple inheritance work at all — and it's also why every class in such a hierarchy must call super() and accept compatible arguments. One class that skips it breaks the chain silently.

            

            
DesignInheritance or composition?
              
Composition by default. Inheritance couples you to a base class's internals, and the coupling compounds — a change three levels up breaks a subclass nobody remembered. Composition means holding a collaborator and delegating, which you can swap, test in isolation and reason about locally.
Use inheritance when there's a genuine is-a relationship and you need polymorphism — a framework requires you to subclass (a Django model, an Exception), or you're providing several interchangeable implementations of one interface.
The test: do you want the base class's interface, or just its code? Wanting the code is the wrong reason — that's what a helper function or a composed object is for. In data pipelines specifically, composition wins almost always: a Pipeline that has a loader, a transformer and a writer is far easier to test than one that inherits from all three.

            

            
PracticalWhen do mixins become a problem?
              
When there are more than two or three, when they have state, or when their order matters and nobody documented why. The symptom is a class declaration like class Job(A, B, C, D, Base) where reordering the bases changes behaviour and no one can predict how.
Mixins work best when they are stateless, single-purpose, and independent — each adding one method that doesn't interact with the others. Once two mixins both override the same method and rely on super() chaining, you've built something that requires reading the MRO to understand, which is a maintenance cost you'll pay repeatedly.
The alternative is usually composition or a plain decorator, and it's worth saying so rather than defending the mixin design.

            

          

        

      


      

        
5.9 A sklearn-compatible estimator ⭐

        
The practical OOP question for a data scientist: can you write a class that fits into someone else's framework? There are real rules, and breaking them fails in confusing ways.


        

          
rules The scikit-learn estimator contract

          
__init__
Store parameters only — no validation, no computation, and the attribute name must match the argument name exactly. get_params introspects the signature.

          
fit
Learn from data, store results in attributes ending with an underscore (self.medians_), and return self.

          
transform
Use only the fitted attributes. Never look at the incoming data's statistics — that's how leakage happens.

          
never
Compute statistics in transform, mutate the input, or do work in __init__ — all three break clone, GridSearchCV and cross-validation.

Then get_params returns the two constructor arguments, clone produces an unfitted copy (hasattr(..., "medians_") is False), and set_params works — all for free, because the contract was followed.

        


        

          
Likely interview questions

          

            
CodingWrite a custom scikit-learn transformer.
              
Inherit from BaseEstimator and TransformerMixin — the first gives you get_params/set_params, the second gives you fit_transform free.
Then follow the contract: __init__ stores parameters only, with attribute names matching argument names exactly (that's how get_params introspects them, and mismatching them breaks clone). fit(X, y=None) learns and stores state in trailing-underscore attributes and returns self. transform(X) uses only that fitted state and doesn't mutate the input.
The two mistakes to call out because they're the ones that actually happen: doing validation or computation in __init__ (breaks clone and therefore GridSearchCV), and computing statistics inside transform — which silently leaks test information into your features (§10.7).

            

            
DesignWhy must fit return self?
              
So calls chain — est.fit(X, y).transform(X) — and so Pipeline, GridSearchCV and cross_val_score can treat every step uniformly. Those internals do est = est.fit(...); a fit that returns None silently replaces your estimator with None, and the error surfaces much later as 'NoneType' object has no attribute 'transform'.
It's a convention rather than a language requirement, which is precisely why it's asked — it tests whether you've read the estimator contract or just copied a class skeleton.

            

            
GotchaYour transformer works alone but fails inside GridSearchCV. Why?
              
Almost certainly a clone problem. GridSearchCV clones the estimator for every fold and parameter combination, and clone works by calling get_params() and passing the result to __init__. So it breaks if: your __init__ renames or transforms an argument before storing it; your __init__ computes something that the cloned copy then lacks; you use *args/**kwargs in the signature (nothing to introspect); or you stored fitted state without a trailing underscore, so clone doesn't know to drop it.
Diagnose it directly: call sklearn.base.clone(est) yourself and see what raises. Better still, run sklearn.utils.estimator_checks.check_estimator, which tests the whole contract for you — mentioning that tool is a strong signal.
