7.1 Series, DataFrame, and the index ⭐⭐

A DataFrame is a dict of Series that share one index. Almost every pandas surprise is really an index surprise, so start here.

Run itanatomy.pyidle
⌘/Ctrl + Enter 

          
Expected: pandas 3.0.2, the frame, and dtypes float64 / int64 / str — note city is str, not object, which is the pandas 3.0 default (§7.3). df['price'] is a Series; df[['price']] is a one-column DataFrame — the single-versus-double bracket distinction. set_index('city') then .loc['de', 'qty'] returns 2.

        


        

          
Likely interview questions

          

            
Very commonWhat is a DataFrame, really?
              
A dict of Series sharing one index. Each column is a separate, typed, contiguous buffer; the index is a shared label array that every column aligns to.
Two consequences follow, and they explain a lot of the rest of pandas. Because storage is column-oriented, whole-column arithmetic is one C loop over contiguous memory and is fast, while iterating rows touches every buffer and constructs a Series per row — which is why iterrows is so slow (§9.3). And because the index is shared and meaningful, operations align on it automatically, which is the source of both pandas' power and its most confusing behaviour.
The habit to state: think in columns, not rows. Nearly every pandas performance problem is someone thinking of a frame as a list of records.

            

            
Codingdf['col'] vs df[['col']]?
              
Single brackets return a Series (1-D, no column name in the shape); double brackets pass a list of columns and return a DataFrame, even with one element.
It matters more than it looks. scikit-learn generally wants 2-D for X and 1-D for y, so X = df[['feature']] and y = df['target'] is the correct pairing — getting it backwards produces shape errors, or worse, a silent broadcast (§6.7). Series and DataFrame also have different methods and different .apply semantics, so a function written for one can behave oddly on the other.

            

          

        

      


      

        
7.2 Index alignment ⭐

        
pandas aligns on the index before doing arithmetic. This is a feature, and it is also the source of mysterious NaNs and duplicated rows.


        

          
Run italignment.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: a + b gives NaN for w and x (present in only one side) and values for y, z — the union of indexes. df["scaled"] is NaN for the first two rows because the filtered Series only had index 2 and 3. In df2, the label-based assignment is all NaN (no index overlap) while .to_numpy() works positionally. And duplicate labels produce four rows from two — alignment does a cross-product on repeated labels.

        


        

          
Likely interview questions

          

            
DebugYou assigned a column and got NaNs. Why?
              
Index alignment. Assigning a Series to a DataFrame column matches on the index, not on position. If the Series came from a filtered frame, its index has gaps — so the rows that were filtered out get NaN.
Three fixes, each appropriate in different situations. .to_numpy() (or .values) to force positional assignment — correct only if you're certain the order matches. .reset_index(drop=True) on both sides before combining. Or, best, don't filter then reassign — compute on the whole frame with np.where or a masked .loc assignment, so alignment is never in question.
The framing that shows understanding: alignment is a feature — it's what makes df['a'] / df['b'] safe across differently-ordered frames — and this bug is that feature meeting an unintended index.

            

            
GotchaYour row count went up after an operation you thought was elementwise.
              
Duplicate index labels. When aligning, pandas matches every occurrence of a label on the left with every occurrence on the right — so two "k" rows meeting one "k" row gives two, and two meeting two gives four. It's the same cross-product behaviour that makes many-to-many joins explode (§8.5).
Diagnose with df.index.is_unique or df.index.duplicated().sum(). Fix by resetting the index, aggregating to make labels unique, or being explicit about the join you actually wanted.
The habit worth stating: assert the row count after any align, merge or concat. It's one line and it catches this class of bug at the point it happens rather than three transformations later.

            

          

        

      


      

        
7.3 dtypes after pandas 3.0 ⭐⭐

        
A genuine currency question for 2026. pandas 3.0 changed the default string dtype, which invalidates a lot of muscle memory and a lot of existing code.


        

          
changed What pandas 3.0 (Jan 2026) did to dtypes

          
strings
Inferred as str, not object. Backed by PyArrow when installed. So df.dtypes == "object" checks now miss your string columns.

          
datetimes
Default resolution is microseconds, not nanoseconds — so dates before 1678 and after 2262 no longer overflow.

          
copy-on-write
The only mode. See §7.5 — this is the big one.

          
removals
Everything deprecated in 2.x is gone. The upgrade path is 2.3 → fix all warnings → 3.0.

        


        

          
Run itdtypes.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the string Series reports dtype str and s.dtype == object is False — that single line is why 3.0 broke a lot of code. category cuts the 120k-element string Series to a fraction of its memory. pd.Series([1, 2, None]) silently becomes float64 while dtype="Int64" stays integer with pd.NA. And the 1600 date parses without an out-of-bounds error, thanks to the microsecond default.

        


        

          
Likely interview questions

          

            
ModernWhat changed about dtypes in pandas 3.0?
              
Strings get a dedicated str dtype by default, backed by PyArrow if it's installed and falling back to NumPy object storage if not. Previously every string column was object dtype — a column of pointers to individual Python string objects, which was slow and memory-hungry.
The breaking part, and the reason to know this: any code checking df.dtypes == "object" or select_dtypes("object") to find string columns now misses them. That pattern is extremely common in feature-engineering code, so it's a real upgrade hazard.
Also in 3.0: datetime defaults to microsecond resolution rather than nanosecond, which removes the old 1678–2262 date range limit; Copy-on-Write became the only mode (§7.5); and everything deprecated in 2.x was removed. The recommended path is upgrade to 2.3 first, clear every warning, then move to 3.0.

            

            
PracticalWhen would you use the category dtype?
              
For low-cardinality columns — a few hundred distinct values or fewer across many rows. It stores the distinct values once and the column as small integer codes, so a country column over ten million rows goes from hundreds of megabytes to a few.
It also makes groupby and merges on that column faster, and it lets you declare an ordering (CategoricalDtype(ordered=True)), which makes < comparisons and sorting meaningful for things like ordinal survey responses.
The gotchas worth naming: appending an unseen value gives NaN rather than adding a category; groupby on a categorical includes unobserved combinations by default, which can produce a surprisingly large result (use observed=True); and for a high-cardinality column like a user id, categorical is worse than a plain string because the category mapping is nearly as big as the data.

            

            
GotchaWhy did your integer column become float?
              
Because it contains missing values, and the classic NumPy-backed int64 dtype has no representation for NaN. pandas silently upcasts to float64 so it has somewhere to put the NaN. The visible symptoms are ids printing as 12345.0 and, past 2⁵³, actual precision loss on large integer ids.
Fix: use the nullable integer dtype — Series([...], dtype="Int64") with a capital I — which stores an integer array plus a separate boolean mask and uses pd.NA. Or specify dtypes at read time so it never happens.
Same trap applies to booleans: a bool column with missing values becomes object, and the nullable equivalent is "boolean". This is the single most common cause of “my join key stopped matching” — one side is int64, the other became float64.

Expected: loc[11] and iloc[1] both return the second row, for different reasons. Critically, loc[10:12] returns three rows (label slicing is inclusive) while iloc[0:2] returns two. Then the ambiguity demo: df['v'] selects a column but df[0:2] selects rows — the same operator switching axis based on the argument type, which is exactly why explicit accessors exist.

        


        

          
Likely interview questions

          

            
Very common.loc vs .iloc?
              
.loc selects by label (and accepts boolean masks); .iloc selects by integer position. They coincide only when the index happens to be a default RangeIndex, which is why the difference is invisible until it bites.
The detail that scores: .loc slices are inclusive of the endpoint, .iloc slices are not. df.loc[10:12] returns three rows; df.iloc[10:12] returns two. That's deliberate — with arbitrary labels there's no “next” label to stop before.
Then explain why plain df[...] should be avoided beyond column access: it's overloaded — df['v'] takes a column, df[0:2] takes rows, df[mask] takes rows. Same syntax, different axis, decided by the argument's type. Being explicit removes a whole class of confusion, which is why .loc is the recommended default for anything beyond grabbing a column.

            

            
CodingHow do you conditionally update a column?
              
df.loc[mask, "col"] = value. A single .loc call handles both the row selection and the column, so pandas knows unambiguously that you are assigning into the frame.
What not to write: df[mask]["col"] = value. That's chained assignment — two separate indexing operations — and under pandas 3.0's Copy-on-Write it silently does nothing (§7.5). Before 3.0 it sometimes worked and sometimes didn't, which is what SettingWithCopyWarning was warning about.
Alternatives worth naming: np.where(cond, a, b) for a two-branch assignment over the whole column, df["col"].mask(cond, value), and df.assign(col=...) when you want to stay in a method chain rather than mutate.

            

          

        

      


      

        
7.5 Copy-on-Write and the end of SettingWithCopyWarning ⭐⭐

        
The single most valuable currency answer in this subject. pandas 3.0 made Copy-on-Write the only mode, which removed SettingWithCopyWarning entirely and changed what chained assignment does.


        

        

          
Run itcopy_on_write.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the chained assignment leaves a as [1, 2, 3, 4] — completely unchanged, and with no warning at all. The .loc form then sets rows 1–3 to 100. Mutating the filtered sub leaves the parent untouched, which is why the defensive .copy() after a filter is now redundant. The hasattr check should report False or a deprecated shim, because the warning class was removed in 3.0.

        


        

          
Likely interview questions

          

            
ModernWhat is SettingWithCopyWarning and how do you fix it?
              
Lead with the currency, because this is the version of the question that shows you're current: in pandas 3.0 it no longer exists. Copy-on-Write became the only mode in January 2026, and because indexing results are now unambiguously copies, the warning had nothing left to warn about and was removed.
What it was: pandas couldn't tell whether df["a"][mask] = x would modify the original or a temporary, because df["a"] might return a view or a copy depending on dtypes and internal block layout. The warning meant “this might not do what you want” — and it fired on correct code too, which is why everyone learned to ignore it.
What happens now: chained assignment reliably does nothing — it writes to a temporary that's immediately discarded. Silent, but at least consistent, and the fix was always the same: one .loc call, df.loc[mask, "a"] = x.

            

            
ModernWhat is Copy-on-Write, and is it faster or slower?
              
Faster, which surprises people who assume “more copies”. Under CoW, every indexing result behaves as an independent copy, but pandas doesn't actually duplicate the data until something writes to it. So reads share memory and only a genuine mutation triggers the copy.
The performance win is that it lets pandas remove defensive copies it previously made because it couldn't prove they were unnecessary. And it lets you remove the .copy() calls that were idiomatic after every filter — under CoW those force an eager copy that would otherwise never have happened, so deleting them is a real memory improvement on upgrade.
The behavioural change to be precise about: mutating a slice can no longer reach back into the parent frame. Any code that relied on that — deliberately or accidentally — silently stops working, which is the main upgrade risk.

            

            
GotchaDoes inplace=True save memory?
              
Generally no — and this is a persistent myth worth correcting. Most inplace operations still build a new object internally and then rebind it, so peak memory is similar. What inplace=True saves is a variable name, not memory. Under Copy-on-Write it's even less meaningful, and the pandas team has been steadily deprecating it.
The practical arguments against it: it returns None, so it breaks method chaining; it mutates a frame someone else may hold a reference to, which is the §1.1 aliasing problem; and it makes code harder to reason about because you can't see the transformation as a value.
Prefer df = df.rename(...) or a chain with .assign() and .pipe(). If you genuinely need to reduce peak memory, the levers are dtypes, usecols, chunking and dropping columns early (§9.4) — not inplace.

            

          

        

      


      

        
7.6 Missing data ⭐

        
Three sentinels, several dtypes, and a choice of strategies. The interview answer is about why the values are missing, not which function fills them.


        

          
Run itmissing.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: two missing in each column; int stays Int64 with pd.NA rather than upcasting to float. np.nan == np.nan is False, hence .isna(). ffill carries values forward, the median fill uses 2.0, and interpolate gives [1.0, 2.0, 3.0, 3.0]. The num_was_missing indicator is the part worth internalising: it preserves information that any imputation destroys.

        


        

          
Likely interview questions

          

            
Very commonHow do you handle missing values?
              
Start with the question that determines everything else: why are they missing? Missing completely at random, missing at random given other features, or missing not at random — where the missingness itself carries signal (income unreported by high earners, a sensor that fails under load).
Then the options. Drop rows only when few and plausibly random — quantify the loss first. Drop the column if mostly empty. Impute: median for skewed numerics, mean for symmetric, mode or an explicit "UNKNOWN" category for categoricals, forward-fill for time series, and model-based (IterativeImputer, KNN) when the pattern is structured.
The two points that make this a senior answer. Add a missingness indicator — col_was_missing — because for MNAR data that flag is often more predictive than the imputed value. And fit the imputer on train only, inside a Pipeline, or you've leaked test statistics into training (§10.7).

            

            
ConceptualNaN vs None vs pd.NA?
              
np.nan is a float — an IEEE-754 value that propagates through arithmetic and is never equal to itself. It's the historical missing marker for NumPy-backed numeric columns, which is why an integer column with gaps upcasts to float64.
None is Python's null object. In an object column it can sit alongside other values; pandas usually converts it to NaN in numeric contexts.
pd.NA is the newer, dtype-agnostic sentinel used by the nullable dtypes (Int64, boolean, str). It propagates in comparisons too — pd.NA > 1 is pd.NA, not False — which is more logically consistent and occasionally surprising in boolean masks.
Practical takeaway: always test with .isna(), never == np.nan or is None; and prefer nullable dtypes when you need integers or booleans that can be missing.

            

          

        

      


      

        
7.7 Reading data properly ⭐

        
Most pipeline bugs are born at read time. Five arguments to read_csv prevent most of them — and the best answer is often “don't use CSV”.


        

          
Run itreading.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the naive read turns 01234 into the integer 1234 — a silently corrupted identifier, which is the single most common CSV bug — leaves the date as a string and the flag as text. The explicit read preserves the zipcode as "01234", parses the date, and reads yes/no as booleans. The Parquet round-trip returns every dtype unchanged, which is the argument for using it: CSV has no schema, so every read re-guesses.

        


        

          
Likely interview questions

          

            
PracticalWhat arguments do you always pass to read_csv?
              
dtype= — the big one. Without it pandas infers per column, which turns zip codes, phone numbers and zero-padded ids into integers, losing leading zeros silently. It also prevents the float64-by-default memory bloat.
usecols= — read only what you need; on a wide file this is the cheapest possible speed and memory win. parse_dates= so dates are datetimes rather than strings. na_values= because real files use "NULL", "N/A", "-", "missing". chunksize= when the file is large.
Then the answer that shows judgement: prefer Parquet. CSV has no schema, so every reader re-guesses types and every writer loses them; Parquet is columnar, compressed, stores dtypes, and supports column and predicate pushdown so you read a fraction of the bytes. Converting once at ingestion pays for itself immediately.

            

            
DebugYour join key stopped matching after a CSV round-trip.
              
Almost certainly a dtype mismatch introduced by the read. The usual suspects: one side is int64 and the other float64 (because that file had a missing value, forcing an upcast), so 1 never matches 1.0; or a numeric-looking id was read as an integer on one side and a string on the other; or leading zeros were stripped from one file and not the other.
Diagnose by comparing df.dtypes on both sides and inspecting a few keys with repr() — that reveals whitespace and quote characters that print invisibly.
Prevent it: declare key dtypes explicitly at read time (ids as str unless you do arithmetic on them), strip whitespace, and assert the expected row count after the merge (§8.5). Better still, stop using CSV for anything that travels between steps.

            

          

        

      


      

        
7.8 Duplicates and type conversion

        
Two routine operations with important arguments people forget: subset= and keep= on duplicates, and errors= on conversion.


        

          
Run itdupes.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: zero fully-duplicated rows but two duplicated on user. keep='first' and keep='last' select different rows, and the “latest per user” version sorts by ts first — that sort is the step people omit, which makes the result depend on the arbitrary input order. to_numeric(errors="coerce") gives [1.0, 2.0, nan, 4.0] while the default raises. convert_dtypes upgrades to Int64 and str.

        


        

          
Likely interview questions

          

            
CodingKeep only the most recent record per user.
              
df.sort_values("ts").drop_duplicates("user", keep="last") — and the sort is the essential part. keep="last" means “last in the current row order”, not “latest by timestamp”, so without sorting the result depends on whatever order the data happened to arrive in.
Alternatives worth naming: df.loc[df.groupby("user")["ts"].idxmax()], which is explicit about the criterion and doesn't rely on sort order; or df.sort_values(["user","ts"]).groupby("user").tail(1).
The edge case to raise unprompted: ties. If two records share the maximum timestamp, you need a documented tie-break — a secondary sort key, or an aggregation. Silently taking whichever comes first is a non-deterministic pipeline.

            

          

        

      


      

        
7.9 Method chaining ⭐

        
A readable chain replaces a stack of intermediate variables and avoids mutation entirely. pandas 3.0 adds pd.col to make it cleaner still.


        

          
Run itchaining.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: both versions produce the same result (uk 13.5, de 10.0 or similar) and identical: True. The chained form has no temporary variables and no mutation, so there's no .copy() question and no chance of a stale intermediate. The last block shows assign can reference a column it created earlier in the same call — the lambdas are evaluated in order, which is what makes multi-step feature creation readable.

        


        

          
Likely interview questions

          

            
DesignWhy prefer method chaining?
              
Four reasons. No mutation, so no aliasing questions and no defensive .copy(). No temporary names — tmp, tmp2, df_final are where stale-intermediate bugs live, especially in notebooks where cells run out of order. Reads top-to-bottom as the transformation it is, which makes review much easier. Composable — .pipe() lets you drop a tested function into the middle.
Use lambda inside .assign() and .query() so each step refers to the frame at that point in the chain rather than the original — that's what keeps it correct after a filter.
The honest limits: very long chains are hard to debug because there's no intermediate to inspect (break them at a meaningful boundary, or insert a .pipe(lambda d: (print(d.shape), d)[1]) probe), and query uses string expressions that no linter or type checker will check for you.
