1.1 Names, objects and bindings ⭐⭐

One sentence unlocks most of Python's surprises: a name is a label attached to an object, not a box containing one. Assignment moves labels; it never copies objects.

See it for yourself

Run italiasing.pyidle
⌘/Ctrl + Enter 

          
Expected: a and b start aliased, so a.append(4) changes both. b + [5] builds a new list and breaks the alias. The pair at the end is the real test: c += [3] mutates (so d sees it), while e += (3,) rebinds (so f does not) — same operator, opposite behaviour, decided entirely by mutability.

        


        

          
          += is not sugar for x = x + y
          
For a mutable target, += calls __iadd__ and mutates in place — every alias sees the change. For an immutable target there is no in-place option, so it falls back to __add__ and rebinds. This is why df += 1 and arr += 1 behave differently from df = df + 1 in ways that matter for memory.

        


        

          
Likely interview questions

          

            
Very commonIs Python pass-by-value or pass-by-reference?
              
Neither — it's pass-by-object-reference (sometimes called call-by-sharing). The function receives a new local name bound to the same object as the caller's name.
The consequence is the bit that matters, and it's the part to say next: if the function mutates the object (lst.append(x), df['col'] = ...), the caller sees it. If the function rebinds its local name (lst = [...]), the caller sees nothing, because you only moved the local label.
So “does my function affect the caller's data?” is never about Python's calling convention — it's about whether you mutated or rebound. That's why a function taking a DataFrame should either return a new one or be explicitly documented as mutating in place, never leave it ambiguous.

            

            
Gotchac = [1,2]; d = c; c += [3] — what is d?
              
[1, 2, 3]. For a list, += invokes __iadd__, which extends the list in place, so both names still point at the same mutated object.
Contrast with c = c + [3], which builds a new list and rebinds only c, leaving d == [1, 2]. And contrast with tuples, where e += (3,) must rebind because there is no in-place option.
This matters beyond trivia: with NumPy and pandas, arr += 1 mutates the buffer (cheap, but visible to every view) while arr = arr + 1 allocates a whole new array (safe, but doubles peak memory). Choosing between them is a real decision on a large frame.

            

            
ConceptualWhy does this matter for data-science code specifically?
              
Because DataFrames and arrays are large mutable objects that get passed between functions constantly. Three concrete failure modes:
1. A helper mutates its caller's frame. def clean(df): df['x'] = df['x'].fillna(0) silently edits the caller's data. Six months later someone runs clean() in a loop and can't work out why the “raw” frame has changed.
2. Aliasing across a pipeline. train = df; test = df then mutating one — a bug that vanishes when you look for it, because both names print the same thing.
3. Memory. Knowing that df2 = df1 costs nothing while df2 = df1.copy() doubles memory is the difference between a job that fits in RAM and one that doesn't.
The habit that prevents all three: functions return new objects, or are named for the fact that they mutate — never both, never silently.

            

          

        

      


      

        
1.2 Mutable vs immutable ⭐⭐

        
Mutability is the single property that decides how an object behaves in a dict, in a function call, as a default argument, and under copying. Learn the split once and a dozen questions collapse into one.


        

          

            
ImmutableMutable

            
              
int, float, complex, boollist

              
str, bytesdict

“Shallowly” immutable is the interesting case

        
A tuple guarantees that its own slots can't be reassigned. It says nothing about the objects in those slots. So t = ([1], [2]) is an immutable container of mutable lists: you cannot do t[0] = ..., but t[0].append(9) works fine. That's also why such a tuple is unhashable — see §1.4.


        

          
Run itmutability.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: ([1, 9], [2]), then a TypeError: 'tuple' object does not support item assignment, then two different ids for s, then 01234. The last block is the practical lesson: because str is immutable, s += x in a loop copies the whole string every iteration — O(n²) — so you accumulate into a list and join once.

        


        

          
Likely interview questions

          

            
Very commonWhat's the difference between mutable and immutable, and why should I care?
              
Mutable objects can be changed in place, keeping their identity; immutable objects cannot, so any “change” produces a new object.
Then give the four consequences, because that's what makes it an answer rather than a definition. Hashability: only immutables (with immutable contents) can be dict keys or set members. Aliasing: mutating an object is visible through every name bound to it. Default arguments: a mutable default is created once and shared across calls. Performance: immutability makes string concatenation in a loop quadratic, and makes tuples cheaper to hash and safe to share.
A tuple is only shallowly immutable — ([1],) can have its inner list mutated, which is why it's unhashable.

            

            
CodingWhy is building a string with += in a loop a bug?
              
Because strings are immutable, so each s += x allocates a new string and copies everything accumulated so far. Over n iterations that's 1 + 2 + … + n character copies — O(n²). On a million rows it's the difference between a second and several minutes.
The fix is to accumulate into a list and join once: parts.append(x) then "".join(parts), which is O(n) with a single final allocation. For file output, writing incrementally to the file handle is better still, since you never hold the whole thing.
Worth adding: CPython has an optimisation that sometimes makes s += x look linear when the string has a refcount of 1, which is exactly why people don't notice the bug until it's in a hot loop with an extra reference floating around. Don't rely on it.

            

            
ConceptualAre NumPy arrays and DataFrames mutable?
              
Yes, both. An ndarray's buffer can be written in place, and a DataFrame's columns can be assigned. That's precisely why views, aliasing and copy semantics dominate Parts 6 and 7 of this guide.
Two refinements worth volunteering. NumPy arrays have a .flags.writeable switch you can set to False to get an immutable view — useful for handing data to a function you don't trust. And in pandas 3.0, Copy-on-Write means the result of an indexing operation always behaves as an independent copy, so mutating a slice can no longer reach back into the parent frame. The objects are still mutable; what changed is that the aliasing is no longer implicit.

            

          

        

      


      

        
1.3 is vs == ⭐

        
== asks “same value?”; is asks “same object?”. The trap is that for small integers and short strings, is often appears to work — because CPython caches them.


        

          
Run itidentity.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: 256 is 256 → True (cached). 257 is 257 and 1000 is 1000 may print True or False depending on whether the compiler folded the constants into the same code object — which is the whole point: it's an implementation detail, so never depend on it. Lists are always separate objects. The NumPy line shows why: == on an array returns an array of booleans, so if arr == 2 raises “truth value of an array is ambiguous”.

        


        

          
          The rule
          
Use is only for singletons: is None, is not None, and occasionally a sentinel object you created yourself. Everything else uses ==. In pandas, use .isna() rather than either — np.nan == np.nan is False and x is np.nan is a coin flip.

        


        

          
Likely interview questions

          

            
Very commonDifference between is and ==?
              
== compares value by calling __eq__; is compares identity — whether both names point at the same object, equivalent to id(a) == id(b).
The part that scores: explain why beginners think is works on numbers. CPython interns small integers (roughly −5 to 256) and some short strings, so 256 is 256 is True while 1000 is 1000 may or may not be, depending on constant folding. That's an implementation detail, not a language guarantee — CPython, PyPy and different Python versions differ.
The rule: is only for singletons (None, True, False, your own sentinels), == for everything else.

            

            
GotchaWhy does if df == None break, and what's correct?
              
Two separate problems. First, == against a DataFrame or array is elementwise, so it returns a whole frame of booleans, and putting that in an if raises “The truth value of a DataFrame is ambiguous”. Second, even for scalars, == None is the wrong idiom because a custom __eq__ can override it.
Correct forms: if df is None: to test for the object being absent; if df.empty: to test for no rows; df.isna() for missing values elementwise. And for NaN specifically, never use == — np.nan == np.nan is False by IEEE-754 design, which is exactly why .isna() exists.

            

          

        

      


      

        
1.4 Hashability ⭐

        
Why can a tuple be a dict key but a list can't? Because a dict needs the key's hash to stay constant for as long as it's in the dict — and a mutable object can't promise that.


        
The contract has three clauses: an object is hashable if it implements __hash__; objects that compare equal must have the same hash; and the hash must not change during the object's lifetime. A list could be mutated after insertion, which would strand it in the wrong bucket — so list.__hash__ is deliberately None.


        

          
Run ithashability.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: tuples and frozensets hash; lists raise unhashable type: 'list'; a tuple containing lists also raises, which is the point of “shallowly immutable”. The dict literal collapses to {1: 'bool'} — because 1 == 1.0 == True and they all hash to 1, so each assignment overwrites the same slot while keeping the first key. That's a genuine trap when you build a dict from mixed-type values.

        


        

          
Likely interview questions

          

            
Very commonWhy can't a list be a dictionary key?
              
Because a dict stores each key in a bucket chosen from its hash, and it needs that hash to remain constant while the key is in the dict. A list is mutable, so mutating it after insertion would change its hash and leave it unfindable — the entry would be in the wrong bucket, and lookups for the “same” list would miss.
Rather than allow that corruption, Python sets list.__hash__ = None, so the failure is an immediate TypeError: unhashable type: 'list' instead of a silent data bug.
Use a tuple instead — and note that a tuple containing a list is also unhashable, because hashing is recursive. If you need a set of sets, that's what frozenset is for.

            

            
Deep diveWhat's the __hash__/__eq__ contract?
              
Three rules. Equal objects must have equal hashes — if a == b then hash(a) == hash(b), or dict lookups become unreliable. The hash must be stable for the object's lifetime. And unequal objects may share a hash — that's just a collision, which the dict resolves by comparing with ==.
The practical consequence for your own classes: if you define __eq__, Python sets __hash__ to None and your class becomes unhashable. You must define __hash__ too, typically as hash((self.a, self.b)) over the same fields __eq__ uses. This is exactly why @dataclass(frozen=True) gives you both for free and plain @dataclass gives you only __eq__.

            

            
GotchaWhat does {1: 'a', True: 'b', 1.0: 'c'} evaluate to?
              
{1: 'c'} — one entry. Because 1 == True == 1.0 and all three hash to the same value, each assignment overwrites the same slot. The value becomes the last one written, but the key stays the first one inserted, which is why it prints as 1 rather than 1.0.
Where this actually bites: building a lookup keyed on a column that mixes int and float (very easy after a pandas operation that upcasts), or keying on a flag column that is sometimes 1 and sometimes True. You silently lose entries. The fix is to normalise key types explicitly before building the dict.

            

          

        

      


      

        
1.5 The mutable default argument trap ⭐⭐

        
Close to a guaranteed question. Default values are evaluated once, when the function is defined — not on each call. A mutable default is therefore shared state across every call.


        

          
Run itmutable_default.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: ['a'], ['a', 'b'], ['a', 'b', 'c'] — the default list accumulates across calls, and broken.__defaults__ shows the shared object holding all three. The fixed version prints three independent single-item lists. The stale example is the same bug in a form people miss: a default computed at import time (a date, a config read, a time.time()) is frozen for the life of the process.

        


        

          
Likely interview questions

          

            
Very commonWhat's wrong with def f(x, acc=[])?
              
The default is evaluated once, at function-definition time, and stored on the function object in __defaults__. Every call that omits the argument gets the same list, so mutations accumulate across calls — and across different callers, and across the whole process lifetime.
Fix: use None as the sentinel and build a fresh object inside the body — if acc is None: acc = []. Use is None rather than if not acc, because an explicitly-passed empty list should be respected, not replaced.
Worth adding that the same trap catches any computed default: def f(when=datetime.now()) freezes the timestamp at import. And that the rule is only about mutable defaults — def f(n=0) or def f(s="") are perfectly safe, because rebinding an immutable can't leak.

            

            
PracticalIs there ever a legitimate use for a mutable default?
              
Rarely, and always deliberately. The one idiom you'll see in real code is a memo cache: def f(n, _cache={}): exploits the shared default as per-function persistent storage. It works, but functools.lru_cache does the same job with a documented API, thread safety and cache statistics, so prefer that.
The tell that it's deliberate rather than a bug is the leading underscore on the parameter name and a comment saying so. If you see a mutable default without both, treat it as a bug.

            

          

        

      


      

        
1.6 Copies: none, shallow, deep ⭐⭐

        
Three distinct operations that people call “copying”, with three different behaviours on nested data. This is the question that separates people who have debugged a real aliasing bug from people who have read about one.


        

        

          
Run itcopies.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: after original[0].append(99), both alias and shallow show [1, 2, 99] — only deep is clean. Then original.append(["new"]) grows original and alias but not shallow, proving the outer list really was duplicated. The final dict block is the version you'll actually hit: dict(cfg) looks like a copy and shares every list inside it.

        


        

          
Likely interview questions

          

            
Very commonShallow copy vs deep copy?
              
A shallow copy creates a new outer container holding references to the same inner objects. A deep copy recursively duplicates everything, so the result shares nothing with the original.
The practical rule: shallow is enough when the contents are immutable (a list of ints, a dict of strings); you need deep as soon as the contents are mutable and you intend to mutate them. And say which operations are shallow, because that's where people get caught: a[:], list(a), a.copy(), dict(d), {**d} and copy.copy are all shallow. Only copy.deepcopy is deep.
Add the cost, since it's a real decision: deepcopy walks the whole object graph and is slow — on a big nested structure it can dominate your runtime, and on objects holding file handles or DB connections it may fail outright. Often the better answer is to restructure so you don't need to copy at all.

            

            
GotchaIs df.copy() shallow or deep?
              
Deep by default — df.copy() is df.copy(deep=True), which duplicates the data buffers, so the result is fully independent. df.copy(deep=False) gives you a new frame object sharing the same data.
The 2026 wrinkle worth mentioning: under pandas 3.0's Copy-on-Write, the distinction matters much less than it used to, because any indexing result already behaves as an independent copy, and pandas defers the actual data duplication until something is written. So the defensive .copy() that everyone used to sprinkle after a filter is now usually redundant — it just forces an eager copy that CoW would have avoided. Dropping those is a genuine memory win when you upgrade.

            

            
CodingHow would you copy a nested dict of lists safely without deepcopy?
              
A comprehension that copies exactly the level you need: {k: list(v) for k, v in cfg.items()}. This is often the right answer because it's explicit about the depth, far faster than deepcopy, and it won't choke on unpicklable values buried somewhere in the structure.
The general principle: deepcopy is a blunt instrument that copies more than you usually need. When you know the shape, copy the shape. When you don't, prefer making the data immutable (tuples, frozen dataclasses) so copying stops being necessary at all — that's the design fix rather than the workaround.

            

          

        

      


      

        
1.7 Scope and the LEGB rule ⭐

        
Python resolves a name by searching four scopes in order: Local, Enclosing, Global, Built-in. The surprise is that assigning to a name anywhere in a function makes it local for the whole function.


        

          
Run itlegb.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: inner sees: enclosing, then a successful global read, then UnboundLocalError: cannot access local variable 'x' where it is not associated with a value. That error is the whole lesson: the x = "local" on the next line makes x local for the entire function body, so the print above it reads an unassigned local rather than the global. Finally: global count: 2 | closure counter: 1 2 3.

        


        

          
Likely interview questions

          

            
ConceptualExplain the LEGB rule.
              
Name lookup searches four scopes in order: Local (this function), Enclosing (any outer function, for nested defs), Global (module level), Built-in (len, print, …). First match wins.
The non-obvious part is that assignment determines scope at compile time, for the whole function. If a function assigns to x anywhere in its body, x is local throughout — so reading it before that assignment raises UnboundLocalError, even if a global x exists. That surprises people because reading a global without assigning works fine.
To rebind an outer name deliberately you need a declaration: global for module level, nonlocal for an enclosing function. Note you don't need either to mutate a mutable global — CACHE['k'] = v works without global, because that mutates rather than rebinds.

            

            
PracticalWhy is shadowing a builtin a problem?
              
Because it removes the builtin for the rest of that scope, and the failure often surfaces far from the cause. list = df['x'].tolist() means the next list(...) call in that scope raises TypeError: 'list' object is not callable. In a notebook, where the global scope persists across cells, the shadowing survives until you restart the kernel — which is why “it worked yesterday” is such a common notebook complaint.
The usual offenders in data code: list, dict, set, type, id, sum, max, min, filter, input, and — painfully — df reused for six different frames. A linter flags all of them for free, which is the real answer: this is a problem you solve with tooling, not vigilance.

            

          

        

      


      

        
1.8 Late binding in closures ⭐

        
A closure captures the variable, not its value at capture time. Build functions in a loop and they all see the loop variable's final value — a bug that shows up constantly when generating callbacks or transformers.


        

          
Run itlate_binding.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: broken : [2, 2, 2] — every lambda closes over the same i, which ends at 2. The three fixes all print [0, 1, 2]. The final pair makes it concrete: the “bad” scalers both divide by len("qty") = 3 giving [3.33, 3.33], while the “good” ones bind their own column and give [2.0, 3.33]. Note that c=c in the signature is the idiomatic fix, not a typo.

        


        

          
Likely interview questions

          

            
GotchaWhat does [lambda: i for i in range(3)] produce when called?
              
[2, 2, 2], not [0, 1, 2]. Closures capture the variable, not a snapshot of its value, and by the time you call the lambdas the loop has finished with i == 2. This is called late binding.
Three fixes, and it's worth knowing more than one. Default argument: lambda i=i: i — the default is evaluated at definition time, so each lambda gets its own value. (Note this is the same mechanism as the §1.5 trap, used deliberately.) functools.partial, which binds the argument explicitly. A factory function, which creates a fresh enclosing scope per call.
Where it bites in real work: generating a dict of per-column transformers, registering callbacks in a loop, or building a list of delayed jobs for joblib — all silently apply the last iteration's parameters to every task.

            

          

        

      


      

        
1.9 Memory and garbage collection

        
CPython frees objects by reference counting, with a generational collector on top to catch reference cycles. You mostly don't need to think about it — until a notebook eats 40 GB and you need to know why.


        

          

            
MechanismWhat it handlesWhat it misses

            
              
Reference countingFrees immediately when the count hits zero — deterministic and fastCycles: a.b = b; b.a = a never reaches zero

              
Generational GCPeriodically finds and breaks unreachable cyclesNothing reachable — a live reference is a live reference

              
__slots__Drops the per-instance __dict__; big win for millions of small objectsNo dynamic attributes; interacts awkwardly with multiple inheritance

            
          

        


        
The practical point for data work: the collector cannot help you if something still holds a reference. In a notebook the usual culprits are _, __ and Out[...], which keep every displayed result alive, plus intermediate frames that a cell left bound to a name. del df; gc.collect() only works if you got all the references.


        

          
Run itmemory.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: roughly 8 KB for the list of pointers plus ~28 KB for the thousand int objects — about 36 KB to hold 1000 numbers, versus 8 KB for the equivalent np.arange(1000). That gap is the entire argument for NumPy, and it's the number to quote in an interview. The __slots__ instance is meaningfully smaller than the dict-backed one, and Noisy freed prints the moment the last reference goes — showing refcounting is immediate, not deferred.

        


        

          
Likely interview questions

          

            
ConceptualHow does Python manage memory?
              
Primarily reference counting: every object tracks how many references point at it, and it's freed the instant that count reaches zero. That makes deallocation deterministic and usually immediate.
Because refcounting can't free cycles — two objects referring to each other never reach zero — CPython adds a generational garbage collector that periodically scans for unreachable cycles. Three generations, on the theory that most objects die young, so gen-0 is scanned far more often than gen-2.
Two practical notes that make this a useful answer rather than trivia: memory freed by Python often stays in the process's allocator rather than returning to the OS, which is why RSS doesn't drop after del; and the GC cannot help while something is still reachable, so a leak in Python is almost always an unintended reference, not a collector failure.

            

            
DebugYour notebook is using 40 GB. How do you find out why?
              
First, list what's actually bound: iterate globals() and report the largest objects (for frames, df.memory_usage(deep=True).sum(), since sys.getsizeof undercounts). That alone usually finds it — an intermediate frame from three cells ago still bound to tmp.
Then the notebook-specific causes: Jupyter keeps every displayed result alive in Out[...], _, __ and ___, so a frame you merely displayed is retained; %reset out or %xdel clears those. Also check for accidental copies from chained operations, and object-dtype columns holding Python strings.
Then the fixes: read with explicit dtypes and usecols; downcast numerics and convert low-cardinality strings to category; process in chunks; and del intermediates inside a function so they go out of scope automatically. The structural fix is to move the work into functions — locals are freed on return, which is exactly what a notebook's flat global scope prevents.

            

            
Deep diveWhy is a Python list of a million ints so much bigger than a NumPy array?
              
Because the list stores a million pointers (8 bytes each) to a million separate int objects, and each of those objects carries a refcount, a type pointer and variable-width digits — about 28 bytes for a small int. So you pay roughly 36 bytes per element, scattered across the heap.
A NumPy int64 array stores a million raw 8-byte integers in one contiguous buffer with a single dtype and no per-element object. That's ~8 MB instead of ~36 MB, a 4.5× memory win — and the bigger win is speed, because contiguity means the CPU cache and vectorised instructions actually work.
This is the answer to “why NumPy?” and it's worth giving in exactly these terms: no boxing, one dtype, contiguous memory. Everything in Part 6 follows from it.
