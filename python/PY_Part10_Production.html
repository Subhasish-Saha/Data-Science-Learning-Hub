10.1 From notebook to module ⭐

At four years' experience the interesting question isn't “can you write pandas” — it's “can someone else run your work next year?” That starts with getting out of the notebook.

why What a notebook makes structurally hard
order
Cells can run in any order, so state depends on your history. “Restart and run all” is the only honest test, and it frequently fails.
scope
One flat global namespace. Nothing is freed, names get shadowed (§1.7), and an intermediate from three cells ago is still holding 4 GB.
testing
No importable units, so nothing can be unit-tested. Diffs are JSON. Review is guesswork.
the fix
Extract pure functions into a module, import them into the notebook, and keep the notebook for exploration and charts.
Run itrefactor.pyidle
⌘/Ctrl + Enter

The comment at the end is the important part: taking fill as a parameter rather than computing the median inside is precisely what makes the function reusable across train and test without leakage.

        


        

          
Likely interview questions

          

            
PracticalHow do you move a notebook into production?
              
Extract pure functions into a module, then import them back into the notebook. The notebook keeps the charts and the narrative; the logic lives in importable, testable code — and crucially the notebook still works, so you don't lose the exploration.
The mechanical steps: get “Restart and Run All” passing first (if it doesn't, the notebook is already lying to you); pull each transformation into a function that takes a frame and returns a frame with no global reads and no mutation; parameterise anything hard-coded — paths, dates, thresholds — into a config; add a thin entrypoint script; write tests for the functions; pin the environment.
The design point worth stating: any statistic the transformation needs (a median, a category list, a scaler) should be a parameter, not computed inside. That's what lets the same function serve training and inference, and it's the difference between code that transfers and code that has to be rewritten.

Likely interview questions

          

            
PracticalHow do you make an environment reproducible?
              
A lockfile, committed to the repo. Declare loose intent in pyproject.toml (pandas>=3,<4) and generate a lock that pins every direct and transitive dependency to an exact version and hash — uv lock, poetry lock, or pip-compile. Installs then come from the lock, not the resolver.
Why the transitive part matters: your code pins pandas, but pandas depends on numpy, and a numpy patch release can change a numeric result. A loose requirements.txt reproduces nothing.
Beyond Python packages: pin the interpreter version; use a container when you depend on system libraries (GDAL, CUDA, a database client); and set seeds and record versions in the run artefacts (§10.8). The one-line summary: pyproject declares intent, the lockfile declares reality, and only reality is reproducible.

            

          

        

      


      

        
10.3 Config, secrets and logging ⭐

        
Three small disciplines that make the difference between a script and a job someone can operate.


        

          
Run itconfig_logging.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the config dict, then log lines at INFO, WARNING and ERROR — with the DEBUG lines absent, showing that verbosity is a runtime setting rather than a code change. The final section prints connecting to db.internal:5432/analytics with the password stripped, which is the practice: log enough to debug, never enough to leak.

        


        

          
Likely interview questions

          

            
PracticalWhy logging instead of print?
              
Levels, routing and structure. Levels let you change verbosity at runtime without editing code — DEBUG locally, INFO in production, and turn DEBUG on for one module when investigating. Handlers route output to a file, stdout or a log aggregator without touching the call sites. Records carry a timestamp, module name and level, so you can filter and alert on them.
Two mechanical details worth mentioning: use lazy formatting — log.info("n=%d", n) rather than an f-string — so the message is only built if the level is enabled; and use logging.getLogger(__name__) so the logger name reflects the module and can be configured independently.
And in a data pipeline, log the things you'll actually want at 3 a.m.: row counts in and out at each stage, the fraction of rows dropped, the config in use, and timings. Those turn “the numbers look wrong” into a specific stage.

            

            
DesignWhere do configuration and secrets belong?
              
Config outside the code, secrets outside the config. Configuration — paths, thresholds, date ranges, model hyperparameters — goes in a file or environment variables and is loaded into a single typed object (a frozen dataclass or Pydantic model) at startup. That gives you validation, one place to look, and the ability to log the whole config with the run.
Secrets come from the environment or a secret manager, are never written to a file that could be committed, and are never logged. Redact them at the boundary — log the host, not the DSN.
Two habits worth adding: make the config object frozen so it can't drift mid-run and diverge from what you logged; and fail fast at startup if a required value is missing, rather than three hours in when the write step finally needs the credential.

            

          

        

      


      

        
10.4 Testing data code ⭐⭐

        
The section most candidates have no answer for at all — which makes even a modest one stand out. Data code is testable; you just test different things.

Expected: all five tests pass — note test_nan_region_is_not_dropped only passes because revenue_by_region uses dropna=False; remove that and the test catches the silent row loss from §8.3, which is exactly what a test is for. The last block shows left.equals(right) is False for 0.1+0.2 vs 0.3 while assert_frame_equal with a tolerance passes — always compare frames with tolerances.

        


        

          
Likely interview questions

          

            
Very commonHow do you test a data pipeline?
              
Test the transformations, not the data. Each transformation should be a pure function taking a frame and returning a frame, which makes it testable with a hand-built fixture of five rows and a known answer.
Then the four layers. Unit tests on each transformation with a tiny fixture. Edge cases, which is where the value is: empty frame, all-NaN column, a single row, duplicate keys, an unseen category, a NaN group key. Invariants that must hold for any input — row count preserved, totals conserved, no nulls in a required column, ids unique. An integration test running the whole pipeline on a small golden input and comparing to a stored expected output.
Mechanics that matter: use pd.testing.assert_frame_equal with rtol rather than == (floats, §6.10); @pytest.mark.parametrize for the edge-case matrix; fixtures for shared inputs; and fix seeds so anything random is deterministic.
And the cultural half: every production bug becomes a test before it's fixed.

            

            
PracticalHow do you test something non-deterministic, like a model?
              
Separate what's deterministic from what isn't. Most of a training pipeline is deterministic given a seed: the feature transformations, the split logic, the schema of the output. Test those normally.
For the model itself, don't assert exact numbers — assert properties and bounds: the pipeline runs end to end on a small fixture; the output shape and dtypes are right; predicted probabilities lie in [0, 1]; performance on a fixed holdout is above a threshold rather than equal to a value; and a deliberately shuffled-label run performs no better than chance, which is a genuinely good test that catches leakage.
Then fix every seed and pin versions so a change in output is a signal rather than noise. And use golden files for regression: store last known-good predictions and compare with a tolerance, so an unintended behaviour change is caught even if you can't specify the right answer in advance.

            

          

        

      


      

        
10.5 Validating data at the boundary ⭐

        
Check the schema where data enters, not forty lines deep in a transformation. Fail with a message that names what was wrong.


        

          
Run itvalidation.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the good frame validates silently. The bad frame raises a single error listing all four problems at once — the missing region column (and what was actually present), the duplicate id, and the negative amount. Reporting every fault together rather than failing on the first is what makes a validator usable: one run tells you everything to fix.

        


        

          
Likely interview questions

          

            
DesignWhere and how do you validate incoming data?
              
At the boundary — immediately after reading, before any transformation. That way a schema change upstream fails with “column region is missing, got [regionx, …]” instead of a KeyError forty lines into a groupby with no indication of which step broke.
What to check: required columns present, dtypes as expected, nulls where they aren't allowed, uniqueness of keys, value ranges (a negative amount, a date in the future), and row count in a plausible band — a 90% drop in volume is a failure even if every row is individually valid.
Tools: pandera for dataframe schemas (declarative, composable, usable as a type annotation), Pydantic for record-shaped JSON, or plain assertions for something small. And report all the problems at once rather than the first, so one run tells the caller everything to fix.

            

          

        

      


      

        
10.6 Pipelines and ColumnTransformer ⭐⭐

        
A Pipeline is not tidiness — it is the mechanism that makes leakage structurally impossible rather than merely discouraged.


        

          
Run itpipelines.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: a test accuracy and five CV scores. The important structural facts: cross_val_score refits the imputer and scaler inside every fold, so no fold's statistics come from its own validation set; handle_unknown="ignore" lets the unseen city "jp" predict rather than raise; and the learned medians are inspectable via named_steps, computed from training data only.

        


        

          
Likely interview questions

          

            
Very commonWhy use a scikit-learn Pipeline?
              
Because it makes leakage structurally impossible. Every transformer's fit is called only on the training portion, so when you cross-validate, the imputer's median and the scaler's mean are recomputed inside each fold from that fold's training data alone. Do it manually and you will eventually fit a scaler on the full dataset and quietly inflate every score.
Three further benefits. One object to serialise — the fitted preprocessing travels with the model, so training and inference can't drift apart. Hyperparameter search across the whole pipeline, so you can tune the imputation strategy alongside the model with "pre__num__impute__strategy". And column-aware preprocessing via ColumnTransformer, applying different steps to numeric and categorical columns in one fitted object.
The detail that shows production experience: OneHotEncoder(handle_unknown="ignore"), so a category unseen in training doesn't crash at inference time.

            

            
CodingHow do you tune a preprocessing choice along with the model?
              
Use the double-underscore parameter path in the search grid. With Pipeline([("pre", ColumnTransformer([("num", Pipeline([("impute", …)]), cols)])), ("clf", …)]), the imputer's strategy is "pre__num__impute__strategy" and the model's regularisation is "clf__C".
Pass that grid to GridSearchCV(pipe, grid, cv=5) and every combination is evaluated with the preprocessing refitted per fold — so the comparison between imputation strategies is itself leak-free, which it wouldn't be if you preprocessed once up front.
Worth adding: you can swap whole steps, not just parameters, by putting the estimator itself in the grid ({"clf": [LogisticRegression(), RandomForestClassifier()]}), which is how you compare models on identical preprocessing.

            

          

        

      


      

        
10.7 Data leakage ⭐⭐

        
The highest-stakes section in this guide. Leakage produces a wonderful cross-validation score and a model that fails in production — and it is almost always introduced by well-intentioned preprocessing.


        

        

          
Run itleakage.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: on pure random noise, feature selection done outside the CV loop scores well above 0.5 — often 0.60–0.70 — while the honest pipeline scores ~0.50. That gap is entirely fabricated by letting the selector see all the labels, and it's the clearest possible demonstration that leakage is not a small effect. The shuffled-label check returns ~0.5, which is the sanity test to run on any suspiciously good model.

        


        

          

            
FlavourWhat it looks likeFix

            
              
Preprocessing leakageScaler / imputer / encoder fitted before the splitPut it in a Pipeline

              
Feature-selection leakageSelecting features using all the labelsSelection inside the CV loop

              
Target leakageA feature that encodes the outcome (days_until_churn)Ask “would I have this at prediction time?”

              
Temporal leakageRandom split on time-ordered data; unshifted rolling featuresTimeSeriesSplit; shift(1) (§8.9)

              
Group leakageThe same customer in train and testGroupKFold on the entity id

              
Duplicate leakageDuplicated rows split across train and testDeduplicate before splitting

            
          

        


        

          
Likely interview questions

          

            
Very commonWhat is data leakage and how do you prevent it?
              
Any information in your features that wouldn't be available at prediction time. The model learns from it, scores brilliantly in validation, and fails in production — and the code runs perfectly, which is why it survives.
Name the flavours: preprocessing (scaler or imputer fitted before the split); feature selection using all the labels; target leakage (a feature derived from the outcome, like days_until_churn); temporal (a random split on time-ordered data, or an unshifted rolling feature); group (the same customer in train and test); duplicate rows split across both.
Prevention: put all preprocessing and selection in a Pipeline so it refits per fold; choose the right splitter — TimeSeriesSplit for temporal, GroupKFold for entities; deduplicate before splitting; and audit every feature with the question “would I have this value at the moment I need the prediction?”
And the detection tests: an implausibly high score, a single feature with suspicious importance, and a shuffled-label run that should score at chance.

            

            
DebugYour model gets 0.99 AUC in CV and 0.6 in production. Diagnose it.
              
Assume leakage first — a 0.39 AUC gap is almost never distribution shift alone.
Check in this order. Feature importances: one feature dominating is the classic signature of target leakage; trace where it comes from and when it becomes available. Split strategy: was the data time-ordered and split randomly? Does the same entity appear in both sides? Were duplicates removed before splitting? Preprocessing order: was anything fitted outside the pipeline, on the full dataset? Feature timestamps: for each feature, is its value knowable at prediction time — a point-in-time join issue (§8.6)?
Then the confirming test: shuffle the labels and re-run. If accuracy stays well above chance, information is reaching the model through a channel you haven't accounted for.
And rule out the non-leakage explanations so the answer is complete: train/serve skew (features computed differently in production), a genuinely shifted population, or a label definition that differs between the training data and reality.

            

            
DesignHow do you split time-series data?
              
Chronologically — never randomly. A random split lets the model train on next month and predict last month, which is not a task it will ever face. Use TimeSeriesSplit, which produces expanding (or rolling) windows where the validation fold is always after the training fold.
Two additional requirements. A gap between train and validation if your features use a lookback window or your label has a horizon, otherwise the windows overlap and leak. And features shifted so each row uses only prior information (§8.9) — a rolling mean that includes the current row leaks the target.
If the data is both temporal and grouped — many customers over time — you need both constraints: split by time and keep each customer's history on one side where the problem demands it. And evaluate on the most recent holdout, since that's the closest analogue to production.

            

          

        

      


      

        
10.8 Reproducibility ⭐

        
Seeds are necessary but nowhere near sufficient. The honest answer names the other sources of nondeterminism.


        

          
Run itreproducible.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: identical draws from two generators with the same seed; three independent spawned streams; a short content hash; and a JSON run record. The closing list is the substance of the answer — seeds don't control thread count, GPU reductions, library versions, or anything reading the clock, which is why reproducibility needs pinned versions and a recorded fingerprint, not just seed=42.

        


        

          
Likely interview questions

          

            
PracticalHow do you make an ML experiment reproducible?
              
Four things, and seeds are only the first.
Seeds: Python's random, NumPy (prefer an explicit default_rng passed around over the global np.random.seed), PYTHONHASHSEED, your framework, and random_state= on every scikit-learn estimator and splitter.
Pinned environment: a lockfile with exact versions (§10.2) — a numpy patch release can change a numeric result.
Data versioning: a content hash or an immutable snapshot, so “same data?” is answerable. “I reran it and got a different number” is very often a changed input.
A run record: seed, versions, data hash, parameters and git commit, written alongside the output.
Then the honesty that makes it a senior answer: seeds cannot control thread count (parallel float summation order), GPU reductions, or anything reading the clock. Bit-exact reproducibility is sometimes unattainable — so also define what tolerance counts as “reproduced”.

            

          

        

      


      

        
10.9 The code-review checklist ⭐

        
What you'd look for reviewing someone else's data code. A concrete list here reads as experience, and it's a common closing question.


        

          
review In rough order of how often it matters

          
correctness
Leakage (§10.7). Joins without validate= or a row-count assertion (§8.5). groupby silently dropping NaN keys (§8.3). Unshifted rolling features (§8.9).

          
silent failure
except: pass. Filters with no count logged. fillna(0) on something where 0 is meaningful. Chained assignment that now does nothing (§7.5).

          
dtypes
Ids read as integers, losing leading zeros. object columns that should be numeric or categorical. Downcasts that can overflow (§6.3).

          
reproducibility
Unseeded randomness. Hard-coded paths and dates. datetime.now() inside a transformation.

          
performance
iterrows/apply where vectorised works (§9.2). A frame grown row by row. x in list in a loop (§2.3).

          
structure
Pure functions with a frame in and a frame out. Statistics passed as parameters. Tests for the edge cases. Logged row counts at each stage.

        


        

          
Likely interview questions

          

            
PracticalWhat do you look for when reviewing data code?
              
Correctness first, and specifically the failures that are silent. Leakage in the modelling path; joins without validate= or a row-count assertion; groupby dropping NaN keys so totals don't reconcile; rolling features without a shift. All of these produce plausible wrong numbers rather than errors, which is what makes them dangerous.
Then silent failure generally: except: pass, filters that drop rows without logging how many, fillna(0) where zero is a real value, chained assignment that under pandas 3.0 does nothing at all.
Then dtypes (ids as integers, stray object columns), reproducibility (unseeded randomness, hard-coded dates, now() inside a transformation), and only then performance.
What I'd want to see: small pure functions, statistics passed as parameters rather than computed inline, row counts logged at each stage, and tests covering the empty frame and the duplicate key. And I'd ask for a number on any claim of correctness — “how do you know?” is the most useful review comment there is.

            

            
PracticalWhat would you change about a pipeline you inherited?
              
A good answer is sequenced, not a wish list, because rewriting inherited code wholesale is how you introduce regressions.
First, make it observable: log row counts and timings at each stage, so you can see what it currently does before changing anything. Second, pin it — a lockfile, so you're debugging one variable at a time. Third, add a golden-output test on a small input, which lets every later change be verified rather than hoped about.
Then fix correctness issues (validation, leakage, silent drops), extract functions to make it testable, and only after that optimise. Performance work before you have a regression test is how a fast wrong answer replaces a slow right one.
