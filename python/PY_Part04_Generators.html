4.1 The iterator protocol ⭐

Every for loop in Python is sugar over two methods. Knowing them is what lets you answer “what's the difference between an iterable and an iterator?” crisply.

for x in obj calls iter(obj) to get an iterator, then calls next() on it repeatedly until it raises StopIteration, which the loop catches silently.

Run itprotocol.pyidle
⌘/Ctrl + Enter 

          
Expected: 10 20 30, then the StopIteration message. Countdown(4) yields [4, 3, 2, 1]. The last two lines are the lesson: the re-iterable container gives [1, 2] both times, while the self-iterating Countdown gives [2, 1] then [] — silently empty, no error. That silence is why exhausted-iterator bugs are hard to spot.

        


        

          
Likely interview questions

          

            
Very commonIterable vs iterator?
              
An iterable implements __iter__ and can produce an iterator — lists, dicts, strings, files. An iterator implements __next__ (and __iter__ returning itself) and holds the position; it is consumed as you advance it.
The consequence that matters: a list is iterable and re-iterable — iter(lst) gives you a fresh iterator each time, so you can loop over it twice. A generator is its own iterator, so once exhausted it yields nothing more, silently, with no exception.
That's the bug this question exists to test: gen = (x for x in data) then sum(gen) followed by max(gen) gives you a correct sum and then a ValueError on an empty sequence — or worse, len(list(gen)) == 0 and no error at all.

            

            
CodingWrite a class you can use in a for loop.
              
Two designs, and choosing deliberately is the answer.
Self-iterating: __iter__ returns self and __next__ advances internal state, raising StopIteration when done. Simple, but single-use — a second loop is silently empty.
Re-iterable container: __iter__ returns a fresh iterator each call, typically by delegating (return iter(self.data)) or by being a generator function. This is what you almost always want for something that models a collection.
Simplest correct version: make __iter__ a generator — def __iter__(self): yield from self.data. You get a new generator per call, so it's re-iterable, and you never write __next__ or StopIteration by hand.

            

          

        

      


      

        
4.2 Iterable vs iterator, in practice ⭐

        
The single-use nature of generators causes a specific, quiet class of bug. It is worth seeing fail.


        

          
Run itexhaustion.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: total: 6, then count: 0 and max: [] — the generator is exhausted and nothing complains. bad_stats returns {'n': 3, 'total': 0}: the len(list(...)) consumed it, so sum saw an empty stream and returned a plausible-looking zero. That's the dangerous shape — a wrong number rather than an error. good_stats and streaming_stats both give n=3, total=6.

        


        

          
Likely interview questions

          

            
GotchaWhy does my function return zero for the sum but the right count?
              
Because it was passed a generator and iterates it twice. The first pass (len(list(values))) consumes it; the second (sum(values)) sees an empty stream and returns 0 — a wrong answer with no exception, which is worse than a crash.
Three fixes, in order of preference. Make one pass do everything — accumulate count and total in a single loop; this keeps the streaming benefit. Materialise once at the top: values = list(values), correct but loses the memory advantage. itertools.tee if you genuinely need two independent passes over an unrepeatable source — but note it buffers whatever the slower consumer hasn't reached yet, so it isn't free.
The defensive habit worth mentioning: a function that needs multiple passes should document that it requires a sequence, not an iterator — or convert defensively on the first line.

            

          

        

      


      

        
4.3 Generators ⭐⭐

        
A function containing yield returns a generator: a lazy, resumable stream that holds one item at a time. The interview answer is a memory answer.


        

        

          
Run itgenerators.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the list weighs ~1.6 MB while the generator is a couple of hundred bytes — and that number does not change if you raise N. Both sum to the same value. The noisy block proves laziness: nothing prints on creation, ...started appears only on the first next. Then [0, 1, 2, 3, 4] from an infinite generator, and running means [10.0, 15.0, 20.0] from a generator holding state across send.

        


        

          
Likely interview questions

          

            
Very commonWhat is a generator and why use one?
              
A function containing yield. Calling it returns a generator object that produces values lazily: execution pauses at each yield, keeping local state, and resumes on the next next().
Give the reason as a number, because that's the answer: [x*x for x in range(10_000_000)] materialises ten million ints — hundreds of megabytes — before anything consumes them. The generator expression holds one. Peak memory goes from O(n) to O(1).
Then the three secondary benefits: you can represent infinite streams; you get early exit for free (any() over a generator stops at the first match rather than computing everything); and generators compose into pipelines where each stage still holds one item.
And the honest caveat: generators don't make the work faster, they make the memory constant — and they're single-use.

            

            
CodingList comprehension or generator expression — how do you choose?
              
Ask what happens next. If you consume it exactly once — sum, max, any, "".join, a single for loop, feeding another generator — use a generator expression. If you need to index it, take its len, sort it, iterate more than once, or hand it to something that will, use a list.
Two practical notes. When a generator expression is the only argument to a function you can drop the extra parentheses: sum(x*x for x in xs). And for small collections the difference is irrelevant — this is a decision that matters at scale, not a style rule to apply everywhere.

            

            
Deep diveWhat does yield from do?
              
It delegates to another iterable: yield from sub yields every item sub produces, and — the part people miss — also forwards send(), throw() and the sub-generator's return value back to the caller.
The obvious use is flattening a recursive structure without manual loops: a recursive generator that does yield from walk(child) for each child reads exactly like the tree it's walking. The other common use is composing pipeline stages while keeping laziness.
for x in sub: yield x is equivalent only for simple iteration; it loses the two-way protocol, which is why yield from was added rather than left as sugar.

            

          

        

      


      

        
4.4 Streaming a file too big for RAM ⭐⭐

        
The practical payoff of everything above, and a very common take-home requirement: aggregate a file larger than your machine's memory.


        

          
Run itstreaming.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the CSV, then {'uk': {'sum': 36, 'n': 3, ...}, 'de': {...}, 'fr': {...}}. The one-liner total is 90. Two chunks of 4 and 2 rows. The important structural point: memory is bounded by the number of groups, not the number of rows — so this scales to a file of any size as long as the group cardinality is manageable. That framing is what an interviewer is listening for.

        


        

          
Likely interview questions

          

            
Very commonHow do you process a 50 GB CSV on a 16 GB machine?
              
Stream it and aggregate as you go. A file object is already a lazy iterator of lines, so for line in fh never holds more than one; csv.DictReader(fh) is the same, parsed. Accumulate into a dict of running totals and counts, so memory scales with the number of groups, not rows.
Then the pandas-flavoured versions, because that's the expected follow-up: pd.read_csv(path, chunksize=500_000) gives an iterator of frames, so you aggregate per chunk and combine at the end — this lets each chunk use vectorised operations, which is usually much faster than pure-Python streaming. Read only what you need with usecols=, and specify dtype= to avoid pandas inferring float64 for everything.
And the answer that scores highest: don't do it in pandas at all. Convert to Parquet once (columnar and compressed, so a column subset reads a fraction of the bytes) and query with DuckDB or Polars, both of which stream larger-than-memory joins and aggregations natively. Recognising that the tool choice beats the technique is the senior answer.

            

            
CodingWhat can't you do in a single streaming pass?
              
Anything needing global order or the whole distribution. Exact median and other quantiles, a full sort, exact distinct counts on high cardinality, and anything requiring the last rows while processing the first.
The workarounds are worth naming: two passes if you can afford to re-read (pass one for the bounds or the group keys, pass two for the work); approximate algorithms — t-digest or reservoir sampling for quantiles, HyperLogLog for distinct counts — which give bounded error in constant memory; external sort (sort chunks, write them out, merge); or push it to a database and let a query engine handle the spilling.
Interesting sub-case: mean and variance are single-pass via Welford's algorithm, which is numerically stable — better than accumulating the sum of squares. Mentioning that is a nice signal.

Likely interview questions

          

            
GotchaHow does itertools.groupby differ from pandas.groupby?
              
Two important differences. itertools.groupby groups consecutive runs of equal keys — it does not sort — so unsorted input produces the same key multiple times. pandas.groupby collects all rows with the same key regardless of order.
And itertools.groupby is lazy and single-pass: each group is a sub-iterator that becomes invalid as soon as you advance to the next group, so list(groupby(...)) gives you keys with empty groups. You must consume each group before moving on.
Why the itertools version is still useful: it's constant-memory, so it groups a sorted stream far larger than RAM. And its run-based behaviour is exactly right for sessionisation — detecting consecutive runs in a time-ordered log is a feature there, not a bug.

Chain generators and each stage still holds one item. This is the pure-Python analogue of a lazy dataframe engine, and it reads beautifully.

            ⌘/Ctrl + Enter

The early-exit block returns the de row (amount 200) without ever touching the remaining lines — which is the property that makes lazy pipelines cheap.

        


        

          
Likely interview questions

          

            
DesignWhy build an ETL as a generator pipeline rather than a series of lists?
              
Constant memory — no intermediate stage is ever materialised, so a five-stage pipeline over a 100 GB file still holds a handful of rows. Early exit — a downstream any() or next() stops all upstream work immediately. Testability — each stage is a small function you can feed a three-item list and assert on. Composability — stages combine without knowing about each other.
The trade-offs to state, so it doesn't sound like advocacy: debugging is harder because nothing exists until consumed, and a print inside a stage fires interleaved rather than per-stage; you cannot inspect an intermediate result without materialising it; and it's single-pass, so anything needing two passes needs restructuring.
Also worth saying: for tabular numeric work, vectorised pandas or Polars beats a Python generator pipeline on speed by a wide margin. Generators win on memory and on irregular, record-shaped data — not on raw throughput over numbers.

            

          

        

      


      

        
4.7 Context managers ⭐

        
A with block guarantees cleanup, even on an exception. Writing your own with @contextmanager is a generator trick, which is why it lives in this part.

            ⌘/Ctrl + Enter
          

          

          
Expected: a timing line then the total; then [boom] … (failed) followed by propagated: expected — proving __exit__ ran and the exception still surfaced because it returned False. The @contextmanager version prints its own timing, suppress swallows the division error, and the last line prints two nested timings, inner first.

        


        

          
Likely interview questions

          

            
Very commonWhat is the with statement for?
              
Guaranteed setup and teardown. with calls __enter__ on entry and __exit__ on exit — and __exit__ runs whether the block finished normally, returned early, or raised. It's try/finally with a name and a reusable implementation.
The canonical use is files: with open(p) as fh: closes the handle even if parsing throws, whereas a bare open leaks the descriptor on the error path. Same pattern for DB connections and transactions, locks, temporary directories, and changing then restoring global state.
Two details worth adding: __exit__ receives the exception triple and its return value decides suppression — returning True swallows the exception, which you almost never want. And contextlib.ExitStack handles a variable number of managers, which is how you open N files without nesting N with blocks.

            

            
CodingWrite a context manager that times a block.
              
The generator form is the one to write, because it's four lines: decorate with @contextmanager, record t0, yield inside a try, and report in the finally.
Explain the mapping while you write it: everything before the yield is __enter__, whatever you yield becomes the as target, and everything after is __exit__. The try/finally is essential — without it, an exception in the body skips your teardown entirely.
Mention when you'd use the class form instead: when the manager needs to be re-entrant, hold inspectable state after the block (e.g. you want to read timer.elapsed afterwards), or subclass. Otherwise the generator form wins on brevity.

            

          

        

      


      

        
4.8 Exceptions in a data pipeline ⭐

        
The question is rarely “what is try/except”. It is “a row is malformed — do you skip it, fail the batch, or quarantine it?” That's a design answer.


        

          
rule The four clauses, and what each is for

          
try
Wrap the smallest possible block. A broad try hides which line failed.

          
except
Catch specific types. except Exception swallows typos, KeyboardInterrupt-adjacent bugs and real defects.

          
else
Runs only if no exception. Keeps the “happy path” out of the try, so you don't accidentally catch its errors.

          
finally
Always runs. Cleanup, metrics, releasing resources.

          
never
except: pass — the single worst line in data engineering. It converts a loud failure into silently wrong numbers.

The bad rate is 40%, which trips the threshold and reports that the batch should fail rather than publish partial results — that's the design point. The chained exception shows __cause__ preserved as ValueError, which is what raise … from … buys you in a traceback.

        


        

          
Likely interview questions

          

            
DesignA row in your input is malformed. What do you do?
              
It depends on the cost of being wrong, and saying so is the answer — this is a judgement question dressed as a coding one.
Quarantine and continue is the usual right answer for analytics: write the bad rows to a dead-letter table with the index, the raw text and the parse error, process the rest, and alert on the bad rate. That gives you a usable result today plus the evidence to fix the source.
Fail the batch when partial results are dangerous — financial reporting, regulatory submissions, anything downstream that will treat your output as complete. A silently-30%-short revenue number is worse than a failed job.
The mechanism that makes both safe is a threshold: tolerate up to X% bad rows, fail above it. Without one, “skip bad rows” means a schema change upstream can drop 90% of your data and the pipeline reports success.

            

            
GotchaWhy is except Exception: pass so bad?
              
Because it converts every failure — including your own typos, a KeyError from a renamed column, an out-of-memory condition — into silence, and the pipeline reports success with wrong numbers. In data work that's the worst possible failure mode: a loud crash gets fixed, a quiet wrong answer gets into a dashboard and then into a decision.
What to do instead: catch the specific exceptions you can actually handle; log the ones you swallow with enough context to find the record; and re-raise anything unexpected. If you truly want to ignore one specific error, contextlib.suppress(ValueError) at least says so explicitly.
The related sin worth naming: a bare except: (no exception class) also catches KeyboardInterrupt and SystemExit, so it can make a job impossible to Ctrl-C out of.

            

            
CodingWhat's else for in a try block?
              
It runs only if no exception was raised, and its purpose is to keep the happy path out of the try. If you put the success logic inside the try, you'll accidentally catch exceptions from that code too, which is how a genuine bug in your success handling gets misreported as a parse failure.
So the shape is: try the one risky operation, except the specific failures, else do the work that depends on success, finally clean up. It's a narrow tool but it makes the intent unambiguous, and it's a good detail to know because most people have never used it.
