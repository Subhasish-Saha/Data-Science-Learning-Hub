This part is where live-coding rounds are quietly won and lost. Not because anyone asks you to implement a hash table, but because the difference between a five-second solution and a five-minute one is almost always one container choice — a set instead of a list for membership, a Counter instead of a hand-rolled dict, a heapq instead of a full sort. The complexity table in §2.2 is the one piece of memorisation in this guide that genuinely pays, and §2.3 is the bug interviewers watch for you to notice unprompted.

2.1 The four-way choice ⭐⭐

list, tuple, set, dict. Most people pick by habit; the interview asks you to pick by reason. There are only three questions to answer.

The decision, in three questions

1. Do I need order and duplicates? Yes → list or tuple. No → set. 2. Do I need to look things up by a key? Yes → dict. 3. Will it change? No → tuple (hashable, cheaper, safe to share). Yes → list.

The one that earns points

Row 5 is the whole reason this question is asked. x in some_list is a linear scan. Inside a loop over m items against a list of n, that is O(n·m) — the most common accidental quadratic in data code, and the subject of §2.3.

Likely interview questions
Very commonDifference between a list, tuple, set and dict?

Give the axes rather than a list of facts: ordered?, duplicates?, mutable?, hashable?, and lookup cost.

list — ordered, duplicates, mutable, O(n) membership. tuple — the same but immutable, therefore hashable and usable as a dict key. set — unordered, unique, mutable, O(1) membership. dict — key→value, insertion-ordered since 3.7, O(1) lookup by key.

Then close with the decision rule, because that's what they're actually testing: need lookup by key → dict; need membership or dedup → set; need a fixed record or a dict key → tuple; otherwise list. And name the trap: membership on a list is a linear scan, which is where accidental O(n²) comes from.

ConceptualWhy use a tuple when a list does everything?

Four reasons, in ascending order of how much they matter. Hashability — a tuple can be a dict key or a set member, which is the only one that's a hard capability rather than a preference. Intent — a tuple signals “fixed-size record, positions mean something”, so (lat, lon) reads better than a two-element list. Safety — it can't be mutated by a function you pass it to. Slightly cheaper to construct and iterate, and smaller in memory, though rarely enough to matter on its own.

The honest caveat: if you find yourself indexing a tuple by position in more than a couple of places (row[3]), you want a NamedTuple or a dataclass instead — see §5.7.

Expected: the set lookups finish in well under a millisecond while the list lookups take hundreds of milliseconds — typically a 100–1000× gap, growing with N. Likewise popleft is near-instant while pop(0) takes hundreds of milliseconds, because each removal shifts every remaining element. Exact numbers vary with your machine and WebAssembly overhead; the ratio is the lesson.

        


        

          
Likely interview questions

          

            
Very commonWhat's the time complexity of x in list vs x in set?
              
O(n) for a list, O(1) average for a set or dict. A list has to scan element by element; a set hashes x and jumps straight to a bucket.
Add the caveats to show depth: the set case is average O(1) and amortised — pathological hash collisions degrade it to O(n), and it costs memory (a set is roughly 3–4× the footprint of the equivalent list) plus the requirement that elements be hashable.
Then the practical version: converting a list to a set once, before a loop, turns an O(n·m) scan into O(n+m). On a 100k-row filter against a 50k-item allow-list that's minutes to milliseconds — and it's a one-line change, which is why interviewers like it.

            

            
GotchaWhy is list.pop(0) a problem?
              
It's O(n): removing the first element means shifting every other element down one slot. Do that n times to drain a queue and you've written an O(n²) loop, which looks perfectly innocent.
Use collections.deque, which is a doubly-linked list of blocks and gives O(1) append, appendleft, pop and popleft. The trade is that deque[i] is O(n), so it's the right structure for a queue and the wrong one for random access.
Same reasoning applies to list.insert(0, x) and to del a[0]. If you only ever push and pop at the end, a list is already O(1) and perfectly fine.

            

            
ConceptualWhy is list.append “amortised” O(1)?
              
Because a list holds a contiguous buffer with spare capacity. Most appends just write into the spare slot — genuinely O(1). When the buffer fills, Python allocates a bigger one (growth is proportional, not fixed) and copies everything across, which is O(n) for that one append.
Because the reallocation happens geometrically rarely, the average cost per append over many appends is constant — that's what “amortised” means. The distinction matters in two real situations: a single append can occasionally be slow (which shows up as jitter in latency-sensitive code), and if you know the final size, preallocating or using array/NumPy avoids the copies entirely.

            

          

        

      


      

        
2.3 The accidental O(n²) ⭐

        
The most common performance bug in take-home submissions, and interviewers watch to see whether you spot it unprompted. It always looks like reasonable code.

Expected: the list-membership version takes on the order of seconds while the set version is a couple of milliseconds — a speedup in the hundreds or thousands, with identical results. The two follow-on blocks show the same asymptotic mistake in its other disguises: s += "x" versus join, and acc = acc + [i] versus append. All three are “rebuild the whole thing each iteration”.

        


        

          
Likely interview questions

          

            
DebugHere's a function that's slow on 100k rows. Find the problem.
              
Scan for a linear operation inside a loop — that's the shape of nearly every one of these. The four to look for, in frequency order:
1. x in some_list inside a loop → convert to a set once, outside. 2. String or list concatenation in a loop (s += ..., acc = acc + [...]) → accumulate and join, or append. 3. df.append / pd.concat per row → build a list of dicts and construct the frame once (this one is O(n²) in copies of the whole frame, so it's brutal). 4. .pop(0) or .insert(0, …) → use a deque.
Then say how you'd confirm rather than guess: time it at two input sizes. If doubling the input quadruples the runtime, it's quadratic, and you've localised the class of bug before reading another line.

            

            
PracticalWhat's the pandas version of this mistake?
              
Growing a DataFrame row by row. df = pd.concat([df, new_row]) in a loop reallocates and copies the entire frame on every iteration, so building 10,000 rows performs ~50 million row-copies. It is comfortably the slowest thing people routinely write in pandas.
The fix: accumulate plain Python (a list of dicts, or a list of small frames) and construct once — pd.DataFrame(records) or a single pd.concat(list_of_frames) at the end. That's O(n) with one allocation.
Related and equally common: for idx in df.index: df.loc[idx, 'col'] = f(...). Each .loc assignment is a whole indexing operation; the vectorised or map-based version is typically 100× faster. Both mistakes come from thinking of a DataFrame as a list of rows rather than a set of columns.

            

          

        

      


      

        
2.4 Dictionaries in depth ⭐

        
The workhorse. Worth knowing how it's ordered, how to avoid KeyError in four different ways, and what the merge operators do.


        

          
Run itdicts.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: ['b', 'a', 'c'] — insertion order, not sorted, which is the point. get returns a default without touching the dict; setdefault returns a default and inserts it. defaultdict(list) gives the clean grouping idiom. Then a | b → {'x': 1, 'y': 99, 'z': 3} (right-hand side wins), and finally RuntimeError: dictionary changed size during iteration — iterate over list(d) if you need to delete while looping.

        


        

          
Likely interview questions

          

            
ConceptualAre dictionaries ordered?
              
Yes — insertion-ordered, and that has been a language guarantee since Python 3.7 (it was a CPython 3.6 implementation detail first). Iteration, keys(), values() and items() all follow insertion order.
Two precisions worth adding. Insertion order is not sorted order — people conflate them, and sorted(d) is what you want if you need keys in order. And re-assigning an existing key keeps its original position; only deleting and re-inserting moves it to the end.
collections.OrderedDict still exists and is still occasionally right: it has move_to_end, and its __eq__ is order-sensitive, whereas two plain dicts with the same pairs in different orders compare equal.

            

            
Codingget vs setdefault vs defaultdict — when each?
              
d.get(k, default) — read with a fallback, without modifying the dict. The default choice for lookups.
d.setdefault(k, default) — read, and insert the default if missing. Only when you want that side effect; otherwise it silently grows your dict, which surprises people reading the code later.
defaultdict(factory) — when every miss should produce a fresh container, typically for grouping: groups[key].append(x). Cleaner and faster than setdefault in a loop.
The gotcha to mention: a defaultdict creates entries on read, so merely checking dd[k] inserts k. Use k in dd to test membership, and consider converting to a plain dict before returning it from a function so the caller doesn't inherit the surprise.

Likely interview questions

          

            
CodingCount word frequencies and return the top 3.
              
Counter(words).most_common(3). One line, and reaching for it immediately is the signal.
Be ready for the follow-up “now without Counter”: build a defaultdict(int) and increment, then heapq.nlargest(3, d.items(), key=lambda kv: kv[1]). Mentioning nlargest rather than sorted(...)[:3] is worth a point — it's O(n log k) instead of O(n log n), which matters when you want the top 3 of ten million.
And the detail interviewers sometimes probe: most_common breaks ties by insertion order, so if the tie-break matters you must sort explicitly with a secondary key.

            

            
PracticalWhen would you use deque over a list in data work?
              
Three cases. A queue — BFS over a graph, or a work queue — because popleft is O(1) and list.pop(0) is O(n). A fixed-size rolling window — deque(maxlen=k) evicts from the far end automatically, which makes streaming statistics over a window trivial and constant-memory. A capped buffer for the last N log lines or predictions.
The counter-case, worth stating so you look balanced: if you need random access or slicing, a deque is worse — indexing is O(n) and slicing isn't supported. And for numeric rolling windows over a whole column, df.rolling() beats both because it drops into C.

            

          

        

      


      

        
2.6 deque, heapq, bisect

        
Three standard-library tools that turn a plausible O(n log n) or O(n²) answer into the right one. Knowing they exist is most of the value.


        

          
Run itheap_bisect.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the five largest and smallest values; the streaming heap agreeing with nlargest while only ever holding 5 items in memory; grade bucketing giving F, C, A, A; and [1, 4, 5, 9]. The streaming block is the one worth internalising — it's how you take a top-k over a stream you can't fit in RAM, and bisect-based bucketing is the Python equivalent of pd.cut.

        


        

          
Likely interview questions

          

            
CodingFind the top 10 items from a stream of a billion records.
              
A bounded min-heap of size 10. Push the first 10; after that, compare each new item to heap[0] (the smallest of the current top-10) and if it's larger, heapreplace. Memory is O(k) regardless of stream length; time is O(n log k).
Why not the obvious alternatives: sorted(data)[-10:] needs the whole stream in memory and is O(n log n); heapq.nlargest(10, stream) is actually fine and does this internally, so mention it — but the manual version is what they're checking you can reason about.
Good follow-ups to pre-empt: for top-k per group use one small heap per group; if k is large relative to n, sorting is simpler and comparable; and if the data is already in a database or a Parquet file, ORDER BY … LIMIT or a pushdown query beats anything you write in Python.

            

          

        

      


      

        
2.7 Sorting properly ⭐

        
Everyone knows sorted(). The interview is about key=, stability, and multi-key sorts with mixed directions.


        

          
Run itsorting.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: ['dan', 'ada', 'brian', 'cara'] by score descending. The mixed-direction sort gives de before ml, with 95 before 91 inside de. The “via stability” result matches it — that's the general technique when a key isn't numeric and can't be negated. The stability proof shows cara (78) first, then ada before brian, preserving their input order at equal scores.

        


        

          
Likely interview questions

          

            
Very commonSort by one field ascending and another descending.
              
Two techniques, and knowing both is the answer.
Negate the numeric key: sorted(rows, key=lambda r: (r["team"], -r["score"])). Concise, but only works when the descending key is numeric.
Exploit stability: sort by the least significant key first, then the most significant. Because Python's sort is stable (Timsort), the second sort preserves the first's ordering within ties. This works for any key type, including strings and dates you can't negate.
The pandas equivalent is df.sort_values(["team", "score"], ascending=[True, False]), which handles mixed directions directly — worth mentioning, because in a data interview the follow-up is usually “and in pandas?”

            

            
ConceptualWhat does “stable sort” mean and why does it matter?
              
A stable sort preserves the relative order of items that compare equal. Python's sorted and list.sort use Timsort, which is stable and O(n log n) worst case (and O(n) on already-sorted or nearly-sorted input, which is common in real data).
Why it matters practically: it makes multi-pass sorting valid, which is the mixed-direction technique above. It also means an existing meaningful order — insertion order, arrival time, a previous sort — survives a subsequent sort on a different key, so you don't scramble ties.
The trap: np.sort's default quicksort is not stable, and neither is df.sort_values's default. If you rely on tie order, pass kind="stable" (or mergesort) explicitly — otherwise you have a bug that only appears on some inputs.

            

            
Codingsorted() vs .sort()?
              
sorted(iterable) returns a new list and accepts any iterable — a generator, a dict, a set. list.sort() sorts in place, returns None, and only exists on lists.
The bug that follows from the None: rows = rows.sort() silently sets rows to None. It's a classic, and it's why the in-place methods deliberately return None — to make the mistake loud rather than subtle.
Prefer sorted() by default: it doesn't mutate its input, which keeps functions free of surprising side effects (§1.1). Use .sort() when the list is large and local and you genuinely want to avoid the copy.

            

          

        

      


      

        
2.8 Comprehensions ⭐

        
Idiomatic, faster than an equivalent loop, and the thing most likely to be asked to write on the spot. The skill is knowing when they stop being readable.


        

          
Run itcomprehensions.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: ids [1, 2, 3]; the dict mapping id→v; the set {10, 30}; [20, 60] for the filtered double; [10, 0, 30] for the conditional expression — note the difference between filtering out a row and substituting a value. Flatten gives [1, 2, 3, 4, 5], the genexp sums to 40, and the walrus version computes each square root once.

        


        

          
Likely interview questions

          

            
Very commonExplain list, dict and set comprehensions, and when you'd avoid them.
              
All three build a container from an iterable in one expression: [f(x) for x in it if cond], {k: v for …}, {x for …}. They're idiomatic and modestly faster than the equivalent for loop with append, because the append is done in C rather than as a bytecode method call.
The distinction worth drawing: the if at the end filters (drops items); a conditional expression at the front substitutes (keeps every item). [x for x in xs if x] and [x or 0 for x in xs] produce different lengths, and mixing them up is a real bug.
When to avoid: more than one for plus a condition, any side effect (never use a comprehension for its side effects — use a loop), or when the expression no longer fits on one line. Readability wins; a comprehension you have to parse twice is worse than four lines of loop.

            

            
CodingFlatten a list of lists.
              
[x for row in matrix for x in row]. The clause order matches the nested loop you'd write — outer loop first — which is the bit people reverse.
Alternatives worth naming: list(itertools.chain.from_iterable(matrix)), which is slightly faster and clearer for a one-level flatten; and np.concatenate or .ravel() if it's numeric. For arbitrarily nested structures you need recursion or an explicit stack, and the follow-up question is often exactly that — so be ready to write a small recursive generator with an isinstance check.
The anti-pattern to mention: sum(matrix, []) works and is O(n²), because it builds a new list per concatenation. It shows up in code golf and should never survive review.

            

          

        

      


      

        
2.9 Slicing, unpacking and zip

        
The syntax that makes Python code look like Python. Cheap to learn, and its absence is conspicuous in a live-coding round.


        

          
Run itidioms.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the slices behave as labelled — note a[::-1] is a copy, not a view, so it costs O(n) memory. Slice assignment replaces three elements with one and shortens the list to 8. Starred unpacking gives 0 9 with 8 in the middle. zip(*rows) transposes to [(1, 2, 3), ('a', 'b', 'c')]. The last block is the important one: zip silently truncates to the shortest input, which loses rows without any warning — use strict=True when the lengths should match.

        


        

          
Likely interview questions

          

            
GotchaWhat's dangerous about zip?
              
It stops at the shortest iterable, silently. Zipping a 1000-row list of ids against a 998-row list of predictions gives you 998 pairs and no error — you've just dropped two rows and misaligned nothing visibly. In a data pipeline that's a correctness bug that can survive to production.
Fixes: zip(a, b, strict=True) (Python 3.10+) raises ValueError on a length mismatch, which is what you want almost every time you zip data. itertools.zip_longest pads with a fill value when unequal lengths are legitimate. Or assert the lengths first.
The related pandas lesson: this is exactly why aligning on an index or joining on a key beats zipping positionally. Positional alignment assumes an invariant nobody is checking.

            

            
CodingReverse a list, and transpose a list of rows.
              
Reverse: a[::-1] for a new list, a.reverse() in place, reversed(a) for a lazy iterator. Mention that the slice makes a full copy — on a large list, reversed() is the memory-cheap option.
Transpose: list(zip(*rows)). The * unpacks each row as a separate argument to zip, so zip takes one element from each — which is exactly a transpose. It returns tuples; wrap in [list(c) for c in zip(*rows)] if you need lists.
Worth adding the caveat: this assumes rows are equal length, and zip will silently truncate to the shortest if they aren't. For numeric data, np.array(rows).T is faster and will raise on ragged input rather than truncate — which is usually what you want.
