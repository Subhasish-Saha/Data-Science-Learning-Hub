1.1 Names, objects and bindings ⭐⭐

One sentence unlocks most of Python's surprises: a name is a label attached to an object, not a box containing one. Assignment moves labels; it never copies objects.

See it for yourself

Run italiasing.pyidle
⌘/Ctrl + Enter 

          
Expected: a and b start aliased, so a.append(4) changes both. b + [5] builds a new list and breaks the alias. The pair at the end is the real test: c += [3] mutates (so d sees it), while e += (3,) rebinds (so f does not) — same operator, opposite behaviour, decided entirely by mutability.

        


        

          
          += is not sugar for x = x + y
          
For a mutable target, += calls __iadd__ and mutates in place — every alias sees the change. For an immutable target there is no in-place option, so it falls back to __add__ and rebinds. This is why df += 1 and arr += 1 behave differently from df = df + 1 in ways that matter for memory.

        


        

          
Likely interview questions

          

            
Very commonIs Python pass-by-value or pass-by-reference?
              
Neither — it's pass-by-object-reference (sometimes called call-by-sharing). The function receives a new local name bound to the same object as the caller's name.
The consequence is the bit that matters, and it's the part to say next: if the function mutates the object (lst.append(x), df['col'] = ...), the caller sees it. If the function rebinds its local name (lst = [...]), the caller sees nothing, because you only moved the local label.
So “does my function affect the caller's data?” is never about Python's calling convention — it's about whether you mutated or rebound. That's why a function taking a DataFrame should either return a new one or be explicitly documented as mutating in place, never leave it ambiguous.

            

            
Gotchac = [1,2]; d = c; c += [3] — what is d?
              
[1, 2, 3]. For a list, += invokes __iadd__, which extends the list in place, so both names still point at the same mutated object.
Contrast with c = c + [3], which builds a new list and rebinds only c, leaving d == [1, 2]. And contrast with tuples, where e += (3,) must rebind because there is no in-place option.
This matters beyond trivia: with NumPy and pandas, arr += 1 mutates the buffer (cheap, but visible to every view) while arr = arr + 1 allocates a whole new array (safe, but doubles peak memory). Choosing between them is a real decision on a large frame.

            

            
ConceptualWhy does this matter for data-science code specifically?
              
Because DataFrames and arrays are large mutable objects that get passed between functions constantly. Three concrete failure modes:
1. A helper mutates its caller's frame. def clean(df): df['x'] = df['x'].fillna(0) silently edits the caller's data. Six months later someone runs clean() in a loop and can't work out why the “raw” frame has changed.
2. Aliasing across a pipeline. train = df; test = df then mutating one — a bug that vanishes when you look for it, because both names print the same thing.
3. Memory. Knowing that df2 = df1 costs nothing while df2 = df1.copy() doubles memory is the difference between a job that fits in RAM and one that doesn't.
The habit that prevents all three: functions return new objects, or are named for the fact that they mutate — never both, never silently.

            

          

        

      


      

        
1.2 Mutable vs immutable ⭐⭐

        
Mutability is the single property that decides how an object behaves in a dict, in a function call, as a default argument, and under copying. Learn the split once and a dozen questions collapse into one.

“Shallowly” immutable is the interesting case

        
A tuple guarantees that its own slots can't be reassigned. It says nothing about the objects in those slots. So t = ([1], [2]) is an immutable container of mutable lists: you cannot do t[0] = ..., but t[0].append(9) works fine. That's also why such a tuple is unhashable — see §1.4.


        

          
Run itmutability.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: ([1, 9], [2]), then a TypeError: 'tuple' object does not support item assignment, then two different ids for s, then 01234. The last block is the practical lesson: because str is immutable, s += x in a loop copies the whole string every iteration — O(n²) — so you accumulate into a list and join once.

        


        

          
Likely interview questions

          

            
Very commonWhat's the difference between mutable and immutable, and why should I care?
              
Mutable objects can be changed in place, keeping their identity; immutable objects cannot, so any “change” produces a new object.
Then give the four consequences, because that's what makes it an answer rather than a definition. Hashability: only immutables (with immutable contents) can be dict keys or set members. Aliasing: mutating an object is visible through every name bound to it. Default arguments: a mutable default is created once and shared across calls. Performance: immutability makes string concatenation in a loop quadratic, and makes tuples cheaper to hash and safe to share.
A tuple is only shallowly immutable — ([1],) can have its inner list mutated, which is why it's unhashable.

            

            
CodingWhy is building a string with += in a loop a bug?
              
Because strings are immutable, so each s += x allocates a new string and copies everything accumulated so far. Over n iterations that's 1 + 2 + … + n character copies — O(n²). On a million rows it's the difference between a second and several minutes.
The fix is to accumulate into a list and join once: parts.append(x) then "".join(parts), which is O(n) with a single final allocation. For file output, writing incrementally to the file handle is better still, since you never hold the whole thing.
Worth adding: CPython has an optimisation that sometimes makes s += x look linear when the string has a refcount of 1, which is exactly why people don't notice the bug until it's in a hot loop with an extra reference floating around. Don't rely on it.

            

            
ConceptualAre NumPy arrays and DataFrames mutable?
              
Yes, both. An ndarray's buffer can be written in place, and a DataFrame's columns can be assigned. That's precisely why views, aliasing and copy semantics dominate Parts 6 and 7 of this guide.
Two refinements worth volunteering. NumPy arrays have a .flags.writeable switch you can set to False to get an immutable view — useful for handing data to a function you don't trust. And in pandas 3.0, Copy-on-Write means the result of an indexing operation always behaves as an independent copy, so mutating a slice can no longer reach back into the parent frame. The objects are still mutable; what changed is that the aliasing is no longer implicit.

            

          

        

      


      

        
1.3 is vs == ⭐

        
== asks “same value?”; is asks “same object?”. The trap is that for small integers and short strings, is often appears to work — because CPython caches them.


        

          
Run itidentity.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: 256 is 256 → True (cached). 257 is 257 and 1000 is 1000 may print True or False depending on whether the compiler folded the constants into the same code object — which is the whole point: it's an implementation detail, so never depend on it. Lists are always separate objects. The NumPy line shows why: == on an array returns an array of booleans, so if arr == 2 raises “truth value of an array is ambiguous”.

        


        

          
          The rule
          
Use is only for singletons: is None, is not None, and occasionally a sentinel object you created yourself. Everything else uses ==. In pandas, use .isna() rather than either — np.nan == np.nan is False and x is np.nan is a coin flip.

        


        

          
Likely interview questions

          

            
Very commonDifference between is and ==?
              
== compares value by calling __eq__; is compares identity — whether both names point at the same object, equivalent to id(a) == id(b).
The part that scores: explain why beginners think is works on numbers. CPython interns small integers (roughly −5 to 256) and some short strings, so 256 is 256 is True while 1000 is 1000 may or may not be, depending on constant folding. That's an implementation detail, not a language guarantee — CPython, PyPy and different Python versions differ.
The rule: is only for singletons (None, True, False, your own sentinels), == for everything else.

            

            
GotchaWhy does if df == None break, and what's correct?
              
Two separate problems. First, == against a DataFrame or array is elementwise, so it returns a whole frame of booleans, and putting that in an if raises “The truth value of a DataFrame is ambiguous”. Second, even for scalars, == None is the wrong idiom because a custom __eq__ can override it.
Correct forms: if df is None: to test for the object being absent; if df.empty: to test for no rows; df.isna() for missing values elementwise. And for NaN specifically, never use == — np.nan == np.nan is False by IEEE-754 design, which is exactly why .isna() exists.

            

          

        

      


      

        
1.4 Hashability ⭐

        
Why can a tuple be a dict key but a list can't? Because a dict needs the key's hash to stay constant for as long as it's in the dict — and a mutable object can't promise that.


        
The contract has three clauses: an object is hashable if it implements __hash__; objects that compare equal must have the same hash; and the hash must not change during the object's lifetime. A list could be mutated after insertion, which would strand it in the wrong bucket — so list.__hash__ is deliberately None.


        

          
Run ithashability.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: tuples and frozensets hash; lists raise unhashable type: 'list'; a tuple containing lists also raises, which is the point of “shallowly immutable”. The dict literal collapses to {1: 'bool'} — because 1 == 1.0 == True and they all hash to 1, so each assignment overwrites the same slot while keeping the first key. That's a genuine trap when you build a dict from mixed-type values.

        


        

          
Likely interview questions

          

            
Very commonWhy can't a list be a dictionary key?
              
Because a dict stores each key in a bucket chosen from its hash, and it needs that hash to remain constant while the key is in the dict. A list is mutable, so mutating it after insertion would change its hash and leave it unfindable — the entry would be in the wrong bucket, and lookups for the “same” list would miss.
Rather than allow that corruption, Python sets list.__hash__ = None, so the failure is an immediate TypeError: unhashable type: 'list' instead of a silent data bug.
Use a tuple instead — and note that a tuple containing a list is also unhashable, because hashing is recursive. If you need a set of sets, that's what frozenset is for.

            

            
Deep diveWhat's the __hash__/__eq__ contract?
              
Three rules. Equal objects must have equal hashes — if a == b then hash(a) == hash(b), or dict lookups become unreliable. The hash must be stable for the object's lifetime. And unequal objects may share a hash — that's just a collision, which the dict resolves by comparing with ==.
The practical consequence for your own classes: if you define __eq__, Python sets __hash__ to None and your class becomes unhashable. You must define __hash__ too, typically as hash((self.a, self.b)) over the same fields __eq__ uses. This is exactly why @dataclass(frozen=True) gives you both for free and plain @dataclass gives you only __eq__.

            

            
GotchaWhat does {1: 'a', True: 'b', 1.0: 'c'} evaluate to?
              
{1: 'c'} — one entry. Because 1 == True == 1.0 and all three hash to the same value, each assignment overwrites the same slot. The value becomes the last one written, but the key stays the first one inserted, which is why it prints as 1 rather than 1.0.
Where this actually bites: building a lookup keyed on a column that mixes int and float (very easy after a pandas operation that upcasts), or keying on a flag column that is sometimes 1 and sometimes True. You silently lose entries. The fix is to normalise key types explicitly before building the dict.

            

          

        

      


      

        
1.5 The mutable default argument trap ⭐⭐

        
Close to a guaranteed question. Default values are evaluated once, when the function is defined — not on each call. A mutable default is therefore shared state across every call.


        

          
Run itmutable_default.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: ['a'], ['a', 'b'], ['a', 'b', 'c'] — the default list accumulates across calls, and broken.__defaults__ shows the shared object holding all three. The fixed version prints three independent single-item lists. The stale example is the same bug in a form people miss: a default computed at import time (a date, a config read, a time.time()) is frozen for the life of the process.

        


        

          
Likely interview questions

          

            
Very commonWhat's wrong with def f(x, acc=[])?
              
The default is evaluated once, at function-definition time, and stored on the function object in __defaults__. Every call that omits the argument gets the same list, so mutations accumulate across calls — and across different callers, and across the whole process lifetime.
Fix: use None as the sentinel and build a fresh object inside the body — if acc is None: acc = []. Use is None rather than if not acc, because an explicitly-passed empty list should be respected, not replaced.
Worth adding that the same trap catches any computed default: def f(when=datetime.now()) freezes the timestamp at import. And that the rule is only about mutable defaults — def f(n=0) or def f(s="") are perfectly safe, because rebinding an immutable can't leak.

            

            
PracticalIs there ever a legitimate use for a mutable default?
              
Rarely, and always deliberately. The one idiom you'll see in real code is a memo cache: def f(n, _cache={}): exploits the shared default as per-function persistent storage. It works, but functools.lru_cache does the same job with a documented API, thread safety and cache statistics, so prefer that.
The tell that it's deliberate rather than a bug is the leading underscore on the parameter name and a comment saying so. If you see a mutable default without both, treat it as a bug.

            

          

        

      


      

        
1.6 Copies: none, shallow, deep ⭐⭐

        
Three distinct operations that people call “copying”, with three different behaviours on nested data. This is the question that separates people who have debugged a real aliasing bug from people who have read about one.


        

        

          
Run itcopies.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: after original[0].append(99), both alias and shallow show [1, 2, 99] — only deep is clean. Then original.append(["new"]) grows original and alias but not shallow, proving the outer list really was duplicated. The final dict block is the version you'll actually hit: dict(cfg) looks like a copy and shares every list inside it.

        


        

          
Likely interview questions

          

            
Very commonShallow copy vs deep copy?
              
A shallow copy creates a new outer container holding references to the same inner objects. A deep copy recursively duplicates everything, so the result shares nothing with the original.
The practical rule: shallow is enough when the contents are immutable (a list of ints, a dict of strings); you need deep as soon as the contents are mutable and you intend to mutate them. And say which operations are shallow, because that's where people get caught: a[:], list(a), a.copy(), dict(d), {**d} and copy.copy are all shallow. Only copy.deepcopy is deep.
Add the cost, since it's a real decision: deepcopy walks the whole object graph and is slow — on a big nested structure it can dominate your runtime, and on objects holding file handles or DB connections it may fail outright. Often the better answer is to restructure so you don't need to copy at all.

            

            
GotchaIs df.copy() shallow or deep?
              
Deep by default — df.copy() is df.copy(deep=True), which duplicates the data buffers, so the result is fully independent. df.copy(deep=False) gives you a new frame object sharing the same data.
The 2026 wrinkle worth mentioning: under pandas 3.0's Copy-on-Write, the distinction matters much less than it used to, because any indexing result already behaves as an independent copy, and pandas defers the actual data duplication until something is written. So the defensive .copy() that everyone used to sprinkle after a filter is now usually redundant — it just forces an eager copy that CoW would have avoided. Dropping those is a genuine memory win when you upgrade.

            

            
CodingHow would you copy a nested dict of lists safely without deepcopy?
              
A comprehension that copies exactly the level you need: {k: list(v) for k, v in cfg.items()}. This is often the right answer because it's explicit about the depth, far faster than deepcopy, and it won't choke on unpicklable values buried somewhere in the structure.
The general principle: deepcopy is a blunt instrument that copies more than you usually need. When you know the shape, copy the shape. When you don't, prefer making the data immutable (tuples, frozen dataclasses) so copying stops being necessary at all — that's the design fix rather than the workaround.

            

          

        

      


      

        
1.7 Scope and the LEGB rule ⭐

        
Python resolves a name by searching four scopes in order: Local, Enclosing, Global, Built-in. The surprise is that assigning to a name anywhere in a function makes it local for the whole function.


        

          
Run itlegb.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: inner sees: enclosing, then a successful global read, then UnboundLocalError: cannot access local variable 'x' where it is not associated with a value. That error is the whole lesson: the x = "local" on the next line makes x local for the entire function body, so the print above it reads an unassigned local rather than the global. Finally: global count: 2 | closure counter: 1 2 3.

        


        

          
Likely interview questions

          

            
ConceptualExplain the LEGB rule.
              
Name lookup searches four scopes in order: Local (this function), Enclosing (any outer function, for nested defs), Global (module level), Built-in (len, print, …). First match wins.
The non-obvious part is that assignment determines scope at compile time, for the whole function. If a function assigns to x anywhere in its body, x is local throughout — so reading it before that assignment raises UnboundLocalError, even if a global x exists. That surprises people because reading a global without assigning works fine.
To rebind an outer name deliberately you need a declaration: global for module level, nonlocal for an enclosing function. Note you don't need either to mutate a mutable global — CACHE['k'] = v works without global, because that mutates rather than rebinds.

            

            
PracticalWhy is shadowing a builtin a problem?
              
Because it removes the builtin for the rest of that scope, and the failure often surfaces far from the cause. list = df['x'].tolist() means the next list(...) call in that scope raises TypeError: 'list' object is not callable. In a notebook, where the global scope persists across cells, the shadowing survives until you restart the kernel — which is why “it worked yesterday” is such a common notebook complaint.
The usual offenders in data code: list, dict, set, type, id, sum, max, min, filter, input, and — painfully — df reused for six different frames. A linter flags all of them for free, which is the real answer: this is a problem you solve with tooling, not vigilance.

            

          

        

      


      

        
1.8 Late binding in closures ⭐

        
A closure captures the variable, not its value at capture time. Build functions in a loop and they all see the loop variable's final value — a bug that shows up constantly when generating callbacks or transformers.


        

          
Run itlate_binding.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: broken : [2, 2, 2] — every lambda closes over the same i, which ends at 2. The three fixes all print [0, 1, 2]. The final pair makes it concrete: the “bad” scalers both divide by len("qty") = 3 giving [3.33, 3.33], while the “good” ones bind their own column and give [2.0, 3.33]. Note that c=c in the signature is the idiomatic fix, not a typo.

        


        

          
Likely interview questions

          

            
GotchaWhat does [lambda: i for i in range(3)] produce when called?
              
[2, 2, 2], not [0, 1, 2]. Closures capture the variable, not a snapshot of its value, and by the time you call the lambdas the loop has finished with i == 2. This is called late binding.
Three fixes, and it's worth knowing more than one. Default argument: lambda i=i: i — the default is evaluated at definition time, so each lambda gets its own value. (Note this is the same mechanism as the §1.5 trap, used deliberately.) functools.partial, which binds the argument explicitly. A factory function, which creates a fresh enclosing scope per call.
Where it bites in real work: generating a dict of per-column transformers, registering callbacks in a loop, or building a list of delayed jobs for joblib — all silently apply the last iteration's parameters to every task.

Likely interview questions

          

            
ConceptualHow does Python manage memory?
              
Primarily reference counting: every object tracks how many references point at it, and it's freed the instant that count reaches zero. That makes deallocation deterministic and usually immediate.
Because refcounting can't free cycles — two objects referring to each other never reach zero — CPython adds a generational garbage collector that periodically scans for unreachable cycles. Three generations, on the theory that most objects die young, so gen-0 is scanned far more often than gen-2.
Two practical notes that make this a useful answer rather than trivia: memory freed by Python often stays in the process's allocator rather than returning to the OS, which is why RSS doesn't drop after del; and the GC cannot help while something is still reachable, so a leak in Python is almost always an unintended reference, not a collector failure.

            

            
DebugYour notebook is using 40 GB. How do you find out why?
              
First, list what's actually bound: iterate globals() and report the largest objects (for frames, df.memory_usage(deep=True).sum(), since sys.getsizeof undercounts). That alone usually finds it — an intermediate frame from three cells ago still bound to tmp.
Then the notebook-specific causes: Jupyter keeps every displayed result alive in Out[...], _, __ and ___, so a frame you merely displayed is retained; %reset out or %xdel clears those. Also check for accidental copies from chained operations, and object-dtype columns holding Python strings.
Then the fixes: read with explicit dtypes and usecols; downcast numerics and convert low-cardinality strings to category; process in chunks; and del intermediates inside a function so they go out of scope automatically. The structural fix is to move the work into functions — locals are freed on return, which is exactly what a notebook's flat global scope prevents.

            

            
Deep diveWhy is a Python list of a million ints so much bigger than a NumPy array?
              
Because the list stores a million pointers (8 bytes each) to a million separate int objects, and each of those objects carries a refcount, a type pointer and variable-width digits — about 28 bytes for a small int. So you pay roughly 36 bytes per element, scattered across the heap.
A NumPy int64 array stores a million raw 8-byte integers in one contiguous buffer with a single dtype and no per-element object. That's ~8 MB instead of ~36 MB, a 4.5× memory win — and the bigger win is speed, because contiguity means the CPU cache and vectorised instructions actually work.
This is the answer to “why NumPy?” and it's worth giving in exactly these terms: no boxing, one dtype, contiguous memory. Everything in Part 6 follows from it.

Very commonWhat's the time complexity of x in list vs x in set?

Add the caveats to show depth: the set case is average O(1) and amortised — pathological hash collisions degrade it to O(n), and it costs memory (a set is roughly 3–4× the footprint of the equivalent list) plus the requirement that elements be hashable.
Then the practical version: converting a list to a set once, before a loop, turns an O(n·m) scan into O(n+m). On a 100k-row filter against a 50k-item allow-list that's minutes to milliseconds — and it's a one-line change, which is why interviewers like it.

            

            
GotchaWhy is list.pop(0) a problem?
              
It's O(n): removing the first element means shifting every other element down one slot. Do that n times to drain a queue and you've written an O(n²) loop, which looks perfectly innocent.
Use collections.deque, which is a doubly-linked list of blocks and gives O(1) append, appendleft, pop and popleft. The trade is that deque[i] is O(n), so it's the right structure for a queue and the wrong one for random access.
Same reasoning applies to list.insert(0, x) and to del a[0]. If you only ever push and pop at the end, a list is already O(1) and perfectly fine.

            

            
ConceptualWhy is list.append “amortised” O(1)?
              
Because a list holds a contiguous buffer with spare capacity. Most appends just write into the spare slot — genuinely O(1). When the buffer fills, Python allocates a bigger one (growth is proportional, not fixed) and copies everything across, which is O(n) for that one append.
Because the reallocation happens geometrically rarely, the average cost per append over many appends is constant — that's what “amortised” means. The distinction matters in two real situations: a single append can occasionally be slow (which shows up as jitter in latency-sensitive code), and if you know the final size, preallocating or using array/NumPy avoids the copies entirely.

Likely interview questions

          

            
DebugHere's a function that's slow on 100k rows. Find the problem.
              
Scan for a linear operation inside a loop — that's the shape of nearly every one of these. The four to look for, in frequency order:
1. x in some_list inside a loop → convert to a set once, outside. 2. String or list concatenation in a loop (s += ..., acc = acc + [...]) → accumulate and join, or append. 3. df.append / pd.concat per row → build a list of dicts and construct the frame once (this one is O(n²) in copies of the whole frame, so it's brutal). 4. .pop(0) or .insert(0, …) → use a deque.

PracticalWhat's the pandas version of this mistake?
              
Growing a DataFrame row by row. df = pd.concat([df, new_row]) in a loop reallocates and copies the entire frame on every iteration, so building 10,000 rows performs ~50 million row-copies. It is comfortably the slowest thing people routinely write in pandas.
The fix: accumulate plain Python (a list of dicts, or a list of small frames) and construct once — pd.DataFrame(records) or a single pd.concat(list_of_frames) at the end. That's O(n) with one allocation.
Related and equally common: for idx in df.index: df.loc[idx, 'col'] = f(...). Each .loc assignment is a whole indexing operation; the vectorised or map-based version is typically 100× faster. Both mistakes come from thinking of a DataFrame as a list of rows rather than a set of columns.

ConceptualAre dictionaries ordered?

Likely interview questions

          

            
Very commonSort by one field ascending and another descending.
              
Two techniques, and knowing both is the answer.
Negate the numeric key: sorted(rows, key=lambda r: (r["team"], -r["score"])). Concise, but only works when the descending key is numeric.
Exploit stability: sort by the least significant key first, then the most significant. Because Python's sort is stable (Timsort), the second sort preserves the first's ordering within ties. This works for any key type, including strings and dates you can't negate.
The pandas equivalent is df.sort_values(["team", "score"], ascending=[True, False]), which handles mixed directions directly — worth mentioning, because in a data interview the follow-up is usually “and in pandas?”

            

            
ConceptualWhat does “stable sort” mean and why does it matter?
              
A stable sort preserves the relative order of items that compare equal. Python's sorted and list.sort use Timsort, which is stable and O(n log n) worst case (and O(n) on already-sorted or nearly-sorted input, which is common in real data).
Why it matters practically: it makes multi-pass sorting valid, which is the mixed-direction technique above. It also means an existing meaningful order — insertion order, arrival time, a previous sort — survives a subsequent sort on a different key, so you don't scramble ties.
The trap: np.sort's default quicksort is not stable, and neither is df.sort_values's default. If you rely on tie order, pass kind="stable" (or mergesort) explicitly — otherwise you have a bug that only appears on some inputs.

            

            
Codingsorted() vs .sort()?
              
sorted(iterable) returns a new list and accepts any iterable — a generator, a dict, a set. list.sort() sorts in place, returns None, and only exists on lists.
The bug that follows from the None: rows = rows.sort() silently sets rows to None. It's a classic, and it's why the in-place methods deliberately return None — to make the mistake loud rather than subtle.
Prefer sorted() by default: it doesn't mutate its input, which keeps functions free of surprising side effects (§1.1). Use .sort() when the list is large and local and you genuinely want to avoid the copy.

Very commonExplain list, dict and set comprehensions, and when you'd avoid them.
              
All three build a container from an iterable in one expression: [f(x) for x in it if cond], {k: v for …}, {x for …}. They're idiomatic and modestly faster than the equivalent for loop with append, because the append is done in C rather than as a bytecode method call.

For arbitrarily nested structures you need recursion or an explicit stack, and the follow-up question is often exactly that — so be ready to write a small recursive generator with an isinstance check.
The anti-pattern to mention: sum(matrix, []) works and is O(n²), because it builds a new list per concatenation. It shows up in code golf and should never survive review.

Likely interview questions

          

            
Very commonExplain *args and **kwargs.
              
In a definition they collect: *args gathers extra positional arguments into a tuple, **kwargs gathers extra keyword arguments into a dict. In a call the same symbols do the opposite — they unpack: f(*my_list, **my_dict) spreads a sequence into positional arguments and a mapping into keyword arguments.
That symmetry is the thing to say out loud, because it's what makes transparent wrappers possible: def wrapper(*a, **kw): return fn(*a, **kw) forwards any signature, which is the backbone of every decorator.
Then add the ordering rule, since it's the natural follow-up: positional-only /, positional-or-keyword, *args, keyword-only, **kwargs. A bare * marks the start of keyword-only parameters without collecting anything; a / marks the end of positional-only ones.

            

            
PracticalWhy would you force keyword-only arguments?
              
To make call sites readable and to stop positional mistakes. train(df, 0.2, 42, True) is unreadable and the arguments are trivially swappable; train(df, *, test_size=0.2, seed=42, shuffle=True) forces every caller to name them, so a reordering mistake becomes impossible rather than silent.
The second reason is API evolution: keyword-only parameters can be reordered or have new ones inserted without breaking callers, because nobody depends on their position. That's exactly why pandas and scikit-learn have been progressively converting their APIs to keyword-only — df.drop("col", axis=1) becoming df.drop(columns="col") is the same idea.
Rule of thumb: anything that's a flag or a tuning parameter should be keyword-only; only the primary data argument deserves to be positional.

Likely interview questions

          

            
Very commonWhat is a closure?
              
A function that remembers variables from the scope where it was defined, even after that scope has exited. Concretely: an inner function referencing an outer function's local, returned from the outer function. Python keeps the referenced variables alive in cells, visible as fn.__closure__ and named in fn.__code__.co_freevars.
Two properties to state, because they're what get tested. It captures the variable, not the value — hence late binding (§1.8). And each call to the factory produces independent cells, so two closures from the same factory don't share state, while two closures from the same call do.
Why it matters in practice: closures are how decorators work, how you build configured callables without a class, and how functools.partial-style specialisation is expressed.

            

            
ConceptualClosure or class — when would you pick which?
              
Closure when there's essentially one behaviour and a little configuration: a scaler, a validator, a key function, a decorator. It's less code and there's nothing to name.
Class when there are several related methods over the same state, when the state needs inspecting or serialising, or when the object must fit a framework's protocol — a scikit-learn estimator needs fit, transform, get_params and picklability, and a closure can't provide any of that.
The deciding question: does anything other than “call it” need to happen to this thing? Inspect it, pickle it, subclass it, give it a second method — then use a class. Otherwise a closure is the lighter answer, and reaching for a class reflexively is over-engineering.

Very commonWhat is a decorator? Write one.
              
A callable that takes a function and returns a replacement, letting you add behaviour without editing the original. @deco above a def is exactly f = deco(f).
The canonical shape, which you should be able to write from memory:

GotchaWhat does functools.wraps do, and what breaks without it?
              
It copies the wrapped function's identity onto the wrapper: __name__, __doc__, __module__, __qualname__, __dict__ and __annotations__, and sets __wrapped__ so the original is still reachable.
Without it, every decorated function reports itself as wrapper with no docstring. Concretely that breaks: tracebacks and logs (every frame is “wrapper”, so you can't tell which function failed), help() and generated docs, introspection like inspect.signature, and any framework that dispatches on __name__ — pytest collection, Flask routes, Celery task names, and click commands all misbehave.
It's one line and there is no reason to omit it. Its absence in a code sample is a reliable tell that the author copied the pattern without understanding it.

            

            
Deep diveCan you decorate a class, or use a class as a decorator?
              
Both, yes. A class as a decorator: implement __init__(self, fn) to store the function and __call__(self, *a, **kw) to invoke it. This is the cleaner option when the decorator needs meaningful state — a call counter, a cache with statistics, a circuit breaker — because instance attributes beat nonlocal for anything you want to inspect.
Decorating a class: the decorator receives the class object and returns a class (or the same class, modified). That's how @dataclass and @functools.total_ordering work — they inspect annotations or existing methods and inject generated ones.
The gotcha with class-based decorators: they don't automatically behave like methods, because they lack the descriptor protocol. Decorating an instance method with a class-based decorator loses self binding unless you also implement __get__. That's a real edge case and worth knowing exists.

Codingcache vs lru_cache — and when is caching wrong?
              
@cache is @lru_cache(maxsize=None) — unbounded, slightly faster, and it will grow forever. @lru_cache(maxsize=n) is bounded and evicts the least recently used entry, which is what you want when the key space is large or unbounded.

Conceptualpartial vs a lambda?
              
partial(f, a=1) pre-binds arguments and returns a new callable. A lambda does the same thing by hand.
partial is better when it matters: it's picklable (a lambda is not, which breaks multiprocessing and joblib — a very real constraint in data work), it's introspectable (p.func, p.keywords), it has a useful repr, and it avoids the late-binding trap from §1.8 because arguments are bound at creation.
A lambda is fine for a quick inline key function — sorted(rows, key=lambda r: r["score"]) — where none of that applies. But if the callable is going to cross a process boundary or be stored, partial is the right tool.

            

          

        

      


      

        
3.7 Lambdas, and their limits

        
A lambda is an anonymous single-expression function. Useful in exactly one context and over-used in several others.


        
Use one for a short inline callable passed straight to another function: key=, map, a small .apply. Don't use one when you assign it to a name (just write def — you get a real name in tracebacks for free), when it needs more than one expression, or when a built-in already exists: key=lambda x: x[1] is better written key=itemgetter(1), and lambda s: s.lower() is str.lower.


        

          
          Lambdas can't be pickled
          
Which means they break multiprocessing, joblib with a process backend, Dask, and any attempt to save a scikit-learn pipeline containing a FunctionTransformer(lambda …). The error appears at save or fan-out time, far from the lambda. Use a module-level def or functools.partial for anything that might cross a process boundary.

        


        

          
Likely interview questions

          

            
ConceptualWhen should you not use a lambda?
              
Whenever you give it a name. f = lambda x: x + 1 is strictly worse than def f(x): return x + 1 — same length, but the def version gets a real __name__, can carry a docstring, and shows up properly in tracebacks. PEP 8 says this explicitly.
Also avoid them when the logic needs a statement (a try, an assignment, a loop) — a lambda is a single expression, so people contort the logic to fit; when a built-in or operator function already does the job; and when the callable must be picklable for multiprocessing or model serialisation.
The legitimate case is narrow and worth stating so the answer isn't just negative: a short throwaway callable passed directly as an argument, most often key= in a sort.

4.1 The iterator protocol ⭐

        
Every for loop in Python is sugar over two methods. Knowing them is what lets you answer “what's the difference between an iterable and an iterator?” crisply.


        
for x in obj calls iter(obj) to get an iterator, then calls next() on it repeatedly until it raises StopIteration, which the loop catches silently.

That silence is why exhausted-iterator bugs are hard to spot.

        


        

          
Likely interview questions

          

            
Very commonIterable vs iterator?
              
An iterable implements __iter__ and can produce an iterator — lists, dicts, strings, files. An iterator implements __next__ (and __iter__ returning itself) and holds the position; it is consumed as you advance it.
The consequence that matters: a list is iterable and re-iterable — iter(lst) gives you a fresh iterator each time, so you can loop over it twice. A generator is its own iterator, so once exhausted it yields nothing more, silently, with no exception.
That's the bug this question exists to test: gen = (x for x in data) then sum(gen) followed by max(gen) gives you a correct sum and then a ValueError on an empty sequence — or worse, len(list(gen)) == 0 and no error at all.

            

            
CodingWrite a class you can use in a for loop.
              
Two designs, and choosing deliberately is the answer.
Self-iterating: __iter__ returns self and __next__ advances internal state, raising StopIteration when done. Simple, but single-use — a second loop is silently empty.
Re-iterable container: __iter__ returns a fresh iterator each call, typically by delegating (return iter(self.data)) or by being a generator function. This is what you almost always want for something that models a collection.
Simplest correct version: make __iter__ a generator — def __iter__(self): yield from self.data. You get a new generator per call, so it's re-iterable, and you never write __next__ or StopIteration by hand.

Likely interview questions

          

            
Very commonWhat is a generator and why use one?
              
A function containing yield. Calling it returns a generator object that produces values lazily: execution pauses at each yield, keeping local state, and resumes on the next next().
Give the reason as a number, because that's the answer: [x*x for x in range(10_000_000)] materialises ten million ints — hundreds of megabytes — before anything consumes them. The generator expression holds one. Peak memory goes from O(n) to O(1).
Then the three secondary benefits: you can represent infinite streams; you get early exit for free (any() over a generator stops at the first match rather than computing everything); and generators compose into pipelines where each stage still holds one item.
And the honest caveat: generators don't make the work faster, they make the memory constant — and they're single-use.

            

            
CodingList comprehension or generator expression — how do you choose?
              
Ask what happens next. If you consume it exactly once — sum, max, any, "".join, a single for loop, feeding another generator — use a generator expression. If you need to index it, take its len, sort it, iterate more than once, or hand it to something that will, use a list.
Two practical notes. When a generator expression is the only argument to a function you can drop the extra parentheses: sum(x*x for x in xs). And for small collections the difference is irrelevant — this is a decision that matters at scale, not a style rule to apply everywhere.

            

            
Deep diveWhat does yield from do?
              
It delegates to another iterable: yield from sub yields every item sub produces, and — the part people miss — also forwards send(), throw() and the sub-generator's return value back to the caller.
The obvious use is flattening a recursive structure without manual loops: a recursive generator that does yield from walk(child) for each child reads exactly like the tree it's walking. The other common use is composing pipeline stages while keeping laziness.
for x in sub: yield x is equivalent only for simple iteration; it loses the two-way protocol, which is why yield from was added rather than left as sugar.

DesignA row in your input is malformed. What do you do?

Fail the batch when partial results are dangerous — financial reporting, regulatory submissions, anything downstream that will treat your output as complete. A silently-30%-short revenue number is worse than a failed job.

GotchaWhy is except Exception: pass so bad?
              
Because it converts every failure — including your own typos, a KeyError from a renamed column, an out-of-memory condition — into silence, and the pipeline reports success with wrong numbers. In data work that's the worst possible failure mode: a loud crash gets fixed, a quiet wrong answer gets into a dashboard and then into a decision.
What to do instead: catch the specific exceptions you can actually handle; log the ones you swallow with enough context to find the record; and re-raise anything unexpected. If you truly want to ignore one specific error, contextlib.suppress(ValueError) at least says so explicitly.
The related sin worth naming: a bare except: (no exception class) also catches KeyboardInterrupt and SystemExit, so it can make a job impossible to Ctrl-C out of.

            

            
CodingWhat's else for in a try block?
              
It runs only if no exception was raised, and its purpose is to keep the happy path out of the try. If you put the success logic inside the try, you'll accidentally catch exceptions from that code too, which is how a genuine bug in your success handling gets misreported as a parse failure.
So the shape is: try the one risky operation, except the specific failures, else do the work that depends on success, finally clean up. It's a narrow tool but it makes the intent unambiguous, and it's a good detail to know because most people have never used it.

This is why you return NotImplemented instead of False for unknown types: returning False claims the objects are definitively unequal and prevents the other type from offering a sensible answer. It matters when comparing against a subclass or a compatible type from another library.

Likely interview questions

          

            
Deep diveWhat is the MRO and what does super() actually do?
              
The Method Resolution Order is the linearised sequence of classes Python searches for an attribute, computed by the C3 linearisation algorithm. It guarantees each class appears once, subclasses precede their bases, and the order you listed the bases is respected.
The correction that scores: super() does not mean “my parent class” — it means “the next class in the MRO of type(self)”. So in a diamond, a single super().__init__() chain visits every class exactly once, which is why the shared base isn't initialised twice.
That's what makes cooperative multiple inheritance work at all — and it's also why every class in such a hierarchy must call super() and accept compatible arguments. One class that skips it breaks the chain silently.

            

            
DesignInheritance or composition?
              
Composition by default. Inheritance couples you to a base class's internals, and the coupling compounds — a change three levels up breaks a subclass nobody remembered. Composition means holding a collaborator and delegating, which you can swap, test in isolation and reason about locally.
Use inheritance when there's a genuine is-a relationship and you need polymorphism — a framework requires you to subclass (a Django model, an Exception), or you're providing several interchangeable implementations of one interface.
The test: do you want the base class's interface, or just its code? Wanting the code is the wrong reason — that's what a helper function or a composed object is for. In data pipelines specifically, composition wins almost always: a Pipeline that has a loader, a transformer and a writer is far easier to test than one that inherits from all three.

            

            
PracticalWhen do mixins become a problem?
              
When there are more than two or three, when they have state, or when their order matters and nobody documented why. The symptom is a class declaration like class Job(A, B, C, D, Base) where reordering the bases changes behaviour and no one can predict how.
Mixins work best when they are stateless, single-purpose, and independent — each adding one method that doesn't interact with the others. Once two mixins both override the same method and rely on super() chaining, you've built something that requires reading the MRO to understand, which is a maintenance cost you'll pay repeatedly.
The alternative is usually composition or a plain decorator, and it's worth saying so rather than defending the mixin design.

Likely interview questions

          

            
CodingWrite a custom scikit-learn transformer.

Then follow the contract: __init__ stores parameters only, with attribute names matching argument names exactly (that's how get_params introspects them, and mismatching them breaks clone). fit(X, y=None) learns and stores state in trailing-underscore attributes and returns self. transform(X) uses only that fitted state and doesn't mutate the input.
The two mistakes to call out because they're the ones that actually happen: doing validation or computation in __init__ (breaks clone and therefore GridSearchCV), and computing statistics inside transform — which silently leaks test information into your features (§10.7).

            

            
DesignWhy must fit return self?
              
So calls chain — est.fit(X, y).transform(X) — and so Pipeline, GridSearchCV and cross_val_score can treat every step uniformly. Those internals do est = est.fit(...); a fit that returns None silently replaces your estimator with None, and the error surfaces much later as 'NoneType' object has no attribute 'transform'.
It's a convention rather than a language requirement, which is precisely why it's asked — it tests whether you've read the estimator contract or just copied a class skeleton.

            

            
GotchaYour transformer works alone but fails inside GridSearchCV. Why?
              
Almost certainly a clone problem. GridSearchCV clones the estimator for every fold and parameter combination, and clone works by calling get_params() and passing the result to __init__. So it breaks if: your __init__ renames or transforms an argument before storing it; your __init__ computes something that the cloned copy then lacks; you use *args/**kwargs in the signature (nothing to introspect); or you stored fitted state without a trailing underscore, so clone doesn't know to drop it.

6.1 Anatomy of an ndarray ⭐⭐

        
One sentence explains the entire library: an array is a flat memory buffer plus a dtype, a shape, and strides. Almost everything that feels like magic is just new strides over the same buffer.

Likely interview questions

          

            
Deep diveWhat are strides, and why do they matter?
              
Strides are the number of bytes to step to move one position along each axis. For a C-ordered int64 array of shape (3, 4) they're (32, 8): 8 bytes to the next column, 32 to the next row.
They matter because shape + strides is how NumPy maps an n-dimensional index onto a flat buffer, and that means several expensive-looking operations are free. reshape, transpose and basic slicing just produce new metadata over the same memory — O(1), no copying.
Two consequences worth stating. It explains views versus copies: if the result is expressible as strides over the existing buffer, you get a view; if not (fancy indexing, or reshaping a transpose), NumPy must copy. And it explains performance: iterating along the contiguous axis is cache-friendly, while iterating across it strides through memory and can be several times slower.

            

            
ConceptualWhat's the difference between C order and Fortran order?
              
C order (row-major) stores rows contiguously — the last axis varies fastest. Fortran order (column-major) stores columns contiguously — the first axis varies fastest. NumPy defaults to C order.
It matters for speed, not correctness: summing along the contiguous axis reads sequential memory and is cache-friendly, while summing across it jumps by a stride each step. On a large 2-D array that can be a 2–5× difference for the identical operation, which is why a.sum(axis=1) and a.sum(axis=0) don't always cost the same.
Where it surfaces in practice: a.T is F-contiguous, so passing a transpose into a library expecting C order can trigger a hidden copy; and some BLAS/LAPACK routines want Fortran order, so scikit-learn occasionally copies your data with np.asfortranarray. If you see an unexplained memory spike, a layout conversion is a good suspect.

Likely interview questions

          

            
Very commonWhat are the advantages of NumPy arrays over Python lists?
              
Three structural reasons, and they're worth giving in this order because each explains the next.
No boxing. A list of a million ints is a million pointers to a million int objects, each ~28 bytes with a refcount and type pointer. An array is a million raw 8-byte values. That's roughly 4–5× less memory.
One dtype. Because every element has the same type, the inner loop needs no per-element type dispatch — it runs in compiled C, not the interpreter.
Contiguous memory. One buffer means the CPU can prefetch and use SIMD instructions, so operations vectorise.
Net effect: typically 10–100× faster for elementwise numeric work, plus the API — broadcasting, slicing, aggregations, linear algebra. The cost to acknowledge: arrays are homogeneous and fixed-size, so appending is expensive and mixed types force an upcast.

            

            
PracticalWhen would you still use a Python list?
              
When the data is heterogeneous (mixed types that shouldn't be coerced), when you're growing it incrementally (list.append is amortised O(1); np.append reallocates and copies the whole array every time, so building an array in a loop is O(n²)), when it's small enough that NumPy's fixed overhead dominates, or when you need to hold arbitrary Python objects.
The idiomatic pattern that follows: accumulate in a list, convert once — np.array(rows) at the end. That's the same lesson as not growing a DataFrame row by row (§2.3).

Fixed-width integers wrap around without warning. This is a real source of wrong numbers in feature engineering, and it does not happen with Python ints.

Python's own int handles 2**70 fine; np.int64 raises.

        


        

          
Likely interview questions

          

            
GotchaYour sum of a downcast column is negative. What happened?
              
Integer overflow. NumPy integers are fixed-width and wrap silently — no exception, no warning. If you downcast a column to int16 to save memory, the individual values fit but the aggregate exceeds 32,767 and wraps around, often to a negative number.
Fixes: aggregate with an explicit accumulator, arr.sum(dtype=np.int64), which is the cleanest; or promote before summing. And before downcasting at all, check the range against np.iinfo(dtype).max — with headroom for future growth, not just today's data.
The general lesson worth stating: memory optimisation by downcasting is real and useful (§9.4), but it introduces a correctness risk that plain int64 does not have. Downcast storage, compute in a wider type.

            

            
Conceptualfloat32 or float64 for machine learning?
              
float32 for most model training: half the memory and bandwidth, and on GPUs substantially faster. Deep learning trains in float32 or lower (bfloat16/float16) routinely, because gradient noise dwarfs the extra precision.
float64 when precision genuinely matters: accumulating a sum over millions of rows (float32 has ~7 significant digits, so a long summation loses low-order bits — this is catastrophic cancellation), financial calculations, or iterative numerical methods that amplify error. Note pandas and NumPy default to float64 for exactly this reason.
The practical compromise: store in float32, accumulate in float64 — arr.mean(dtype=np.float64). And never test float equality; use np.isclose or np.allclose with an explicit tolerance (§6.10).

            

          

        

      


      

        
6.4 Views vs copies ⭐⭐

        
The question that separates people who have debugged a real aliasing bug from people who have read about one. A slice of an array can mutate its parent.

          How to check, rather than guess

Likely interview questions

          

            
Very commonWhen does NumPy return a view and when a copy?
              
View when the result can be expressed as new strides over the same buffer: basic slicing (a[2:6], a[::2]), reshape when compatible, transpose, and .view().
Copy when it can't: fancy indexing (an integer array or list of indices), boolean masking, any arithmetic (a + 1), .copy(), and reshaping a non-contiguous array.
The reason is the mechanism from §6.1: a view is just metadata, so it's only possible when the selection is a regular strided pattern. Fancy indexing picks arbitrary positions, which no stride can describe.
Why it matters: a view writes through to the parent, so mutating a slice changes the original — the aliasing bug from §1.1 with numeric data. And check rather than assume: arr.base is not None or np.shares_memory(a, b).

            

            
DebugA function you called changed your array. How did that happen?
              
Either it mutated the array in place, or it mutated a view it derived from your array. Both are visible to you because arrays are mutable and views write through (§1.1).
Diagnosis: check whether the function does in-place operations (arr += 1, arr[mask] = x, np.sort(arr) vs sorted, or any ufunc with out=). Then check whether what it received was a view of something bigger.
Prevention, in order: pass a copy if you don't trust the callee; hand it a read-only view (v = arr.view(); v.flags.writeable = False) so an in-place write raises immediately rather than corrupting silently; and by convention, make your own functions return new arrays unless in-place behaviour is in the name.

Likely interview questions

          

            
Deep diveWhat does a[[0,1,2], [3,2,1]] return?
              
Three elements — [a[0,3], a[1,2], a[2,1]] — because fancy indexing broadcasts the index arrays against each other and pairs them elementwise. It does not select a 3×3 block.

The distinction matters at scale: on ten million values, argpartition is several times faster, and it's the NumPy equivalent of the bounded-heap answer from §2.6.
Then the practical bit: these return indices, which you use to index the original array or a parallel one — names[idx], df.iloc[idx]. Forgetting that argsort gives positions rather than values is a common slip.

            

          

        

      


      

        
6.7 Broadcasting ⭐⭐

        
How NumPy operates on arrays of different shapes without copying them. Three rules, and they are worth memorising verbatim because the error messages assume you know them.


        

        

          
Run itbroadcasting.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: a + row adds the row to every row. a + col raises operands could not be broadcast together with shapes (3,4) (3,), and col[:, None] — shape (3, 1) — fixes it by adding per row. Standardised columns come out with mean ≈0 and std ≈1. The outer product is the 3×3 multiplication table. The last block makes the memory point: the operands broadcast for free, but the result is materialised at full size.

        


        

          
Likely interview questions

          

            
Very commonExplain broadcasting.
              
It's how NumPy applies an elementwise operation to arrays of different shapes without you writing a loop or copying data. Three rules: right-align the shapes; a missing leading dimension counts as 1; each dimension must then be either equal or 1, and a 1 is stretched to match.
The mechanism is the part worth adding: a stretched dimension is implemented with stride 0, so the same memory is read repeatedly rather than duplicated. That's why broadcasting costs nothing for the operands — though the result is a full-size array, which is the memory trap people hit on large data.
Canonical example: standardising columns, (X - X.mean(axis=0)) / X.std(axis=0), where a (n, k) array meets a (k,) vector. And the fix for the failing case is almost always [:, None] to insert an axis so the shapes align the way you intended.

            

            
Debug“operands could not be broadcast together with shapes (1000,) (1000,1)”. What's wrong?
              
Right-align them: (1000,) becomes (1, 1000) and you're comparing (1, 1000) with (1000, 1). Both dimensions are 1-or-equal, so it actually succeeds — and produces a 1000×1000 array, which is usually not what you wanted and may blow your memory.
That's the more dangerous version of this bug: broadcasting silently giving you an outer product where you expected an elementwise result. The usual cause is a stray (n, 1) shape from a scikit-learn predict, a reshape(-1, 1), or a DataFrame column selected with double brackets.
Fixes: .ravel() or .squeeze() the (n, 1) down to (n,), and assert shapes at function boundaries — assert y.shape == (n,) catches it at the source rather than as a memory error three lines later. Printing .shape is the first thing to do with any broadcasting confusion.

Likely interview questions

          

            
Very commonWhat does axis=0 actually mean?
              
The axis you name is the one that disappears. For a (3, 4) array, sum(axis=0) collapses the 3 rows and returns 4 values — one per column. sum(axis=1) collapses the 4 columns and returns 3 values — one per row.
That phrasing works in any number of dimensions and avoids the “is axis 0 rows or columns” muddle. The muddle exists because people describe axis=0 as “rows” while it computes a result per column — both true, which is why the collapse framing is safer.
Same rule in pandas: df.sum(axis=0) gives a value per column, df.mean(axis=1) a value per row. The confusing exception is df.drop(..., axis=1), where axis names what you're addressing rather than what collapses — which is exactly why the modern API prefers df.drop(columns=[...]).

            

            
CodingWhy use keepdims=True?
              
It keeps the reduced axis as size 1 instead of removing it, so the result broadcasts straight back against the original. a / a.sum(axis=1, keepdims=True) row-normalises in one expression; without it you get shape (3,), which right-aligns as (1, 3) and either fails or — worse — silently broadcasts the wrong way.
It's the tidy alternative to sprinkling [:, None], and it makes the intent explicit. Use it whenever a reduction feeds straight back into an operation with the original array — normalising, centring, computing softmax, subtracting a per-row max for numerical stability.

All three agree to within floating-point tolerance. The closing note is the senior point: broadcasting builds an (n, m, 3) intermediate, so at n=m=20,000 it would need ~10 GB, while the algebraic form only ever holds (n, m).

        


        

          
Likely interview questions

          

            
Very commonWhat is vectorisation, and why is it faster?
              
Expressing a computation as operations on whole arrays rather than element-by-element in Python. The speedup comes from three things, and naming them beats saying “it's implemented in C”.
No interpreter overhead per element — one C loop instead of a million bytecode dispatches, each with reference counting and type checks. SIMD — the CPU processes several values per instruction on contiguous data. Cache efficiency — sequential access with prefetching, versus chasing pointers to scattered int objects.
Typical gains are 10–100×, and for anything reducible to matrix multiplication you get more, because it lands in a hand-tuned BLAS kernel.
The honest caveat worth adding: vectorisation often trades memory for speed. A broadcast intermediate can be far larger than either input, so on big data the fastest formulation is sometimes the one that avoids materialising it — as in the distance example, where the algebraic identity beats broadcasting.

            

            
CodingVectorise pairwise Euclidean distances.
              
Broadcasting version: diff = A[:, None, :] - B[None, :, :] then np.sqrt((diff**2).sum(axis=-1)). Shapes (n,1,d) and (1,m,d) broadcast to (n,m,d), and summing the last axis gives (n,m).
The better version for large n: use |a−b|² = |a|² + |b|² − 2a·b, so d2 = a2[:, None] + b2[None, :] - 2 * A @ B.T. This never materialises the (n,m,d) intermediate and pushes the heavy work into BLAS.
Two details that show care: clip with np.maximum(d2, 0) before the square root, because floating-point error can produce tiny negatives on the diagonal; and mention that in practice you'd call scipy.spatial.distance.cdist or sklearn.metrics.pairwise_distances, which handle chunking and numerical edge cases for you.

            

            
GotchaIs np.vectorize a way to vectorise code?
              
No — and this is a deliberate trap. The docs say so explicitly: np.vectorize is a convenience wrapper that provides broadcasting semantics for a scalar function, but it loops in Python internally. It is essentially as slow as the loop you started with.
What actually vectorises: expressing the logic with array operations; np.where or np.select for conditionals; boolean masks for filtering; np.digitize/searchsorted for binning; and existing ufuncs.
When the logic genuinely can't be expressed that way — an irreducible scalar loop with branching — the real answers are Numba (@njit, often 100×) or Cython. Naming np.vectorize as a performance tool is a reliable tell that someone hasn't measured it.

Plain sum/mean/max return nan; the nan* variants skip it. The float32 cancellation loses the +1 entirely, giving 0.0, while float64 gets it right. Two generators with the same seed produce identical draws.

        


        

          
Likely interview questions

          

            
Very commonWhy is 0.1 + 0.2 != 0.3?
              
Because binary floating point cannot represent 0.1, 0.2 or 0.3 exactly — they're stored as the nearest representable binary fractions, and the rounding errors don't cancel. The sum is 0.30000000000000004.
Consequences and fixes: never test float equality — use math.isclose or np.isclose/np.allclose with explicit tolerances, and pd.testing.assert_frame_equal for frames. For money, use decimal.Decimal or integer minor units, because a fraction of a penny per row compounds.
The related deeper issue worth mentioning: floating-point addition is not associative, so summation order changes the result. That's why parallel or chunked sums can differ slightly from a serial sum, and why np.sum uses pairwise summation to reduce error rather than a naive accumulator.

            

            
GotchaHow do you count and handle NaN correctly?
              
Count: np.isnan(a).sum(), or df.isna().sum() in pandas. Never a == np.nan — NaN is not equal to itself by IEEE-754 design, so that comparison is always False.
Aggregate: plain sum/mean/max propagate NaN, returning NaN for the whole array. Use np.nansum, np.nanmean, np.nanmax to skip them. Note pandas does the opposite by default — df.mean() skips NaN via skipna=True — which is a genuine inconsistency between the two libraries and a good thing to flag.
Two more traps: np.sort silently places NaN last, so a “maximum” taken from a sorted array may be NaN; and NaN only exists in float dtypes, so an integer column with missing values becomes float64 — or, in modern pandas, a nullable Int64 with pd.NA (§7.6).

            

            
PracticalHow do you make random results reproducible?
              
Use the modern generator API: rng = np.random.default_rng(42) and pass rng explicitly to whatever needs randomness. Avoid np.random.seed(), which mutates hidden global state — any library that also draws from the global stream changes your results, and it's not thread-safe.
For a whole pipeline you need more than NumPy: seed Python's random, set PYTHONHASHSEED, pass random_state to every scikit-learn estimator and splitter, and seed your framework (torch.manual_seed). For independent parallel streams use rng.spawn(n) rather than seeding each worker with seed + i, which can produce correlated streams.
And the honest caveat: seeds are necessary but not sufficient. Thread counts, GPU kernels, floating-point summation order and library versions all introduce nondeterminism — which is why reproducibility also means pinning versions (§10.12).

Very commonWhat is a DataFrame, really?

Two consequences follow, and they explain a lot of the rest of pandas. It matters more than it looks. scikit-learn generally wants 2-D for X and 1-D for y, so X = df[['feature']] and y = df['target'] is the correct pairing — getting it backwards produces shape errors, or worse, a silent broadcast (§6.7). Series and DataFrame also have different methods and different .apply semantics, so a function written for one can behave oddly on the other.

Likely interview questions

          

            
DebugYou assigned a column and got NaNs. Why?
              
Index alignment. Assigning a Series to a DataFrame column matches on the index, not on position. If the Series came from a filtered frame, its index has gaps — so the rows that were filtered out get NaN.
Three fixes, each appropriate in different situations. .to_numpy() (or .values) to force positional assignment — correct only if you're certain the order matches. .reset_index(drop=True) on both sides before combining. The framing that shows understanding: alignment is a feature — it's what makes df['a'] / df['b'] safe across differently-ordered frames — and this bug is that feature meeting an unintended index.

            

            
GotchaYour row count went up after an operation you thought was elementwise.

Diagnose with df.index.is_unique or df.index.duplicated().sum(). Fix by resetting the index, aggregating to make labels unique, or being explicit about the join you actually wanted.
The habit worth stating: assert the row count after any align, merge or concat. It's one line and it catches this class of bug at the point it happens rather than three transformations later.

The recommended path is upgrade to 2.3 first, clear every warning, then move to 3.0.

            

            
PracticalWhen would you use the category dtype?
              
For low-cardinality columns — a few hundred distinct values or fewer across many rows. It stores the distinct values once and the column as small integer codes, so a country column over ten million rows goes from hundreds of megabytes to a few.
It also makes groupby and merges on that column faster, and it lets you declare an ordering (CategoricalDtype(ordered=True)), which makes < comparisons and sorting meaningful for things like ordinal survey responses.
The gotchas worth naming: appending an unseen value gives NaN rather than adding a category; groupby on a categorical includes unobserved combinations by default, which can produce a surprisingly large result (use observed=True); and for a high-cardinality column like a user id, categorical is worse than a plain string because the category mapping is nearly as big as the data.

            

            
GotchaWhy did your integer column become float?
              
Because it contains missing values, and the classic NumPy-backed int64 dtype has no representation for NaN. pandas silently upcasts to float64 so it has somewhere to put the NaN. The visible symptoms are ids printing as 12345.0 and, past 2⁵³, actual precision loss on large integer ids.
Fix: use the nullable integer dtype — Series([...], dtype="Int64") with a capital I — which stores an integer array plus a separate boolean mask and uses pd.NA. Or specify dtypes at read time so it never happens.
Same trap applies to booleans: a bool column with missing values becomes object, and the nullable equivalent is "boolean". This is the single most common cause of “my join key stopped matching” — one side is int64, the other became float64.

The hasattr check should report False or a deprecated shim, because the warning class was removed in 3.0.

        


        

          
Likely interview questions

          

            
ModernWhat is SettingWithCopyWarning and how do you fix it?
              
Lead with the currency, because this is the version of the question that shows you're current: in pandas 3.0 it no longer exists. Copy-on-Write became the only mode in January 2026, and because indexing results are now unambiguously copies, the warning had nothing left to warn about and was removed.
What it was: pandas couldn't tell whether df["a"][mask] = x would modify the original or a temporary, because df["a"] might return a view or a copy depending on dtypes and internal block layout. The warning meant “this might not do what you want” — and it fired on correct code too, which is why everyone learned to ignore it.
What happens now: chained assignment reliably does nothing — it writes to a temporary that's immediately discarded. Silent, but at least consistent, and the fix was always the same: one .loc call, df.loc[mask, "a"] = x.

            

            
ModernWhat is Copy-on-Write, and is it faster or slower?
              
Faster, which surprises people who assume “more copies”. Under CoW, every indexing result behaves as an independent copy, but pandas doesn't actually duplicate the data until something writes to it. So reads share memory and only a genuine mutation triggers the copy.
The performance win is that it lets pandas remove defensive copies it previously made because it couldn't prove they were unnecessary. And it lets you remove the .copy() calls that were idiomatic after every filter — under CoW those force an eager copy that would otherwise never have happened, so deleting them is a real memory improvement on upgrade.
The behavioural change to be precise about: mutating a slice can no longer reach back into the parent frame. Any code that relied on that — deliberately or accidentally — silently stops working, which is the main upgrade risk.

            

            
GotchaDoes inplace=True save memory?
              
Generally no — and this is a persistent myth worth correcting. Most inplace operations still build a new object internally and then rebind it, so peak memory is similar. What inplace=True saves is a variable name, not memory. Under Copy-on-Write it's even less meaningful, and the pandas team has been steadily deprecating it.
The practical arguments against it: it returns None, so it breaks method chaining; it mutates a frame someone else may hold a reference to, which is the §1.1 aliasing problem; and it makes code harder to reason about because you can't see the transformation as a value.
Prefer df = df.rename(...) or a chain with .assign() and .pipe(). If you genuinely need to reduce peak memory, the levers are dtypes, usecols, chunking and dropping columns early (§9.4) — not inplace.

Likely interview questions

          

            
Very commonHow do you handle missing values?
              
Start with the question that determines everything else: why are they missing? Missing completely at random, missing at random given other features, or missing not at random — where the missingness itself carries signal (income unreported by high earners, a sensor that fails under load).
Then the options. Drop rows only when few and plausibly random — quantify the loss first. Drop the column if mostly empty. The two points that make this a senior answer. Add a missingness indicator — col_was_missing — because for MNAR data that flag is often more predictive than the imputed value. And fit the imputer on train only, inside a Pipeline, or you've leaked test statistics into training (§10.7).

            

            
ConceptualNaN vs None vs pd.NA?
              
np.nan is a float — an IEEE-754 value that propagates through arithmetic and is never equal to itself. It's the historical missing marker for NumPy-backed numeric columns, which is why an integer column with gaps upcasts to float64.
None is Python's null object. In an object column it can sit alongside other values; pandas usually converts it to NaN in numeric contexts.
pd.NA is the newer, dtype-agnostic sentinel used by the nullable dtypes (Int64, boolean, str). It propagates in comparisons too — pd.NA > 1 is pd.NA, not False — which is more logically consistent and occasionally surprising in boolean masks.
Practical takeaway: always test with .isna(), never == np.nan or is None; and prefer nullable dtypes when you need integers or booleans that can be missing.

Very commonExplain groupby.

Same rows as the input, with the group's result broadcast back to every member. This is how you add a group statistic as a column.

Anything. Receives the whole sub-frame, can return a scalar, Series or frame. Flexible and slow — a Python call per group.

Keeps or drops whole groups by a predicate. Easy to confuse with row filtering.

Likely interview questions

          

            
Very commonagg vs transform vs apply?
              
Shape is the deciding factor. agg reduces each group to a scalar, so you get one row per group. transform returns a value per input row, broadcasting the group result back, so the output has the same index as the input. apply receives the whole sub-frame and can return anything.
Then the practical rule: use transform when you want to add a group statistic as a column — df["grp_mean"] = df.groupby("g")["v"].transform("mean") — because it aligns automatically. Use agg for summary tables. Use apply only when the operation genuinely needs multiple columns of the group at once.
And the performance note: agg/transform with a named string function ("mean", "sum") dispatch to a Cython implementation, while apply and lambdas run Python per group — typically 5–30× slower. So .agg("mean") beats .apply(lambda s: s.mean()) for the identical result.

            

            
CodingAdd a column with each row's percentage of its group total.
              
df["pct"] = df["val"] / df.groupby("grp")["val"].transform("sum").
This is the canonical transform use case, and it's worth explaining why the alternatives are worse. With agg you'd get a 2-row result that you then have to merge or map back — more code, an extra join, and a chance of misalignment. With apply you'd be running Python per group for no benefit. transform broadcasts the group total to every member row automatically and aligns on the index.
The same pattern covers most within-group feature engineering: rank within group, deviation from group mean, share of group, group-wise z-score, and group-wise forward-fill.

            

            
GotchaWhat's the difference between groupby().filter() and boolean masking?
              
groupby().filter(fn) evaluates the predicate per group and keeps or drops every row of that group together. Boolean masking evaluates per row.
So df.groupby("user").filter(lambda g: len(g) >= 5) keeps all rows for users with at least five records, and drops all rows for the rest — you cannot express that with a row mask without first computing a group size. Conversely df[df["val"] > 10] keeps individual qualifying rows regardless of their group.
The idiom worth knowing as an alternative: df[df.groupby("user")["val"].transform("size") >= 5] does the same thing with transform, and is usually faster than filter because it avoids the per-group Python call.

Likely interview questions

          

            
GotchaYour group totals don't add up to the overall total. Why?
              
groupby drops rows with a missing key by default (dropna=True). Any row whose grouping column is NaN vanishes from the output entirely, with no warning — so the group sums are legitimately less than the column sum.
Fixes: pass dropna=False to get an explicit NaN group; or, better for a pipeline, fillna("UNKNOWN") on the key first so the missing category is a first-class value you can see and report on.

With a single key that's mildly annoying; with two or three categorical keys it produces the full cross-product of all category levels, which can be thousands of empty rows and a large memory spike.
Pass observed=True to get only the combinations that actually occur. The behaviour does have a legitimate use — guaranteeing a complete grid for a report or a pivot where you want zeros for absent combinations — but it should be a deliberate choice.

2. Assert the row count. For a left join enriching a table, assert len(out) == len(left). If it grew, your right side had duplicate keys.
3. indicator=True then inspect _merge.value_counts() — how many matched, how many are left-only. An unexpectedly large left_only count usually means a dtype mismatch or whitespace in the keys (§7.7).
4. Check null rates on the newly-added columns before and after.

Likely interview questions

          

            
DebugYour row count went from 1M to 4M after a join. What happened and how do you fix it?
              
A many-to-many match. The join key is duplicated on one or both sides, so pandas produces the cross-product for each key — m left rows × n right rows per key. Every downstream sum, count and average is now wrong, and nothing raised.
Diagnose: right["key"].is_unique, or right["key"].duplicated().sum(). Add indicator=True to see the match breakdown.
Fix depending on intent. If the duplicates are genuine data-quality noise, drop_duplicates(subset="key") — but decide which row wins, with a sort, rather than taking an arbitrary one. If the many-to-many is genuinely what you want, keep it but make it explicit and re-check your aggregations.
Prevent: validate="many_to_one" plus assert len(out) == len(left) on every enrichment join.

            

            
PracticalYour left join produced far more NaNs than expected.
              
The keys aren't matching, and it's almost never a logic error — it's a data-hygiene one. In order of likelihood:
dtype mismatch — int64 on one side, float64 or str on the other (§7.3), so 1 never equals 1.0 or "1". Whitespace or case — "UK " vs "UK"; check with repr(), which makes trailing spaces visible. Leading zeros stripped by a CSV read on one side only. Different granularity — you're joining a daily table to a monthly one.
Diagnostic recipe: compare dtypes; look at set(left_keys) - set(right_keys) for a handful of examples; and use indicator=True to quantify how many rows are left_only. Fix at the source by normalising key columns — strip, casefold, cast to a declared dtype — as a documented step before any join.

The details that matter: both frames must be sorted on the join key or the result is silently wrong; use by= to match within an entity (per customer, per symbol); and use tolerance= so an unreasonably stale match becomes NaN rather than a misleading value.
Why it's the right answer rather than a plain merge: joining on a naive key gives every fact row the current dimension value, which encodes information from after the event. The model then looks excellent in backtest and fails in production — the classic leakage failure (§10.7).

Very commonpivot vs pivot_table?

Long (tidy) for storage and processing; wide for presentation and modelling.
Long — one row per observation, with the variable name in a column — is easier to extend (a new month is new rows, not a schema change), plays well with groupby, and is how databases and Parquet files naturally store event data. Wide is what a human wants to read and what a model wants as a feature matrix.
melt goes wide→long and pivot/pivot_table goes long→wide, so treat the wide form as a view you materialise at the end of a pipeline rather than the thing you keep. The tell that you've got it backwards: a schema migration every time a new period arrives.

Likely interview questions

          

            
Codingresample vs groupby?
              
resample is a groupby, specialised for a datetime index: it groups into regular time bins. The differences that matter are that it produces a complete, evenly-spaced set of bins — including empty ones, which groupby would omit — and it understands frequency strings and calendar semantics like month-end.
So df.resample("ME").sum() gives a row for every month in the range even if some had no data, which is what you want for a chart or a time-series model. df.groupby(df.index.month).sum() would silently skip empty months and would also collapse different years together.
Also worth knowing: resample both downsamples (aggregate) and upsamples (then ffill/interpolate to fill), and Grouper(freq=...) lets you combine a time bin with other grouping keys in one groupby.

            

            
GotchaWhat's the timezone trap?
              
Mixing naive and aware timestamps. A tz-naive timestamp has no offset; a tz-aware one does. Comparing or subtracting one from the other raises TypeError, and — worse — concatenating frames where one side is naive can silently produce an object column that stops behaving like a datetime.
The discipline: store everything in UTC, convert to local only for display. tz_localize attaches a timezone to a naive timestamp; tz_convert changes an aware one. Getting those two confused shifts your data by hours.
Then the DST edge cases, which are the ones that actually cause incidents: on a spring-forward day some local times don't exist and on autumn-back some are ambiguous, so tz_localize raises unless you pass nonexistent= and ambiguous=. Daily aggregates in local time also have 23- and 25-hour days, which quietly breaks any “per hour” average.

            

          

        

      


      

        
8.9 Windows and lag features without leakage ⭐⭐

        
Where a pandas question becomes a machine-learning question. A rolling mean computed without shifting includes the current row — so your feature contains its own target.

And the last pair shows a count-based window ignoring the 18-day gap while rolling("3D") correctly isolates the 20th.

        


        

          
Likely interview questions

          

            
DesignHow do you build a rolling-average feature without leakage?
              
.shift(1) before .rolling(). By default rolling(3) includes the current row, so a “past 3 days average” feature actually contains today's value — and if you're predicting today's value, the feature contains the target. The model scores brilliantly in backtest and fails in production.
Correct form: df["sales"].shift(1).rolling(3).mean() — shift first so the window sees only prior rows.
For panel data the order matters too: sort by entity and time, group by entity, then shift, then roll — df.groupby("user")["v"].transform(lambda s: s.shift(1).rolling(3).mean()). Rolling across the whole frame without grouping bleeds one user's history into another's features.
And use rolling("3D") rather than rolling(3) when the series has gaps, so the window is three days rather than three rows.

            

            
Codingrolling vs expanding vs ewm?
              
rolling(n) — a fixed-width window; older observations drop out entirely. Use when only recent history is relevant.
expanding() — everything from the start up to now, so the window grows. Use for cumulative statistics like a running mean or a to-date total.
ewm() — exponentially weighted; all history contributes but with geometrically decaying weight, controlled by alpha, span or halflife. Use when recent data matters more but you don't want a hard cutoff, and it's smoother than a rolling mean because there's no abrupt drop-out.
All three take min_periods, which controls the warm-up: by default rolling(3) gives NaN for the first two rows, and min_periods=1 fills them with partial windows. Whether that's right depends on whether a partial window is meaningful for your feature — silently accepting the default is how you get a model that can't score the first rows of every new entity.

Very commonHow would you speed up a slow pandas operation?

9.3 Why apply is a loop ⭐

        
The most common misconception in pandas performance. apply is not vectorised — it calls your Python function once per row or per group.

Likely interview questions

          

            
GotchaIs df.apply vectorised?
              
No. It calls your Python function once per row (axis=1) or once per column (axis=0), so you pay full interpreter overhead per call. With axis=1 it also constructs a Series object for every row, which is why it's barely faster than iterrows.
What to use instead, by case: arithmetic → plain column expressions; conditionals → np.where or np.select; binning → pd.cut; lookups → .map(dict); joins → merge; strings → the .str accessor; dates → the .dt accessor.
When apply is genuinely fine: small data where clarity beats speed, or logic that truly can't be expressed as array operations — and then say what you'd do if it were the bottleneck (Numba, or restructure the problem).

np.select([cond1, cond2, cond3], ["a", "b", "c"], default="other"). Conditions are evaluated in order and the first match wins, so it maps directly onto an if/elif chain — which makes the translation mechanical.
For two branches, np.where(cond, x, y). For numeric banding, pd.cut with explicit bin edges is clearer and gives you an ordered categorical for free. For a lookup from a mapping, df["col"].map(mapping) beats both.
The detail worth mentioning: np.select evaluates every condition over the whole column, so if one condition is very expensive you're paying for it on all rows — occasionally a reason to restructure. But it's still typically two orders of magnitude faster than the equivalent apply.

Very commonYour DataFrame doesn't fit in memory. What do you do?
              
Read less, store it smaller, or don't hold it all at once — in that order, because the first is free.

Related: pandas 3.0's PyArrow-backed str dtype stores strings compactly rather than as individual Python objects, so the gap between shallow and deep is much smaller than it used to be — one of the practical wins of upgrading (§7.3).

CodingCompute a group mean over a file that doesn't fit in memory.

Likely interview questions

          

            
Very commonWhat is the GIL?
              
The Global Interpreter Lock — a mutex in CPython that allows only one thread to execute Python bytecode at a time. Its purpose is memory management: it makes reference counting and internal structures safe without fine-grained locking everywhere, which also makes single-threaded Python faster.
The consequence: threads don't speed up CPU-bound pure-Python code. But the nuance that scores is what the GIL doesn't block — it's released during I/O and during compiled extension work. So threads help a lot for network and disk work, and NumPy, pandas, scikit-learn and BLAS already run their heavy kernels in parallel because they drop the GIL.
Which means for data work the GIL is much less of a constraint than its reputation suggests: the expensive parts were never running under it.

            

            
ModernWhat changed with free-threaded Python?
              
PEP 779: as of Python 3.14, the free-threaded build is officially supported — it moved from experimental to a supported configuration. It's a separate build of CPython compiled without the GIL, so the default interpreter still has one; you opt in.
What it enables: genuine multi-core parallelism for CPU-bound pure-Python code using threads, without the memory duplication and pickling costs of multiprocessing.
The honest caveats, which are the interesting half of the answer. Single-threaded performance on the free-threaded build is somewhat slower, since removing the GIL requires extra work in the object model. C extensions must be explicitly compatible, and the ecosystem has been catching up — NumPy 2.5 improved its free-threading support, for instance. And you now have to think about data races in Python code that the GIL used to paper over.
Practical position for 2026: promising and worth tracking, but for data work the existing answers — vectorised C code, multiprocessing, joblib — still cover most cases.

Likely interview questions

          

            
Very commonThreads, processes or async — how do you choose?
              
Ask what the work is doing.
I/O-bound (network, disk, database): ThreadPoolExecutor for tens to hundreds of concurrent operations — simple, shared memory, and the GIL is released while waiting. asyncio when you need thousands, because a coroutine costs far less than a thread — but only if the whole path is async.

And the 2026 footnote: free-threaded 3.14 (§9.6) makes threads viable for CPU-bound Python too, though not yet the default.

            

            
GotchaWhat goes wrong with multiprocessing in data code?
              
Pickling and memory. Everything crossing the process boundary must be picklable, so lambdas, closures and local functions fail — which is why functools.partial and module-level functions matter (§3.7). And a large DataFrame passed as an argument is serialised and copied into every worker, so eight workers can mean eight copies plus the serialisation time, which frequently makes the parallel version slower.
Then the platform difference: fork (Linux default historically) shares memory copy-on-write and is fast but unsafe with threads; spawn (macOS and Windows default, and increasingly the default generally) re-imports your module in each child — so any module-level code runs again, and you need the if __name__ == "__main__" guard or you get infinite process spawning.
Practical mitigations: pass file paths or ranges rather than data and let workers load their own slice; use joblib, which memory-maps large arrays instead of pickling them; and measure — parallelism has real fixed costs and often loses on medium-sized work.

DesignWhen is Numba the right answer?
              
When the algorithm is genuinely a scalar loop with data-dependent branching or carried state that no array expression can capture — a custom recursive filter, a path-dependent simulation, a bespoke distance with early exit. Add @njit and you often get 50–200× with the same code.
Before reaching for it, try two cheaper things: vectorise, and restructure the problem — many “inherently sequential” loops become segment-wise cumsums, sorts or joins once you find the right formulation, which needs no new dependency.
The costs to acknowledge: JIT compilation on first call (annoying in short-lived jobs, fixable with caching or AOT), support for only a subset of NumPy and almost no pandas, obscure error messages when you stray outside it, and a heavyweight dependency. It's a targeted tool for a hot kernel, not a general accelerator.

PracticalWhy logging instead of print?
              
Levels, routing and structure. Levels let you change verbosity at runtime without editing code — DEBUG locally, INFO in production, and turn DEBUG on for one module when investigating. Config outside the code, secrets outside the config. That gives you validation, one place to look, and the ability to log the whole config with the run.
Secrets come from the environment or a secret manager, are never written to a file that could be committed, and are never logged. Redact them at the boundary — log the host, not the DSN.
Two habits worth adding: make the config object frozen so it can't drift mid-run and diverge from what you logged; and fail fast at startup if a required value is missing, rather than three hours in when the write step finally needs the credential.

Likely interview questions

          

            
Very commonHow do you test a data pipeline?
              
Test the transformations, not the data. Each transformation should be a pure function taking a frame and returning a frame, which makes it testable with a hand-built fixture of five rows and a known answer.
Then the four layers. Unit tests on each transformation with a tiny fixture. Edge cases, which is where the value is: empty frame, all-NaN column, a single row, duplicate keys, an unseen category, a NaN group key. And the cultural half: every production bug becomes a test before it's fixed.

Separate what's deterministic from what isn't. Most of a training pipeline is deterministic given a seed: the feature transformations, the split logic, the schema of the output. Test those normally.
For the model itself, don't assert exact numbers — assert properties and bounds: the pipeline runs end to end on a small fixture; the output shape and dtypes are right; predicted probabilities lie in [0, 1]; performance on a fixed holdout is above a threshold rather than equal to a value; and a deliberately shuffled-label run performs no better than chance, which is a genuinely good test that catches leakage.
Then fix every seed and pin versions so a change in output is a signal rather than noise. And use golden files for regression: store last known-good predictions and compare with a tolerance, so an unintended behaviour change is caught even if you can't specify the right answer in advance.

Likely interview questions

          

            
Very commonWhy use a scikit-learn Pipeline?
              
Because it makes leakage structurally impossible. Every transformer's fit is called only on the training portion, so when you cross-validate, the imputer's median and the scaler's mean are recomputed inside each fold from that fold's training data alone. Pass that grid to GridSearchCV(pipe, grid, cv=5) and every combination is evaluated with the preprocessing refitted per fold — so the comparison between imputation strategies is itself leak-free, which it wouldn't be if you preprocessed once up front.
Worth adding: you can swap whole steps, not just parameters, by putting the estimator itself in the grid ({"clf": [LogisticRegression(), RandomForestClassifier()]}), which is how you compare models on identical preprocessing.

Very commonWhat is data leakage and how do you prevent it?
              
Any information in your features that wouldn't be available at prediction time. The model learns from it, scores brilliantly in validation, and fails in production — and the code runs perfectly, which is why it survives.
Name the flavours: preprocessing (scaler or imputer fitted before the split); feature selection using all the labels; target leakage (a feature derived from the outcome, like days_until_churn); temporal (a random split on time-ordered data, or an unshifted rolling feature); group (the same customer in train and test); duplicate rows split across both.
Prevention: put all preprocessing and selection in a Pipeline so it refits per fold; choose the right splitter — TimeSeriesSplit for temporal, GroupKFold for entities; deduplicate before splitting; and audit every feature with the question “would I have this value at the moment I need the prediction?”
And the detection tests: an implausibly high score, a single feature with suspicious importance, and a shuffled-label run that should score at chance.

            

            
DebugYour model gets 0.99 AUC in CV and 0.6 in production. Diagnose it.
              
Assume leakage first — a 0.39 AUC gap is almost never distribution shift alone.
Check in this order. Feature importances: one feature dominating is the classic signature of target leakage; trace where it comes from and when it becomes available. Split strategy: was the data time-ordered and split randomly? Does the same entity appear in both sides? Were duplicates removed before splitting? Preprocessing order: was anything fitted outside the pipeline, on the full dataset? Feature timestamps: for each feature, is its value knowable at prediction time — a point-in-time join issue (§8.6)?
Then the confirming test: shuffle the labels and re-run. If accuracy stays well above chance, information is reaching the model through a channel you haven't accounted for.
And rule out the non-leakage explanations so the answer is complete: train/serve skew (features computed differently in production), a genuinely shifted population, or a label definition that differs between the training data and reality.

            

            
DesignHow do you split time-series data?
              
Chronologically — never randomly. A random split lets the model train on next month and predict last month, which is not a task it will ever face. Use TimeSeriesSplit, which produces expanding (or rolling) windows where the validation fold is always after the training fold.
Two additional requirements. A gap between train and validation if your features use a lookback window or your label has a horizon, otherwise the windows overlap and leak. And features shifted so each row uses only prior information (§8.9) — a rolling mean that includes the current row leaks the target.
If the data is both temporal and grouped — many customers over time — you need both constraints: split by time and keep each customer's history on one side where the problem demands it. And evaluate on the most recent holdout, since that's the closest analogue to production.

PracticalWhat do you look for when reviewing data code?

Then silent failure generally: except: pass, filters that drop rows without logging how many, fillna(0) where zero is a real value, chained assignment that under pandas 3.0 does nothing at all.

Second, pin it — a lockfile, so you're debugging one variable at a time. Third, add a golden-output test on a small input, which lets every later change be verified rather than hoped about.

11.1 The data model

        
Where self-taught fluency and genuine understanding diverge. Expect two or three of these in any Python screen.


        

          
Drill

          

            
Very commonIs Python pass-by-value or pass-by-reference?
              
Neither — pass-by-object-reference. The function gets a new local name bound to the same object as the caller's.
The consequence is the answer: if the function mutates the object, the caller sees it; if it rebinds its local name, the caller sees nothing. So “does my function affect the caller's DataFrame?” is never about the calling convention — it's about whether you mutated or rebound.
Practical rule: functions either return a new object, or are named for the fact that they mutate. Never both, never silently.

            

            
Very commonMutable vs immutable — and why should I care?
              
Mutable objects change in place keeping their identity; immutable ones can't, so any “change” makes a new object.
Four consequences that make it worth caring: hashability (only immutables with immutable contents can be dict keys); aliasing (mutation is visible through every name); default arguments (a mutable default is shared across calls); performance (s += x in a loop is O(n²) because each step copies).
And a tuple is only shallowly immutable — ([1],) can have its inner list mutated, which is why it's unhashable.

            

            
Gotchac = [1,2]; d = c; c += [3] — what is d?
              
[1, 2, 3]. For a list, += invokes __iadd__ and extends in place, so both names see it. c = c + [3] would instead build a new list and rebind only c.
For a tuple, e += (3,) must rebind — same operator, opposite behaviour, decided by mutability.
Why it matters beyond trivia: arr += 1 mutates a NumPy buffer (cheap, but visible to every view) while arr = arr + 1 allocates a new array (safe, but doubles peak memory).

            

            
Very commonWhat's wrong with def f(x, acc=[])?
              
The default is evaluated once at function-definition time and stored on the function object, so every call omitting the argument shares the same list — mutations accumulate across calls and across the whole process.
Fix: acc=None, then if acc is None: acc = []. Use is None rather than if not acc, so an explicitly-passed empty list is respected.
Same trap catches any computed default: def f(when=datetime.now()) freezes the timestamp at import.

            

            
Very commonShallow copy vs deep copy?
              
Shallow makes a new outer container holding references to the same inner objects; deep recursively duplicates everything.
The part people get wrong: a[:], list(a), a.copy(), dict(d), {**d} and copy.copy are all shallow. Only copy.deepcopy is deep.
Shallow suffices when the contents are immutable. And deepcopy is slow — often the better answer is a comprehension that copies exactly the level you need, or making the data immutable so copying is unnecessary.

            

            
Very commonis vs ==?
              
== compares value via __eq__; is compares identity (same object).
Explain why is seems to work on numbers: CPython interns small ints (about −5 to 256) and some short strings, so 256 is 256 is True while 1000 is 1000 may not be — an implementation detail, not a guarantee.
Rule: is only for singletons (None, True, sentinels). For NaN use .isna() — np.nan == np.nan is False and x is np.nan is unreliable.

            

            
Very commonWhy can't a list be a dictionary key?
              
A dict places keys in buckets by hash and needs that hash stable while the key is stored. A list is mutable, so mutating it after insertion would strand it in the wrong bucket. Rather than allow silent corruption, list.__hash__ is None and you get an immediate TypeError.
Use a tuple — and note hashing is recursive, so a tuple containing a list is also unhashable. frozenset is the hashable set.

            

            
GotchaWhat does {1: 'a', True: 'b', 1.0: 'c'} give you?
              
{1: 'c'} — one entry. 1 == True == 1.0 and all three hash identically, so each assignment overwrites the same slot; the value is the last written while the key stays the first inserted.
Where it bites: building a lookup from a column that mixes int and float (very easy after a pandas upcast), or a flag column that's sometimes 1 and sometimes True. You silently lose entries. Normalise key types before building the dict.

            

            
ConceptualExplain the LEGB rule.
              
Name lookup searches Local → Enclosing → Global → Built-in; first match wins.
The non-obvious part: assignment determines scope at compile time for the whole function. If a function assigns to x anywhere, x is local throughout — so reading it before that line raises UnboundLocalError, even with a global x present.
Use global/nonlocal to rebind an outer name. You don't need either to mutate a mutable global — CACHE[k] = v works, because that mutates rather than rebinds.

            

            
Gotcha[lambda: i for i in range(3)] — what do they return?
              
[2, 2, 2]. Closures capture the variable, not a snapshot — late binding — and by call time the loop has finished with i == 2.
Fixes: a default argument (lambda i=i: i, evaluated at definition time — the §1.5 mechanism used deliberately), functools.partial, or a factory function creating a fresh scope.
Where it bites in data work: building a dict of per-column transformers, registering callbacks in a loop, or a list of delayed joblib jobs — all silently apply the last iteration's parameters to everything.

            

            
Deep diveWhy is a Python list of a million ints so much bigger than a NumPy array?
              
The list stores a million pointers (8 bytes) to a million int objects (~28 bytes each, carrying a refcount and type pointer), scattered across the heap — roughly 36 bytes per element. A NumPy int64 array stores a million raw 8-byte values in one contiguous buffer.
So ~8 MB versus ~36 MB, and the bigger win is speed, because contiguity lets the CPU cache and SIMD instructions work.
That's the whole answer to “why NumPy?”: no boxing, one dtype, contiguous memory.

            

          

        

      


      

        
11.2 Data structures & complexity

        
Where live-coding rounds are quietly won. The complexity table is the one thing worth memorising.


        

          
Drill

          

            
Very commonlist vs tuple vs set vs dict?
              
Give the axes: ordered, duplicates, mutable, hashable, lookup cost.
list — ordered, duplicates, mutable, O(n) membership. tuple — same but immutable, therefore hashable and usable as a key. set — unordered, unique, O(1) membership. dict — key→value, insertion-ordered since 3.7, O(1) lookup.
Then the decision rule: lookup by key → dict; membership or dedup → set; fixed record or dict key → tuple; otherwise list. And name the trap: membership on a list is a linear scan.

            

            
Very commonx in list vs x in set?
              
O(n) vs O(1) average. A list scans; a set hashes and jumps to a bucket.
Caveats worth adding: the set case is average and amortised (collisions degrade it), it costs ~3–4× the memory, and elements must be hashable.
The practical version: converting once before a loop turns O(n·m) into O(n+m). On a 100k-row filter against a 50k allow-list that's minutes to milliseconds, from a one-line change.

            

            
GotchaWhy is list.pop(0) a problem?
              
It's O(n) — removing the first element shifts every other one down. Draining a list that way is O(n²), and it looks innocent.
Use collections.deque: O(1) append/appendleft/pop/popleft. The trade is that deque[i] is O(n), so it's right for a queue and wrong for random access. Same reasoning applies to list.insert(0, x).

            

            
ConceptualWhy is list.append “amortised” O(1)?
              
The list holds a buffer with spare capacity, so most appends just write into a slot. When it fills, Python allocates a geometrically larger buffer and copies — O(n) for that one append.
Because reallocations are geometrically rare, the average per append is constant. Two practical consequences: a single append can occasionally be slow (latency jitter), and if you know the final size, preallocating or using NumPy avoids the copies entirely.

            

            
DebugThis function is slow on 100k rows. Find the problem.
              
Look for a linear operation inside a loop. Four candidates in frequency order: x in some_list (→ set); string or list concatenation in a loop (→ accumulate and join/append); pd.concat or df.append per row (→ build a list of dicts, construct once); .pop(0)/.insert(0,…) (→ deque).
And say how you'd confirm rather than guess: time it at two input sizes. Doubling the input and seeing 4× means quadratic, which localises the bug class before you read another line.

            

            
ConceptualAre dictionaries ordered?
              
Yes — insertion-ordered, a language guarantee since 3.7 (a CPython 3.6 implementation detail first).
Two precisions: insertion order is not sorted order (sorted(d) if you want that), and re-assigning an existing key keeps its original position — only delete-and-reinsert moves it.
OrderedDict is still occasionally right: it has move_to_end, and its equality is order-sensitive whereas plain dicts compare equal regardless of order.

            

            
Codingget vs setdefault vs defaultdict?
              
get reads with a fallback and doesn't modify the dict — the default choice. setdefault reads and inserts the default. defaultdict(factory) creates a fresh container on every miss — the grouping idiom.
The gotcha: a defaultdict creates entries on read, so merely checking dd[k] inserts k. Use k in dd to test, and consider converting to a plain dict before returning it so callers don't inherit the surprise.

            

            
CodingTop 10 items from a stream of a billion records.
              
A bounded min-heap of size 10: push the first 10, then compare each new item to heap[0] and heapreplace if larger. Memory O(k) regardless of stream length; time O(n log k).
Why not the alternatives: sorted(data)[-10:] needs everything in memory and is O(n log n). heapq.nlargest(10, stream) does exactly this internally, so mention it — but the manual version is what's being tested.
Follow-ups to pre-empt: top-k per group uses one small heap per group; if the data is already in a DB, ORDER BY … LIMIT beats anything in Python.

            

            
Very commonSort by one field ascending and another descending.
              
Two techniques. Negate the numeric key: key=lambda r: (r["team"], -r["score"]) — concise, numeric only. Exploit stability: sort by the least significant key first, then the most significant; because Timsort is stable the second sort preserves the first within ties, and this works for any key type.
In pandas: df.sort_values(["team","score"], ascending=[True, False]).

            

            
ConceptualWhat does “stable sort” mean and why care?
              
Equal elements keep their relative order. Python's sorted/list.sort use Timsort — stable, O(n log n) worst case, O(n) on nearly-sorted input.
It makes multi-pass sorting valid, and it means an existing meaningful order survives a later sort on a different key.
The trap: np.sort's default quicksort is not stable, and neither is df.sort_values's default. If you rely on tie order, pass kind="stable" explicitly.

            

            
CodingFlatten a list of lists.
              
[x for row in matrix for x in row] — clause order matches the nested loop you'd write, outer first, which is the bit people reverse.
Alternatives: list(itertools.chain.from_iterable(matrix)) (slightly faster, clearer), or np.concatenate/.ravel() for numeric data. Arbitrary nesting needs recursion with an isinstance check.
The anti-pattern: sum(matrix, []) works and is O(n²).

            

            
GotchaWhat's dangerous about zip?
              
It stops at the shortest iterable, silently. Zipping 1000 ids against 998 predictions gives 998 pairs and no error — you've dropped rows invisibly.
Fix: zip(a, b, strict=True) (3.10+) raises on a length mismatch — use it whenever the lengths should match. itertools.zip_longest when unequal lengths are legitimate.
The related lesson: this is why aligning on an index or joining on a key beats zipping positionally — positional alignment assumes an invariant nobody is checking.

            

          

        

      


      

        
11.3 Functions, decorators, generators

        
“What is a decorator?” is close to guaranteed, and the answer is to write one.


        

          
Drill

          

            
Very commonExplain *args and **kwargs.
              
In a definition they collect extra positional args into a tuple and extra keyword args into a dict. In a call they do the opposite — unpack a sequence into positional args and a mapping into keyword args.
That symmetry is what makes transparent wrappers possible: def wrapper(*a, **kw): return fn(*a, **kw) forwards any signature, which is the backbone of every decorator.
Ordering: positional-only /, positional-or-keyword, *args, keyword-only, **kwargs. A bare * starts keyword-only params without collecting.

            

            
PracticalWhy force keyword-only arguments?
              
Readable call sites and no positional mistakes. train(df, 0.2, 42, True) is unreadable and trivially mis-ordered; forcing names makes a reordering error impossible.
Second reason: API evolution — keyword-only params can be reordered or added without breaking callers, which is why pandas and scikit-learn have been converting to them.
Rule of thumb: flags and tuning parameters keyword-only; only the primary data argument stays positional.

            

            
Very commonWhat is a closure?
              
A function that keeps referring to variables from its defining scope after that scope exits. Python holds them in cells — visible as fn.__closure__, named in fn.__code__.co_freevars.
Two properties: it captures the variable, not the value (hence late binding), and each call to the factory produces independent cells.
Why it matters: closures are how decorators work, and how you build configured callables without a class.

            

            
Very commonWhat is a decorator? Write one.
              
A callable taking a function and returning a replacement. @deco is exactly f = deco(f).
The shape to write from memory: def timed(fn): → @functools.wraps(fn) → def wrapper(*args, **kwargs): → time it, call fn(*args, **kwargs) inside try with the reporting in finally → return wrapper.
Three details that separate a good answer: *args, **kwargs to wrap any signature, functools.wraps so metadata survives, and try/finally so the added behaviour happens even when the function raises. A decorator is just a closure over fn.

            

            
GotchaWhat does functools.wraps do, and what breaks without it?
              
Copies __name__, __doc__, __module__, __qualname__, __dict__ and __annotations__ onto the wrapper, and sets __wrapped__.
Without it every decorated function reports itself as wrapper with no docstring — breaking tracebacks and logs (every frame is “wrapper”), help() and generated docs, inspect.signature, and any framework dispatching on __name__ (pytest collection, Flask routes, Celery task names).

            

            
CodingWrite a decorator that takes an argument.
              
Three nested levels, because @deco(arg) calls deco(arg) and applies the result. Outer takes the config, middle takes the function, inner takes the call.
The mistake to flag: forgetting the parentheses. @retry on a parameterised decorator passes the function as the config, producing a bizarre error later. The fn=None plus functools.partial pattern makes a decorator work both with and without parentheses.

            

            
GotchaWhy can't you lru_cache a function taking a DataFrame?
              
The cache keys on the arguments, so they must be hashable — DataFrames, arrays, lists and dicts aren't. You get TypeError: unhashable type.
Options: cache on a hashable identifier (a path, a query string, a version tag) and load inside; hash the content with pd.util.hash_pandas_object(df).sum(); or use an explicit dict cache.
The deeper caution: caching on mutable data is dangerous — the frame can change while the cache holds the old result. Cache the load, not the transform.

            

            
Codingcache vs lru_cache, and when is caching wrong?
              
@cache is @lru_cache(maxsize=None) — unbounded, slightly faster, grows forever. lru_cache(maxsize=n) evicts the least recently used.
Caching is wrong when the function has side effects, the underlying data changes (no invalidation hook), arguments are unhashable, the key space is unbounded and you used @cache (a memory leak with a friendly name), or the function is cheap enough that the lookup costs more.
Also: lru_cache on a method keys on self and keeps every instance alive — use cached_property instead.

            

            
Very commonIterable vs iterator?
              
An iterable has __iter__ and can produce an iterator; an iterator has __next__ and holds the position.
The consequence: a list is re-iterable — iter(lst) gives a fresh iterator each time. A generator is its own iterator, so once exhausted it yields nothing more, silently.
That's the bug being tested: sum(gen) then len(list(gen)) gives a correct sum and then zero, with no error.

            

            
Very commonWhat is a generator and why use one?
              
A function containing yield; calling it returns a generator that produces values lazily, pausing at each yield with its locals intact.
Give the reason as a number: [x*x for x in range(10_000_000)] materialises ten million ints — hundreds of MB; the generator expression holds one. Peak memory O(n) → O(1).
Plus: infinite streams, free early exit (any() stops at the first match), and composition into pipelines. Caveats: no speedup, and single-use.

            

            
Very commonHow do you process a 50 GB CSV on a 16 GB machine?
              
Stream and aggregate as you go. A file object is already a lazy line iterator; csv.DictReader(fh) is the same, parsed. Accumulate into a dict of running totals, so memory scales with the number of groups, not rows.
In pandas: read_csv(chunksize=500_000), aggregate per chunk (which keeps each chunk vectorised), combine at the end. Read only what you need with usecols= and declare dtype=.
The best answer: convert to Parquet and query with DuckDB or Polars, which stream larger-than-memory joins and aggregations natively. Recognising that the tool choice beats the technique is the senior move.

            

            
Very commonWhat is the with statement for?
              
Guaranteed setup and teardown. __enter__ on entry, __exit__ on exit — and __exit__ runs whether the block finished, returned early, or raised. It's try/finally with a reusable name.
To write one: @contextmanager, record state, yield inside a try, clean up in finally. Everything before the yield is __enter__; after is __exit__.
Detail: __exit__'s return value decides suppression — returning True swallows the exception, which you almost never want.

            

            
DesignA row in your input is malformed. What do you do?
              
It depends on the cost of being wrong — and saying so is the answer, because this is a judgement question.
Quarantine and continue for analytics: write bad rows to a dead-letter table with the index, raw text and parse error, process the rest, and alert on the bad rate. Fail the batch when partial results are dangerous — financial or regulatory output, where a silently-30%-short number is worse than a failed job.
What makes either safe is a threshold: tolerate up to X% bad rows, fail above it. Without one, an upstream schema change can drop 90% of your data and the pipeline reports success.

            

          

        

      


      

        
11.4 OOP & dataclasses

        
Fewer questions than a backend interview, and more practical: can you write a class that fits someone else's framework?


        

          
Drill

          

            
Very commonWhat's wrong with a mutable class attribute?
              
It's created once when the class body executes and shared by every instance, so self.items.append(x) mutates state visible to all of them. Structurally the same as the mutable default argument.
Fix: initialise in __init__, or field(default_factory=list) in a dataclass.
The refinement that shows understanding: an immutable class attribute is fine — self.total += 1 rebinds on the instance, silently creating an instance attribute and leaving the class value untouched. That asymmetry is why class-level constants are idiomatic and class-level lists are a bug.

            

            
Very commonstaticmethod vs classmethod vs instance method?
              
Instance takes self; classmethod takes cls; staticmethod takes neither and is just namespacing.
The killer use for classmethod is alternative constructors — Dataset.from_csv. Because it calls cls(...) rather than a hardcoded name, it returns the correct subclass when inherited, which a staticmethod cannot. Real examples: dict.fromkeys, datetime.fromisoformat, pd.DataFrame.from_records.

            

            
Very common__repr__ vs __str__?
              
__repr__ is for developers — unambiguous, ideally reconstructible, and what the REPL, debuggers and containers use (printing a list calls repr on each element). __str__ is for users.
Rule: always implement __repr__; add __str__ only if the human form differs. str() falls back to __repr__.
Why it earns its keep: the default <Foo object at 0x…> is useless in a log or a pytest failure. Five lines saves hours.

            

            
GotchaYou defined __eq__ and now the object won't go in a set.
              
Defining __eq__ sets __hash__ = None, making the class unhashable. That's deliberate — equal objects must hash equally, and Python can't infer a correct hash from your equality logic, so rather than let you violate the contract it removes hashing.
Fix: define __hash__ over the same fields — hash((self.a, self.b)) — and only if those fields are effectively immutable.
Which is exactly why @dataclass(frozen=True) generates both and plain @dataclass generates only __eq__.

            

            
Very commonWhat does @dataclass give you?
              
Generated __init__, __repr__ and __eq__ from the annotations.
Then the options: frozen=True (immutable + hashable), slots=True (drops the per-instance dict — real memory win at scale), kw_only=True (forces named args), field(default_factory=...) for mutable defaults — and dataclasses refuse a bare mutable default, which is the language preventing the §1.5 bug. __post_init__ for validation.
What it isn't: a runtime type validator (see below), or a substitute for a class with real behaviour.

            

            
GotchaDoes a dataclass validate types?
              
No. @dataclass class C: x: int accepts C("hello") happily — annotations generate methods, they don't enforce anything.
For enforcement: Pydantic (reads the same annotations and validates/coerces on construction), checks in __post_init__, or a static type checker in CI.
The division: dataclass for internal objects you construct, Pydantic at boundaries where data comes from JSON, a request, or a config file.

            

            
Designdataclass vs NamedTuple vs TypedDict vs Pydantic?
              
dataclass — the default for internal records and configs; mutable by choice, supports methods.
NamedTuple — immutable and tuple-compatible: unpackable, sortable, indexable, cheap. Good for coordinates and small fixed records.
TypedDict — when the data is already a dict (parsed JSON) and you want annotations without changing the runtime type.
Pydantic — at boundaries, because it's the only one that validates at runtime.
One line: dataclass inside, Pydantic at the edges, NamedTuple when it should act like a tuple, TypedDict when it must stay a dict.

            

            
Deep diveWhat is the MRO and what does super() do?
              
The Method Resolution Order — the linearised search sequence computed by C3 linearisation: each class appears once, subclasses precede bases, declared order respected.
The correction that scores: super() does not mean “my parent” — it means “the next class in the MRO of type(self)”. So in a diamond, a single super().__init__() chain visits every class exactly once, which is why the shared base isn't initialised twice.
Corollary: every class in such a hierarchy must call super() and accept compatible arguments, or the chain breaks silently.

            

            
DesignInheritance or composition?
              
Composition by default. Inheritance couples you to a base class's internals and the coupling compounds; composition means holding a collaborator you can swap and test in isolation.
Use inheritance when there's a genuine is-a relationship and you need polymorphism — a framework requires subclassing, or you're providing interchangeable implementations of one interface.
The test: do you want the base class's interface, or just its code? Wanting the code is the wrong reason. In data pipelines composition wins almost always.

            

            
CodingWrite a custom scikit-learn transformer.
              
Inherit BaseEstimator (gives get_params/set_params) and TransformerMixin (gives fit_transform).
Contract: __init__ stores parameters only, with attribute names matching argument names exactly; fit learns, stores state in trailing-underscore attributes, returns self; transform uses only that fitted state and doesn't mutate the input.
The two mistakes that actually happen: computation or validation in __init__ (breaks clone, therefore GridSearchCV), and computing statistics inside transform — which leaks test information.

            

            
GotchaYour transformer works alone but fails in GridSearchCV.
              
A clone problem. GridSearchCV clones per fold and per parameter set, and clone calls get_params() then passes the result to __init__.
So it breaks if __init__ renames or transforms an argument before storing it, computes something the clone then lacks, uses *args/**kwargs (nothing to introspect), or you stored fitted state without a trailing underscore.
Diagnose by calling sklearn.base.clone(est) yourself. Better: run sklearn.utils.estimator_checks.check_estimator, which tests the whole contract.

            

          

        

      


      

        
11.5 NumPy

        
NumPy questions are a proxy for whether you understand memory.


        

          
Drill

          

            
Very commonAdvantages of NumPy arrays over lists?
              
No boxing — raw values instead of pointers to int objects, so ~4–5× less memory. One dtype — no per-element type dispatch, so the loop runs in compiled C. Contiguous memory — prefetching and SIMD work.
Net: typically 10–100× faster for elementwise numeric work, plus broadcasting, slicing and linear algebra.
Cost to acknowledge: arrays are homogeneous and fixed-size, so appending is expensive (np.append reallocates every time — building one in a loop is O(n²)) and mixed types force an upcast.

            

            
Deep diveWhat are strides and why do they matter?
              
The number of bytes to step per axis — (32, 8) for a C-ordered int64 (3,4) array.
They matter because shape + strides is how NumPy maps an n-D index onto a flat buffer, which makes reshape, transpose and basic slicing O(1) metadata changes over the same memory.
Two consequences: it explains views vs copies (a view is possible only when the selection is a regular strided pattern), and it explains performance — iterating along the contiguous axis is cache-friendly, across it is not.

            

            
Very commonWhen does NumPy return a view vs a copy?
              
View: basic slicing (a[2:6], a[::2]), compatible reshape, transpose, .view(). Copy: fancy indexing, boolean masking, arithmetic, .copy(), reshaping a non-contiguous array.
Why: a view is just metadata, so it's only possible for a regular strided pattern — fancy indexing picks arbitrary positions no stride can describe.
It matters because a view writes through to the parent. Check rather than assume: arr.base is not None, np.shares_memory(a, b).

            

            
Very commonExplain broadcasting.
              
Elementwise operations on different-shaped arrays without loops or copies. Three rules: right-align the shapes; missing leading dims count as 1; each dim must be equal or 1, and a 1 is stretched.
The mechanism: a stretched dim is implemented with stride 0, re-reading the same memory — so it costs nothing for the operands, though the result is full size, which is the memory trap on large data.
Canonical use: (X - X.mean(axis=0)) / X.std(axis=0). The fix for a failure is almost always [:, None].

            

            
Debug“could not be broadcast together with shapes (1000,) (1000,1)”
              
Right-align: (1, 1000) vs (1000, 1). Both dims are 1-or-equal, so it succeeds — and produces a 1000×1000 array, which is usually not what you wanted and may exhaust memory.
That's the dangerous version: broadcasting silently giving an outer product where you expected elementwise. Usual cause is a stray (n,1) from a sklearn predict, a reshape(-1,1), or double-bracket column selection.
Fix: .ravel()/.squeeze(), and assert shapes at function boundaries.

            

            
Very commonWhat does axis=0 mean?
              
The axis you name is the one that disappears. On a (3,4) array, sum(axis=0) collapses the 3 rows → 4 values (one per column); sum(axis=1) → 3 values.
That phrasing works in any dimensionality and avoids the “is axis 0 rows or columns” muddle — which exists because axis=0 is described as “rows” but produces a result per column.
Same in pandas. The confusing exception is df.drop(..., axis=1), where axis names what you're addressing — which is why df.drop(columns=[...]) is preferred.

            

            
Very commonWhat is vectorisation and why is it faster?
              
Operations on whole arrays rather than element-by-element in Python. Three reasons, better than “it's in C”: no interpreter overhead per element; SIMD on contiguous data; cache efficiency versus chasing pointers to scattered objects.
Typically 10–100×, and more for anything reducible to matrix multiplication because it lands in a tuned BLAS kernel.
Caveat worth adding: vectorisation often trades memory for speed — a broadcast intermediate can exceed both inputs, so sometimes the fastest formulation is the one that avoids materialising it.

            

            
CodingVectorise pairwise Euclidean distances.
              
Broadcasting: diff = A[:, None, :] - B[None, :, :] then np.sqrt((diff**2).sum(axis=-1)).
Better for large n: use |a−b|² = |a|² + |b|² − 2a·b, so a2[:,None] + b2[None,:] - 2 * A @ B.T. This never materialises the (n,m,d) intermediate and pushes the work into BLAS.
Two details that show care: clip with np.maximum(d2, 0) before the sqrt (floating-point can give tiny negatives), and mention that in practice you'd call scipy.spatial.distance.cdist or sklearn.metrics.pairwise_distances.

            

            
GotchaIs np.vectorize a way to vectorise code?
              
No — the docs say so explicitly. It provides broadcasting semantics for a scalar function but loops in Python internally, so it's essentially as slow as the loop you started with.
What actually vectorises: array expressions, np.where/np.select for conditionals, boolean masks, np.digitize/searchsorted for binning, existing ufuncs.
For an irreducible scalar loop, the real answers are Numba or Cython. Citing np.vectorize as a performance tool is a reliable tell.

            

            
GotchaYour sum of a downcast column is negative.
              
Integer overflow. NumPy integers are fixed-width and wrap silently. Individual values fit in int16 but the aggregate exceeds 32,767 and wraps.
Fix: arr.sum(dtype=np.int64), or promote before summing. Before downcasting, check the range against np.iinfo(dtype).max with headroom.
General lesson: downcast storage, compute in a wider type.

            

            
Very commonWhy is 0.1 + 0.2 != 0.3?
              
Binary floating point can't represent those decimals exactly, and the rounding errors don't cancel — the result is 0.30000000000000004.
Fixes: never test float equality — math.isclose, np.isclose/allclose, pd.testing.assert_frame_equal with rtol. For money, Decimal or integer minor units.
The deeper issue: float addition is not associative, so summation order changes the result — which is why parallel sums can differ and why np.sum uses pairwise summation.

            

            
GotchaHow do you count and handle NaN correctly?
              
Count: np.isnan(a).sum() or df.isna().sum(). Never a == np.nan — NaN isn't equal to itself.
Aggregate: NumPy's sum/mean/max propagate NaN; use np.nansum etc. to skip. Note pandas does the opposite by default (skipna=True) — a genuine inconsistency worth flagging.
Two more: np.sort places NaN last, so a “max” from a sorted array may be NaN; and NaN only exists in float dtypes, so an int column with gaps upcasts to float — or uses nullable Int64 with pd.NA.

            

          

        

      

      

        
11.6 pandas core

        
If an interview touches one library, it's this one. §11.6 and §11.7 carry the most weight in the whole bank.


        

          
Drill

          

            
Very commonWhat is a DataFrame, really?
              
A dict of Series sharing one index. Each column is a separate typed contiguous buffer; the index is a shared label array everything aligns to.
Two consequences: storage is column-oriented, so whole-column arithmetic is one C loop and fast, while iterating rows touches every buffer and builds a Series per row. And the index is meaningful, so operations align on it automatically — the source of both pandas' power and its most confusing behaviour.
The habit: think in columns, not rows.

            

            
Very common.loc vs .iloc?
              
Label vs integer position. They coincide only on a default RangeIndex, which is why the difference is invisible until it bites.
The detail that scores: .loc slices are inclusive of the endpoint, .iloc are not — with arbitrary labels there's no “next” label to stop before.
Then why to avoid bare df[...]: it's overloaded — df['v'] takes a column, df[0:2] takes rows, df[mask] takes rows. Same syntax, different axis, decided by the argument type.

            

            
CodingHow do you conditionally update a column?
              
df.loc[mask, "col"] = value — one .loc call handling both row selection and column, so pandas knows unambiguously you're assigning into the frame.
Not df[mask]["col"] = value: that's chained assignment, two separate indexing operations, and under pandas 3.0 it silently does nothing.
Alternatives: np.where(cond, a, b), df["col"].mask(cond, value), or df.assign(...) to stay in a chain.

            

            
ModernWhat is SettingWithCopyWarning and how do you fix it?
              
Lead with the currency: in pandas 3.0 it no longer exists. Copy-on-Write became the only mode in January 2026, and because indexing results are unambiguously copies, the warning had nothing to warn about and was removed.
What it was: pandas couldn't tell whether df["a"][mask] = x would modify the original or a temporary, because df["a"] might return a view or a copy depending on dtypes and block layout.
What happens now: chained assignment reliably does nothing — silent, but consistent. The fix was always the same: one .loc call.

            

            
ModernWhat is Copy-on-Write — faster or slower?
              
Faster, which surprises people. Every indexing result behaves as an independent copy, but pandas defers the actual duplication until a write happens — so reads share memory.
The win: pandas can drop defensive copies it previously made, and you can drop the .copy() calls that were idiomatic after every filter. Those now force an eager copy CoW would have avoided, so deleting them is a real memory improvement on upgrade.
The behavioural change: mutating a slice can no longer reach into the parent — so code that relied on that silently stops working, which is the main upgrade risk.

            

            
ModernWhat changed about dtypes in pandas 3.0?
              
Strings get a dedicated str dtype by default (PyArrow-backed when available), instead of object.
The breaking part: code checking df.dtypes == "object" or select_dtypes("object") to find string columns now misses them — and that pattern is extremely common in feature-engineering code.
Also: datetimes default to microseconds not nanoseconds, removing the 1678–2262 range limit; CoW is the only mode; and everything deprecated in 2.x was removed. Upgrade path: 2.3 → clear all warnings → 3.0.

            

            
GotchaWhy did your integer column become float?
              
It contains missing values, and NumPy-backed int64 has no NaN representation, so pandas upcasts to float64. Symptoms: ids printing as 12345.0, and past 2⁵³ actual precision loss.
Fix: the nullable Int64 dtype (capital I), which stores an integer array plus a mask and uses pd.NA. Or declare dtypes at read time.
Same for booleans (→ object; nullable equivalent is "boolean"). This is the most common cause of “my join key stopped matching”.

            

            
PracticalWhen would you use the category dtype?
              
For low-cardinality columns — a few hundred distinct values or fewer over many rows. Stores distinct values once plus small integer codes, so a country column over ten million rows goes from hundreds of MB to a few. Also speeds up groupby and merges on that column, and supports declared ordering.
Gotchas: appending an unseen value gives NaN; groupby includes unobserved combinations by default (use observed=True); and for a high-cardinality column like a user id it's worse than a plain string.

            

            
Very commonHow do you handle missing values?
              
Start with why they're missing: completely at random, at random given other features, or not at random — where the missingness itself carries signal.
Then: drop rows only if few and plausibly random (quantify the loss); drop the column if mostly empty; impute — median for skewed numerics, mode or an explicit "UNKNOWN" for categoricals, forward-fill for time series, model-based when structured.
Two points that make it senior: add a missingness indicator, because for MNAR data that flag is often more predictive than the imputed value; and fit the imputer on train only, inside a Pipeline.

            

            
PracticalWhat do you always pass to read_csv?
              
dtype= above all — without it pandas infers per column and turns zip codes, phone numbers and padded ids into integers, silently losing leading zeros. usecols= to read only what you need. parse_dates=. na_values= because real files use "NULL", "N/A", "-". chunksize= when large.
Then the judgement: prefer Parquet. CSV has no schema so every read re-guesses; Parquet is columnar, compressed, stores dtypes, and supports column/predicate pushdown. Convert once at ingestion.

            

            
DebugYour join key stopped matching after a CSV round-trip.
              
A dtype mismatch introduced by the read. Usual suspects: one side int64, the other float64 (a missing value forced an upcast), so 1 never matches 1.0; a numeric-looking id read as int on one side and str on the other; leading zeros stripped from one file only.
Diagnose: compare dtypes, and inspect keys with repr() to reveal whitespace and quotes.
Prevent: declare key dtypes explicitly (ids as str unless you do arithmetic), strip whitespace, assert the row count after the merge.

            

            
DesignWhy prefer method chaining?
              
No mutation (no aliasing question, no defensive .copy()), no temporary names (where stale-intermediate bugs live, especially in notebooks), reads as the transformation it is, and composable via .pipe().
Use lambda inside .assign()/.query() so each step refers to the frame at that point.
Honest limits: hard to debug because there's no intermediate to inspect, and query uses strings no linter checks.

            

            
GotchaDoes inplace=True save memory?
              
Generally no — a persistent myth. Most inplace operations still build a new object internally and rebind, so peak memory is similar. It saves a variable name, not memory, and under CoW it's even less meaningful.
Arguments against: it returns None so it breaks chaining; it mutates a frame others may hold a reference to; and it makes code harder to reason about.
Real memory levers: dtypes, usecols, chunking, dropping columns early.

            

          

        

      


      

        
11.7 pandas transformation

        
The part that mirrors the actual job. Three answers here carry outsized weight: agg/transform/apply, join validation, and leakage-free windows.


        

          
Drill

          

            
Very commonExplain groupby.
              
Split-apply-combine: split rows into groups by key, apply a function to each, combine into a new object with the keys as index.
Add that groupby itself is lazy — it returns a GroupBy object having done almost no work; nothing computes until agg, transform, apply or a direct method.
Then the practical shape: prefer named aggregation — .agg(total=("rev","sum"), n=("rev","size")) — for flat readable column names instead of a MultiIndex to flatten.

            

            
Very commonagg vs transform vs apply?
              
Shape decides. agg reduces each group to a scalar (one row per group). transform returns a value per input row, broadcasting the group result back. apply gets the whole sub-frame and can return anything.
Rule: use transform to add a group statistic as a column — df["m"] = df.groupby("g")["v"].transform("mean") — because it aligns automatically. agg for summary tables. apply only when you need multiple columns of the group at once.
Performance: agg/transform with a named string function dispatch to Cython; apply and lambdas run Python per group — typically 5–30× slower.

            

            
CodingAdd each row's percentage of its group total.
              
df["pct"] = df["val"] / df.groupby("grp")["val"].transform("sum").
Why the alternatives are worse: with agg you'd get a small result you must merge back — more code, an extra join, a chance of misalignment. With apply you'd run Python per group for no benefit.
Same pattern covers most within-group feature engineering: rank, deviation from group mean, share of group, group z-score, group-wise fill.

            

            
GotchaYour group totals don't add up to the overall total.
              
groupby drops rows with a missing key by default (dropna=True). Rows whose grouping column is NaN vanish, with no warning.
Fixes: dropna=False for an explicit NaN group, or fillna("UNKNOWN") on the key first so the missing category is visible and reportable.
The general habit: after any aggregation, assert the total is conserved. Silent row loss is the most dangerous class of pandas bug because the output still looks plausible.

            

            
GotchaYou grouped by a categorical and got far more rows than groups.
              
observed=False emits a row for every declared category, not just those present — and with several categorical keys that's the full cross-product of all levels, potentially thousands of empty rows.
Pass observed=True. The behaviour has a legitimate use — guaranteeing a complete grid for a report — but it should be deliberate.

            

            
Codingcount vs size vs nunique?
              
size = all rows including nulls, one Series. count = non-null values, per column. nunique = distinct values.
“How many orders” is size; “how many had a discount recorded” is count; “how many distinct products” is nunique. Using count where you meant size silently under-reports whenever nulls exist.

            

            
Very commonmerge vs join vs concat?
              
merge — SQL-style join on columns or index, with how. The general tool. join — convenience, merges on the index by default, and note its default is left unlike merge's inner. concat — doesn't join, it stacks: axis=0 appends rows aligning columns by name, axis=1 appends columns aligning rows by index.
Rule: matching on keys → merge; stacking like-shaped pieces → concat.

            

            
PracticalHow do you verify a join did what you intended?
              
1. validate= — declare the expected cardinality ("many_to_one" etc.) and pandas raises if violated. The highest-value argument in merge and almost nobody uses it.
2. Assert the row count — for a left enrichment join, assert len(out) == len(left).
3. indicator=True then _merge.value_counts() — an unexpectedly large left_only usually means a dtype mismatch or whitespace in the keys.
4. Check null rates on the newly-added columns.

            

            
DebugRow count went 1M → 4M after a join.
              
Many-to-many. The key is duplicated on one or both sides, so you get the cross-product per key. Every downstream sum is now wrong, and nothing raised.
Diagnose: right["key"].is_unique, or duplicated().sum().
Fix by intent: if the duplicates are data-quality noise, drop_duplicates(subset="key") — but decide which row wins, with a sort, rather than taking an arbitrary one. If multiple rows per key are legitimate, aggregate the right side first.
Prevent: validate="many_to_one" plus a row-count assertion on every enrichment join.

            

            
DesignJoin a fact table to a slowly-changing dimension without leaking.
              
pd.merge_asof with direction="backward" — for each fact row take the most recent dimension record at or before its timestamp. A point-in-time join.
Details: both frames must be sorted on the key or the result is silently wrong; by= matches within an entity; tolerance= turns an unreasonably stale match into NaN.
Why it's the right answer: a plain merge gives every fact row the current value, encoding information from after the event — the model looks excellent in backtest and fails in production.

            

            
Very commonpivot vs pivot_table?
              
pivot is a pure reshape requiring unique index/column pairs, and raises otherwise. pivot_table aggregates duplicates via aggfunc (mean by default).
The implication: pivot's error is useful information — your data has more than one record per cell. Reaching straight for pivot_table silently averages them and may hide a duplicate-record bug.
So use pivot when the data should be unique, precisely so it fails loudly. Pass aggfunc explicitly when you do aggregate.

            

            
DesignHow do you build a rolling feature without leakage?
              
.shift(1) before .rolling(). Default rolling(3) includes the current row, so a “past 3 days average” contains today's value — and if you're predicting today, the feature contains the target.
For panel data: sort by entity and time, group by entity, then shift, then roll. Rolling across the whole frame bleeds one entity's history into another's features.
And use rolling("3D") rather than rolling(3) when the series has gaps, so the window is three days not three rows.

            

            
Codingrolling vs expanding vs ewm?
              
rolling(n) — fixed window, older data drops out. expanding() — everything from the start, growing. ewm() — all history with geometrically decaying weight, smoother because there's no abrupt drop-out.
All take min_periods, which controls the warm-up. Whether min_periods=1 is right depends on whether a partial window is meaningful — accepting the default silently is how you get a model that can't score the first rows of every new entity.

            

            
CodingTranslate ROW_NUMBER() OVER (PARTITION BY g ORDER BY t).
              
df.sort_values(["g","t"]).groupby("g").cumcount() + 1, or df.groupby("g")["t"].rank(method="first").astype(int).
The tie semantics are usually the real point: method="first" ≈ ROW_NUMBER, "min" ≈ RANK, "dense" ≈ DENSE_RANK.
General mapping: SQL window functions ↔ groupby().transform(), shift(), rank(), cumsum() — the ones that preserve row count.

            

            
DesignWould you do this in SQL or pandas?
              
SQL wherever the data lives in a database — push filtering, joining and aggregation to the engine so you move less data and use its indexes. Pulling a hundred million rows into pandas to group them is the classic mistake.
pandas for exploratory and iterative work, complex reshaping, anything feeding scikit-learn, and custom Python logic.
The 2026 answer that shows range: DuckDB runs SQL directly against a DataFrame or Parquet file, out-of-core and multi-threaded, so it isn't binary — and Polars gives a lazy optimised DataFrame API. Say you'd benchmark rather than assume.

            

          

        

      


      

        
11.8 Performance & concurrency

        
Diagnosis questions dressed as optimisation questions. Profile first; the GIL answer changed in 2026.


        

          
Drill

          

            
Very commonHow would you speed up a slow pandas operation?
              
Measure, then climb the ladder: iterrows → itertuples → apply → vectorised pandas → NumPy. Each step is roughly an order of magnitude, and the big cliff is between apply and vectorised because everything above it is a Python loop.
Concretely: column arithmetic instead of row iteration; np.where/np.select for conditionals; .map(dict) for lookups; merge for joins; .str/.dt accessors.
Other levers: fix dtypes (an object column defeats vectorisation), reduce memory so you stop swapping, use agg("sum") not apply, and if it genuinely can't vectorise reach for Numba, Polars or DuckDB.

            

            
GotchaIs df.apply vectorised?
              
No. It calls your Python function once per row (axis=1) or column, and with axis=1 it constructs a Series per row — which is why it's barely faster than iterrows.
Instead: arithmetic → column expressions; conditionals → np.where/np.select; binning → pd.cut; lookups → .map; joins → merge; strings → .str; dates → .dt.
When it's fine: small data where clarity wins, or logic that truly can't be array-expressed — and then say what you'd do if it were the bottleneck.

            

            
DebugA pipeline went from 5 minutes to 3 hours.
              
Establish what changed first — code, data volume, or dependency versions.
Then measure: time it at two input sizes (4× per doubling means quadratic, so hunt a linear op inside a loop); cProfile for the function; line_profiler for the line; and check memory, because a 3-hour runtime with swapping is a memory problem wearing a CPU costume.
Usual culprits: a frame grown row by row, an apply where vectorised exists, an exploded join, x in list in a loop, or a dtype regression to object.

            

            
Very commonYour DataFrame doesn't fit in memory.
              
Read less, store it smaller, or don't hold it all — in that order.
Read less: usecols= and dtype= at read time — often solves it alone on a wide file. Smaller: downcast numerics, category for low-cardinality strings, drop columns early — 50–90% reductions are routine. Don't hold it: chunksize= and aggregate per chunk; or Parquet + DuckDB/Polars for native out-of-core.
Caveat: downcasting narrows the range, so aggregate with a wider accumulator or you get silent overflow.

            

            
GotchaWhy does memory_usage() undercount?
              
By default it counts only the NumPy buffer, not the Python objects it points to. For an object string column the buffer is just 8-byte pointers while the strings live elsewhere — the gap can be an order of magnitude.
Pass deep=True, or use df.info(memory_usage="deep").
Related: pandas 3.0's PyArrow-backed str dtype stores strings compactly, so the gap is much smaller than it used to be — a practical win of upgrading.

            

            
CodingCompute a group mean over a file that doesn't fit in memory.
              
Accumulate sum and count per group across chunks, then divide once at the end.
The mistake to name: averaging the per-chunk means is wrong unless every chunk has the same number of rows in every group. Mean isn't associative under unequal weights; sum and count are.
Extends to variance (from sum, sum-of-squares and count, or Welford's algorithm for stability). And mention the better tool: duckdb.sql("SELECT key, avg(v) FROM 'f.parquet' GROUP BY 1").

            

            
ConceptualWhich statistics can't be computed in one chunked pass?
              
Anything needing global order or the full distribution: exact median and quantiles, a full sort, exact distinct counts at high cardinality.
Workarounds: two passes; approximate algorithms — t-digest or reservoir sampling for quantiles, HyperLogLog for cardinality; external sort; or push it to a query engine.
The nice exception: mean and variance are single-pass via Welford's algorithm, which is also more numerically stable than accumulating raw sums of squares.

            

            
Very commonWhat is the GIL?
              
A mutex in CPython allowing only one thread to execute Python bytecode at a time. Its purpose is memory management — making reference counting safe without fine-grained locking, which also keeps single-threaded Python fast.
So threads don't speed up CPU-bound pure-Python code. But the nuance that scores is what it doesn't block: it's released during I/O and compiled extension work, so threads help a lot for network and disk, and NumPy, pandas and BLAS already parallelise because they drop it.
For data work the GIL is much less of a constraint than its reputation suggests — the expensive parts were never running under it.

            

            
ModernWhat changed with free-threaded Python?
              
PEP 779: as of Python 3.14 the free-threaded build is officially supported — moved from experimental to supported. It's a separate build compiled without the GIL; the default interpreter still has one.
What it enables: real multi-core parallelism for CPU-bound pure-Python code using threads, without multiprocessing's pickling and memory duplication.
The honest caveats: single-threaded performance is somewhat slower; C extensions must be explicitly compatible and the ecosystem is still catching up (NumPy 2.5 improved its support); and you now have to think about data races the GIL used to paper over.
Position for 2026: promising, worth tracking, but vectorised C code, multiprocessing and joblib still cover most data work.

            

            
Very commonThreads, processes or async?
              
Choose by workload. I/O-bound, tens to hundreds of operations → ThreadPoolExecutor. I/O-bound at very high concurrency → asyncio, because a coroutine is far cheaper than a thread — but only if the whole path is async. CPU-bound pure Python → processes.
CPU-bound numeric → none of them: vectorise. NumPy and BLAS already thread internally, so wrapping them in processes oversubscribes the cores and often gets slower; set OMP_NUM_THREADS=1 in workers if you do parallelise.

            

            
GotchaWhat goes wrong with multiprocessing in data code?
              
Pickling and memory. Everything crossing the boundary must be picklable, so lambdas, closures and local functions fail. And a large DataFrame passed as an argument is serialised and copied into every worker — eight workers, eight copies — which frequently makes the parallel version slower.
Platform difference: fork shares memory copy-on-write but is unsafe with threads; spawn re-imports your module in each child, so module-level code runs again and you need the if __name__ == "__main__" guard.
Mitigations: pass paths or ranges and let workers load their own slice; use joblib, which memory-maps large arrays; and measure, because parallelism has real fixed costs.

            

            
ModernWould you use Polars instead of pandas?
              
For new performance-sensitive pipeline work, seriously consider it. Rust-based, multi-threaded by default, Arrow-backed, with a lazy API and a query optimiser that does predicate/projection pushdown and streams larger-than-memory data.
Where pandas wins: ecosystem (scikit-learn, plotting, tutorials all assume it) and team familiarity. Rewriting a working pipeline for speed alone rarely justifies the risk.
Pragmatic position: they interoperate cheaply via Arrow, so use Polars or DuckDB for the heavy load-and-aggregate and hand a pandas frame to the modelling code.

            

          

        

      


      

        
11.9 Production, testing & leakage

        
At four years' experience this section decides your level. Most candidates have no testing answer at all.


        

          
Drill

          

            
Very commonWhat is data leakage and how do you prevent it?
              
Any information in your features that wouldn't be available at prediction time. The model learns it, scores brilliantly in validation, fails in production — and the code runs perfectly, which is why it survives.
Flavours: preprocessing (scaler/imputer fitted before the split), feature selection using all the labels, target (a feature derived from the outcome), temporal (random split on time-ordered data, unshifted rolling features), group (same customer in train and test), duplicate rows split across both.
Prevention: all preprocessing and selection inside a Pipeline so it refits per fold; the right splitter (TimeSeriesSplit, GroupKFold); deduplicate before splitting; and audit every feature with “would I have this at prediction time?”
Detection: an implausible score, one feature dominating importances, and a shuffled-label run that should score at chance.

            

            
Debug0.99 AUC in CV, 0.6 in production.
              
Assume leakage first — a gap that size is almost never distribution shift alone.
Check: feature importances (one feature dominating is the target-leakage signature); split strategy (time-ordered data split randomly? same entity both sides? duplicates removed before splitting?); preprocessing order (anything fitted outside the pipeline on the full data?); feature timestamps (is each value knowable at prediction time?).
Then the confirming test: shuffle the labels and re-run. Above chance means information is reaching the model through an unaccounted channel.
Rule out the alternatives too: train/serve skew, genuine population shift, or a label definition that differs from reality.

            

            
Very commonWhy use a scikit-learn Pipeline?
              
It makes leakage structurally impossible. Every transformer's fit is called only on the training portion, so under cross-validation the imputer's median and the scaler's mean are recomputed inside each fold.
Plus: one object to serialise, so fitted preprocessing travels with the model and training/inference can't drift; hyperparameter search across the whole pipeline via "pre__num__impute__strategy"; and column-aware preprocessing with ColumnTransformer.
The production detail: OneHotEncoder(handle_unknown="ignore"), so an unseen category doesn't crash at inference.

            

            
DesignHow do you split time-series data?
              
Chronologically, never randomly. A random split lets the model train on next month to predict last month — a task it will never face. Use TimeSeriesSplit, where validation always follows training.
Two more requirements: a gap between train and validation if features use a lookback or the label has a horizon; and features shifted so each row uses only prior information.
If the data is both temporal and grouped you need both constraints — and evaluate on the most recent holdout, as the closest analogue to production.

            

            
Very commonHow do you test a data pipeline?
              
Test the transformations, not the data. Each should be a pure function frame-in/frame-out, testable with a five-row fixture and a known answer.
Four layers: unit tests per transformation; edge cases — empty frame, all-NaN column, single row, duplicate keys, unseen category, NaN group key (this is where the value is); invariants — row count preserved, totals conserved, ids unique; and an integration test on a small golden input.
Mechanics: pd.testing.assert_frame_equal with rtol rather than ==; @pytest.mark.parametrize for the edge-case matrix; fixed seeds.
And the cultural half: every production bug becomes a test before it's fixed.

            

            
PracticalHow do you test something non-deterministic, like a model?
              
Separate the deterministic parts — feature transformations, split logic, output schema — and test those normally.
For the model, assert properties and bounds, not exact numbers: it runs end to end; output shape and dtypes are right; probabilities in [0,1]; holdout performance above a threshold; and a shuffled-label run performs no better than chance, which is a genuinely good leakage test.
Then fix every seed, pin versions, and use golden files with a tolerance so unintended behaviour changes are caught even when you can't specify the right answer in advance.

            

            
DesignWhere and how do you validate incoming data?
              
At the boundary — right after reading, before any transformation — so a schema change fails with “column region missing, got […]” instead of a KeyError forty lines in.
Check: required columns, dtypes, nulls where disallowed, key uniqueness, value ranges, and row count in a plausible band — a 90% volume drop is a failure even if every row is individually valid.
Tools: pandera for dataframe schemas, Pydantic for records. And report all problems at once, so one run tells the caller everything to fix.

            

            
PracticalHow do you make an environment reproducible?
              
A lockfile, committed. Loose intent in pyproject.toml, exact pins for every direct and transitive dependency in a lock (uv lock, poetry lock, pip-compile).
Why transitive matters: you pin pandas, pandas depends on numpy, and a numpy patch release can change a numeric result. A loose requirements.txt reproduces nothing.
Beyond packages: pin the interpreter, use a container for system libraries, and record versions plus a data hash in the run artefacts.

            

            
PracticalHow do you make an ML experiment reproducible?
              
Four things, and seeds are only the first. Seeds: Python's random, an explicit NumPy default_rng passed around, PYTHONHASHSEED, and random_state= on every sklearn object. Pinned environment. Data versioning — a content hash or immutable snapshot, since “I got a different number” is often a changed input. A run record — seed, versions, data hash, params, git commit.
Then the honesty: seeds cannot control thread count (parallel float summation order), GPU reductions, or anything reading the clock. Bit-exact reproducibility is sometimes unattainable — so define what tolerance counts as “reproduced”.

            

            
PracticalHow do you move a notebook into production?
              
Extract pure functions into a module, then import them back into the notebook — the notebook keeps the charts and still works.
Steps: get “Restart and Run All” passing first; pull each transformation into a function taking a frame and returning a frame, no globals, no mutation; parameterise hard-coded paths, dates and thresholds into a config; add a thin entrypoint; write tests; pin the environment.
The design point: any statistic the transformation needs — a median, a category list — should be a parameter, not computed inside. That's what lets one function serve training and inference.

            

            
PracticalWhy logging instead of print?
              
Levels, routing and structure. Levels let you change verbosity at runtime; handlers route to a file or aggregator without touching call sites; records carry timestamp, module and level so you can filter and alert.
Mechanics: lazy formatting — log.info("n=%d", n) not an f-string — so the message is only built if enabled; and getLogger(__name__) so the name reflects the module.
In a pipeline, log what you'll want at 3 a.m.: row counts in and out per stage, fraction dropped, the config in use, timings.

            

            
PracticalWhat do you look for reviewing data code?
              
Correctness first, especially the silent failures. Leakage; joins without validate= or a row-count assertion; groupby dropping NaN keys; rolling features without a shift. All produce plausible wrong numbers rather than errors.
Then silent failure generally (except: pass, unlogged filters, fillna(0) where zero is meaningful, chained assignment that now no-ops), dtypes, reproducibility, and only then performance.
What I want to see: small pure functions, statistics passed as parameters, row counts logged per stage, tests for the empty frame and duplicate key. And I'd ask “how do you know?” about any correctness claim.

            

          

        

      


      

        
11.10 The trap questions ⭐⭐

        
Python screens are lost on a small number of confidently-wrong answers. Each of these has an obvious answer that is wrong, and a correct answer that sounds less impressive.


        

          
Traps — the answer that sounds good and isn't

          

            
Trap 1“So apply is the vectorised way to do it?”
              
Trap: agreeing. Correct: apply is a Python loop. It calls your function once per row, and with axis=1 it builds a Series per row, making it barely faster than iterrows.
The vectorised alternatives are np.where, np.select, pd.cut, .map, .str, .dt and plain column arithmetic — typically 50–100× faster for the same result.

            

            
Trap 2“The GIL means Python can't do parallelism.”
              
Trap: agreeing, or reciting it as a blanket limitation. Correct: the GIL is released during I/O and compiled extension work, so threads already parallelise network and disk operations, and NumPy, pandas, scikit-learn and BLAS already use multiple cores.
It only ever limited CPU-bound pure-Python code — which is rare in data work because the heavy lifting is in C. And as of Python 3.14, PEP 779 makes free-threaded builds officially supported, so even that limit is being lifted.

            

            
Trap 3“Use inplace=True to save memory.”
              
Trap: repeating it. Correct: most inplace operations still build a new object internally and rebind, so peak memory is similar. It saves a variable name, not memory — and it returns None, which breaks chaining, and mutates a frame others may reference.
The real memory levers are dtypes, usecols, category, chunking and dropping columns early. pandas has been steadily deprecating inplace.

            

            
Trap 4“Fix SettingWithCopyWarning by adding .copy().”
              
Trap: giving the 2019 answer. Correct: in pandas 3.0 the warning doesn't exist — Copy-on-Write removed the ambiguity it warned about, and chained assignment now reliably does nothing.
The fix was always one .loc call: df.loc[mask, "col"] = x. And under CoW the defensive .copy() after a filter is now redundant — it forces an eager copy that would otherwise never happen, so removing those is a memory win.

            

            
Trap 5“np.vectorize will speed this up.”
              
Trap: believing the name. Correct: the NumPy docs say explicitly that it's a convenience wrapper providing broadcasting semantics, not performance — it loops in Python.
Real options: express the logic as array operations, use np.where/np.select, or for a genuinely irreducible scalar loop use Numba's @njit.

            

            
Trap 6“I scaled the features, then split into train and test.”
              
Trap: not noticing. Correct: that's leakage — the scaler's mean and standard deviation were computed over the test set, so test information is baked into the transform the model trains on. Your validation score is optimistic.
Fix: split first, or put the scaler in a Pipeline so it refits inside every CV fold. The same applies to imputers, encoders and feature selectors.
How much does it matter? On pure random noise, feature selection outside the CV loop can lift apparent accuracy from 0.50 to 0.70 — entirely fabricated.

            

            
Trap 7“I used a random 80/20 split.” (on time-series data)
              
Trap: treating it as the default. Correct: on time-ordered data a random split lets the model train on the future to predict the past, which is not the task. Use TimeSeriesSplit with a gap if your features have a lookback or your label has a horizon.
And the same reasoning for grouped data: if the same customer appears in train and test, the model memorises the customer rather than learning the pattern — use GroupKFold.

            

            
Trap 8“c = [1,2]; d = c; c += [3] — so d is [1,2].”
              
Trap: assuming += always rebinds. Correct: d is [1,2,3] — for a mutable target, += calls __iadd__ and mutates in place, so every alias sees it.
For an immutable target there's no in-place option, so it rebinds and the alias is unaffected. Same operator, opposite behaviour, decided by mutability — which is why arr += 1 and arr = arr + 1 differ in memory behaviour too.

            

            
Trap 9“a[:] gives me a safe copy.”
              
Trap: assuming it's deep. Correct: it's shallow — a new outer list holding references to the same inner objects. So nested[:] then copy[0].append(x) mutates the original's inner list.
list(a), a.copy(), dict(d), {**d} and copy.copy are all shallow too. Only copy.deepcopy is deep — and it's slow, so often the better answer is a comprehension copying exactly the level you need.

            

            
Trap 10“A left join can't change my row count.”
              
Trap: a very common and expensive assumption. Correct: a left join preserves row count only if the right side is unique on the key. If it isn't, each left row is duplicated once per matching right row — so 1M rows can become 4M, and every downstream sum is inflated.
Guard with validate="many_to_one" and assert len(out) == len(left). This produces plausible wrong numbers, not a crash, which is what makes it dangerous.

            

            
Trap 11“df.dtypes == 'object' finds my string columns.”
              
Trap: muscle memory from pandas 2.x. Correct: in pandas 3.0 strings are inferred as str dtype, not object — so that check, and select_dtypes("object"), silently miss them.
This is one of the main upgrade hazards, because the pattern is ubiquitous in feature-engineering code and the failure is silent: your categorical-encoding step just processes zero columns.

            

            
Trap 12“My rolling 7-day average feature is fine.”
              
Trap: not checking the window boundary. Correct: rolling(7) includes the current row, so if you're predicting today's value the feature contains its own target. Backtest looks superb; production doesn't.
Fix: .shift(1) before .rolling(). For panel data: sort, group by entity, then shift, then roll — otherwise you also bleed one entity's history into another's features.

            

            
Trap 13“except Exception: pass makes the pipeline robust.”
              
Trap: calling it robustness. Correct: it converts every failure — including your own typos and a renamed column — into silence, and the pipeline reports success with wrong numbers. In data work that's the worst failure mode: a crash gets fixed, a quiet wrong answer reaches a dashboard and then a decision.
Instead: catch specific exceptions, log what you swallow with enough context to find the record, re-raise anything unexpected, and put a threshold on the acceptable bad-row rate.

            

            
Trap 14“groupby().sum() covers every row.”
              
Trap: assuming completeness. Correct: groupby drops rows whose key is NaN by default, so the group totals can be legitimately less than the column total — with no warning.
Pass dropna=False, or fillna("UNKNOWN") on the key first. And make it a habit to assert the total is conserved after any aggregation.

            

          

        

      


      

        
11.11 Live-coding exercises ⭐

        
Eight problems that actually appear. Type the solution yourself in the cell — reading one teaches you much less than writing one under time pressure. Each has a reference solution underneath.


        

          
          How to use these

CodingWhere does the SQL↔pandas mapping break down?
              
Three places. The index — SQL has no equivalent, so pandas operations align on it in ways a SQL translation doesn't capture; that's the source of surprise NaNs. Order — SQL results are unordered without ORDER BY, while pandas preserves and relies on row order (shift, diff, keep="last"). Nulls — SQL's three-valued logic differs from NaN semantics, so WHERE x != 5 excludes nulls in SQL, and a pandas mask on NaN gives False rather than NULL.
And the practical one: pandas has no query planner. SQL will reorder your joins and push down predicates; pandas executes exactly what you wrote, in order — which is why filtering before joining matters in pandas and not in SQL.

            

          

        

      


      

        
11.14 The 90-second project story

        
You will be asked to describe your work. A rehearsed 90-second structure beats a rambling five minutes, and it's the cheapest preparation available.


        

          
structure Five beats, 90 seconds

          
1 · context
One sentence on the business problem and why it mattered. Not the tech stack.

          
2 · simplest first
What you tried first and why it wasn't enough. This signals judgement rather than reflexive complexity.

          
3 · the hard part
One specific technical obstacle and how you diagnosed it — leakage found, a join exploding, a memory ceiling.

          
4 · the number
Land on a measurement. Latency, cost, accuracy, hours saved. Vague impact is the most common failure.

          
5 · what you'd change
One honest limitation. A candidate with no criticisms of their own project reads as someone who never measured it.

        


        

          
Drill

          

            
Practical“Tell me about a project you're proud of.”
              
Use the five beats: context (the business problem in one sentence), simplest thing first (and why it wasn't enough), the hard part (one specific obstacle, and how you diagnosed it rather than guessed), the number, what you'd change.
The number is what most answers lack. “It improved things” is unmemorable; “cut the nightly job from 3 hours to 12 minutes, which let us move from daily to hourly refresh” is a story with a shape.
And pick a project where the hard part was technical and specific — a leakage bug you found, a join that silently inflated revenue 50%, a memory ceiling you worked around. Those make the interviewer ask a follow-up, which is exactly what you want.

            

            
Practical“What was the hardest bug you've debugged?”
              
Pick one with a non-obvious cause and a clear diagnostic path, and include the wrong hypothesis you had first — that's what makes it believable and shows how you actually work.
Strong candidates from this guide: a missing add_messages-style reducer or an index-alignment NaN; a sync client blocking an event loop so “parallel” work ran serially; a many-to-many join inflating revenue; a scaler fitted before the split producing a 0.99 AUC that collapsed in production; an int16 downcast overflowing on aggregation.
Structure: symptom → first hypothesis → the evidence that disproved it → actual cause → fix → what you added so it can't recur. That last clause is the part that distinguishes a debugging story from an engineering one.

Self-test

          

            
DebugCover the table. Given “my numbers are 50% too high”, what are your three checks?
              
1. A join that duplicated rows. Check len() before and after every merge, and whether the right side was unique on the key. This is the most likely cause of a systematic overstatement.
2. Double-counting from a concat or an append that ran twice — check for duplicated rows with df.duplicated().sum().
3. An aggregation over the wrong grain — summing a column that was already a per-group total, which is what happens after a transform is mistaken for an agg.
And the general diagnostic: reconcile against a known total at each stage. If revenue is right after step 2 and wrong after step 3, you've localised it in one pass.

            

            
DebugGiven “it works in the notebook but fails in the script”, what's your first hypothesis?
              
Hidden state from out-of-order cell execution. The notebook has a variable, an import, or a monkey-patched setting that the script doesn't, because you defined it in a cell you later edited or deleted. The test is “Restart and Run All” — if that fails, the notebook was lying.
Second hypothesis: a different working directory or environment, so relative paths resolve differently or a package version differs. Third: something depending on display rather than value — a frame that looked fine because Jupyter truncated it.
