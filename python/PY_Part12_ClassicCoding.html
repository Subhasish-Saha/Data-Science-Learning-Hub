12.1 How the classic round is actually scored ⭐⭐

Nobody asks you to reverse a string because they are unsure whether you can. They ask because it is a five-minute problem with no difficulty to hide behind — so what is left on the table is entirely how you work.

This matters more at four years than at zero. A graduate who produces s[::-1] and stops has answered the question. Someone with four years of experience who produces s[::-1] and stops has answered a different, easier question, and the interviewer notices. The expected shape of a senior answer to a junior problem is: the idiomatic solution, the from-scratch solution, the complexity of both, the edge case, and a sentence on how you would test it. That is thirty extra seconds of talking and it is most of the score.

Likely interview questions

          

            
Very commonShould I give the Pythonic one-liner or write it out manually?
              
Both, in that order, and say why you are giving both. The one-liner proves you know the language; the manual version proves you know what the language is doing for you. Leading with the one-liner and stopping is the single most common way to under-perform on an easy question.
The script: “In real code I'd write s[::-1]. But I assume you want the mechanics, so here's the loop version — same O(n) time, and it makes the two-pointer variant obvious if you want it in place.” You have now answered the question, the follow-up, and demonstrated that you can read the room.
The one case to skip the one-liner: if they explicitly said “without using built-ins”. Then mentioning it once is fine; using it is not following instructions.

            

            
Very commonWhat complexity do I state when the work is done by a built-in?
              
State the built-in's cost, not O(1) because you only wrote one line. This is a real trap — plenty of candidates call sorted() and then claim O(n).
The numbers you are expected to have: sorted / list.sort are O(n log n) (Timsort, and O(n) on already-sorted input); x in list is O(n); x in set / x in dict are O(1) average; list.insert(0, x) and list.pop(0) are O(n); s[::-1] is O(n) time and O(n) space because strings are immutable; Counter(s) is O(n); heapq.heappush is O(log n).
Also state space honestly. Slicing, sorted, list(reversed(...)) and comprehensions all allocate. “O(n) time, O(1) extra space” is a meaningfully better answer than “O(n)” and it is what distinguishes a two-pointer solution from a slice.

            

            
BehaviouralYou have blanked on the exact syntax. What do you do?
              
Say what you are reaching for and keep moving. “I want the sliding-window Counter here — I think it's Counter.subtract but I'd check the docs; the logic is: add the incoming character, remove the outgoing one, compare to the target counter.” Interviewers overwhelmingly report that they do not care about memorised signatures; they care whether the plan is right and whether you get stuck silently.
What loses points is freezing, or quietly writing something you know is wrong and hoping. Pseudo-code the line, flag it, finish the function, then come back if there's time.

            

            
GotchaThey ask for “in place”. What is the trap?
              
In Python, strings and tuples cannot be modified in place at all — they are immutable, so any “in-place string reverse” is a contradiction. The honest answer is: convert to a list and swap with two pointers for O(1) extra space beyond the conversion, or accept that in Python the O(n)-space slice is the real answer and the in-place version is a C/C++ question wearing Python clothes.
Where in-place genuinely applies: lists (list.reverse(), list.sort(), random.shuffle), NumPy arrays (arr[::-1] is a view, and arr.sort() is in place), and bytearray. Saying “sorted() returns a new list, .sort() mutates and returns None” unprompted is a small, reliable credibility win.

The three follow-ups

Likely interview questions

          

            
Very commonReverse a string. Now do it without slicing.
              
Slicing first: s[::-1] — O(n) time, O(n) space, implemented in C so it is also the fastest. Then without it, and there are two acceptable answers.
Iterator: "".join(reversed(s)). reversed returns a lazy iterator; join sizes the result once and fills it, so this is linear.
Two-pointer: convert to a list, swap i and j moving inward while i < j, join. This is the answer they are usually fishing for because it is the language-independent algorithm and it is O(1) extra space once you have the list.
What not to write: out = ch + out in a loop. It looks like the manual version but it is O(n²) — every iteration allocates a new string and copies everything so far. If you write it, say so and fix it; noticing it is the point.

            

            
GotchaIs s[::-1] O(1) because it is a slice?
              
No. Slicing a str, list or tuple copies — O(k) time and O(k) space for a slice of length k. Strings are immutable, so there is no way to produce a reversed str without allocating a new one.
The place where a reversed slice is O(1) is NumPy: arr[::-1] returns a view with a negative stride, no data copied. That contrast is a great thing to volunteer — it shows you know the difference between a Python sequence and a strided buffer, and it links straight to the views-versus-copies discussion in §6.3.
range is the other O(1) case: range(10)[::-1] is a lazy range object, not a materialised list.

            

            
GotchaDoes s[::-1] always give you the string backwards?
              
It always reverses the code points. That is not the same as reversing what a human sees. A grapheme cluster — an accented letter written in decomposed form, an emoji with a skin-tone modifier, a ZWJ sequence, a Devanagari consonant plus vowel sign — is several code points, and reversing them individually tears the cluster apart.
Concretely: "café"[::-1] puts the combining acute at the front where it modifies nothing and leaves the e bare. Length also lies: that string has len 5 for 4 visible characters.
Handling it: unicodedata.normalize("NFC", s) fixes the decomposed-accent case by composing clusters that have a single-code-point form. For the general case you need grapheme segmentation — the third-party regex module's \X pattern, which matches one grapheme cluster.
You will almost never be asked to implement this. Mentioning it in one sentence — “this reverses code points; if the input can contain emoji or combining marks I'd segment graphemes first” — is what marks the answer as senior.

            

            
Codingreversed(s) versus s[::-1] — when does the difference matter?
              
reversed is lazy: it returns an iterator and allocates nothing until you consume it. s[::-1] is eager: it builds the whole reversed object immediately.
So for “is this a palindrome” on a huge string you can do all(a == b for a, b in zip(s, reversed(s))) and stop at the first mismatch without ever materialising a copy. For “give me the reversed string” you need the copy anyway, so the slice wins on speed.
Two details worth knowing: reversed requires __reversed__ or both __len__ and __getitem__, so it works on sequences but not on a generator or a plain iterator — reversed(x for x in "abc") raises TypeError. And reversed on a dict has iterated keys newest-first since 3.8.

            

            
CodingReverse an integer without converting it to a string.
              
Peel digits with divmod and rebuild:
sign, n = (-1 if n < 0 else 1), abs(n), then while n: n, d = divmod(n, 10); out = out * 10 + d, return sign * out. O(number of digits) — that is O(log n) in the value of n, which is the answer to give if they ask for complexity.
Three clarifying questions that earn marks because they are requirements, not code: negatives — preserve the sign or reject? trailing zeros — 1200 becomes 21, is that acceptable? overflow — in C or Java you would need a 32-bit bounds check and return 0, and the reason you do not here is that Python integers are arbitrary precision. Saying that last part shows you know why the LeetCode version of this problem has a rule that looks arbitrary in Python.

            

          

        

      


      

        
12.3 Palindromes ⭐⭐

        
The follow-up to string reversal, and the first problem where the interesting part is not the algorithm but what counts as equal.


        
Two solutions, and the reason there are two

        
Reverse and compare — s == s[::-1]. One line, O(n) time, O(n) space, and it is what you would write in real code. Two pointers — walk in from both ends, return False on the first mismatch. Also O(n) time but O(1) extra space, and it exits early: for a 10 MB string whose first and last characters differ, it does one comparison instead of allocating 10 MB.

        
State both, then say which you would ship: the slice, unless the strings are large or you are in a memory-constrained loop. That sentence is the entire point of the question.


        

          
          The question behind the question
          
Is "A man, a plan, a canal: Panama" a palindrome? Is "Ärger"? Is "12321"? The interviewer wants you to ask, because normalisation is where the real decisions are: strip non-alphanumerics or not, lower() or casefold(), and whether the input can be non-ASCII. Candidates who ask score above candidates who guess correctly.

        


        
casefold() over lower() is a small detail that lands well. lower() does a per-character mapping; casefold() does aggressive case folding designed for comparison, so German "ß" folds to "ss" and Greek final sigma folds to plain sigma. For any case-insensitive comparison, casefold is the correct tool.

The two follow-ups that actually get asked

        
“A palindrome if you may delete at most one character.” Two pointers until the first mismatch, then try skipping the left character or the right one and check whether either remainder is a palindrome. Still O(n) — you only branch once.

        
“Longest palindromic substring.” Expand around every centre: 2n−1 centres (each character and each gap), expanding outward while the ends match. O(n²) time, O(1) space, and about twelve lines. The O(n) Manacher's algorithm exists; nobody expects it, and saying “there is a linear algorithm, Manacher's, but I'd write the expand-around-centre version unless you need it” is the correct amount of knowledge to display.

Likely interview questions

          

            
Very commonCheck whether a string is a palindrome.
              
Start by asking the normalisation question — case, punctuation, whitespace, non-ASCII — because the answer changes the code. Then give both implementations.
s == s[::-1] is O(n) time and O(n) space and is what you would ship. The two-pointer version is O(n) time and O(1) extra space and short-circuits on the first mismatch, which matters when strings are large or the function is hot.
Edge cases to volunteer: the empty string is a palindrome, a single character is a palindrome, and comparison should use casefold() rather than lower() if case is to be ignored. If the input can be a full sentence, normalise with "".join(c for c in s.casefold() if c.isalnum()) first.

            

            
Gotchalower() or casefold()?
              
casefold() for any comparison. lower() is a display transform — it maps each character to its lowercase form. casefold() is a comparison transform designed to make case-insensitive matching work across the whole of Unicode, so German "ß" folds to "ss" and Greek final sigma "ς" folds to "σ".
Consequence: "Straße".lower() == "STRASSE".lower() is False, but the casefold version is True. Same rule applies to deduplicating user-supplied keys, matching column names, and grouping labels in a dataframe — df["k"].str.casefold() is the safer normaliser.
Third member of the family: unicodedata.normalize. Case folding does not compose accents, so a proper comparison pipeline is normalise → casefold → filter.

            

            
CodingPalindrome allowing at most one deletion.
              
Two pointers inward. At the first mismatch you have exactly two options — delete the left character or delete the right one — so check whether s[i+1:j+1] or s[i:j] is a palindrome and return the or of the two. If you reach the middle without a mismatch, it was already a palindrome.
Complexity O(n) time, O(1) space. The key insight to state: the branch happens at most once, because after using your one deletion the remainder must match exactly. That is why this is not a dynamic-programming problem, and saying so pre-empts the “could you memoise it?” probe.
The natural generalisation — at most k deletions — is DP: it is the edit-distance table between s and s[::-1], and you need the longest palindromic subsequence. Knowing where the cliff is matters more than being able to write the table.

            

            
CodingLongest palindromic substring.
              
Expand around centre. There are 2n−1 possible centres — n characters for odd-length palindromes and n−1 gaps for even-length ones — and from each you expand while the outer characters match, tracking the best span. O(n²) time, O(1) space.
Two mistakes to avoid. Forgetting the even-length centres, which silently fails on "cbbd". And confusing substring (contiguous) with subsequence (not necessarily contiguous) — the subsequence version is a different, DP problem.
If pushed on the optimum: Manacher's algorithm is O(n). Naming it and saying you would not write it from memory unless required is the right answer; nobody sensible expects it in a data-science interview.

            

          

        

      


      

        
12.4 Anagrams ⭐⭐

        
The question that quietly tests whether you reach for sorted or for Counter — and whether you can say which is faster and why.


        
Two answers, different complexity

        

          

            
ApproachCodeTimeSpaceNotes

            
              
Sort bothsorted(a) == sorted(b)O(n log n)O(n)Shortest to say; the obvious answer

              
Count bothCounter(a) == Counter(b)O(n)O(k) distinct charsThe answer they want; one hash pass each

Both one-liners are correct, so the discriminator is the sentence after: “sorting is O(n log n); counting is O(n) because it is a single pass into a hash map, so I'd use Counter.” Add the early exit — if the lengths differ they cannot be anagrams, so check that first and skip the work entirely.


        

          
          Worth knowing about Counter equality
          
Counter subclasses dict, so == compares key/value pairs and order does not matter — which is exactly the anagram test. Since 3.10 a Counter with a zero count is not equal to one without that key, so Counter({"a": 0}) != Counter(). That bites if you build counters by subtraction rather than by counting.

Likely interview questions

          

            
Very commonCheck whether two strings are anagrams.
              
The one-liner most people give: sorted(a) == sorted(b). Correct, O(n log n).
The one to give instead: len(a) == len(b) and Counter(a) == Counter(b). O(n) — one hash pass per string — plus a free early exit on unequal lengths. Then explain the difference, because that is what is being scored: sorting does more work than the problem needs, since anagram-ness only depends on character multiplicities, not on order.
Clarify first: case-sensitive? Do spaces and punctuation count? Unicode? “Dormitory” and “Dirty Room” are anagrams only after casefolding and stripping the space.
If they say “no imports”, build the dict by hand: count up on the first string, count down on the second, return whether the dict emptied. That version also shows you understand what Counter is doing.

            

            
CodingGroup a list of words into anagram groups.
              
One pass with a defaultdict(list) keyed by a canonical form. The key must be hashable, which is why it is tuple(sorted(word)) and not sorted(word) — a list cannot be a dict key.
Complexity: O(w · k log k) for w words of average length k. If you want to avoid the sort, key on the character counts instead — frozenset(Counter(word).items()), or for a fixed a–z alphabet a 26-tuple of counts, which is O(k) per word.
Follow-up they like: “what if the word list does not fit in memory?” The answer is that the key is a pure function of the word, so you can shard — compute the key, hash it to a bucket, and every anagram group lands in exactly one bucket. That is the map step of a MapReduce, and saying so connects the puzzle to actual data engineering.

            

            
GotchaWhy tuple(sorted(w)) rather than sorted(w) as the key?
              
Because sorted returns a list, and lists are unhashable — list.__hash__ is None, so using one as a dict key raises TypeError: unhashable type: 'list'. A dict needs the key's hash to stay stable for as long as the entry exists, which a mutable object cannot promise.
tuple is the fix, and it is hashable only because its contents are — a tuple containing a list is still unhashable. Alternatives with the same property: "".join(sorted(w)) (a string key, often the neatest), or frozenset when order genuinely does not matter, though note frozenset discards multiplicity so it is wrong as an anagram key on its own — "aab" and "abb" would collide.

            

            
CodingFind every starting index where an anagram of p occurs in s.
              
Fixed-width sliding window with a running Counter. Initialise the window on the first len(p) characters, compare to Counter(p), then for each step add the entering character and decrement the leaving one, deleting keys that reach zero. O(len(s)) time; O(k) space for k distinct characters.
The naive version — slice each window and sort it — is O(n · m log m) and is the answer to visibly reject.
The subtle bug: a Counter holding {"a": 0} does not compare equal to one that lacks the key at all, so if you only decrement and never delete, the equality test silently stops matching. Either delete zeros, or compare with a helper that ignores them. This is the detail that separates “I have written a sliding window” from “I have read about one”.

Famous as a filter for people who cannot program at all — which means at four years' experience it is never really about FizzBuzz. It is about whether your first instinct produces code that survives a new requirement.

Likely interview questions

          

            
Very commonWrite FizzBuzz.
              
Return a value per number rather than printing inside a loop — that is the first differentiator. Check the most specific condition first: n % 15, then n % 3, then n % 5, else str(n). O(1) per number, O(n) for the range.
Then volunteer the version with no ordering to get wrong: build the label by concatenation — ("Fizz" if n % 3 == 0 else "") + ("Buzz" if n % 5 == 0 else "") — and return out or str(n). It is shorter, it has no unreachable branch, and it generalises.
Clarifications that show care: inclusive or exclusive upper bound, is 0 in scope (it is divisible by 15), and do they want the strings returned or printed. Ask once, briefly, then code.

            

            
Very commonNow add: multiples of 7 print Bazz.
              
This is the actual question. With an if/elif chain you now need branches for 3, 5, 7, 15, 21, 35 and 105 — the cases grow as 2k in the number of rules, and the ordering must be maintained by hand.
The answer that scales: rules as data. RULES = [(3, "Fizz"), (5, "Buzz"), (7, "Bazz")], then "".join(word for div, word in RULES if n % div == 0) or str(n). Adding a rule is appending a tuple; the combined labels and their order emerge from the list. Complexity is O(k) per number for k rules.
If they push further — “the rules come from a config file”, “a rule can be an arbitrary predicate” — the same structure absorbs it: store (predicate, label) pairs instead of (divisor, label). Being able to say “I would rather change data than change code” and then demonstrate it is the whole point of asking a senior candidate a trivial problem.

            

            
CodingVectorise FizzBuzz over a million rows in pandas.
              
Boolean masks and assignment, or np.select. The masked version: start with s = pd.Series(n.astype(str)), then assign s[n % 3 == 0] = "Fizz", s[n % 5 == 0] = "Buzz", s[n % 15 == 0] = "FizzBuzz".
The order inverts. With if/elif the most specific test must come first because the first match wins; with masked assignment it must come last because the last write wins. Getting this backwards produces a silently wrong column with no error — exactly the kind of bug that survives into production.
np.select([n % 15 == 0, n % 3 == 0, n % 5 == 0], ["FizzBuzz", "Fizz", "Buzz"], default=n.astype(str)) restores the first-match-wins semantics and is usually the clearer choice. Either way, avoid df.apply(fizzbuzz) — it is a Python-level loop and roughly two orders of magnitude slower; see §9.2.

            

            
ConceptualWhy is FizzBuzz still asked to experienced candidates?
              
Not to check that you can code. Three things are actually being observed. Does your first draft have the unreachable branch? — a proxy for whether you reason about condition ordering or pattern-match on the wording. Do you return or print? — a proxy for testability instincts. Does your solution survive the follow-up? — the real test, because a new rule either costs one line or a rewrite.
There is a fourth, quieter one: how you behave when handed a problem beneath your level. Treating it seriously, clarifying the bounds, and offering the extensible version without being condescending about it is itself a signal. Sighing at it is a much worse answer than any code.

Likely interview questions

          

            
Very commonWrite a function for the nth Fibonacci number.
              
Write the iterative one and say why: a, b = 0, 1 then for _ in range(n): a, b = b, a + b, return a. O(n) time, O(1) space, no recursion limit, no cache.
Then situate it. The naive recursion is O(φⁿ) — about 1.6× more work per increment — because it recomputes the same subproblems; the tree for fib(5) evaluates fib(2) three times. Adding @functools.cache makes that O(n) with one line, which is the cheapest possible fix if you have already written the recursion. If they want sub-linear, fast doubling is O(log n).
Clarify the indexing convention — is fib(0) 0 or 1? — and handle negative input explicitly. Those two questions take five seconds and are the difference between a tidy answer and a “works on my example” answer.

            

            
Very commonPrint all Fibonacci numbers below a given N.
              
This is the phrasing data-science screens actually use, and it is not the nth-number problem — it is a stream with a stopping condition, so a generator is the natural fit.
def fib_stream(): a, b = 0, 1; while True: yield a; a, b = b, a + b, then list(itertools.takewhile(lambda v: v < N, fib_stream())). O(k) time for k terms, O(1) memory, and the generator is reusable for “first k terms” or “sum of even terms below N” without modification.
Two edge cases to raise: is the bound inclusive, and what should N = 1 return? Interviewers use both to check you tested rather than eyeballed.

            

            
GotchaWhy not use the closed-form Binet formula? It is O(1).
              
Because it uses floating point and therefore returns wrong answers from n = 71. F(71) is 308,061,521,170,129, which exceeds 253, and a double has only 53 bits of mantissa, so the rounded result is off by one or more and gets worse from there. It fails silently — no exception, just an incorrect integer.
It is also not really O(1): PHI ** n for large n is not a constant-time operation, and if you use exact arithmetic instead of floats to fix the precision problem you are back to O(log n) multiplications of large numbers.
The good answer mentions it as a known result and rejects it for the stated reason. This is the same class of issue as “never test floats with ==” and “sum a float column in a different order and get a different total” — the interviewer is often really probing whether you know that float has limits and int does not.

            

            
CodingMemoise it. What are the options and their trade-offs?
              
@functools.cache (3.9+) — unbounded, thread-safe, minimal overhead; it is lru_cache(maxsize=None) without the LRU bookkeeping. @lru_cache(maxsize=128) — bounded, evicts least-recently-used, which is what you want in a long-running service. A hand-rolled dict — what to write if they say “no imports”, and it is worth writing once so you can explain what the decorator does.
Three trade-offs to name. Memory: cache is a leak by design in a process that sees unbounded distinct arguments. Hashability: arguments must be hashable, so a memoised function cannot take a list or a DataFrame — a very common real-world blocker. Purity: caching a function whose result depends on anything other than its arguments (a file, a clock, a database) is a correctness bug, not an optimisation.
Also mention that @cache on a method keeps self alive in the cache key and so leaks instances — the reason functools.cached_property exists.

            

            
GotchaNaive recursion on fib(2000) — what actually happens?
              
With memoisation you hit RecursionError: maximum recursion depth exceeded long before any arithmetic problem, because the chain fib(2000) → fib(1999) → … is 2000 frames deep and CPython's default limit is 1000. Without memoisation you never find out, because it would not finish.
The options, in the order you should offer them: rewrite iteratively (correct); raise the limit with sys.setrecursionlimit (a foot-gun — the real constraint is the C stack, and exceeding it segfaults rather than raising); increase the thread stack size and run it in a thread (works, and is what you do when a recursive algorithm is genuinely the clearest). Python has no tail-call optimisation and Guido has explicitly declined to add it, so deep recursion is never the idiomatic answer.
Note that the arithmetic is fine: Python integers are arbitrary precision, so F(2000) — 418 digits — is exact. The limit you meet is the interpreter's, not the number's.

            

          

        

      


      

        
12.7 Factorial, recursion limits and big integers ⭐

        
Three lines of code and two genuinely surprising limits — one in the interpreter, one that was added as a security fix and catches almost everybody.


        
The three implementations, and which to reach for

        
math.factorial(n) — C implementation, correct, fast, handles large n; use it in real code and say so. Iterative — for i in range(2, n+1): out *= i; O(n) multiplications, O(1) space, no stack. Recursive — the textbook version, and the one they usually want to see because factorial is the canonical example of a recurrence with a base case. Get the base case right (0! == 1) and validate negatives.


        

          
          The 4300-digit wall
          
Since the September 2022 security releases, converting an int to a str raises ValueError above 4300 digits by default — because the conversion is quadratic and was a denial-of-service vector. The practical consequence: math.factorial(1559) computes fine, but printing it raises. The arithmetic is unlimited; only the decimal rendering is capped. Raise it with sys.set_int_max_str_digits(n), or note that hex(), bin() and bit_length() have no such limit because those conversions are linear.

Likely interview questions

          

            
Very commonWrite factorial, recursively and iteratively.
              
Recursive: return 1 if n < 2 else n * fact(n - 1). Using n < 2 rather than n == 0 covers both base cases in one line and avoids an extra call. Iterative: multiply range(2, n + 1) into an accumulator — O(n) multiplications, O(1) space.
Three things to say unprompted. 0! == 1, because it is the empty product — a definition, not a special case. Negatives should raise ValueError, not silently return 1. And in production use math.factorial, which is a C implementation that is faster and already handles these cases.
The recursive version is a genuine liability for large n: CPython's default recursion limit is 1000, there is no tail-call optimisation, and it will raise RecursionError where the iterative version simply works. Naming that is the correct instinct — recursion here is pedagogy, not engineering.

            

            
Gotchamath.factorial(2000) works but printing it crashes. Why?
              
Because int → str is capped at 4300 digits by default and raises ValueError above it. This landed in the September 2022 security releases (CPython 3.11 and backports to 3.7–3.10) as a fix for a denial-of-service vector: decimal conversion of a huge integer is quadratic, so a hostile input of a few megabytes could pin a CPU for a very long time.
The distinction that matters: arbitrary-precision arithmetic is untouched. You can compute, add, multiply and compare integers of any size; only the decimal rendering is limited. hex(), bin(), oct() and bit_length() are all linear and therefore uncapped.
Fixes, in order of preference: do not render it (compare, or take n % 10**k for the digits you need); sys.set_int_max_str_digits(N) for a deliberate raise; the PYTHONINTMAXSTRDIGITS environment variable or -X int_max_str_digits at startup. Knowing this exists is a strong currency signal — plenty of people with four years of Python have never met it.

            

            
CodingHow many trailing zeros does n! have?
              
Count the factors of 5. A trailing zero needs a factor of 10 = 2 × 5, and factorials always contain more 2s than 5s, so the number of 5s is the binding constraint.
count = 0; p = 5; while p <= n: count += n // p; p *= 5. The n // 25 term catches numbers contributing two 5s, n // 125 those contributing three, and so on. For n = 100 that is 20 + 4 = 24.
Complexity O(log₅ n), and — the point of the question — it never computes the factorial. A candidate who builds math.factorial(n) and strips zeros from the string has solved the example but not the problem, and on n = 10⁹ their version cannot run at all.

            

            
GotchaHow do you compute nCr without overflow?
              
In Python there is no overflow, so the real question is about wasted work and precision. math.factorial(n) // (math.factorial(k) * math.factorial(n - k)) is correct but builds three gigantic integers to return a comparatively small one — for comb(1000, 500) that is thousands of digits of intermediate multiplication.
Use math.comb(n, k) (3.8+), which cancels terms as it multiplies. If you must hand-roll it, iterate out = out * (n - i) // (i + 1) for i in range(k), exploiting that the running value stays an exact integer at each step, and take k = min(k, n - k) first by symmetry.
What not to do: compute it in floating point via math.lgamma and round, unless you genuinely only need an approximation — that loses exactness silently. If the answer feeds a probability, math.comb then divide, or work in log space deliberately and say that you are.

            

          

        

      


      

        
12.8 Primes and number theory ⭐

        
Trial division, the square-root bound, the sieve, and a floating-point trap in the one line everybody writes.


        
Primality: three levels of answer

        
Level 1 — test every divisor from 2 to n−1. O(n), and the answer nobody wants. Level 2 — stop at √n, because if n = a·b then one of the factors is at most √n. That single observation takes it to O(√n) and is the answer being fished for. Level 3 — test 2 and 3, then only 6k ± 1, since every other candidate is divisible by 2 or 3. Same complexity class, roughly a third of the work.


        

          
          Use math.isqrt, not int(n ** 0.5)
          
n ** 0.5 goes through a float, which has 53 bits of mantissa. For n = 10**18 - 1 it rounds up: int(n ** 0.5) gives 1000000000 where the true integer square root is 999999999. In a primality loop that means you test one divisor too many or too few — a silently wrong answer for large inputs. math.isqrt (3.8+) is exact integer arithmetic and has no such failure mode.

Euclid's algorithm is while b: a, b = b, a % b — three lines, O(log min(a,b)). In real code use math.gcd, which since 3.9 takes any number of arguments, and math.lcm, which arrived at the same time. Likely interview questions

          

            
Very commonCheck whether a number is prime.
              
Guard n < 2, handle 2 and 3, reject even numbers, then trial-divide by odd numbers up to math.isqrt(n) inclusive. O(√n) time, O(1) space.
The key sentence: if n = a · b then one of a, b is at most √n, so anything past the square root is redundant. Use math.isqrt rather than int(n ** 0.5) — the float version is off by one for large n because a double has only 53 bits of mantissa.
Edge cases interviewers deliberately check: 0 and 1 are not prime, 2 is prime, and negatives are not. A naive all(n % d for d in range(2, n)) returns True for both 0 and 1 because the range is empty — the classic off-by-guard bug on this question.
If they want more: the 6k ± 1 skip cuts the work by about two thirds, and for genuinely large numbers you would use Miller–Rabin — probabilistic, or deterministic with a fixed witness set below 3.3 × 10²⁴. Naming it is enough.

            

            
Very commonPrint all primes below N.
              
Sieve of Eratosthenes, not trial division per number. Allocate a boolean array of size N, mark 0 and 1 as composite, then for each p up to √N that is still marked prime, cross out p*p, p*p+p, p*p+2p, …. What survives is the primes.
Complexity O(n log log n) time and O(n) space — effectively linear, versus O(n√n) for testing each number independently. Two details that show you have written one: start crossing out at p*p (smaller multiples were already handled by smaller primes), and use a bytearray with slice assignment — flags[p*p::p] = bytearray(len(flags[p*p::p])) — so the inner loop runs in C rather than Python.
If N is huge, mention the segmented sieve: process the range in cache-sized blocks so memory stays bounded. That is the honest answer to “primes below 10¹²”.

            

            
GotchaWhat is wrong with int(n ** 0.5)?
              
It converts to float first, and a double holds 53 bits of mantissa, so above about 2⁵³ the result can be off by one — in either direction. Concretely: for n = 10**18 - 1, int(n ** 0.5) returns 1000000000 although 1000000000² is strictly greater than n; the true integer square root is 999999999.
In a primality loop that either skips a divisor or tests one too many, and the failure is silent — a wrong True for a composite. In a “is this a perfect square” check it is worse, because int(n ** 0.5) ** 2 == n can be False for genuine squares.
math.isqrt(n) (3.8+) computes the floor of the square root using integer arithmetic only, with a guarantee: isqrt(n)**2 <= n < (isqrt(n)+1)**2. It is also the right tool for perfect-square tests: math.isqrt(n) ** 2 == n.

            

            
CodingGCD and LCM without importing anything.
              
GCD is Euclid: while b: a, b = b, a % b, then return a. O(log min(a, b)) — the modulo shrinks the pair fast. Take abs first if negatives are possible, and note gcd(0, n) == n, which the loop gives you for free.
LCM from GCD: abs(a) // gcd(a, b) * abs(b). Divide before multiplying — mathematically identical but it keeps the intermediate value small, which matters in languages with fixed-width integers and is simply tidier here. Guard the zero case: lcm(0, n) is 0 and the naive formula divides by zero.
In real code: math.gcd and math.lcm, both variadic since 3.9, both C. Mentioning that you would use the stdlib while still being able to write Euclid is the balance the question is looking for.

Likely interview questions

          

            
Very commonFind the first non-repeating character in a string.
              
Two passes. Count with Counter(s), then scan s in order and return the first character whose count is 1. O(n) time, O(k) space for k distinct characters. next((ch for ch in s if counts[ch] == 1), None) gives the early exit and a clean “no such character” result.
The neater variant, and a nice thing to know: iterate the counter rather than the string — next((ch for ch, c in counts.items() if c == 1), None) — which works because Counter is a dict and dicts have preserved insertion order since 3.7, so the first key with count 1 is the first such character in the string. Saying why that is valid is the interesting part; relying on it without knowing why is a latent bug.
Edge cases: empty string, all characters repeating, and single character. Return None or a sentinel rather than raising, and say which contract you chose.

            

            
Very commonRemove duplicates from a list. Does order matter?
              
Ask, because the two answers are different. Order irrelevant: list(set(x)), O(n). Order preserved: list(dict.fromkeys(x)), also O(n) — dict keys are unique and insertion-ordered, so this is the idiomatic one-liner and it beats the manual seen-set loop on brevity while matching it on complexity.
Two caveats worth raising. Both require hashable elements, so a list of dicts or lists needs a key function — dict.fromkeys(tuple(sorted(d.items())) for d in rows) or a manual loop keyed on something canonical. And set ordering is arbitrary and varies between runs for strings, because string hashing is salted per process unless PYTHONHASHSEED is fixed — so list(set(...)) in a pipeline whose output is compared between runs is a real source of flaky diffs.
In pandas the equivalents are Series.unique() (preserves order of appearance) and drop_duplicates(keep="first").

            

            
Very commonCount word frequencies in a block of text and return the top 10.
              
Three steps, and the marks are in the first. Tokenise with re.findall(r"[a-z']+", text.casefold()) rather than text.split(), because splitting on whitespace leaves "times," and "times" as distinct tokens — that is where most answers silently go wrong. Filter stopwords with a set for O(1) membership. Count with Counter and take .most_common(10).
Complexity O(n) for the count; most_common(k) is O(n log k) via a heap, and most_common() with no argument sorts everything at O(n log n). Mentioning that distinction is a small, cheap win.
Follow-ups they reach for: ties — most_common breaks them by insertion order, so sort by (-count, word) if you need determinism. Scale — if the text does not fit in memory, stream it line by line and counter.update(tokens) per line; memory is then proportional to the vocabulary, not the corpus. Real pipelines — stemming or lemmatising, and whether "don't" is one token or two, are modelling decisions to raise rather than guess.

            

            
CodingFind the duplicates in a list. What is the naive answer and why is it bad?
              
The naive answer is a nested loop — for each element, scan the rest — which is O(n²) and is the single most common accidental quadratic in interview code. On 100,000 items it is 5 × 10⁹ comparisons.
The hash answer is one pass: [v for v, c in Counter(x).items() if c > 1] for all duplicates, O(n) time and O(n) space. If you only need the first duplicate, keep a seen set and return as soon as a member is already present — same complexity, but it stops early and uses less memory on inputs that repeat quickly.
State the trade explicitly, because it is the lesson: you are buying O(n) time with O(n) space. If memory is the binding constraint and the input can be reordered, sorting first and scanning adjacent pairs is O(n log n) time with O(1) extra space. Offering both and naming the trade-off is a better answer than either alone.

A small family of problems with an O(1)-space solution that looks like magic until you can state the one property it rests on.


        
The property everything here depends on

        
XOR is commutative, associative, and every value is its own inverse: x ^ x == 0 and x ^ 0 == x. So XOR-ing a whole collection together cancels every value that appears an even number of times, regardless of order, leaving only what appears an odd number of times. Say those three properties and every problem below becomes obvious.

The bit worth memorising: x & -x isolates the lowest set bit, because in two's complement -x is ~x + 1, which flips everything above the lowest set bit and leaves it aligned. It is the standard partition trick for “two singles” and it also appears in Fenwick trees. And note the last block: Boyer–Moore returns a wrong answer rather than None when no majority exists — verifying the candidate is not optional unless the problem guarantees existence.

        


        

          
Likely interview questions

          

            
Very commonAn array holds 0..n with one number missing. Find it.
              
Two O(n)-time, O(1)-space answers. Gauss: the expected total is n*(n+1)//2, so the missing value is expected minus actual. XOR: XOR the indices 0..n together with every element; each present value cancels with its index and the missing one survives.
Then the comparison, which is the actual content of the question: in C or Java the sum can overflow a 32-bit integer for large n, which is exactly why the XOR version is the canonical textbook answer. In Python integers are arbitrary precision, so the sum version is safe and clearer — and saying that shows you understand why the trick exists rather than just reciting it.
Rejected answers and why: sorting is O(n log n); a set difference is O(n) time but O(n) space. Both are fine if you say so; presenting them as optimal is not.

            

            
Very commonEvery element appears twice except one. Find it in O(1) space.
              
reduce(operator.xor, nums, 0), or a plain loop with out ^= v. O(n) time, O(1) space.
Justify it with the three properties rather than asserting it works: XOR is commutative and associative, so order does not matter; x ^ x == 0, so every pair cancels; x ^ 0 == x, so the unpaired value survives. Those three sentences are the answer.
The follow-up is “now exactly two elements appear once”. XOR everything to get a ^ b, isolate any bit where they differ with x & -x, partition the array on that bit, and XOR each half independently. Still O(n) time and O(1) space. If instead every element appears three times except one, XOR no longer cancels — you count bits modulo 3, or admit that a Counter is the sane engineering answer.

            

            
GotchaBoyer–Moore voting for the majority element — what is the catch?
              
It is only correct if a majority element is guaranteed to exist. The algorithm keeps a candidate and a counter, incrementing on a match and decrementing otherwise, resetting the candidate when the counter hits zero. On [1, 2, 3, 4] it returns 3 — confidently wrong, with no signal.
So when existence is not promised, verify in a second pass: count the candidate and check it exceeds n // 2. That keeps O(n) time and O(1) space and makes the function honest.
Why bother when Counter(nums).most_common(1) is one line? Because that costs O(n) space, and the question is explicitly about doing it in constant space. Give the Counter answer first as the thing you would ship, then the voting algorithm as the constant-space version, then the verification caveat. That ordering is the complete answer.

            

            
ConceptualAre these bit tricks worth learning for a data-science interview?
              
Honestly: the specific tricks, rarely. XOR-to-find-the-single is a stock question and worth having ready, but nobody's data pipeline depends on x & -x.
What is worth taking from the family is the shape of the reasoning — find an invariant that makes the extra storage unnecessary. That same move is Welford's algorithm for a streaming mean and variance, reservoir sampling for a uniform sample from a stream of unknown length, HyperLogLog for approximate distinct counts, and the running-counter sliding window from §12.4. Those do appear in real data engineering, and interviewers who ask the XOR question are often really asking whether you think in invariants.
So the useful preparation is not memorising bit identities. It is being able to say, for any “do this in O(1) space” problem, “what quantity can I maintain incrementally that determines the answer?”

Likely interview questions

          

            
Very commonTwo Sum — return the indices of the two numbers adding to a target.
              
One pass with a dict from value to index. For each element, check whether target - x is already in the dict; if so return the stored index and the current one, otherwise store x. O(n) time, O(n) space.
Say the transformation explicitly, because it is the reason this question exists: the brute force searches forward for a partner, which is O(n²); the dict lets each element be found by whoever needs it later, which is O(n). You are trading space for time.

Very commonThe array is already sorted. Can you do better?
              
Yes — two pointers, O(n) time and O(1) space, which beats the dict on memory. Start lo at the front and hi at the back; if the sum is too small move lo up, if too large move hi down, and stop when they meet.
Justify the correctness rather than just describing the loop: because the array is sorted, moving lo can only increase the sum and moving hi can only decrease it, so at each step exactly one move is safe and no valid pair is ever skipped.
Two caveats: the two-pointer version returns values, so if the caller needs original indices you must either carry them along or sort (value, index) pairs. And if the input is not sorted, sorting first costs O(n log n), which is worse than the dict's O(n) — so sorting is only the right answer when the input arrives sorted, when you need O(1) space, or when you need all pairs.

            

            
CodingThree Sum — all unique triples summing to zero.
              
Sort, then fix one element and two-pointer the remainder. O(n²) time, O(1) extra space beyond the sort. The naive triple loop is O(n³) and the “dict of pairs” approach costs O(n²) space, so this is the standard answer.
All the difficulty is in uniqueness, and that is what is being marked. Three skips are needed: skip an anchor equal to the previous anchor, and after recording a triple, advance past runs of equal values on both the lo and hi sides. Miss any of them and you emit duplicates on input like [0,0,0,0].
Two easy optimisations worth mentioning: once the anchor is positive you can break, since the array is sorted and three positives cannot sum to zero; and deduplicating with a set of sorted tuples is a legitimate fallback if you cannot get the skips right under pressure — say that you are trading clarity for O(k) memory rather than pretending it is optimal.

            

            
GotchaFind the two factors of X with the smallest sum.
              
Iterate d from 2 to math.isqrt(x), remember the largest divisor found, and return (d, x // d). O(√X) time, O(1) space.
The proof is one line and you should give it: the product d · (x/d) is fixed, and by AM–GM the sum d + x/d is minimised when d = √x. So the divisor closest to √x from below is optimal, and since you are walking upward that is simply the last divisor you find.
Edge cases: x prime, where the only pair is (1, x) — initialise best to that; x = 1, giving (1, 1); and x <= 0, which should raise. This question is popular in screening tests precisely because the brute-force O(X) loop passes the small test cases and times out on the large ones.

            

          

        

      


      

        
12.12 Sliding window and subarrays ⭐

        
Two patterns cover almost every “find the best contiguous stretch” question: a window that grows and shrinks, and a running total that resets. Both are O(n) and both replace an O(n²) instinct.


        
Kadane's algorithm, stated properly

        
Maximum subarray sum: at each element, either extend the previous best-ending-here or start fresh at this element — cur = max(x, cur + x) — and track the best cur seen. O(n) time, O(1) space. The insight worth articulating is that a running sum which has gone negative can never help a later subarray, so discarding it is always safe.

        
The trap: initialising best = 0. On an all-negative array the answer is then 0, which is not a subarray at all. Initialise from the first element, and ask whether the empty subarray is allowed.

Very commonMaximum sum of a contiguous subarray.
              
Kadane's algorithm. Keep cur = max(x, cur + x) — at each element either extend the run or start a new one here — and track the maximum cur. O(n) time, O(1) space.
The reasoning to state: if the running sum has gone negative it can only hurt any subarray that continues through it, so discarding it is always at least as good as keeping it. That is the whole algorithm, and saying it is much stronger than reciting the recurrence.
The trap is initialisation. Setting best = 0 returns 0 for an all-negative array, which is the empty subarray and usually not what is wanted — the correct answer for [-3, -1, -7] is −1. Initialise both variables from nums[0], and ask whether the empty subarray counts.
Follow-up: return the indices too. Track where the current run started and copy those bounds whenever best improves. Related: maximum product subarray, which needs both the running max and min because a negative can flip them.

            

            
Very commonLongest substring without repeating characters.
              
Variable-width sliding window with a dict of char → last seen index. Advance the right edge; if the incoming character was seen at or after the current left edge, move the left edge to one past that index. Track the best width. O(n) time, O(k) space for k distinct characters.
The bug almost everyone writes: lo = last[ch] + 1 without the last[ch] >= lo guard. On "dvdf" that drags the left edge backwards when it meets a stale occurrence and returns 3 for a window that contains a duplicate. Mention the guard and why it exists.
Why it is O(n) despite the nested movement: both edges only move forward, so each index is processed a bounded number of times. That argument generalises to the whole window family — “at most k distinct”, “minimum window containing T”, “shortest subarray with sum ≥ target”.

            

            
GotchaWhen does the sliding window not work?
              
When adding an element can make an invalid window valid again — that is, when the validity condition is not monotonic in the window's contents. The shrink step assumes “too big” can only be fixed by removing from the left, and that assumption is what makes the linear scan sound.
The standard example: subarray sum with negative numbers. “Shortest subarray with sum ≥ target” is a clean window when all values are non-negative, and is not a window problem once negatives are allowed, because extending right can decrease the sum. The tool then is prefix sums plus a hash map (for exact sums) or a monotonic deque (for extrema), both O(n).
This is a great thing to raise unprompted, because it shows you understand why the pattern works rather than pattern-matching on the words “contiguous subarray”. It is also the honest answer to “count subarrays summing to exactly k”, which is prefix-sum-plus-counter, not a window.

Very commonFlatten an arbitrarily nested list.

CodingRotate a list by k positions.

If they want it in place with O(1) space, the trick is three reversals: reverse the whole list, then reverse the first n-k, then the last k. Worth knowing, and worth saying that in Python a[:] = a[k:] + a[:k] is what you would actually write.

Recognising that the answer is “change the container” rather than “optimise the loop” is the senior instinct here — and it is the same lesson as §2.3.

            

            
GotchaWhat is wrong with list(zip(*[iter(a)] * n)) for chunking?
              
It silently drops the incomplete final chunk. zip stops at the shortest input, so chunking a 7-element list into 3s gives two chunks and loses the seventh element with no error. In a data pipeline that is a quietly missing row.
Correct options: itertools.batched(a, n) (3.12+), which yields the short tail as its own tuple; itertools.zip_longest(*[iter(a)] * n, fillvalue=None) if a padded tail is acceptable; or plain slicing, [a[i:i+n] for i in range(0, len(a), n)], which is the clearest and works on any sequence.
Related and worth mentioning: zip(a, b) also truncates to the shorter argument, which is why zip(strict=True) was added in 3.10 to raise instead. Reaching for strict=True when two sequences are supposed to be the same length is a small, real robustness habit.

            

            
CodingMerge two sorted lists. And a thousand sorted files?

Do not answer sorted(a + b). It is correct but O((n+m) log(n+m)) and throws away the fact that the inputs were already sorted, which is precisely the information the question is testing.
Many streams: heapq.merge(*iterables). It keeps one heap of k front-elements, so it is O(N log k) and — crucially — lazy, holding one element per stream in memory. That is the standard answer to “merge sorted files larger than RAM” and to the external-sort question, and it accepts a key and reverse like sorted.

            

          

        

      


      

        
12.14 Search, sort and top-k ⭐

        
Binary search is the most commonly botched “easy” problem there is, and “top k” is the most commonly over-solved one.


        
Binary search, and the three things to get right

        
The invariant — say what the loop maintains: the answer, if it exists, is always within [lo, hi]. The midpoint — lo + (hi - lo) // 2 is the overflow-safe form and costs nothing to write, even though Python cannot overflow. The termination — with while lo <= hi and integer division, each iteration strictly shrinks the range, so it cannot loop forever; the classic bug is while lo < hi combined with hi = mid, which can stall.

        
In real code use bisect. bisect_left gives the first index where the value could be inserted to keep order — so it is also “first element ≥ x” — and bisect_right gives “first element > x”. The difference between them is the count of exact matches, which is a neat way to answer “how many times does x occur in this sorted list?” in O(log n).

The stability point is the useful one. For k much smaller than n that is a large constant-and-asymptotic win, and it is the answer being looked for. For the kth smallest specifically, heapq.nsmallest(k, ...)[-1] works, and statistics.quantiles or NumPy's np.partition — which is O(n) via quickselect — is the right tool at scale.

Likely interview questions

          

            
Very commonImplement binary search.
              
Inclusive bounds and a strict shrink each step: lo, hi = 0, len(a) - 1; while lo <= hi; mid = lo + (hi - lo) // 2; compare and set lo = mid + 1 or hi = mid - 1. Return -1 if the loop exits. O(log n) time, O(1) space.
State the precondition — the input must be sorted — and the invariant: if x is present it is always inside [lo, hi]. The two classic bugs are the loop condition (lo < hi with hi = mid can fail to terminate if you write lo = mid) and forgetting the ± 1, which leaves the same midpoint under test forever.
mid = lo + (hi - lo) // 2 rather than (lo + hi) // 2 is the overflow-safe idiom; in Python it makes no difference because integers are unbounded, and saying that — knowing the reason and knowing it does not apply here — is better than either writing it blindly or not knowing it.
In real code: bisect.bisect_left. And on a recursive implementation, mention that Python has no tail-call optimisation, so the iterative form is preferred.

            

            
Very commonFind the k largest elements in a list of a million.
              
heapq.nlargest(k, items). It maintains a heap of size k, so it is O(n log k) time and O(k) space — versus O(n log n) time and O(n) space for sorted(items, reverse=True)[:k]. For k = 10 and n = 10⁶ that is the difference between 10 million and 20 million comparisons, plus a much smaller allocation.
Give the thresholds, because they show judgement rather than reflex: for k close to n, just sort. For a single extreme, max/min is O(n) and beats both. For numeric arrays at scale, np.partition(arr, -k)[-k:] is O(n) quickselect and faster still, though it leaves the k values unordered so you sort just those.
Both nlargest and nsmallest accept a key, so “top 5 records by revenue” is one call. And if the data arrives as a stream you cannot re-read, the heap version is the only one of these that works at all — a good closing point.

            

            
CodingMerge overlapping intervals.
              
Sort by start, then walk once: if the current interval starts at or before the last kept interval's end, extend that end to max(last_end, current_end); otherwise append. O(n log n) time — the sort dominates — and O(n) output.
Three things are being graded. Sorting first, without which the single greedy pass is simply incorrect. Using max() for the new end, because a fully nested interval like [(1, 10), (2, 3)] would otherwise shrink the result to (1, 3). And asking whether touching intervals merge — [(1, 4), (4, 5)] — which is a requirements question with no default answer.
Related questions in the same family, worth naming: insert an interval into a sorted non-overlapping list (binary search plus a local merge), find whether any two intervals overlap (sort and check adjacent pairs), and the meeting-rooms problem (sweep the sorted start and end events with a counter). They all reduce to “sort the boundaries, then sweep”.

            

            
GotchaSort by one key ascending and another descending.
              
Two clean options. Tuple key with negation: key=lambda r: (r.age, -r.score) — concise, but only works for numeric fields, and fails on strings or dates.

Timsort is O(n) on already-sorted or reverse-sorted input, which is why it is the default. And sort_values(["a", "b"], ascending=[True, False]) is the pandas equivalent of the tuple trick, with no negation needed.

The last cluster of classics: one problem that is the canonical use of a stack, and a handful of matrix manipulations that Python does more neatly than most languages.


        
Balanced brackets — why a stack and not a counter

        
With one bracket type, a counter works: increment on open, decrement on close, fail if it ever goes negative, and require zero at the end. With several types it does not, because ([)] keeps every counter balanced while being obviously wrong. You need the order of the unclosed openers, and that is exactly a stack: push openers, and on a closer check that the top matches.

Likely interview questions

          

            
Very commonCheck whether a string of brackets is balanced.
              
A stack. Push every opener; on a closer, fail if the stack is empty or its top is not the matching opener, otherwise pop. At the end, the string is balanced only if the stack is empty. O(n) time, O(n) space worst case.
Why not a counter: with a single bracket type a depth counter is sufficient, but with several types "([)]" has a perfectly valid depth profile and is still invalid. What matters is the order of the currently-open brackets, and a stack is the data structure whose whole purpose is remembering that.
Three cases they will test: a closer arriving with nothing open (")(" — a naive “count and compare at the end” passes it and should not), leftover openers at the end, and the interleaved case above. If the input mixes brackets with other characters, ask whether to ignore them.

            

            
CodingDesign a stack with O(1) get_min.
              
Keep a second stack of running minima in lockstep with the data. On push, append min(x, mins[-1]); on pop, pop both. get_min is then just mins[-1] — O(1) for every operation, at the cost of O(n) extra space.
The insight to articulate: the minimum of a stack is a function of its depth, and since pushes and pops only happen at the top, you can precompute and store “the minimum of everything at or below this level” as you go. Nothing needs recomputing because nothing below the top ever changes.
The space-optimised variant — store a min only when it changes, or store encoded deltas from the current minimum — is a reasonable follow-up to mention, though the two-stack version is what to write. This is the standard warm-up for the monotonic-stack family (next-greater-element, largest rectangle in a histogram, daily temperatures), which is worth naming if there is time.

Transpose is list(zip(*m)) — unpacking the rows as arguments makes zip pick one element from each, which is a column. Wrap in [list(r) for r in ...] if lists rather than tuples are wanted.
Derive the rotations from it rather than memorising: clockwise = transpose then reverse each row, [list(r)[::-1] for r in zip(*m)]. Anticlockwise = transpose then reverse the row order, list(zip(*m))[::-1]. Both O(rows × cols). A trap worth flagging: zip(*m[::-1]) is clockwise — reversing before the transpose and reversing after it give different rotations, and quoting the wrong one from memory is very easy.
If they insist on in place with O(1) extra space (square matrices only): swap across the diagonal — iterating j from i + 1 so you touch each pair once — then reverse each row. Starting j at 0 swaps every pair twice and leaves the matrix unchanged, which is the bug to avoid. In NumPy all of this is arr.T or np.rot90, and both are O(1) views rather than copies — a good closing remark.

Likely interview questions

          

            
Very commonCount the words in a file that does not fit in memory.
              
Stream it. Iterate the file object line by line — which is lazy, one buffered read at a time — tokenise with a regex, and counter.update(tokens). Peak memory is proportional to the vocabulary, not the corpus, so a 40 GB log with 200,000 distinct words is entirely comfortable.
What not to do: f.read().split(), or f.readlines(), both of which materialise the file. This is the same distinction as generators versus lists in §4.2, and it is the single most common “does this person understand laziness” probe.
Follow-ups worth pre-empting: if the vocabulary is too large, shard by hash(word) % N into per-bucket counters and merge — which is MapReduce, and every anagram-key argument from §12.4 applies. If approximate counts are acceptable, Count-Min Sketch or HyperLogLog for distinct counts trades exactness for bounded memory. And tokenisation is a modelling decision — casefolding, punctuation, contractions, stemming — so state your choice rather than letting split() make it silently.

            

            
GotchaCompute a 7-day rolling average per user as a model feature.
              
df.groupby("user")["value"].transform(lambda s: s.shift().rolling(7, min_periods=1).mean()). The shift() is the entire answer.
Without it, the window includes the current row, so the feature for day t contains day t's value — which, if the target is derived from that value, is target leakage. It produces a model that validates beautifully and fails in production, and it is one of the most common real defects in feature pipelines. Sort by time first, and if there can be ties on the timestamp, decide explicitly whether same-timestamp rows may see each other.
Two related traps: rolling on an unsorted frame silently computes over the wrong neighbours, and groupby.rolling returns a MultiIndex that will not align back to the original frame — which is why transform with a lambda, or an explicit reset_index(level=0, drop=True), is the safer form. See §8.7 and §10.7.

            

            
CodingCollapse overlapping sessions per user in pandas.
              
It is merge-intervals, vectorised. Sort by (user, start); compute the per-user running maximum of end and shift it so each row sees only the past; flag rows whose start exceeds that previous maximum as the beginning of a new block; cumsum the flag within the user to get block ids; then groupby(["user", "block"]).agg(start="min", end="max").
Two details that are the actual test. Use cummax of end, not the previous row's raw end — otherwise a fully nested session (10:00–11:00 followed by 10:10–10:20) wrongly starts a new block, which is precisely the max() bug from §12.14 in another costume. And decide whether touching sessions merge, which is > versus >=.
The flag-then-cumsum idiom is worth naming explicitly, because the same three lines also do sessionisation by inactivity gap, run-length encoding, streak numbering and “label consecutive blocks of equal values”. If you learn one vectorised pattern from this guide, learn that one.

            

            
ConceptualIs it worth practising LeetCode for a data-science role?
              
Some, and with a different aim than a software-engineering candidate would have. The realistic distribution for a data role at four years is: a lot of pandas and SQL, a moderate amount of statistics and modelling judgement, and a small but non-zero number of classic algorithm questions — most often as a screening filter, and drawn almost entirely from the easy tier: strings, counting, hash maps, two pointers, sorting.
So the efficient preparation is breadth over depth. Be fluent in the material on this page and you have covered most of what actually appears. Grinding hard dynamic programming, graph algorithms and tree traversals has a much lower expected return for these roles — worth knowing the names and shapes, not worth weeks.
Where the effort does pay: the complexity vocabulary (§12.17), because you will be asked to justify a pandas approach in those terms; the hash-map reflex (§12.11), because it is the same instinct as replacing a merge-in-a-loop with a single join; and the “what would you do if this didn't fit in memory” answer, which is the bridge from puzzle to engineering and is asked far more often than any specific algorithm.

Likely interview questions

          

            
Very commonWhat is the time complexity of your solution?
              
Answer in four parts and you will never be caught out. Time, space, what n is, and whether it is worst case or average.
“O(n) time where n is the number of characters, O(k) space where k is the number of distinct characters — so O(1) if the alphabet is fixed. Dict lookups are O(1) average; adversarial worst case is O(n) per lookup, which does not arise here because the keys are not attacker-chosen.”
The two failure modes to avoid. Ignoring built-ins: if you called sorted, you are O(n log n), not O(n). Ignoring space: slices, comprehensions and Counter all allocate, and a follow-up is often specifically about reducing space. Volunteering both numbers before being asked is one of the cheapest points available in any coding round.

            

            
BehaviouralHow much should you talk while coding?
              
Enough that the interviewer never has to guess what you are doing, and not so much that you stop making progress. Practically: narrate at the decision points, work quietly through the mechanical parts.
Narrate: the restatement, the approach and its complexity, each clarifying question, every deliberate trade-off (“I'm using a dict here, which costs O(n) memory to save the inner loop”), and each edge case as you handle it. Do not narrate variable names or syntax.
If you need to think, say so — “give me twenty seconds to work out the index bounds” — rather than going silent for a minute. Silence is the thing interviewers report as most costly, because they genuinely cannot tell whether you are thinking or stuck, and their only options are to interrupt or to mark you down.

Likely interview questions

          

            
BehaviouralYou finish with time left. What do you do?
              
Do not sit quietly, and do not start refactoring for aesthetics. Three things are worth the remaining minutes, in order.
Test it harder. Add the cases you listed but did not run — empty, single, all-identical, the largest realistic input. Finding your own bug is a strong positive signal, not a negative one.
Offer the alternative. “This is O(n log n) because of the sort; there's an O(n) version using a heap if k is small — want me to write it?” That turns dead time into evidence of range.
Talk about production. Type hints, a docstring stating the complexity, what should raise rather than return a sentinel, what you would log, and what happens if the input does not fit in memory. BehaviouralYou cannot finish in time. How do you salvage it?
              
Land a working brute force plus a clear description of the optimisation, rather than an unfinished clever solution.
