11.1 The data model

Where self-taught fluency and genuine understanding diverge. Expect two or three of these in any Python screen.

Drill
Very commonIs Python pass-by-value or pass-by-reference?

Neither — pass-by-object-reference. The function gets a new local name bound to the same object as the caller's.

The consequence is the answer: if the function mutates the object, the caller sees it; if it rebinds its local name, the caller sees nothing. So “does my function affect the caller's DataFrame?” is never about the calling convention — it's about whether you mutated or rebound.

Practical rule: functions either return a new object, or are named for the fact that they mutate. Never both, never silently.

Very commonMutable vs immutable — and why should I care?

Mutable objects change in place keeping their identity; immutable ones can't, so any “change” makes a new object.

Four consequences that make it worth caring: hashability (only immutables with immutable contents can be dict keys); aliasing (mutation is visible through every name); default arguments (a mutable default is shared across calls); performance (s += x in a loop is O(n²) because each step copies).

And a tuple is only shallowly immutable — ([1],) can have its inner list mutated, which is why it's unhashable.

Gotchac = [1,2]; d = c; c += [3] — what is d?

[1, 2, 3]. For a list, += invokes __iadd__ and extends in place, so both names see it. c = c + [3] would instead build a new list and rebind only c.

For a tuple, e += (3,) must rebind — same operator, opposite behaviour, decided by mutability.

Why it matters beyond trivia: arr += 1 mutates a NumPy buffer (cheap, but visible to every view) while arr = arr + 1 allocates a new array (safe, but doubles peak memory).

Very commonWhat's wrong with def f(x, acc=[])?

The default is evaluated once at function-definition time and stored on the function object, so every call omitting the argument shares the same list — mutations accumulate across calls and across the whole process.

Fix: acc=None, then if acc is None: acc = []. Use is None rather than if not acc, so an explicitly-passed empty list is respected.

Same trap catches any computed default: def f(when=datetime.now()) freezes the timestamp at import.

Very commonShallow copy vs deep copy?

Shallow makes a new outer container holding references to the same inner objects; deep recursively duplicates everything.

The part people get wrong: a[:], list(a), a.copy(), dict(d), {**d} and copy.copy are all shallow. Only copy.deepcopy is deep.

Shallow suffices when the contents are immutable. And deepcopy is slow — often the better answer is a comprehension that copies exactly the level you need, or making the data immutable so copying is unnecessary.

Very commonis vs ==?

== compares value via __eq__; is compares identity (same object).

Explain why is seems to work on numbers: CPython interns small ints (about −5 to 256) and some short strings, so 256 is 256 is True while 1000 is 1000 may not be — an implementation detail, not a guarantee.

Rule: is only for singletons (None, True, sentinels). For NaN use .isna() — np.nan == np.nan is False and x is np.nan is unreliable.

Very commonWhy can't a list be a dictionary key?

A dict places keys in buckets by hash and needs that hash stable while the key is stored. A list is mutable, so mutating it after insertion would strand it in the wrong bucket. Rather than allow silent corruption, list.__hash__ is None and you get an immediate TypeError.

Use a tuple — and note hashing is recursive, so a tuple containing a list is also unhashable. frozenset is the hashable set.

GotchaWhat does {1: 'a', True: 'b', 1.0: 'c'} give you?

{1: 'c'} — one entry. 1 == True == 1.0 and all three hash identically, so each assignment overwrites the same slot; the value is the last written while the key stays the first inserted.

Where it bites: building a lookup from a column that mixes int and float (very easy after a pandas upcast), or a flag column that's sometimes 1 and sometimes True. You silently lose entries. Normalise key types before building the dict.

ConceptualExplain the LEGB rule.

Name lookup searches Local → Enclosing → Global → Built-in; first match wins.

The non-obvious part: assignment determines scope at compile time for the whole function. If a function assigns to x anywhere, x is local throughout — so reading it before that line raises UnboundLocalError, even with a global x present.

Use global/nonlocal to rebind an outer name. You don't need either to mutate a mutable global — CACHE[k] = v works, because that mutates rather than rebinds.

Gotcha[lambda: i for i in range(3)] — what do they return?

[2, 2, 2]. Closures capture the variable, not a snapshot — late binding — and by call time the loop has finished with i == 2.

Fixes: a default argument (lambda i=i: i, evaluated at definition time — the §1.5 mechanism used deliberately), functools.partial, or a factory function creating a fresh scope.

Where it bites in data work: building a dict of per-column transformers, registering callbacks in a loop, or a list of delayed joblib jobs — all silently apply the last iteration's parameters to everything.

Deep diveWhy is a Python list of a million ints so much bigger than a NumPy array?

The list stores a million pointers (8 bytes) to a million int objects (~28 bytes each, carrying a refcount and type pointer), scattered across the heap — roughly 36 bytes per element. A NumPy int64 array stores a million raw 8-byte values in one contiguous buffer.

So ~8 MB versus ~36 MB, and the bigger win is speed, because contiguity lets the CPU cache and SIMD instructions work.

That's the whole answer to “why NumPy?”: no boxing, one dtype, contiguous memory.

11.2 Data structures & complexity

Where live-coding rounds are quietly won. The complexity table is the one thing worth memorising.

Drill
Very commonlist vs tuple vs set vs dict?

Give the axes: ordered, duplicates, mutable, hashable, lookup cost.

list — ordered, duplicates, mutable, O(n) membership. tuple — same but immutable, therefore hashable and usable as a key. set — unordered, unique, O(1) membership. dict — key→value, insertion-ordered since 3.7, O(1) lookup.

Then the decision rule: lookup by key → dict; membership or dedup → set; fixed record or dict key → tuple; otherwise list. And name the trap: membership on a list is a linear scan.

Very commonx in list vs x in set?

O(n) vs O(1) average. A list scans; a set hashes and jumps to a bucket.

Caveats worth adding: the set case is average and amortised (collisions degrade it), it costs ~3–4× the memory, and elements must be hashable.

The practical version: converting once before a loop turns O(n·m) into O(n+m). On a 100k-row filter against a 50k allow-list that's minutes to milliseconds, from a one-line change.

GotchaWhy is list.pop(0) a problem?

It's O(n) — removing the first element shifts every other one down. Draining a list that way is O(n²), and it looks innocent.

Use collections.deque: O(1) append/appendleft/pop/popleft. The trade is that deque[i] is O(n), so it's right for a queue and wrong for random access. Same reasoning applies to list.insert(0, x).

ConceptualWhy is list.append “amortised” O(1)?

The list holds a buffer with spare capacity, so most appends just write into a slot. When it fills, Python allocates a geometrically larger buffer and copies — O(n) for that one append.

Because reallocations are geometrically rare, the average per append is constant. Two practical consequences: a single append can occasionally be slow (latency jitter), and if you know the final size, preallocating or using NumPy avoids the copies entirely.

DebugThis function is slow on 100k rows. Find the problem.

Look for a linear operation inside a loop. Four candidates in frequency order: x in some_list (→ set); string or list concatenation in a loop (→ accumulate and join/append); pd.concat or df.append per row (→ build a list of dicts, construct once); .pop(0)/.insert(0,…) (→ deque).

And say how you'd confirm rather than guess: time it at two input sizes. Doubling the input and seeing 4× means quadratic, which localises the bug class before you read another line.

ConceptualAre dictionaries ordered?

Yes — insertion-ordered, a language guarantee since 3.7 (a CPython 3.6 implementation detail first).

Two precisions: insertion order is not sorted order (sorted(d) if you want that), and re-assigning an existing key keeps its original position — only delete-and-reinsert moves it.

OrderedDict is still occasionally right: it has move_to_end, and its equality is order-sensitive whereas plain dicts compare equal regardless of order.

Codingget vs setdefault vs defaultdict?

get reads with a fallback and doesn't modify the dict — the default choice. setdefault reads and inserts the default. defaultdict(factory) creates a fresh container on every miss — the grouping idiom.

The gotcha: a defaultdict creates entries on read, so merely checking dd[k] inserts k. Use k in dd to test, and consider converting to a plain dict before returning it so callers don't inherit the surprise.

CodingTop 10 items from a stream of a billion records.

A bounded min-heap of size 10: push the first 10, then compare each new item to heap[0] and heapreplace if larger. Memory O(k) regardless of stream length; time O(n log k).

Why not the alternatives: sorted(data)[-10:] needs everything in memory and is O(n log n). heapq.nlargest(10, stream) does exactly this internally, so mention it — but the manual version is what's being tested.

Follow-ups to pre-empt: top-k per group uses one small heap per group; if the data is already in a DB, ORDER BY … LIMIT beats anything in Python.

Very commonSort by one field ascending and another descending.

Two techniques. Negate the numeric key: key=lambda r: (r["team"], -r["score"]) — concise, numeric only. Exploit stability: sort by the least significant key first, then the most significant; because Timsort is stable the second sort preserves the first within ties, and this works for any key type.

In pandas: df.sort_values(["team","score"], ascending=[True, False]).

ConceptualWhat does “stable sort” mean and why care?

Equal elements keep their relative order. Python's sorted/list.sort use Timsort — stable, O(n log n) worst case, O(n) on nearly-sorted input.

It makes multi-pass sorting valid, and it means an existing meaningful order survives a later sort on a different key.

The trap: np.sort's default quicksort is not stable, and neither is df.sort_values's default. If you rely on tie order, pass kind="stable" explicitly.

CodingFlatten a list of lists.

[x for row in matrix for x in row] — clause order matches the nested loop you'd write, outer first, which is the bit people reverse.

Alternatives: list(itertools.chain.from_iterable(matrix)) (slightly faster, clearer), or np.concatenate/.ravel() for numeric data. Arbitrary nesting needs recursion with an isinstance check.

The anti-pattern: sum(matrix, []) works and is O(n²).

GotchaWhat's dangerous about zip?

It stops at the shortest iterable, silently. Zipping 1000 ids against 998 predictions gives 998 pairs and no error — you've dropped rows invisibly.

Fix: zip(a, b, strict=True) (3.10+) raises on a length mismatch — use it whenever the lengths should match. itertools.zip_longest when unequal lengths are legitimate.

The related lesson: this is why aligning on an index or joining on a key beats zipping positionally — positional alignment assumes an invariant nobody is checking.

11.3 Functions, decorators, generators

“What is a decorator?” is close to guaranteed, and the answer is to write one.

Drill
Very commonExplain *args and **kwargs.

In a definition they collect extra positional args into a tuple and extra keyword args into a dict. In a call they do the opposite — unpack a sequence into positional args and a mapping into keyword args.

That symmetry is what makes transparent wrappers possible: def wrapper(*a, **kw): return fn(*a, **kw) forwards any signature, which is the backbone of every decorator.

Ordering: positional-only /, positional-or-keyword, *args, keyword-only, **kwargs. A bare * starts keyword-only params without collecting.

PracticalWhy force keyword-only arguments?

Readable call sites and no positional mistakes. train(df, 0.2, 42, True) is unreadable and trivially mis-ordered; forcing names makes a reordering error impossible.

Second reason: API evolution — keyword-only params can be reordered or added without breaking callers, which is why pandas and scikit-learn have been converting to them.

Rule of thumb: flags and tuning parameters keyword-only; only the primary data argument stays positional.

Very commonWhat is a closure?

A function that keeps referring to variables from its defining scope after that scope exits. Python holds them in cells — visible as fn.__closure__, named in fn.__code__.co_freevars.

Two properties: it captures the variable, not the value (hence late binding), and each call to the factory produces independent cells.

Why it matters: closures are how decorators work, and how you build configured callables without a class.

Very commonWhat is a decorator? Write one.

A callable taking a function and returning a replacement. @deco is exactly f = deco(f).

The shape to write from memory: def timed(fn): → @functools.wraps(fn) → def wrapper(*args, **kwargs): → time it, call fn(*args, **kwargs) inside try with the reporting in finally → return wrapper.

Three details that separate a good answer: *args, **kwargs to wrap any signature, functools.wraps so metadata survives, and try/finally so the added behaviour happens even when the function raises. A decorator is just a closure over fn.

GotchaWhat does functools.wraps do, and what breaks without it?

Copies __name__, __doc__, __module__, __qualname__, __dict__ and __annotations__ onto the wrapper, and sets __wrapped__.

Without it every decorated function reports itself as wrapper with no docstring — breaking tracebacks and logs (every frame is “wrapper”), help() and generated docs, inspect.signature, and any framework dispatching on __name__ (pytest collection, Flask routes, Celery task names).

CodingWrite a decorator that takes an argument.

Three nested levels, because @deco(arg) calls deco(arg) and applies the result. Outer takes the config, middle takes the function, inner takes the call.

The mistake to flag: forgetting the parentheses. @retry on a parameterised decorator passes the function as the config, producing a bizarre error later. The fn=None plus functools.partial pattern makes a decorator work both with and without parentheses.

GotchaWhy can't you lru_cache a function taking a DataFrame?

The cache keys on the arguments, so they must be hashable — DataFrames, arrays, lists and dicts aren't. You get TypeError: unhashable type.

Options: cache on a hashable identifier (a path, a query string, a version tag) and load inside; hash the content with pd.util.hash_pandas_object(df).sum(); or use an explicit dict cache.

The deeper caution: caching on mutable data is dangerous — the frame can change while the cache holds the old result. Cache the load, not the transform.

Codingcache vs lru_cache, and when is caching wrong?

@cache is @lru_cache(maxsize=None) — unbounded, slightly faster, grows forever. lru_cache(maxsize=n) evicts the least recently used.

Caching is wrong when the function has side effects, the underlying data changes (no invalidation hook), arguments are unhashable, the key space is unbounded and you used @cache (a memory leak with a friendly name), or the function is cheap enough that the lookup costs more.

Also: lru_cache on a method keys on self and keeps every instance alive — use cached_property instead.

Very commonIterable vs iterator?

An iterable has __iter__ and can produce an iterator; an iterator has __next__ and holds the position.

The consequence: a list is re-iterable — iter(lst) gives a fresh iterator each time. A generator is its own iterator, so once exhausted it yields nothing more, silently.

That's the bug being tested: sum(gen) then len(list(gen)) gives a correct sum and then zero, with no error.

Very commonWhat is a generator and why use one?

A function containing yield; calling it returns a generator that produces values lazily, pausing at each yield with its locals intact.

Give the reason as a number: [x*x for x in range(10_000_000)] materialises ten million ints — hundreds of MB; the generator expression holds one. Peak memory O(n) → O(1).

Plus: infinite streams, free early exit (any() stops at the first match), and composition into pipelines. Caveats: no speedup, and single-use.

Very commonHow do you process a 50 GB CSV on a 16 GB machine?

Stream and aggregate as you go. A file object is already a lazy line iterator; csv.DictReader(fh) is the same, parsed. Accumulate into a dict of running totals, so memory scales with the number of groups, not rows.

In pandas: read_csv(chunksize=500_000), aggregate per chunk (which keeps each chunk vectorised), combine at the end. Read only what you need with usecols= and declare dtype=.

The best answer: convert to Parquet and query with DuckDB or Polars, which stream larger-than-memory joins and aggregations natively. Recognising that the tool choice beats the technique is the senior move.

Very commonWhat is the with statement for?

Guaranteed setup and teardown. __enter__ on entry, __exit__ on exit — and __exit__ runs whether the block finished, returned early, or raised. It's try/finally with a reusable name.

To write one: @contextmanager, record state, yield inside a try, clean up in finally. Everything before the yield is __enter__; after is __exit__.

Detail: __exit__'s return value decides suppression — returning True swallows the exception, which you almost never want.

DesignA row in your input is malformed. What do you do?

It depends on the cost of being wrong — and saying so is the answer, because this is a judgement question.

Quarantine and continue for analytics: write bad rows to a dead-letter table with the index, raw text and parse error, process the rest, and alert on the bad rate. Fail the batch when partial results are dangerous — financial or regulatory output, where a silently-30%-short number is worse than a failed job.

What makes either safe is a threshold: tolerate up to X% bad rows, fail above it. Without one, an upstream schema change can drop 90% of your data and the pipeline reports success.

11.4 OOP & dataclasses

Fewer questions than a backend interview, and more practical: can you write a class that fits someone else's framework?

Drill
Very commonWhat's wrong with a mutable class attribute?

It's created once when the class body executes and shared by every instance, so self.items.append(x) mutates state visible to all of them. Structurally the same as the mutable default argument.

Fix: initialise in __init__, or field(default_factory=list) in a dataclass.

The refinement that shows understanding: an immutable class attribute is fine — self.total += 1 rebinds on the instance, silently creating an instance attribute and leaving the class value untouched. That asymmetry is why class-level constants are idiomatic and class-level lists are a bug.

Very commonstaticmethod vs classmethod vs instance method?

Instance takes self; classmethod takes cls; staticmethod takes neither and is just namespacing.

The killer use for classmethod is alternative constructors — Dataset.from_csv. Because it calls cls(...) rather than a hardcoded name, it returns the correct subclass when inherited, which a staticmethod cannot. Real examples: dict.fromkeys, datetime.fromisoformat, pd.DataFrame.from_records.

Very common__repr__ vs __str__?

__repr__ is for developers — unambiguous, ideally reconstructible, and what the REPL, debuggers and containers use (printing a list calls repr on each element). __str__ is for users.

Rule: always implement __repr__; add __str__ only if the human form differs. str() falls back to __repr__.

Why it earns its keep: the default <Foo object at 0x…> is useless in a log or a pytest failure. Five lines saves hours.

GotchaYou defined __eq__ and now the object won't go in a set.

Defining __eq__ sets __hash__ = None, making the class unhashable. That's deliberate — equal objects must hash equally, and Python can't infer a correct hash from your equality logic, so rather than let you violate the contract it removes hashing.

Fix: define __hash__ over the same fields — hash((self.a, self.b)) — and only if those fields are effectively immutable.

Which is exactly why @dataclass(frozen=True) generates both and plain @dataclass generates only __eq__.

Very commonWhat does @dataclass give you?

Generated __init__, __repr__ and __eq__ from the annotations.

Then the options: frozen=True (immutable + hashable), slots=True (drops the per-instance dict — real memory win at scale), kw_only=True (forces named args), field(default_factory=...) for mutable defaults — and dataclasses refuse a bare mutable default, which is the language preventing the §1.5 bug. __post_init__ for validation.

What it isn't: a runtime type validator (see below), or a substitute for a class with real behaviour.

GotchaDoes a dataclass validate types?

No. @dataclass class C: x: int accepts C("hello") happily — annotations generate methods, they don't enforce anything.

For enforcement: Pydantic (reads the same annotations and validates/coerces on construction), checks in __post_init__, or a static type checker in CI.

The division: dataclass for internal objects you construct, Pydantic at boundaries where data comes from JSON, a request, or a config file.

Designdataclass vs NamedTuple vs TypedDict vs Pydantic?

dataclass — the default for internal records and configs; mutable by choice, supports methods.

NamedTuple — immutable and tuple-compatible: unpackable, sortable, indexable, cheap. Good for coordinates and small fixed records.

TypedDict — when the data is already a dict (parsed JSON) and you want annotations without changing the runtime type.

Pydantic — at boundaries, because it's the only one that validates at runtime.

One line: dataclass inside, Pydantic at the edges, NamedTuple when it should act like a tuple, TypedDict when it must stay a dict.

Deep diveWhat is the MRO and what does super() do?

The Method Resolution Order — the linearised search sequence computed by C3 linearisation: each class appears once, subclasses precede bases, declared order respected.

The correction that scores: super() does not mean “my parent” — it means “the next class in the MRO of type(self)”. So in a diamond, a single super().__init__() chain visits every class exactly once, which is why the shared base isn't initialised twice.

Corollary: every class in such a hierarchy must call super() and accept compatible arguments, or the chain breaks silently.

DesignInheritance or composition?

Composition by default. Inheritance couples you to a base class's internals and the coupling compounds; composition means holding a collaborator you can swap and test in isolation.

Use inheritance when there's a genuine is-a relationship and you need polymorphism — a framework requires subclassing, or you're providing interchangeable implementations of one interface.

The test: do you want the base class's interface, or just its code? Wanting the code is the wrong reason. In data pipelines composition wins almost always.

CodingWrite a custom scikit-learn transformer.

Inherit BaseEstimator (gives get_params/set_params) and TransformerMixin (gives fit_transform).

Contract: __init__ stores parameters only, with attribute names matching argument names exactly; fit learns, stores state in trailing-underscore attributes, returns self; transform uses only that fitted state and doesn't mutate the input.

The two mistakes that actually happen: computation or validation in __init__ (breaks clone, therefore GridSearchCV), and computing statistics inside transform — which leaks test information.

GotchaYour transformer works alone but fails in GridSearchCV.

A clone problem. GridSearchCV clones per fold and per parameter set, and clone calls get_params() then passes the result to __init__.

So it breaks if __init__ renames or transforms an argument before storing it, computes something the clone then lacks, uses *args/**kwargs (nothing to introspect), or you stored fitted state without a trailing underscore.

Diagnose by calling sklearn.base.clone(est) yourself. Better: run sklearn.utils.estimator_checks.check_estimator, which tests the whole contract.

11.5 NumPy

NumPy questions are a proxy for whether you understand memory.

Drill
Very commonAdvantages of NumPy arrays over lists?

No boxing — raw values instead of pointers to int objects, so ~4–5× less memory. One dtype — no per-element type dispatch, so the loop runs in compiled C. Contiguous memory — prefetching and SIMD work.

Net: typically 10–100× faster for elementwise numeric work, plus broadcasting, slicing and linear algebra.

Cost to acknowledge: arrays are homogeneous and fixed-size, so appending is expensive (np.append reallocates every time — building one in a loop is O(n²)) and mixed types force an upcast.

Deep diveWhat are strides and why do they matter?

The number of bytes to step per axis — (32, 8) for a C-ordered int64 (3,4) array.

They matter because shape + strides is how NumPy maps an n-D index onto a flat buffer, which makes reshape, transpose and basic slicing O(1) metadata changes over the same memory.

Two consequences: it explains views vs copies (a view is possible only when the selection is a regular strided pattern), and it explains performance — iterating along the contiguous axis is cache-friendly, across it is not.

Very commonWhen does NumPy return a view vs a copy?

View: basic slicing (a[2:6], a[::2]), compatible reshape, transpose, .view(). Copy: fancy indexing, boolean masking, arithmetic, .copy(), reshaping a non-contiguous array.

Why: a view is just metadata, so it's only possible for a regular strided pattern — fancy indexing picks arbitrary positions no stride can describe.

It matters because a view writes through to the parent. Check rather than assume: arr.base is not None, np.shares_memory(a, b).

Very commonExplain broadcasting.

Elementwise operations on different-shaped arrays without loops or copies. Three rules: right-align the shapes; missing leading dims count as 1; each dim must be equal or 1, and a 1 is stretched.

The mechanism: a stretched dim is implemented with stride 0, re-reading the same memory — so it costs nothing for the operands, though the result is full size, which is the memory trap on large data.

Canonical use: (X - X.mean(axis=0)) / X.std(axis=0). The fix for a failure is almost always [:, None].

Debug“could not be broadcast together with shapes (1000,) (1000,1)”

Right-align: (1, 1000) vs (1000, 1). Both dims are 1-or-equal, so it succeeds — and produces a 1000×1000 array, which is usually not what you wanted and may exhaust memory.

That's the dangerous version: broadcasting silently giving an outer product where you expected elementwise. Usual cause is a stray (n,1) from a sklearn predict, a reshape(-1,1), or double-bracket column selection.

Fix: .ravel()/.squeeze(), and assert shapes at function boundaries.

Very commonWhat does axis=0 mean?

The axis you name is the one that disappears. On a (3,4) array, sum(axis=0) collapses the 3 rows → 4 values (one per column); sum(axis=1) → 3 values.

That phrasing works in any dimensionality and avoids the “is axis 0 rows or columns” muddle — which exists because axis=0 is described as “rows” but produces a result per column.

Same in pandas. The confusing exception is df.drop(..., axis=1), where axis names what you're addressing — which is why df.drop(columns=[...]) is preferred.

Very commonWhat is vectorisation and why is it faster?

Operations on whole arrays rather than element-by-element in Python. Three reasons, better than “it's in C”: no interpreter overhead per element; SIMD on contiguous data; cache efficiency versus chasing pointers to scattered objects.

Typically 10–100×, and more for anything reducible to matrix multiplication because it lands in a tuned BLAS kernel.

Caveat worth adding: vectorisation often trades memory for speed — a broadcast intermediate can exceed both inputs, so sometimes the fastest formulation is the one that avoids materialising it.

CodingVectorise pairwise Euclidean distances.

Broadcasting: diff = A[:, None, :] - B[None, :, :] then np.sqrt((diff**2).sum(axis=-1)).

Better for large n: use |a−b|² = |a|² + |b|² − 2a·b, so a2[:,None] + b2[None,:] - 2 * A @ B.T. This never materialises the (n,m,d) intermediate and pushes the work into BLAS.

Two details that show care: clip with np.maximum(d2, 0) before the sqrt (floating-point can give tiny negatives), and mention that in practice you'd call scipy.spatial.distance.cdist or sklearn.metrics.pairwise_distances.

GotchaIs np.vectorize a way to vectorise code?

No — the docs say so explicitly. It provides broadcasting semantics for a scalar function but loops in Python internally, so it's essentially as slow as the loop you started with.

What actually vectorises: array expressions, np.where/np.select for conditionals, boolean masks, np.digitize/searchsorted for binning, existing ufuncs.

For an irreducible scalar loop, the real answers are Numba or Cython. Citing np.vectorize as a performance tool is a reliable tell.

GotchaYour sum of a downcast column is negative.

Integer overflow. NumPy integers are fixed-width and wrap silently. Individual values fit in int16 but the aggregate exceeds 32,767 and wraps.

Fix: arr.sum(dtype=np.int64), or promote before summing. Before downcasting, check the range against np.iinfo(dtype).max with headroom.

General lesson: downcast storage, compute in a wider type.

Very commonWhy is 0.1 + 0.2 != 0.3?

Binary floating point can't represent those decimals exactly, and the rounding errors don't cancel — the result is 0.30000000000000004.

Fixes: never test float equality — math.isclose, np.isclose/allclose, pd.testing.assert_frame_equal with rtol. For money, Decimal or integer minor units.

The deeper issue: float addition is not associative, so summation order changes the result — which is why parallel sums can differ and why np.sum uses pairwise summation.

GotchaHow do you count and handle NaN correctly?

Count: np.isnan(a).sum() or df.isna().sum(). Never a == np.nan — NaN isn't equal to itself.

Aggregate: NumPy's sum/mean/max propagate NaN; use np.nansum etc. to skip. Note pandas does the opposite by default (skipna=True) — a genuine inconsistency worth flagging.

Two more: np.sort places NaN last, so a “max” from a sorted array may be NaN; and NaN only exists in float dtypes, so an int column with gaps upcasts to float — or uses nullable Int64 with pd.NA.

11.6 pandas core

If an interview touches one library, it's this one. §11.6 and §11.7 carry the most weight in the whole bank.

Drill
Very commonWhat is a DataFrame, really?

A dict of Series sharing one index. Each column is a separate typed contiguous buffer; the index is a shared label array everything aligns to.

Two consequences: storage is column-oriented, so whole-column arithmetic is one C loop and fast, while iterating rows touches every buffer and builds a Series per row. And the index is meaningful, so operations align on it automatically — the source of both pandas' power and its most confusing behaviour.

The habit: think in columns, not rows.

Very common.loc vs .iloc?

Label vs integer position. They coincide only on a default RangeIndex, which is why the difference is invisible until it bites.

The detail that scores: .loc slices are inclusive of the endpoint, .iloc are not — with arbitrary labels there's no “next” label to stop before.

Then why to avoid bare df[...]: it's overloaded — df['v'] takes a column, df[0:2] takes rows, df[mask] takes rows. Same syntax, different axis, decided by the argument type.

CodingHow do you conditionally update a column?

df.loc[mask, "col"] = value — one .loc call handling both row selection and column, so pandas knows unambiguously you're assigning into the frame.

Not df[mask]["col"] = value: that's chained assignment, two separate indexing operations, and under pandas 3.0 it silently does nothing.

Alternatives: np.where(cond, a, b), df["col"].mask(cond, value), or df.assign(...) to stay in a chain.

ModernWhat is SettingWithCopyWarning and how do you fix it?

Lead with the currency: in pandas 3.0 it no longer exists. Copy-on-Write became the only mode in January 2026, and because indexing results are unambiguously copies, the warning had nothing to warn about and was removed.

What it was: pandas couldn't tell whether df["a"][mask] = x would modify the original or a temporary, because df["a"] might return a view or a copy depending on dtypes and block layout.

What happens now: chained assignment reliably does nothing — silent, but consistent. The fix was always the same: one .loc call.

ModernWhat is Copy-on-Write — faster or slower?

Faster, which surprises people. Every indexing result behaves as an independent copy, but pandas defers the actual duplication until a write happens — so reads share memory.

The win: pandas can drop defensive copies it previously made, and you can drop the .copy() calls that were idiomatic after every filter. Those now force an eager copy CoW would have avoided, so deleting them is a real memory improvement on upgrade.

The behavioural change: mutating a slice can no longer reach into the parent — so code that relied on that silently stops working, which is the main upgrade risk.

ModernWhat changed about dtypes in pandas 3.0?

Strings get a dedicated str dtype by default (PyArrow-backed when available), instead of object.

The breaking part: code checking df.dtypes == "object" or select_dtypes("object") to find string columns now misses them — and that pattern is extremely common in feature-engineering code.

Also: datetimes default to microseconds not nanoseconds, removing the 1678–2262 range limit; CoW is the only mode; and everything deprecated in 2.x was removed. Upgrade path: 2.3 → clear all warnings → 3.0.

GotchaWhy did your integer column become float?

It contains missing values, and NumPy-backed int64 has no NaN representation, so pandas upcasts to float64. Symptoms: ids printing as 12345.0, and past 2⁵³ actual precision loss.

Fix: the nullable Int64 dtype (capital I), which stores an integer array plus a mask and uses pd.NA. Or declare dtypes at read time.

Same for booleans (→ object; nullable equivalent is "boolean"). This is the most common cause of “my join key stopped matching”.

PracticalWhen would you use the category dtype?

For low-cardinality columns — a few hundred distinct values or fewer over many rows. Stores distinct values once plus small integer codes, so a country column over ten million rows goes from hundreds of MB to a few. Also speeds up groupby and merges on that column, and supports declared ordering.

Gotchas: appending an unseen value gives NaN; groupby includes unobserved combinations by default (use observed=True); and for a high-cardinality column like a user id it's worse than a plain string.

Very commonHow do you handle missing values?

Start with why they're missing: completely at random, at random given other features, or not at random — where the missingness itself carries signal.

Then: drop rows only if few and plausibly random (quantify the loss); drop the column if mostly empty; impute — median for skewed numerics, mode or an explicit "UNKNOWN" for categoricals, forward-fill for time series, model-based when structured.

Two points that make it senior: add a missingness indicator, because for MNAR data that flag is often more predictive than the imputed value; and fit the imputer on train only, inside a Pipeline.

PracticalWhat do you always pass to read_csv?

dtype= above all — without it pandas infers per column and turns zip codes, phone numbers and padded ids into integers, silently losing leading zeros. usecols= to read only what you need. parse_dates=. na_values= because real files use "NULL", "N/A", "-". chunksize= when large.

Then the judgement: prefer Parquet. CSV has no schema so every read re-guesses; Parquet is columnar, compressed, stores dtypes, and supports column/predicate pushdown. Convert once at ingestion.

DebugYour join key stopped matching after a CSV round-trip.

A dtype mismatch introduced by the read. Usual suspects: one side int64, the other float64 (a missing value forced an upcast), so 1 never matches 1.0; a numeric-looking id read as int on one side and str on the other; leading zeros stripped from one file only.

Diagnose: compare dtypes, and inspect keys with repr() to reveal whitespace and quotes.

Prevent: declare key dtypes explicitly (ids as str unless you do arithmetic), strip whitespace, assert the row count after the merge.

DesignWhy prefer method chaining?

No mutation (no aliasing question, no defensive .copy()), no temporary names (where stale-intermediate bugs live, especially in notebooks), reads as the transformation it is, and composable via .pipe().

Use lambda inside .assign()/.query() so each step refers to the frame at that point.

Honest limits: hard to debug because there's no intermediate to inspect, and query uses strings no linter checks.

GotchaDoes inplace=True save memory?

Generally no — a persistent myth. Most inplace operations still build a new object internally and rebind, so peak memory is similar. It saves a variable name, not memory, and under CoW it's even less meaningful.

Arguments against: it returns None so it breaks chaining; it mutates a frame others may hold a reference to; and it makes code harder to reason about.

Real memory levers: dtypes, usecols, chunking, dropping columns early.

11.7 pandas transformation

The part that mirrors the actual job. Three answers here carry outsized weight: agg/transform/apply, join validation, and leakage-free windows.

Drill
Very commonExplain groupby.

Split-apply-combine: split rows into groups by key, apply a function to each, combine into a new object with the keys as index.

Add that groupby itself is lazy — it returns a GroupBy object having done almost no work; nothing computes until agg, transform, apply or a direct method.

Then the practical shape: prefer named aggregation — .agg(total=("rev","sum"), n=("rev","size")) — for flat readable column names instead of a MultiIndex to flatten.

Very commonagg vs transform vs apply?

Shape decides. agg reduces each group to a scalar (one row per group). transform returns a value per input row, broadcasting the group result back. apply gets the whole sub-frame and can return anything.

Rule: use transform to add a group statistic as a column — df["m"] = df.groupby("g")["v"].transform("mean") — because it aligns automatically. agg for summary tables. apply only when you need multiple columns of the group at once.

Performance: agg/transform with a named string function dispatch to Cython; apply and lambdas run Python per group — typically 5–30× slower.

CodingAdd each row's percentage of its group total.

df["pct"] = df["val"] / df.groupby("grp")["val"].transform("sum").

Why the alternatives are worse: with agg you'd get a small result you must merge back — more code, an extra join, a chance of misalignment. With apply you'd run Python per group for no benefit.

Same pattern covers most within-group feature engineering: rank, deviation from group mean, share of group, group z-score, group-wise fill.

GotchaYour group totals don't add up to the overall total.

groupby drops rows with a missing key by default (dropna=True). Rows whose grouping column is NaN vanish, with no warning.

Fixes: dropna=False for an explicit NaN group, or fillna("UNKNOWN") on the key first so the missing category is visible and reportable.

The general habit: after any aggregation, assert the total is conserved. Silent row loss is the most dangerous class of pandas bug because the output still looks plausible.

GotchaYou grouped by a categorical and got far more rows than groups.

observed=False emits a row for every declared category, not just those present — and with several categorical keys that's the full cross-product of all levels, potentially thousands of empty rows.

Pass observed=True. The behaviour has a legitimate use — guaranteeing a complete grid for a report — but it should be deliberate.

Codingcount vs size vs nunique?

size = all rows including nulls, one Series. count = non-null values, per column. nunique = distinct values.

“How many orders” is size; “how many had a discount recorded” is count; “how many distinct products” is nunique. Using count where you meant size silently under-reports whenever nulls exist.

Very commonmerge vs join vs concat?

merge — SQL-style join on columns or index, with how. The general tool. join — convenience, merges on the index by default, and note its default is left unlike merge's inner. concat — doesn't join, it stacks: axis=0 appends rows aligning columns by name, axis=1 appends columns aligning rows by index.

Rule: matching on keys → merge; stacking like-shaped pieces → concat.

PracticalHow do you verify a join did what you intended?

1. validate= — declare the expected cardinality ("many_to_one" etc.) and pandas raises if violated. The highest-value argument in merge and almost nobody uses it.

2. Assert the row count — for a left enrichment join, assert len(out) == len(left).

3. indicator=True then _merge.value_counts() — an unexpectedly large left_only usually means a dtype mismatch or whitespace in the keys.

4. Check null rates on the newly-added columns.

DebugRow count went 1M → 4M after a join.

Many-to-many. The key is duplicated on one or both sides, so you get the cross-product per key. Every downstream sum is now wrong, and nothing raised.

Diagnose: right["key"].is_unique, or duplicated().sum().

Fix by intent: if the duplicates are data-quality noise, drop_duplicates(subset="key") — but decide which row wins, with a sort, rather than taking an arbitrary one. If multiple rows per key are legitimate, aggregate the right side first.

Prevent: validate="many_to_one" plus a row-count assertion on every enrichment join.

DesignJoin a fact table to a slowly-changing dimension without leaking.

pd.merge_asof with direction="backward" — for each fact row take the most recent dimension record at or before its timestamp. A point-in-time join.

Details: both frames must be sorted on the key or the result is silently wrong; by= matches within an entity; tolerance= turns an unreasonably stale match into NaN.

Why it's the right answer: a plain merge gives every fact row the current value, encoding information from after the event — the model looks excellent in backtest and fails in production.

Very commonpivot vs pivot_table?

pivot is a pure reshape requiring unique index/column pairs, and raises otherwise. pivot_table aggregates duplicates via aggfunc (mean by default).

The implication: pivot's error is useful information — your data has more than one record per cell. Reaching straight for pivot_table silently averages them and may hide a duplicate-record bug.

So use pivot when the data should be unique, precisely so it fails loudly. Pass aggfunc explicitly when you do aggregate.

DesignHow do you build a rolling feature without leakage?

.shift(1) before .rolling(). Default rolling(3) includes the current row, so a “past 3 days average” contains today's value — and if you're predicting today, the feature contains the target.

For panel data: sort by entity and time, group by entity, then shift, then roll. Rolling across the whole frame bleeds one entity's history into another's features.

And use rolling("3D") rather than rolling(3) when the series has gaps, so the window is three days not three rows.

Codingrolling vs expanding vs ewm?

rolling(n) — fixed window, older data drops out. expanding() — everything from the start, growing. ewm() — all history with geometrically decaying weight, smoother because there's no abrupt drop-out.

All take min_periods, which controls the warm-up. Whether min_periods=1 is right depends on whether a partial window is meaningful — accepting the default silently is how you get a model that can't score the first rows of every new entity.

CodingTranslate ROW_NUMBER() OVER (PARTITION BY g ORDER BY t).

df.sort_values(["g","t"]).groupby("g").cumcount() + 1, or df.groupby("g")["t"].rank(method="first").astype(int).

The tie semantics are usually the real point: method="first" ≈ ROW_NUMBER, "min" ≈ RANK, "dense" ≈ DENSE_RANK.

General mapping: SQL window functions ↔ groupby().transform(), shift(), rank(), cumsum() — the ones that preserve row count.

DesignWould you do this in SQL or pandas?

SQL wherever the data lives in a database — push filtering, joining and aggregation to the engine so you move less data and use its indexes. Pulling a hundred million rows into pandas to group them is the classic mistake.

pandas for exploratory and iterative work, complex reshaping, anything feeding scikit-learn, and custom Python logic.

The 2026 answer that shows range: DuckDB runs SQL directly against a DataFrame or Parquet file, out-of-core and multi-threaded, so it isn't binary — and Polars gives a lazy optimised DataFrame API. Say you'd benchmark rather than assume.

11.8 Performance & concurrency

Diagnosis questions dressed as optimisation questions. Profile first; the GIL answer changed in 2026.

Drill
Very commonHow would you speed up a slow pandas operation?

Measure, then climb the ladder: iterrows → itertuples → apply → vectorised pandas → NumPy. Each step is roughly an order of magnitude, and the big cliff is between apply and vectorised because everything above it is a Python loop.

Concretely: column arithmetic instead of row iteration; np.where/np.select for conditionals; .map(dict) for lookups; merge for joins; .str/.dt accessors.

Other levers: fix dtypes (an object column defeats vectorisation), reduce memory so you stop swapping, use agg("sum") not apply, and if it genuinely can't vectorise reach for Numba, Polars or DuckDB.

GotchaIs df.apply vectorised?

No. It calls your Python function once per row (axis=1) or column, and with axis=1 it constructs a Series per row — which is why it's barely faster than iterrows.

Instead: arithmetic → column expressions; conditionals → np.where/np.select; binning → pd.cut; lookups → .map; joins → merge; strings → .str; dates → .dt.

When it's fine: small data where clarity wins, or logic that truly can't be array-expressed — and then say what you'd do if it were the bottleneck.

DebugA pipeline went from 5 minutes to 3 hours.

Establish what changed first — code, data volume, or dependency versions.

Then measure: time it at two input sizes (4× per doubling means quadratic, so hunt a linear op inside a loop); cProfile for the function; line_profiler for the line; and check memory, because a 3-hour runtime with swapping is a memory problem wearing a CPU costume.

Usual culprits: a frame grown row by row, an apply where vectorised exists, an exploded join, x in list in a loop, or a dtype regression to object.

Very commonYour DataFrame doesn't fit in memory.

Read less, store it smaller, or don't hold it all — in that order.

Read less: usecols= and dtype= at read time — often solves it alone on a wide file. Smaller: downcast numerics, category for low-cardinality strings, drop columns early — 50–90% reductions are routine. Don't hold it: chunksize= and aggregate per chunk; or Parquet + DuckDB/Polars for native out-of-core.

Caveat: downcasting narrows the range, so aggregate with a wider accumulator or you get silent overflow.

GotchaWhy does memory_usage() undercount?

By default it counts only the NumPy buffer, not the Python objects it points to. For an object string column the buffer is just 8-byte pointers while the strings live elsewhere — the gap can be an order of magnitude.

Pass deep=True, or use df.info(memory_usage="deep").

Related: pandas 3.0's PyArrow-backed str dtype stores strings compactly, so the gap is much smaller than it used to be — a practical win of upgrading.

CodingCompute a group mean over a file that doesn't fit in memory.

Accumulate sum and count per group across chunks, then divide once at the end.

The mistake to name: averaging the per-chunk means is wrong unless every chunk has the same number of rows in every group. Mean isn't associative under unequal weights; sum and count are.

Extends to variance (from sum, sum-of-squares and count, or Welford's algorithm for stability). And mention the better tool: duckdb.sql("SELECT key, avg(v) FROM 'f.parquet' GROUP BY 1").

ConceptualWhich statistics can't be computed in one chunked pass?

Anything needing global order or the full distribution: exact median and quantiles, a full sort, exact distinct counts at high cardinality.

Workarounds: two passes; approximate algorithms — t-digest or reservoir sampling for quantiles, HyperLogLog for cardinality; external sort; or push it to a query engine.

The nice exception: mean and variance are single-pass via Welford's algorithm, which is also more numerically stable than accumulating raw sums of squares.

Very commonWhat is the GIL?

A mutex in CPython allowing only one thread to execute Python bytecode at a time. Its purpose is memory management — making reference counting safe without fine-grained locking, which also keeps single-threaded Python fast.

So threads don't speed up CPU-bound pure-Python code. But the nuance that scores is what it doesn't block: it's released during I/O and compiled extension work, so threads help a lot for network and disk, and NumPy, pandas and BLAS already parallelise because they drop it.

For data work the GIL is much less of a constraint than its reputation suggests — the expensive parts were never running under it.

ModernWhat changed with free-threaded Python?

PEP 779: as of Python 3.14 the free-threaded build is officially supported — moved from experimental to supported. It's a separate build compiled without the GIL; the default interpreter still has one.

What it enables: real multi-core parallelism for CPU-bound pure-Python code using threads, without multiprocessing's pickling and memory duplication.

The honest caveats: single-threaded performance is somewhat slower; C extensions must be explicitly compatible and the ecosystem is still catching up (NumPy 2.5 improved its support); and you now have to think about data races the GIL used to paper over.

Position for 2026: promising, worth tracking, but vectorised C code, multiprocessing and joblib still cover most data work.

Very commonThreads, processes or async?

Choose by workload. I/O-bound, tens to hundreds of operations → ThreadPoolExecutor. I/O-bound at very high concurrency → asyncio, because a coroutine is far cheaper than a thread — but only if the whole path is async. CPU-bound pure Python → processes.

CPU-bound numeric → none of them: vectorise. NumPy and BLAS already thread internally, so wrapping them in processes oversubscribes the cores and often gets slower; set OMP_NUM_THREADS=1 in workers if you do parallelise.

GotchaWhat goes wrong with multiprocessing in data code?

Pickling and memory. Everything crossing the boundary must be picklable, so lambdas, closures and local functions fail. And a large DataFrame passed as an argument is serialised and copied into every worker — eight workers, eight copies — which frequently makes the parallel version slower.

Platform difference: fork shares memory copy-on-write but is unsafe with threads; spawn re-imports your module in each child, so module-level code runs again and you need the if __name__ == "__main__" guard.

Mitigations: pass paths or ranges and let workers load their own slice; use joblib, which memory-maps large arrays; and measure, because parallelism has real fixed costs.

ModernWould you use Polars instead of pandas?

For new performance-sensitive pipeline work, seriously consider it. Rust-based, multi-threaded by default, Arrow-backed, with a lazy API and a query optimiser that does predicate/projection pushdown and streams larger-than-memory data.

Where pandas wins: ecosystem (scikit-learn, plotting, tutorials all assume it) and team familiarity. Rewriting a working pipeline for speed alone rarely justifies the risk.

Pragmatic position: they interoperate cheaply via Arrow, so use Polars or DuckDB for the heavy load-and-aggregate and hand a pandas frame to the modelling code.

11.9 Production, testing & leakage

At four years' experience this section decides your level. Most candidates have no testing answer at all.

Drill
Very commonWhat is data leakage and how do you prevent it?

Any information in your features that wouldn't be available at prediction time. The model learns it, scores brilliantly in validation, fails in production — and the code runs perfectly, which is why it survives.

Flavours: preprocessing (scaler/imputer fitted before the split), feature selection using all the labels, target (a feature derived from the outcome), temporal (random split on time-ordered data, unshifted rolling features), group (same customer in train and test), duplicate rows split across both.

Prevention: all preprocessing and selection inside a Pipeline so it refits per fold; the right splitter (TimeSeriesSplit, GroupKFold); deduplicate before splitting; and audit every feature with “would I have this at prediction time?”

Detection: an implausible score, one feature dominating importances, and a shuffled-label run that should score at chance.

Debug0.99 AUC in CV, 0.6 in production.

Assume leakage first — a gap that size is almost never distribution shift alone.

Check: feature importances (one feature dominating is the target-leakage signature); split strategy (time-ordered data split randomly? same entity both sides? duplicates removed before splitting?); preprocessing order (anything fitted outside the pipeline on the full data?); feature timestamps (is each value knowable at prediction time?).

Then the confirming test: shuffle the labels and re-run. Above chance means information is reaching the model through an unaccounted channel.

Rule out the alternatives too: train/serve skew, genuine population shift, or a label definition that differs from reality.

Very commonWhy use a scikit-learn Pipeline?

It makes leakage structurally impossible. Every transformer's fit is called only on the training portion, so under cross-validation the imputer's median and the scaler's mean are recomputed inside each fold.

Plus: one object to serialise, so fitted preprocessing travels with the model and training/inference can't drift; hyperparameter search across the whole pipeline via "pre__num__impute__strategy"; and column-aware preprocessing with ColumnTransformer.

The production detail: OneHotEncoder(handle_unknown="ignore"), so an unseen category doesn't crash at inference.

DesignHow do you split time-series data?

Chronologically, never randomly. A random split lets the model train on next month to predict last month — a task it will never face. Use TimeSeriesSplit, where validation always follows training.

Two more requirements: a gap between train and validation if features use a lookback or the label has a horizon; and features shifted so each row uses only prior information.

If the data is both temporal and grouped you need both constraints — and evaluate on the most recent holdout, as the closest analogue to production.

Very commonHow do you test a data pipeline?

Test the transformations, not the data. Each should be a pure function frame-in/frame-out, testable with a five-row fixture and a known answer.

Four layers: unit tests per transformation; edge cases — empty frame, all-NaN column, single row, duplicate keys, unseen category, NaN group key (this is where the value is); invariants — row count preserved, totals conserved, ids unique; and an integration test on a small golden input.

Mechanics: pd.testing.assert_frame_equal with rtol rather than ==; @pytest.mark.parametrize for the edge-case matrix; fixed seeds.

And the cultural half: every production bug becomes a test before it's fixed.

PracticalHow do you test something non-deterministic, like a model?

Separate the deterministic parts — feature transformations, split logic, output schema — and test those normally.

For the model, assert properties and bounds, not exact numbers: it runs end to end; output shape and dtypes are right; probabilities in [0,1]; holdout performance above a threshold; and a shuffled-label run performs no better than chance, which is a genuinely good leakage test.

Then fix every seed, pin versions, and use golden files with a tolerance so unintended behaviour changes are caught even when you can't specify the right answer in advance.

DesignWhere and how do you validate incoming data?

At the boundary — right after reading, before any transformation — so a schema change fails with “column region missing, got […]” instead of a KeyError forty lines in.

Check: required columns, dtypes, nulls where disallowed, key uniqueness, value ranges, and row count in a plausible band — a 90% volume drop is a failure even if every row is individually valid.

Tools: pandera for dataframe schemas, Pydantic for records. And report all problems at once, so one run tells the caller everything to fix.

PracticalHow do you make an environment reproducible?

A lockfile, committed. Loose intent in pyproject.toml, exact pins for every direct and transitive dependency in a lock (uv lock, poetry lock, pip-compile).

Why transitive matters: you pin pandas, pandas depends on numpy, and a numpy patch release can change a numeric result. A loose requirements.txt reproduces nothing.

Beyond packages: pin the interpreter, use a container for system libraries, and record versions plus a data hash in the run artefacts.

PracticalHow do you make an ML experiment reproducible?

Four things, and seeds are only the first. Seeds: Python's random, an explicit NumPy default_rng passed around, PYTHONHASHSEED, and random_state= on every sklearn object. Pinned environment. Data versioning — a content hash or immutable snapshot, since “I got a different number” is often a changed input. A run record — seed, versions, data hash, params, git commit.

Then the honesty: seeds cannot control thread count (parallel float summation order), GPU reductions, or anything reading the clock. Bit-exact reproducibility is sometimes unattainable — so define what tolerance counts as “reproduced”.

PracticalHow do you move a notebook into production?

Extract pure functions into a module, then import them back into the notebook — the notebook keeps the charts and still works.

Steps: get “Restart and Run All” passing first; pull each transformation into a function taking a frame and returning a frame, no globals, no mutation; parameterise hard-coded paths, dates and thresholds into a config; add a thin entrypoint; write tests; pin the environment.

The design point: any statistic the transformation needs — a median, a category list — should be a parameter, not computed inside. That's what lets one function serve training and inference.

PracticalWhy logging instead of print?

Levels, routing and structure. Levels let you change verbosity at runtime; handlers route to a file or aggregator without touching call sites; records carry timestamp, module and level so you can filter and alert.

Mechanics: lazy formatting — log.info("n=%d", n) not an f-string — so the message is only built if enabled; and getLogger(__name__) so the name reflects the module.

In a pipeline, log what you'll want at 3 a.m.: row counts in and out per stage, fraction dropped, the config in use, timings.

PracticalWhat do you look for reviewing data code?

Correctness first, especially the silent failures. Leakage; joins without validate= or a row-count assertion; groupby dropping NaN keys; rolling features without a shift. All produce plausible wrong numbers rather than errors.

Then silent failure generally (except: pass, unlogged filters, fillna(0) where zero is meaningful, chained assignment that now no-ops), dtypes, reproducibility, and only then performance.

What I want to see: small pure functions, statistics passed as parameters, row counts logged per stage, tests for the empty frame and duplicate key. And I'd ask “how do you know?” about any correctness claim.

11.10 The trap questions ⭐⭐

Python screens are lost on a small number of confidently-wrong answers. Each of these has an obvious answer that is wrong, and a correct answer that sounds less impressive.

Traps — the answer that sounds good and isn't
Trap 1“So apply is the vectorised way to do it?”

Trap: agreeing. Correct: apply is a Python loop. It calls your function once per row, and with axis=1 it builds a Series per row, making it barely faster than iterrows.

The vectorised alternatives are np.where, np.select, pd.cut, .map, .str, .dt and plain column arithmetic — typically 50–100× faster for the same result.

Trap 2“The GIL means Python can't do parallelism.”

Trap: agreeing, or reciting it as a blanket limitation. Correct: the GIL is released during I/O and compiled extension work, so threads already parallelise network and disk operations, and NumPy, pandas, scikit-learn and BLAS already use multiple cores.

It only ever limited CPU-bound pure-Python code — which is rare in data work because the heavy lifting is in C. And as of Python 3.14, PEP 779 makes free-threaded builds officially supported, so even that limit is being lifted.

Trap 3“Use inplace=True to save memory.”

Trap: repeating it. Correct: most inplace operations still build a new object internally and rebind, so peak memory is similar. It saves a variable name, not memory — and it returns None, which breaks chaining, and mutates a frame others may reference.

The real memory levers are dtypes, usecols, category, chunking and dropping columns early. pandas has been steadily deprecating inplace.

Trap 4“Fix SettingWithCopyWarning by adding .copy().”

Trap: giving the 2019 answer. Correct: in pandas 3.0 the warning doesn't exist — Copy-on-Write removed the ambiguity it warned about, and chained assignment now reliably does nothing.

The fix was always one .loc call: df.loc[mask, "col"] = x. And under CoW the defensive .copy() after a filter is now redundant — it forces an eager copy that would otherwise never happen, so removing those is a memory win.

Trap 5“np.vectorize will speed this up.”

Trap: believing the name. Correct: the NumPy docs say explicitly that it's a convenience wrapper providing broadcasting semantics, not performance — it loops in Python.

Real options: express the logic as array operations, use np.where/np.select, or for a genuinely irreducible scalar loop use Numba's @njit.

Trap 6“I scaled the features, then split into train and test.”

Trap: not noticing. Correct: that's leakage — the scaler's mean and standard deviation were computed over the test set, so test information is baked into the transform the model trains on. Your validation score is optimistic.

Fix: split first, or put the scaler in a Pipeline so it refits inside every CV fold. The same applies to imputers, encoders and feature selectors.

How much does it matter? On pure random noise, feature selection outside the CV loop can lift apparent accuracy from 0.50 to 0.70 — entirely fabricated.

Trap 7“I used a random 80/20 split.” (on time-series data)

Trap: treating it as the default. Correct: on time-ordered data a random split lets the model train on the future to predict the past, which is not the task. Use TimeSeriesSplit with a gap if your features have a lookback or your label has a horizon.

And the same reasoning for grouped data: if the same customer appears in train and test, the model memorises the customer rather than learning the pattern — use GroupKFold.

Trap 8“c = [1,2]; d = c; c += [3] — so d is [1,2].”

Trap: assuming += always rebinds. Correct: d is [1,2,3] — for a mutable target, += calls __iadd__ and mutates in place, so every alias sees it.

For an immutable target there's no in-place option, so it rebinds and the alias is unaffected. Same operator, opposite behaviour, decided by mutability — which is why arr += 1 and arr = arr + 1 differ in memory behaviour too.

Trap 9“a[:] gives me a safe copy.”

Trap: assuming it's deep. Correct: it's shallow — a new outer list holding references to the same inner objects. So nested[:] then copy[0].append(x) mutates the original's inner list.

list(a), a.copy(), dict(d), {**d} and copy.copy are all shallow too. Only copy.deepcopy is deep — and it's slow, so often the better answer is a comprehension copying exactly the level you need.

Trap 10“A left join can't change my row count.”

Trap: a very common and expensive assumption. Correct: a left join preserves row count only if the right side is unique on the key. If it isn't, each left row is duplicated once per matching right row — so 1M rows can become 4M, and every downstream sum is inflated.

Guard with validate="many_to_one" and assert len(out) == len(left). This produces plausible wrong numbers, not a crash, which is what makes it dangerous.

Trap 11“df.dtypes == 'object' finds my string columns.”

Trap: muscle memory from pandas 2.x. Correct: in pandas 3.0 strings are inferred as str dtype, not object — so that check, and select_dtypes("object"), silently miss them.

This is one of the main upgrade hazards, because the pattern is ubiquitous in feature-engineering code and the failure is silent: your categorical-encoding step just processes zero columns.

Trap 12“My rolling 7-day average feature is fine.”

Trap: not checking the window boundary. Correct: rolling(7) includes the current row, so if you're predicting today's value the feature contains its own target. Backtest looks superb; production doesn't.

Fix: .shift(1) before .rolling(). For panel data: sort, group by entity, then shift, then roll — otherwise you also bleed one entity's history into another's features.

Trap 13“except Exception: pass makes the pipeline robust.”

Trap: calling it robustness. Correct: it converts every failure — including your own typos and a renamed column — into silence, and the pipeline reports success with wrong numbers. In data work that's the worst failure mode: a crash gets fixed, a quiet wrong answer reaches a dashboard and then a decision.

Instead: catch specific exceptions, log what you swallow with enough context to find the record, re-raise anything unexpected, and put a threshold on the acceptable bad-row rate.

Trap 14“groupby().sum() covers every row.”

Trap: assuming completeness. Correct: groupby drops rows whose key is NaN by default, so the group totals can be legitimately less than the column total — with no warning.

Pass dropna=False, or fillna("UNKNOWN") on the key first. And make it a habit to assert the total is conserved after any aggregation.

CodingWhere does the SQL↔pandas mapping break down?
              
Three places. The index — SQL has no equivalent, so pandas operations align on it in ways a SQL translation doesn't capture; that's the source of surprise NaNs. Order — SQL results are unordered without ORDER BY, while pandas preserves and relies on row order (shift, diff, keep="last"). Nulls — SQL's three-valued logic differs from NaN semantics, so WHERE x != 5 excludes nulls in SQL, and a pandas mask on NaN gives False rather than NULL.
And the practical one: pandas has no query planner. SQL will reorder your joins and push down predicates; pandas executes exactly what you wrote, in order — which is why filtering before joining matters in pandas and not in SQL.

            

          

        

      


      

        
11.14 The 90-second project story

        
You will be asked to describe your work. A rehearsed 90-second structure beats a rambling five minutes, and it's the cheapest preparation available.


        

          
structure Five beats, 90 seconds

          
1 · context
One sentence on the business problem and why it mattered. Not the tech stack.

          
2 · simplest first
What you tried first and why it wasn't enough. This signals judgement rather than reflexive complexity.

          
3 · the hard part
One specific technical obstacle and how you diagnosed it — leakage found, a join exploding, a memory ceiling.

          
4 · the number
Land on a measurement. Latency, cost, accuracy, hours saved. Vague impact is the most common failure.

          
5 · what you'd change
One honest limitation. A candidate with no criticisms of their own project reads as someone who never measured it.

        


        

          
Drill

          

            
Practical“Tell me about a project you're proud of.”
              
Use the five beats: context (the business problem in one sentence), simplest thing first (and why it wasn't enough), the hard part (one specific obstacle, and how you diagnosed it rather than guessed), the number, what you'd change.
The number is what most answers lack. “It improved things” is unmemorable; “cut the nightly job from 3 hours to 12 minutes, which let us move from daily to hourly refresh” is a story with a shape.
And pick a project where the hard part was technical and specific — a leakage bug you found, a join that silently inflated revenue 50%, a memory ceiling you worked around. Those make the interviewer ask a follow-up, which is exactly what you want.

            

            
Practical“What was the hardest bug you've debugged?”
              
Pick one with a non-obvious cause and a clear diagnostic path, and include the wrong hypothesis you had first — that's what makes it believable and shows how you actually work.
Strong candidates from this guide: a missing add_messages-style reducer or an index-alignment NaN; a sync client blocking an event loop so “parallel” work ran serially; a many-to-many join inflating revenue; a scaler fitted before the split producing a 0.99 AUC that collapsed in production; an int16 downcast overflowing on aggregation.
Structure: symptom → first hypothesis → the evidence that disproved it → actual cause → fix → what you added so it can't recur. That last clause is the part that distinguishes a debugging story from an engineering one.

Self-test

          

            
DebugCover the table. Given “my numbers are 50% too high”, what are your three checks?
              
1. A join that duplicated rows. Check len() before and after every merge, and whether the right side was unique on the key. This is the most likely cause of a systematic overstatement.
2. Double-counting from a concat or an append that ran twice — check for duplicated rows with df.duplicated().sum().
3. An aggregation over the wrong grain — summing a column that was already a per-group total, which is what happens after a transform is mistaken for an agg.
And the general diagnostic: reconcile against a known total at each stage. If revenue is right after step 2 and wrong after step 3, you've localised it in one pass.

            

            
DebugGiven “it works in the notebook but fails in the script”, what's your first hypothesis?
              
Hidden state from out-of-order cell execution. The notebook has a variable, an import, or a monkey-patched setting that the script doesn't, because you defined it in a cell you later edited or deleted. The test is “Restart and Run All” — if that fails, the notebook was lying.
Second hypothesis: a different working directory or environment, so relative paths resolve differently or a package version differs. Third: something depending on display rather than value — a frame that looked fine because Jupyter truncated it.
