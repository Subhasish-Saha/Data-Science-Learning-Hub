6.1 Anatomy of an ndarray ⭐⭐

One sentence explains the entire library: an array is a flat memory buffer plus a dtype, a shape, and strides. Almost everything that feels like magic is just new strides over the same buffer.

Run itanatomy.pyidle
⌘/Ctrl + Enter 

          
Expected: dtype int64, itemsize 8, shape (3, 4), strides (32, 8), nbytes 96. The offset arithmetic gives byte 48 → flat index 6, matching a[1,2] == 6. The transpose has swapped strides (8, 32) and shares memory, but is F-contiguous rather than C-contiguous — and reshaping that must copy, because the requested layout isn't expressible as strides over the existing buffer.

        


        

          
Likely interview questions

          

            
Deep diveWhat are strides, and why do they matter?
              
Strides are the number of bytes to step to move one position along each axis. For a C-ordered int64 array of shape (3, 4) they're (32, 8): 8 bytes to the next column, 32 to the next row.
They matter because shape + strides is how NumPy maps an n-dimensional index onto a flat buffer, and that means several expensive-looking operations are free. reshape, transpose and basic slicing just produce new metadata over the same memory — O(1), no copying.
Two consequences worth stating. It explains views versus copies: if the result is expressible as strides over the existing buffer, you get a view; if not (fancy indexing, or reshaping a transpose), NumPy must copy. And it explains performance: iterating along the contiguous axis is cache-friendly, while iterating across it strides through memory and can be several times slower.

            

            
ConceptualWhat's the difference between C order and Fortran order?
              
C order (row-major) stores rows contiguously — the last axis varies fastest. Fortran order (column-major) stores columns contiguously — the first axis varies fastest. NumPy defaults to C order.
It matters for speed, not correctness: summing along the contiguous axis reads sequential memory and is cache-friendly, while summing across it jumps by a stride each step. On a large 2-D array that can be a 2–5× difference for the identical operation, which is why a.sum(axis=1) and a.sum(axis=0) don't always cost the same.
Where it surfaces in practice: a.T is F-contiguous, so passing a transpose into a library expecting C order can trigger a hidden copy; and some BLAS/LAPACK routines want Fortran order, so scikit-learn occasionally copies your data with np.asfortranarray. If you see an unexplained memory spike, a layout conversion is a good suspect.

            

          

        

      


      

        
6.2 Why arrays beat lists ⭐

        
Three reasons, and you should be able to give them with numbers: no boxing, one dtype, contiguous memory.


        

          
Run itwhy_numpy.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the list costs roughly 4–5× the memory of the array (≈11 MB vs 2.4 MB at N=300k), and the NumPy computation is typically 50–200× faster with an identical result. The final line shows the trade-off: mixing types forces a common dtype — here everything becomes a string — which is why arrays are homogeneous and pandas exists to give you per-column dtypes.

        


        

          
Likely interview questions

          

            
Very commonWhat are the advantages of NumPy arrays over Python lists?
              
Three structural reasons, and they're worth giving in this order because each explains the next.
No boxing. A list of a million ints is a million pointers to a million int objects, each ~28 bytes with a refcount and type pointer. An array is a million raw 8-byte values. That's roughly 4–5× less memory.
One dtype. Because every element has the same type, the inner loop needs no per-element type dispatch — it runs in compiled C, not the interpreter.
Contiguous memory. One buffer means the CPU can prefetch and use SIMD instructions, so operations vectorise.
Net effect: typically 10–100× faster for elementwise numeric work, plus the API — broadcasting, slicing, aggregations, linear algebra. The cost to acknowledge: arrays are homogeneous and fixed-size, so appending is expensive and mixed types force an upcast.

            

            
PracticalWhen would you still use a Python list?
              
When the data is heterogeneous (mixed types that shouldn't be coerced), when you're growing it incrementally (list.append is amortised O(1); np.append reallocates and copies the whole array every time, so building an array in a loop is O(n²)), when it's small enough that NumPy's fixed overhead dominates, or when you need to hold arbitrary Python objects.
The idiomatic pattern that follows: accumulate in a list, convert once — np.array(rows) at the end. That's the same lesson as not growing a DataFrame row by row (§2.3).

            

          

        

      


      

        
6.3 dtypes and silent overflow ⭐

        
Fixed-width integers wrap around without warning. This is a real source of wrong numbers in feature engineering, and it does not happen with Python ints.


        

          
Run itdtypes.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: 120 + 10 in int8 gives -126. The int16 sum of three 30,000s overflows to a wrong (often negative) number, while promoting first gives the correct 90,000 — sum(dtype=np.int64) is the clean fix. float32 shows 0.1 stored with visible error, and 1e8 + 1 == 1e8 is True because the increment is below the representable gap. Python's own int handles 2**70 fine; np.int64 raises.

        


        

          
Likely interview questions

          

            
GotchaYour sum of a downcast column is negative. What happened?
              
Integer overflow. NumPy integers are fixed-width and wrap silently — no exception, no warning. If you downcast a column to int16 to save memory, the individual values fit but the aggregate exceeds 32,767 and wraps around, often to a negative number.
Fixes: aggregate with an explicit accumulator, arr.sum(dtype=np.int64), which is the cleanest; or promote before summing. And before downcasting at all, check the range against np.iinfo(dtype).max — with headroom for future growth, not just today's data.
The general lesson worth stating: memory optimisation by downcasting is real and useful (§9.4), but it introduces a correctness risk that plain int64 does not have. Downcast storage, compute in a wider type.

            

            
Conceptualfloat32 or float64 for machine learning?
              
float32 for most model training: half the memory and bandwidth, and on GPUs substantially faster. Deep learning trains in float32 or lower (bfloat16/float16) routinely, because gradient noise dwarfs the extra precision.
float64 when precision genuinely matters: accumulating a sum over millions of rows (float32 has ~7 significant digits, so a long summation loses low-order bits — this is catastrophic cancellation), financial calculations, or iterative numerical methods that amplify error. Note pandas and NumPy default to float64 for exactly this reason.
The practical compromise: store in float32, accumulate in float64 — arr.mean(dtype=np.float64). And never test float equality; use np.isclose or np.allclose with an explicit tolerance (§6.10).

            

          

        

      


      

        
6.4 Views vs copies ⭐⭐

        
The question that separates people who have debugged a real aliasing bug from people who have read about one. A slice of an array can mutate its parent.


        

          
Run itviews.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: a shows 999 at index 2 — the view wrote through — while the fancy-indexed copy's edit doesn't appear in a. The table shows slicing, a[::2], a.T and reshape are views, while a boolean mask, .copy() and a + 0 are copies. The data block is the bug in situ: cleaning a row in place silently edits the parent array, and .copy() fixes it.

        


        

          
          How to check, rather than guess
          
arr.base is not None tells you it's a view; np.shares_memory(a, b) tells you two arrays overlap. Use them in a debugger rather than reasoning from the rules — and note np.may_share_memory is the fast, conservative version that can return True when there's no actual overlap.

        


        

          
Likely interview questions

          

            
Very commonWhen does NumPy return a view and when a copy?
              
View when the result can be expressed as new strides over the same buffer: basic slicing (a[2:6], a[::2]), reshape when compatible, transpose, and .view().
Copy when it can't: fancy indexing (an integer array or list of indices), boolean masking, any arithmetic (a + 1), .copy(), and reshaping a non-contiguous array.
The reason is the mechanism from §6.1: a view is just metadata, so it's only possible when the selection is a regular strided pattern. Fancy indexing picks arbitrary positions, which no stride can describe.
Why it matters: a view writes through to the parent, so mutating a slice changes the original — the aliasing bug from §1.1 with numeric data. And check rather than assume: arr.base is not None or np.shares_memory(a, b).

            

            
DebugA function you called changed your array. How did that happen?
              
Either it mutated the array in place, or it mutated a view it derived from your array. Both are visible to you because arrays are mutable and views write through (§1.1).
Diagnosis: check whether the function does in-place operations (arr += 1, arr[mask] = x, np.sort(arr) vs sorted, or any ufunc with out=). Then check whether what it received was a view of something bigger.
Prevention, in order: pass a copy if you don't trust the callee; hand it a read-only view (v = arr.view(); v.flags.writeable = False) so an in-place write raises immediately rather than corrupting silently; and by convention, make your own functions return new arrays unless in-place behaviour is in the name.

            

          

        

      


      

        
6.5 Strides, reshape and transpose ⭐

        
Follows directly from §6.1: these operations rewrite metadata, so they cost nothing — until the layout they'd need isn't expressible, at which point NumPy copies.


        

          
Run itstrides.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: strides (48, 8); the transpose shows (8, 48); a[::2] doubles the row stride to 96; a column slice has stride 48. ravel shares memory while flatten never does, and a.T.ravel() must copy. The timing comparison shows the two sum directions differ measurably on a 2000×2000 array despite doing identical arithmetic — that gap is cache behaviour, and it's the practical consequence of layout.

        


        

          
Likely interview questions

          

            
Codingravel vs flatten vs reshape(-1)?
              
ravel() returns a view when possible, a copy when not. flatten() always copies. reshape(-1) behaves like ravel — view if the layout allows.
So: use ravel or reshape(-1) when you just want to iterate or aggregate and don't intend to mutate — it's free. Use flatten when you specifically want an independent copy you can safely modify.
The -1 means “infer this dimension”, and only one axis may be -1. Common uses: reshape(-1, 1) to turn a 1-D array into a column vector for scikit-learn, and reshape(n, -1) to flatten trailing dimensions of an image batch.

            

          

        

      


      

        
6.6 Basic vs fancy indexing ⭐⭐

        
Two different mechanisms with different return semantics. The distinction is exactly the view/copy question, and it also explains a surprising indexing result people get wrong.


        

          
Run itindexing.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the slice, the two selected rows, and [0 3 6 9] from the boolean mask. The important line: a[rows, cols] gives [3 6 9] — it pairs the index arrays elementwise rather than taking a cross-product, which is the most common fancy-indexing surprise. np.ix_ (or adding [:, None]) gives the 3×3 outer selection instead. Then where, in-place masked assignment, and names[scores.argsort()[::-1]] → ['b' 'c' 'a'].

        


        

          
Likely interview questions

          

            
Deep diveWhat does a[[0,1,2], [3,2,1]] return?
              
Three elements — [a[0,3], a[1,2], a[2,1]] — because fancy indexing broadcasts the index arrays against each other and pairs them elementwise. It does not select a 3×3 block.
To get the cross-product you must make the indices broadcast into a 2-D shape: a[np.ix_(rows, cols)], or explicitly a[np.array(rows)[:, None], cols], where the [:, None] turns the row indices into a column so they broadcast against the row of column indices.
This is worth knowing because the pairing behaviour is genuinely useful — it's how you gather one element per row, e.g. picking the predicted-class probability for each sample: probs[np.arange(n), labels]. That idiom appears constantly in ML code.

            

            
CodingGet the indices of the top 5 values.
              
np.argsort(a)[-5:][::-1] for a full sort, or better np.argpartition(a, -5)[-5:] which is O(n) rather than O(n log n) because it only partially orders the array. Follow with a small argsort on those five if you need them ranked.
The distinction matters at scale: on ten million values, argpartition is several times faster, and it's the NumPy equivalent of the bounded-heap answer from §2.6.
Then the practical bit: these return indices, which you use to index the original array or a parallel one — names[idx], df.iloc[idx]. Forgetting that argsort gives positions rather than values is a common slip.

            

          

        

      


      

        
6.7 Broadcasting ⭐⭐

        
How NumPy operates on arrays of different shapes without copying them. Three rules, and they are worth memorising verbatim because the error messages assume you know them.


        

        

          
Run itbroadcasting.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: a + row adds the row to every row. a + col raises operands could not be broadcast together with shapes (3,4) (3,), and col[:, None] — shape (3, 1) — fixes it by adding per row. Standardised columns come out with mean ≈0 and std ≈1. The outer product is the 3×3 multiplication table. The last block makes the memory point: the operands broadcast for free, but the result is materialised at full size.

        


        

          
Likely interview questions

          

            
Very commonExplain broadcasting.
              
It's how NumPy applies an elementwise operation to arrays of different shapes without you writing a loop or copying data. Three rules: right-align the shapes; a missing leading dimension counts as 1; each dimension must then be either equal or 1, and a 1 is stretched to match.
The mechanism is the part worth adding: a stretched dimension is implemented with stride 0, so the same memory is read repeatedly rather than duplicated. That's why broadcasting costs nothing for the operands — though the result is a full-size array, which is the memory trap people hit on large data.
Canonical example: standardising columns, (X - X.mean(axis=0)) / X.std(axis=0), where a (n, k) array meets a (k,) vector. And the fix for the failing case is almost always [:, None] to insert an axis so the shapes align the way you intended.

            

            
Debug“operands could not be broadcast together with shapes (1000,) (1000,1)”. What's wrong?
              
Right-align them: (1000,) becomes (1, 1000) and you're comparing (1, 1000) with (1000, 1). Both dimensions are 1-or-equal, so it actually succeeds — and produces a 1000×1000 array, which is usually not what you wanted and may blow your memory.
That's the more dangerous version of this bug: broadcasting silently giving you an outer product where you expected an elementwise result. The usual cause is a stray (n, 1) shape from a scikit-learn predict, a reshape(-1, 1), or a DataFrame column selected with double brackets.
Fixes: .ravel() or .squeeze() the (n, 1) down to (n,), and assert shapes at function boundaries — assert y.shape == (n,) catches it at the source rather than as a memory error three lines later. Printing .shape is the first thing to do with any broadcasting confusion.

            

          

        

      


      

        
6.8 Axis semantics ⭐

        
axis=0 confuses everyone at least once. The reliable mental model: axis is the dimension that disappears.


        

          
Run itaxes.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: a.sum(axis=0) → [12 15 18 21], shape (4,) — four values, one per column, because the 3-row axis collapsed. a.sum(axis=1) → [6 22 38], shape (3,). With keepdims=True the shape stays (1, 4) so it broadcasts back with no extra work. In 3-D, summing axis 0/1/2 of a (2,3,4) array gives (3,4), (2,4), (2,3) — the named axis is always the one removed.

        


        

          
Likely interview questions

          

            
Very commonWhat does axis=0 actually mean?
              
The axis you name is the one that disappears. For a (3, 4) array, sum(axis=0) collapses the 3 rows and returns 4 values — one per column. sum(axis=1) collapses the 4 columns and returns 3 values — one per row.
That phrasing works in any number of dimensions and avoids the “is axis 0 rows or columns” muddle. The muddle exists because people describe axis=0 as “rows” while it computes a result per column — both true, which is why the collapse framing is safer.
Same rule in pandas: df.sum(axis=0) gives a value per column, df.mean(axis=1) a value per row. The confusing exception is df.drop(..., axis=1), where axis names what you're addressing rather than what collapses — which is exactly why the modern API prefers df.drop(columns=[...]).

            

            
CodingWhy use keepdims=True?
              
It keeps the reduced axis as size 1 instead of removing it, so the result broadcasts straight back against the original. a / a.sum(axis=1, keepdims=True) row-normalises in one expression; without it you get shape (3,), which right-aligns as (1, 3) and either fails or — worse — silently broadcasts the wrong way.
It's the tidy alternative to sprinkling [:, None], and it makes the intent explicit. Use it whenever a reduction feeds straight back into an operation with the original array — normalising, centring, computing softmax, subtracting a per-row max for numerical stability.

            

          

        

      


      

        
6.9 Vectorising a loop ⭐⭐

        
The classic live-coding task: here's a nested Python loop, make it fast. The method is always the same — express the computation as whole-array arithmetic.


        

          
Run itvectorise.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the nested loops take hundreds of milliseconds; broadcasting is typically 50–200× faster; the Gram-matrix version is faster again because it delegates to BLAS matrix multiplication. All three agree to within floating-point tolerance. The closing note is the senior point: broadcasting builds an (n, m, 3) intermediate, so at n=m=20,000 it would need ~10 GB, while the algebraic form only ever holds (n, m).

        


        

          
Likely interview questions

          

            
Very commonWhat is vectorisation, and why is it faster?
              
Expressing a computation as operations on whole arrays rather than element-by-element in Python. The speedup comes from three things, and naming them beats saying “it's implemented in C”.
No interpreter overhead per element — one C loop instead of a million bytecode dispatches, each with reference counting and type checks. SIMD — the CPU processes several values per instruction on contiguous data. Cache efficiency — sequential access with prefetching, versus chasing pointers to scattered int objects.
Typical gains are 10–100×, and for anything reducible to matrix multiplication you get more, because it lands in a hand-tuned BLAS kernel.
The honest caveat worth adding: vectorisation often trades memory for speed. A broadcast intermediate can be far larger than either input, so on big data the fastest formulation is sometimes the one that avoids materialising it — as in the distance example, where the algebraic identity beats broadcasting.

            

            
CodingVectorise pairwise Euclidean distances.
              
Broadcasting version: diff = A[:, None, :] - B[None, :, :] then np.sqrt((diff**2).sum(axis=-1)). Shapes (n,1,d) and (1,m,d) broadcast to (n,m,d), and summing the last axis gives (n,m).
The better version for large n: use |a−b|² = |a|² + |b|² − 2a·b, so d2 = a2[:, None] + b2[None, :] - 2 * A @ B.T. This never materialises the (n,m,d) intermediate and pushes the heavy work into BLAS.
Two details that show care: clip with np.maximum(d2, 0) before the square root, because floating-point error can produce tiny negatives on the diagonal; and mention that in practice you'd call scipy.spatial.distance.cdist or sklearn.metrics.pairwise_distances, which handle chunking and numerical edge cases for you.

            

            
GotchaIs np.vectorize a way to vectorise code?
              
No — and this is a deliberate trap. The docs say so explicitly: np.vectorize is a convenience wrapper that provides broadcasting semantics for a scalar function, but it loops in Python internally. It is essentially as slow as the loop you started with.
What actually vectorises: expressing the logic with array operations; np.where or np.select for conditionals; boolean masks for filtering; np.digitize/searchsorted for binning; and existing ufuncs.
When the logic genuinely can't be expressed that way — an irreducible scalar loop with branching — the real answers are Numba (@njit, often 100×) or Cython. Naming np.vectorize as a performance tool is a reliable tell that someone hasn't measured it.

            

          

        

      


      

        
6.10 Floats, NaN and reproducibility ⭐

        
Floating-point care and seeded randomness. Both come up because both cause bugs that look like someone else's fault.


        

          
Run itfloats_nan.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: 0.1 + 0.2 == 0.3 is False (the true value ends …04), while np.isclose is True. nan == nan is False but nan is nan is True — which is exactly why is is not a NaN test. Plain sum/mean/max return nan; the nan* variants skip it. The float32 cancellation loses the +1 entirely, giving 0.0, while float64 gets it right. Two generators with the same seed produce identical draws.

        


        

          
Likely interview questions

          

            
Very commonWhy is 0.1 + 0.2 != 0.3?
              
Because binary floating point cannot represent 0.1, 0.2 or 0.3 exactly — they're stored as the nearest representable binary fractions, and the rounding errors don't cancel. The sum is 0.30000000000000004.
Consequences and fixes: never test float equality — use math.isclose or np.isclose/np.allclose with explicit tolerances, and pd.testing.assert_frame_equal for frames. For money, use decimal.Decimal or integer minor units, because a fraction of a penny per row compounds.
The related deeper issue worth mentioning: floating-point addition is not associative, so summation order changes the result. That's why parallel or chunked sums can differ slightly from a serial sum, and why np.sum uses pairwise summation to reduce error rather than a naive accumulator.

            

            
GotchaHow do you count and handle NaN correctly?
              
Count: np.isnan(a).sum(), or df.isna().sum() in pandas. Never a == np.nan — NaN is not equal to itself by IEEE-754 design, so that comparison is always False.
Aggregate: plain sum/mean/max propagate NaN, returning NaN for the whole array. Use np.nansum, np.nanmean, np.nanmax to skip them. Note pandas does the opposite by default — df.mean() skips NaN via skipna=True — which is a genuine inconsistency between the two libraries and a good thing to flag.
Two more traps: np.sort silently places NaN last, so a “maximum” taken from a sorted array may be NaN; and NaN only exists in float dtypes, so an integer column with missing values becomes float64 — or, in modern pandas, a nullable Int64 with pd.NA (§7.6).

            

            
PracticalHow do you make random results reproducible?
              
Use the modern generator API: rng = np.random.default_rng(42) and pass rng explicitly to whatever needs randomness. Avoid np.random.seed(), which mutates hidden global state — any library that also draws from the global stream changes your results, and it's not thread-safe.
For a whole pipeline you need more than NumPy: seed Python's random, set PYTHONHASHSEED, pass random_state to every scikit-learn estimator and splitter, and seed your framework (torch.manual_seed). For independent parallel streams use rng.spawn(n) rather than seeding each worker with seed + i, which can produce correlated streams.
And the honest caveat: seeds are necessary but not sufficient. Thread counts, GPU kernels, floating-point summation order and library versions all introduce nondeterminism — which is why reproducibility also means pinning versions (§10.12).
