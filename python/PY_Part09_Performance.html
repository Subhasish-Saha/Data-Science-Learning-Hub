9.1 Measure first ⭐

Performance questions are really diagnosis questions. Anyone can say “vectorise it”; the signal is whether you profile before you guess.

ToolAnswersUse when
%timeit / timeitHow long does this one expression take?Comparing two implementations
cProfileWhich function dominates?A slow script, no idea where
line_profilerWhich line dominates?You know the function, not the line
memory_profiler / tracemallocWhere does the memory go?OOM, or unexplained RSS growth
df.memory_usage(deep=True)Which column is expensive?A frame that's bigger than expected
Two input sizesIs it linear or quadratic?Always — cheapest diagnostic there is
Run itmeasure.pyidle
⌘/Ctrl + Enter 

          
Expected: the set version roughly doubles each time you double n (ratio ≈2×), while the list version roughly quadruples (ratio ≈4×). That ratio alone tells you the complexity class without reading a line of code, which is why it's the first thing to try. The cProfile output then names quadratic as the dominant function by cumulative time.

        


        

          
Likely interview questions

          

            
DebugA pipeline that ran in 5 minutes now takes 3 hours. Walk me through it.
              
Establish what changed first — code, data volume, or dependency versions. A 36× slowdown from a code change is a different investigation from one caused by 10× the data hitting a quadratic step.
Then measure rather than guess. Time it at two input sizes: if doubling the input quadruples the time, you have a quadratic step and you're looking for a linear operation inside a loop (§2.3). cProfile to find the dominant function, then line_profiler to find the line. Check memory too — a 3-hour runtime with heavy swapping is a memory problem wearing a CPU costume, and df.memory_usage(deep=True) plus RSS will show it.
The usual culprits in data code: a DataFrame grown row by row, an apply where a vectorised operation exists, a join that exploded (§8.5), x in list inside a loop, or a dtype regression where a column became object and every operation now runs in Python.

            

            
PracticalWhat's the cheapest useful diagnostic?
              
Run it at two input sizes and look at the ratio. Double the rows: ~2× slower means linear and probably fine; ~4× means quadratic and you have a specific class of bug to hunt. That takes thirty seconds and narrows the search enormously, before you've set up any tooling.
Second cheapest: df.info(memory_usage="deep") and df.dtypes. A surprising share of “pandas is slow” turns out to be an object-dtype column where a numeric or categorical one was intended, which drops every operation on it back into Python.

            

          

        

      


      

        
9.2 The vectorisation ladder ⭐⭐

        
Five ways to compute the same column, each roughly an order of magnitude apart. This is the mental model behind every pandas performance answer.


        

        

          
Run itladder.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: iterrows is by far the slowest; itertuples is several times faster; apply(axis=1) lands close to itertuples rather than close to vectorised — that's the point. The vectorised and NumPy versions are typically 50–200× faster than iterrows, and nearly identical to each other. All six produce the same numbers.

        


        

          
Likely interview questions

          

            
Very commonHow would you speed up a slow pandas operation?
              
Measure, then climb the ladder. The ladder from slowest to fastest: iterrows → itertuples → apply → vectorised pandas → NumPy on the raw arrays. Each step up is roughly an order of magnitude, and the big cliff is between apply and vectorised, because everything above that line is still a Python loop.
Concretely: replace row iteration with column arithmetic; replace apply with a vectorised expression, np.where/np.select for conditionals, map with a dict for lookups, or merge for joins; replace string apply with .str methods.
Then the other levers, because vectorisation isn't the only one: fix dtypes (an object column defeats vectorisation entirely), reduce memory so you stop swapping, use groupby().agg("sum") rather than apply, and if the operation genuinely can't be vectorised, reach for Numba, Polars or DuckDB rather than trying to out-clever pandas.

            

          

        

      


      

        
9.3 Why apply is a loop ⭐

        
The most common misconception in pandas performance. apply is not vectorised — it calls your Python function once per row or per group.


        

          
Run itapply_truth.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the function is called 8 times for 8 rows — direct proof it's a loop. Then apply(axis=1) takes hundreds of milliseconds while np.select and pd.cut take single-digit milliseconds for the identical banding, typically a 50–100× gap. Even Series.apply(np.sqrt) is much slower than np.sqrt(series), because apply pays Python call overhead per element rather than letting the ufunc run over the buffer.

        


        

          
Likely interview questions

          

            
GotchaIs df.apply vectorised?
              
No. It calls your Python function once per row (axis=1) or once per column (axis=0), so you pay full interpreter overhead per call. With axis=1 it also constructs a Series object for every row, which is why it's barely faster than iterrows.
What to use instead, by case: arithmetic → plain column expressions; conditionals → np.where or np.select; binning → pd.cut; lookups → .map(dict); joins → merge; strings → the .str accessor; dates → the .dt accessor.
When apply is genuinely fine: small data where clarity beats speed, or logic that truly can't be expressed as array operations — and then say what you'd do if it were the bottleneck (Numba, or restructure the problem).

            

            
CodingVectorise a multi-condition category assignment.
              
np.select([cond1, cond2, cond3], ["a", "b", "c"], default="other"). Conditions are evaluated in order and the first match wins, so it maps directly onto an if/elif chain — which makes the translation mechanical.
For two branches, np.where(cond, x, y). For numeric banding, pd.cut with explicit bin edges is clearer and gives you an ordered categorical for free. For a lookup from a mapping, df["col"].map(mapping) beats both.
The detail worth mentioning: np.select evaluates every condition over the whole column, so if one condition is very expensive you're paying for it on all rows — occasionally a reason to restructure. But it's still typically two orders of magnitude faster than the equivalent apply.

            

          

        

      


      

        
9.4 Cutting memory in half ⭐⭐

        
Three levers — dtype downcasting, the category dtype, and reading less in the first place — routinely give a 50–90% reduction on real frames.


        

          
Run itmemory.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: a substantial reduction — typically 60–80% smaller. The biggest single win is country → category (three distinct values stored once plus tiny codes), followed by flag → int8 (an 8× reduction for a column that only needs one bit) and score → float32. The per-column table shows where to look first. The closing warning matters: narrower dtypes overflow silently (§6.3).

        


        

          
Likely interview questions

          

            
Very commonYour DataFrame doesn't fit in memory. What do you do?
              
Read less, store it smaller, or don't hold it all at once — in that order, because the first is free.
Read less: usecols= to take only the columns you need, and dtype= at read time so pandas never materialises the wide version. On a wide file this alone often solves it.
Store it smaller: downcast integers and floats, convert low-cardinality strings to category, drop columns as soon as you're done with them. 50–90% reductions are routine.
Don't hold it all: chunksize= and aggregate per chunk; or convert to Parquet and use DuckDB or Polars, which stream larger-than-memory aggregations and joins natively.
The caveat that shows care: downcasting narrows the representable range, so aggregate with a wider accumulator (sum(dtype=np.int64)) or you'll get silent overflow (§6.3).

            

            
GotchaWhy does memory_usage() undercount?
              
Because by default it counts only the NumPy buffer for each column, not the Python objects those buffers point to. For a string column stored as object, the buffer is just pointers — 8 bytes per row — while the actual strings live elsewhere on the heap and can be many times larger.
Pass deep=True to include them: df.memory_usage(deep=True), or df.info(memory_usage="deep"). The difference on a wide text-heavy frame can be an order of magnitude, which is exactly when you need the number.
Related: pandas 3.0's PyArrow-backed str dtype stores strings compactly rather than as individual Python objects, so the gap between shallow and deep is much smaller than it used to be — one of the practical wins of upgrading (§7.3).

            

          

        

      


      

        
9.5 Out-of-core with chunks ⭐

        
Process a file bigger than RAM by aggregating chunk by chunk. The trick is knowing which statistics are chunkable and which aren't.


        

          
Run itchunked.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the chunked group sums and counts match the full read exactly. The important methodological point is in the note: you accumulate sum and count separately and divide at the end — averaging the per-chunk means would be wrong unless every chunk had the same number of rows in every group. The chunked variance, computed from the sum of squares, also matches.

        


        

          
Likely interview questions

          

            
CodingCompute a group mean over a file that doesn't fit in memory.
              
Accumulate sum and count per group across chunks, then divide once at the end. pd.read_csv(path, chunksize=N) yields frames; per chunk do groupby(key)["v"].agg(["sum","count"]), collect the partials, pd.concat them and groupby(level=0).sum().
The mistake to name explicitly: averaging the per-chunk means is wrong unless every chunk has the same number of rows in every group. Mean isn't associative under unequal weights; sum and count are.
Same idea extends: variance from sum, sum-of-squares and count (or Welford's algorithm, which is numerically more stable); min/max trivially. And mention the better tool — duckdb.sql("SELECT key, avg(v) FROM 'file.parquet' GROUP BY 1") does this out-of-core in one line.

            

            
ConceptualWhich statistics can't be computed in a single chunked pass?
              
Anything needing global order or the full distribution: exact median and quantiles, a full sort, and exact distinct counts at high cardinality (the set of seen values can itself exceed memory).
The workarounds: two passes if re-reading is affordable; approximate algorithms with bounded error — t-digest or reservoir sampling for quantiles, HyperLogLog for cardinality; external sort (sort chunks, spill, merge); or push it to a database or DuckDB, which implement the spilling for you.
Worth adding the exception: mean and variance are single-pass via Welford's algorithm, which is more numerically stable than accumulating the raw sum of squares — a nice detail that shows you've thought about float precision as well as memory.

            

          

        

      


      

        
9.6 The GIL, and Python 3.14 ⭐⭐

        
The 2026 currency question. The standard answer changed this year, because PEP 779 made free-threaded builds officially supported in Python 3.14.


        

        

          
Run itgil.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: the CPU-bound sequential and threaded times are roughly equal — two threads gained nothing, because both needed the GIL to execute bytecode. The I/O-bound case is roughly 3× faster with three threads, because sleep releases the GIL while waiting. That contrast is the answer to the GIL question. (In this browser runtime threading is constrained, so treat the shapes rather than the numbers as the lesson.)

        


        

          
Likely interview questions

          

            
Very commonWhat is the GIL?
              
The Global Interpreter Lock — a mutex in CPython that allows only one thread to execute Python bytecode at a time. Its purpose is memory management: it makes reference counting and internal structures safe without fine-grained locking everywhere, which also makes single-threaded Python faster.
The consequence: threads don't speed up CPU-bound pure-Python code. But the nuance that scores is what the GIL doesn't block — it's released during I/O and during compiled extension work. So threads help a lot for network and disk work, and NumPy, pandas, scikit-learn and BLAS already run their heavy kernels in parallel because they drop the GIL.
Which means for data work the GIL is much less of a constraint than its reputation suggests: the expensive parts were never running under it.

            

            
ModernWhat changed with free-threaded Python?
              
PEP 779: as of Python 3.14, the free-threaded build is officially supported — it moved from experimental to a supported configuration. It's a separate build of CPython compiled without the GIL, so the default interpreter still has one; you opt in.
What it enables: genuine multi-core parallelism for CPU-bound pure-Python code using threads, without the memory duplication and pickling costs of multiprocessing.
The honest caveats, which are the interesting half of the answer. Single-threaded performance on the free-threaded build is somewhat slower, since removing the GIL requires extra work in the object model. C extensions must be explicitly compatible, and the ecosystem has been catching up — NumPy 2.5 improved its free-threading support, for instance. And you now have to think about data races in Python code that the GIL used to paper over.
Practical position for 2026: promising and worth tracking, but for data work the existing answers — vectorised C code, multiprocessing, joblib — still cover most cases.

            

          

        

      


      

        
9.7 Threads vs processes vs async ⭐⭐

        
Choose by workload, not by preference. Three questions decide it.


        

          
choose By what the work is actually doing

          
threads
I/O-bound, moderate concurrency. Reading files, DB queries, a few hundred HTTP calls. Cheap, shared memory, and the GIL is released while waiting.

          
async
I/O-bound, very high concurrency. Thousands of API calls. Far lower per-task overhead than threads — but one blocking call stalls the whole loop.

          
processes
CPU-bound pure Python. True parallelism, at the cost of pickling arguments and duplicating memory.

          
none of them
CPU-bound numeric work. Vectorise it — NumPy/BLAS already use multiple cores internally. Adding processes on top often makes it slower by oversubscribing.

        


        

          
Run itconcurrency.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: sequential takes ~800 ms; threads and async both finish in ~100–150 ms, roughly an 8× improvement, with identical results. The final block is the lesson: using time.sleep (blocking) inside a coroutine takes ~400 ms for four tasks rather than ~100 — the concurrency evaporates, because a blocking call holds the event loop and no other coroutine can run.

        


        

          
Likely interview questions

          

            
Very commonThreads, processes or async — how do you choose?
              
Ask what the work is doing.
I/O-bound (network, disk, database): ThreadPoolExecutor for tens to hundreds of concurrent operations — simple, shared memory, and the GIL is released while waiting. asyncio when you need thousands, because a coroutine costs far less than a thread — but only if the whole path is async.
CPU-bound pure Python: ProcessPoolExecutor or multiprocessing for real parallelism. Costs: arguments and results must be picklable, and each process gets its own memory.
CPU-bound numeric: none of the above — vectorise instead. NumPy and BLAS already thread internally, so wrapping them in processes usually oversubscribes the cores and gets slower. If you do parallelise, set OMP_NUM_THREADS=1 in the workers to stop nested threading.
And the 2026 footnote: free-threaded 3.14 (§9.6) makes threads viable for CPU-bound Python too, though not yet the default.

            

            
GotchaWhat goes wrong with multiprocessing in data code?
              
Pickling and memory. Everything crossing the process boundary must be picklable, so lambdas, closures and local functions fail — which is why functools.partial and module-level functions matter (§3.7). And a large DataFrame passed as an argument is serialised and copied into every worker, so eight workers can mean eight copies plus the serialisation time, which frequently makes the parallel version slower.
Then the platform difference: fork (Linux default historically) shares memory copy-on-write and is fast but unsafe with threads; spawn (macOS and Windows default, and increasingly the default generally) re-imports your module in each child — so any module-level code runs again, and you need the if __name__ == "__main__" guard or you get infinite process spawning.
Practical mitigations: pass file paths or ranges rather than data and let workers load their own slice; use joblib, which memory-maps large arrays instead of pickling them; and measure — parallelism has real fixed costs and often loses on medium-sized work.

            

          

        

      


      

        
9.8 Escape hatches: Numba, Polars, DuckDB ⭐

        
When vectorisation isn't enough or isn't possible. Knowing which tool matches which problem is a strong senior signal — and so is knowing when not to switch.

Likely interview questions

          

            
ModernWould you use Polars instead of pandas?
              
For new, performance-sensitive pipeline work — yes, seriously consider it. Polars is Rust-based, multi-threaded by default, Arrow-backed, and has a lazy API with a query optimiser that can do predicate and projection pushdown and stream larger-than-memory data. On large group-bys and joins it's typically several times faster than pandas.
Where pandas still wins: ecosystem — everything from scikit-learn to plotting libraries to tutorials assumes it — and familiarity across a team. Rewriting a working pandas pipeline for speed alone is rarely worth the risk.
The pragmatic position, and the one I'd give: they interoperate cheaply through Arrow, so you can use Polars or DuckDB for the heavy load-and-aggregate step and hand a pandas frame to the modelling code. That's usually the best of both, and it avoids framing it as a religious choice.

            

            
DesignWhen is Numba the right answer?
              
When the algorithm is genuinely a scalar loop with data-dependent branching or carried state that no array expression can capture — a custom recursive filter, a path-dependent simulation, a bespoke distance with early exit. Add @njit and you often get 50–200× with the same code.
Before reaching for it, try two cheaper things: vectorise, and restructure the problem — many “inherently sequential” loops become segment-wise cumsums, sorts or joins once you find the right formulation, which needs no new dependency.
The costs to acknowledge: JIT compilation on first call (annoying in short-lived jobs, fixable with caching or AOT), support for only a subset of NumPy and almost no pandas, obscure error messages when you stray outside it, and a heavyweight dependency. It's a targeted tool for a hot kernel, not a general accelerator.
