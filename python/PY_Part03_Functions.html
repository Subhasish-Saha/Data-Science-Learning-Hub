3.1 The full signature grammar ⭐

Most people know *args and **kwargs. Fewer can explain the / and * markers — which is where the question usually goes.

Run itsignatures.pyidle
⌘/Ctrl + Enter 

          
Expected: the first call packs args=(3, 4) and kwargs={'other': 'z'}. Then two TypeErrors demonstrating the markers: pos_only cannot be passed by keyword, and kw_only cannot be passed positionally. The resample pair shows the practical value — forcing freq to be a keyword makes resample(100, "D") an immediate error rather than a silently mis-assigned argument.

        


        

          
Likely interview questions

          

            
Very commonExplain *args and **kwargs.
              
In a definition they collect: *args gathers extra positional arguments into a tuple, **kwargs gathers extra keyword arguments into a dict. In a call the same symbols do the opposite — they unpack: f(*my_list, **my_dict) spreads a sequence into positional arguments and a mapping into keyword arguments.
That symmetry is the thing to say out loud, because it's what makes transparent wrappers possible: def wrapper(*a, **kw): return fn(*a, **kw) forwards any signature, which is the backbone of every decorator.
Then add the ordering rule, since it's the natural follow-up: positional-only /, positional-or-keyword, *args, keyword-only, **kwargs. A bare * marks the start of keyword-only parameters without collecting anything; a / marks the end of positional-only ones.

            

            
PracticalWhy would you force keyword-only arguments?
              
To make call sites readable and to stop positional mistakes. train(df, 0.2, 42, True) is unreadable and the arguments are trivially swappable; train(df, *, test_size=0.2, seed=42, shuffle=True) forces every caller to name them, so a reordering mistake becomes impossible rather than silent.
The second reason is API evolution: keyword-only parameters can be reordered or have new ones inserted without breaking callers, because nobody depends on their position. That's exactly why pandas and scikit-learn have been progressively converting their APIs to keyword-only — df.drop("col", axis=1) becoming df.drop(columns="col") is the same idea.
Rule of thumb: anything that's a flag or a tuning parameter should be keyword-only; only the primary data argument deserves to be positional.

            

          

        

      


      

        
3.2 Closures and what they capture ⭐⭐

        
A closure is a function plus the enclosing variables it still refers to. Understand this and decorators become bookkeeping rather than magic.

Expected: 30, then a tuple containing one cell, 3 as its contents, and ('factor',) as the free variables — direct evidence that the captured variable outlives the call. The counter prints 3, and the second factory call prints 1 vs 3, proving each closure gets its own cell. The final pair repeats late binding: [2, 2, 2] then [0, 1, 2].

        


        

          
Likely interview questions

          

            
Very commonWhat is a closure?
              
A function that remembers variables from the scope where it was defined, even after that scope has exited. Concretely: an inner function referencing an outer function's local, returned from the outer function. Python keeps the referenced variables alive in cells, visible as fn.__closure__ and named in fn.__code__.co_freevars.
Two properties to state, because they're what get tested. It captures the variable, not the value — hence late binding (§1.8). And each call to the factory produces independent cells, so two closures from the same factory don't share state, while two closures from the same call do.
Why it matters in practice: closures are how decorators work, how you build configured callables without a class, and how functools.partial-style specialisation is expressed.

            

            
ConceptualClosure or class — when would you pick which?
              
Closure when there's essentially one behaviour and a little configuration: a scaler, a validator, a key function, a decorator. It's less code and there's nothing to name.
Class when there are several related methods over the same state, when the state needs inspecting or serialising, or when the object must fit a framework's protocol — a scikit-learn estimator needs fit, transform, get_params and picklability, and a closure can't provide any of that.
The deciding question: does anything other than “call it” need to happen to this thing? Inspect it, pickle it, subclass it, give it a second method — then use a class. Otherwise a closure is the lighter answer, and reaching for a class reflexively is over-engineering.

            

          

        

      


      

        
3.3 Decorators from scratch ⭐⭐

        
Close to guaranteed. And the answer that scores is not the definition — it is writing one correctly on a whiteboard, functools.wraps included, and explaining what breaks without it.


        
A decorator is a callable that takes a function and returns a replacement. The @ syntax is pure sugar: @deco above def f means exactly f = deco(f).


        

          
Run itdecorator_basics.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: a timing line, the sum 19999900000, then slow_sum / its real docstring / slow_sum again from __wrapped__. The broken version prints wrapper and None — that is exactly what functools.wraps prevents, and it's what breaks tracebacks, help(), Sphinx docs, and any framework that dispatches on __name__. The last block shows the finally still reporting the timing when the function raises.

        


        

          
Likely interview questions

          

            
Very commonWhat is a decorator? Write one.
              
A callable that takes a function and returns a replacement, letting you add behaviour without editing the original. @deco above a def is exactly f = deco(f).
The canonical shape, which you should be able to write from memory:
def timed(fn): → @functools.wraps(fn) → def wrapper(*args, **kwargs): → time it, return fn(*args, **kwargs) in a try with the timing in finally → return wrapper.
Three details that separate a good answer from a passable one: *args, **kwargs so it wraps any signature; functools.wraps so metadata survives; and try/finally so the added behaviour still happens when the wrapped function raises. Mention that a decorator is just a closure over fn — which is why §3.2 comes first.

            

            
GotchaWhat does functools.wraps do, and what breaks without it?
              
It copies the wrapped function's identity onto the wrapper: __name__, __doc__, __module__, __qualname__, __dict__ and __annotations__, and sets __wrapped__ so the original is still reachable.
Without it, every decorated function reports itself as wrapper with no docstring. Concretely that breaks: tracebacks and logs (every frame is “wrapper”, so you can't tell which function failed), help() and generated docs, introspection like inspect.signature, and any framework that dispatches on __name__ — pytest collection, Flask routes, Celery task names, and click commands all misbehave.
It's one line and there is no reason to omit it. Its absence in a code sample is a reliable tell that the author copied the pattern without understanding it.

            

            
Deep diveCan you decorate a class, or use a class as a decorator?
              
Both, yes. A class as a decorator: implement __init__(self, fn) to store the function and __call__(self, *a, **kw) to invoke it. This is the cleaner option when the decorator needs meaningful state — a call counter, a cache with statistics, a circuit breaker — because instance attributes beat nonlocal for anything you want to inspect.
Decorating a class: the decorator receives the class object and returns a class (or the same class, modified). That's how @dataclass and @functools.total_ordering work — they inspect annotations or existing methods and inject generated ones.
The gotcha with class-based decorators: they don't automatically behave like methods, because they lack the descriptor protocol. Decorating an instance method with a class-based decorator loses self binding unless you also implement __get__. That's a real edge case and worth knowing exists.

            

          

        

      


      

        
3.4 Decorators with arguments ⭐

        
Three levels of nesting, and the reason is mechanical: @retry(3) means call retry(3) first, then apply whatever it returns as the decorator.


        

          
Run itdecorator_args.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: two “attempt failed: transient” lines, then succeeded on attempt 3. The desugared line prints ok, showing @retry(times=4) is just retry(times=4)(fn). The final line prints [tagged] plain | [custom] fancy — the fn=None plus partial trick that lets one decorator work both with and without parentheses, which is how most library decorators are written.

        


        

          
Likely interview questions

          

            
CodingWrite a decorator that takes an argument.
              
Three nested levels, and the reason is that @deco(arg) calls deco(arg) and then applies the result as the decorator.
So: outer takes the config and returns a decorator; middle takes the function and returns a wrapper; inner takes the call arguments. def retry(times): → def decorator(fn): → @wraps(fn) def wrapper(*a, **k): → return wrapper → return decorator.
The mistake to avoid, and worth flagging: forgetting the parentheses. @retry on a parameterised decorator passes the function as times, which produces a bizarre error later rather than immediately. The fn=None plus functools.partial pattern makes a decorator work both ways and is what well-written libraries do.

            

          

        

      


      

        
3.5 The four you will actually write ⭐

        
Timing, retry, caching, validation. Between them they cover most real uses in a data pipeline, and each has a subtlety worth knowing.

TimingLog how long a step tookUse try/finally so failures are timed too

              
RetrySurvive a flaky API or DBCatch specific exceptions; add backoff; never retry a 4xx

Likely interview questions

          

            
PracticalWhere have you used a decorator in real work?
              
Have a concrete answer ready — this is a “have you actually done this” probe. Good ones: timing and logging each stage of an ETL so a slow step is obvious in the logs; retry with exponential backoff around a flaky third-party API; caching an expensive reference lookup; and schema validation that fails at the function boundary with a message naming the missing columns.
The last one is the most persuasive because it prevents a whole class of debugging: without it, a missing column surfaces as a KeyError forty lines deep in a transformation, with no indication of which upstream step dropped it.
Also worth mentioning that you'd reach for existing tools before writing your own — tenacity for retries, functools.cache for memoisation, pandera or pydantic for schemas — because knowing when not to hand-roll is part of the answer.

            

            
GotchaWhy can't you @lru_cache a function that takes a DataFrame?
              
Because lru_cache keys the cache on the arguments, which means they must be hashable — and DataFrames, arrays, lists and dicts are not. You get TypeError: unhashable type.
Options, in order of preference: cache on a hashable identifier instead (a file path, a query string, a version tag) and load inside the function; convert to a hashable form at the boundary — a tuple of tuples for small data, or hash the content with pd.util.hash_pandas_object(df).sum(); or use an explicit dict cache keyed on whatever you choose.
The deeper caution: even if you make it hashable, caching on mutable data is dangerous — the frame can change under you while the cache still holds the old result. Caching works best keyed on immutable identifiers, which is usually a sign you should be caching the load, not the transform.

            

          

        

      


      

        
3.6 functools ⭐

        
Five things worth knowing, and one worth avoiding.

Likely interview questions

          

            
Codingcache vs lru_cache — and when is caching wrong?
              
@cache is @lru_cache(maxsize=None) — unbounded, slightly faster, and it will grow forever. @lru_cache(maxsize=n) is bounded and evicts the least recently used entry, which is what you want when the key space is large or unbounded.
Caching is wrong when: the function has side effects (you'll skip them); the underlying data changes (you'll serve stale results, and there's no invalidation hook); arguments are unhashable; the key space is unbounded and you used @cache, which is then a memory leak with a friendly name; or the function is cheap, in which case the cache lookup and the retained memory cost more than recomputing.
Also worth knowing: lru_cache on a method keys on self, so it keeps every instance alive forever — a genuine leak. Use cached_property for per-instance memoisation instead.

            

            
Conceptualpartial vs a lambda?
              
partial(f, a=1) pre-binds arguments and returns a new callable. A lambda does the same thing by hand.
partial is better when it matters: it's picklable (a lambda is not, which breaks multiprocessing and joblib — a very real constraint in data work), it's introspectable (p.func, p.keywords), it has a useful repr, and it avoids the late-binding trap from §1.8 because arguments are bound at creation.
A lambda is fine for a quick inline key function — sorted(rows, key=lambda r: r["score"]) — where none of that applies. But if the callable is going to cross a process boundary or be stored, partial is the right tool.

            

          

        

      


      

        
3.7 Lambdas, and their limits

        
A lambda is an anonymous single-expression function. Useful in exactly one context and over-used in several others.


        
Use one for a short inline callable passed straight to another function: key=, map, a small .apply. Don't use one when you assign it to a name (just write def — you get a real name in tracebacks for free), when it needs more than one expression, or when a built-in already exists: key=lambda x: x[1] is better written key=itemgetter(1), and lambda s: s.lower() is str.lower.


        

          
          Lambdas can't be pickled
          
Which means they break multiprocessing, joblib with a process backend, Dask, and any attempt to save a scikit-learn pipeline containing a FunctionTransformer(lambda …). The error appears at save or fan-out time, far from the lambda. Use a module-level def or functools.partial for anything that might cross a process boundary.

        


        

          
Likely interview questions

          

            
ConceptualWhen should you not use a lambda?
              
Whenever you give it a name. f = lambda x: x + 1 is strictly worse than def f(x): return x + 1 — same length, but the def version gets a real __name__, can carry a docstring, and shows up properly in tracebacks. PEP 8 says this explicitly.
Also avoid them when the logic needs a statement (a try, an assignment, a loop) — a lambda is a single expression, so people contort the logic to fit; when a built-in or operator function already does the job; and when the callable must be picklable for multiprocessing or model serialisation.
The legitimate case is narrow and worth stating so the answer isn't just negative: a short throwaway callable passed directly as an argument, most often key= in a sort.

            

          

        

      


      

        
3.8 Type hints that earn their keep

        
Hints are not enforced at runtime — they're documentation a tool can check. In data code, a small number of them pay for themselves.


        

          
Run ittyping_basics.pyidle

          
          

            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: {'a': 2.0, 'b': 1.0}, then no runtime check: xy — proving hints are ignored at runtime; add("x", "y") happily concatenates strings while a type checker would reject it. Then the resample string, [10, 20, 30], the TypedDict row, and the raw __annotations__ dict.

        


        

          
Likely interview questions

          

            
PracticalDo type hints do anything at runtime?
              
No. Python stores them in __annotations__ and otherwise ignores them — def f(x: int) will happily accept a string. They exist for static checkers (mypy, pyright, ty), editors, and human readers.
Things that do use them at runtime, because it's a natural follow-up: Pydantic and FastAPI read annotations to build validators; dataclasses read them to generate __init__; typing.get_type_hints exposes them. So annotations become enforcement only when a library chooses to act on them.
For data code, the honest position: hint the boundaries — public function signatures, config objects, the shapes crossing module lines — and don't bother annotating every local. The value is a checker in CI catching a None you didn't handle, not decoration.

            

            
ConceptualHow do you usefully type a function that takes a DataFrame?
              
pd.DataFrame as the annotation is honest but nearly contentless — it tells the reader nothing about which columns are required, which is the thing that actually breaks.
Better options, in ascending rigour: document the schema in the docstring and validate at the top of the function (the requires_columns decorator from §3.5 is this, made reusable). Use pandera, which gives you a declarative schema with dtypes, nullability and value ranges, checked at runtime and usable as a type annotation. Or, when the data is small and record-shaped, model rows as a TypedDict or dataclass and build the frame from those, so the schema lives in the type system.
The point to make: with DataFrames the useful contract is the schema, not the Python type, and annotations alone can't express it. Saying that shows you understand the limit of the tool.
