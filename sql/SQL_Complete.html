1.1 The logical order of execution ⭐⭐

The one piece of theory in this whole subject that pays for itself immediately, because it explains three separate error messages you will otherwise memorise as arbitrary rules.

You write a query in one order and the database evaluates it in another. The logical evaluation order is:

#ClauseWhat exists by the end of it
1FROM / JOINThe combined row set. Nothing is filtered yet.
2WHERERows surviving the row-level filter.
3GROUP BYGroups. Individual rows are no longer addressable.
4HAVINGGroups surviving the group-level filter.
5window functionsComputed over the surviving groups/rows.
6SELECTThe output columns — and only now do aliases exist.
7DISTINCTDuplicate output rows removed.
8ORDER BYOrdering. Aliases are available here.
9LIMIT / OFFSETThe final slice.

Three consequences, and they are the whole reason to know this

An alias defined in SELECT cannot be used in WHERE, because WHERE ran at step 2 and the alias was not created until step 6. It can be used in ORDER BY, which runs at step 8. That is not an inconsistency; it is the order.

An aggregate cannot appear in WHERE, because at step 2 no groups exist yet. That is what HAVING is for.

A window function cannot appear in WHERE either, because windows are computed at step 5, after the filter. This is why top-N-per-group needs a subquery or CTE — see §4.9.

Likely interview questions

          

            
Very commonWhat is the order of execution of a SQL query?
              
FROM/JOIN → WHERE → GROUP BY → HAVING → window functions → SELECT → DISTINCT → ORDER BY → LIMIT.
Then immediately say why it matters, because reciting the list is only half the answer: it explains why a SELECT alias works in ORDER BY but not in WHERE, why an aggregate belongs in HAVING rather than WHERE, and why a window function cannot be filtered without wrapping the query.
One precision point that reads well: this is the logical order, which defines semantics. The optimiser is free to execute in any order that produces the same result — it will happily push a predicate below a join or evaluate LIMIT early. So logical order tells you what a query means; the EXPLAIN plan tells you what it does. See §11.1.

            

            
GotchaWhy can I use a column alias in ORDER BY but not in WHERE?
              
Because WHERE is evaluated at step 2 and the alias is not created until SELECT at step 6. ORDER BY is step 8, by which time the alias exists. Same reason GROUP BY in most dialects wants the expression rather than the alias.
Dialect detail worth knowing, because it is exactly the kind of thing that makes a query non-portable: MySQL and SQLite permit the alias in HAVING and GROUP BY as an extension, PostgreSQL allows it in GROUP BY and ORDER BY but not WHERE or HAVING, and SQL Server allows it only in ORDER BY. If you want one query that runs everywhere, repeat the expression or wrap it in a CTE — a CTE is the clean answer, because the alias becomes a real column of the CTE and every clause downstream can use it.

            

            
ConceptualIf the optimiser can reorder things, why learn the logical order at all?
              
Because it is the contract. The optimiser is only permitted to reorder in ways that preserve the result as defined by the logical order, so the logical order is what makes a query's meaning unambiguous.
It also predicts your error messages, which is the practical payoff. Every “column does not exist” and “aggregate functions are not allowed in WHERE” is the logical order telling you that the thing you referenced had not been created yet.
Where the distinction genuinely bites: LEFT JOIN plus a WHERE filter on the right table. Logically the join happens first and produces NULLs, then WHERE discards them — which silently turns the outer join into an inner one. Understanding that as an ordering consequence rather than a mystery is the whole of §2.2.

            

          

        

      


      

        
1.2 SELECT, WHERE, ORDER BY and the LIMIT trap

        
Ninety percent of the syntax, and one genuine trap that shows up in the most-asked question in SQL interviewing.


        
Things worth being precise about

        
ORDER BY without a total order is non-deterministic. If you sort by a column with ties and take LIMIT 3, which of the tied rows you get is up to the engine, and it can change between runs, between versions, and between a table scan and an index scan. Any time the result must be stable, add a tie-break column — usually a unique id. This is the single most common source of “the test passed locally and failed in CI”.

        
LIMIT without ORDER BY returns arbitrary rows, not the “first” ones. There is no first row in a relation.

        
OFFSET counts rows, not distinct values. This is why LIMIT 1 OFFSET 1 is the wrong answer to “second highest salary” whenever the highest salary is shared — the topic of §4.4, and the demo table is built so you can see it fail.

Likely interview questions

          

            
GotchaIs SELECT ... LIMIT 10 deterministic?
              
No, on two counts. Without ORDER BY the ten rows are whatever the engine finds first, which depends on the plan, the storage layout and prior updates. And with ORDER BY it is still non-deterministic if the sort key has ties, because nothing specifies which of the tied rows wins.
The fix is a total order: append a unique column to the sort key, e.g. ORDER BY salary DESC, id. Volunteering this unprompted is a small, cheap credibility win, and it is the correct answer to “why does this test flake?”
Related trap worth naming: deep OFFSET is slow. LIMIT 20 OFFSET 100000 makes the engine produce and discard 100,000 rows. For pagination at scale you want keyset pagination — WHERE id > :last_seen ORDER BY id LIMIT 20 — which uses the index and stays O(page) rather than O(offset).

            

            
Very commonHow do you get the top 5 rows in each of several dialects?
              
PostgreSQL, MySQL, SQLite, BigQuery, Snowflake, DuckDB: LIMIT 5. SQL Server: SELECT TOP 5, or OFFSET 0 ROWS FETCH NEXT 5 ROWS ONLY. Oracle 12c+: FETCH FIRST 5 ROWS ONLY; older Oracle used WHERE ROWNUM <= 5, which is worth knowing because it applies before ordering and therefore breaks in exactly the way people expect LIMIT to work.
The interviewer usually asks this to find out whether you have used more than one database. A good answer names the standard form — FETCH FIRST n ROWS ONLY is the ANSI spelling — and then says which dialect you actually work in.

            

          

        

      


      

        
1.3 The three COUNTs ⭐

        
A one-line question that eliminates a surprising number of candidates, because the three forms differ only on NULLs and duplicates — and every real table has both.


        

          
COUNT(*)
Counts rows. Never looks at any value, so NULLs are counted. This is the row count of the group.

          
COUNT(col)
Counts rows where col IS NOT NULL. Silently smaller than COUNT(*) whenever the column is nullable.

          
COUNT(DISTINCT col)
Counts distinct non-NULL values. NULL is not a value, so it never contributes.

Likely interview questions

          

            
Very commonDifference between COUNT(*), COUNT(1) and COUNT(col)?
              
COUNT(*) counts rows. COUNT(1) counts rows too and is identical — the argument is a non-null constant, so it can never be skipped; every modern optimiser treats the two the same and any claim that one is faster is folklore. COUNT(col) counts rows where col is not NULL.
So the real content of the question is: do you know that COUNT(col) silently ignores NULLs? That is what makes it a filter in disguise, and it is why a “total orders” number can come out lower than expected when someone counts a nullable column instead of counting rows.
Two extras that land well. COUNT(DISTINCT a, b) counts distinct pairs in MySQL, and the portable version is COUNT(DISTINCT a || '-' || b) with a separator that cannot appear in the data — or better, count over a subquery. And on a large table COUNT(DISTINCT ...) is expensive because it needs to deduplicate; engines offer approximate versions (APPROX_COUNT_DISTINCT, HLL) that trade a percent or so of accuracy for a large speed-up.

            

            
GotchaWhy is my COUNT lower than the row count?
              
Almost always because you counted a nullable column. COUNT(*) - COUNT(col) gives you exactly how many rows were dropped, and that is the first thing to run.
The other two causes, in order of frequency: a JOIN that lost rows because it was an INNER JOIN where you wanted LEFT (or a LEFT JOIN demoted by a WHERE — §2.2), and a DISTINCT you forgot was there.
The habit worth having: after any aggregation, run an assertion that the total is conserved. SELECT COUNT(*) FROM base against SELECT SUM(n) FROM result. §10.7 makes the case for this properly, and volunteering it in an interview reads as someone who has been burned in production.

            

            
CodingCount how many employees each department has, including departments with none.
              
The point of this question is the combination of two things you have to get right together: a LEFT JOIN from departments, and COUNT(e.id) rather than COUNT(*).
SELECT d.name, COUNT(e.id) AS n FROM departments d LEFT JOIN employees e ON e.dept_id = d.id GROUP BY d.name
COUNT(*) would return 1 for the empty department, because the outer join manufactures one all-NULL row and COUNT(*) counts it. COUNT(e.id) returns 0, which is the answer anyone actually wants. This is the cleanest possible demonstration that the difference between the two COUNTs is not academic — try both in the cell in §2.1.

            

          

        

      


      

        
1.4 GROUP BY, properly ⭐

        
The rule is simple and the dialects disagree about how strictly to enforce it — which is exactly why it gets asked.


        
The rule: every column in SELECT must either appear in GROUP BY or be wrapped in an aggregate. The reason is not pedantry — after grouping, individual rows no longer exist, so an ungrouped, unaggregated column has no single value to report.


        
The dialect split. PostgreSQL and SQL Server reject the violation outright. MySQL historically returned an arbitrary row's value, silently, which produced a decade of wrong dashboards; since 5.7 ONLY_FULL_GROUP_BY is on by default and it errors like everyone else. SQLite still allows it and picks an arbitrary row — which you can watch happen in the cell below. That freedom is occasionally useful and mostly a hazard.


        

          
          “The name of the highest earner per department” is not a GROUP BY problem
          
The instinct is SELECT dept_id, name, MAX(salary) ... GROUP BY dept_id. In PostgreSQL that is an error; in MySQL's loose mode it returns a name from an arbitrary row alongside the correct maximum, so the two columns can describe different people. There is no general fix with GROUP BY alone — you need a window function (§4.5) or a correlated filter. Recognising that the question is asking for a row, not an aggregate, is the actual skill.

Likely interview questions

          

            
Very commonWhat is the rule for what can appear in SELECT alongside a GROUP BY?
              
Every selected expression must be either in the GROUP BY list or inside an aggregate. Grouping collapses rows, so any column not covered by one of those two has no defined single value.
The exception worth naming: functional dependency. PostgreSQL will accept SELECT d.id, d.name ... GROUP BY d.id when d.id is the primary key, because name is then uniquely determined by the grouping key. That is standard-compliant and genuinely handy; not every engine implements it.
The trap it protects you from is MySQL's old default, which returned an arbitrary value instead of an error. If you are ever asked why ONLY_FULL_GROUP_BY exists, that is the answer: silently plausible wrong numbers are worse than a failed query.

            

            
Very commonGet the name of the highest-paid employee in each department.
              
This is not a GROUP BY question, and saying so is most of the answer. MAX(salary) gives you a value; you were asked for a row.
Window function, which is the answer to give: rank within each department and filter to rank 1. SELECT dept_id, name, salary FROM (SELECT *, RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) r FROM employees) t WHERE r = 1.
Then handle ties out loud, because it is the follow-up: RANK returns all tied top earners, ROW_NUMBER returns exactly one arbitrarily. Which you want is a requirements question. If they want exactly one deterministically, add a tie-break to the ORDER BY — ORDER BY salary DESC, hire_date, id.
The alternative without windows, worth knowing for “no window functions” constraints: join back to the per-department maximum. JOIN (SELECT dept_id, MAX(salary) ms FROM employees GROUP BY dept_id) m ON e.dept_id = m.dept_id AND e.salary = m.ms. Same tie behaviour as RANK.

            

            
GotchaDoes GROUP BY put NULLs in their own group?
              
Yes. GROUP BY treats all NULLs as one group, even though NULL = NULL is not true. That is a deliberate exception in the standard: grouping, DISTINCT, UNION and ORDER BY all use “not distinct from” semantics rather than equality.
So the demo query in this section returns a group for dept_id = NULL containing Kabir. That is usually what you want, but it means a “per department” report can contain an unlabelled row, and if you later join that result to departments you will lose it. The habit: either COALESCE(dept_id, -1) into an explicit “unassigned” bucket, or filter deliberately and say why.
Contrast this with aggregates, which do skip NULLs — AVG(salary) divides by the count of non-nulls. Grouping keeps NULLs together; aggregating throws them away. Two different rules in the same query, and §1.7 covers the second one.

            

          

        

      


      

        
1.5 WHERE vs HAVING vs QUALIFY ⭐

        
Three filters at three different stages. Knowing which stage each one runs at means you never guess.


        

          
WHERE — step 2
Filters rows, before grouping. Cannot see aggregates or window functions. Cheapest filter: it reduces what everything downstream has to process.

          
HAVING — step 4
Filters groups, after aggregation. This is the only place an aggregate can be filtered.

          
QUALIFY — step 5+
Filters on a window function result. Snowflake, BigQuery, Teradata and DuckDB have it; PostgreSQL, MySQL, SQL Server and SQLite do not — wrap in a subquery instead.

        


        
The performance point, if they ask: put a condition in WHERE whenever it does not depend on an aggregate, because filtering before grouping means fewer rows to group. A condition that belongs in WHERE but is written in HAVING is usually still correct — the optimiser often pushes it down — but it reads as not knowing the difference.

Likely interview questions

          

            
Very commonWHERE vs HAVING — when must you use each?
              
WHERE filters rows before grouping; HAVING filters groups after aggregating. You must use HAVING when the condition involves an aggregate, because at WHERE time no groups exist yet. You should use WHERE for everything else, because fewer rows reach the grouping step.
The example that makes it concrete: “customers with more than three completed orders” needs WHERE status = 'completed' (a row property) and HAVING COUNT(*) > 3 (a group property). Putting the status test in HAVING would be a different question, and putting the count test in WHERE is an error.
Two things worth adding. HAVING without GROUP BY is legal — the whole result is one group — so SELECT SUM(amount) FROM orders HAVING SUM(amount) > 0 works. And for filtering on a window function you need neither: that is QUALIFY where it exists, and a subquery everywhere else.

            

            
ConceptualWhat is QUALIFY and why should I care if my database lacks it?
              
QUALIFY is to window functions what HAVING is to aggregates: a filter that runs after the window is computed. SELECT ... QUALIFY ROW_NUMBER() OVER (PARTITION BY user ORDER BY ts DESC) = 1 is the whole of “latest row per user” in one statement.
It exists in Snowflake, BigQuery, Teradata, Databricks and DuckDB. It is not in PostgreSQL, MySQL, SQL Server or SQLite, where you wrap the query and filter in the outer WHERE.
Why care either way: it is a useful marker of which warehouses you have actually used, and the wrapped-subquery form is the portable idiom you should default to. Writing QUALIFY in a Postgres interview is a small tell; knowing it exists and saying “on Snowflake I'd use QUALIFY, here I'll wrap it” is the opposite.

In several places, which is the genuinely confusing part — the “NULL is never equal to NULL” rule applies to comparison, and a different rule applies to grouping.
Treated as equal (one group / one value): GROUP BY, DISTINCT, UNION, INTERSECT, EXCEPT, ORDER BY and window PARTITION BY. All use “not distinct from” semantics.
Treated as unknown: WHERE, ON, HAVING, CHECK, and IN/NOT IN.
Skipped entirely: aggregates other than COUNT(*).
Depends: a UNIQUE constraint permits multiple NULLs in most engines (they are not equal, so not duplicates) — but SQL Server allows only one, and PostgreSQL 15 added NULLS NOT DISTINCT to opt into the stricter behaviour. And sort position differs: PostgreSQL puts NULLs last ascending, MySQL and SQLite put them first, which is why NULLS FIRST/NULLS LAST exists.

            

            
CodingCount rows where a nullable flag is not 'yes'.
              
The trap: WHERE flag <> 'yes' excludes the NULLs, so if “not yes” is meant to include “unknown” the count is too low. You have to decide what NULL means in this question and then write it explicitly.
If unknown counts as not-yes: WHERE flag IS DISTINCT FROM 'yes', or portably WHERE flag <> 'yes' OR flag IS NULL, or WHERE COALESCE(flag, '') <> 'yes'.
If unknown is a third category: keep three buckets and report them separately — which is usually the honest answer, and the one to suggest.
This is worth practising because it is the shape of a real interview follow-up: the interviewer adds a NULL to the sample data and asks you to re-run. The candidate who asks “how should I treat unknown here?” before writing anything is the one who passes.

            

          

        

      


      

        
1.7 NULLs inside aggregates ⭐

        
Aggregates skip NULLs. That single sentence has three consequences, and one of them is an AVG that quietly answers a different question than the one asked.


        
Every aggregate except COUNT(*) ignores NULLs. So AVG(col) is SUM(col) / COUNT(col), dividing by the number of non-null values — not by the number of rows. If missing means zero in your domain, AVG is wrong and you want SUM(col) / COUNT(*), or AVG(COALESCE(col, 0)).

        
SUM of an empty set is NULL, not zero. A SUM over zero matching rows returns NULL, which then propagates through any arithmetic downstream. Wrap it: COALESCE(SUM(x), 0). COUNT is the exception — it returns 0.

This exact pair — a phantom 1 and a NULL where you wanted 0 — is one of the most common bugs in reporting SQL, and it is why “count customers with zero orders” is a good interview question: it tests the join direction, the COUNT argument and the COALESCE all at once.

            

          

        

      


      

        
1.8 COALESCE, NULLIF and safe division

        
Three small functions that between them prevent most NULL-related and divide-by-zero incidents.


        
COALESCE(a, b, c, ...) returns the first non-null argument. Standard, variadic, everywhere. IFNULL (MySQL, SQLite) and ISNULL (SQL Server) are two-argument dialect versions of the same idea — prefer COALESCE, it is portable.

        
NULLIF(a, b) returns NULL if a = b, else a. Its one killer use is safe division: x / NULLIF(y, 0) turns a would-be divide-by-zero into NULL, which is almost always the honest answer. It is also the neat way to convert a sentinel — NULLIF(status, 'unknown') — into a real NULL.

MySQL and SQLite are more forgiving, which is exactly why the bug survives a local test and appears in production. §10.5 covers it properly.

One real difference beyond portability: in SQL Server, ISNULL forces the result to the data type of the first argument, so ISNULL(short_varchar_col, 'a long default') silently truncates. COALESCE uses standard type-precedence rules instead. That is a genuine correctness difference, not just style, and it is the reason to prefer COALESCE even on SQL Server.
COALESCE also short-circuits left to right, so COALESCE(cheap_col, expensive_subquery) avoids the subquery when the first value is present — though not every planner guarantees that, so do not rely on it for correctness.

            

          

        

      


      

        
1.9 DISTINCT vs GROUP BY

        
For deduplication they are equivalent. The interesting answer is about when they are not, and about why SELECT DISTINCT is often a smell.


        
SELECT DISTINCT a, b FROM t and SELECT a, b FROM t GROUP BY a, b return the same rows, and on any modern optimiser they usually produce the same plan. GROUP BY is strictly more capable, because you can attach aggregates to it; DISTINCT cannot.


        

          
Use DISTINCT when
You genuinely want unique rows and no aggregation. It reads better than an empty GROUP BY.

          
Suspect DISTINCT when
You added it to make duplicate rows go away. That usually means a join fanned out (§2.6) and you are now hiding a modelling error rather than fixing it.

        


        
The point to make in an interview: DISTINCT applied to a whole SELECT list is a blunt instrument. If a join produced duplicates, deduplicating the output can still be wrong — a customer with two matching addresses will collapse correctly, but a SUM computed over the fanned-out rows was already double-counted before DISTINCT ever ran. Fix the join; do not sand down the symptom.

Worse, if the duplicated rows differ in any column, DISTINCT keeps them all and you have hidden nothing.
So the correct reflex when you feel the urge to add DISTINCT is to ask where the duplicates came from: is the join key non-unique on the right side, is there a genuine many-to-many needing an aggregate-then-join, or was a LEFT JOIN the wrong shape? Saying that in an interview is a much stronger answer than the syntax. §2.6 is the full treatment.

2.2 The LEFT JOIN + WHERE trap ⭐⭐

        
The most common semantic bug in production SQL, and one of the most reliable interview filters. The query runs, returns plausible rows, and has silently become an inner join.


        
Recall the execution order from §1.1: the join runs at step 1 and produces NULLs for unmatched rows; WHERE runs at step 2 and evaluates its predicate against those NULLs. Any comparison with NULL is UNKNOWN, WHERE keeps only TRUE — so every manufactured row is discarded and the outer join is undone.


        

          
Demoted to INNER
FROM a LEFT JOIN b ON b.a_id = a.id
WHERE b.status = 'x'

Rows of a with no b have b.status = NULL, which fails the test. They vanish.

          
Still an outer join
FROM a LEFT JOIN b ON b.a_id = a.id
  AND b.status = 'x'

The condition restricts what counts as a match. Unmatched rows of a survive with NULLs.

        


        
The exception that is also the fix: WHERE b.id IS NULL is a perfectly good thing to put in WHERE after a LEFT JOIN — it is how you write an anti-join. The rule is not “never filter the right table in WHERE”; it is “a WHERE predicate on the right table must be null-aware, or you have chosen an inner join by accident”.

The performance point that is real: filters on the driving table should be as selective as possible and are best expressed in WHERE, because that gives the planner the clearest opportunity to reduce the row set before the join. And a filter that could apply to either side of an inner join is worth writing on the larger table, since that is where eliminating rows saves the most work. 2.4 Anti-joins, and why NOT IN breaks on NULL ⭐⭐

        
Three ways to write “rows in A with no match in B”, one of which returns zero rows the moment a single NULL appears. This is asked constantly, and the reason is pure three-valued logic.


        
Why NOT IN collapses

        
x NOT IN (1, 2, NULL) expands to x <> 1 AND x <> 2 AND x <> NULL. That last term is UNKNOWN for every x, and TRUE AND UNKNOWN is UNKNOWN — so the whole predicate can never be TRUE, and WHERE keeps nothing. One NULL in the subquery annihilates the entire result set. No error, no warning, just an empty answer.

        
Note the asymmetry precisely, because the usual shorthand is slightly wrong. IN is also three-valued: with no match and a NULL present it returns UNKNOWN, not FALSE. The difference is that inside a WHERE clause UNKNOWN and FALSE have the same effect — the row is dropped — and for IN that is the outcome you wanted. A genuine match still returns TRUE and wins. So IN is safe in practice; NOT IN is not, because there the dropped row is the answer.


        

          
NOT EXISTS
Correct with NULLs. Row-by-row existence test, short-circuits, usually the best plan. Default to this.

          
LEFT JOIN ... IS NULL
Correct. The classic anti-join, and often the fastest on older engines. Slightly more to read.

          
NOT IN
Correct only if the subquery column can never be NULL. Add WHERE col IS NOT NULL or do not use it.

So IN is not immune to NULL either — it just does not matter, because inside WHERE both UNKNOWN and FALSE drop the row, which is what you wanted anyway. With NOT IN, UNKNOWN also drops the row — and there it is exactly what you did not want. That asymmetry, not immunity, is the real explanation.

        


        

          
Likely interview questions

          

            
Very commonWrite an anti-join three ways. Which do you prefer?
              
NOT EXISTS — SELECT * FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.k = a.k). Correct with NULLs, expresses intent directly, and modern optimisers turn it into a hash anti-join.
LEFT JOIN + IS NULL — FROM a LEFT JOIN b ON b.k = a.k WHERE b.k IS NULL. Also correct. Historically the fastest on MySQL, and still what many optimisers produce internally.
NOT IN — correct only when the subquery column is guaranteed non-null.
My preference is NOT EXISTS, for three reasons worth saying: it is null-safe by construction, it reads as the requirement, and it does not risk someone later adding a SELECT column that turns the anti-join into a fan-out. Also mention EXCEPT as a fourth option when you are comparing whole key lists rather than filtering a table.

            

            
GotchaWhy does NOT IN with a subquery return no rows?
              
Because the subquery produced at least one NULL. x NOT IN (a, b, NULL) is x <> a AND x <> b AND x <> NULL, and the final term is UNKNOWN for every possible x. Since TRUE AND UNKNOWN is UNKNOWN and WHERE keeps only TRUE, the result is empty regardless of the data.
Then state the asymmetry precisely, because the common shorthand “IN is unaffected” is not quite right. IN is three-valued too: with no match and a NULL in the list it returns UNKNOWN, not FALSE. It is harmless only because WHERE discards UNKNOWN and FALSE alike, and for the positive test that is the right outcome. A genuine match still yields TRUE and wins. With NOT IN, the discarded UNKNOWN rows are the answer, which is why only the negation is dangerous.
Fixes, in order of preference: use NOT EXISTS; or add WHERE col IS NOT NULL inside the subquery; or make the column NOT NULL in the schema if that is the truth. There is also a performance angle — some optimisers cannot convert a NOT IN over a nullable column into an anti-join at all, precisely because of these semantics, so it can be both wrong and slow.

            

            
ConceptualIs NOT EXISTS always faster than NOT IN?
              
Not always, and claiming so is a weaker answer than explaining the asymmetry. On PostgreSQL and SQL Server the two usually produce the same anti-join plan when the column is NOT NULL, because then the semantics coincide and the optimiser is free to rewrite.
Where NOT EXISTS wins is on a nullable column: the NOT IN semantics force the engine to evaluate the whole subquery and handle the three-valued case, which blocks the anti-join rewrite. So the honest answer is “they are usually equivalent on non-nullable keys, and NOT EXISTS is both correct and better-optimised on nullable ones, which is why I default to it”.
One more: NOT EXISTS can short-circuit per outer row, which matters when the inner table is large and indexed on the join key. NOT IN with an uncorrelated subquery may materialise the whole list first.

            

          

        

      


      

        
2.5 Semi-joins: EXISTS vs IN vs JOIN + DISTINCT ⭐

        
“Rows in A that have at least one match in B” — three spellings again, and here the difference is about row multiplication rather than NULLs.


        
EXISTS is a semi-join: it asks “is there at least one?” and stops at the first hit. It never duplicates a left row, whatever the cardinality on the right. IN with a subquery is the same thing semantically. A plain JOIN is not — it returns one row per match, so a customer with four orders appears four times, and people then paper over it with DISTINCT.

        
The rule: if you only need existence, use EXISTS. Reach for a join when you actually want columns from the right table. Reaching for JOIN ... DISTINCT to answer an existence question is the smell described in §1.9.

Likely interview questions

          

            
Very commonEXISTS vs IN vs JOIN — when do you use each?
              
EXISTS for an existence test. It is a semi-join: at most one output row per left row, regardless of how many matches exist, and it can stop scanning at the first hit.
IN for the same test against a small, known list or a non-null subquery. Semantically equivalent to EXISTS for the positive case; only the negation differs (§2.4).
JOIN when you need columns from the other table. Accept that it multiplies rows and handle that deliberately — aggregate, or deduplicate on a key you can justify.

On modern PostgreSQL, SQL Server and MySQL 8 the optimiser rewrites both to the same semi-join, so the real reasons to choose are correctness on NULLs and readability. A candidate who says “they're usually the same plan now; I choose on clarity” sounds current.

            

            
CodingCustomers who ordered both a hardware and a software product.

Group and count distinct: filter to the two categories, group by customer, and require COUNT(DISTINCT p.category) = 2. This is the one to write; it generalises to N categories by changing one number.
Two EXISTS clauses: one per category, ANDed together. Very readable, and the most efficient when the categories are highly selective and indexed.
INTERSECT: the set of customers who bought hardware intersected with those who bought software. Elegant, and the natural answer if the interviewer just covered set operators.
The follow-up to expect is “now hardware but not software”, which is the group-and-count version with COUNT(DISTINCT ...) = 1 plus a MAX(category) check, or cleanly an EXISTS plus a NOT EXISTS.

            

          

        

      


      

        
2.6 Fan-out: the join that doubles your revenue ⭐⭐

        
The most expensive join bug there is, because it does not lose data — it invents it, and the resulting number is plausible enough to reach a slide.

          The rule that prevents it
          
Never aggregate a column from the “one” side after joining to the “many” side. Either aggregate the many-side first and join the result (one row per key, so no fan-out), or aggregate over a key that survives the multiplication — SUM(items.qty * items.price) is safe because those columns belong to the many side. The general fix is aggregate first, join second.

Likely interview questions

          

            
Very commonYour revenue number doubled after adding a join. What happened?
              
Fan-out. You joined a one-side table to a many-side table, so each parent row is repeated once per child, and the parent's amount is now summed once per child. An order with three line items contributes its total three times.
Diagnose it in one query: compare COUNT(*) before and after the join. If the count grew, every aggregate over parent columns is now inflated by exactly that factor, per group.
Fixes, in order of preference. Aggregate first, then join — collapse the many side to one row per key in a subquery or CTE, then join. Aggregate only many-side columns — SUM(qty * price) is fine because both live on the child. SUM(DISTINCT ...) exists but is a trap: it deduplicates by value, so two genuinely different orders that happen to bill the same amount get collapsed into one. Mention it and reject it.
And the habit: after any join, assert that the total is conserved. §10.7.

            

            
GotchaCan an INNER JOIN return more rows than either input table?
              
Yes, and this is a genuinely good question because so many people describe joins as filters. If the join key is non-unique on both sides, the output for that key is the product of the multiplicities: three matching rows on the left and four on the right produce twelve rows.
That is a many-to-many join, and it is almost always a modelling error rather than an intention. If the key really is many-to-many, you need a bridge table or you need to aggregate one side before joining.
The practical check to volunteer: before joining, verify uniqueness of the intended key on at least one side — SELECT k, COUNT(*) FROM t GROUP BY k HAVING COUNT(*) > 1. If it returns rows, you have a fan-out waiting to happen, and knowing that before writing the join is the difference between an hour and a week.

Usually a bug. Occasionally the only correct tool — and knowing the second case is what separates “never use it” from a real answer.

2.9 Range joins and the as-of join ⭐

        
Joining on BETWEEN rather than =. This is how you attach a value that was true at the time, and it is the single most important join for anyone doing modelling work.


        
Range join: the condition is an interval containment rather than equality — bucketing an amount into a band, or matching a row to the version of a dimension that was valid on its date. As-of join: a range join against a history table where you want the most recent record not later than the event. Both matter because a naive equality join to a dimension table gives you today's attribute, not the one in force when the fact happened.


        

          
          Why this is the join that matters for modelling
          
If you train a model on features joined from a dimension table by key alone, every row gets the attribute's current value — including rows from two years ago. That is look-ahead leakage, and it is invisible in the SQL. The as-of join is the fix: join on the key and the validity window. Interviewers with an ML background ask this specifically, and it is the SQL half of the point-in-time discussion in §6.10.

        


        
Half-open intervals, always. Store and compare validity windows as valid_from <= t AND t < valid_to. Using <= on both ends makes the boundary instant belong to two rows, so a row-per-event join silently doubles. The half-open convention [from, to) makes adjacent periods tile perfectly with no overlap and no gap.

Very commonYou have a fact table and a slowly-changing dimension. How do you join them correctly?
              
Join on the business key and the validity window: ON f.key = d.key AND f.event_date >= d.valid_from AND f.event_date < d.valid_to. That returns the version of the dimension row that was in force when the fact occurred.
Say why the naive join is wrong, because that is the substance: joining on the key alone either multiplies the fact by every historical version of the dimension, or — if you also filter WHERE d.is_current = 1 — attaches today's attributes to a two-year-old event. The second is worse, because it produces exactly one row per fact and therefore looks correct.
Two details that mark experience. Use half-open intervals [from, to), so adjacent versions tile without overlapping; with BETWEEN on both ends the boundary date matches two versions and the fact is duplicated. And set the open-ended valid_to to a sentinel like '9999-12-31' rather than NULL, because NULL fails the comparison and silently drops the current version — or handle it with COALESCE(valid_to, '9999-12-31').
If the engine has a native as-of join — DuckDB's ASOF JOIN, ClickHouse's ASOF, or LATERAL plus ORDER BY ... LIMIT 1 in PostgreSQL — say so; range joins are expensive and the specialised operator is far faster.

            

            
GotchaWhy are range joins slow, and what do you do about it?
              
Because an inequality cannot be satisfied by a hash join. Hash joins need equality to build a hash key, so a pure range condition falls back to a nested loop — every left row scanned against a range of right rows — which is quadratic in the worst case.
Mitigations, roughly in order of impact. Add an equality predicate if one exists (the business key, a tenant id, a date bucket): the planner can hash on that and only apply the range test within each bucket. Index the range column so the inner side is a seek rather than a scan. Bucket both sides to a coarse grain — join on the month and then filter the exact range — which turns most of the work into an equality join.
And use the purpose-built operator where it exists: PostgreSQL has range types with GiST indexes, DuckDB and ClickHouse have ASOF JOIN, and Spark has range-join hints with a configurable bin size. Knowing that a range join is a known-hard operator with dedicated support, rather than just “slow SQL”, is the answer that lands.

            

          

        

      


      

        
2.10 Composite-key joins

        
Joining on more than one column. Simple, except for two failure modes that are both silent.


        
Failure one: a forgotten key column. Joining daily metrics on date alone when the grain is (date, region) produces a fan-out by the number of regions. The output row count is a clean multiple of the input, which is why comparing counts before and after every join catches it immediately.

        
Failure two: a NULL in one of the key columns. Composite equality means every column must match, and NULL = NULL is UNKNOWN, so a row with a NULL in any key component matches nothing. If the key is legitimately optional, join with IS NOT DISTINCT FROM (PostgreSQL) or COALESCE both sides to a sentinel — and note in a comment that you did, because it is a semantic choice.


        
USING and natural joins. JOIN ... USING (a, b) is shorthand when the columns are identically named, and it collapses them into one output column. NATURAL JOIN goes further and joins on every identically-named column — which is why you should never use it: adding an unrelated updated_at column to both tables silently changes the join key and the result. Say that if asked; it is a good instinct to display.

GotchaWhy should you avoid NATURAL JOIN?

Nothing in the query text changed and nothing errors.

Its one wrinkle is that you can no longer qualify the joined column as t.a in some engines, since it belongs to neither table.
Explicit ON is what I would write in anything long-lived: it is verbose, and being verbose about the join key is the point.

3.2 Correlated subqueries, and what they cost ⭐

        
A subquery that references the outer row. Conceptually a loop, which is both why it is expressive and why it has a reputation.


        
WHERE e.salary > (SELECT AVG(salary) FROM employees x WHERE x.dept_id = e.dept_id) cannot be evaluated once — it depends on e.dept_id, so logically it runs per outer row. That is O(n·m) in the naive execution model, and it is where “correlated subqueries are slow” comes from.

        
The modern correction: optimisers decorrelate. PostgreSQL and SQL Server will often rewrite a correlated aggregate into a join against a grouped derived table, giving you the same plan you would have written by hand. So the honest answer is “it may be fine, and I would check the plan” rather than a blanket condemnation. Very commonWhat is a correlated subquery, and are they slow?

On whether they are slow, give the calibrated answer rather than the folklore. Historically yes, because the naive execution is a nested loop, O(outer × inner). 3.3 CTEs vs subqueries vs temp tables ⭐

        
Mostly a readability decision, with two real technical differences worth knowing.


        

          
Derived table
Inline, in FROM. Fine for one use. Nesting three deep is where queries become unreadable.

          
CTE (WITH)
Named, top-down, reusable within the query, and the only way to recurse. Default to this.

          
Temp table
Materialised, can be indexed, survives across statements. For genuinely expensive intermediates reused many times.

        


        
Difference one: materialisation. A CTE referenced twice may be computed twice — it is a name, not necessarily a cached result. PostgreSQL before v12 always materialised CTEs (an optimisation fence); since v12 it inlines them when referenced once, and you can force either behaviour with MATERIALIZED / NOT MATERIALIZED. That history matters because a lot of tuning advice on the internet is about the pre-12 behaviour.

        
Difference two: statistics. A temp table can be analysed and indexed, so the planner has real statistics for it. A CTE gets estimates. For a multi-step pipeline where one intermediate is large and reused, materialising into a temp table and indexing the join key is sometimes an order of magnitude faster — and that is a good answer to “how would you speed up this 200-line query”.

Likely interview questions

          

            
Very commonCTE vs subquery — when do you use which?
              
Readability first: a CTE names the intermediate result, reads top-down, can be referenced more than once, and can be selected from in isolation while debugging. A derived subquery is fine for a single simple use. Beyond two levels of nesting, CTEs win decisively.

If an intermediate is expensive and reused several times, the real answer may be a temp table you can index — which is also the answer to “this 300-line query times out”.

            

          

        

      


      

        
3.4 Recursive CTEs ⭐

        
The only iterative construct in standard SQL. Three parts, one termination condition, and two problems it solves that nothing else can.


        
The anatomy: an anchor query producing the starting rows; UNION ALL; a recursive query that references the CTE itself and consumes the rows the previous iteration produced; and a condition that eventually yields no new rows, which is what terminates it.

        
Two uses, and they cover nearly everything. Hierarchy traversal — walk an employee-manager or category-parent tree to arbitrary depth, accumulating a depth counter and a path string. Sequence generation — produce a run of dates or integers that does not exist in any table, which is how you build the date spine in §6.3 on engines without generate_series.


        

          
          Infinite recursion is a data problem, not a syntax one
          
A cycle in the hierarchy — A reports to B reports to A, which happens in real org tables — makes the recursion never terminate. Guard it: carry the path and add WHERE path NOT LIKE '%' || e.name || '%', or carry a depth counter and cap it. SQL Server has MAXRECURSION (default 100), PostgreSQL and SQLite have no default limit and will happily run until they exhaust memory. Volunteering the cycle guard is a strong signal.

3.5 Aggregating an aggregate ⭐

        
“The average order value per customer” and “the average customer's order value” are different numbers. Recognising two-level aggregation in a question is a real skill and it is tested constantly.


        
You cannot nest aggregates directly — AVG(SUM(x)) is a syntax error, because SUM already collapsed the rows. You need two levels: a subquery or CTE that groups at the finer grain, then an outer aggregate over that result.


        

          
Average of all orders
AVG(amount) over the raw table. Every order weighted equally, so a customer with 20 orders dominates.

          
Average per customer
Sum per customer, then average those. Every customer weighted equally. Usually what a stakeholder means.

        


        
The interview move: when a question contains “average of a total”, “count of a count”, “the median customer” or “per user per day”, say out loud “this is two levels of aggregation — what is the grain of the inner one?” That sentence is worth more than the query, because ambiguity about grain is where the wrong answer comes from.

Likely interview questions

          

            
Very commonWhat is the average number of orders per customer?
              
Ask one clarifying question first, because there are two answers and they differ by a lot: per customer who has ordered, or per customer on the books (including those with zero)? The second requires a LEFT JOIN from customers so the zeros are in the denominator.

GotchaWhy can't you write AVG(SUM(x))?
              
Because SUM(x) has already collapsed the rows of the group into one value, so there is no set left for AVG to average. Aggregates operate on rows, and after the first aggregate there is one row per group. Engines reject it as “aggregate function calls cannot be nested”.
The fix is two levels: group at the fine grain in a subquery or CTE, then aggregate that result. Which is the whole point of the section — the syntax error is the language telling you the question has two grains.
The one place nesting is legal and looks like an exception: an aggregate inside a window function's argument. SUM(SUM(amount)) OVER () is valid, because the inner SUM is the group aggregate and the outer is a window over the grouped rows. That is the trick behind percent-of-total in one query, and it is §3.6.

ORDER BY defines the sequence, which ranking, LAG/LEAD and running totals all need. It is unrelated to the query's final ORDER BY; you can order the window one way and the output another.

        
The frame restricts which rows within the partition the function sees. Adding ORDER BY to an aggregate window silently changes the default frame from the whole partition to everything up to the current row — which is what turns SUM into a running total, and is the source of the tie bug in §5.2.

Likely interview questions

          

            
Very commonWhat is a window function?
              
A function that computes across a set of rows related to the current row, without collapsing them. That last clause is the definition — an aggregate returns one row per group, a window function returns one value per row while still seeing the whole group.
That is why you can show a salary next to its department average on the same line, which is impossible with GROUP BY alone without a join back.
Give the three components — PARTITION BY, ORDER BY, frame — and note where they run: after WHERE, GROUP BY and HAVING, before SELECT. Two consequences follow immediately and both get asked: you cannot filter on a window result in WHERE (§4.9), and a window function can take a grouped aggregate as its argument (§3.6).

            

            
GotchaWhat is the difference between PARTITION BY and GROUP BY?
              
GROUP BY reduces the result to one row per group. PARTITION BY keeps every row and computes the function within each group. Same grouping concept, opposite effect on cardinality.
Practical consequences worth listing. With GROUP BY you lose access to individual rows, so “the name of the top earner per department” is not expressible (§1.4); with PARTITION BY it is trivial. You can use both in one query — GROUP BY first, then a window over the grouped rows, which is how percent-of-total works. And they can partition on different things: GROUP BY month with a window PARTITION BY nothing gives you each month's share of the year.
Performance note: a window function usually costs a sort per distinct PARTITION BY/ORDER BY combination, so several windows with the same specification are cheap (one sort, reused) while several with different specifications each pay. Reusing one named window (§5.9) makes that explicit.

Two passes, a join to get wrong, and the join key must be unique or you fan out. Still the right answer when the engine has no window functions.

          
Window function
One pass, no join, and the comparison to the group is available on every row. Also composes: several different windows in one SELECT.

5.1 The frame clause ⭐⭐

        
Which rows the function can actually see. Three modes, and choosing the wrong one is not an error — it is a different number.

The boundary vocabulary: UNBOUNDED PRECEDING, n PRECEDING, CURRENT ROW, n FOLLOWING, UNBOUNDED FOLLOWING. So ROWS BETWEEN 6 PRECEDING AND CURRENT ROW is a 7-row trailing window, and ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW is a running total.

        
Ranking functions ignore the frame entirely — ROW_NUMBER, RANK, DENSE_RANK and NTILE are defined over the whole partition regardless of what you write. Frames only affect aggregates and the value functions (FIRST_VALUE, LAST_VALUE, NTH_VALUE).


        

          
Likely interview questions

          

            
ConceptualWhat is a window frame, and what is the difference between ROWS and RANGE?
              
The frame is the subset of the partition visible to the function for the current row. ROWS counts physical rows — “the two rows before this one”. RANGE counts values of the ordering key — “all rows whose date is at or before this date”.
They are identical whenever the ORDER BY key is unique. They diverge on ties, and that divergence is the bug in §5.2: with RANGE, every row sharing a date sees the same frame, so a running total jumps by the whole day's worth at once and no row shows a partial value.
Two things worth adding. The default is RANGE, not ROWS — so if you write SUM(x) OVER (ORDER BY d) you have silently chosen the tie-sharing behaviour. And RANGE is the mode that supports value offsets, which is how you express a genuine time window: RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW in PostgreSQL means seven calendar days regardless of how many rows fall in them — something ROWS cannot express.

It depends on whether OVER has an ORDER BY. Without one, the frame is the whole partition, so an aggregate returns the group total on every row. With one, the frame defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — which is what turns the same expression into a running total.

Practical rule: if you write ORDER BY inside OVER for an aggregate, write the frame explicitly too. ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW for a ledger, ROWS BETWEEN 6 PRECEDING AND CURRENT ROW for a 7-row trailing window. It costs eight words and removes an entire class of bug.
And note the asymmetry that makes this so easy to miss: ranking functions ignore the frame, so you can write ROW_NUMBER() OVER (ORDER BY d) for years and never encounter the issue until the day you write SUM.

5.7 FIRST_VALUE, LAST_VALUE, and the frame that breaks LAST_VALUE ⭐

        
A function that appears broken on first use, is actually behaving exactly as specified, and catches nearly everyone once.

The fix: LAST_VALUE(x) OVER (ORDER BY d ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING). FIRST_VALUE looks fine by luck, because the frame's start already is the partition's start.

Define the window once, reuse it. Reduces repetition, prevents a class of copy-paste bug, and hints to the reader that one sort is being shared.

In production, persist it. A dim_date table with a row per day and columns for month, quarter, ISO week, fiscal period, weekday and holiday flags removes dialect functions from every downstream query and makes fiscal calendars expressible at all. Generating it on the fly is for ad-hoc work.


        

          
Likely interview questions

          

            
Very commonWhy do you need a date dimension table?

The production version adds columns you cannot compute portably: fiscal periods, holiday flags, business-day counts, ISO week numbers. 6.7 Time zones and UTC discipline ⭐

        
The rule is short. The consequences of breaking it are not.


        
Store UTC, convert at the edge. Every timestamp in the warehouse in UTC, converted to a local zone only in the final presentation query, using a named zone ('Asia/Kolkata') rather than a fixed offset ('+05:30') so daylight saving is handled.

        
Why it matters for analytics: “daily active users” depends on where the day boundary is. Grouping UTC timestamps by date gives you UTC days, which for a US audience splits every evening across two days. Converting first and then truncating gives local days. Both are defensible; picking one silently is not.

        
The types: PostgreSQL's timestamptz stores an absolute instant and renders in the session zone; plain timestamp stores wall-clock text with no zone and is a frequent source of silent errors. Prefer the zone-aware type. And note that a date has no zone at all, so any conversion has to happen before truncation, never after.


        

          
Likely interview questions

          

            
ConceptualHow do you handle time zones in a data warehouse?
              
Store everything in UTC with a zone-aware type, and convert to local time only in the outermost presentation layer. Use named time zones ('Europe/London') not fixed offsets, because offsets do not know about daylight saving and a report built on +01:00 is wrong for half the year.
The analytics consequence to raise unprompted: truncating to a date has to happen after the conversion, not before. DATE_TRUNC('day', ts AT TIME ZONE 'Asia/Kolkata') gives local days; DATE_TRUNC('day', ts) gives UTC days, and for a non-UTC audience those differ for every event near midnight. 8.1 The pattern, and the one trick behind all of it ⭐⭐

        
Ten interview questions, two techniques. Learn both and this entire level collapses into a single idea.


        
An island is a contiguous run of rows; a gap is the break between runs. The problem is always the same: rows do not carry a group id for their run, so you must manufacture one.


        

          
Technique 1 — the row_number difference
For a sequence with a fixed step (consecutive days, consecutive integers), value − ROW_NUMBER() is constant within a run and changes at every break. That difference is the group key.

Use when: the step is known and regular.

          
Technique 2 — flag then cumsum
LAG to find the gap, flag rows where it exceeds a threshold, then a running SUM of the flags. The running sum is the island id.

Use when: the rule is a tolerance, a timeout, or a value change. More general.

        


        
Why technique 1 works: if dates increase by exactly one per row, then date and row-number increase in lockstep, so their difference is fixed. Skip a day and the date jumps while the row number does not, so the difference shifts permanently — giving every subsequent run a new constant.

        
Why technique 2 is the one to learn: it handles anything. Sessionisation with a 30-minute timeout (§7.7), streaks allowing one missed day, merging overlapping intervals, detecting when a value stopped changing — all are “flag the boundary, cumsum the flags”. If you internalise one idiom from this subject, make it that one.

Very commonExplain the gaps-and-islands pattern.
              
An island is a contiguous run; a gap is the break between runs. The whole difficulty is that rows do not know which run they belong to, so you construct a group key and then aggregate on it normally.
Technique 1, for regularly-stepped sequences: value − ROW_NUMBER() OVER (PARTITION BY entity ORDER BY value) is constant within a run, because both sides increment together, and shifts at each break. Group by that difference.
Technique 2, general: LAG the previous value, flag rows where the gap exceeds the allowed threshold, then take a running SUM of the flags — the cumulative sum is the island number.
Say why technique 2 is worth preferring: it takes an arbitrary boundary rule, so the same three lines handle a 30-minute session timeout, a “one missed day allowed” streak, overlapping-interval merging, and run-length encoding of a changing value. Technique 1 is elegant but only works when the step is fixed and the values are unique.
The prerequisite nobody mentions: deduplicate first. Two rows for the same date break technique 1 completely, because the row number advances while the date does not.

            

            
GotchaCan you nest one window function inside another?
              
No. SUM(LAG(x) OVER w) OVER w is rejected — engines report something like “window function calls cannot be nested” or “misuse of window function”. The reason is the evaluation model: all window functions in a SELECT are computed in the same phase from the same input rows, so one cannot consume another's output.
This bites precisely here, because the flag-then-cumsum idiom looks like it needs nesting: you want a running sum of a LAG-derived flag. The fix is always the same — compute the inner window in its own CTE or subquery, then apply the outer window to that result. Two steps, and it also reads better.
One thing that is allowed and often confused with it: an aggregate inside a window function's argument, such as SUM(SUM(x)) OVER (). That works because the inner aggregate belongs to the GROUP BY phase, which completes before windows are evaluated (§3.6). Aggregate-inside-window: fine. Window-inside-window: never.

9.4 Weighted averages and compressed histograms ⭐

        
When each row represents many observations, AVG is the wrong function — and the mistake is easy to miss because it returns a plausible number.


        
The rule: a weighted average is SUM(value * weight) / SUM(weight), never AVG(value). If your table has a quantity or count column, AVG treats a row representing 1,000 units the same as a row representing 1.

        
The same applies to averaging averages. AVG(daily_avg) over 30 days is not the monthly average unless every day had the same number of observations. You need SUM(daily_total) / SUM(daily_count) — this is Simpson's-paradox territory, and it appears in real dashboards constantly.

Likely interview questions

          

            
GotchaWhy is the average of the daily averages not the monthly average?
              
Because AVG of averages weights every day equally regardless of how many observations each day contained. A Tuesday with 10,000 orders and a Sunday with 100 contribute the same amount to AVG(daily_avg), which is almost never what anyone means.
The pooled mean is SUM(total) / SUM(count) — equivalently AVG over the raw rows. The two coincide only when every group is the same size.
This is the same structure as Simpson's paradox: an aggregate over unequal groups can point the opposite way from the groups themselves, so a conversion rate can rise in every segment and fall overall. Naming that connection is what makes this a strong answer rather than a formula.
The general rule: keep the numerator and denominator, and divide at the end. That is also why a well-built metrics layer materialises sums and counts, never averages.

10.3 Case, whitespace and collation ⭐⭐

        
Whether 'A' = 'a' depends on the column's collation, which is a schema property most people never look at — and it silently changes the meaning of every comparison, join and GROUP BY.


        
The defaults differ. PostgreSQL is case-sensitive. MySQL's usual default collation (utf8mb4_0900_ai_ci) is case-insensitive and accent-insensitive. SQL Server depends on the instance collation, commonly case-insensitive. SQLite is case-sensitive unless a column is declared COLLATE NOCASE. So the same query genuinely returns different results on different engines.

        
The consequences: a JOIN on an email column matches or does not; a GROUP BY on a category produces one bucket or two; a UNIQUE constraint permits 'Ada' alongside 'ada' or does not. Normalise at write time if you can, and normalise explicitly in the query if you cannot.

The related trap worth naming: trailing whitespace. Some engines pad-compare CHAR columns so 'a ' equals 'a', and others do not, which is why VARCHAR/TEXT plus explicit trim is the safer combination.

            

          

        

      


      

        
10.4 Implicit type coercion ⭐

        
Comparing a string to a number sometimes works, sometimes silently does the wrong thing, and the rules differ by engine.


        
The classic: '10' > '9' is false, because string comparison is lexicographic — '1' sorts before '9'. If a numeric id or a version is stored as text, every range filter and every ORDER BY on it is wrong in a way that looks almost right.

MySQL coerces aggressively — 'abc' = 0 is true in some modes, which has caused real security bugs. SQLite has type affinity: it will coerce a text value to numeric if the column's affinity says so, and compare as text otherwise.

10.6 Floating point and money ⭐

        
0.1 + 0.2 <> 0.3. Everyone knows this and money columns are still declared as float.


        
The rule: use NUMERIC/DECIMAL for money, or store integer minor units (pence, cents). FLOAT and DOUBLE are binary approximations and cannot represent 0.1 exactly, so sums drift and equality comparisons fail unpredictably.

11.1 Logical order vs the physical plan ⭐

        
§1.1 described what a query means. This is about what the engine actually does, and the two are deliberately different.


        
The logical order defines semantics. The optimiser is free to execute in any order that produces the same result, and it routinely does: predicate pushdown applies filters before joins, join reordering starts with whichever table is most selective, projection pruning stops reading columns you never reference, and limit pushdown can stop a scan early.

        
Why this matters for you: it means “filter early” is often already done for you, so hand-optimising by rewriting the query is frequently pointless. What the optimiser cannot fix is a missing index, a non-sargable predicate, a bad row estimate, or a fundamentally wrong join. Those are the four things worth looking for.


        

          
Likely interview questions

          

            
ConceptualShould you rewrite a query to filter earlier?
              
Usually not, because the optimiser already pushes predicates down. Moving a WHERE clause around in an inner-join query typically produces an identical plan, and time spent on it is wasted.
Where rewriting genuinely helps: when the optimiser cannot push the filter. A predicate on the output of a window function, an aggregate, or a non-inlinable CTE forms an optimisation barrier, so filtering before that step is a real change. Similarly, replacing a correlated subquery in the SELECT list with a join or a window can turn N passes into one (§3.2).
The four things that actually matter, in order: a missing index on the join or filter column; a non-sargable predicate that disables an index you already have (§11.5); a bad cardinality estimate that makes the planner choose a nested loop over a hash join; and a wrong join that is fanning out and forcing the engine to process rows that should not exist.
So the method is: read the plan, find the step with the largest row count or cost, and fix that. “I would look at EXPLAIN before changing anything” is a much better answer than any specific rewrite.

And say the thing most people omit: ask whether the query needs to be fast at all. Knowing when not to optimise is part of the answer.

The detail that shows depth: a B-tree cannot help a leading-wildcard LIKE '%foo', because the index is sorted by prefix and there is no prefix to seek on. That is why full-text search needs a different index type entirely.

            

          

        

      


      

        
11.4 The leftmost-prefix rule ⭐

        
Why a composite index on (a, b) helps a query filtering on a, and does nothing for a query filtering only on b. Demonstrable in three plans.


        
The reason: a composite index is sorted by a, then by b within each a. Like a phone book sorted by surname then forename — you can find everyone called Patel, and everyone called Patel whose forename starts with A, but you cannot efficiently find every Anil regardless of surname.

        
The consequences: an index on (a, b) serves filters on a, and on a+b, but not on b alone. Column order matters, so put the most selective or most frequently filtered column first — and put equality predicates before range predicates, because once you hit a range the index can no longer seek on later columns.

Very commonYou have an index on (a, b, c). Which queries can use it?

Some engines can do an inefficient full index scan in that case, which is better than a table scan but is not a seek.
Once you hit a range, later columns stop being seekable. With a filter a = 1 AND b > 5 AND c = 3, the index seeks on a and b and then must filter c by inspection. So the design rule is equality columns first, range columns last, and the most selective equality column leftmost.
Which leads to the practical advice: design indexes for your query patterns, not per column. Three single-column indexes are usually worse than one well-ordered composite, and a table with fifteen indexes is paying a large write tax for coverage it does not need.

Likely interview questions

          

            
Very commonWhen does an index hurt performance?
              
Start from the trade-off: an index accelerates reads and taxes every write, because each modification has to maintain it. So it hurts whenever the write cost exceeds the read benefit.
Write-heavy tables are the clearest case — an append-only event or audit table with several indexes pays for all of them on every insert. Low-cardinality columns are the subtlest: an index on a two-value flag rarely helps, because the engine would touch most of the table regardless, and a partial index on the rare value is the correct alternative. Unselective queries are the counter-intuitive one: past roughly 5–20% of rows, a sequential scan beats scattered index lookups, so the planner ignores the index — which people then read as “the index isn't working”.
Also: small tables, where a scan is one page read; redundant indexes, where (a) duplicates the prefix of (a,b); and bulk loads, where dropping and rebuilding is much faster than maintaining.
The habit worth mentioning: audit unused indexes. PostgreSQL exposes pg_stat_user_indexes with scan counts, and an index with zero scans after a month is pure cost. Removing indexes is a legitimate optimisation, and hardly anyone volunteers it.

            

          

        

      


      

        
11.7 Join algorithms ⭐

        
Three ways an engine can execute a join. Knowing which one you are getting, and why, is most of join tuning.


        

          
Nested loop
For each outer row, look up matches in the inner. Good when the outer side is tiny and the inner is indexed. Catastrophic when the outer side is large and the inner is unindexed — that is the O(n·m) plan you never want.

          
Hash join
Build a hash table on the smaller side, probe with the larger. The workhorse for large equality joins. Needs memory; spills to disk if the build side does not fit. Equality only.

          
Merge join
Sort both sides, walk them in step. Good when both inputs are already sorted — for example by an index on the join key. Supports inequality joins.

        


        
What this tells you. A range join (§2.9) cannot be a hash join, because hashing needs equality — so it falls back to a nested loop, and that is why range joins are slow and why adding any equality predicate helps so much. A nested loop with a large outer side almost always means a missing index on the inner join key. And a hash join that spills means the build side is bigger than the planner expected, which points at a cardinality mis-estimate.


        

          
Likely interview questions

          

            
ConceptualExplain the join algorithms and when each is chosen.
              
Nested loop: for each row of the outer input, probe the inner. Cost is outer × inner-probe, so it is excellent when the outer is small and the inner has an index on the join key, and disastrous otherwise.
Hash join: build a hash table from the smaller input, then stream the larger one through it. O(n + m), memory-hungry, and equality-only. This is what a large analytical join should be getting.
Merge join: sort both inputs on the join key and walk them together. O(n log n + m log m), or O(n + m) if both are already ordered — which is why an index on the join key can turn a hash join into a cheaper merge join. It also handles inequality conditions, which hash cannot.
The consequences worth stating. A range or as-of join has no equality to hash on, so it degrades to a nested loop — that is the mechanism behind “range joins are slow” and the reason adding a coarse equality predicate (a date bucket, a tenant id) transforms it. A nested loop over a large outer side is a missing-index signal. And a hash spill to disk means the planner underestimated the build side, so ANALYZE and check the estimates.
Distributed engines add one more dimension: whether the join is a broadcast (small side sent everywhere) or a shuffle (both sides repartitioned by key). Getting a shuffle where a broadcast would do — or vice versa — is the main cause of slow Spark joins, and it is the same reasoning one level up.

            

          

        

      


      

        
11.8 Partitioning and pruning ⭐

        
Splitting a table so the engine can skip most of it without reading it. At warehouse scale this matters more than indexing.


        
Partitioning divides a table physically, usually by date. A query filtered to one day then reads one partition — partition pruning — and the rest of the table is never touched. Clustering (BigQuery) or sort keys (Redshift, Snowflake's clustering) order data within a partition so the engine can skip blocks using per-block min/max metadata.

        
The rule that makes it work: the filter must be on the partition column, and it must be sargable. WHERE DATE(ts) = '2026-03-01' defeats pruning on a table partitioned by ts for exactly the reason in §11.5 — the engine cannot map the function's output back to partitions. Every warehouse cost-control document is essentially this one sentence.


        

          
Likely interview questions

          

            
Very commonWhat is partitioning, and how is it different from indexing?
              
An index is an auxiliary structure that helps you find specific rows. Partitioning physically splits the table so entire chunks can be skipped without being read at all. They are complementary: partitioning eliminates data, indexing locates rows within what remains.
The mechanism is partition pruning: with a table partitioned by day, a query filtered to a week reads seven partitions rather than the whole history. That is why partitioning is the dominant optimisation on large fact tables and why the partition column is almost always a date.
Clustering / sort keys are the next level down: ordering rows within a partition so the engine can skip blocks using min/max metadata per block. BigQuery calls it clustering, Snowflake calls it clustering keys, Redshift calls it a sort key, Delta and Iceberg do it with file statistics and Z-ordering.
The failure modes to name. Filtering on a function of the partition column defeats pruning entirely (§11.5). Too many small partitions — partitioning by hour on a low-volume table — creates metadata overhead and tiny files, which is its own performance problem. And partitioning on the wrong column: it must be the one your queries actually filter on, which is usually the event date and almost never the primary key.

            

          

        

      


      

        
11.9 Data skew and the straggler ⭐

        
On a distributed engine, one key with far more rows than the others makes one worker do most of the work while the rest idle. The job's runtime becomes that worker's runtime.


        
Where it comes from: a join or GROUP BY key with a hot value — NULL, an 'unknown' sentinel, a default tenant, a single enormous customer. All rows with that key hash to the same partition, so one task processes 60% of the data.

        
How to spot it: SELECT key, COUNT(*) FROM t GROUP BY key ORDER BY 2 DESC LIMIT 20. If the top key is orders of magnitude above the median, that is your straggler. In the Spark UI it is the one task taking twenty minutes while 199 took ten seconds.

        
Fixes: filter the sentinel out if it is meaningless (NULL keys usually are — and note NULLs never join anyway); salt the hot key by appending a random bucket number and aggregating in two stages; broadcast the small side so no shuffle happens at all; or split the hot keys into a separate job.

On a real events table keyed by user_id you routinely see ratios in the thousands because of bot traffic or a service account — and that single key is what makes the nightly job take four hours instead of twenty minutes.

        


        

          
Likely interview questions

          

            
ConceptualA Spark job has 199 fast tasks and one that takes an hour. What is happening?
              
Data skew. The shuffle partitions by hash of the key, so all rows sharing a hot key land on one executor. That task processes a disproportionate share and the job cannot finish until it does — the runtime is the straggler's runtime, and adding executors does not help.
Diagnose it with a key-frequency query: group by the join or aggregation key, order by count descending, and look at the top values against the median. A ratio in the hundreds or thousands is the answer.
Fixes, in the order I would try them. Filter the sentinel — the hot key is very often NULL or 'unknown', and if it is meaningless it should not be in the join at all (NULLs never match anyway, so they are pure shuffle cost). Broadcast the small side, which removes the shuffle entirely and is the single most effective fix when one input fits in memory. Salt the key: append a random bucket to the hot key, aggregate per bucket, then aggregate the buckets — two stages, evenly distributed. Or split: process the hot keys in a separate job with different parallelism.
Worth naming: Spark's adaptive query execution can now detect and split skewed partitions automatically, so the first thing to check is whether AQE is enabled. But it cannot fix a skew that comes from a meaningless sentinel — that one is a modelling problem.

            

          

        

      


      

        
11.10 OLTP vs OLAP, rows vs columns ⭐

        
Why your analytical query is slow on Postgres and fast on BigQuery, and why the reverse is true for a single-row lookup.


        

          
Row store (OLTP)
All of a row's columns stored together. Reading one whole row is one I/O. Great for point lookups and transactional writes. Bad for scanning one column of a billion rows — you read every column to get one.

          
Column store (OLAP)
Each column stored separately and compressed. Reading three columns of a billion rows touches only those three. Great for aggregation. Bad for fetching or updating a single complete row.

        


        
Why columnar wins so decisively for analytics: projection pruning — you only read the columns you select, which is why SELECT * is far more expensive there than in a row store; compression — a column of one data type with repeated values compresses enormously, often 10× or more, and less data means less I/O; and vectorised execution — operating on batches of a single type is cache-friendly and SIMD-friendly.

        
The practical consequence: the habits differ. On a row store you index for selectivity. On a column store you select fewer columns, partition and cluster, and accept that there are no indexes in the traditional sense at all.


        

          
Likely interview questions

          

            
Very commonWhy are columnar databases faster for analytics?
              
Three reasons, and they compound.
Projection pruning. Columns are stored separately, so a query selecting three of two hundred columns reads 1.5% of the data. A row store must read every row in full to extract those three fields.
Compression. A single column holds one data type with heavily repeated values, so run-length and dictionary encoding are extremely effective — often 10× or better. Less bytes on disk means less I/O, and I/O is the bottleneck.
Vectorised execution. Processing a contiguous batch of same-typed values is cache-friendly and maps onto SIMD instructions, which is a large constant-factor win over row-at-a-time interpretation.
Then the trade-off, because the question is really about knowing when not to use one: a columnar store is poor at single-row reads (it must reassemble the row from every column) and poor at row-level updates (it is designed for append and rewrite). So OLTP stays row-oriented and OLAP goes columnar, which is why most organisations run both and move data between them.
The consequence for how you write SQL: on a columnar engine SELECT * is genuinely expensive rather than merely untidy, and on a scanned-bytes pricing model it is a line item on the invoice.

            

          

        

      


      

        
11.11 Cost control on a scanned-bytes engine ⭐

        
On BigQuery, Athena and Snowflake, a slow query is also an expensive one — and the levers are not the ones you would use on Postgres.


        

          

            
LeverWhy it works

            
              
Name your columnsColumnar storage means you are billed for the columns you touch. SELECT * on a 200-column table costs 200× the necessary scan

              
Filter on the partition columnPartition pruning skips whole days. And keep it sargable, or pruning is defeated (§11.5, §11.8)

              
Cluster on the common filterBlock-level min/max metadata lets the engine skip files within a partition

              
Materialise the expensive intermediateIf forty dashboards each aggregate the raw events table, aggregate once into a table and point them at it

The counter-intuitive one worth remembering: SELECT * FROM huge_table LIMIT 10 can cost as much as scanning the whole table, because the pricing is on bytes read and the limit is applied after. That single misunderstanding accounts for a lot of surprise invoices.


        

          
Likely interview questions

          

            
Very commonYour warehouse bill doubled. How do you bring it down?
              
Start by finding where it goes: most warehouses expose a query history with bytes scanned or credits per query. Sort by cost, and the top ten queries usually account for most of the bill. Optimising anything else is wasted effort.
Then the levers, in order of typical impact. Incremental models — a nightly full rebuild of a history table is usually the single largest line item, and processing only new partitions can cut it by 95%. Materialise shared intermediates — if many dashboards each scan the raw events table, aggregate once. Partition and cluster, and make sure the filters are sargable so pruning actually happens. Name columns instead of SELECT *, which on columnar storage is a direct multiplier. Approximate aggregates where exactness is not required.
The trap to name: LIMIT does not reduce bytes scanned on BigQuery, so “I only looked at 10 rows” can still be a full-table charge. Preview features and TABLESAMPLE are the cheap ways to look at data.
And the governance point, which is what a senior answer includes: set per-query and per-user byte limits and alerting, so a runaway query is caught at £20 rather than at £2,000. Cost control is a guardrail problem as much as an optimisation problem.

            

          

        

      


      

        
11.12 Materialised views and incremental models

        
The difference between computing something every time it is asked for and computing it once.


        

          

            
ViewMaterialised viewIncremental table

            
              
StorageNone — it is a saved queryStores the resultStores the result

              
Read costFull cost, every timeCheapCheap

              
FreshnessAlways currentDepends on refresh; some engines auto-refreshAs of the last run

              
Best forSimplifying a query; access controlA fixed aggregate over a slowly-changing baseLarge append-mostly fact tables

            
          

        


        
The incremental pattern is the one that matters at scale: instead of rebuilding the whole table, process rows newer than the current watermark and append. The complications are real and worth naming — late-arriving data means you must reprocess a trailing window rather than only the newest partition; idempotency means a re-run must not double-count, so you delete-and-insert the affected partitions rather than blindly appending; and backfills need a separate full-refresh path.

        
Views are still valuable for a different reason: they are the interface. A view that encapsulates the agreed definition of “active customer” means every team uses one definition, which prevents the §10.8 reconciliation argument from happening at all.


        

          
Likely interview questions

          

            
ConceptualView vs materialised view vs table?
              
A view is a stored query with no data: reading it re-runs the underlying SQL, so it is always fresh and always costs full price. A materialised view stores the computed result, so reads are cheap and freshness depends on the refresh schedule. A table built by a pipeline is the same idea with you owning the refresh logic — which is what dbt models are.
Choose by read/write ratio and freshness requirement. Frequently read, slowly changing, tolerant of minutes-old data → materialise. Rarely read or needs to be exactly current → view. Large and append-mostly → an incremental table, processing only new partitions.
The incremental complications are what a senior answer covers: late-arriving data forces you to reprocess a trailing window, not just the newest partition; idempotency means the run must be safe to repeat, which usually means delete-and-insert by partition rather than append; and you need a full-refresh path for backfills and for when the logic changes.
And the non-performance reason to use views: they are a contract. Putting the agreed definition of a metric in a view means every consumer shares it, which is the structural fix for two dashboards disagreeing.

12.2 The warm-up questions

        
From Part 1. If any of these takes more than a few seconds, that is where to spend your time.


        

          
Rapid drill — Level 0

          

            
Very commonWhat is the order of execution of a SQL query?
              
FROM/JOIN → WHERE → GROUP BY → HAVING → window functions → SELECT → DISTINCT → ORDER BY → LIMIT. It explains why a SELECT alias works in ORDER BY but not WHERE, why aggregates go in HAVING, and why a window function cannot be filtered without wrapping the query. Full treatment: §1.1.

            

            
Very commonCOUNT(*) vs COUNT(col) vs COUNT(DISTINCT col)?
              
Rows; non-null values of col; distinct non-null values. COUNT(1) is identical to COUNT(*). The one that bites: COUNT(col) is a filter in disguise, and COUNT(*) - COUNT(col) is the fastest null audit there is. §1.3.

            

            
Very commonWHERE vs HAVING?
              
WHERE filters rows before grouping; HAVING filters groups after aggregating. You must use HAVING for a condition on an aggregate; you should use WHERE for everything else, because fewer rows reach the grouping step. QUALIFY is the window-function equivalent, and it exists only on Snowflake, BigQuery, Teradata, Databricks and DuckDB. §1.5.

            

            
Very commonWhy does WHERE col = NULL return nothing?
              
NULL means unknown, so any comparison with it yields UNKNOWN, and WHERE keeps only TRUE. Use IS NULL. The consequence worth stating: col = x and col <> x do not partition the table, because NULL rows satisfy neither. §1.6.

            

            
GotchaWhere does SQL treat NULLs as equal?
              
In GROUP BY, DISTINCT, UNION/INTERSECT/EXCEPT, ORDER BY and window PARTITION BY — all use “not distinct from”. In WHERE, ON, HAVING and IN they are unknown. Aggregates other than COUNT(*) skip them entirely. §1.6.

            

            
Very commonHow do aggregates treat NULL?
              
They ignore them. So AVG(col) divides by COUNT(col), not COUNT(*) — if missing means zero in your domain, AVG overstates. And SUM over an empty or all-null set returns NULL, not 0, so guard it with COALESCE before doing arithmetic. §1.7.

            

            
Very commonHow do you avoid a divide-by-zero?
              
n / NULLIF(d, 0). And remember the engines disagree on what raw division by zero does — PostgreSQL and SQL Server raise, MySQL and SQLite return NULL — so the guard also makes the query portable. §1.8, §10.5.

            

            
Very commonYour rate column is all zeros. Why?
              
Integer division. 3/4 is 0 in PostgreSQL, SQL Server and Oracle. Multiply by 100.0, or CAST, or use AVG of a 0/1 flag. It is invisible on MySQL and SQLite, which is exactly why it reaches production. §1.8.

            

            
Very commonCount completed and cancelled orders as two columns.
              
Conditional aggregation: SUM(CASE WHEN status='completed' THEN 1 ELSE 0 END) per column. With COUNT, omit the ELSE — COUNT counts a zero but skips a NULL, so ELSE 0 would count every row. FILTER (WHERE ...) is the standard spelling where available. §1.10, §3.7.

            

            
Very commonUNION vs UNION ALL?
              
UNION deduplicates, which costs a sort or hash over the whole combined result. Use UNION ALL unless you specifically need dedup. Extra point: UNION can hide a genuine duplicate-data problem. §1.11.

            

            
GotchaIs SELECT ... ORDER BY x LIMIT 3 deterministic?
              
Not if x has ties — nothing specifies which tied row wins, and it can change with the plan. Append a unique column: ORDER BY x, id. This is the single most common cause of intermittently failing data tests. §1.2, §4.10.

            

          

        

      


      

        
12.3 Joins and NULLs

        
From Part 2. Where most wrong answers come from, and the highest-value section to have reflexive.


        

          
Rapid drill — Level 1

          

            
Very commonWhat is the difference between a condition in ON and in WHERE?
              
For an inner join, none. For an outer join it changes the result: ON defines what counts as a match and unmatched rows survive with NULLs; the same condition in WHERE runs after the join and discards those manufactured rows, silently turning a LEFT JOIN into an INNER JOIN. Rule: filter the right table in ON, the driving table in WHERE. §2.2, §2.3.

            

            
Very commonWhy did my NOT IN subquery return zero rows?
              
A NULL in the subquery. x NOT IN (a, NULL) expands to x<>a AND x<>NULL, and the second term is UNKNOWN for every x, so the predicate can never be true. Use NOT EXISTS, or add WHERE col IS NOT NULL to the subquery. §2.4.

            

            
Very commonWrite an anti-join three ways.
              
NOT EXISTS (preferred — null-safe, expresses intent, optimises to an anti-join); LEFT JOIN ... WHERE right.key IS NULL; EXCEPT on key lists. NOT IN is the fourth and the dangerous one. §2.4.

            

            
Very commonYour revenue doubled after adding a join. What happened?
              
Fan-out: a one-to-many join repeated each parent row per child, so a SUM of the parent's amount counted it once per child. Fix by aggregating the many side first and then joining, or by aggregating only many-side columns. Compare row counts before and after any join. §2.6.

            

            
GotchaCan an INNER JOIN return more rows than either table?
              
Yes — if the key is non-unique on both sides, the output for that key is the product of the multiplicities. Joins are not filters. Check uniqueness with GROUP BY key HAVING COUNT(*) > 1 before writing the join. §2.6.

            

            
Very commonEXISTS vs IN vs JOIN?
              
EXISTS for an existence test — a semi-join, never duplicates rows, short-circuits. IN is equivalent for the positive case. JOIN when you need columns from the other table, and accept the row multiplication. The old “EXISTS is faster” folklore is largely obsolete: modern optimisers produce the same semi-join plan. §2.5.

            

            
Very commonEmployees earning more than their manager.
              
Self-join on e.manager_id = m.id, compare salaries. Note the root of the hierarchy has a NULL manager and is dropped by the inner join — correct here, but switch to LEFT JOIN the moment the question becomes “list everyone with their manager”. §2.7.

            

            
Very commonHow do you join a fact table to a slowly-changing dimension correctly?
              
On the key and the validity window, with half-open bounds: f.ts >= d.valid_from AND f.ts < d.valid_to. Joining on the key alone with is_current = 1 attaches today's attributes to historical facts, which is look-ahead leakage that produces exactly one row per fact and therefore looks correct. §2.9, §6.10, §9.9.

            

            
CodingHow do you test whether two date ranges overlap?
              
a.start <= b.end AND a.end >= b.start — two clauses, not four cases. Strict inequalities for half-open intervals. §2.10.

            

            
ConceptualWhy avoid NATURAL JOIN?
              
The join key is implicit and follows column names, so an unrelated migration that adds a same-named column to both tables silently changes the join. USING (a, b) is the safe shorthand; explicit ON is what to write in anything long-lived. §2.10.

            

          

        

      


      

        
12.4 Windows and ranking

        
From Parts 3, 4 and 5. The most-tested topic in a SQL screen.


        

          
Rapid drill — Levels 2–4

          

            
Very commonROW_NUMBER vs RANK vs DENSE_RANK?
              
On 100, 100, 90: 1,2,3 / 1,1,3 / 1,1,2. ROW_NUMBER for dedup and “exactly one row”; RANK for competition ranking; DENSE_RANK for “the Nth distinct value”. §4.3.

            

            
Very commonSecond highest salary.
              
DENSE_RANK() OVER (ORDER BY salary DESC) = 2, wrapped. LIMIT 1 OFFSET 1 is wrong whenever the top salary is shared — it returns the maximum again. MAX below the MAX works for N=2 and does not generalise. Add PARTITION BY for per-department. §4.4.

            

            
Very commonTop 3 per group — which ranking function?
              
Ask what should happen at a tie on third place. ROW_NUMBER gives exactly three, cutting through the tie arbitrarily; RANK/DENSE_RANK return all tied rows, so you may get more. Aggregate to the right grain before ranking. On Snowflake/BigQuery/DuckDB, QUALIFY saves the subquery. §4.5.

            

            
Very commonMost recent record per user.
              
ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts DESC, id DESC) = 1. The tie-break is not optional — with date-granularity timestamps or bulk loads, ties are common and the “latest” row would otherwise vary between runs. Alternatives: DISTINCT ON (PostgreSQL), LATERAL/CROSS APPLY with LIMIT 1. §4.5, §4.10.

            

            
Very commonWhy can't you filter on a window function in WHERE?
              
Windows are computed at step 5, after WHERE at step 2 — the value does not exist yet. Wrap in a subquery/CTE, or use QUALIFY. And note the two placements are not equivalent: filtering in WHERE changes the window's input, so ranks renumber. §4.9.

            

            
GotchaWhat is the default window frame?
              
Without ORDER BY in OVER: the whole partition. With it: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — and it is RANGE, not ROWS, so tied ordering keys share a frame and a running total jumps by the whole tie group. Always write the frame explicitly for aggregates. §5.1, §5.2.

            

            
GotchaWhy does LAST_VALUE return the current row?
              
Because the default frame ends at CURRENT ROW, so the last row of the frame is the current row. Fix with an explicit UNBOUNDED FOLLOWING frame, or — better — FIRST_VALUE(x) OVER (ORDER BY d DESC). §5.7.

            

            
Very commonMonth-over-month growth.
              
Aggregate to month, then (rev - LAG(rev) OVER (ORDER BY mo)) / NULLIF(LAG(rev) OVER (ORDER BY mo), 0) * 100.0. Three defects to pre-empt: integer division, division by zero, and missing months — LAG counts rows, so a gap silently shifts every later comparison. §5.6.

            

            
GotchaBuild a feature: the customer's average order value before this order.
              
Frame ending at 1 PRECEDING, not CURRENT ROW. Including the current row is target leakage — the model learns from the answer, validates beautifully, and fails in production. §5.8.

            

            
CodingRunning count of unique customers by month.
              
COUNT(DISTINCT ...) is not available as a window function, because a distinct count is not incrementally computable. Reduce each customer to their first month, then take a cumulative SUM of the per-month counts. §5.10.

            

            
GotchaCan you nest one window function inside another?
              
No — all windows in a SELECT are computed in the same phase, so one cannot consume another's output. Compute the inner one in a CTE first. But an aggregate inside a window is legal: SUM(SUM(x)) OVER () works, and it is how percent-of-total is written. §8.1, §3.6.

            

            
Very commonCTE vs subquery vs temp table?
              
CTEs for readability, reuse within the query, and recursion. Subqueries for one simple inline use. Temp tables when an expensive intermediate is reused many times and you want to index it or give the planner real statistics. CTEs are not inherently faster — that belief comes from PostgreSQL's pre-v12 optimisation fence. §3.3.

            

          

        

      


      

        
12.5 Dates, funnels and retention

        
From Parts 6 and 7. The product-analytics core.


        

          
Rapid drill — Levels 5–6

          

            
Very commonWhat is wrong with ts BETWEEN '2026-03-01' AND '2026-03-31'?
              
On a timestamp column the end literal means midnight, so you lose almost the whole of the 31st. Use a half-open range: ts >= '2026-03-01' AND ts < '2026-04-01' — correct at any precision, and sargable. Do not “fix” it with CAST(ts AS date), which disables the index. §6.5.

            

            
Very commonWhy do you need a date dimension or spine?
              
Because GROUP BY date only returns dates present in the data. A day with no activity becomes a missing row rather than a zero, so charts interpolate over outages and a “7-day average” divides by however many rows exist. Generate the calendar, then LEFT JOIN the facts onto it. §6.3, §6.4.

            

            
Very commonBuild a funnel.
              
Count distinct users per step from a VALUES step list LEFT JOINed to the events, then LAG for step-to-step rate and FIRST_VALUE for overall. Ask three things first: must the steps be in order, within what time window, and distinct users or events. §7.2.

            

            
GotchaHow do you enforce funnel step ordering?
              
Collapse each user to their first timestamp per step with conditional MIN, then require t2 > t1, t3 > t2 and so on. Out-of-order events are normal in real event tables — clock skew, batched SDKs, retries — so the naive “did it happen at all” funnel overstates conversion. §7.3.

            

            
Very commonWrite a monthly cohort retention query.
              
Three CTEs: cohort = first-activity month per user; activity = distinct user-months; grid = join them and compute month_n from a monotonic period number. Then count distinct users per (cohort, month_n) over the cohort size. Flag incomplete recent cohorts, and say whether “retained” means active in month N (allows resurrection) or active every month since (survival). §7.4.

            

            
Very commonWhat is day-7 retention?
              
Ambiguous — active on exactly day 7, on day 7 or later, or at any point within 7 days. And the denominator must be users who had the opportunity to reach day 7, or the metric falls mechanically as acquisition grows. Put the definition in the column name. §7.5.

            

            
Very commonMAU is flat. What do you look at?
              
Decompose into new / retained / reactivated / churned per period, and check the identity active(t) = active(t−1) + new + reactivated − churned. Flat MAU is equally consistent with health and with churning as fast as you acquire. §7.6.

            

            
Very commonSessionise events with a 30-minute timeout.
              
LAG the previous timestamp, flag rows whose gap exceeds 30 minutes, running SUM of the flags is the session id. Flag the boundary, cumsum the flags — the most reusable idiom in analytical SQL, and the same three lines as everything in Part 8. §7.7.

            

            
Very commonCompute rolling 7-day actives.
              
Drive from a date spine; for each day count distinct users in the trailing seven days via a correlated subquery or range join. COUNT(DISTINCT ...) is unavailable as a window function. Keep the window half-open — > d−7 AND <= d — or you have an eight-day week. §6.9, §7.1.

            

            
Very commonWhat is point-in-time correctness?
              
Every value in a training row was knowable at that row's timestamp. Three parts: as-of dimension joins on the validity window; rolling features ending at 1 PRECEDING; and availability time rather than event time where data arrives late. Leakage inflates offline metrics and cannot be caught by cross-validation, because every fold shares it. §6.10.

            

          

        

      


      

        
12.6 Gaps, islands and hard patterns

        
From Parts 8 and 9. The genuinely difficult tier.


        

          
Rapid drill — Levels 7–8

          

            
Very commonExplain gaps and islands.
              
Two techniques. Row-number difference: for a fixed-step sequence, value − ROW_NUMBER() is constant within a run, so it is the group key. Flag and cumsum: LAG to find the gap, flag the boundary, running SUM gives the island id — more general, handles tolerances and timeouts. Deduplicate first, or a repeated value splits the run. §8.1.

            

            
Very commonUsers active 3+ consecutive days.
              
Islands, then HAVING COUNT(*) >= 3. The self-join-on-+1 day-and-+2 days alternative works for exactly three and encodes the number in the query structure, so it does not generalise. Report the run length and boundaries, not just the user id. §8.3.

            

            
Very commonLongest streak vs current streak.
              
Longest: count per island, take the per-user max — and use ROW_NUMBER rather than MAX if you also want which streak. Current: the run must reach the reference date, so a user with a great past streak has a current streak of zero. Decide whether “today or yesterday” counts. §8.4, §8.5.

            

            
Very commonMerge overlapping date ranges.
              
Sort by start; a new block begins where the start exceeds the running maximum of previous ends; cumsum the flags; aggregate min-start/max-end per block. The running maximum — not the previous row's end — is what handles a fully nested interval. §8.7.

            

            
CodingMaximum concurrent sessions.
              
Sweep line: +1 at each start, −1 at each end, UNION ALL, order by time, running SUM. MAX of that is the peak. O(n log n), versus O(n²) for comparing every pair of intervals. §8.10.

            

            
Very commonMedian without a percentile function.
              
Number the rows, count them, average the values at (n+1)/2 and (n+2)/2 with integer division — one formula for odd and even. Include a tie-break in the ORDER BY: the popular “number from both ends” trick returns a wrong median when values tie, because the two numberings are not mirrors. §9.1.

            

            
ConceptualPERCENTILE_CONT vs PERCENTILE_DISC?
              
DISC returns an actual data value; CONT interpolates and may return a value not in the data. Both respect ties, unlike NTILE. Two tools reporting “p95” with different definitions is a common source of disagreement. §9.2, §4.8.

            

            
GotchaWhy is the average of daily averages not the monthly average?
              
It weights every day equally regardless of volume. The pooled mean is SUM(total)/SUM(count). This is Simpson's-paradox territory, and the general rule is: keep numerator and denominator separately and divide at the end — sums re-aggregate, ratios do not. §9.4.

            

            
Very commonCount everyone in a manager's reporting line, at any depth.
              
Recursive CTE pairing each ancestor with all descendants. A self-join adds one level per join and the depth is data-dependent, which is what recursion is for. Carry a depth counter or path as a cycle guard, use UNION ALL, and mention closure tables or materialised paths for read-heavy workloads. §9.6.

            

            
Very commonExplain slowly changing dimensions.
              
Type 1 overwrites; Type 2 closes the old row and inserts a new one with valid_from/valid_to; Type 3 keeps one previous value. Query Type 2 point-in-time with half-open bounds. Validate the table with LEAD(valid_from) — overlaps duplicate facts, gaps lose them. Building it from snapshots is run-length encoding. §9.9.

            

          

        

      


      

        
12.7 Correctness and performance

        
From Parts 10 and 11. The questions that separate someone who writes queries from someone who ships them.


        

          
Rapid drill — Levels 9–10

          

            
Very commonHow do you find and delete duplicates?
              
Find: GROUP BY key HAVING COUNT(*) > 1, or ROW_NUMBER to see the rows. Delete: ROW_NUMBER() OVER (PARTITION BY key ORDER BY survivor_rule) and remove rn > 1. But first agree what duplicate means — casefolded, trimmed, normalised — and SELECT the victims before deleting, inside a transaction. Then add the constraint that prevents recurrence. §10.1, §10.2.

            

            
GotchaIs 'Ada' = 'ada' true?
              
Depends on the collation, which is a schema property. PostgreSQL: no. MySQL's usual default: yes. SQLite: no unless COLLATE NOCASE. Do not rely on it — normalise explicitly, and use a functional index if the normalisation would otherwise disable the index. §10.3.

            

            
Very commonHow should money be stored?
              
NUMERIC/DECIMAL, or integer minor units. Never FLOAT: 0.1 + 0.2 <> 0.3, and float addition is not associative, so SUM can vary with row order and therefore with the plan — which makes reconciliation impossible to close. §10.6.

            

            
Very commonHow do you know your query is correct?
              
Assert the invariants. Row count against the driving table. Conserved SUM after grouping. Mutually exclusive categories summing to the whole. One entity traced by hand end to end. Boundaries re-checked by shifting the date range a day. Then automate them as tests, because an assertion you have to remember to run is one you will forget. §10.7.

            

            
Very commonTwo reports disagree on revenue. How do you find out why?
              
Check the population (dates, time zone, status filters, test accounts), then the grain (order vs line item — fan-out), then the as-of time (late-arriving data), and only then the SQL. Use EXCEPT both ways on the key list. Present a reconciliation ladder: one row per adjustment from the raw total to each party's figure. §10.8.

            

            
Very commonYou are handed an unfamiliar table. What do you run?
              
A profile: row count, key uniqueness (COUNT(*) vs COUNT(DISTINCT id)), nulls per column, min/max on dates and amounts, cardinality of categoricals, orphans in both directions, and freshness (MAX(updated_at)). Then ask a human: what is the grain? §10.9.

            

            
Very commonThis query takes 40 minutes. What do you do?
              
Read the plan first. Look for a full scan where a seek was expected, estimated-versus-actual row divergence, a nested loop over a large inner side, and row counts exploding mid-plan. Then fix the index, the sargability, the partitioning, or the join — in that order. And ask whether it needs to be fast at all. §11.2.

            

            
Very commonWhy is WHERE YEAR(d) = 2026 slow?
              
Non-sargable: the index stores d, not YEAR(d), so the engine must compute the function per row. Use a half-open range on the bare column, or create a functional index on the expression. Same rule for LOWER(col), CAST(col), arithmetic on the column, and LIKE '%foo'. §11.5.

            

            
Very commonWhich queries can use an index on (a, b, c)?
              
Any leftmost prefix: a; a,b; a,b,c. Not b alone or c alone. And once a predicate is a range, later columns stop being seekable — so order equality columns first, most selective leftmost. §11.4.

            

            
Very commonWhen does an index hurt?
              
Write-heavy tables (every write maintains every index); low-cardinality columns (a partial index is the right tool); unselective queries above roughly 5–20% of rows, where a scan beats scattered lookups; small tables; redundant indexes duplicating a composite's prefix; and bulk loads. Auditing and removing unused indexes is a legitimate optimisation. §11.6.

            

            
ConceptualExplain the join algorithms.
              
Nested loop (small outer, indexed inner); hash join (large equality joins, memory-hungry, equality-only); merge join (both inputs sorted, supports inequality). A range join cannot hash, so it degrades to a nested loop — which is why adding any equality predicate transforms it. §11.7.

            

            
Very commonWhy are columnar databases faster for analytics?
              
Projection pruning (read only the columns you select), compression (one type, repeated values, often 10×), and vectorised execution. The trade-off: poor at single-row reads and row-level updates. Consequence for how you write SQL: SELECT * is genuinely expensive, and on scanned-bytes pricing it is an invoice line. §11.10, §11.11.

            

          

        

      


      

        
12.8 The trap questions ⭐⭐

        
Fourteen statements that sound right and are wrong. SQL screens are lost here — not on missing knowledge, but on a confidently wrong answer that the interviewer then probes.


        

          

            
The plausible claimWhy it is wrong

            
              
“COUNT(*) and COUNT(col) are the same”COUNT(col) skips NULLs. On a nullable column it is a filter in disguise (§1.3)

              
“COUNT(1) is faster than COUNT(*)”Identical on every modern optimiser. Pure folklore (§1.3)

              
“LIMIT 1 OFFSET 1 gives the second highest”It gives the second row. With a shared top value it returns the maximum again (§1.2, §4.4)

              
“NOT IN and NOT EXISTS are interchangeable”One NULL in the subquery makes NOT IN return zero rows (§2.4)

              
“A LEFT JOIN can only add rows”A WHERE filter on the right table silently demotes it to an inner join (§2.2)

              
“An INNER JOIN can only reduce rows”A one-to-many join multiplies them. Output can exceed both inputs (§2.6)

              
“DISTINCT fixes duplicate rows”It hides them. Any aggregate computed over the fanned-out rows was already wrong (§1.9, §2.6)

              
“SUM(x) OVER (ORDER BY d) is a row-by-row running total”The default frame is RANGE, so tied dates share a value and no row shows the intermediate (§5.2)

              
“LAST_VALUE gives the last value in the partition”The default frame ends at the current row, so it returns the current row (§5.7)

              
“LAG(x, 12) is the same month last year”It is twelve rows back. One missing month shifts every later comparison permanently (§5.6)

              
“BETWEEN two dates covers both days fully”On a timestamp column the end literal is midnight, so most of the last day is excluded (§6.5)

              
“NTILE(10) gives value-based deciles”It splits by row position, so identical values can land in different buckets (§4.7)

              
“Adding an index makes queries faster”It taxes every write, and on unselective queries the planner will ignore it anyway (§11.6)

              
“LIMIT 10 means I only scanned 10 rows”On BigQuery you are billed for bytes scanned; the limit is applied after (§11.11)

            
          

        


        

          
          The pattern behind all fourteen
          
Every one is a case where SQL is syntactically valid and semantically different from what you meant. There is no error message. That is why the habits in §10.7 — assert the row count, assert the conserved total, trace one entity by hand — matter more than knowing the individual traps: they catch the ones you have not memorised.

        


        

          
Likely interview questions

          

            
BehaviouralWhat is the worst SQL bug you have shipped?
              
Pick a real one from this list's shape — a silent semantic error, not a typo — and tell it in four beats: what the query looked like, what number it produced, how it was caught, and what you changed so the class of bug could not recur.
A good example structure: “A revenue report joined orders to line items to pick up the product category, which fanned the orders out and inflated revenue by about 20%. It was plausible enough to survive review and was caught when finance reconciled. The fix was to aggregate the items to one row per order before joining — and the durable fix was a test asserting that the report's total equals the source total, which now runs in CI.”
What makes this answer land is the third and fourth beats. Anyone can describe a bug. Describing the detection gap and the systemic fix is the difference between an anecdote and evidence that you learn.
What to avoid: a bug that was really someone else's fault, a bug with no consequence, or claiming you have never shipped one.

BehaviouralYou cannot finish the query in time. What do you do?

Likely interview questions

          

            
ConceptualIf you had to teach SQL for interviews in one hour, what would you cover?
              
Four things, in this order.
1. NULL semantics and the execution order. They explain most error messages and most silent wrong answers — the NOT IN collapse, the demoted LEFT JOIN, the alias that will not work in WHERE.
2. The three ranking functions and ties. One example — 100, 100, 90 → 1,2,3 / 1,1,3 / 1,1,2 — plus the top-N-per-group shape. That is the most-tested topic there is.
3. Conditional aggregation. SUM(CASE WHEN ...) is the answer to pivots, funnel counts, per-segment metrics and cohort cells, and most people never realise those are one technique.
4. Flag-and-cumsum. LAG → boundary flag → running SUM solves sessionisation, streaks, interval merging and run-length encoding — the entire “hard” tier from three lines.
And one habit rather than a technique: after any query, check that the row count and the total are what they should be. That catches the bugs you have not memorised, which is most of them.
