Correct on clean data is not correct Defining and finding duplicates, deleting all but one, case-folding and collation, silent type coercion, integer division and divide-by-zero, money in floating point, assertion queries, reconciliation and reproducibility.

Interviewers who have shipped anything ask from this level, because it is the difference between a query that is right and a query that is right on the data you have. Three things recur. Duplicates are a definition, not a fact — the demo table here has the same customer three times with different casing and whitespace, so “how many customers” has three defensible answers. Integer division truncates, so a conversion rate computed as wins/total is zero. And an aggregation should conserve its total — the habit of writing an assertion query after a join is the single most senior-looking thing you can volunteer in a SQL round.

10.1 Finding duplicates, and defining what duplicate means ⭐⭐

The query is four words. The question “duplicate on what?” is the actual work, and every answer gives a different count.

The template: GROUP BY key HAVING COUNT(*) > 1. What varies is the key, and the key is a business decision — exact row, one column, a normalised column, or a fuzzy match (§9.8).

Run itfour definitions of duplicate, four different countsidle
⌘/Ctrl + Enter 

          
Expected: 7 rows, 7 distinct whole rows, 6 distinct (email,name) pairs, 6 distinct raw emails, 5 distinct normalised. Five different numbers for “how many customers” from a seven-row table — and the last query names the offenders: three ada rows and two ben rows. Picking a number without stating the rule is how two teams end up disagreeing about the customer count.

        


        

          
Likely interview questions

          

            
Very commonHow do you find duplicate rows?
              
SELECT key, COUNT(*) FROM t GROUP BY key HAVING COUNT(*) > 1. To see the rows rather than the counts, use ROW_NUMBER() OVER (PARTITION BY key ORDER BY ...) and keep rn > 1 — that also tells you which copy you would keep.
Then the part that matters: ask what the key is. Exact whole-row duplicates are rare and usually a pipeline replay. Business duplicates are almost always on a normalised natural key — casefolded email, trimmed phone, canonical postcode — and the counts differ substantially between definitions.
What I would report back is not one number but the set: rows, distinct on the raw key, distinct on the normalised key. The gaps between those numbers are themselves a data-quality finding, and they tell the stakeholder something the single figure hides.
Then, separately, why the duplicates exist: a replayed load, a missing unique constraint, a genuine many-to-many being stored flat, or a fan-out introduced by an upstream join (§2.6). Deduplicating without answering that means doing it again next week.

            

          

        

      


      

        
10.2 Deleting duplicates, keeping one ⭐

        
A destructive operation, so the process matters more than the syntax.


        

          
          The order of operations
          
1. Agree the duplicate key and the survivor rule with whoever owns the data. 2. Write it as a SELECT of the rows that would be deleted, and have someone look at it. 3. Count them, and sanity-check that count against expectation. 4. Run inside a transaction with a rollback plan, or against a copy. 5. Add the constraint that prevents recurrence. Skipping step 2 is how a DELETE becomes an incident.

        


        
The dialect wrinkle: MySQL will not let you reference the table being deleted from in a subquery, so the idiom is a self-join DELETE t1 FROM t t1 JOIN t t2 ON ... or a wrapping derived table. PostgreSQL uses ctid, SQL Server uses a CTE with ROW_NUMBER and deletes from the CTE directly. Portable across most engines: delete where the primary key is not the surviving one.

Expected: three rows flagged for deletion (ids 2, 3 and 5), 7 rows before and 5 after, and then — because of the ROLLBACK — all 7 rows still present at the end. That last check is the habit: prove the transaction did what you thought. Swap ROLLBACK for COMMIT and re-run to see the real thing, then press Reset data.

        


        

          
Likely interview questions

          

            
Very commonDelete duplicate rows, keeping the earliest.
              
Portable form: DELETE FROM t WHERE id NOT IN (SELECT MIN(id) FROM t GROUP BY key). Modern form: a CTE with ROW_NUMBER() OVER (PARTITION BY key ORDER BY created, id) and delete where rn > 1 — which is better because the survivor rule is explicit and arbitrary tie-breaks are visible.
Watch the NOT IN / NULL interaction (§2.4): if the grouping key can be NULL, MIN(id) per group is fine but a NULL in the subquery's output would annihilate the whole predicate and delete nothing — or in a differently-shaped query, everything. COALESCE the key.
Dialect notes: MySQL forbids referencing the target table in a subquery, so use a self-join delete or wrap the subquery in another derived table. SQL Server lets you DELETE FROM cte directly, which is the cleanest version anywhere.
What I would actually say in an interview: show me the SELECT first. Run the query that identifies the victims, eyeball it, count it, then wrap the DELETE in a transaction. And afterwards add the unique constraint or unique index that makes it impossible to happen again — otherwise you have fixed the symptom on a schedule.

            

          

        

      


      

        
10.3 Case, whitespace and collation ⭐⭐

        
Whether 'A' = 'a' depends on the column's collation, which is a schema property most people never look at — and it silently changes the meaning of every comparison, join and GROUP BY.


        
The defaults differ. PostgreSQL is case-sensitive. MySQL's usual default collation (utf8mb4_0900_ai_ci) is case-insensitive and accent-insensitive. SQL Server depends on the instance collation, commonly case-insensitive. SQLite is case-sensitive unless a column is declared COLLATE NOCASE. So the same query genuinely returns different results on different engines.

        
The consequences: a JOIN on an email column matches or does not; a GROUP BY on a category produces one bucket or two; a UNIQUE constraint permits 'Ada' alongside 'ada' or does not. Normalise at write time if you can, and normalise explicitly in the query if you cannot.

The join matches 1 row exactly and 3 normalised; the GROUP BY gives 3 buckets raw and 2 normalised. Every one of those differences is invisible in the query text.

        


        

          
Likely interview questions

          

            
GotchaIs 'Ada' = 'ada' true in SQL?
              
It depends on the collation, which is a property of the column, table or database rather than of the query. PostgreSQL is case-sensitive by default; MySQL's common default is case-insensitive; SQL Server depends on the instance; SQLite is case-sensitive unless the column is COLLATE NOCASE.
So the honest answer is “check the collation”, and the practical answer is do not rely on it. Normalise explicitly — lower(trim(x)) — wherever the comparison matters, or better, normalise on write so the stored data has one canonical form.
The costs to mention. Wrapping a column in lower() makes the predicate non-sargable and disables the index (§11.5) — the fixes are a functional index on lower(email), or a stored normalised column. And a case-insensitive collation is not free either: it can prevent index use for range scans and it makes ORDER BY results engine-dependent.
The related trap worth naming: trailing whitespace. Some engines pad-compare CHAR columns so 'a ' equals 'a', and others do not, which is why VARCHAR/TEXT plus explicit trim is the safer combination.

            

          

        

      


      

        
10.4 Implicit type coercion ⭐

        
Comparing a string to a number sometimes works, sometimes silently does the wrong thing, and the rules differ by engine.


        
The classic: '10' > '9' is false, because string comparison is lexicographic — '1' sorts before '9'. If a numeric id or a version is stored as text, every range filter and every ORDER BY on it is wrong in a way that looks almost right.

        
The engine differences: PostgreSQL is strict and raises an error for most mixed-type comparisons, which is the good outcome. MySQL coerces aggressively — 'abc' = 0 is true in some modes, which has caused real security bugs. SQLite has type affinity: it will coerce a text value to numeric if the column's affinity says so, and compare as text otherwise.


        

          
Trapstring vs numeric comparison, and lexicographic orderingidle

Expected: '10' > 9 is 1 (coerced to numbers) but '10' > '9' is 0 (compared as text), and 1 = '1' is 0 in SQLite. Then the ordering: lexicographic gives 10, 100, 2, 9 while numeric gives 2, 9, 10, 100. If an id column is text, a “last 10 records” query ordered by it returns the wrong ten and nothing errors.

        


        

          
Likely interview questions

          

            
GotchaA filter on an id column returns the wrong rows. What do you suspect?
              
That the column is stored as text rather than a number, so comparisons and ordering are lexicographic: '10' < '9', and WHERE id > '100' excludes '99' while including '1000'.
Diagnose with typeof(col) in SQLite, or by inspecting the schema. Fix properly by correcting the column type; fix tactically with an explicit CAST in the query — while noting that casting a column disables the index (§11.5), so at scale you want a stored typed column or a functional index.
Two adjacent traps worth naming. Leading zeros: '007' and '7' are different strings and the same number, so a cast changes the join cardinality. MySQL's aggressive coercion: WHERE name = 0 can match every non-numeric string, which is both a correctness and a security problem — PostgreSQL raising an error instead is the safer design.
The general habit: be suspicious of any comparison between columns of different declared types, and make the conversion explicit so the reader can see which direction it goes.

            

          

        

      


      

        
10.5 Divide by zero and integer division ⭐

        
Two arithmetic hazards that produce plausible wrong numbers rather than errors. Covered briefly in §1.8; here is the full version.


        

          
Integer division
3 / 4 is 0 in PostgreSQL, SQL Server and Oracle. Every rate below 1 becomes zero. MySQL and SQLite do not truncate, so the bug is invisible locally and appears in the warehouse.

          
Divide by zero
PostgreSQL, SQL Server and Oracle raise. MySQL and SQLite return NULL. So the same query aborts a job on one engine and silently produces nulls on another.

        


        
Write the guard always: 100.0 * numerator / NULLIF(denominator, 0). It handles both hazards in one expression and it is portable.

            ⌘/Ctrl + Enter
          

          

          
Look at rate_int_div: zero for every country except the ones at 100%. Both operands are integers, so the division truncates. Note also 1/0 returns NULL here — on PostgreSQL that same expression aborts the query, which means a job that runs fine on SQLite or MySQL will fail in the warehouse. The NULLIF guard makes the behaviour identical everywhere.

        


        

          
Likely interview questions

          

            
Very commonYour percentage column is all zeros. What happened?
              
Integer division. Both operands are integers, so the engine truncates toward zero and every value below 1 becomes 0. It is not a formatting issue — the stored value really is zero.
Three fixes: multiply by 100.0 (or 1.0), CAST one side to numeric/float, or express the rate as AVG of a 0/1 indicator, which avoids division entirely and is my preference for readability.
The reason this bug reaches production: MySQL and SQLite do not truncate integer division, so it is invisible in a local sandbox and appears the first time the query runs against PostgreSQL, SQL Server or a warehouse. That asymmetry is why 100.0 * should be a reflex rather than a remembered fix.
Pair it with NULLIF(denominator, 0), because the same engines that truncate also tend to raise on divide-by-zero, and a nightly job that aborts on one empty group is worse than one that returns a null.

            

          

        

      


      

        
10.6 Floating point and money ⭐

        
0.1 + 0.2 <> 0.3. Everyone knows this and money columns are still declared as float.


        
The rule: use NUMERIC/DECIMAL for money, or store integer minor units (pence, cents). FLOAT and DOUBLE are binary approximations and cannot represent 0.1 exactly, so sums drift and equality comparisons fail unpredictably.

        
The subtler consequence: floating-point addition is not associative, so SUM over a float column can return a different total depending on row order — which means a parallel or differently-planned execution of the same query gives a slightly different answer. That is a genuinely maddening class of reconciliation bug and it is worth naming.

Expected: 0.1 + 0.2 prints as 0.30000000000000004 and the equality is 0. Then watch still_equal in the second query flip to 0 as the repeated addition diverges from the multiplication. Adding 0.1 ten times and multiplying 0.1 by ten are not the same number in binary floating point, and if one of those is a running balance you have a reconciliation problem.

        


        

          
Likely interview questions

          

            
Very commonHow should you store money in a database?
              
NUMERIC(p,s) / DECIMAL, which is exact decimal arithmetic, or an integer count of minor units (pence, cents) with the scale documented. Never FLOAT or DOUBLE: they are binary approximations, cannot represent 0.1 exactly, and accumulate drift over sums.
Consequences to name. Equality comparisons on floats fail unpredictably, so any WHERE amount = 0.3 is unreliable — compare within an epsilon, or use exact types and avoid the question. And floating-point addition is not associative, so SUM over a float column can vary with row order and therefore with the execution plan; two runs of the same query can disagree in the last decimal place, which makes reconciliation impossible to close.
The trade-off, stated honestly: NUMERIC is slower than FLOAT because it is software arithmetic rather than hardware. For money that is entirely the right trade. For scientific measurements or ML features, FLOAT is correct and the precision is irrelevant.
One more: rounding is a business rule. Half-up, half-even (banker's rounding), and where in the pipeline you round all change the total. Round once, at the end, and document which convention.

            

          

        

      


      

        
10.7 Assertions: did the total survive? ⭐⭐

        
The single most senior-looking habit you can display in a SQL round: after transforming data, prove the transformation conserved what it should have.


        
The idea: most transformations have an invariant. A GROUP BY should conserve the sum. A join should conserve the row count of the driving table. A pivot's row totals should equal the original group totals. Writing a query that checks the invariant costs a minute and catches fan-out, dropped rows and demoted outer joins immediately.

Joining orders to order_items inflates the total from 4,255 to 5,115 — the fan-out from §2.6, caught automatically by a three-line assertion rather than by someone noticing a suspicious figure in a meeting. That is the entire argument for writing these.

        


        

          
Likely interview questions

          

            
Very commonHow do you know your query is correct?
              
Check the invariants, and name them. This is the question where most candidates say “I'd eyeball the output” and the good answer is a short list of things that must be true.
Row counts. After a join, compare against the driving table's count. Fewer means rows were dropped — an inner join or a demoted outer join. More means fan-out. Either way you now know which.
Conserved totals. A GROUP BY should preserve SUM of the measure. If it does not, something was filtered or duplicated.
Partitions. Mutually exclusive categories should sum to the whole. If “new + retained + reactivated” does not equal “active”, two definitions overlap (§7.6).
Spot checks. Pick one entity and verify it by hand end to end. Aggregates hide individual errors; one traced row catches them.
Boundaries. Re-run with the date range shifted by a day and confirm the numbers move as expected — that catches the BETWEEN bug from §6.5.
Then the production version: put these in the pipeline as tests. dbt calls them unique, not_null, relationships and singular tests; without a tool they are just SELECT statements that must return zero rows. Saying “an assertion that isn't automated is a thing you'll forget to run” is a good closing line.

            

          

        

      


      

        
10.8 Reconciling two sources that disagree ⭐

        
“Finance says 4,255 and the dashboard says 5,115.” A procedure, not a query — and having the procedure is the answer.


        
The order of investigation, because it moves from cheapest to most expensive: 1. Are the two counting the same population? Different date ranges, time zones, status filters, or test accounts included in one and not the other. 2. The same grain? One at order level, one at line-item level — that is §2.6. 3. The same point in time? Late-arriving data means a figure computed yesterday differs from the same figure recomputed today. 4. Only then look for a bug in the SQL.

        
The tool is EXCEPT both ways (§1.11): the symmetric difference tells you exactly which keys are in one source and not the other, which usually identifies the cause in one query.

The second result set is the reconciliation itself. Each row is one hypothesis about why the two numbers differ, and you read down until you find the step that produces the other party's figure. Presenting a disagreement this way — “your number is my step C, mine is step E, and the difference is the item-level fan-out” — resolves the argument in one message instead of three meetings.

        


        

          
Likely interview questions

          

            
Very commonTwo reports show different revenue for the same month. How do you find out why?
              
Work down a checklist rather than reading the SQL first, because the cause is usually a definition rather than a bug.
Population: same date range, same time zone, same status filter, same treatment of test accounts, internal orders and refunds? A one-day boundary difference (§6.5) or a UTC-versus-local day (§6.7) explains a surprising share of these.
Grain: is one at order level and the other at line-item level? That is fan-out and it inflates by exactly the average items per order (§2.6).
As-of time: late-arriving data means the same query run on two dates gives two answers. Compare snapshots, not queries.
Then the SQL: use EXCEPT in both directions on the key list to find which records one side has and the other does not — that usually names the cause immediately.
How I would present it: a reconciliation ladder, one row per adjustment, starting from the raw total and ending at each party's figure. It converts “your number is wrong” into “here are the four filters between us”, and it is the artefact that actually closes the conversation. Then agree one definition, put it in a shared model, and delete the other query.

The cheap checks worth running on any table you have just met, before you trust anything you compute from it.

The referential check is the useful one: 12 orders have no line items, which is a genuine finding — it explains the gap between the order total and the item total in §10.8, and it is the sort of thing nobody notices until a number does not reconcile. Running this profile on an unfamiliar table takes thirty seconds and saves an afternoon.

        


        

          
Likely interview questions

          

            
Very commonYou are handed an unfamiliar table. What do you run first?
              
A profile, not a query against the business question. Six things, in one statement where possible.
Volume — COUNT(*), and rows per day to see the load pattern and any gaps. Key uniqueness — COUNT(*) versus COUNT(DISTINCT id); if they differ, the “primary key” is not one and every join will fan out. Nullability — COUNT(*) - COUNT(col) per column, which tells you where the joins and filters will silently drop rows. Ranges — MIN/MAX on dates and amounts, which catches sentinel values like 1900-01-01 and −1. Cardinality — distinct counts on the categorical columns, so you know whether status has 4 values or 4,000. Referential integrity — orphans in both directions.
Then the question I would ask a human: what is the grain? One row per what? Every downstream mistake in this subject — fan-out, double counting, wrong denominators — traces back to not knowing the answer.
And check the freshness: MAX(updated_at) against now. A table that stopped updating three weeks ago will happily answer every query you write.

            

          

        

      


      

        
10.10 Making a query reproducible

        
The same query, the same data, the same answer — tomorrow, and on someone else's machine. Less obvious than it sounds.


        

          

            
Source of non-determinismFix

            
              
ORDER BY without a total order (§4.10)Append a unique column to the sort key

              
LIMIT without ORDER BYAlways order before limiting

              
current_date / now() inside the queryPass the reference date in as a parameter

              
RANDOM() for samplingSeed it, or sample deterministically on a hash of the key

              
Bare columns with GROUP BY (§1.4)Aggregate or group every column

              
Late-arriving dataFilter on an ingestion watermark, not on “everything up to now”

              
SELECT *Name the columns — a new upstream column changes the result shape

              
Float SUM order-dependence (§10.6)Use exact numeric types for anything reconciled

            
          

        


        
Deterministic sampling deserves a mention because it is genuinely useful: WHERE abs(hash(user_id)) % 100 < 10 gives a stable 10% sample — the same users every time, no seed to manage, and it is consistent across tables joined on that key. ORDER BY RANDOM() LIMIT n gives a different sample every run and also sorts the whole table.


        

          
Run itdeterministic vs random sampling, twice eachidle

          
          

            
            
            
            ⌘/Ctrl + Enter
          

          

          
The two deterministic runs are identical; the two random runs are not — and they will differ again next time you press Run. For a reproducible analysis, a debugging sample you want to revisit, or a test fixture, the hash-modulo approach is strictly better. It is also the standard way to assign users to experiment arms, for exactly the same reason.

        


        

          
Likely interview questions

          

            
CodingHow would you take a reproducible 10% sample?
              
Hash the key and take a modulo: WHERE abs(hashtext(user_id)) % 10 = 0 in PostgreSQL, MOD(ABS(FARM_FINGERPRINT(CAST(user_id AS STRING))), 10) = 0 in BigQuery. Same rows every run, no seed to store, and — the property that matters most — consistent across tables, so a sampled fact table joins correctly to a sampled dimension.
Why not ORDER BY RANDOM() LIMIT n: it is non-reproducible, and it sorts the entire table to pick a few rows, so it is also slow. TABLESAMPLE is faster but samples blocks rather than rows, which correlates the sample with physical layout and is not stable across runs either.
The caveat worth raising: hash sampling on user_id gives you a random sample of users, not of events. If users have wildly different event counts, those are different populations and the choice depends on the question. Sampling on the event id instead gives an event sample and breaks per-user analysis.
And the same technique is how deterministic experiment assignment works — hash the user id with the experiment name and bucket it — which is a nice connection to make.
