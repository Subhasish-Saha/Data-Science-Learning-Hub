3.1 Scalar, row and table subqueries

A subquery's shape determines where it is legal. Three shapes, three sets of places they can go.

ShapeReturnsLegal inFails when
ScalarOne row, one columnAnywhere a value goes: SELECT, WHERE, ON, CASEIt returns more than one row — a runtime error, not a compile one
RowOne row, many columnsTuple comparison: WHERE (a,b) = (SELECT x,y ...)Not supported in SQL Server; niche elsewhere
TableMany rowsFROM, JOIN, IN, EXISTSUsed where a scalar was expected

The failure worth knowing: a scalar subquery that unexpectedly returns two rows raises an error in PostgreSQL and SQL Server, but SQLite and MySQL's older modes silently take the first row. That is a data-dependent bug: it works until the day a duplicate appears upstream. If a subquery must be scalar, make it provably scalar — aggregate it, or add LIMIT 1 with an explicit ORDER BY so at least the choice is deterministic.

Likely interview questions

          

            
ConceptualWhere can a subquery appear?
              
In SELECT (scalar only), in FROM as a derived table, in JOIN, in WHERE/HAVING with IN, EXISTS, ANY/ALL or a scalar comparison, and in some engines in ORDER BY, GROUP BY and even VALUES.
The rule that ties it together is shape: a position that expects a single value needs a subquery returning one row and one column, and everything else needs a table. A derived table in FROM must be aliased in most dialects — forgetting the alias is the single most common syntax error here.
Two things worth adding. A lateral subquery (LATERAL in PostgreSQL, CROSS APPLY in SQL Server) can reference columns from earlier FROM items, which is how you write “the three most recent orders per customer” without a window function. And a scalar subquery in SELECT that references the outer row is a correlated subquery, evaluated per row — §3.2.

            

            
GotchaWhat happens if a scalar subquery returns two rows?
              
In PostgreSQL, SQL Server and Oracle you get a runtime error — “more than one row returned by a subquery used as an expression”. That is the good outcome, because it is loud.
In SQLite and MySQL the behaviour is looser: SQLite takes the first row it happens to find, and older MySQL modes did similar. The query succeeds and returns a plausible number chosen non-deterministically. It will work in development and produce a different answer in production once the upstream table gains a duplicate.
So the defensive habit: if a subquery is supposed to be scalar, make it provably scalar — wrap it in MAX()/MIN() if any row will do, or add ORDER BY ... LIMIT 1 so the choice is at least deterministic and visible. And if it should never have two rows, that is a uniqueness assumption worth asserting explicitly (§10.7) rather than trusting.

            

          

        

      


      

        
3.2 Correlated subqueries, and what they cost ⭐

        
A subquery that references the outer row. Conceptually a loop, which is both why it is expressive and why it has a reputation.


        
WHERE e.salary > (SELECT AVG(salary) FROM employees x WHERE x.dept_id = e.dept_id) cannot be evaluated once — it depends on e.dept_id, so logically it runs per outer row. That is O(n·m) in the naive execution model, and it is where “correlated subqueries are slow” comes from.

        
The modern correction: optimisers decorrelate. PostgreSQL and SQL Server will often rewrite a correlated aggregate into a join against a grouped derived table, giving you the same plan you would have written by hand. So the honest answer is “it may be fine, and I would check the plan” rather than a blanket condemnation. What optimisers handle less well is a correlated subquery in the SELECT list, especially several of them, and correlation inside OR branches.


        

          
          The rewrite worth knowing by heart
          
Almost every correlated aggregate has a window-function twin, and the window version reads better and is computed in one pass: AVG(salary) OVER (PARTITION BY dept_id) replaces the correlated AVG above. Being able to convert between the two forms on demand is one of the more useful party tricks in a SQL interview.

Likely interview questions

          

            
Very commonWhat is a correlated subquery, and are they slow?
              
One that references a column from the outer query, so it cannot be evaluated independently — logically it runs once per outer row.
On whether they are slow, give the calibrated answer rather than the folklore. Historically yes, because the naive execution is a nested loop, O(outer × inner). Now often no: PostgreSQL, SQL Server and modern MySQL decorrelate many of them, rewriting a correlated aggregate into a hash join against a grouped subquery — the exact plan you would have hand-written. So the right answer is “check EXPLAIN; the optimiser may already have fixed it”.
Where they genuinely stay slow: several correlated subqueries in the SELECT list (each one is a separate pass), correlation inside an OR, and correlated subqueries over a table with no index on the correlating column.
Then offer the two rewrites, which is what the question is really fishing for: a window function if you want the aggregate alongside every row, or a grouped derived table joined back if you want one row per group. Both are single-pass and both read better.

            

            
CodingEmployees earning above their department's average — three ways.
              
Correlated subquery: WHERE e.salary > (SELECT AVG(salary) FROM employees x WHERE x.dept_id = e.dept_id). Direct transcription of the requirement.
Join to a grouped derived table: JOIN (SELECT dept_id, AVG(salary) a FROM employees GROUP BY dept_id) d USING (dept_id) WHERE salary > d.a. One pass over the table for the averages, then a hash join.
Window function: compute AVG(salary) OVER (PARTITION BY dept_id) in a subquery and filter it in the outer WHERE. Single pass, and it is the version I would write.
The edge case to volunteer: employees with a NULL department. In all three forms they drop out — the correlated average over no rows is NULL, the join finds no group, and the window partition of one gives an average equal to the salary so the strict > fails. If unassigned staff should be reported, that needs deciding explicitly, and noticing it unprompted is worth more than the query.

            

          

        

      


      

        
3.3 CTEs vs subqueries vs temp tables ⭐

        
Mostly a readability decision, with two real technical differences worth knowing.


        

          
Derived table
Inline, in FROM. Fine for one use. Nesting three deep is where queries become unreadable.

          
CTE (WITH)
Named, top-down, reusable within the query, and the only way to recurse. Default to this.

          
Temp table
Materialised, can be indexed, survives across statements. For genuinely expensive intermediates reused many times.

        


        
Difference one: materialisation. A CTE referenced twice may be computed twice — it is a name, not necessarily a cached result. PostgreSQL before v12 always materialised CTEs (an optimisation fence); since v12 it inlines them when referenced once, and you can force either behaviour with MATERIALIZED / NOT MATERIALIZED. That history matters because a lot of tuning advice on the internet is about the pre-12 behaviour.

        
Difference two: statistics. A temp table can be analysed and indexed, so the planner has real statistics for it. A CTE gets estimates. For a multi-step pipeline where one intermediate is large and reused, materialising into a temp table and indexing the join key is sometimes an order of magnitude faster — and that is a good answer to “how would you speed up this 200-line query”.

Likely interview questions

          

            
Very commonCTE vs subquery — when do you use which?
              
Readability first: a CTE names the intermediate result, reads top-down, can be referenced more than once, and can be selected from in isolation while debugging. A derived subquery is fine for a single simple use. Beyond two levels of nesting, CTEs win decisively.
Then the two technical differences. Recursion is only possible with a CTE. And materialisation semantics differ: a CTE is a name, not a guaranteed cached result, so referencing it three times may compute it three times. PostgreSQL materialised CTEs unconditionally before v12 and now inlines single-reference ones, with MATERIALIZED/NOT MATERIALIZED as explicit control. SQL Server and MySQL have always inlined.
The performance caveat to state honestly: CTEs are not faster by nature, and the belief that they are comes from the old Postgres fence. If an intermediate is expensive and reused several times, the real answer may be a temp table you can index — which is also the answer to “this 300-line query times out”.

            

          

        

      


      

        
3.4 Recursive CTEs ⭐

        
The only iterative construct in standard SQL. Three parts, one termination condition, and two problems it solves that nothing else can.


        
The anatomy: an anchor query producing the starting rows; UNION ALL; a recursive query that references the CTE itself and consumes the rows the previous iteration produced; and a condition that eventually yields no new rows, which is what terminates it.

        
Two uses, and they cover nearly everything. Hierarchy traversal — walk an employee-manager or category-parent tree to arbitrary depth, accumulating a depth counter and a path string. Sequence generation — produce a run of dates or integers that does not exist in any table, which is how you build the date spine in §6.3 on engines without generate_series.


        

          
          Infinite recursion is a data problem, not a syntax one
          
A cycle in the hierarchy — A reports to B reports to A, which happens in real org tables — makes the recursion never terminate. Guard it: carry the path and add WHERE path NOT LIKE '%' || e.name || '%', or carry a depth counter and cap it. SQL Server has MAXRECURSION (default 100), PostgreSQL and SQLite have no default limit and will happily run until they exhaust memory. Volunteering the cycle guard is a strong signal.

Likely interview questions

          

            
Very commonWrite a recursive CTE to find everyone reporting up to a given manager.
              
Anchor on the manager, then repeatedly join employees whose manager_id is already in the result:
WITH RECURSIVE r AS (SELECT id, name, 0 AS depth FROM employees WHERE id = :mgr UNION ALL SELECT e.id, e.name, r.depth+1 FROM employees e JOIN r ON e.manager_id = r.id) SELECT * FROM r WHERE id <> :mgr
Four things to say while writing it. The UNION ALL must be ALL — plain UNION deduplicates each iteration, which is slower and can mask a cycle. Carry a depth column, both for reporting and as a termination guard. Carry a path string if you want to detect cycles properly or order the output as a tree. And exclude the anchor row at the end if the question asks for reports rather than the manager themselves.
The dialect notes: RECURSIVE is required in PostgreSQL, MySQL and SQLite, and forbidden in SQL Server (which infers it) — and SQL Server caps recursion at 100 levels unless you say OPTION (MAXRECURSION n).

            

            
CodingGenerate every date in a range, including days with no data.
              
PostgreSQL: generate_series('2026-01-01'::date, '2026-03-31', '1 day'). BigQuery: GENERATE_DATE_ARRAY plus UNNEST. Snowflake: GENERATOR with ROW_NUMBER. MySQL, SQLite, SQL Server: a recursive CTE, or a permanent calendar table.
The recursive form: anchor on the start date, then SELECT date + 1 FROM cte WHERE date < end.
Then say why you want it, because that is the real question: grouping by day only returns days that have rows, so a gap in the data becomes a missing row rather than a zero. Any chart, any “7-day average” and any period-over-period comparison built on that is quietly wrong — the average divides by however many rows exist instead of by seven. The fix is always the same shape: generate the spine, then LEFT JOIN the facts onto it.
In a real warehouse the better answer is a persisted dim_date table with flags for weekends, holidays and fiscal periods. Recursive generation is for when you do not have one.

            

          

        

      


      

        
3.5 Aggregating an aggregate ⭐

        
“The average order value per customer” and “the average customer's order value” are different numbers. Recognising two-level aggregation in a question is a real skill and it is tested constantly.


        
You cannot nest aggregates directly — AVG(SUM(x)) is a syntax error, because SUM already collapsed the rows. You need two levels: a subquery or CTE that groups at the finer grain, then an outer aggregate over that result.


        

          
Average of all orders
AVG(amount) over the raw table. Every order weighted equally, so a customer with 20 orders dominates.

          
Average per customer
Sum per customer, then average those. Every customer weighted equally. Usually what a stakeholder means.

        


        
The interview move: when a question contains “average of a total”, “count of a count”, “the median customer” or “per user per day”, say out loud “this is two levels of aggregation — what is the grain of the inner one?” That sentence is worth more than the query, because ambiguity about grain is where the wrong answer comes from.

Likely interview questions

          

            
Very commonWhat is the average number of orders per customer?
              
Ask one clarifying question first, because there are two answers and they differ by a lot: per customer who has ordered, or per customer on the books (including those with zero)? The second requires a LEFT JOIN from customers so the zeros are in the denominator.
Then: SELECT AVG(n) FROM (SELECT c.id, COUNT(o.id) AS n FROM customers c LEFT JOIN orders o ON o.customer_id = c.id GROUP BY c.id). The COUNT(o.id) rather than COUNT(*) is what makes the zero-order customers show 0 rather than 1 (§1.3).
The shortcut worth knowing and its caveat: COUNT(*) * 1.0 / COUNT(DISTINCT customer_id) over the orders table gives the same figure only for customers who have ordered, and it silently uses a different denominator. It is fine if you say which denominator you used.
And the follow-up that usually lands next: “is the mean the right statistic here?” Order counts are heavily right-skewed, so the median and the distribution are more informative — which is a good opening to talk about §9.1.

            

            
GotchaWhy can't you write AVG(SUM(x))?
              
Because SUM(x) has already collapsed the rows of the group into one value, so there is no set left for AVG to average. Aggregates operate on rows, and after the first aggregate there is one row per group. Engines reject it as “aggregate function calls cannot be nested”.
The fix is two levels: group at the fine grain in a subquery or CTE, then aggregate that result. Which is the whole point of the section — the syntax error is the language telling you the question has two grains.
The one place nesting is legal and looks like an exception: an aggregate inside a window function's argument. SUM(SUM(amount)) OVER () is valid, because the inner SUM is the group aggregate and the outer is a window over the grouped rows. That is the trick behind percent-of-total in one query, and it is §3.6.

            

          

        

      


      

        
3.6 Percent of total, and percent of group ⭐

        
A share calculation needs the row's value and a total computed over a wider set. There are three ways to get that total, and one of them is a single elegant line.


        
The elegant one: a window aggregate over an aggregate. SUM(SUM(amount)) OVER () — the inner SUM is the group total, the outer window SUM adds up all the groups, and because windows run after GROUP BY this is legal and single-pass. Change OVER () to OVER (PARTITION BY region) and you get percent-of-region instead. That one substitution is the whole flexibility of the approach.

        
The alternatives: a scalar subquery holding the grand total (readable, computes it separately), or a CROSS JOIN to a one-row totals subquery (useful when you need several totals at once).

That is a free correctness check on any share calculation, and it is worth running — a share column that does not sum to 100 means the denominator is not what you think it is.

        


        

          
Likely interview questions

          

            
Very commonShow each region's revenue as a percentage of the total.
              
100.0 * SUM(amount) / SUM(SUM(amount)) OVER (), grouped by region. The nested aggregate looks odd the first time but is standard: the inner one is the group's sum, the outer window sums across groups because windows are evaluated after grouping.
Three details that make this a complete answer. Multiply by 100.0 not 100, or integer division truncates the whole thing to zero on Postgres. Guard the denominator with NULLIF(..., 0) if the filter could produce an empty set. And check it sums to 100 — if it does not, the denominator is over a different population than you intended, which is the actual bug this question is looking for.
Alternatives worth naming: a scalar subquery for the total (clearer to some readers, computed independently), or RATIO_TO_REPORT in Oracle and Snowflake, which is this exact operation as a built-in.

            

          

        

      


      

        
3.7 Pivot without PIVOT ⭐⭐

        
Turning rows into columns. PIVOT exists in SQL Server, Oracle, Snowflake and DuckDB and nowhere else — so the portable answer is conditional aggregation, and it is better anyway.


        
The pattern is exactly §1.10 applied deliberately: one SUM(CASE WHEN ...) per output column. Group by whatever you want on the rows, and write one conditional aggregate per value you want as a column.


        

        
The limitation to state before being asked: the columns are hard-coded, so a new status value silently does not appear. SQL has a fixed result shape determined at parse time, which means a truly dynamic pivot is impossible in pure SQL — you need dynamic SQL that reads the distinct values and builds the query text, or you return long-format rows and pivot in the presentation layer. Saying that is the mature answer; candidates who claim they can do a dynamic pivot in one statement are wrong.

In the count pivot, dropping ELSE is load-bearing: with ELSE 0 every column would equal total.

        


        

          
Likely interview questions

          

            
Very commonPivot rows into columns without a PIVOT operator.
              
Conditional aggregation: one SUM(CASE WHEN key = 'value' THEN measure ELSE 0 END) per output column, grouped by the row dimension. Portable to every engine, and readable.
Use SUM with ELSE 0 for measures, and COUNT(CASE WHEN ... THEN 1 END) without an ELSE for counts — because COUNT counts a zero but skips a NULL, so ELSE 0 would count every row. If the engine supports it, SUM(measure) FILTER (WHERE key = 'value') is the standard spelling and reads better.
Then state the constraint, because it is the follow-up: the column list is fixed at parse time. A new key value will not appear as a new column. SQL result shapes are static, so a genuinely dynamic pivot requires either dynamic SQL built from a first query over the distinct values, or returning long format and pivoting in the BI tool or in pandas. That is not a limitation of your technique, it is a property of SQL.

            

          

        

      


      

        
3.8 Unpivot without UNPIVOT

        
The reverse: wide columns into tall rows. Less glamorous, and more often what you actually need, because long format is what joins and aggregates well.


        
The portable form is UNION ALL, one branch per column, each branch labelling the metric. It is verbose in proportion to the column count, which is honest — an eighty-column wide table genuinely is painful to unpivot in SQL, and that is a signal the table is modelled wrong.

        
The neater forms: a CROSS JOIN to a small list of metric names with a CASE picking the right column (one scan instead of N), UNPIVOT in SQL Server and Oracle, UNNEST over an array in PostgreSQL and BigQuery, or UNPIVOT in Snowflake and DuckDB.

Likely interview questions

          

            
CodingTurn twelve monthly columns into one row per month.
              
UNION ALL with twelve branches is the portable answer, each branch selecting the key, a literal month label, and that month's column. Verbose but obviously correct, and it is what to write if the engine has nothing better.
Better if available: UNPIVOT (SQL Server, Oracle, Snowflake, DuckDB), or in PostgreSQL/BigQuery build an array of the values and UNNEST it alongside an array of labels, which is a single scan.
The CROSS JOIN trick is the portable single-scan version: cross-join to a twelve-row list of month labels and use a CASE on the label to pick the matching column. Same output, one pass.
What I would actually say in an interview: the need to unpivot twelve monthly columns is a data-modelling smell. A long table keyed on (entity, month) makes every downstream query easier, and adding a thirteenth month becomes a row rather than a schema migration. If the wide format is a fixed input you cannot change, unpivot it once in a staging model rather than repeatedly in every query.

            

          

        

      


      

        
3.9 GROUPING SETS, ROLLUP and CUBE

        
Several levels of aggregation from one pass. Widely supported, entirely absent from SQLite — which makes this a useful lesson in emulating a missing feature.


        

          

            
ConstructProducesGrouping combinations for (a, b)

            
              
GROUP BY a, bOne level(a,b)

              
GROUPING SETS ((a,b),(a),())Exactly the sets you listwhatever you wrote

              
ROLLUP(a, b)A hierarchy, right to left(a,b), (a), ()

              
CUBE(a, b)Every subset(a,b), (a), (b), ()

            
          

        


        
Why they matter: subtotals and grand totals in the same result set, computed in one pass instead of a UNION ALL per level. ROLLUP(region, city) gives you city detail, a region subtotal and a grand total together — exactly the shape of a management report.

        
The GROUPING() function tells you which rows are subtotals, because a subtotal row has NULL in the columns it aggregated over — indistinguishable from a genuine NULL in the data without it. GROUPING(city) = 1 means “this row is a total across cities”. Forgetting this is how subtotal rows get mislabelled as “unknown”.

        
Support: PostgreSQL, SQL Server, Oracle, MySQL (ROLLUP only), BigQuery, Snowflake, Spark, DuckDB all have them. SQLite has none, so the cell below emulates ROLLUP with UNION ALL — which is also exactly what you would write on any engine that lacked it.

That is the performance argument for the feature, and it is why emulation is a fallback rather than a preference. Likely interview questions

          

            
ConceptualExplain ROLLUP vs CUBE vs GROUPING SETS.
              
GROUPING SETS is the general form: you list exactly which combinations of grouping columns you want, and the engine computes each in one pass. ROLLUP(a,b,c) is shorthand for a hierarchy — (a,b,c), (a,b), (a), () — which suits naturally nested dimensions like country/region/city. CUBE(a,b,c) is every subset, 2n of them, for when the dimensions are independent.
Say the practical points. The benefit is one pass instead of N, plus one result set the BI tool can render directly. The cost is that CUBE grows exponentially, so on four or five dimensions you should be listing GROUPING SETS explicitly rather than cubing.
And the detail that shows you have used them: subtotal rows carry NULL in the rolled-up columns, which is ambiguous with real NULLs in the data. GROUPING(col) returns 1 for “this is a subtotal over col”, and you wrap it in a CASE to produce a readable label. Without it, a report shows “(null)” where it means “Total”.

            

          

        

      


      

        
3.10 FILTER (WHERE ...) ⭐

        
The standard, readable spelling of conditional aggregation. Worth knowing both because it is nicer and because knowing where it is unavailable is itself a dialect signal.


        
COUNT(*) FILTER (WHERE status = 'completed') means exactly COUNT(CASE WHEN status = 'completed' THEN 1 END) and reads far better, especially with several of them side by side. It is ANSI SQL, and it is supported in PostgreSQL, SQLite and DuckDB. It is not in MySQL, SQL Server, BigQuery or Snowflake, where you write the CASE form.

        
One genuine advantage beyond looks: with FILTER there is no ELSE to get wrong, so the COUNT(... ELSE 0) bug from §1.10 cannot happen. And FILTER composes with window functions in PostgreSQL, letting you write a filtered running total, which the CASE form also does but less clearly.

Likely interview questions

          

            
ConceptualWhat is FILTER and how does it differ from WHERE?
              
WHERE filters the rows that reach the whole query. FILTER attaches to a single aggregate and restricts only that aggregate's input, so different columns in the same SELECT can be computed over different subsets. That is the entire distinction, and it is why FILTER can produce a total and a subtotal side by side while WHERE cannot.
It is standard ANSI SQL, supported in PostgreSQL, SQLite and DuckDB; MySQL, SQL Server, BigQuery and Snowflake require the equivalent CASE form. So the practical answer is: use FILTER where you have it, know the CASE translation cold, and never assume portability.
The small correctness win worth mentioning: with FILTER there is no ELSE branch to get wrong, so you cannot accidentally write COUNT(CASE WHEN ... ELSE 0 END) and count every row.
