They all query the same seeded 12-table demo database — 174 rows, small enough to check answers by eye and built to be deliberately awkward: four tied salary pairs, an employee with a NULL department, a department with nobody in it, a user who checked out before adding to cart, overlapping and nested subscription rows, one-to-many order items that inflate a naive SUM, and the same customer three times under different casing. Every trap in this subject fires in front of you rather than being described.

Part 11 runs EXPLAIN QUERY PLAN for real — create an index and watch the plan flip from SCAN to SEARCH, then wrap the column in a function and watch it flip back. Every cell also states its expected output, so the pages still work offline.

⚠ Dialect honesty

The answers are written in portable SQL and the runnable cells execute on SQLite, which is not what you will be interviewed on. Where a dialect genuinely differs, it is called out inline — and the full comparison across PostgreSQL, MySQL, SQL Server, BigQuery, Snowflake and SQLite is in §12.11. The differences that cause silent bugs rather than syntax errors are worth memorising:

  • Integer division truncates on PostgreSQL, SQL Server and Oracle; it does not on MySQL and Snowflake. So COUNT(x)/COUNT(*) is 0 on one and correct on the other, with no error either way.
  • Default collation is case-sensitive on PostgreSQL and case-insensitive on MySQL, so the same JOIN matches a different number of rows.
  • Divide by zero raises on PostgreSQL and SQL Server, returns NULL on MySQL and SQLite.
  • QUALIFY, FILTER, GROUPING SETS and the percentile functions exist on some engines and not others — §12.11 has the grid.

SQLite also lacks GROUPING SETS and PERCENTILE_CONT, which is why §3.9 and §9.1 show you how to build them by hand — a more useful skill than knowing the built-in.
