11.1 Logical order vs the physical plan ⭐

§1.1 described what a query means. This is about what the engine actually does, and the two are deliberately different.

The logical order defines semantics. The optimiser is free to execute in any order that produces the same result, and it routinely does: predicate pushdown applies filters before joins, join reordering starts with whichever table is most selective, projection pruning stops reading columns you never reference, and limit pushdown can stop a scan early.

Why this matters for you: it means “filter early” is often already done for you, so hand-optimising by rewriting the query is frequently pointless. What the optimiser cannot fix is a missing index, a non-sargable predicate, a bad row estimate, or a fundamentally wrong join. Those are the four things worth looking for.

Likely interview questions
ConceptualShould you rewrite a query to filter earlier?

Usually not, because the optimiser already pushes predicates down. Moving a WHERE clause around in an inner-join query typically produces an identical plan, and time spent on it is wasted.

Where rewriting genuinely helps: when the optimiser cannot push the filter. A predicate on the output of a window function, an aggregate, or a non-inlinable CTE forms an optimisation barrier, so filtering before that step is a real change. Similarly, replacing a correlated subquery in the SELECT list with a join or a window can turn N passes into one (§3.2).

The four things that actually matter, in order: a missing index on the join or filter column; a non-sargable predicate that disables an index you already have (§11.5); a bad cardinality estimate that makes the planner choose a nested loop over a hash join; and a wrong join that is fanning out and forcing the engine to process rows that should not exist.

So the method is: read the plan, find the step with the largest row count or cost, and fix that. “I would look at EXPLAIN before changing anything” is a much better answer than any specific rewrite.

11.2 Reading an EXPLAIN plan ⭐⭐

The one diagnostic skill in this level. And you can practise it right here.

What to look for, in order. A full scan on a large table where you expected an index seek. The estimated versus actual row counts — a big divergence means the planner is working from bad statistics and every downstream choice is suspect. The join algorithm (§11.7). And sorts and spills — a sort that exceeds working memory writes to disk and dominates everything.

The syntax: EXPLAIN shows the plan; EXPLAIN ANALYZE in PostgreSQL and MySQL 8 actually runs it and reports real timings and row counts, which is far more useful. SQL Server has SET SHOWPLAN_ALL or the graphical plan; BigQuery shows the execution graph after the fact; SQLite has EXPLAIN QUERY PLAN.

Likely interview questions

          

            
Very commonThis query takes 40 minutes. Walk me through what you do.
              
Do not start by rewriting. Start by measuring.
1. Read the plan. EXPLAIN ANALYZE where available, so you get actual row counts and timings rather than estimates. Find the single most expensive node.
2. Look for the four usual causes. A full scan where a seek was expected → missing or unusable index. Estimated rows wildly different from actual → stale statistics, so ANALYZE the table. A nested loop over a large inner side → the planner mis-estimated cardinality. Row counts exploding mid-plan → a fan-out join (§2.6).
3. Check the shape of the work. How many rows does the query need to touch versus how many it touches? A query that scans a year to return one day is a partitioning or indexing problem, not a SQL problem.
4. Then consider structural fixes, roughly in order of leverage: add or fix the index; make the predicate sargable; partition or cluster the table so irrelevant data is pruned; pre-aggregate into an incremental model so the expensive work happens once rather than per query.
And say the thing most people omit: ask whether the query needs to be fast at all. A nightly batch that takes 40 minutes and finishes before anyone arrives may be fine, and the effort belongs elsewhere. Knowing when not to optimise is part of the answer.

            

          

        

      


      

        
11.3 Index types ⭐⭐

        
What an index actually is, and the four or five kinds worth being able to name.


        
What it is: a separate, sorted data structure mapping key values to row locations. It turns a linear scan into a logarithmic lookup, at the cost of storage and of extra work on every write.


        

          

            
TypeStructureGood forUseless for

            
              
B-treeBalanced tree, O(log n)Equality, ranges, ORDER BY, MIN/MAX, prefix LIKE 'abc%'Leading-wildcard LIKE '%abc'

              
HashHash tableEquality only, slightly faster than B-treeAny range or ordering

              
CompositeB-tree on several columnsMulti-column filters, in leftmost-prefix order (§11.4)Filtering only on a later column

              
CoveringIndex that includes all queried columnsIndex-only scans — no table lookup at allNothing, but it is wider and costlier to maintain

              
Partial / filteredIndex over a subset of rows“Where status = 'active'” on a mostly-inactive table. Small and fastQueries outside the predicate

              
GIN / invertedTerm → row listFull-text search, JSON containment, array membershipOrdinary scalar comparisons

            
          

        


        
Clustered vs non-clustered is worth knowing because it comes up: a clustered index defines the physical order of the table, so there can be only one, and a range scan on it is sequential I/O. In SQL Server the clustered index is the table; in PostgreSQL all indexes are secondary and CLUSTER is a one-off reorganisation; in MySQL/InnoDB the primary key is the clustered index and every secondary index stores the primary key as its pointer — which is why a wide primary key makes every other index bigger.

Watch for the phrase USING COVERING INDEX in the second plan. With (customer_id) alone the engine seeks the index and then fetches each row from the table; with (customer_id, amount) the index already contains everything the query selected, so the table is never touched. On a wide table that is often a 5–10× difference, and it is the cheapest optimisation available.

        


        

          
Likely interview questions

          

            
Very commonWhat is an index and how does it work?
              
A separate sorted structure — almost always a B-tree — mapping key values to row locations, so a lookup is O(log n) instead of a linear scan. The tree is kept shallow and wide deliberately, because each level is a disk page read and the goal is to minimise I/O rather than comparisons.
What it buys you: equality lookups, range scans, sorted output without a sort step, and cheap MIN/MAX. What it costs: storage, and write amplification — every INSERT, UPDATE and DELETE must maintain every affected index.
Then the types worth naming: composite for multi-column filters, subject to the leftmost-prefix rule; covering, which includes every column the query needs so no table lookup is required; partial, restricted to a subset of rows and therefore much smaller; and specialised structures like GIN for text and JSON.
The detail that shows depth: a B-tree cannot help a leading-wildcard LIKE '%foo', because the index is sorted by prefix and there is no prefix to seek on. That is why full-text search needs a different index type entirely.

            

          

        

      


      

        
11.4 The leftmost-prefix rule ⭐

        
Why a composite index on (a, b) helps a query filtering on a, and does nothing for a query filtering only on b. Demonstrable in three plans.


        
The reason: a composite index is sorted by a, then by b within each a. Like a phone book sorted by surname then forename — you can find everyone called Patel, and everyone called Patel whose forename starts with A, but you cannot efficiently find every Anil regardless of surname.

        
The consequences: an index on (a, b) serves filters on a, and on a+b, but not on b alone. Column order matters, so put the most selective or most frequently filtered column first — and put equality predicates before range predicates, because once you hit a range the index can no longer seek on later columns.


        

          
Run itone composite index, three queries, two different outcomesidle

          
          

            
            
            
            ⌘/Ctrl + Enter
          

          

          
Expected: plan 1 says SEARCH ... USING INDEX idx_status_date (status=?); plan 2 says SCAN orders — the index is useless for a filter on its second column; plan 3 says (status=? AND order_date>?), using both. That middle plan is the leftmost-prefix rule, demonstrated rather than asserted. It is also why “we have an index on that table” is not an answer to “why is this slow”.

        


        

          
Likely interview questions

          

            
Very commonYou have an index on (a, b, c). Which queries can use it?
              
Any query whose predicates form a leftmost prefix: filters on a; on a and b; on a, b and c. Also a plus an ordering on b, since the index is already sorted that way.
It cannot efficiently serve a filter on b alone, on c alone, or on b and c without a — because the index is ordered by a first, and without a value for a there is nowhere to start seeking. Some engines can do an inefficient full index scan in that case, which is better than a table scan but is not a seek.
Once you hit a range, later columns stop being seekable. With a filter a = 1 AND b > 5 AND c = 3, the index seeks on a and b and then must filter c by inspection. So the design rule is equality columns first, range columns last, and the most selective equality column leftmost.
Which leads to the practical advice: design indexes for your query patterns, not per column. Three single-column indexes are usually worse than one well-ordered composite, and a table with fifteen indexes is paying a large write tax for coverage it does not need.

            

          

        

      


      

        
11.5 Sargability ⭐⭐

        
A predicate is sargable if the engine can use an index for it. Wrapping a column in a function destroys that, and this is the most common self-inflicted performance bug in analytical SQL.


        
The rule: keep the column bare on one side of the comparison. The index stores order_date, not strftime('%Y', order_date), so the engine cannot seek on the transformed value — it must compute the function for every row, which means reading every row.


        

          
Non-sargable
WHERE YEAR(d) = 2026
WHERE LOWER(email) = 'a@b.c'
WHERE amount * 1.2 > 100
WHERE CAST(id AS TEXT) = '4'
WHERE name LIKE '%smith'

          
Sargable equivalent
d >= '2026-01-01' AND d < '2027-01-01'
store normalised, or index lower(email)
amount > 100/1.2
id = 4
name LIKE 'smith%', or a trigram index

        


        
The escape hatch when you genuinely need the function: a functional (expression) index. CREATE INDEX ON t (lower(email)) makes WHERE lower(email) = ... sargable again. PostgreSQL, SQLite and Oracle support these directly; MySQL 8 has them via generated columns; SQL Server uses a computed column plus an index.


        

          
Trapthe same filter, sargable and not, then rescued by a functional indexidle

          
          

            
            
            
            ⌘/Ctrl + Enter
          

          

          
Three plans, and the middle one is the lesson: range on the bare column → SEARCH; function on the column → SCAN; after creating an index on that exact expression → SEARCH again. Both filters return the same 11 rows. On a billion-row table the first reads a few thousand and the second reads a billion, and nothing in the query text tells you which you wrote.

        


        

          
Likely interview questions

          

            
Very commonWhy is WHERE YEAR(order_date) = 2026 slow?
              
Because it is non-sargable. The index stores order_date, not YEAR(order_date), so the engine cannot seek — it must evaluate the function on every row, which means a full scan.
The fix is a half-open range on the bare column: order_date >= '2026-01-01' AND order_date < '2027-01-01'. Same result, index-friendly, and it also avoids the BETWEEN-on-timestamp bug from §6.5.
The same rule covers the other common cases: LOWER(email) = ... (normalise on write, or index the expression), amount * 1.2 > 100 (move the arithmetic to the constant side), CAST(id AS TEXT) = '4' (fix the type), and LIKE '%foo' (a leading wildcard cannot use a B-tree at all — that needs a trigram or full-text index).
And the escape hatch when the function is unavoidable: a functional index on the exact expression, or a stored generated column that you index. Worth naming, because it turns “don't do that” into “here's how to do that fast”.

            

          

        

      


      

        
11.6 When an index hurts ⭐⭐

        
Explicitly flagged as an asked question in one of the interview-prep documents behind this subject. “Add an index” is not always the answer, and knowing when it is not is the more interesting half.


        

          

            
SituationWhy the index hurts

            
              
Write-heavy tableEvery INSERT/UPDATE/DELETE must maintain every index. A logging or event table with six indexes pays six times the write cost for reads that rarely happen

              
Low-cardinality columnAn index on a boolean or a two-value status is often worse than a scan — the engine would read most of the table anyway, plus the index. A partial index on the rare value is the right tool

              
Query returns a large fraction of rowsAbove roughly 5–20% selectivity, a sequential scan beats random index lookups. The optimiser usually knows this and ignores your index, which is correct and confusing

              
Small tableA few hundred rows fit in a page or two; the scan is already one read

              
Redundant indexesAn index on (a) is redundant when (a, b) exists. It costs writes and storage and buys nothing

              
Bulk loadingLoading with indexes present is far slower than dropping them, loading, and rebuilding

            
          

        


        
The answer to give: “an index is a read optimisation paid for with writes and storage, so it is only worth it if the read pattern justifies the write tax. I would look at the query patterns, check for redundant indexes, and consider a partial or covering index rather than adding another plain one.”


        

          
Likely interview questions

          

            
Very commonWhen does an index hurt performance?
              
Start from the trade-off: an index accelerates reads and taxes every write, because each modification has to maintain it. So it hurts whenever the write cost exceeds the read benefit.
Write-heavy tables are the clearest case — an append-only event or audit table with several indexes pays for all of them on every insert. Low-cardinality columns are the subtlest: an index on a two-value flag rarely helps, because the engine would touch most of the table regardless, and a partial index on the rare value is the correct alternative. Unselective queries are the counter-intuitive one: past roughly 5–20% of rows, a sequential scan beats scattered index lookups, so the planner ignores the index — which people then read as “the index isn't working”.
Also: small tables, where a scan is one page read; redundant indexes, where (a) duplicates the prefix of (a,b); and bulk loads, where dropping and rebuilding is much faster than maintaining.
The habit worth mentioning: audit unused indexes. PostgreSQL exposes pg_stat_user_indexes with scan counts, and an index with zero scans after a month is pure cost. Removing indexes is a legitimate optimisation, and hardly anyone volunteers it.

            

          

        

      


      

        
11.7 Join algorithms ⭐

        
Three ways an engine can execute a join. Knowing which one you are getting, and why, is most of join tuning.


        

          
Nested loop
For each outer row, look up matches in the inner. Good when the outer side is tiny and the inner is indexed. Catastrophic when the outer side is large and the inner is unindexed — that is the O(n·m) plan you never want.

          
Hash join
Build a hash table on the smaller side, probe with the larger. The workhorse for large equality joins. Needs memory; spills to disk if the build side does not fit. Equality only.

          
Merge join
Sort both sides, walk them in step. Good when both inputs are already sorted — for example by an index on the join key. Supports inequality joins.

        


        
What this tells you. A range join (§2.9) cannot be a hash join, because hashing needs equality — so it falls back to a nested loop, and that is why range joins are slow and why adding any equality predicate helps so much. A nested loop with a large outer side almost always means a missing index on the inner join key. And a hash join that spills means the build side is bigger than the planner expected, which points at a cardinality mis-estimate.


        

          
Likely interview questions

          

            
ConceptualExplain the join algorithms and when each is chosen.
              
Nested loop: for each row of the outer input, probe the inner. Cost is outer × inner-probe, so it is excellent when the outer is small and the inner has an index on the join key, and disastrous otherwise.
Hash join: build a hash table from the smaller input, then stream the larger one through it. O(n + m), memory-hungry, and equality-only. This is what a large analytical join should be getting.
Merge join: sort both inputs on the join key and walk them together. O(n log n + m log m), or O(n + m) if both are already ordered — which is why an index on the join key can turn a hash join into a cheaper merge join. It also handles inequality conditions, which hash cannot.
The consequences worth stating. A range or as-of join has no equality to hash on, so it degrades to a nested loop — that is the mechanism behind “range joins are slow” and the reason adding a coarse equality predicate (a date bucket, a tenant id) transforms it. A nested loop over a large outer side is a missing-index signal. And a hash spill to disk means the planner underestimated the build side, so ANALYZE and check the estimates.
Distributed engines add one more dimension: whether the join is a broadcast (small side sent everywhere) or a shuffle (both sides repartitioned by key). Getting a shuffle where a broadcast would do — or vice versa — is the main cause of slow Spark joins, and it is the same reasoning one level up.

            

          

        

      


      

        
11.8 Partitioning and pruning ⭐

        
Splitting a table so the engine can skip most of it without reading it. At warehouse scale this matters more than indexing.


        
Partitioning divides a table physically, usually by date. A query filtered to one day then reads one partition — partition pruning — and the rest of the table is never touched. Clustering (BigQuery) or sort keys (Redshift, Snowflake's clustering) order data within a partition so the engine can skip blocks using per-block min/max metadata.

        
The rule that makes it work: the filter must be on the partition column, and it must be sargable. WHERE DATE(ts) = '2026-03-01' defeats pruning on a table partitioned by ts for exactly the reason in §11.5 — the engine cannot map the function's output back to partitions. Every warehouse cost-control document is essentially this one sentence.


        

          
Likely interview questions

          

            
Very commonWhat is partitioning, and how is it different from indexing?
              
An index is an auxiliary structure that helps you find specific rows. Partitioning physically splits the table so entire chunks can be skipped without being read at all. They are complementary: partitioning eliminates data, indexing locates rows within what remains.
The mechanism is partition pruning: with a table partitioned by day, a query filtered to a week reads seven partitions rather than the whole history. That is why partitioning is the dominant optimisation on large fact tables and why the partition column is almost always a date.
Clustering / sort keys are the next level down: ordering rows within a partition so the engine can skip blocks using min/max metadata per block. BigQuery calls it clustering, Snowflake calls it clustering keys, Redshift calls it a sort key, Delta and Iceberg do it with file statistics and Z-ordering.
The failure modes to name. Filtering on a function of the partition column defeats pruning entirely (§11.5). Too many small partitions — partitioning by hour on a low-volume table — creates metadata overhead and tiny files, which is its own performance problem. And partitioning on the wrong column: it must be the one your queries actually filter on, which is usually the event date and almost never the primary key.

            

          

        

      


      

        
11.9 Data skew and the straggler ⭐

        
On a distributed engine, one key with far more rows than the others makes one worker do most of the work while the rest idle. The job's runtime becomes that worker's runtime.


        
Where it comes from: a join or GROUP BY key with a hot value — NULL, an 'unknown' sentinel, a default tenant, a single enormous customer. All rows with that key hash to the same partition, so one task processes 60% of the data.

        
How to spot it: SELECT key, COUNT(*) FROM t GROUP BY key ORDER BY 2 DESC LIMIT 20. If the top key is orders of magnitude above the median, that is your straggler. In the Spark UI it is the one task taking twenty minutes while 199 took ten seconds.

        
Fixes: filter the sentinel out if it is meaningless (NULL keys usually are — and note NULLs never join anyway); salt the hot key by appending a random bucket number and aggregating in two stages; broadcast the small side so no shuffle happens at all; or split the hot keys into a separate job.

The skew_ratio is the number to look at. On this toy table it is near 1, which is healthy. On a real events table keyed by user_id you routinely see ratios in the thousands because of bot traffic or a service account — and that single key is what makes the nightly job take four hours instead of twenty minutes.

        


        

          
Likely interview questions

          

            
ConceptualA Spark job has 199 fast tasks and one that takes an hour. What is happening?
              
Data skew. The shuffle partitions by hash of the key, so all rows sharing a hot key land on one executor. That task processes a disproportionate share and the job cannot finish until it does — the runtime is the straggler's runtime, and adding executors does not help.
Diagnose it with a key-frequency query: group by the join or aggregation key, order by count descending, and look at the top values against the median. A ratio in the hundreds or thousands is the answer.
Fixes, in the order I would try them. Filter the sentinel — the hot key is very often NULL or 'unknown', and if it is meaningless it should not be in the join at all (NULLs never match anyway, so they are pure shuffle cost). Broadcast the small side, which removes the shuffle entirely and is the single most effective fix when one input fits in memory. Salt the key: append a random bucket to the hot key, aggregate per bucket, then aggregate the buckets — two stages, evenly distributed. Or split: process the hot keys in a separate job with different parallelism.
Worth naming: Spark's adaptive query execution can now detect and split skewed partitions automatically, so the first thing to check is whether AQE is enabled. But it cannot fix a skew that comes from a meaningless sentinel — that one is a modelling problem.

            

          

        

      


      

        
11.10 OLTP vs OLAP, rows vs columns ⭐

        
Why your analytical query is slow on Postgres and fast on BigQuery, and why the reverse is true for a single-row lookup.


        

          
Row store (OLTP)
All of a row's columns stored together. Reading one whole row is one I/O. Great for point lookups and transactional writes. Bad for scanning one column of a billion rows — you read every column to get one.

          
Column store (OLAP)
Each column stored separately and compressed. Reading three columns of a billion rows touches only those three. Great for aggregation. Bad for fetching or updating a single complete row.

        


        
Why columnar wins so decisively for analytics: projection pruning — you only read the columns you select, which is why SELECT * is far more expensive there than in a row store; compression — a column of one data type with repeated values compresses enormously, often 10× or more, and less data means less I/O; and vectorised execution — operating on batches of a single type is cache-friendly and SIMD-friendly.

        
The practical consequence: the habits differ. On a row store you index for selectivity. On a column store you select fewer columns, partition and cluster, and accept that there are no indexes in the traditional sense at all.


        

          
Likely interview questions

          

            
Very commonWhy are columnar databases faster for analytics?
              
Three reasons, and they compound.
Projection pruning. Columns are stored separately, so a query selecting three of two hundred columns reads 1.5% of the data. A row store must read every row in full to extract those three fields.
Compression. A single column holds one data type with heavily repeated values, so run-length and dictionary encoding are extremely effective — often 10× or better. Less bytes on disk means less I/O, and I/O is the bottleneck.
Vectorised execution. Processing a contiguous batch of same-typed values is cache-friendly and maps onto SIMD instructions, which is a large constant-factor win over row-at-a-time interpretation.
Then the trade-off, because the question is really about knowing when not to use one: a columnar store is poor at single-row reads (it must reassemble the row from every column) and poor at row-level updates (it is designed for append and rewrite). So OLTP stays row-oriented and OLAP goes columnar, which is why most organisations run both and move data between them.
The consequence for how you write SQL: on a columnar engine SELECT * is genuinely expensive rather than merely untidy, and on a scanned-bytes pricing model it is a line item on the invoice.

            

          

        

      


      

        
11.11 Cost control on a scanned-bytes engine ⭐

        
On BigQuery, Athena and Snowflake, a slow query is also an expensive one — and the levers are not the ones you would use on Postgres.


        

          

            
LeverWhy it works

            
              
Name your columnsColumnar storage means you are billed for the columns you touch. SELECT * on a 200-column table costs 200× the necessary scan

              
Filter on the partition columnPartition pruning skips whole days. And keep it sargable, or pruning is defeated (§11.5, §11.8)

              
Cluster on the common filterBlock-level min/max metadata lets the engine skip files within a partition

              
Materialise the expensive intermediateIf forty dashboards each aggregate the raw events table, aggregate once into a table and point them at it

              
Incremental modelsProcess only new partitions rather than rebuilding history nightly. Usually the single biggest saving

              
Approximate functionsAPPROX_COUNT_DISTINCT instead of exact, where a 1% error is acceptable

              
Preview instead of LIMITLIMIT does not reduce bytes scanned on BigQuery. Use the table preview or TABLESAMPLE

            
          

        


        
The counter-intuitive one worth remembering: SELECT * FROM huge_table LIMIT 10 can cost as much as scanning the whole table, because the pricing is on bytes read and the limit is applied after. That single misunderstanding accounts for a lot of surprise invoices.


        

          
Likely interview questions

          

            
Very commonYour warehouse bill doubled. How do you bring it down?
              
Start by finding where it goes: most warehouses expose a query history with bytes scanned or credits per query. Sort by cost, and the top ten queries usually account for most of the bill. Optimising anything else is wasted effort.
Then the levers, in order of typical impact. Incremental models — a nightly full rebuild of a history table is usually the single largest line item, and processing only new partitions can cut it by 95%. Materialise shared intermediates — if many dashboards each scan the raw events table, aggregate once. Partition and cluster, and make sure the filters are sargable so pruning actually happens. Name columns instead of SELECT *, which on columnar storage is a direct multiplier. Approximate aggregates where exactness is not required.
The trap to name: LIMIT does not reduce bytes scanned on BigQuery, so “I only looked at 10 rows” can still be a full-table charge. Preview features and TABLESAMPLE are the cheap ways to look at data.
And the governance point, which is what a senior answer includes: set per-query and per-user byte limits and alerting, so a runaway query is caught at £20 rather than at £2,000. Cost control is a guardrail problem as much as an optimisation problem.

            

          

        

      


      

        
11.12 Materialised views and incremental models

        
The difference between computing something every time it is asked for and computing it once.


        

          

            
ViewMaterialised viewIncremental table

            
              
StorageNone — it is a saved queryStores the resultStores the result

              
Read costFull cost, every timeCheapCheap

The incremental pattern is the one that matters at scale: instead of rebuilding the whole table, process rows newer than the current watermark and append. The complications are real and worth naming — late-arriving data means you must reprocess a trailing window rather than only the newest partition; idempotency means a re-run must not double-count, so you delete-and-insert the affected partitions rather than blindly appending; and backfills need a separate full-refresh path.

        
Views are still valuable for a different reason: they are the interface. A view that encapsulates the agreed definition of “active customer” means every team uses one definition, which prevents the §10.8 reconciliation argument from happening at all.


        

          
Likely interview questions

          

            
ConceptualView vs materialised view vs table?
              
A view is a stored query with no data: reading it re-runs the underlying SQL, so it is always fresh and always costs full price. A materialised view stores the computed result, so reads are cheap and freshness depends on the refresh schedule. A table built by a pipeline is the same idea with you owning the refresh logic — which is what dbt models are.
Choose by read/write ratio and freshness requirement. Frequently read, slowly changing, tolerant of minutes-old data → materialise. Rarely read or needs to be exactly current → view. Large and append-mostly → an incremental table, processing only new partitions.
The incremental complications are what a senior answer covers: late-arriving data forces you to reprocess a trailing window, not just the newest partition; idempotency means the run must be safe to repeat, which usually means delete-and-insert by partition rather than append; and you need a full-refresh path for backfills and for when the logic changes.
And the non-performance reason to use views: they are a contract. Putting the agreed definition of a metric in a view means every consumer shares it, which is the structural fix for two dashboards disagreeing.
