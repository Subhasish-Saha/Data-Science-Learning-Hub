12.1 How to use this drill

Every part of this subject ends its topics with the questions that topic answers. This is the consolidated bank, stripped of context so you cannot coast on adjacency.

The method

Read the question. Answer out loud. Then expand and compare. Reading an answer without attempting it first feels productive and is not — recall is what is being trained, and recognition is not recall. Say it aloud rather than thinking it: the gap between “I know this” and “I can say this in forty seconds” is exactly what an interview measures.

For the coding questions, write the query in a cell before you look. §12.9 has blank drills with the tests already in place. A query you have typed under time pressure is worth ten you have read.

Likely interview questions
BehaviouralHow should you behave during a live SQL exercise?

Restate the question first. “So: one row per customer, only completed orders, and customers with none should show zero — is that right?” That single sentence catches half of all misunderstandings and costs ten seconds.

Ask about the grain and the edge cases before writing. One row per what? Are ties possible? Should rows with no match appear? NULLs? Those four questions cover most of the traps in this subject, and asking them reads as experience rather than hesitation.

Build in stages and narrate. Write a CTE, say what it produces, then build on it. If you go quiet for two minutes the interviewer cannot tell whether you are thinking or stuck — and their only options are to interrupt or to mark you down.

Say the complexity and the check. “This is one pass plus a sort for the window. Afterwards I'd assert the row count matches the customer count.”

And if you cannot finish: land a working simpler version plus a clear description of the optimisation. That scores far better than half of a clever query that runs on nothing.

12.2 The warm-up questions

From Part 1. If any of these takes more than a few seconds, that is where to spend your time.

Rapid drill — Level 0
Very commonWhat is the order of execution of a SQL query?

FROM/JOIN → WHERE → GROUP BY → HAVING → window functions → SELECT → DISTINCT → ORDER BY → LIMIT. It explains why a SELECT alias works in ORDER BY but not WHERE, why aggregates go in HAVING, and why a window function cannot be filtered without wrapping the query. Full treatment: §1.1.

Very commonCOUNT(*) vs COUNT(col) vs COUNT(DISTINCT col)?

Rows; non-null values of col; distinct non-null values. COUNT(1) is identical to COUNT(*). The one that bites: COUNT(col) is a filter in disguise, and COUNT(*) - COUNT(col) is the fastest null audit there is. §1.3.

Very commonWHERE vs HAVING?

WHERE filters rows before grouping; HAVING filters groups after aggregating. You must use HAVING for a condition on an aggregate; you should use WHERE for everything else, because fewer rows reach the grouping step. QUALIFY is the window-function equivalent, and it exists only on Snowflake, BigQuery, Teradata, Databricks and DuckDB. §1.5.

Very commonWhy does WHERE col = NULL return nothing?

NULL means unknown, so any comparison with it yields UNKNOWN, and WHERE keeps only TRUE. Use IS NULL. The consequence worth stating: col = x and col <> x do not partition the table, because NULL rows satisfy neither. §1.6.

GotchaWhere does SQL treat NULLs as equal?

In GROUP BY, DISTINCT, UNION/INTERSECT/EXCEPT, ORDER BY and window PARTITION BY — all use “not distinct from”. In WHERE, ON, HAVING and IN they are unknown. Aggregates other than COUNT(*) skip them entirely. §1.6.

Very commonHow do aggregates treat NULL?

They ignore them. So AVG(col) divides by COUNT(col), not COUNT(*) — if missing means zero in your domain, AVG overstates. And SUM over an empty or all-null set returns NULL, not 0, so guard it with COALESCE before doing arithmetic. §1.7.

Very commonHow do you avoid a divide-by-zero?

n / NULLIF(d, 0). And remember the engines disagree on what raw division by zero does — PostgreSQL and SQL Server raise, MySQL and SQLite return NULL — so the guard also makes the query portable. §1.8, §10.5.

Very commonYour rate column is all zeros. Why?

Integer division. 3/4 is 0 in PostgreSQL, SQL Server and Oracle. Multiply by 100.0, or CAST, or use AVG of a 0/1 flag. It is invisible on MySQL and SQLite, which is exactly why it reaches production. §1.8.

Very commonCount completed and cancelled orders as two columns.

Conditional aggregation: SUM(CASE WHEN status='completed' THEN 1 ELSE 0 END) per column. With COUNT, omit the ELSE — COUNT counts a zero but skips a NULL, so ELSE 0 would count every row. FILTER (WHERE ...) is the standard spelling where available. §1.10, §3.7.

Very commonUNION vs UNION ALL?

UNION deduplicates, which costs a sort or hash over the whole combined result. Use UNION ALL unless you specifically need dedup. Extra point: UNION can hide a genuine duplicate-data problem. §1.11.

GotchaIs SELECT ... ORDER BY x LIMIT 3 deterministic?

Not if x has ties — nothing specifies which tied row wins, and it can change with the plan. Append a unique column: ORDER BY x, id. This is the single most common cause of intermittently failing data tests. §1.2, §4.10.

12.3 Joins and NULLs

From Part 2. Where most wrong answers come from, and the highest-value section to have reflexive.

Rapid drill — Level 1
Very commonWhat is the difference between a condition in ON and in WHERE?

For an inner join, none. For an outer join it changes the result: ON defines what counts as a match and unmatched rows survive with NULLs; the same condition in WHERE runs after the join and discards those manufactured rows, silently turning a LEFT JOIN into an INNER JOIN. Rule: filter the right table in ON, the driving table in WHERE. §2.2, §2.3.

Very commonWhy did my NOT IN subquery return zero rows?

A NULL in the subquery. x NOT IN (a, NULL) expands to x<>a AND x<>NULL, and the second term is UNKNOWN for every x, so the predicate can never be true. Use NOT EXISTS, or add WHERE col IS NOT NULL to the subquery. §2.4.

Very commonWrite an anti-join three ways.

NOT EXISTS (preferred — null-safe, expresses intent, optimises to an anti-join); LEFT JOIN ... WHERE right.key IS NULL; EXCEPT on key lists. NOT IN is the fourth and the dangerous one. §2.4.

Very commonYour revenue doubled after adding a join. What happened?

Fan-out: a one-to-many join repeated each parent row per child, so a SUM of the parent's amount counted it once per child. Fix by aggregating the many side first and then joining, or by aggregating only many-side columns. Compare row counts before and after any join. §2.6.

GotchaCan an INNER JOIN return more rows than either table?

Yes — if the key is non-unique on both sides, the output for that key is the product of the multiplicities. Joins are not filters. Check uniqueness with GROUP BY key HAVING COUNT(*) > 1 before writing the join. §2.6.

Very commonEXISTS vs IN vs JOIN?

EXISTS for an existence test — a semi-join, never duplicates rows, short-circuits. IN is equivalent for the positive case. JOIN when you need columns from the other table, and accept the row multiplication. The old “EXISTS is faster” folklore is largely obsolete: modern optimisers produce the same semi-join plan. §2.5.

Very commonEmployees earning more than their manager.

Self-join on e.manager_id = m.id, compare salaries. Note the root of the hierarchy has a NULL manager and is dropped by the inner join — correct here, but switch to LEFT JOIN the moment the question becomes “list everyone with their manager”. §2.7.

Very commonHow do you join a fact table to a slowly-changing dimension correctly?

On the key and the validity window, with half-open bounds: f.ts >= d.valid_from AND f.ts < d.valid_to. Joining on the key alone with is_current = 1 attaches today's attributes to historical facts, which is look-ahead leakage that produces exactly one row per fact and therefore looks correct. §2.9, §6.10, §9.9.

CodingHow do you test whether two date ranges overlap?

a.start <= b.end AND a.end >= b.start — two clauses, not four cases. Strict inequalities for half-open intervals. §2.10.

ConceptualWhy avoid NATURAL JOIN?

The join key is implicit and follows column names, so an unrelated migration that adds a same-named column to both tables silently changes the join. USING (a, b) is the safe shorthand; explicit ON is what to write in anything long-lived. §2.10.

12.4 Windows and ranking

From Parts 3, 4 and 5. The most-tested topic in a SQL screen.

Rapid drill — Levels 2–4
Very commonROW_NUMBER vs RANK vs DENSE_RANK?

On 100, 100, 90: 1,2,3 / 1,1,3 / 1,1,2. ROW_NUMBER for dedup and “exactly one row”; RANK for competition ranking; DENSE_RANK for “the Nth distinct value”. §4.3.

Very commonSecond highest salary.

DENSE_RANK() OVER (ORDER BY salary DESC) = 2, wrapped. LIMIT 1 OFFSET 1 is wrong whenever the top salary is shared — it returns the maximum again. MAX below the MAX works for N=2 and does not generalise. Add PARTITION BY for per-department. §4.4.

Very commonTop 3 per group — which ranking function?

Ask what should happen at a tie on third place. ROW_NUMBER gives exactly three, cutting through the tie arbitrarily; RANK/DENSE_RANK return all tied rows, so you may get more. Aggregate to the right grain before ranking. On Snowflake/BigQuery/DuckDB, QUALIFY saves the subquery. §4.5.

Very commonMost recent record per user.

ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts DESC, id DESC) = 1. The tie-break is not optional — with date-granularity timestamps or bulk loads, ties are common and the “latest” row would otherwise vary between runs. Alternatives: DISTINCT ON (PostgreSQL), LATERAL/CROSS APPLY with LIMIT 1. §4.5, §4.10.

Very commonWhy can't you filter on a window function in WHERE?

Windows are computed at step 5, after WHERE at step 2 — the value does not exist yet. Wrap in a subquery/CTE, or use QUALIFY. And note the two placements are not equivalent: filtering in WHERE changes the window's input, so ranks renumber. §4.9.

GotchaWhat is the default window frame?

Without ORDER BY in OVER: the whole partition. With it: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — and it is RANGE, not ROWS, so tied ordering keys share a frame and a running total jumps by the whole tie group. Always write the frame explicitly for aggregates. §5.1, §5.2.

GotchaWhy does LAST_VALUE return the current row?

Because the default frame ends at CURRENT ROW, so the last row of the frame is the current row. Fix with an explicit UNBOUNDED FOLLOWING frame, or — better — FIRST_VALUE(x) OVER (ORDER BY d DESC). §5.7.

Very commonMonth-over-month growth.

Aggregate to month, then (rev - LAG(rev) OVER (ORDER BY mo)) / NULLIF(LAG(rev) OVER (ORDER BY mo), 0) * 100.0. Three defects to pre-empt: integer division, division by zero, and missing months — LAG counts rows, so a gap silently shifts every later comparison. §5.6.

GotchaBuild a feature: the customer's average order value before this order.

Frame ending at 1 PRECEDING, not CURRENT ROW. Including the current row is target leakage — the model learns from the answer, validates beautifully, and fails in production. §5.8.

CodingRunning count of unique customers by month.

COUNT(DISTINCT ...) is not available as a window function, because a distinct count is not incrementally computable. Reduce each customer to their first month, then take a cumulative SUM of the per-month counts. §5.10.

GotchaCan you nest one window function inside another?

No — all windows in a SELECT are computed in the same phase, so one cannot consume another's output. Compute the inner one in a CTE first. But an aggregate inside a window is legal: SUM(SUM(x)) OVER () works, and it is how percent-of-total is written. §8.1, §3.6.

Very commonCTE vs subquery vs temp table?

CTEs for readability, reuse within the query, and recursion. Subqueries for one simple inline use. Temp tables when an expensive intermediate is reused many times and you want to index it or give the planner real statistics. CTEs are not inherently faster — that belief comes from PostgreSQL's pre-v12 optimisation fence. §3.3.

12.5 Dates, funnels and retention

From Parts 6 and 7. The product-analytics core.

Rapid drill — Levels 5–6
Very commonWhat is wrong with ts BETWEEN '2026-03-01' AND '2026-03-31'?

On a timestamp column the end literal means midnight, so you lose almost the whole of the 31st. Use a half-open range: ts >= '2026-03-01' AND ts < '2026-04-01' — correct at any precision, and sargable. Do not “fix” it with CAST(ts AS date), which disables the index. §6.5.

Very commonWhy do you need a date dimension or spine?

Because GROUP BY date only returns dates present in the data. A day with no activity becomes a missing row rather than a zero, so charts interpolate over outages and a “7-day average” divides by however many rows exist. Generate the calendar, then LEFT JOIN the facts onto it. §6.3, §6.4.

Very commonBuild a funnel.

Count distinct users per step from a VALUES step list LEFT JOINed to the events, then LAG for step-to-step rate and FIRST_VALUE for overall. Ask three things first: must the steps be in order, within what time window, and distinct users or events. §7.2.

GotchaHow do you enforce funnel step ordering?

Collapse each user to their first timestamp per step with conditional MIN, then require t2 > t1, t3 > t2 and so on. Out-of-order events are normal in real event tables — clock skew, batched SDKs, retries — so the naive “did it happen at all” funnel overstates conversion. §7.3.

Very commonWrite a monthly cohort retention query.

Three CTEs: cohort = first-activity month per user; activity = distinct user-months; grid = join them and compute month_n from a monotonic period number. Then count distinct users per (cohort, month_n) over the cohort size. Flag incomplete recent cohorts, and say whether “retained” means active in month N (allows resurrection) or active every month since (survival). §7.4.

Very commonWhat is day-7 retention?

Ambiguous — active on exactly day 7, on day 7 or later, or at any point within 7 days. And the denominator must be users who had the opportunity to reach day 7, or the metric falls mechanically as acquisition grows. Put the definition in the column name. §7.5.

Very commonMAU is flat. What do you look at?

Decompose into new / retained / reactivated / churned per period, and check the identity active(t) = active(t−1) + new + reactivated − churned. Flat MAU is equally consistent with health and with churning as fast as you acquire. §7.6.

Very commonSessionise events with a 30-minute timeout.

LAG the previous timestamp, flag rows whose gap exceeds 30 minutes, running SUM of the flags is the session id. Flag the boundary, cumsum the flags — the most reusable idiom in analytical SQL, and the same three lines as everything in Part 8. §7.7.

Very commonCompute rolling 7-day actives.

Drive from a date spine; for each day count distinct users in the trailing seven days via a correlated subquery or range join. COUNT(DISTINCT ...) is unavailable as a window function. Keep the window half-open — > d−7 AND <= d — or you have an eight-day week. §6.9, §7.1.

Very commonWhat is point-in-time correctness?

Every value in a training row was knowable at that row's timestamp. Three parts: as-of dimension joins on the validity window; rolling features ending at 1 PRECEDING; and availability time rather than event time where data arrives late. Leakage inflates offline metrics and cannot be caught by cross-validation, because every fold shares it. §6.10.

12.6 Gaps, islands and hard patterns

From Parts 8 and 9. The genuinely difficult tier.

Rapid drill — Levels 7–8
Very commonExplain gaps and islands.

Two techniques. Row-number difference: for a fixed-step sequence, value − ROW_NUMBER() is constant within a run, so it is the group key. Flag and cumsum: LAG to find the gap, flag the boundary, running SUM gives the island id — more general, handles tolerances and timeouts. Deduplicate first, or a repeated value splits the run. §8.1.

Very commonUsers active 3+ consecutive days.

Islands, then HAVING COUNT(*) >= 3. The self-join-on-+1 day-and-+2 days alternative works for exactly three and encodes the number in the query structure, so it does not generalise. Report the run length and boundaries, not just the user id. §8.3.

Very commonLongest streak vs current streak.

Longest: count per island, take the per-user max — and use ROW_NUMBER rather than MAX if you also want which streak. Current: the run must reach the reference date, so a user with a great past streak has a current streak of zero. Decide whether “today or yesterday” counts. §8.4, §8.5.

Very commonMerge overlapping date ranges.

Sort by start; a new block begins where the start exceeds the running maximum of previous ends; cumsum the flags; aggregate min-start/max-end per block. The running maximum — not the previous row's end — is what handles a fully nested interval. §8.7.

CodingMaximum concurrent sessions.

Sweep line: +1 at each start, −1 at each end, UNION ALL, order by time, running SUM. MAX of that is the peak. O(n log n), versus O(n²) for comparing every pair of intervals. §8.10.

Very commonMedian without a percentile function.

Number the rows, count them, average the values at (n+1)/2 and (n+2)/2 with integer division — one formula for odd and even. Include a tie-break in the ORDER BY: the popular “number from both ends” trick returns a wrong median when values tie, because the two numberings are not mirrors. §9.1.

ConceptualPERCENTILE_CONT vs PERCENTILE_DISC?

DISC returns an actual data value; CONT interpolates and may return a value not in the data. Both respect ties, unlike NTILE. Two tools reporting “p95” with different definitions is a common source of disagreement. §9.2, §4.8.

GotchaWhy is the average of daily averages not the monthly average?

It weights every day equally regardless of volume. The pooled mean is SUM(total)/SUM(count). This is Simpson's-paradox territory, and the general rule is: keep numerator and denominator separately and divide at the end — sums re-aggregate, ratios do not. §9.4.

Very commonCount everyone in a manager's reporting line, at any depth.

Recursive CTE pairing each ancestor with all descendants. A self-join adds one level per join and the depth is data-dependent, which is what recursion is for. Carry a depth counter or path as a cycle guard, use UNION ALL, and mention closure tables or materialised paths for read-heavy workloads. §9.6.

Very commonExplain slowly changing dimensions.

Type 1 overwrites; Type 2 closes the old row and inserts a new one with valid_from/valid_to; Type 3 keeps one previous value. Query Type 2 point-in-time with half-open bounds. Validate the table with LEAD(valid_from) — overlaps duplicate facts, gaps lose them. Building it from snapshots is run-length encoding. §9.9.

12.7 Correctness and performance

From Parts 10 and 11. The questions that separate someone who writes queries from someone who ships them.

Rapid drill — Levels 9–10
Very commonHow do you find and delete duplicates?

Find: GROUP BY key HAVING COUNT(*) > 1, or ROW_NUMBER to see the rows. Delete: ROW_NUMBER() OVER (PARTITION BY key ORDER BY survivor_rule) and remove rn > 1. But first agree what duplicate means — casefolded, trimmed, normalised — and SELECT the victims before deleting, inside a transaction. Then add the constraint that prevents recurrence. §10.1, §10.2.

GotchaIs 'Ada' = 'ada' true?

Depends on the collation, which is a schema property. PostgreSQL: no. MySQL's usual default: yes. SQLite: no unless COLLATE NOCASE. Do not rely on it — normalise explicitly, and use a functional index if the normalisation would otherwise disable the index. §10.3.

Very commonHow should money be stored?

NUMERIC/DECIMAL, or integer minor units. Never FLOAT: 0.1 + 0.2 <> 0.3, and float addition is not associative, so SUM can vary with row order and therefore with the plan — which makes reconciliation impossible to close. §10.6.

Very commonHow do you know your query is correct?

Assert the invariants. Row count against the driving table. Conserved SUM after grouping. Mutually exclusive categories summing to the whole. One entity traced by hand end to end. Boundaries re-checked by shifting the date range a day. Then automate them as tests, because an assertion you have to remember to run is one you will forget. §10.7.

Very commonTwo reports disagree on revenue. How do you find out why?

Check the population (dates, time zone, status filters, test accounts), then the grain (order vs line item — fan-out), then the as-of time (late-arriving data), and only then the SQL. Use EXCEPT both ways on the key list. Present a reconciliation ladder: one row per adjustment from the raw total to each party's figure. §10.8.

Very commonYou are handed an unfamiliar table. What do you run?

A profile: row count, key uniqueness (COUNT(*) vs COUNT(DISTINCT id)), nulls per column, min/max on dates and amounts, cardinality of categoricals, orphans in both directions, and freshness (MAX(updated_at)). Then ask a human: what is the grain? §10.9.

Very commonThis query takes 40 minutes. What do you do?

Read the plan first. Look for a full scan where a seek was expected, estimated-versus-actual row divergence, a nested loop over a large inner side, and row counts exploding mid-plan. Then fix the index, the sargability, the partitioning, or the join — in that order. And ask whether it needs to be fast at all. §11.2.

Very commonWhy is WHERE YEAR(d) = 2026 slow?

Non-sargable: the index stores d, not YEAR(d), so the engine must compute the function per row. Use a half-open range on the bare column, or create a functional index on the expression. Same rule for LOWER(col), CAST(col), arithmetic on the column, and LIKE '%foo'. §11.5.

Very commonWhich queries can use an index on (a, b, c)?

Any leftmost prefix: a; a,b; a,b,c. Not b alone or c alone. And once a predicate is a range, later columns stop being seekable — so order equality columns first, most selective leftmost. §11.4.

Very commonWhen does an index hurt?

Write-heavy tables (every write maintains every index); low-cardinality columns (a partial index is the right tool); unselective queries above roughly 5–20% of rows, where a scan beats scattered lookups; small tables; redundant indexes duplicating a composite's prefix; and bulk loads. Auditing and removing unused indexes is a legitimate optimisation. §11.6.

ConceptualExplain the join algorithms.

Nested loop (small outer, indexed inner); hash join (large equality joins, memory-hungry, equality-only); merge join (both inputs sorted, supports inequality). A range join cannot hash, so it degrades to a nested loop — which is why adding any equality predicate transforms it. §11.7.

Very commonWhy are columnar databases faster for analytics?

Projection pruning (read only the columns you select), compression (one type, repeated values, often 10×), and vectorised execution. The trade-off: poor at single-row reads and row-level updates. Consequence for how you write SQL: SELECT * is genuinely expensive, and on scanned-bytes pricing it is an invoice line. §11.10, §11.11.

12.8 The trap questions ⭐⭐

Fourteen statements that sound right and are wrong. SQL screens are lost here — not on missing knowledge, but on a confidently wrong answer that the interviewer then probes.

The plausible claimWhy it is wrong
“COUNT(*) and COUNT(col) are the same”COUNT(col) skips NULLs. On a nullable column it is a filter in disguise (§1.3)
“COUNT(1) is faster than COUNT(*)”Identical on every modern optimiser. Pure folklore (§1.3)
“LIMIT 1 OFFSET 1 gives the second highest”It gives the second row. With a shared top value it returns the maximum again (§1.2, §4.4)
“NOT IN and NOT EXISTS are interchangeable”One NULL in the subquery makes NOT IN return zero rows (§2.4)
“A LEFT JOIN can only add rows”A WHERE filter on the right table silently demotes it to an inner join (§2.2)
“An INNER JOIN can only reduce rows”A one-to-many join multiplies them. Output can exceed both inputs (§2.6)
“DISTINCT fixes duplicate rows”It hides them. Any aggregate computed over the fanned-out rows was already wrong (§1.9, §2.6)
“SUM(x) OVER (ORDER BY d) is a row-by-row running total”The default frame is RANGE, so tied dates share a value and no row shows the intermediate (§5.2)
“LAST_VALUE gives the last value in the partition”The default frame ends at the current row, so it returns the current row (§5.7)
“LAG(x, 12) is the same month last year”It is twelve rows back. One missing month shifts every later comparison permanently (§5.6)
“BETWEEN two dates covers both days fully”On a timestamp column the end literal is midnight, so most of the last day is excluded (§6.5)
“NTILE(10) gives value-based deciles”It splits by row position, so identical values can land in different buckets (§4.7)
“Adding an index makes queries faster”It taxes every write, and on unselective queries the planner will ignore it anyway (§11.6)
“LIMIT 10 means I only scanned 10 rows”On BigQuery you are billed for bytes scanned; the limit is applied after (§11.11)
The pattern behind all fourteen

Every one is a case where SQL is syntactically valid and semantically different from what you meant. There is no error message. That is why the habits in §10.7 — assert the row count, assert the conserved total, trace one entity by hand — matter more than knowing the individual traps: they catch the ones you have not memorised.

Likely interview questions
BehaviouralWhat is the worst SQL bug you have shipped?

Pick a real one from this list's shape — a silent semantic error, not a typo — and tell it in four beats: what the query looked like, what number it produced, how it was caught, and what you changed so the class of bug could not recur.

A good example structure: “A revenue report joined orders to line items to pick up the product category, which fanned the orders out and inflated revenue by about 20%. It was plausible enough to survive review and was caught when finance reconciled. The fix was to aggregate the items to one row per order before joining — and the durable fix was a test asserting that the report's total equals the source total, which now runs in CI.”

What makes this answer land is the third and fourth beats. Anyone can describe a bug. Describing the detection gap and the systemic fix is the difference between an anecdote and evidence that you learn.

What to avoid: a bug that was really someone else's fault, a bug with no consequence, or claiming you have never shipped one.

The portable subset, if you want one query that runs everywhere: CTEs (non-recursive), window functions with explicit frames, CASE instead of FILTER, COALESCE instead of IFNULL/ISNULL, explicit CAST, half-open date ranges instead of BETWEEN, 100.0 * before every division, and a subquery instead of QUALIFY. Likely interview questions

          

            
Behavioural“Which SQL dialect do you use?”
              
Name one primarily, then show you know it is one of several. “Mostly PostgreSQL and BigQuery. I write the portable subset by habit — CTEs, explicit window frames, COALESCE, half-open date ranges — and I know where the dialects diverge: QUALIFY and approximate quantiles on the warehouse side, FILTER and DISTINCT ON on the Postgres side, no FULL OUTER JOIN on MySQL.”
That answer does two things at once: it is honest about where your depth is, and it demonstrates you have hit real portability problems rather than only ever using one engine.
The two divergences most worth having ready, because they cause silent bugs rather than syntax errors: integer division (truncates on Postgres and SQL Server, not on MySQL and Snowflake) and default collation (case-sensitive on Postgres, insensitive on MySQL). Both mean a query can be correct on one engine and wrong on another with no error.

Six questions that take twenty seconds and prevent most wrong answers. Ask them out loud.

“Should rows with no match appear, as zero?”Decides INNER vs LEFT, and COUNT(*) vs COUNT(key)§2.1, §2.2

              
“Are ties possible, and what should happen?”Decides ROW_NUMBER vs RANK vs DENSE_RANK§4.3, §4.5

“What decision does this feed?”Often changes the metric entirely, and sometimes removes the need for the query§7.5, §9.10

            
          

        


        
The closing script, for after the query runs: “Checks I would run: row count against the customer table, the revenue total against the source, and one customer traced by hand. If this were going into production I would add those as tests, and I would want to know whether late-arriving data means today's partition is incomplete.”


        

          
Likely interview questions

          

            
BehaviouralYou cannot finish the query in time. What do you do?
              
Land a working simpler version plus a clear description of the step you did not get to. A correct query that answers 80% of the question, with “the remaining piece is the tie handling, and I would do it with DENSE_RANK like this”, scores far better than a half-written clever query that runs on nothing.
Say the plan before the time runs out, not after: “I have five minutes — I will get the aggregation correct and then talk through the ranking step.” That is a deliberate trade-off made out loud, which is exactly the behaviour being assessed.
And be accurate about what is unfinished. “This handles the main case; it does not yet handle customers with no orders, and here is where that would go” is honest and specific. Claiming something works when you have not run it is the one genuinely disqualifying move.

Likely interview questions

          

            
ConceptualIf you had to teach SQL for interviews in one hour, what would you cover?
              
Four things, in this order.
1. NULL semantics and the execution order. They explain most error messages and most silent wrong answers — the NOT IN collapse, the demoted LEFT JOIN, the alias that will not work in WHERE.
2. The three ranking functions and ties. One example — 100, 100, 90 → 1,2,3 / 1,1,3 / 1,1,2 — plus the top-N-per-group shape. That is the most-tested topic there is.
3. Conditional aggregation. SUM(CASE WHEN ...) is the answer to pivots, funnel counts, per-segment metrics and cohort cells, and most people never realise those are one technique.
4. Flag-and-cumsum. LAG → boundary flag → running SUM solves sessionisation, streaks, interval merging and run-length encoding — the entire “hard” tier from three lines.
And one habit rather than a technique: after any query, check that the row count and the total are what they should be. That catches the bugs you have not memorised, which is most of them.
