Where correct-looking answers quietly lose rows Date truncation across dialects, interval arithmetic, generating a date spine with a recursive CTE, filling gaps, the BETWEEN-on-timestamp bug, ISO weeks, time zones, rolling actives, and point-in-time correctness.

Two date bugs are so common that interviewers use them as a filter. The first is BETWEEN '2026-03-01' AND '2026-03-31' on a timestamp column, which silently drops almost the whole of the 31st, because the implicit time is midnight. The second is a missing date spine: group by day and days with zero activity simply do not appear, so a line chart interpolates over the outage and a “7-day average” averages over however many rows happen to exist. Both are shown here with real rows, and both are fixed the same way — generate the calendar first, then left-join the data onto it.

6.1 Truncating a date, in five dialects ⭐

“Group by month” is the most common date operation and the least portable.

EngineTruncate to monthNotes
PostgreSQLDATE_TRUNC('month', d)Returns a timestamp at the 1st. The standard everyone else imitates
BigQueryDATE_TRUNC(d, MONTH)Argument order reversed
SnowflakeDATE_TRUNC('month', d)Also TO_VARCHAR(d,'YYYY-MM')
MySQLDATE_FORMAT(d,'%Y-%m-01')No DATE_TRUNC; returns a string unless you cast
SQL ServerDATETRUNC(month, d) (2022+)Older: EOMONTH, or DATEFROMPARTS(YEAR(d),MONTH(d),1)
SQLitestrftime('%Y-%m', d)No date type at all — dates are text, numbers or Julian days

Truncating to a string vs a date. strftime('%Y-%m', d) gives '2026-03', which sorts correctly and groups fine but is not a date — you cannot add a month to it. DATE_TRUNC gives a real date, which keeps arithmetic available. For a GROUP BY label either works; for anything you will later do date maths on, keep it a date.

Likely interview questions

          

            
Very commonHow do you aggregate by month?
              
Truncate the date and group by the result: GROUP BY DATE_TRUNC('month', order_date) in PostgreSQL, DATE_TRUNC(order_date, MONTH) in BigQuery, DATE_FORMAT(d,'%Y-%m-01') in MySQL, strftime('%Y-%m', d) in SQLite.
Three things worth adding. Never group by MONTH(d) alone — that collapses every January across every year into one bucket, which is a genuinely common bug. Prefer a real date over a string for the group key if you will do arithmetic later. And truncating a column kills index usage (§11.5), so for a filtered range prefer WHERE d >= '2026-03-01' AND d < '2026-04-01' over WHERE DATE_TRUNC('month', d) = '2026-03-01'.
In a real warehouse the better answer is a dim_date table joined on the date key, with month, quarter, fiscal period, weekday and holiday flags precomputed. It is portable, it makes fiscal calendars possible, and it removes dialect functions from every query.

The month-arithmetic trap: “one month after 31 January” has no obvious answer. PostgreSQL clamps to 28 February; MySQL clamps too; some engines error. And it is not associative: Jan 31 + 1 month + 1 month gives 28 March, while Jan 31 + 2 months gives 31 March. If exact month boundaries matter, truncate to the month start first and add there.

The middle two columns disagree. Adding a month twice from 31 January lands on 28 March; adding two months at once lands on 31 March. Neither is wrong — “a month later” is genuinely ambiguous at month ends — which is exactly why you should truncate to the month start before doing month arithmetic, as the fourth column does.

        


        

          
Likely interview questions

          

            
GotchaWhat is “one month after 31 January”?
              
There is no single right answer, and saying so is the answer. Most engines clamp to the last valid day — 28 February, or 29 in a leap year. The consequence is that month addition is not associative: two successive +1 month steps from 31 January give 28 March, while a single +2 months gives 31 March.
Practically: if you are iterating month by month, always work from a month start, not from an arbitrary day. Truncate first, add months, and derive the end as start + 1 month - 1 day. That is stable, leap-year-safe and associative.
The related trap is a “30 days” window standing in for “a month” — they are different, and a month-over-month report built on 30-day windows drifts by five days a year. Pick one and name it in the column.

            

          

        

      


      

        
6.3 Generating a date spine ⭐⭐

        
The single most useful date technique. A calendar that exists independently of your data, so gaps become zeros instead of missing rows.


        
By engine: PostgreSQL has generate_series; BigQuery has GENERATE_DATE_ARRAY plus UNNEST; Snowflake uses GENERATOR with ROW_NUMBER; MySQL, SQL Server and SQLite need a recursive CTE (§3.4) or a persisted calendar table.

        
In production, persist it. A dim_date table with a row per day and columns for month, quarter, ISO week, fiscal period, weekday and holiday flags removes dialect functions from every downstream query and makes fiscal calendars expressible at all. Generating it on the fly is for ad-hoc work.


        

          
Likely interview questions

          

            
Very commonWhy do you need a date dimension table?
              
Because GROUP BY date only returns dates that appear in the data. A day with no activity produces no row, so it is invisible rather than zero — and everything downstream is then subtly wrong: a line chart interpolates over the gap, a 7-day rolling average divides by however many rows exist rather than by seven, and a period-over-period comparison silently pairs the wrong periods.
A spine fixes it structurally: generate every date in the range, then LEFT JOIN the facts onto it and COALESCE the measures to zero. Drive from the calendar, not from the facts — that is the whole idea.
The production version adds columns you cannot compute portably: fiscal periods, holiday flags, business-day counts, ISO week numbers. And it makes the join a cheap equality on an indexed key rather than a function call on every row (§11.5).

Expected: the first query returns two rows (the 1st and the 6th). The second returns eight, six of them zero. Now consider a “3-day average” computed on the first result: it would average the 1st and the 6th as if they were adjacent, and report a number that describes no real 3-day period. That is the bug the spine prevents, and it is invisible without it.

        


        

          
Likely interview questions

          

            
Very commonYour daily revenue chart has gaps. Fix it.
              
Generate a date spine for the reporting range, LEFT JOIN the facts onto it, and COALESCE the measures to zero. The critical detail is the join direction: the calendar must be the driving table, so FROM spine LEFT JOIN facts, never the reverse.
If you need a spine per entity as well — every customer × every day, so a customer's inactive days show zero — CROSS JOIN the spine to the distinct entity list first (§2.8), then left-join. That is the shape behind cohort tables and retention curves.
Two follow-ups to be ready for. Is zero the right fill? For revenue, yes. For a price or a stock level, no — you want the last known value, which is a “last observation carried forward” and in SQL that is LAST_VALUE(x IGNORE NULLS) where supported, or a MAX(...) OVER trick over a filled group id. And what about the range ends? Decide whether the spine starts at the first transaction or at a fixed reporting boundary; those give different denominators.

            

          

        

      


      

        
6.5 BETWEEN on timestamps: the last-day bug ⭐⭐

        
A one-character-class mistake that silently drops almost a whole day of data. It is on every list of SQL gotchas because it is on every codebase.


        
WHERE ts BETWEEN '2026-03-01' AND '2026-03-31' looks like “all of March”. But if ts is a timestamp, the literal '2026-03-31' is interpreted as 2026-03-31 00:00:00, so everything after midnight on the 31st is excluded. You lose 23 hours 59 minutes of the last day, every time.


        

          
Inclusive BETWEEN
ts BETWEEN '2026-03-01' AND '2026-03-31'

Drops most of the 31st. Also breaks differently for date and timestamp columns, so it works in dev and fails in prod.

          
Half-open range
ts >= '2026-03-01' AND ts < '2026-04-01'

Correct for dates, timestamps, and any precision. Also sargable — the index still works.

        


        
Always use half-open ranges for time. [start, end) tiles perfectly with no overlap and no gap, works at any precision, survives a column type change from date to timestamp, and keeps the index usable. The habit generalises: the same convention fixes the as-of join in §2.9 and the interval merging in §8.7.

The cast_to_date column is correct too, but wrapping the column in a function makes the predicate non-sargable and disables the index (§11.5), so the half-open range is the answer that is both right and fast.

        


        

          
Likely interview questions

          

            
Very commonWhat is wrong with WHERE ts BETWEEN '2026-03-01' AND '2026-03-31'?
              
BETWEEN is inclusive on both ends, and a bare date literal compared against a timestamp column means midnight. So the range ends at 2026-03-31 00:00:00 and everything later that day is excluded — roughly 3% of a month's data, silently.
Use a half-open range: ts >= '2026-03-01' AND ts < '2026-04-01'. It is correct at any precision, needs no knowledge of whether the column is a date or a timestamp, tiles adjacent periods with no overlap or gap, and stays sargable so the index is used.
Do not fix it with CAST(ts AS date) BETWEEN ...: it gives the right answer but wraps the indexed column in a function, so the engine can no longer use the index and a range scan becomes a full scan. Nor with AND '2026-03-31 23:59:59', which loses sub-second rows and is wrong for microsecond timestamps.
The generalisation worth stating: use half-open intervals for all time ranges. It is the same convention that makes as-of joins and interval merging correct.

            

          

        

      


      

        
6.6 Week boundaries and ISO weeks

        
Weeks are the least standardised unit in SQL, and “weekly revenue” can differ by a day between two engines reporting the same data.


        
The disagreements: the week can start Sunday or Monday; week 1 can be the week containing 1 January or the first week with four days in the new year (ISO 8601); and a date in late December can belong to week 1 of the next ISO year. That last one means YEAR(d) paired with the ISO week number is a bug — you must use the ISO year.

        
Practical advice: derive the week-start date rather than a week number, and group by that. A date is unambiguous, sorts correctly, joins to a spine, and never has a year-boundary problem. DATE_TRUNC('week', d) in PostgreSQL gives the Monday; in SQLite the portable form is date(d, 'weekday 0', '-6 days').

Look at 2025-12-29 through 2026-01-04: those seven days are one ISO week, but calendar_year changes in the middle and the week number resets. Group by calendar_year, week_no and you split a single week into two buckets. Group by week_starting_monday and it stays one row — which is why deriving the date beats deriving the number.

        


        

          
Likely interview questions

          

            
GotchaTwo dashboards report different weekly revenue from the same table. Why?
              
Almost certainly a week-boundary disagreement. Candidates: one starts weeks on Sunday and the other on Monday; one uses ISO week numbering and the other counts from 1 January; one groups by (YEAR, WEEK) and splits the week that straddles New Year; or the two systems are in different time zones so late-evening events land on different days.
The diagnosis is quick — compare a single week's row counts and look at the boundary days. The fix is to standardise on a week-start date rather than a week number, ideally sourced from a shared dim_date table so both dashboards join to the same definition rather than each computing one.
The ISO detail worth knowing: with ISO 8601 weeks you must pair the week number with the ISO year (IYYY in Oracle, isoyear in PostgreSQL's EXTRACT), not the calendar year, because 31 December can legitimately be in week 1 of the following ISO year.

            

          

        

      


      

        
6.7 Time zones and UTC discipline ⭐

        
The rule is short. The consequences of breaking it are not.


        
Store UTC, convert at the edge. Every timestamp in the warehouse in UTC, converted to a local zone only in the final presentation query, using a named zone ('Asia/Kolkata') rather than a fixed offset ('+05:30') so daylight saving is handled.

        
Why it matters for analytics: “daily active users” depends on where the day boundary is. Grouping UTC timestamps by date gives you UTC days, which for a US audience splits every evening across two days. Converting first and then truncating gives local days. Both are defensible; picking one silently is not.

        
The types: PostgreSQL's timestamptz stores an absolute instant and renders in the session zone; plain timestamp stores wall-clock text with no zone and is a frequent source of silent errors. Prefer the zone-aware type. And note that a date has no zone at all, so any conversion has to happen before truncation, never after.


        

          
Likely interview questions

          

            
ConceptualHow do you handle time zones in a data warehouse?
              
Store everything in UTC with a zone-aware type, and convert to local time only in the outermost presentation layer. Use named time zones ('Europe/London') not fixed offsets, because offsets do not know about daylight saving and a report built on +01:00 is wrong for half the year.
The analytics consequence to raise unprompted: truncating to a date has to happen after the conversion, not before. DATE_TRUNC('day', ts AT TIME ZONE 'Asia/Kolkata') gives local days; DATE_TRUNC('day', ts) gives UTC days, and for a non-UTC audience those differ for every event near midnight. That single choice changes DAU, retention and every daily metric.
Two further points. If the business spans zones, decide whether “today” means the user's local day or a single company day, and put the choice in the column name (event_date_utc vs event_date_local) so nobody has to guess. And keep a timezone column on the user or store dimension if local-day reporting per entity is required — you cannot recover it later.

Likely interview questions

          

            
CodingCalculate age in years from a date of birth.
              
The naive (current_date - dob)/365.25 is an approximation and can be off by a year around a birthday, which matters whenever age gates a decision.
The calendar-correct form is “year difference, minus one if the anniversary has not yet occurred this year”. PostgreSQL has it built in: EXTRACT(YEAR FROM AGE(dob)). MySQL has TIMESTAMPDIFF(YEAR, dob, CURDATE()), which already truncates correctly. SQL Server needs the explicit adjustment because DATEDIFF(YEAR, ...) counts year boundaries crossed, so 31 December to 1 January is “one year”.
That SQL Server behaviour is worth naming, because it is a general trap: several engines' DATEDIFF counts boundary crossings rather than elapsed units, so DATEDIFF(MONTH, '2026-01-31', '2026-02-01') is 1. Read the docs for the specific engine rather than assuming elapsed-time semantics.

            

          

        

      


      

        
6.9 Rolling 7-day and 28-day actives ⭐

        
A rolling distinct count. Cannot be done with a plain window (§5.10), so it is a self-join or a correlated subquery over the spine.


        
Why COUNT(DISTINCT ...) over a window will not work: distinct counts are not incrementally computable, so no engine offers a rolling one. The standard answer is to drive from a date spine and, for each day, count distinct users in the preceding window — a correlated subquery, or equivalently a range join.

Note the half-open window — > day-7 AND <= day — which is exactly seven days including today, with no double-counting at the boundary. Using BETWEEN date(day,'-7 day') AND day would make it eight days wide, which is the §6.5 bug wearing a different hat.

        


        

          
Likely interview questions

          

            
Very commonCompute rolling 7-day active users.
              
Drive from a date spine so every day gets a row, then for each day count distinct users whose activity falls in the trailing seven days. A correlated subquery is the clearest form; a self-join on activity.date > spine.day - 7 AND activity.date <= spine.day with COUNT(DISTINCT user_id) is the same thing and often plans better.
Say why the obvious approach fails: COUNT(DISTINCT ...) is not available as a window function in PostgreSQL, MySQL, SQL Server or SQLite, because a distinct count cannot be maintained incrementally as the frame slides.
Get the window boundaries right — half-open, > d-7 and <= d, or you have an eight-day week. And at scale mention the real-world answer: precompute daily HyperLogLog sketches and merge them over the window, which is how warehouses do rolling uniques without rescanning the events table for every day.

            

          

        

      


      

        
6.10 Point-in-time correctness ⭐⭐

        
The discipline that keeps a training set honest. Asked by anyone who has shipped a model, and the SQL is the as-of join from §2.9.


        
Two different clocks. Event time is when the thing happened; availability time is when your system could have known about it. A fact recorded on Monday but loaded on Wednesday was not available on Tuesday, so a feature for Tuesday must not use it. Joining on event time alone is a look-ahead leak that no amount of cross-validation will catch.

        
Three rules: join dimensions as of the event, not as of today (§2.9). Build rolling features with frames ending at 1 PRECEDING, never CURRENT ROW (§5.8). And where restated data exists — revised financials, corrected addresses — use the original value that was visible at the time, which means the source table needs both timestamps.

Likely interview questions

          

            
Very commonWhat is point-in-time correctness and how do you achieve it in SQL?
              
It means every value in a training row was actually knowable at the row's timestamp. Achieving it has three parts.
As-of dimension joins. Join on the key and the validity window — ON f.key = d.key AND f.ts >= d.valid_from AND f.ts < d.valid_to — so you get the attribute as it was, not as it is. Joining on the key alone with is_current = 1 is the dangerous version because it returns exactly one row per fact and therefore looks right.
Causal windows. Rolling aggregates must end at 1 PRECEDING, not CURRENT ROW, or the feature includes the row it is predicting.
Availability vs event time. If data arrives late, event time is not enough — a fact timestamped Monday but loaded Wednesday must be invisible to a Tuesday feature. That requires the source to record both, and it is the part most pipelines get wrong.
Then the honest closing note: the reason this matters is that leakage inflates offline metrics and cannot be detected by cross-validation, because every fold has the same leak. The only defences are structural — as-of joins, causal windows, and a feature store that enforces point-in-time lookups.
