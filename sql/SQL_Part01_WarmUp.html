1.1 The logical order of execution ⭐⭐

The one piece of theory in this whole subject that pays for itself immediately, because it explains three separate error messages you will otherwise memorise as arbitrary rules.

You write a query in one order and the database evaluates it in another. The logical evaluation order is:

#ClauseWhat exists by the end of it
1FROM / JOINThe combined row set. Nothing is filtered yet.
2WHERERows surviving the row-level filter.
3GROUP BYGroups. Individual rows are no longer addressable.
4HAVINGGroups surviving the group-level filter.
5window functionsComputed over the surviving groups/rows.
6SELECTThe output columns — and only now do aliases exist.
7DISTINCTDuplicate output rows removed.
8ORDER BYOrdering. Aliases are available here.
9LIMIT / OFFSETThe final slice.

Three consequences, and they are the whole reason to know this

An alias defined in SELECT cannot be used in WHERE, because WHERE ran at step 2 and the alias was not created until step 6. It can be used in ORDER BY, which runs at step 8. That is not an inconsistency; it is the order.

An aggregate cannot appear in WHERE, because at step 2 no groups exist yet. That is what HAVING is for.

A window function cannot appear in WHERE either, because windows are computed at step 5, after the filter. This is why top-N-per-group needs a subquery or CTE — see §4.9.

Likely interview questions

          

            
Very commonWhat is the order of execution of a SQL query?
              
FROM/JOIN → WHERE → GROUP BY → HAVING → window functions → SELECT → DISTINCT → ORDER BY → LIMIT.
Then immediately say why it matters, because reciting the list is only half the answer: it explains why a SELECT alias works in ORDER BY but not in WHERE, why an aggregate belongs in HAVING rather than WHERE, and why a window function cannot be filtered without wrapping the query.
One precision point that reads well: this is the logical order, which defines semantics. The optimiser is free to execute in any order that produces the same result — it will happily push a predicate below a join or evaluate LIMIT early. So logical order tells you what a query means; the EXPLAIN plan tells you what it does. See §11.1.

            

            
GotchaWhy can I use a column alias in ORDER BY but not in WHERE?
              
Because WHERE is evaluated at step 2 and the alias is not created until SELECT at step 6. ORDER BY is step 8, by which time the alias exists. Same reason GROUP BY in most dialects wants the expression rather than the alias.
Dialect detail worth knowing, because it is exactly the kind of thing that makes a query non-portable: MySQL and SQLite permit the alias in HAVING and GROUP BY as an extension, PostgreSQL allows it in GROUP BY and ORDER BY but not WHERE or HAVING, and SQL Server allows it only in ORDER BY. If you want one query that runs everywhere, repeat the expression or wrap it in a CTE — a CTE is the clean answer, because the alias becomes a real column of the CTE and every clause downstream can use it.

            

            
ConceptualIf the optimiser can reorder things, why learn the logical order at all?
              
Because it is the contract. The optimiser is only permitted to reorder in ways that preserve the result as defined by the logical order, so the logical order is what makes a query's meaning unambiguous.
It also predicts your error messages, which is the practical payoff. Every “column does not exist” and “aggregate functions are not allowed in WHERE” is the logical order telling you that the thing you referenced had not been created yet.
Where the distinction genuinely bites: LEFT JOIN plus a WHERE filter on the right table. Logically the join happens first and produces NULLs, then WHERE discards them — which silently turns the outer join into an inner one. Understanding that as an ordering consequence rather than a mystery is the whole of §2.2.

            

          

        

      


      

        
1.2 SELECT, WHERE, ORDER BY and the LIMIT trap

        
Ninety percent of the syntax, and one genuine trap that shows up in the most-asked question in SQL interviewing.


        
Things worth being precise about

        
ORDER BY without a total order is non-deterministic. If you sort by a column with ties and take LIMIT 3, which of the tied rows you get is up to the engine, and it can change between runs, between versions, and between a table scan and an index scan. Any time the result must be stable, add a tie-break column — usually a unique id. This is the single most common source of “the test passed locally and failed in CI”.

        
LIMIT without ORDER BY returns arbitrary rows, not the “first” ones. There is no first row in a relation.

        
OFFSET counts rows, not distinct values. This is why LIMIT 1 OFFSET 1 is the wrong answer to “second highest salary” whenever the highest salary is shared — the topic of §4.4, and the demo table is built so you can see it fail.

Likely interview questions

          

            
GotchaIs SELECT ... LIMIT 10 deterministic?
              
No, on two counts. Without ORDER BY the ten rows are whatever the engine finds first, which depends on the plan, the storage layout and prior updates. And with ORDER BY it is still non-deterministic if the sort key has ties, because nothing specifies which of the tied rows wins.
The fix is a total order: append a unique column to the sort key, e.g. ORDER BY salary DESC, id. Volunteering this unprompted is a small, cheap credibility win, and it is the correct answer to “why does this test flake?”
Related trap worth naming: deep OFFSET is slow. LIMIT 20 OFFSET 100000 makes the engine produce and discard 100,000 rows. For pagination at scale you want keyset pagination — WHERE id > :last_seen ORDER BY id LIMIT 20 — which uses the index and stays O(page) rather than O(offset).

            

            
Very commonHow do you get the top 5 rows in each of several dialects?
              
PostgreSQL, MySQL, SQLite, BigQuery, Snowflake, DuckDB: LIMIT 5. SQL Server: SELECT TOP 5, or OFFSET 0 ROWS FETCH NEXT 5 ROWS ONLY. Oracle 12c+: FETCH FIRST 5 ROWS ONLY; older Oracle used WHERE ROWNUM <= 5, which is worth knowing because it applies before ordering and therefore breaks in exactly the way people expect LIMIT to work.
The interviewer usually asks this to find out whether you have used more than one database. A good answer names the standard form — FETCH FIRST n ROWS ONLY is the ANSI spelling — and then says which dialect you actually work in.

            

          

        

      


      

        
1.3 The three COUNTs ⭐

        
A one-line question that eliminates a surprising number of candidates, because the three forms differ only on NULLs and duplicates — and every real table has both.


        

          
COUNT(*)
Counts rows. Never looks at any value, so NULLs are counted. This is the row count of the group.

          
COUNT(col)
Counts rows where col IS NOT NULL. Silently smaller than COUNT(*) whenever the column is nullable.

          
COUNT(DISTINCT col)
Counts distinct non-NULL values. NULL is not a value, so it never contributes.

Likely interview questions

          

            
Very commonDifference between COUNT(*), COUNT(1) and COUNT(col)?
              
COUNT(*) counts rows. COUNT(1) counts rows too and is identical — the argument is a non-null constant, so it can never be skipped; every modern optimiser treats the two the same and any claim that one is faster is folklore. COUNT(col) counts rows where col is not NULL.
So the real content of the question is: do you know that COUNT(col) silently ignores NULLs? That is what makes it a filter in disguise, and it is why a “total orders” number can come out lower than expected when someone counts a nullable column instead of counting rows.
Two extras that land well. COUNT(DISTINCT a, b) counts distinct pairs in MySQL, and the portable version is COUNT(DISTINCT a || '-' || b) with a separator that cannot appear in the data — or better, count over a subquery. And on a large table COUNT(DISTINCT ...) is expensive because it needs to deduplicate; engines offer approximate versions (APPROX_COUNT_DISTINCT, HLL) that trade a percent or so of accuracy for a large speed-up.

            

            
GotchaWhy is my COUNT lower than the row count?
              
Almost always because you counted a nullable column. COUNT(*) - COUNT(col) gives you exactly how many rows were dropped, and that is the first thing to run.
The other two causes, in order of frequency: a JOIN that lost rows because it was an INNER JOIN where you wanted LEFT (or a LEFT JOIN demoted by a WHERE — §2.2), and a DISTINCT you forgot was there.
The habit worth having: after any aggregation, run an assertion that the total is conserved. SELECT COUNT(*) FROM base against SELECT SUM(n) FROM result. §10.7 makes the case for this properly, and volunteering it in an interview reads as someone who has been burned in production.

            

            
CodingCount how many employees each department has, including departments with none.
              
The point of this question is the combination of two things you have to get right together: a LEFT JOIN from departments, and COUNT(e.id) rather than COUNT(*).
SELECT d.name, COUNT(e.id) AS n FROM departments d LEFT JOIN employees e ON e.dept_id = d.id GROUP BY d.name
COUNT(*) would return 1 for the empty department, because the outer join manufactures one all-NULL row and COUNT(*) counts it. COUNT(e.id) returns 0, which is the answer anyone actually wants. This is the cleanest possible demonstration that the difference between the two COUNTs is not academic — try both in the cell in §2.1.

            

          

        

      


      

        
1.4 GROUP BY, properly ⭐

        
The rule is simple and the dialects disagree about how strictly to enforce it — which is exactly why it gets asked.


        
The rule: every column in SELECT must either appear in GROUP BY or be wrapped in an aggregate. The reason is not pedantry — after grouping, individual rows no longer exist, so an ungrouped, unaggregated column has no single value to report.


        
The dialect split. PostgreSQL and SQL Server reject the violation outright. MySQL historically returned an arbitrary row's value, silently, which produced a decade of wrong dashboards; since 5.7 ONLY_FULL_GROUP_BY is on by default and it errors like everyone else. SQLite still allows it and picks an arbitrary row — which you can watch happen in the cell below. That freedom is occasionally useful and mostly a hazard.


        

          
          “The name of the highest earner per department” is not a GROUP BY problem
          
The instinct is SELECT dept_id, name, MAX(salary) ... GROUP BY dept_id. In PostgreSQL that is an error; in MySQL's loose mode it returns a name from an arbitrary row alongside the correct maximum, so the two columns can describe different people. There is no general fix with GROUP BY alone — you need a window function (§4.5) or a correlated filter. Recognising that the question is asking for a row, not an aggregate, is the actual skill.

Likely interview questions

          

            
Very commonWhat is the rule for what can appear in SELECT alongside a GROUP BY?
              
Every selected expression must be either in the GROUP BY list or inside an aggregate. Grouping collapses rows, so any column not covered by one of those two has no defined single value.
The exception worth naming: functional dependency. PostgreSQL will accept SELECT d.id, d.name ... GROUP BY d.id when d.id is the primary key, because name is then uniquely determined by the grouping key. That is standard-compliant and genuinely handy; not every engine implements it.
The trap it protects you from is MySQL's old default, which returned an arbitrary value instead of an error. If you are ever asked why ONLY_FULL_GROUP_BY exists, that is the answer: silently plausible wrong numbers are worse than a failed query.

            

            
Very commonGet the name of the highest-paid employee in each department.
              
This is not a GROUP BY question, and saying so is most of the answer. MAX(salary) gives you a value; you were asked for a row.
Window function, which is the answer to give: rank within each department and filter to rank 1. SELECT dept_id, name, salary FROM (SELECT *, RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) r FROM employees) t WHERE r = 1.
Then handle ties out loud, because it is the follow-up: RANK returns all tied top earners, ROW_NUMBER returns exactly one arbitrarily. Which you want is a requirements question. If they want exactly one deterministically, add a tie-break to the ORDER BY — ORDER BY salary DESC, hire_date, id.
The alternative without windows, worth knowing for “no window functions” constraints: join back to the per-department maximum. JOIN (SELECT dept_id, MAX(salary) ms FROM employees GROUP BY dept_id) m ON e.dept_id = m.dept_id AND e.salary = m.ms. Same tie behaviour as RANK.

            

            
GotchaDoes GROUP BY put NULLs in their own group?
              
Yes. GROUP BY treats all NULLs as one group, even though NULL = NULL is not true. That is a deliberate exception in the standard: grouping, DISTINCT, UNION and ORDER BY all use “not distinct from” semantics rather than equality.
So the demo query in this section returns a group for dept_id = NULL containing Kabir. That is usually what you want, but it means a “per department” report can contain an unlabelled row, and if you later join that result to departments you will lose it. The habit: either COALESCE(dept_id, -1) into an explicit “unassigned” bucket, or filter deliberately and say why.
Contrast this with aggregates, which do skip NULLs — AVG(salary) divides by the count of non-nulls. Grouping keeps NULLs together; aggregating throws them away. Two different rules in the same query, and §1.7 covers the second one.

            

          

        

      


      

        
1.5 WHERE vs HAVING vs QUALIFY ⭐

        
Three filters at three different stages. Knowing which stage each one runs at means you never guess.


        

          
WHERE — step 2
Filters rows, before grouping. Cannot see aggregates or window functions. Cheapest filter: it reduces what everything downstream has to process.

          
HAVING — step 4
Filters groups, after aggregation. This is the only place an aggregate can be filtered.

          
QUALIFY — step 5+
Filters on a window function result. Snowflake, BigQuery, Teradata and DuckDB have it; PostgreSQL, MySQL, SQL Server and SQLite do not — wrap in a subquery instead.

        


        
The performance point, if they ask: put a condition in WHERE whenever it does not depend on an aggregate, because filtering before grouping means fewer rows to group. A condition that belongs in WHERE but is written in HAVING is usually still correct — the optimiser often pushes it down — but it reads as not knowing the difference.

Likely interview questions

          

            
Very commonWHERE vs HAVING — when must you use each?
              
WHERE filters rows before grouping; HAVING filters groups after aggregating. You must use HAVING when the condition involves an aggregate, because at WHERE time no groups exist yet. You should use WHERE for everything else, because fewer rows reach the grouping step.
The example that makes it concrete: “customers with more than three completed orders” needs WHERE status = 'completed' (a row property) and HAVING COUNT(*) > 3 (a group property). Putting the status test in HAVING would be a different question, and putting the count test in WHERE is an error.
Two things worth adding. HAVING without GROUP BY is legal — the whole result is one group — so SELECT SUM(amount) FROM orders HAVING SUM(amount) > 0 works. And for filtering on a window function you need neither: that is QUALIFY where it exists, and a subquery everywhere else.

            

            
ConceptualWhat is QUALIFY and why should I care if my database lacks it?
              
QUALIFY is to window functions what HAVING is to aggregates: a filter that runs after the window is computed. SELECT ... QUALIFY ROW_NUMBER() OVER (PARTITION BY user ORDER BY ts DESC) = 1 is the whole of “latest row per user” in one statement.
It exists in Snowflake, BigQuery, Teradata, Databricks and DuckDB. It is not in PostgreSQL, MySQL, SQL Server or SQLite, where you wrap the query and filter in the outer WHERE.
Why care either way: it is a useful marker of which warehouses you have actually used, and the wrapped-subquery form is the portable idiom you should default to. Writing QUALIFY in a Postgres interview is a small tell; knowing it exists and saying “on Snowflake I'd use QUALIFY, here I'll wrap it” is the opposite.

            

          

        

      


      

        
1.6 NULL and three-valued logic ⭐⭐

        
NULL is not a value. It is the absence of one, and SQL therefore has three truth values rather than two. Almost every “why did my query return nothing” question resolves to this.


        
The rules, all of them

        
Any comparison with NULL yields UNKNOWN, not true and not false. WHERE keeps only rows where the predicate is true, so UNKNOWN rows are discarded — which means WHERE col = NULL and WHERE col != NULL both return nothing. Use IS NULL / IS NOT NULL, the only operators that inspect nullness rather than compare values.

Likely interview questions

          

            
Very commonWhy does WHERE col = NULL return no rows?
              
Because NULL means “unknown”, and comparing anything to an unknown gives UNKNOWN rather than true or false. WHERE only keeps rows whose predicate evaluates to true, so UNKNOWN rows are dropped. The same reasoning makes WHERE col != NULL return nothing, which is the part people find counter-intuitive.
Use IS NULL and IS NOT NULL. If you need a null-safe equality between two nullable columns, the operators are IS NOT DISTINCT FROM (PostgreSQL, standard), <=> (MySQL), IS (SQLite), or the portable fallback (a = b OR (a IS NULL AND b IS NULL)).
The consequence to volunteer, because it is what actually bites: col = x and col <> x do not partition the table. Rows where col is NULL appear in neither, so the two counts will not add up to the total.

            

            
GotchaWhere else does SQL treat NULLs as equal to each other?
              
In several places, which is the genuinely confusing part — the “NULL is never equal to NULL” rule applies to comparison, and a different rule applies to grouping.
Treated as equal (one group / one value): GROUP BY, DISTINCT, UNION, INTERSECT, EXCEPT, ORDER BY and window PARTITION BY. All use “not distinct from” semantics.
Treated as unknown: WHERE, ON, HAVING, CHECK, and IN/NOT IN.
Skipped entirely: aggregates other than COUNT(*).
Depends: a UNIQUE constraint permits multiple NULLs in most engines (they are not equal, so not duplicates) — but SQL Server allows only one, and PostgreSQL 15 added NULLS NOT DISTINCT to opt into the stricter behaviour. And sort position differs: PostgreSQL puts NULLs last ascending, MySQL and SQLite put them first, which is why NULLS FIRST/NULLS LAST exists.

            

            
CodingCount rows where a nullable flag is not 'yes'.
              
The trap: WHERE flag <> 'yes' excludes the NULLs, so if “not yes” is meant to include “unknown” the count is too low. You have to decide what NULL means in this question and then write it explicitly.
If unknown counts as not-yes: WHERE flag IS DISTINCT FROM 'yes', or portably WHERE flag <> 'yes' OR flag IS NULL, or WHERE COALESCE(flag, '') <> 'yes'.
If unknown is a third category: keep three buckets and report them separately — which is usually the honest answer, and the one to suggest.
This is worth practising because it is the shape of a real interview follow-up: the interviewer adds a NULL to the sample data and asks you to re-run. The candidate who asks “how should I treat unknown here?” before writing anything is the one who passes.

            

          

        

      


      

        
1.7 NULLs inside aggregates ⭐

        
Aggregates skip NULLs. That single sentence has three consequences, and one of them is an AVG that quietly answers a different question than the one asked.


        
Every aggregate except COUNT(*) ignores NULLs. So AVG(col) is SUM(col) / COUNT(col), dividing by the number of non-null values — not by the number of rows. If missing means zero in your domain, AVG is wrong and you want SUM(col) / COUNT(*), or AVG(COALESCE(col, 0)).

        
SUM of an empty set is NULL, not zero. A SUM over zero matching rows returns NULL, which then propagates through any arithmetic downstream. Wrap it: COALESCE(SUM(x), 0). COUNT is the exception — it returns 0.

Likely interview questions

          

            
Very commonHow do aggregate functions treat NULL?
              
They ignore them. SUM, AVG, MIN, MAX and COUNT(col) all operate on the non-null values only. COUNT(*) is the sole exception, because it counts rows and never looks at a value.
The consequence that matters: AVG(col) divides by COUNT(col), not by COUNT(*). So if a missing value semantically means zero — no purchase, no clicks, no downtime — then AVG overstates the mean, sometimes badly. Whether NULL means “zero” or “not measured” is a domain question you should ask rather than assume, and the two answers are AVG(COALESCE(col,0)) and AVG(col) respectively.
Two more: SUM over an empty or all-null set returns NULL, not 0, so guard it with COALESCE before doing arithmetic. And MIN/MAX over all-nulls is NULL too, which will quietly propagate into a date range.

            

            
GotchaYou LEFT JOIN and SUM. A customer with no orders shows NULL, not 0. Fix it.
              
COALESCE(SUM(o.amount), 0). The outer join manufactures a row with all-NULL right-hand columns, the aggregate skips it, and SUM over nothing is NULL.
Do the same for the count, but differently: COUNT(o.id) already gives 0, whereas COUNT(*) would give 1 because it counts the manufactured row. So in a LEFT JOIN aggregation the rule is COUNT the right table's key, and COALESCE the sums.
This exact pair — a phantom 1 and a NULL where you wanted 0 — is one of the most common bugs in reporting SQL, and it is why “count customers with zero orders” is a good interview question: it tests the join direction, the COUNT argument and the COALESCE all at once.

            

          

        

      


      

        
1.8 COALESCE, NULLIF and safe division

        
Three small functions that between them prevent most NULL-related and divide-by-zero incidents.


        
COALESCE(a, b, c, ...) returns the first non-null argument. Standard, variadic, everywhere. IFNULL (MySQL, SQLite) and ISNULL (SQL Server) are two-argument dialect versions of the same idea — prefer COALESCE, it is portable.

        
NULLIF(a, b) returns NULL if a = b, else a. Its one killer use is safe division: x / NULLIF(y, 0) turns a would-be divide-by-zero into NULL, which is almost always the honest answer. It is also the neat way to convert a sentinel — NULLIF(status, 'unknown') — into a real NULL.


        

          
          Integer division truncates, and it is the more common bug
          
In PostgreSQL, SQL Server and Oracle, 3 / 4 on two integers is 0, not 0.75. So a conversion rate written as COUNT(converted) / COUNT(*) is always zero. The fix is to force one side to a floating or numeric type: 100.0 * conv / total, or CAST(conv AS numeric). MySQL and SQLite are more forgiving, which is exactly why the bug survives a local test and appears in production. §10.5 covers it properly.

SQLite does this, PostgreSQL does this, SQL Server and Oracle do this. The next three columns are the three fixes, and the last one is the idiom worth internalising: AVG of a 0/1 flag is the rate, so there is no division to get wrong.

        


        

          
Likely interview questions

          

            
Very commonHow do you avoid a divide-by-zero error in SQL?
              
numerator / NULLIF(denominator, 0). When the denominator is zero, NULLIF turns it into NULL, and division by NULL is NULL rather than an error. Wrap the whole thing in COALESCE(..., 0) only if zero is genuinely the right answer for “no denominator” — often it is not, and NULL is more honest.
The CASE form works too — CASE WHEN d = 0 THEN NULL ELSE n / d END — and is what to write if the interviewer bans NULLIF. It is more verbose and identical in meaning.
Worth mentioning: engines differ on what a raw division by zero even does. PostgreSQL and SQL Server raise an error; MySQL returns NULL by default; SQLite returns NULL; Oracle raises. So the code that “works” on MySQL will abort a Postgres job — one more reason to write the guard explicitly rather than relying on the engine.

            

            
GotchaYour conversion rate is coming out as 0. Why?
              
Integer division. In PostgreSQL, SQL Server and Oracle, dividing two integers performs integer division and truncates toward zero, so 3 / 4 is 0 and any rate below 1 becomes 0. It is not a rounding-display problem; the value really is 0.
Three fixes, all fine: multiply by 1.0 (or 100.0 for a percentage), CAST one side to numeric/REAL, or reframe as AVG of a 0/1 indicator, which is my preference because it is shorter and its intent is obvious.
Say the second half too, because it is the interesting part: MySQL and SQLite do not truncate, so this bug is invisible in a local MySQL sandbox and appears the moment the query runs against the warehouse. That asymmetry is the reason to write 100.0 * as a reflex rather than only when you remember.

            

            
CodingCOALESCE vs ISNULL vs IFNULL vs NVL?
              
All return a substitute for NULL; only COALESCE is standard and portable, and only COALESCE takes any number of arguments. IFNULL is MySQL/SQLite, ISNULL is SQL Server, NVL is Oracle — all two-argument.
One real difference beyond portability: in SQL Server, ISNULL forces the result to the data type of the first argument, so ISNULL(short_varchar_col, 'a long default') silently truncates. COALESCE uses standard type-precedence rules instead. That is a genuine correctness difference, not just style, and it is the reason to prefer COALESCE even on SQL Server.
COALESCE also short-circuits left to right, so COALESCE(cheap_col, expensive_subquery) avoids the subquery when the first value is present — though not every planner guarantees that, so do not rely on it for correctness.

            

          

        

      


      

        
1.9 DISTINCT vs GROUP BY

        
For deduplication they are equivalent. The interesting answer is about when they are not, and about why SELECT DISTINCT is often a smell.


        
SELECT DISTINCT a, b FROM t and SELECT a, b FROM t GROUP BY a, b return the same rows, and on any modern optimiser they usually produce the same plan. GROUP BY is strictly more capable, because you can attach aggregates to it; DISTINCT cannot.


        

          
Use DISTINCT when
You genuinely want unique rows and no aggregation. It reads better than an empty GROUP BY.

          
Suspect DISTINCT when
You added it to make duplicate rows go away. That usually means a join fanned out (§2.6) and you are now hiding a modelling error rather than fixing it.

        


        
The point to make in an interview: DISTINCT applied to a whole SELECT list is a blunt instrument. If a join produced duplicates, deduplicating the output can still be wrong — a customer with two matching addresses will collapse correctly, but a SUM computed over the fanned-out rows was already double-counted before DISTINCT ever ran. Fix the join; do not sand down the symptom.

The fourth query is the teaching one: DISTINCT is not a modifier on the first column, it applies to the entire row. SELECT DISTINCT country, name returns every distinct pair, which for unique names is just the original table. Candidates who think DISTINCT binds to one column write this bug regularly.

        


        

          
Likely interview questions

          

            
Very commonDISTINCT or GROUP BY — which is faster?
              
For plain deduplication of the same column list, they are semantically identical and on PostgreSQL, SQL Server and most warehouses they compile to the same plan — a hash or sort-based distinct. Claiming one is universally faster is a bad answer; the honest one is “equivalent here, and I'd check EXPLAIN if it mattered”.
Where a real difference can appear: GROUP BY gives the planner a grouping operator it may satisfy from an existing index's ordering, and on some MySQL versions GROUP BY historically implied a sort while DISTINCT did not. Those are version-specific details, not principles.
The more useful thing to say: GROUP BY is more expressive, so if there is any chance you will want a count or a max later, start with GROUP BY. And COUNT(DISTINCT x) is the expensive one to watch — it must deduplicate before counting and does not parallelise as cleanly as a plain count, which is why warehouses ship approximate variants.

            

            
GotchaWhy is SELECT DISTINCT considered a code smell?
              
Because most of the time it was added to suppress duplicates that a join created, and suppressing them is not the same as fixing them.
If a one-to-many join fanned out your rows, DISTINCT will collapse identical output rows — but any aggregate you computed over the fanned-out set was already wrong, and DISTINCT cannot undo a doubled SUM. Worse, if the duplicated rows differ in any column, DISTINCT keeps them all and you have hidden nothing.
So the correct reflex when you feel the urge to add DISTINCT is to ask where the duplicates came from: is the join key non-unique on the right side, is there a genuine many-to-many needing an aggregate-then-join, or was a LEFT JOIN the wrong shape? Saying that in an interview is a much stronger answer than the syntax. §2.6 is the full treatment.

The single most useful pattern in analytical SQL. Learn this one properly and pivots, funnels, per-segment metrics and cohort tables all become the same move.


        
CASE is an expression, so it goes anywhere a value goes — in SELECT, inside an aggregate, in ORDER BY, in GROUP BY, even inside a window's ORDER BY. Put it inside an aggregate and you get conditional aggregation:

Likely interview questions

          

            
Very commonCount completed and cancelled orders per customer, in one query, as two columns.
              
Conditional aggregation. SUM(CASE WHEN status='completed' THEN 1 ELSE 0 END) AS completed, SUM(CASE WHEN status='cancelled' THEN 1 ELSE 0 END) AS cancelled, grouped by customer. One pass, one scan.
What makes this a good interview question is the wrong answers it invites. Two separate queries joined together is twice the work and needs a full outer join to keep customers who have only one of the statuses. Grouping by (customer, status) gives you rows where the question asked for columns. Conditional aggregation is the pivot, and recognising “this is a pivot” is the skill being tested.
If you use COUNT instead of SUM, omit the ELSE — COUNT(CASE WHEN ... THEN 1 END) — because COUNT ignores NULL but counts a zero. And if the engine supports it, COUNT(*) FILTER (WHERE status='completed') is the standard, more readable spelling; it exists in PostgreSQL, SQLite and DuckDB, not in MySQL or SQL Server.

            

            
GotchaWhat does a CASE with no matching branch return?
              
NULL. There is an implicit ELSE NULL. That is not a footnote — it is the mechanism that makes conditional aggregation work, because aggregates skip NULLs.
It also causes the mirror-image bug: AVG(CASE WHEN x THEN amount ELSE 0 END) averages over all rows with zeros filled in, while AVG(CASE WHEN x THEN amount END) averages over the matching subset only. Those are different numbers and both are defensible answers to “average order value for completed orders” — so state which you computed.
Two smaller points that come up: CASE evaluates WHEN branches in order and stops at the first match, so put the most specific condition first — the same ordering discipline as an if/elif chain. And all branches must return a compatible type; mixing a number and a string in different branches is an error in strict engines and a silent coercion in loose ones.

            

          

        

      


      

        
1.11 UNION, UNION ALL, INTERSECT, EXCEPT

        
Set operators stack results vertically. One of them does hidden work, and knowing which is a standard question.


        

          

            
OperatorDoesDeduplicates?Cost

            
              
UNION ALLConcatenatesNoCheap — just appends

              
UNIONConcatenates then dedupsYesNeeds a sort or hash over the whole result

              
INTERSECTRows in bothYesSort/hash; INTERSECT ALL keeps multiplicity

              
EXCEPT / MINUSRows in the first, not the secondYesSort/hash. Oracle spells it MINUS

            
          

        


        
The rule to state: use UNION ALL unless you specifically need deduplication. UNION pays for a distinct over the combined result whether or not there are any duplicates to remove, and on large sets that is a real cost. Writing UNION by habit is one of the easiest performance wins to point out in a code review.

        
Requirements: both sides need the same number of columns in the same order with compatible types. Column names come from the first branch. ORDER BY applies to the whole result and goes at the very end, not on a branch.

        
EXCEPT is a lovely reconciliation tool. Running (A EXCEPT B) UNION ALL (B EXCEPT A) gives you the symmetric difference — every row present in one source and not the other. That is the fastest way to answer “why do these two tables disagree”, and it comes up in §10.8.

Likely interview questions

          

            
Very commonUNION vs UNION ALL — which and why?
              
UNION removes duplicate rows from the combined result; UNION ALL does not. The deduplication is not free — it requires sorting or hashing the entire combined set — so use UNION ALL unless you actually need dedup.
That is the whole answer, but two additions make it a senior one. First, if you know the branches are disjoint — different date partitions, different statuses, different source systems — then UNION can only ever do wasted work, so UNION ALL is both faster and more truthful about your intent. Second, UNION silently deduplicating can hide a genuine data problem: if the same row appears twice because an upstream job ran twice, UNION conceals it and UNION ALL shows it to you.
Mechanics to have ready: same column count and compatible types on both sides, names taken from the first branch, and a single ORDER BY at the end applying to the whole result.

            

            
CodingFind rows present in table A but not in table B — three ways.
              
EXCEPT — SELECT k FROM a EXCEPT SELECT k FROM b. Cleanest when you are comparing whole rows or a key list, and it deduplicates for free. Oracle spells it MINUS; MySQL only gained it in 8.0.31.
NOT EXISTS — SELECT * FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.k = a.k). The right choice when you need other columns from a, and it is NULL-safe.
LEFT JOIN ... WHERE b.k IS NULL — the anti-join. Equivalent, and often the fastest plan on older engines.
The fourth option, NOT IN, is the one to flag as dangerous: a single NULL in b.k makes it return zero rows. That is §2.4, and volunteering it here is exactly the kind of unprompted precision interviewers are listening for.
