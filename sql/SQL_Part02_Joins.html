Ask an interviewer where candidates lose SQL rounds and you will hear the same answer: joins that are syntactically fine and semantically wrong. The query runs, returns plausible numbers, and is off by a factor of two. Three failures account for most of it — a WHERE clause quietly demoting a LEFT JOIN, a NOT IN annihilated by a single NULL, and a one-to-many join multiplying the rows you then sum. 2.1 The five join types, stated precisely ⭐

Everyone can draw the Venn diagrams. The interview value is in stating what happens to the unmatched rows, because that is what every follow-up is about.

JoinKeepsUnmatched rows becomeRow count vs left
INNEROnly matching pairsDroppedCan shrink or grow
LEFT [OUTER]All left rows + matchesRight side becomes NULL≥ left, never fewer
RIGHT [OUTER]All right rows + matchesLeft side becomes NULL≥ right
FULL [OUTER]Everything from bothNULL on whichever side is missing≥ max(left, right)
CROSSEvery combinationN/A — no conditionleft × right

The line worth having ready: an INNER JOIN can increase your row count. People describe inner joins as “filtering”, which is only half true — if the right side has two matches for a left row, you get two output rows. That is fan-out, and it is §2.6.

Dialect note: MySQL has no FULL OUTER JOIN — you emulate it with LEFT ... UNION ... RIGHT. SQLite only gained RIGHT and FULL in 3.39 (2022), so older SQLite answers had to swap the table order.

Likely interview questions

          

            
Very commonExplain the join types.
              
Give the definition and what happens to unmatched rows, because that is the part that carries information. INNER keeps only matching pairs. LEFT OUTER keeps every left row, filling the right side with NULLs when there is no match. RIGHT is the mirror. FULL OUTER keeps everything from both sides. CROSS is the Cartesian product with no condition.
Then add the two things most candidates omit. An inner join is not just a filter — with a one-to-many relationship it multiplies rows, so the output can be larger than either input. And RIGHT JOIN is rare in practice: it is the same as a LEFT JOIN with the tables swapped, and since queries read top-down, keeping every join left-outer makes the “driving” table obvious. Saying you prefer LEFT for readability is a real answer, not a dodge.
Dialect facts worth a sentence: MySQL has no FULL OUTER JOIN (emulate with LEFT UNION RIGHT), and SQLite only added RIGHT/FULL in 3.39.

            

            
CodingCount employees per department, including departments with nobody.
              
Two decisions, both of which the question is testing. Drive from departments with a LEFT JOIN, so the empty department survives. And count the right table's key, not *.
SELECT d.name, COUNT(e.id) AS n FROM departments d LEFT JOIN employees e ON e.dept_id = d.id GROUP BY d.name
COUNT(*) returns 1 for the empty department, because the outer join manufactures one row of NULLs and COUNT(*) counts rows regardless of content. COUNT(e.id) returns 0. Same for sums: COALESCE(SUM(...), 0).
If the interviewer then asks “and only departments with none”, that is HAVING COUNT(e.id) = 0, or better an anti-join — §2.4.

            

          

        

      


      

        
2.2 The LEFT JOIN + WHERE trap ⭐⭐

        
The most common semantic bug in production SQL, and one of the most reliable interview filters. The query runs, returns plausible rows, and has silently become an inner join.


        
Recall the execution order from §1.1: the join runs at step 1 and produces NULLs for unmatched rows; WHERE runs at step 2 and evaluates its predicate against those NULLs. Any comparison with NULL is UNKNOWN, WHERE keeps only TRUE — so every manufactured row is discarded and the outer join is undone.


        

          
Demoted to INNER
FROM a LEFT JOIN b ON b.a_id = a.id
WHERE b.status = 'x'

Rows of a with no b have b.status = NULL, which fails the test. They vanish.

          
Still an outer join
FROM a LEFT JOIN b ON b.a_id = a.id
  AND b.status = 'x'

The condition restricts what counts as a match. Unmatched rows of a survive with NULLs.

        


        
The exception that is also the fix: WHERE b.id IS NULL is a perfectly good thing to put in WHERE after a LEFT JOIN — it is how you write an anti-join. The rule is not “never filter the right table in WHERE”; it is “a WHERE predicate on the right table must be null-aware, or you have chosen an inner join by accident”.

Putting the predicate in ON is the one variant that answers the question, because it says “a cancelled order is not a match” before the outer join ever fills anything in.

        


        

          
Likely interview questions

          

            
Very commonWhat is the difference between a condition in ON and the same condition in WHERE?
              
For an INNER JOIN, none — the optimiser treats them identically, and you can put the predicate wherever reads better.
For an outer join, it changes the result. A condition in ON defines what counts as a match; unmatched left rows still come through with NULLs. The same condition in WHERE runs after the join has already produced those NULLs, and since NULL = 'x' is UNKNOWN rather than true, the manufactured rows are filtered out — silently converting your LEFT JOIN into an INNER JOIN.
So the rule: filter the right-hand table in ON; filter the left-hand (driving) table in WHERE. The one deliberate exception is WHERE right.key IS NULL, which is how you express an anti-join.
Why this is such a good interview question: the buggy query returns fewer rows but no error, and the numbers look reasonable. It is the canonical example of SQL being syntactically fine and semantically wrong.

            

            
GotchaYou wrote a LEFT JOIN and got the same row count as an INNER JOIN. What do you check?
              
Three things, in order.
A WHERE predicate on the right table, which is the trap above. Move it into ON or make it null-aware.
An implicit filter you did not notice — a downstream JOIN to a third table on a right-side column does the same thing, and so does an INNER JOIN anywhere later in the chain. Join order matters: a LEFT JOIN b INNER JOIN c can eliminate the rows b preserved.
Or it is genuinely correct — if every left row happens to have a match, LEFT and INNER agree, and that is a fact about your data rather than a bug. Confirm with SELECT COUNT(*) FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE ...).
The habit worth stating: after writing any join, check the row count against the driving table's count and be able to explain the difference. That one check catches both this bug and fan-out.

            

          

        

      


      

        
2.3 Filter in ON vs filter in WHERE, deliberately ⭐

        
Having seen the trap, here is the decision table — because sometimes the demotion is what you want, and saying so is the mature answer.


        

          

            
You wantPut the condition inWhy

            
              
Every customer, with completed-order statsONKeeps customers with no completed orders, showing 0

              
Only customers who have a completed orderWHERE (or use INNER)The demotion is the requirement — but write INNER JOIN so intent is explicit

              
Customers with no completed orderON + WHERE o.id IS NULLAnti-join. The ON restricts matching, the WHERE keeps only non-matches

              
Filter on the driving tableWHERENo NULLs involved; WHERE also lets the optimiser filter before joining

            
          

        


        
The style rule that avoids the whole problem: if a filter belongs to the join's meaning, write it in ON. If a filter belongs to the question's scope — a date range, a region, a tenant id on the driving table — write it in WHERE. And if you actually want an inner join, write INNER JOIN rather than a LEFT JOIN you plan to demote; reviewers cannot tell an intentional demotion from an accident.

Likely interview questions

          

            
CodingCustomers who have never placed a completed order.
              
The subtlety is “never placed a completed order” is not the same as “has no orders”. A customer with only cancelled orders must be included, so the status test has to live in the ON clause, not be applied afterwards.
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'completed' WHERE o.id IS NULL
Equivalent and arguably clearer: WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status = 'completed'). I would write the NOT EXISTS version in production because the intent is legible without reasoning about outer-join semantics, and it stays correct if someone later adds a column to the SELECT.
What not to write: WHERE c.id NOT IN (SELECT customer_id FROM orders WHERE status='completed') — correct only as long as customer_id is never NULL. §2.4.

            

            
ConceptualDoes moving a filter from WHERE to ON affect performance?
              
For an inner join, no — the optimiser normalises both into the same plan, and predicate pushdown will apply the filter as early as it can regardless of which clause you wrote it in.
For an outer join it is not a performance question at all, it is a correctness question, so the comparison does not apply: the two forms compute different results.
The performance point that is real: filters on the driving table should be as selective as possible and are best expressed in WHERE, because that gives the planner the clearest opportunity to reduce the row set before the join. And a filter that could apply to either side of an inner join is worth writing on the larger table, since that is where eliminating rows saves the most work. Beyond that, read the EXPLAIN plan rather than theorising — §11.2.

            

          

        

      


      

        
2.4 Anti-joins, and why NOT IN breaks on NULL ⭐⭐

        
Three ways to write “rows in A with no match in B”, one of which returns zero rows the moment a single NULL appears. This is asked constantly, and the reason is pure three-valued logic.


        
Why NOT IN collapses

        
x NOT IN (1, 2, NULL) expands to x <> 1 AND x <> 2 AND x <> NULL. That last term is UNKNOWN for every x, and TRUE AND UNKNOWN is UNKNOWN — so the whole predicate can never be TRUE, and WHERE keeps nothing. One NULL in the subquery annihilates the entire result set. No error, no warning, just an empty answer.

        
Note the asymmetry precisely, because the usual shorthand is slightly wrong. IN is also three-valued: with no match and a NULL present it returns UNKNOWN, not FALSE. The difference is that inside a WHERE clause UNKNOWN and FALSE have the same effect — the row is dropped — and for IN that is the outcome you wanted. A genuine match still returns TRUE and wins. So IN is safe in practice; NOT IN is not, because there the dropped row is the answer.


        

          
NOT EXISTS
Correct with NULLs. Row-by-row existence test, short-circuits, usually the best plan. Default to this.

          
LEFT JOIN ... IS NULL
Correct. The classic anti-join, and often the fastest on older engines. Slightly more to read.

          
NOT IN
Correct only if the subquery column can never be NULL. Add WHERE col IS NOT NULL or do not use it.

So IN is not immune to NULL either — it just does not matter, because inside WHERE both UNKNOWN and FALSE drop the row, which is what you wanted anyway. With NOT IN, UNKNOWN also drops the row — and there it is exactly what you did not want. That asymmetry, not immunity, is the real explanation.

        


        

          
Likely interview questions

          

            
Very commonWrite an anti-join three ways. Which do you prefer?
              
NOT EXISTS — SELECT * FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.k = a.k). Correct with NULLs, expresses intent directly, and modern optimisers turn it into a hash anti-join.
LEFT JOIN + IS NULL — FROM a LEFT JOIN b ON b.k = a.k WHERE b.k IS NULL. Also correct. Historically the fastest on MySQL, and still what many optimisers produce internally.
NOT IN — correct only when the subquery column is guaranteed non-null.
My preference is NOT EXISTS, for three reasons worth saying: it is null-safe by construction, it reads as the requirement, and it does not risk someone later adding a SELECT column that turns the anti-join into a fan-out. Also mention EXCEPT as a fourth option when you are comparing whole key lists rather than filtering a table.

            

            
GotchaWhy does NOT IN with a subquery return no rows?
              
Because the subquery produced at least one NULL. x NOT IN (a, b, NULL) is x <> a AND x <> b AND x <> NULL, and the final term is UNKNOWN for every possible x. Since TRUE AND UNKNOWN is UNKNOWN and WHERE keeps only TRUE, the result is empty regardless of the data.
Then state the asymmetry precisely, because the common shorthand “IN is unaffected” is not quite right. IN is three-valued too: with no match and a NULL in the list it returns UNKNOWN, not FALSE. It is harmless only because WHERE discards UNKNOWN and FALSE alike, and for the positive test that is the right outcome. A genuine match still yields TRUE and wins. With NOT IN, the discarded UNKNOWN rows are the answer, which is why only the negation is dangerous.
Fixes, in order of preference: use NOT EXISTS; or add WHERE col IS NOT NULL inside the subquery; or make the column NOT NULL in the schema if that is the truth. There is also a performance angle — some optimisers cannot convert a NOT IN over a nullable column into an anti-join at all, precisely because of these semantics, so it can be both wrong and slow.

            

            
ConceptualIs NOT EXISTS always faster than NOT IN?
              
Not always, and claiming so is a weaker answer than explaining the asymmetry. On PostgreSQL and SQL Server the two usually produce the same anti-join plan when the column is NOT NULL, because then the semantics coincide and the optimiser is free to rewrite.
Where NOT EXISTS wins is on a nullable column: the NOT IN semantics force the engine to evaluate the whole subquery and handle the three-valued case, which blocks the anti-join rewrite. So the honest answer is “they are usually equivalent on non-nullable keys, and NOT EXISTS is both correct and better-optimised on nullable ones, which is why I default to it”.
One more: NOT EXISTS can short-circuit per outer row, which matters when the inner table is large and indexed on the join key. NOT IN with an uncorrelated subquery may materialise the whole list first.

            

          

        

      


      

        
2.5 Semi-joins: EXISTS vs IN vs JOIN + DISTINCT ⭐

        
“Rows in A that have at least one match in B” — three spellings again, and here the difference is about row multiplication rather than NULLs.


        
EXISTS is a semi-join: it asks “is there at least one?” and stops at the first hit. It never duplicates a left row, whatever the cardinality on the right. IN with a subquery is the same thing semantically. A plain JOIN is not — it returns one row per match, so a customer with four orders appears four times, and people then paper over it with DISTINCT.

        
The rule: if you only need existence, use EXISTS. Reach for a join when you actually want columns from the right table. Reaching for JOIN ... DISTINCT to answer an existence question is the smell described in §1.9.

Likely interview questions

          

            
Very commonEXISTS vs IN vs JOIN — when do you use each?
              
EXISTS for an existence test. It is a semi-join: at most one output row per left row, regardless of how many matches exist, and it can stop scanning at the first hit.
IN for the same test against a small, known list or a non-null subquery. Semantically equivalent to EXISTS for the positive case; only the negation differs (§2.4).
JOIN when you need columns from the other table. Accept that it multiplies rows and handle that deliberately — aggregate, or deduplicate on a key you can justify.
The performance folklore worth correcting: “EXISTS is faster than IN” was true on old MySQL, where an IN subquery was re-executed per row. On modern PostgreSQL, SQL Server and MySQL 8 the optimiser rewrites both to the same semi-join, so the real reasons to choose are correctness on NULLs and readability. A candidate who says “they're usually the same plan now; I choose on clarity” sounds current.

            

            
CodingCustomers who ordered both a hardware and a software product.
              
This is the “AND across rows” problem, and the wrong answer is WHERE category = 'hardware' AND category = 'software' — impossible for a single row. Three correct approaches:
Group and count distinct: filter to the two categories, group by customer, and require COUNT(DISTINCT p.category) = 2. This is the one to write; it generalises to N categories by changing one number.
Two EXISTS clauses: one per category, ANDed together. Very readable, and the most efficient when the categories are highly selective and indexed.
INTERSECT: the set of customers who bought hardware intersected with those who bought software. Elegant, and the natural answer if the interviewer just covered set operators.
The follow-up to expect is “now hardware but not software”, which is the group-and-count version with COUNT(DISTINCT ...) = 1 plus a MAX(category) check, or cleanly an EXISTS plus a NOT EXISTS.

            

          

        

      


      

        
2.6 Fan-out: the join that doubles your revenue ⭐⭐

        
The most expensive join bug there is, because it does not lose data — it invents it, and the resulting number is plausible enough to reach a slide.


        
Join orders to order_items and each order appears once per item. Now SUM(orders.amount) counts the order's total once per line item. An order with two items reports double revenue. Nothing errors; the total is simply wrong, and wrong in the direction that flatters.


        

          
          The rule that prevents it
          
Never aggregate a column from the “one” side after joining to the “many” side. Either aggregate the many-side first and join the result (one row per key, so no fan-out), or aggregate over a key that survives the multiplication — SUM(items.qty * items.price) is safe because those columns belong to the many side. The general fix is aggregate first, join second.

The gap between 4,255 and 2,530 is real — not every order has itemised lines — and noticing that the two questions have different answers is more valuable than either query. The last result set shows exactly which five orders were double-counted.

        


        

          
Likely interview questions

          

            
Very commonYour revenue number doubled after adding a join. What happened?
              
Fan-out. You joined a one-side table to a many-side table, so each parent row is repeated once per child, and the parent's amount is now summed once per child. An order with three line items contributes its total three times.
Diagnose it in one query: compare COUNT(*) before and after the join. If the count grew, every aggregate over parent columns is now inflated by exactly that factor, per group.
Fixes, in order of preference. Aggregate first, then join — collapse the many side to one row per key in a subquery or CTE, then join. Aggregate only many-side columns — SUM(qty * price) is fine because both live on the child. SUM(DISTINCT ...) exists but is a trap: it deduplicates by value, so two genuinely different orders that happen to bill the same amount get collapsed into one. Mention it and reject it.
And the habit: after any join, assert that the total is conserved. §10.7.

            

            
GotchaCan an INNER JOIN return more rows than either input table?
              
Yes, and this is a genuinely good question because so many people describe joins as filters. If the join key is non-unique on both sides, the output for that key is the product of the multiplicities: three matching rows on the left and four on the right produce twelve rows.
That is a many-to-many join, and it is almost always a modelling error rather than an intention. If the key really is many-to-many, you need a bridge table or you need to aggregate one side before joining.
The practical check to volunteer: before joining, verify uniqueness of the intended key on at least one side — SELECT k, COUNT(*) FROM t GROUP BY k HAVING COUNT(*) > 1. If it returns rows, you have a fan-out waiting to happen, and knowing that before writing the join is the difference between an hour and a week.

Whenever a hierarchy has a root, a self-join to the parent must be LEFT or you delete the root from your own report.

        


        

          
Likely interview questions

          

            
Very commonFind employees who earn more than their manager.
              
Self-join on e.manager_id = m.id and compare salaries: SELECT e.name FROM employees e JOIN employees m ON e.manager_id = m.id WHERE e.salary > m.salary. Aliasing the same table twice is the whole trick, and it is worth saying out loud that the two aliases are two independent scans of one table.
Then volunteer the edge case, because it is the follow-up: the root of the hierarchy has a NULL manager and is dropped by the inner join. That is correct for this question — a CEO cannot out-earn a manager they do not have — but if the question were “list every employee with their manager” you must switch to LEFT JOIN or you silently omit the top of the org.
Extensions they may add: “more than their manager's manager” (join three times, or use a recursive CTE — §9.6), “more than the department average” (a window function, AVG(salary) OVER (PARTITION BY dept_id), which is neater than a correlated subquery), and “everyone in a manager's whole reporting tree”, which genuinely needs recursion.

            

            
CodingFind all pairs of employees in the same department.
              
Self-join on the department, plus a condition to avoid the two obvious defects: ON a.dept_id = b.dept_id AND a.id < b.id.
The < rather than <> is the point of the question. a.id <> b.id gives you each pair twice — once as (Asha, Bhavin) and once as (Bhavin, Asha). Using < keeps exactly one ordering of each pair and simultaneously excludes self-pairs. Omitting the condition entirely also pairs everyone with themselves.
Say the count: for a group of n, you get n(n−1)/2 pairs, so the output grows quadratically. On a large table “all pairs” is a query to push back on rather than run — which is a good instinct to voice, and it is the same reasoning as §9.5 on combinations.

            

          

        

      


      

        
2.8 CROSS JOIN, deliberately

        
Usually a bug. Occasionally the only correct tool — and knowing the second case is what separates “never use it” from a real answer.


        
A CROSS JOIN pairs every left row with every right row. Accidentally, that is the missing-ON-clause disaster: two 100,000-row tables become ten billion rows. Deliberately, it is how you manufacture a complete grid — every combination that should exist — so you can left-join real data onto it and see the zeros.


        
That is the same reasoning as the date spine in §6.3, generalised: if you group by something, you only get the combinations your data happens to contain. A country-by-status report built with GROUP BY silently omits “UK, cancelled” if no UK order was ever cancelled — and “zero” is usually the most interesting cell on the report.

Likely interview questions

          

            
ConceptualWhen would you deliberately write a CROSS JOIN?
              
Three legitimate uses, and having them ready turns a “never” answer into a real one.
To build a complete grid. Cross-join the dimension members you want reported — every date × every product, every country × every status — then LEFT JOIN the facts onto it. Without this, combinations with no data are missing rows rather than zeros, and a “zero sales” row is often the point of the report.
To generate rows. Cross-joining a small numbers table against itself gives you a sequence generator, which is how you build a date spine on engines lacking generate_series.
To apply one scalar to every row — cross-joining a one-row subquery holding a total or a threshold. This is cleaner than repeating a scalar subquery in several places, and it computes it once.
The guardrail to state: always bound both sides. A cross join against a table you have not filtered is the classic runaway query, and it is worth saying that you would check the row-count estimate in EXPLAIN before running one on production.

            

          

        

      


      

        
2.9 Range joins and the as-of join ⭐

        
Joining on BETWEEN rather than =. This is how you attach a value that was true at the time, and it is the single most important join for anyone doing modelling work.


        
Range join: the condition is an interval containment rather than equality — bucketing an amount into a band, or matching a row to the version of a dimension that was valid on its date. As-of join: a range join against a history table where you want the most recent record not later than the event. Both matter because a naive equality join to a dimension table gives you today's attribute, not the one in force when the fact happened.


        

          
          Why this is the join that matters for modelling
          
If you train a model on features joined from a dimension table by key alone, every row gets the attribute's current value — including rows from two years ago. That is look-ahead leakage, and it is invisible in the SQL. The as-of join is the fix: join on the key and the validity window. Interviewers with an ML background ask this specifically, and it is the SQL half of the point-in-time discussion in §6.10.

        


        
Half-open intervals, always. Store and compare validity windows as valid_from <= t AND t < valid_to. Using <= on both ends makes the boundary instant belong to two rows, so a row-per-event join silently doubles. The half-open convention [from, to) makes adjacent periods tile perfectly with no overlap and no gap.

Likely interview questions

          

            
Very commonYou have a fact table and a slowly-changing dimension. How do you join them correctly?
              
Join on the business key and the validity window: ON f.key = d.key AND f.event_date >= d.valid_from AND f.event_date < d.valid_to. That returns the version of the dimension row that was in force when the fact occurred.
Say why the naive join is wrong, because that is the substance: joining on the key alone either multiplies the fact by every historical version of the dimension, or — if you also filter WHERE d.is_current = 1 — attaches today's attributes to a two-year-old event. The second is worse, because it produces exactly one row per fact and therefore looks correct.
Two details that mark experience. Use half-open intervals [from, to), so adjacent versions tile without overlapping; with BETWEEN on both ends the boundary date matches two versions and the fact is duplicated. And set the open-ended valid_to to a sentinel like '9999-12-31' rather than NULL, because NULL fails the comparison and silently drops the current version — or handle it with COALESCE(valid_to, '9999-12-31').
If the engine has a native as-of join — DuckDB's ASOF JOIN, ClickHouse's ASOF, or LATERAL plus ORDER BY ... LIMIT 1 in PostgreSQL — say so; range joins are expensive and the specialised operator is far faster.

            

            
GotchaWhy are range joins slow, and what do you do about it?
              
Because an inequality cannot be satisfied by a hash join. Hash joins need equality to build a hash key, so a pure range condition falls back to a nested loop — every left row scanned against a range of right rows — which is quadratic in the worst case.
Mitigations, roughly in order of impact. Add an equality predicate if one exists (the business key, a tenant id, a date bucket): the planner can hash on that and only apply the range test within each bucket. Index the range column so the inner side is a seek rather than a scan. Bucket both sides to a coarse grain — join on the month and then filter the exact range — which turns most of the work into an equality join.
And use the purpose-built operator where it exists: PostgreSQL has range types with GiST indexes, DuckDB and ClickHouse have ASOF JOIN, and Spark has range-join hints with a configurable bin size. Knowing that a range join is a known-hard operator with dedicated support, rather than just “slow SQL”, is the answer that lands.

            

          

        

      


      

        
2.10 Composite-key joins

        
Joining on more than one column. Simple, except for two failure modes that are both silent.


        
Failure one: a forgotten key column. Joining daily metrics on date alone when the grain is (date, region) produces a fan-out by the number of regions. The output row count is a clean multiple of the input, which is why comparing counts before and after every join catches it immediately.

        
Failure two: a NULL in one of the key columns. Composite equality means every column must match, and NULL = NULL is UNKNOWN, so a row with a NULL in any key component matches nothing. If the key is legitimately optional, join with IS NOT DISTINCT FROM (PostgreSQL) or COALESCE both sides to a sentinel — and note in a comment that you did, because it is a semantic choice.


        
USING and natural joins. JOIN ... USING (a, b) is shorthand when the columns are identically named, and it collapses them into one output column. NATURAL JOIN goes further and joins on every identically-named column — which is why you should never use it: adding an unrelated updated_at column to both tables silently changes the join key and the result. Say that if asked; it is a good instinct to display.

The overlap predicate is worth memorising — a.start <= b.end AND a.end >= b.start. It is shorter and more robust than enumerating the four ways two intervals can intersect, and it reappears in §8.7 for merging intervals. The second query shows that (user_id, plan) is still not unique — user 1 has two pro rows and user 2 has two basic rows — so even the composite key would fan out. That is exactly the check to run before writing the join, not after debugging it.

        


        

          
Likely interview questions

          

            
CodingHow do you test whether two date ranges overlap?
              
a.start <= b.end AND a.end >= b.start. Two intervals overlap if and only if each begins before the other ends, and that single conjunction covers all cases — containment, partial overlap in either direction, and identity.
The wrong instinct is to enumerate cases: “a starts inside b, or b starts inside a, or a contains b, or …”. That is four ORed conditions, easy to get wrong, and it is what most candidates write first. Deriving the two-clause form out loud is a nice piece of reasoning to show.
Two refinements. If the intervals are half-open [start, end) — which they should be — the predicate becomes strict on both: a.start < b.end AND a.end > b.start, so intervals that merely touch do not count as overlapping. And if end can be NULL meaning “still open”, use COALESCE(end, '9999-12-31') or the comparison silently fails.
PostgreSQL has native range types and the && overlap operator with GiST index support, which is worth naming as the production answer.

            

            
GotchaWhy should you avoid NATURAL JOIN?
              
Because the join key is implicit and determined by column names, so it changes when the schema changes. Add a column called created_at to both tables — a routine, unrelated migration — and your NATURAL JOIN silently starts joining on it too, returning far fewer rows. Nothing in the query text changed and nothing errors.
USING (a, b) is the safe middle ground: the key is explicit, and the duplicated columns collapse into one in the output, which is genuinely tidier than ON when the names match. Its one wrinkle is that you can no longer qualify the joined column as t.a in some engines, since it belongs to neither table.
Explicit ON is what I would write in anything long-lived: it is verbose, and being verbose about the join key is the point.
