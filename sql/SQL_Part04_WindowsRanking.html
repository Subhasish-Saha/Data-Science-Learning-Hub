4.1 The anatomy of OVER ⭐⭐

Three independent components. Most people learn two of them, and the third is where §5 lives.

PARTITION BY is GROUP BY that does not collapse — it splits the rows into independent groups, and the function restarts in each. Omit it and the whole result is one partition.

ORDER BY defines the sequence, which ranking, LAG/LEAD and running totals all need. It is unrelated to the query's final ORDER BY; you can order the window one way and the output another.

The frame restricts which rows within the partition the function sees. Adding ORDER BY to an aggregate window silently changes the default frame from the whole partition to everything up to the current row — which is what turns SUM into a running total, and is the source of the tie bug in §5.2.

That is the single most surprising fact about window functions and it is worth internalising here rather than debugging later.

        


        

          
Likely interview questions

          

            
Very commonWhat is a window function?
              
A function that computes across a set of rows related to the current row, without collapsing them. That last clause is the definition — an aggregate returns one row per group, a window function returns one value per row while still seeing the whole group.
That is why you can show a salary next to its department average on the same line, which is impossible with GROUP BY alone without a join back.
Give the three components — PARTITION BY, ORDER BY, frame — and note where they run: after WHERE, GROUP BY and HAVING, before SELECT. Two consequences follow immediately and both get asked: you cannot filter on a window result in WHERE (§4.9), and a window function can take a grouped aggregate as its argument (§3.6).

            

            
GotchaWhat is the difference between PARTITION BY and GROUP BY?
              
GROUP BY reduces the result to one row per group. PARTITION BY keeps every row and computes the function within each group. Same grouping concept, opposite effect on cardinality.
Practical consequences worth listing. With GROUP BY you lose access to individual rows, so “the name of the top earner per department” is not expressible (§1.4); with PARTITION BY it is trivial. You can use both in one query — GROUP BY first, then a window over the grouped rows, which is how percent-of-total works. And they can partition on different things: GROUP BY month with a window PARTITION BY nothing gives you each month's share of the year.
Performance note: a window function usually costs a sort per distinct PARTITION BY/ORDER BY combination, so several windows with the same specification are cheap (one sort, reused) while several with different specifications each pay. Reusing one named window (§5.9) makes that explicit.

            

          

        

      


      

        
4.2 Why a window is not an aggregate ⭐

        
The distinction that makes half the hard questions easy: you can have the detail row and its group's summary at the same time.


        
Before window functions, “show each employee alongside their department average” required grouping into a derived table and joining it back. With a window it is one expression, one pass, no join — and no risk of the join fanning out.


        

          
GROUP BY + join back
Two passes, a join to get wrong, and the join key must be unique or you fan out. Still the right answer when the engine has no window functions.

          
Window function
One pass, no join, and the comparison to the group is available on every row. Also composes: several different windows in one SELECT.

The window version keeps him, because PARTITION BY puts all NULLs in one partition (the same rule as GROUP BY, §1.4), whereas the inner join finds no matching group. Eleven rows versus twelve — another quiet row loss, and a good reason to prefer the window form.

        


        

          
Likely interview questions

          

            
CodingShow each employee's salary as a percentage of their department's total.
              
100.0 * salary / SUM(salary) OVER (PARTITION BY dept_id). One expression, no subquery, no join.
Three things to mention while writing it. 100.0 not 100 — integer division (§1.8). The NULL department becomes its own partition, so Kabir's share is 100% of a one-person group, which is arithmetically right and probably not what a report wants; decide and say so. And the percentages sum to 100 within each partition, which is a free assertion you should actually check.
The pre-window alternative — group to a derived table and join back — is worth naming because it is the answer if the engine is old MySQL, and because it exposes a hazard the window version does not have: the join drops rows whose group key is NULL.

            

          

        

      


      

        
4.3 ROW_NUMBER vs RANK vs DENSE_RANK ⭐⭐

        
The most-asked window question there is. All three agree until there is a tie, and every interview sample has a tie.


        

          

            
Values 100, 100, 90ResultBehaviourUse it for

            
              
ROW_NUMBER()1, 2, 3Always unique. Ties broken arbitrarily unless you add a tie-breakDeduplication; “exactly one row per group”; pagination

              
RANK()1, 1, 3Ties share, then a gapCompetition ranking, where “joint first, no second” is correct

              
DENSE_RANK()1, 1, 2Ties share, no gap“Nth distinct value” — the second-highest-salary problem

            
          

        


        
The decision rule, stated in one line: if the question says “the Nth” and means a distinct value, use DENSE_RANK. If it means a position in a list, use RANK. If you need exactly one row and do not care which, use ROW_NUMBER — and add a tie-break so “which” is at least reproducible.

Read rows 1–4. Asha and Jaya both earn 210000: rn gives them 1 and 2 (an arbitrary split), rnk gives both 1 then jumps Hema to 3, drnk gives both 1 then Hema 2. So “who is second” has three different answers depending on which function you pick, and the question's wording is what decides — not your preference.

        


        

          
Likely interview questions

          

            
Very commonDifference between ROW_NUMBER, RANK and DENSE_RANK?
              
Give the concrete example rather than the prose, because it is unambiguous. On values 100, 100, 90: ROW_NUMBER gives 1, 2, 3; RANK gives 1, 1, 3; DENSE_RANK gives 1, 1, 2.
So: ROW_NUMBER is always unique and therefore breaks ties arbitrarily. RANK lets ties share a rank and then skips, so the numbers reflect how many rows preceded. DENSE_RANK lets ties share and does not skip, so the numbers count distinct values.
Then say when each is right, which is what the follow-up is. Deduplicating to one row per key needs ROW_NUMBER. “All employees tied for top salary” needs RANK. “The second-highest distinct salary” needs DENSE_RANK. And with ROW_NUMBER, always add a tie-break column to the ORDER BY or the result is non-deterministic between runs (§4.10).

            

            
GotchaWhich one do you use for “top 3 per group”?
              
It depends on what should happen at the boundary, and the honest answer is to ask.
ROW_NUMBER() <= 3 returns exactly three rows per group, cutting arbitrarily through a tie at third place. RANK() <= 3 returns all rows tied at third, so you may get four or more. DENSE_RANK() <= 3 returns everyone in the top three distinct values, which can be more rows still.
On the demo table, “top 2 per department” gives 7 rows with ROW_NUMBER and 9 with RANK or DENSE_RANK — because engineering and marketing each have a tie. That is a two-row difference on a twelve-row table, and on real data it is the difference between a correct and an incorrect answer.
What to say in the interview: “if there's a tie at the cutoff, do you want exactly N rows or all the tied ones?” Then implement what they say. Guessing is the only wrong move.

            

          

        

      


      

        
4.4 Nth highest salary, four ways ⭐⭐

        
Explicitly named as an asked question in both of the interview-prep documents that motivated this subject. It is asked so often that the interesting part is no longer the answer but the ties.


        
The demo table has two people on the top salary, which makes three of the four approaches disagree. Lead with DENSE_RANK and you have handled the follow-up before it arrives.

Expected: method 1 returns 210000 — the same as the maximum — while 2, 3 and 4 all return 156000. Then the per-department version: 145000, 98000, 156000. Method 3 is elegant for N=2 and does not generalise; method 4 changes r = 2 to r = N and works per group. That is why it is the one to lead with.

        


        

          
Likely interview questions

          

            
Very commonFind the second highest salary.
              
Ask the tie question first, because it determines the answer: if two people share the top salary, is the “second highest” the next distinct value, or the second person? Almost always the former.
Then: SELECT DISTINCT salary FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) r FROM employees) t WHERE r = 2. DENSE_RANK because it counts distinct values without gaps, so r = N is literally “the Nth distinct salary”.
Name the alternatives and their limits. SELECT MAX(salary) WHERE salary < (SELECT MAX(salary)) is neat, needs no window functions, and does not generalise past N=2. SELECT DISTINCT salary ... LIMIT 1 OFFSET 1 works and is the answer if windows are banned. LIMIT 1 OFFSET 1 without DISTINCT is wrong whenever the top salary is shared — it returns the maximum again.
Edge case to volunteer: if there is no second distinct salary the query returns no rows, and if the caller needs a single row containing NULL instead, wrap it in a scalar subquery. That is the kind of detail that turns a correct answer into a complete one.

            

            
Very commonNow the second highest per department.
              
Add PARTITION BY dept_id to the window and keep r = 2. That is the whole change, and it is the reason to prefer the DENSE_RANK formulation over the clever MAX-below-MAX trick: the trick would need a correlated subquery per department and becomes unreadable.
SELECT dept_id, salary FROM (SELECT DISTINCT dept_id, salary, DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) r FROM employees) WHERE r = 2
Two details. The DISTINCT inside matters when several employees share that second salary and you want the value once — drop it if you want the people rather than the number. And departments with fewer than two distinct salaries simply do not appear; if the report needs a row per department regardless, LEFT JOIN this back onto departments.
Expect the follow-up “now the top 3”, which is r <= 3, and then the tie discussion from §4.3 all over again.

            

          

        

      


      

        
4.5 Top-N per group ⭐⭐

        
The workhorse. “Top 3 products per region”, “most recent order per customer”, “highest-scoring attempt per user” — all the same query.


        
The pattern: number the rows within each group, wrap the query, filter on the number. The wrap is not optional — a window function cannot be filtered in WHERE (§4.9).


        
The N=1 special case is the most common of all: “the latest row per key”. ROW_NUMBER() OVER (PARTITION BY key ORDER BY ts DESC) = 1. Learn that one shape and you have answered a hundred interview questions and about the same number of real tickets.

The detail query shows why: engineering has three rows in its “top 2” (Asha, then Bhavin and Chandra tied) and so does marketing (Eshan, then Farida and Gagan tied). Note the ORDER BY order_date DESC, id DESC in the last query — the id is the tie-break that makes “most recent” deterministic when a customer ordered twice on one day.

        


        

          
Likely interview questions

          

            
Very commonGet the top 3 products by revenue in each region.
              
Aggregate to the grain first, then rank, then filter — three steps, and stating them in that order is half the answer.
WITH agg AS (SELECT region, product, SUM(revenue) rev FROM sales GROUP BY region, product), ranked AS (SELECT *, DENSE_RANK() OVER (PARTITION BY region ORDER BY rev DESC) r FROM agg) SELECT * FROM ranked WHERE r <= 3
The mistake to avoid: ranking before aggregating. If a product has several sales rows, ranking the raw rows ranks individual transactions, not products. Get the grain right first.
Then the tie question — ROW_NUMBER for exactly three, RANK/DENSE_RANK to include ties — and the dialect shortcut: on Snowflake, BigQuery or DuckDB this is one statement with QUALIFY r <= 3 and no wrapping subquery.

            

            
Very commonGet the most recent record per user.
              
ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts DESC) = 1 in a wrapped subquery. This is the single most useful window pattern in existence.
Add a tie-break. If two rows share the maximum timestamp — very common with date-granularity columns or bulk loads — ROW_NUMBER picks one arbitrarily and your “latest” can change between runs. ORDER BY ts DESC, id DESC makes it deterministic.
Alternatives worth naming, because interviewers sometimes ban window functions. A correlated subquery: WHERE ts = (SELECT MAX(ts) FROM t2 WHERE t2.user_id = t.user_id) — correct, but returns all tied rows. A LATERAL/CROSS APPLY with ORDER BY ts DESC LIMIT 1, which is often the fastest plan in PostgreSQL when the table is indexed on (user_id, ts). And DISTINCT ON (user_id), which is PostgreSQL-only and delightfully concise.

            

          

        

      


      

        
4.6 Deduplication with ROW_NUMBER ⭐

        
The standard way to collapse duplicates while choosing which copy survives — which is the part DISTINCT cannot do.


        
DISTINCT keeps unique whole rows. It cannot express “one row per email, keeping the earliest”, because the rows differ in the columns you do not want to key on. ROW_NUMBER can: partition by the identity you care about, order by your tie-break rule, keep number 1.


        
The tie-break rule is the requirement. “Keep the earliest”, “keep the most recently updated”, “keep the one with the most complete record” — these are different ORDER BY clauses and different answers, and the interviewer wants to hear you ask which.

Expected: 7 rows, and every dedup strategy gives a different count — DISTINCT * gives 6 (only the exact Ben duplicate collapses), DISTINCT email gives 5, the normalised version gives 4, and the ROW_NUMBER dedup gives 4 rows with all their columns. That last distinction is the point: the others give you a count or a key list; only ROW_NUMBER gives you back usable rows.

        


        

          
Likely interview questions

          

            
Very commonRemove duplicate rows, keeping the most recent one per key.
              
ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC, id DESC) and keep rn = 1. The PARTITION BY defines what “duplicate” means and the ORDER BY defines which copy wins — both are requirements, not implementation details, so state them back to the interviewer before coding.
Why not DISTINCT: it deduplicates whole rows only, so rows that differ in a timestamp or a surrogate id are not duplicates to it. Why not GROUP BY key: you would have to aggregate every other column, and MAX() on each one can mix values from different source rows — a genuinely dangerous answer that looks reasonable.
If they want an actual DELETE rather than a SELECT, that is §10.2 — and worth flagging that a DELETE with a window function needs a CTE or a subquery on the primary key, since you cannot use a window in a DELETE ... WHERE directly.

            

            
GotchaWhat counts as a duplicate?
              
A definition, not a fact about the data — and that is the whole answer to this question. The demo table contains 'ada@x.com', 'ADA@x.com' and ' ada@x.com '. Are those three customers, or one?
Under exact matching: three. After TRIM: still three. After LOWER(TRIM()): one. So the same table has three defensible customer counts, and picking one silently is how two teams end up reporting different numbers from the same source.
What to say: “before deduplicating I'd agree the matching key — usually case-folded and trimmed, and for emails possibly with the domain normalised. Then I'd count how many rows collapse under each rule and show that to the stakeholder, because the difference is itself information about upstream data quality.” §10.1 and §10.3 go further, including collation surprises.

            

          

        

      


      

        
4.7 NTILE and buckets

        
Split ordered rows into N groups of as-equal-as-possible size. Useful for deciles and quartiles, and it has one property that surprises people.


        
NTILE(4) assigns 1–4 by position. If the row count is not divisible by N, the earlier buckets get the extra rows — 12 rows into 4 buckets is 3/3/3/3, but 10 rows is 3/3/2/2.

        
The surprise: NTILE splits on position, not on value, so tied values can land in different buckets. On the demo table Farida and Gagan both earn 98000 and end up in quartiles 3 and 4. If the buckets must respect value boundaries, NTILE is the wrong tool — use CUME_DIST or explicit range boundaries.


        

          
Run itNTILE splitting a tie across two bucketsidle

Look at quartiles 3 and 4: quartile 3's minimum and quartile 4's maximum are both 98000. Farida and Gagan earn the same salary and were placed in different quartiles purely by row position. If you were assigning a discount tier or a bonus band on that basis, two identically-paid employees would get different treatment — which is why value-based bucketing needs CUME_DIST or explicit thresholds, not NTILE.

        


        

          
Likely interview questions

          

            
GotchaSplit customers into deciles by spend. What can go wrong?
              
NTILE(10) OVER (ORDER BY spend DESC) is the query, and two things can go wrong with it.
Ties split across buckets. NTILE divides by row position, so two customers with identical spend can land in different deciles. If the decile drives a business action, that is unfair and hard to defend. Value-based alternatives: CUME_DIST and a CASE on the resulting fraction, or explicit spend thresholds — both keep equal values together.
Uneven bucket sizes. With a row count not divisible by 10, the earlier buckets take the extra rows. Usually harmless, occasionally confusing when someone expects exactly 10%.
And the modelling point worth adding: spend is heavily right-skewed, so equal-sized deciles produce wildly unequal value ranges — decile 1 might span £5,000 and decile 10 span £20. If the goal is value bands rather than population bands, NTILE is answering the wrong question entirely.

            

          

        

      


      

        
4.8 PERCENT_RANK and CUME_DIST

        
Two relative-position functions that differ by exactly one detail, which is of course what gets asked.


        

          
PERCENT_RANK()
(rank − 1) / (total − 1). Ranges 0 to 1 inclusive — the first row is always exactly 0. “What fraction of rows are strictly below me?”

          
CUME_DIST()
rows ≤ current / total. Ranges >0 to 1 — never 0, and the last row is always 1. “What fraction of rows are at or below me?”

        


        
Both handle ties by value, unlike NTILE: tied rows get identical values. That makes CUME_DIST the right basis for value-respecting bucketing — CEIL(CUME_DIST() OVER (ORDER BY x) * 10) gives you deciles in which equal values never separate.


        

          
Run itPERCENT_RANK vs CUME_DIST, and tie-safe quartilesidle

          
          

            
            
            
            ⌘/Ctrl + Enter
          

          

          
The two quartile columns are the payoff. ntile_quartile splits Farida and Gagan (both 98000) into 3 and 4; cume_quartile keeps them together, because CUME_DIST is computed from the value, not the position. Also note pct_rank starts at exactly 0 while cume_dist never does — that is the whole difference between the two definitions.

        


        

          
Likely interview questions

          

            
ConceptualPERCENT_RANK vs CUME_DIST vs NTILE?
              
PERCENT_RANK = (rank − 1)/(n − 1), so it starts at 0 and answers “what proportion is strictly below me”. CUME_DIST = (rows ≤ me)/n, so it ends at 1 and answers “what proportion is at or below me”. NTILE(k) assigns a bucket number 1..k by position.
The distinction that matters in practice: PERCENT_RANK and CUME_DIST respect ties — equal values get equal results — while NTILE does not, because it counts rows. So for any bucketing that drives a decision affecting people or money, build it from CUME_DIST rather than NTILE.
Related and worth naming: PERCENTILE_CONT and PERCENTILE_DISC go the other way — you give a fraction and get the value at it, which is how you compute a median (§9.1). Those are ordered-set aggregates, not window functions, and neither exists in SQLite or MySQL.

            

          

        

      


      

        
4.9 Window functions in WHERE: why it fails ⭐

        
A frequently-hit error with a one-sentence explanation, straight out of the execution order in §1.1.


        
Windows are computed at step 5, after WHERE (step 2), GROUP BY (3) and HAVING (4). So at the moment WHERE is evaluated the window result does not exist yet. It is not a restriction the designers imposed; it is a consequence of when the calculation happens.


        

          

            
Want toDo this

            
              
Filter on a window resultWrap in a subquery/CTE and filter outside — or QUALIFY where available

              
Filter rows before the window sees themOrdinary WHERE — and note this changes the window's input, so ranks renumber

              
Rank only some rows but keep allRANK() OVER (ORDER BY CASE WHEN cond THEN x END), or FILTER on the aggregate

            
          

        


        
The subtlety worth raising: filtering in WHERE and filtering after the window give different answers, because WHERE removes rows from the window's input. Rank employees and then keep engineering, versus keep engineering and then rank — the first gives company-wide ranks, the second gives within-engineering ranks. Both are legitimate; the question decides which.

Compare the two rank columns for the same five people. Filtering first gives Asha rank 1, Bhavin and Chandra joint 2. Filtering after gives Asha rank 1 (she is joint-top company-wide with Jaya), Bhavin and Chandra joint 4. Same rows, different numbers, both correct — and if you do not say which you computed, the reader cannot tell.

        


        

          
Likely interview questions

          

            
Very commonWhy can't you use a window function in WHERE?
              
Because of evaluation order: WHERE runs at step 2 and window functions are computed at step 5, after GROUP BY and HAVING. The value simply does not exist when WHERE is evaluated. Same reason it cannot go in GROUP BY or HAVING.
The fix is to introduce another query level: a subquery or CTE that computes the window, with the filter in the outer WHERE. Snowflake, BigQuery, Teradata, Databricks and DuckDB give you QUALIFY, which is exactly “HAVING for windows” and saves the wrap.
Then the point that shows real understanding: the two are not interchangeable. A filter in WHERE removes rows before the window is computed, so ranks and running totals are calculated over the filtered set. A filter outside computes over everything and then discards. “Top 3 engineers by company-wide rank” and “top 3 engineers within engineering” are different questions and the placement of one predicate is what distinguishes them.

            

          

        

      


      

        
4.10 Deterministic tie-breaks ⭐

        
The habit that stops your query returning different answers on different days. Cheap to add, and volunteering it is a real seniority signal.


        
If a window's ORDER BY does not impose a total order, then ROW_NUMBER, FIRST_VALUE, LAG and “the latest row per key” are all non-deterministic among the tied rows. The engine may return one row today and another after an index is added, a vacuum runs, or the plan flips to a parallel scan. Nothing errors and nothing warns.


        

          
          The rule
          
Append a unique column to every ORDER BY whose result you depend on — in windows, in LIMIT queries, and in anything a test asserts against. ORDER BY updated_at DESC, id DESC costs nothing and converts “usually right” into “always the same”. If there is no unique column, that is itself worth flagging: it means the table has no reliable identity.

The first query is not guaranteed to return that row; it just does today, on this engine, with this plan. The second query is guaranteed. On a warehouse with parallel scans the first one genuinely varies between runs, which is how a reconciliation test starts failing intermittently with no code change.

        


        

          
Likely interview questions

          

            
GotchaYour “latest record per user” query returns different rows on different runs. Why?
              
Because several rows share the maximum timestamp and the ORDER BY does not say which of them wins. ROW_NUMBER must assign 1 to exactly one of them, so it picks arbitrarily — and “arbitrarily” can change with the execution plan, parallelism, index availability, or the physical order after a rewrite.
This is extremely common with date-granularity columns (two updates the same day) and with bulk loads that stamp every row with the same ingestion timestamp.
The fix is a total order: ORDER BY updated_at DESC, id DESC. If you genuinely want all tied rows, use RANK instead and handle the multiplicity downstream. If ties should be impossible, the real fix is upstream — a uniqueness constraint — and saying that is a better answer than either query.
Related habit worth mentioning: the same non-determinism applies to LIMIT without a total order, and it is why intermittently-failing data tests are so often an ORDER BY problem rather than a data problem.
