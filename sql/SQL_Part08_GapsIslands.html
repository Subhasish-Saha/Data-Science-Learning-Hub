One trick, ten questions The row_number difference that turns a run into a group, consecutive days, the three-day streak, longest and current streaks, gap tolerance, merging overlapping intervals, unchanged-value periods, and peak concurrency.

This is the family that separates candidates, and it deserves its own level because every member is the same two lines of insight. If a sequence is consecutive, then value minus row-number is constant, so that difference is a group key. If instead you have a gap rule, flag every row whose predecessor is too far back and take a running sum of the flags — the running sum is the island id. Once those two moves are reflexive, “users active three days running”, “longest login streak”, “sessionise these events”, “merge these subscriptions” and “how long did the price hold” are all the same question. Recognising that out loud is worth more than any single solution.

8.1 The pattern, and the one trick behind all of it ⭐⭐

Ten interview questions, two techniques. Learn both and this entire level collapses into a single idea.

An island is a contiguous run of rows; a gap is the break between runs. The problem is always the same: rows do not carry a group id for their run, so you must manufacture one.

Technique 1 — the row_number difference
For a sequence with a fixed step (consecutive days, consecutive integers), value − ROW_NUMBER() is constant within a run and changes at every break. That difference is the group key.

Use when: the step is known and regular.
Technique 2 — flag then cumsum
LAG to find the gap, flag rows where it exceeds a threshold, then a running SUM of the flags. The running sum is the island id.

Use when: the rule is a tolerance, a timeout, or a value change. More general.

Why technique 1 works: if dates increase by exactly one per row, then date and row-number increase in lockstep, so their difference is fixed. Skip a day and the date jumps while the row number does not, so the difference shifts permanently — giving every subsequent run a new constant.

Why technique 2 is the one to learn: it handles anything. Sessionisation with a 30-minute timeout (§7.7), streaks allowing one missed day, merging overlapping intervals, detecting when a value stopped changing — all are “flag the boundary, cumsum the flags”. If you internalise one idiom from this subject, make it that one.

Likely interview questions

          

            
Very commonExplain the gaps-and-islands pattern.
              
An island is a contiguous run; a gap is the break between runs. The whole difficulty is that rows do not know which run they belong to, so you construct a group key and then aggregate on it normally.
Technique 1, for regularly-stepped sequences: value − ROW_NUMBER() OVER (PARTITION BY entity ORDER BY value) is constant within a run, because both sides increment together, and shifts at each break. Group by that difference.
Technique 2, general: LAG the previous value, flag rows where the gap exceeds the allowed threshold, then take a running SUM of the flags — the cumulative sum is the island number.
Say why technique 2 is worth preferring: it takes an arbitrary boundary rule, so the same three lines handle a 30-minute session timeout, a “one missed day allowed” streak, overlapping-interval merging, and run-length encoding of a changing value. Technique 1 is elegant but only works when the step is fixed and the values are unique.
The prerequisite nobody mentions: deduplicate first. Two rows for the same date break technique 1 completely, because the row number advances while the date does not.

            

            
GotchaCan you nest one window function inside another?
              
No. SUM(LAG(x) OVER w) OVER w is rejected — engines report something like “window function calls cannot be nested” or “misuse of window function”. The reason is the evaluation model: all window functions in a SELECT are computed in the same phase from the same input rows, so one cannot consume another's output.
This bites precisely here, because the flag-then-cumsum idiom looks like it needs nesting: you want a running sum of a LAG-derived flag. The fix is always the same — compute the inner window in its own CTE or subquery, then apply the outer window to that result. Two steps, and it also reads better.
One thing that is allowed and often confused with it: an aggregate inside a window function's argument, such as SUM(SUM(x)) OVER (). That works because the inner aggregate belongs to the GROUP BY phase, which completes before windows are evaluated (§3.6). Aggregate-inside-window: fine. Window-inside-window: never.

Note the SELECT DISTINCT: user 5 logged in twice on 1 March, and without deduplicating, their row numbers advance twice for one date and the island key breaks.

        


        

          
Likely interview questions

          

            
GotchaWhy must you deduplicate before computing islands?
              
Because technique 1 relies on the date and the row number advancing in lockstep. A duplicate date advances the row number without advancing the date, so the difference changes and the run is split at the duplicate — a user with two logins on Tuesday appears to have two separate streaks.
The fix is SELECT DISTINCT user_id, login_date first, or an equivalent GROUP BY. And it is not hypothetical: any event table where a user can act twice a day has this, which is most of them.
Technique 2 is affected too, in a different way: a duplicate gives a gap of zero, which does not exceed the threshold, so the row joins the current island rather than splitting it — arguably the more forgiving failure. But it still inflates any per-island COUNT(*), so “streak length” comes out wrong. Deduplicate either way.
This is a good detail to volunteer unprompted, because it shows you have run the query on real data rather than on a textbook example.

            

          

        

      


      

        
8.3 Three or more consecutive days ⭐⭐

        
Explicitly named as “the classic hard one” in one of the interview-prep documents behind this subject. It is §8.2 plus a HAVING.


        

          
Run itusers active 3+ consecutive days, and the self-join alternativeidle

Expected: user 3 with a 5-day run, users 1 and 6 with 3-day runs. The self-join returns the same three user ids — but notice it hard-codes the number three into the query structure. Changing the requirement to “5 in a row” means editing the FROM clause; with the islands version you change one digit in the HAVING. That is the argument to make.

        


        

          
Likely interview questions

          

            
Very commonFind users who logged in on 3 or more consecutive days.
              
Islands, then HAVING COUNT(*) >= 3. Deduplicate the user-date pairs, compute julianday(d) − ROW_NUMBER() as the island key, group by user and island, filter on the run length.
Mention the self-join alternative and then reject it: joining the table to itself on +1 day and +2 days is correct for exactly three, but the query structure encodes the number, so “five in a row” needs five joins. It also does not tell you the run length or the boundaries.
Three details to volunteer. Deduplicate first, or a double login splits the run. Decide whether weekends count — for “3 consecutive business days” you row-number over a business-day calendar rather than over raw dates, which is a nice use of the date dimension from §6.3. And report the run itself, not just the user id: the length and the start and end dates are almost always what the question is really after.
The variants this generalises to, worth naming: longest streak per user (§8.4), current streak (§8.5), and “3 consecutive days allowing one miss” (§8.6).

            

          

        

      


      

        
8.4 The longest streak per user ⭐⭐

        
Two levels of aggregation on top of the islands: count per island, then take the maximum per user. A clean §3.5 callback.

Expected: user 3 with 5 days, users 1 and 6 with 3, user 5 with 2, users 2 and 4 with 1. Note the ROW_NUMBER rather than a plain MAX(len): taking the max gives you the number, but the rk = 1 pattern also gives you which streak it was — and the tie-break on s makes it deterministic when a user has two streaks of equal length (§4.10).

        


        

          
Likely interview questions

          

            
Very commonFind each user's longest login streak.
              
Three stages: island key, count per island, then per-user maximum. If you only need the length, MAX(len) grouped by user is enough. If you need the dates of that streak — which is usually the more useful answer — rank the runs per user with ROW_NUMBER() OVER (PARTITION BY user ORDER BY len DESC) and keep rank 1.
That is the §1.4 lesson again: MAX gives you a value, ranking gives you the row. Reaching for the ranking version unprompted signals you have internalised it.
Add the tie-break — two streaks of equal length need a deterministic winner — and mention the natural follow-up, current streak, which is a different question: it requires the run to end at today (or at the data's last date), so a user with a great streak last year has a current streak of zero (§8.5).

            

          

        

      


      

        
8.5 Current streak vs longest streak ⭐

        
A different question with a nearly identical query, and confusing the two is the mistake.


        
A current streak must be anchored to the present: the run has to include today, or yesterday if today's data has not landed. A user with a magnificent streak that ended in January has a current streak of zero. Reporting their longest streak as their current one is how gamification features lose trust.


        

          
Run itcurrent streak as of a reference date, vs longest everidle

          
          

            
            
            
            ⌘/Ctrl + Enter
          

          

          
Compare the two columns. User 3 has the longest streak ever at 5 days but a current streak of 0 — they stopped on 5 March. Users 1 and 6 both have current streaks of 3, because their runs reach 8 March. Same underlying islands, completely different leaderboard, and only one of them is the answer to “who is on a streak right now?”

        


        

          
Likely interview questions

          

            
CodingCompute each user's current streak.
              
Build the islands, then keep only the run whose end date reaches the reference date. Everything else is a past streak and the current streak is zero, so use a COALESCE(..., 0) rather than letting the user disappear from the result.
The judgement call to raise: what is the anchor? If today's events are still loading, requiring the run to include today resets everyone's streak every morning. Most products allow “today or yesterday”, which is a one-day grace period, and that choice belongs in the requirements not in the code.
Two further points. Pass the reference date in as a parameter rather than calling current_date inside the query, so the result is reproducible and testable (§10.10). And decide the time zone — a streak is a local-day concept, so a UTC-truncated day boundary will break streaks for users in some regions (§6.7).

            

          

        

      


      

        
8.6 Islands with a gap tolerance ⭐

        
“A streak survives one missed day.” Technique 1 cannot express this at all; technique 2 handles it by changing one number.

Look at user 2, who logged in on the 1st, 3rd and 5th of March. Strictly, that is three separate one-day runs. With a one-day grace period it becomes one five-day-spanning island. Whether that is the right answer is a product decision — but only technique 2 lets you express either, which is why it is the one worth learning.

        


        

          
Likely interview questions

          

            
CodingA streak should survive one missed day. Adapt your query.
              
Switch to the flag-and-cumsum technique and raise the gap threshold: a new island starts when the gap exceeds 2 days rather than 1. That is the only change.
The value − ROW_NUMBER() trick cannot express this, because it depends on a fixed step of exactly one. Being able to say why the elegant technique fails here — and switching cleanly — is a better answer than either query alone.
Two clarifications worth asking for. Does the missed day count toward the streak length? “Seven-day streak with one miss” could mean seven active days or a seven-day span, and those differ. Report both COUNT(*) (active days) and the date span, and let the stakeholder pick. How many misses are allowed in total? A tolerance per gap is easy; “at most two misses in the whole streak” is a genuinely harder problem that needs a running count of misses within the island, and it is fair to say so.

            

          

        

      


      

        
8.7 Merging overlapping intervals ⭐⭐

        
The same pattern applied to ranges instead of points. “Collapse these overlapping subscriptions into continuous periods.”


        
The algorithm: sort by start; a new block begins when the current start is later than the running maximum of all previous ends. Then cumsum the flags and take min-start / max-end per block.

        
The critical detail is the running maximum. Comparing against the previous row's end is wrong: a fully nested interval — 1 Jan to 1 Mar followed by 10 Jan to 20 Jan — would look like a new block because the second starts after nothing, when in fact it is entirely contained. MAX(end) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) is the fix, and it is exactly the max() requirement from the interval-merging discussion in §2.10.

Expected: user 1's basic (Jan 1–31) and pro (Jan 20 – Mar 15) overlap and merge into Jan 1 – Mar 15, while their April–May subscription stays separate. User 2's two touching periods merge into Feb 1–28. User 3's nested pair merges into Jan 5 – Jun 30 — and that is the case that prev_max_end exists to handle, because the nested basic subscription starts after nothing that precedes it in a naive comparison.

        


        

          
Likely interview questions

          

            
Very commonMerge overlapping date ranges into continuous periods.
              
Sort by start date. Flag a new block where the current start exceeds the running maximum end of all earlier rows. Cumulative-sum the flags to get a block id, then aggregate MIN(start) and MAX(end) per block.
The running maximum is the whole answer and the reason this question is asked. Comparing to the previous row's end fails on a nested interval: if row 1 spans January to March and row 2 spans only mid-January, row 2's start is after row 1's start but the interval is fully contained — and a previous-row comparison would open a spurious new block. MAX(end) OVER (... UNBOUNDED PRECEDING AND 1 PRECEDING) handles it.
Two clarifications to ask. Do touching intervals merge? If one ends on the 10th and the next starts on the 10th, that is > versus >= and it is a requirement, not a preference — and it is why half-open intervals (§2.9) make this cleaner. Can end be NULL for an open period? Then COALESCE it to a far-future sentinel or the comparison silently fails.
The variants this generalises to: total covered days per user (sum the merged block lengths, which is the only correct way — summing the raw rows double-counts the overlap), and finding the gaps between blocks, which is LEAD on the merged result.

            

          

        

      


      

        
8.8 Periods where a value held ⭐

        
Run-length encoding: collapse consecutive rows with the same value into one row per unchanged stretch. Same idiom, different boundary condition.


        
The flag is now a value change rather than a time gap: CASE WHEN value <> LAG(value) THEN 1 ELSE 0 END, then cumsum. This answers “how long did the price stay at £9.99”, “which periods was this server down”, and “when did this customer's plan actually change”.

        
The trap: value <> LAG(value) is NULL when either side is NULL, which flags nothing — so runs containing nulls silently merge. Use IS NOT (SQLite), IS DISTINCT FROM (PostgreSQL), or COALESCE both sides to a sentinel.

Likely interview questions

          

            
CodingFind the periods during which a price stayed unchanged.
              
Flag rows where the value differs from the previous row, cumsum the flags to get a run id, then MIN(date), MAX(date) and COUNT(*) per run. It is the same three lines as sessionisation with a different boundary test.
Two traps. NULL comparisons: price <> LAG(price) evaluates to NULL if either operand is NULL, so a transition into or out of a null run is not flagged and the runs merge silently. Use IS DISTINCT FROM in PostgreSQL, IS NOT in SQLite, or COALESCE both sides. Floating-point equality: comparing prices stored as float can register spurious changes, so store money as numeric/decimal or compare rounded values (§10.6).
And clarify what “unchanged” means when there are gaps in the data. If Tuesday is missing entirely, did the price hold through Tuesday or is that a separate run? Filling the series against a date spine first (§6.4) makes the answer explicit rather than accidental.

            

          

        

      


      

        
8.9 Gaps: what is missing

        
The other half of the pattern. Sometimes the interesting rows are the ones that do not exist.


        
Two approaches. If you have a complete reference sequence — a date spine, or the integers from 1 to n — then the gaps are an anti-join: what is in the spine and not in the data (§2.4). If you do not, use LEAD to find where consecutive rows jump: the gap runs from value + 1 to LEAD(value) − 1.

        
The LEAD version has one advantage worth knowing: it reports the gap ranges compactly rather than one row per missing item, which matters when a gap is a million integers wide.

The two forms answer slightly different questions. The LEAD version finds gaps inside the observed range and cannot know about missing days before the first login or after the last — it has no notion of the intended range. The spine version does, because you told it the boundaries. That is the general trade: derived-from-data is convenient, spine-driven is complete.

        


        

          
Likely interview questions

          

            
CodingFind missing invoice numbers in a sequence.
              
Two ways, and which you choose depends on whether you know the intended range.
LEAD gap detection: order by the number, and wherever LEAD(n) - n > 1 there is a gap from n + 1 to LEAD(n) - 1. Reports gaps as compact ranges, needs no reference table, but cannot detect missing numbers before the minimum or after the maximum.
Anti-join against a generated sequence: generate_series(1, max) or a recursive CTE, then NOT EXISTS. Complete with respect to a range you specify, and gives one row per missing value — which is either what you want or a million rows.
The detail worth raising: for an audit, the range boundaries are part of the question. “Missing invoices” usually means missing within an expected span, and the expected span comes from the business, not from MIN and MAX of a table that might itself be truncated.

            

          

        

      


      

        
8.10 Peak concurrency ⭐

        
“What was the maximum number of simultaneous sessions?” A sweep-line algorithm, expressed in SQL, and a genuinely satisfying use of UNION ALL.


        
The technique: turn each interval into two events — +1 at the start, −1 at the end — union them into one stream, sort by time, and take a running SUM. That running total is the concurrency at each moment, and its maximum is the peak. Linear, and it needs no self-join.

        
The ordering detail: at a moment where one interval ends and another begins, whether they count as concurrent depends on the tie-break. Ordering delta DESC processes starts before ends and counts them as overlapping; delta ASC does the opposite. Half-open intervals make the question disappear.


        

          
Run itthe +1/-1 sweep, and the peakidle

Read the concurrent column as a running headcount. It climbs on each +1 and falls on each −1, and the peak is the busiest instant. Note this is a sweep line — the same algorithm used for meeting-room allocation, hotel occupancy and “maximum servers in use”. Recognising a concurrency question as a sweep, rather than reaching for a self-join over every pair of intervals, is what makes it O(n log n) instead of O(n²).

        


        

          
Likely interview questions

          

            
CodingWhat was the maximum number of concurrent sessions?
              
Sweep line. Emit +1 at every start and −1 at every end, UNION ALL them into a single ordered event stream, and take a running SUM. The running total is the live concurrency; MAX of it is the peak. O(n log n) for the sort, one pass after that.
Reject the alternative out loud: self-joining every interval against every other to count overlaps is O(n²) and will not run on a real session table.
Two details. Tie ordering — when one session ends exactly as another starts, ordering delta DESC counts them as concurrent and delta ASC does not; with half-open intervals the ambiguity disappears, which is another argument for the convention. Reporting the interval — if they want when the peak occurred, keep the event timestamp alongside the running sum and filter to the maximum, remembering the peak may be sustained across several events.
This is the same algorithm as the meeting-rooms problem, and saying so is a nice bit of pattern recognition.
