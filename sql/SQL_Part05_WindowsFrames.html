Part 5 of 12 · Window Functions II: Frames and Offsets

The half of window functions nobody reads about ROWS versus RANGE versus GROUPS, the default frame and the duplicate-date bug it causes, running totals, moving averages, LAG and LEAD, period-over-period growth, the LAST_VALUE frame trap, and leakage-free rolling metrics.

Most people learn OVER (PARTITION BY ... ORDER BY ...) and stop, never learning the third component. That is a problem, because the frame is where the silent bugs live. Adding ORDER BY to an aggregate window changes the default frame from the whole partition to everything up to the current row — and with RANGE, “up to the current row” includes every tied row, so a running total over a date with two orders jumps by both. LAST_VALUE without an explicit frame returns the current row, which looks like a broken function and is actually the spec. Both are demonstrated here.

5.1 The frame clause ⭐⭐

Which rows the function can actually see. Three modes, and choosing the wrong one is not an error — it is a different number.

ModeCountsOn a tieUse for
ROWSPhysical rowsEach tied row sees a different frameAlmost always what you want. Moving averages, running totals
RANGEValues of the ORDER BY keyAll tied rows share one frame“Everything up to this date”; time-based windows like INTERVAL '7 days'
GROUPSPeer groups of tiesWhole tie-groups in or outRare. “The previous three distinct dates”

The boundary vocabulary: UNBOUNDED PRECEDING, n PRECEDING, CURRENT ROW, n FOLLOWING, UNBOUNDED FOLLOWING. So ROWS BETWEEN 6 PRECEDING AND CURRENT ROW is a 7-row trailing window, and ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW is a running total.

Ranking functions ignore the frame entirely — ROW_NUMBER, RANK, DENSE_RANK and NTILE are defined over the whole partition regardless of what you write. Frames only affect aggregates and the value functions (FIRST_VALUE, LAST_VALUE, NTH_VALUE).

Likely interview questions
ConceptualWhat is a window frame, and what is the difference between ROWS and RANGE?

The frame is the subset of the partition visible to the function for the current row. ROWS counts physical rows — “the two rows before this one”. RANGE counts values of the ordering key — “all rows whose date is at or before this date”.

They are identical whenever the ORDER BY key is unique. They diverge on ties, and that divergence is the bug in §5.2: with RANGE, every row sharing a date sees the same frame, so a running total jumps by the whole day's worth at once and no row shows a partial value.

Two things worth adding. The default is RANGE, not ROWS — so if you write SUM(x) OVER (ORDER BY d) you have silently chosen the tie-sharing behaviour. And RANGE is the mode that supports value offsets, which is how you express a genuine time window: RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW in PostgreSQL means seven calendar days regardless of how many rows fall in them — something ROWS cannot express.

5.2 The default frame, and the tie bug it causes ⭐⭐

Two defaults, and knowing which applies when is the difference between a running total and a group total.

No ORDER BY in OVER
Frame is the entire partition. SUM(x) OVER (PARTITION BY g) is the group total, repeated on every row.
ORDER BY present
Frame becomes RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. That is what makes it a running total — and RANGE, not ROWS, which is the trap.

Because the implicit default is RANGE, a running total ordered by a non-unique key includes every tied row. On a daily sales table with two transactions on the same date, both rows show the same running total — the one after both are added. Neither row shows the intermediate figure, and if you were expecting a row-by-row ledger you get something else without any signal.

Likely interview questions

          

            
GotchaWhat is the default window frame?
              
It depends on whether OVER has an ORDER BY. Without one, the frame is the whole partition, so an aggregate returns the group total on every row. With one, the frame defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — which is what turns the same expression into a running total.
The consequence people get caught by: the default is RANGE, not ROWS. So a running total ordered by a non-unique key lumps all tied rows together. Two sales on the same date both show the post-both total; there is no row showing the value in between.
Practical rule: if you write ORDER BY inside OVER for an aggregate, write the frame explicitly too. ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW for a ledger, ROWS BETWEEN 6 PRECEDING AND CURRENT ROW for a 7-row trailing window. It costs eight words and removes an entire class of bug.
And note the asymmetry that makes this so easy to miss: ranking functions ignore the frame, so you can write ROW_NUMBER() OVER (ORDER BY d) for years and never encounter the issue until the day you write SUM.

            

          

        

      


      

        
5.3 Running totals ⭐

        
The canonical window-function exercise, and once §5.2 is understood there is almost nothing left to it.


        
SUM(amount) OVER (ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW). Add PARTITION BY customer_id and it restarts per customer, which is what “running total per customer” means.

        
The pre-window answer, worth knowing because interviewers sometimes ban windows: a self-join on b.date <= a.date with a SUM and a GROUP BY. It is O(n²) and it demonstrates exactly why window functions were added to the standard.

Likely interview questions

          

            
Very commonWrite a running total of revenue by date.
              
SUM(amount) OVER (ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW).
Three things to say while writing it, in this order. Write the frame explicitly, because the default is RANGE and will lump same-date rows together. Add PARTITION BY if the total should restart per customer, region or account. Add a tie-break to the ORDER BY so the sequence is deterministic when dates repeat.
If they want it per day rather than per transaction, aggregate first: GROUP BY order_date in a CTE, then the running SUM over the daily totals. That also side-steps the tie question entirely, since dates are then unique — which is a nice thing to point out.
And if they ask for it without window functions, the self-join with b.date <= a.date is the answer, plus the observation that it is quadratic and is precisely the problem windows were introduced to solve.

            

          

        

      


      

        
5.4 Moving averages ⭐

        
A trailing window instead of an unbounded one. The arithmetic is trivial; the two traps are about what the window is counting.


        
Trap one: rows are not days. ROWS BETWEEN 6 PRECEDING AND CURRENT ROW is “the last seven rows”. If a day has no data there is no row, so your “7-day average” silently reaches back nine or ten calendar days. The fix is either a date spine so every day has a row (§6.3–6.4), or a genuine time frame — RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW in PostgreSQL.

        
Trap two: the leading edge. The first rows have an incomplete window, so a “7-day average” on day 2 is really a 2-day average. Whether to show it, null it out, or start the series later is a reporting decision. Guard it with COUNT(*) OVER (same frame) = 7.

Likely interview questions

          

            
Very commonCompute a 7-day moving average of daily revenue.
              
AVG(daily_rev) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) over a table already aggregated to one row per day.
Then raise the two problems, because both are what the question is testing. Missing days: ROWS counts rows, so if the source has gaps your window spans more than seven calendar days. Fix with a date spine and a LEFT JOIN so every day exists with a zero, or use a RANGE frame with an interval where the dialect supports it. Incomplete leading window: the first six days average fewer than seven values; either accept it, or null them with a COUNT(*) OVER (...) = 7 guard.
A third point that lands well if there is time: aggregate to daily before the window. Running the average over raw transactions makes the window “the last 7 transactions”, which on a busy day is a few hours and on a quiet week is a month.

            

          

        

      


      

        
5.5 LAG and LEAD ⭐⭐

        
Reach backwards or forwards a fixed number of rows. The basis of every period-over-period calculation, every gap measurement, and the sessionisation logic in §7.7.


        
LAG(col, offset, default) — previous row's value; LEAD is the same forward. The third argument is the value to use when there is no such row, and supplying it is often the difference between a clean result and a NULL that poisons the arithmetic downstream. LAG(rev, 1, 0) makes the first period's growth computable rather than NULL — although whether zero is honest there is a judgement call.

Likely interview questions

          

            
Very commonFind the time between each user's consecutive events.
              
ts - LAG(ts) OVER (PARTITION BY user_id ORDER BY ts). That one expression is the foundation of sessionisation, streaks, churn timing and inter-purchase intervals.
Three details worth volunteering. The first row per user is NULL, correctly — there is no previous event — so decide whether to filter it, default it, or keep it. Deduplicate first if the source can contain exact-duplicate timestamps, or you get spurious zero gaps. And the units differ by dialect: PostgreSQL subtraction of timestamps gives an interval, MySQL needs TIMESTAMPDIFF, SQLite needs julianday arithmetic, BigQuery needs TIMESTAMP_DIFF. Saying that shows you have written this against more than one engine.
The natural follow-up is “now group events into sessions with a 30-minute timeout”, which is LAG plus a boundary flag plus a running SUM — §7.7, and the same shape as everything in §8.

            

            
CodingLAG vs a self-join — when does it matter?
              
Functionally you can express “previous row” either way, but the self-join needs you to define what previous means as a predicate, and that is where it goes wrong. ON b.date = a.date - 1 assumes consecutive dates with no gaps; ON b.date < a.date plus “take the max” is correct but is a correlated subquery per row.
LAG defines previous as “the preceding row in this ordering”, which is almost always the intent, and it is computed in one pass over a single sort.
Where the self-join still wins: when “previous” is defined by a value rather than a position — “the last reading at least an hour earlier” — which is a range join or an as-of join (§2.9), not an offset. Knowing which of the two shapes a question is asking for is the actual skill.

            

          

        

      


      

        
5.6 Month-over-month and year-over-year ⭐

        
Explicitly reported as an asked question. The LAG is easy; the two things that make it wrong are the missing month and the division.


        
The shape: aggregate to the period, then LAG one period back, then compute (current - prior) / prior. For year-over-year the offset is 12 rather than 1 — provided every month exists.


        

          
          LAG(x, 12) is not “a year ago”
          
LAG(rev, 12) means twelve rows back. If one month had no sales it has no row, so twelve rows back is thirteen months ago — and every subsequent comparison is off by one period, permanently. The robust version is to build a complete month spine and LEFT JOIN, or to self-join on the computed prior period rather than trusting row positions. This is the single most common defect in period-over-period reporting.

Likely interview questions

          

            
Very commonCompute month-over-month revenue growth.
              
Aggregate to month in a CTE, then (rev - LAG(rev) OVER (ORDER BY mo)) / NULLIF(LAG(rev) OVER (ORDER BY mo), 0), multiplied by 100.0.
Three defects to pre-empt, all of which the interviewer is watching for. Integer division — use 100.0. Division by zero — NULLIF the denominator. Missing months — LAG counts rows, so a month with no sales makes every later comparison compare the wrong pair. The fix is a month spine, or joining on the explicitly computed previous month rather than relying on row order.
Then the presentation point that separates an analyst from a query writer: growth from a small base is meaningless. A jump from £2 to £10 is +400% and belongs in no report. Show the absolute delta alongside the percentage, and consider suppressing the percentage below a base threshold.
For year-over-year the same argument applies with offset 12, and the spine matters even more because a single missing month corrupts twelve comparisons.

            

          

        

      


      

        
5.7 FIRST_VALUE, LAST_VALUE, and the frame that breaks LAST_VALUE ⭐

        
A function that appears broken on first use, is actually behaving exactly as specified, and catches nearly everyone once.


        
LAST_VALUE(x) OVER (ORDER BY d) returns the current row's value, not the partition's last. That is because the default frame ends at CURRENT ROW (§5.2), so “the last value in the frame” is the current row. Nothing is wrong; the default frame is simply not what you wanted.

        
The fix: LAST_VALUE(x) OVER (ORDER BY d ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING). FIRST_VALUE looks fine by luck, because the frame's start already is the partition's start.

        
The idiom to prefer: FIRST_VALUE(x) OVER (ORDER BY d DESC) — flip the sort instead of extending the frame. Shorter, harder to get wrong, and it is what most experienced people write.

Likely interview questions

          

            
GotchaWhy does LAST_VALUE return the current row's value?
              
Because with an ORDER BY in the window and no explicit frame, the frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. The last row of that frame is the current row, so LAST_VALUE is answering correctly — it is the frame that is not what you assumed.
Three fixes: extend the frame to UNBOUNDED FOLLOWING; reverse the sort and use FIRST_VALUE(x) OVER (ORDER BY d DESC); or use MAX/MIN over the whole partition if what you actually want is the extreme value rather than the chronologically last one. The second is my preference — shorter, and it makes the intent visible.
Say why FIRST_VALUE seems fine: it is not immune, it is just that the frame's start already coincides with the partition's start, so the default happens to give the right answer. Understanding that is the difference between memorising a workaround and knowing the mechanism.

            

          

        

      


      

        
5.8 Rolling metrics without leaking the current row ⭐

        
If the window feeds a model, including the current row is target leakage. This is the SQL half of a mistake that invalidates entire experiments.


        
A rolling average that includes the current row lets a feature see the outcome it is supposed to predict. Offline the model looks excellent; in production it collapses, because at prediction time the current row's value does not exist yet.

        
The fix is one word: end the frame at 1 PRECEDING instead of CURRENT ROW. Every value is then strictly historical.


        

          
Leaky
ROWS BETWEEN 3 PRECEDING AND CURRENT ROW

Row t sees its own value. Fine for a chart. Fatal as a feature.

          
Causal
ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING

Row t sees only rows before t. First row is NULL — correctly, there is no history.

A model trained on the first column will validate beautifully and fail in production.

        


        

          
Likely interview questions

          

            
GotchaYou are building a feature: the customer's average order value before this order. Write it.
              
AVG(amount) OVER (PARTITION BY customer_id ORDER BY order_date, id ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING).
The words “before this order” are the whole question, and 1 PRECEDING is how you honour them. Ending at CURRENT ROW includes the row being predicted, which is target leakage — the model learns from the answer.
Three further points that make this a strong answer. The first order per customer correctly yields NULL, and how you fill that (a global prior, a zero, or a “new customer” flag) is a modelling decision, not a SQL one. Ties on the ordering column are dangerous: two orders on the same timestamp can see each other unless the tie-break is deterministic, so add id. And if the real-world constraint is a data availability lag rather than row order — the value is only known a day later — then row-based exclusion is not enough and you need an as-of join on availability time (§2.9, §6.10).
This is worth practising because it is where SQL and ML interviews overlap, and a candidate who spots the leakage unprompted stands out immediately.

            

          

        

      


      

        
5.9 Named windows

        
Define the window once, reuse it. Reduces repetition, prevents a class of copy-paste bug, and hints to the reader that one sort is being shared.


        
The WINDOW clause sits between HAVING and ORDER BY. Once w is defined, every function can say OVER w, and you can extend it — OVER (w ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) — to inherit the partition and order while overriding the frame.

        
Why it matters beyond tidiness: when six window functions repeat the same long specification, one of them eventually differs by a character and nobody notices. Naming it makes them provably identical. Supported in PostgreSQL, MySQL 8, SQLite, Oracle and DuckDB; not in SQL Server or BigQuery, where you repeat the clause.

Likely interview questions

          

            
ConceptualDoes using several window functions mean several sorts?
              
Not necessarily. Window functions sharing an identical PARTITION BY and ORDER BY are evaluated in the same window pass, so one sort serves all of them — the frame can differ without costing another sort. Functions with different specifications each need their own pass, and you can see them stack up in the EXPLAIN plan as separate WindowAgg or Window Spool nodes.
The practical consequences: prefer one window specification and vary the frame; be aware that adding a differently-partitioned window to an existing query can double its cost; and if the partition/order matches an index, the engine may skip the sort entirely, which is why an index on (customer_id, order_date) can transform a windowed query.
Naming the window with WINDOW w AS (...) does not change the plan, but it makes the sharing visible to whoever reads the query next — and it guarantees the specifications really are identical rather than nearly identical.

            

          

        

      


      

        
5.10 Cumulative distinct count

        
“Total customers acquired by each month”. Deceptively hard, because COUNT(DISTINCT ...) is not allowed as a window function in most engines.


        
COUNT(DISTINCT x) OVER (ORDER BY d) is rejected by PostgreSQL, SQL Server, MySQL and SQLite. The reason is real: a distinct count is not incrementally computable the way a sum is — you cannot get the running distinct count from the previous value plus the current row without remembering everything seen so far.

        
The standard trick: reduce each entity to its first appearance, then a plain cumulative SUM of the counts is exactly the running distinct total. That reframing — count each thing once, at the moment it first appears — is the whole answer and it generalises to first purchase, first login, first failure.

Likely interview questions

          

            
CodingRunning count of unique customers by month.
              
COUNT(DISTINCT ...) as a window function is unsupported in PostgreSQL, MySQL, SQL Server and SQLite, so the answer is a reframing rather than a syntax trick.
Reduce each customer to their first month, then take a cumulative SUM of the per-month counts. Counting each customer exactly once at first appearance makes the running sum equal the running distinct count by construction.
Say why the direct form is unsupported, because it shows you understand rather than just remembering: a distinct count is not incrementally computable — you cannot derive it from the previous value plus one row without retaining the whole set seen so far, which is why engines that do offer it (BigQuery, Snowflake) are effectively recomputing or approximating.
Alternatives worth naming: a self-join or correlated subquery counting distinct customers up to each month (correct, O(n²)); APPROX_COUNT_DISTINCT / HyperLogLog sketches, which are mergeable and therefore genuinely incremental, and are how warehouses do this at scale. And the assertion to run afterwards: the final cumulative value must equal a plain COUNT(DISTINCT customer_id) over the whole table.
