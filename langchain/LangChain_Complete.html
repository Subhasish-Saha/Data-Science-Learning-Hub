Part 1 of 6
LLM Foundations
Tokens, context, decoding, tool calling, hallucination
Level 0 · LLM Fundamentals

The machine under the framework

Every LangChain question eventually reduces to something here. Interviewers open with these because they cleanly separate people who understand the model from people who call an API.

1.1 Tokens & tokenization

Models don't see characters or words — they see tokens. Every limit that matters (cost, context, rate limits) is denominated in them, so a wrong mental model here shows up as a surprise bill.

A tokenizer splits text into subword units learned from a corpus — BPE (GPT/tiktoken), WordPiece (BERT), SentencePiece (many others). Common words are one token; rare words shatter. Rough English heuristic: ~4 characters ≈ 1 token, 100 tokens ≈ 75 words.

1.2 The context window

Everything the model can see in one call — and it holds more than you think. It's also not uniform: material in the middle is measurably under-used.

The window holds: system prompt + conversation history + retrieved documents + tool results + the current input + reserved space for the output. Run out and you don't get a clean error — you get silent truncation and quietly worse answers.

Gotcha · "we have a 1M window, so context isn't a problem"

A bigger window changes what fits, not how reliably the model uses it, and every token still costs money and latency. Long prompts also degrade in the middle. The senior framing: context is an allocated budget — see context engineering in Part 2 §2.13.

1.3 Decoding & sampling parameters

The model outputs a probability distribution; these parameters decide how it becomes a token. For LangChain apps you want them cold almost everywhere.

ParameterWhat it doesUse
TemperatureScales logits before softmax — low sharpens toward the top token, high flattens0–0.3 extraction, classification, code, structured output · 0.7–1.0 ideation
Top-p (nucleus)Keeps the smallest token set with cumulative probability ≥ p — adapts to confidenceGenerally preferred over top-k
Top-kFixed number of candidatesBlunter; can over-truncate when the model is genuinely unsure
max_tokensCaps output lengthCost control; remember it competes for window space
stop, seedStop sequences; reproducibility hintStructured formats; testing
Common pitfall · "temperature=0 means deterministic"

It's near-deterministic, not guaranteed. Floating-point non-associativity, GPU batching, MoE routing, and silent model-version updates all introduce variation. If you need reproducibility: pin the model version, set a seed where supported, and test against a schema rather than an exact string. High temperature is also the top cause of malformed JSON — a very common bug report.

1.4 Model families & selection

Choosing a model is a three-way trade — quality, latency, cost — plus a fourth axis most people forget: whether it's a reasoning model, which changes how you prompt it.

  • Base vs instruction-tuned vs reasoning models — reasoning models do chain-of-thought internally, so explicit "think step by step" is redundant and can hurt (Part 2 §2.9)
  • Proprietary (Claude, GPT, Gemini) vs open-weight (Llama, Qwen, Mistral, DeepSeek) — the latter for privacy, cost at scale, or fine-tuning control
  • Model routing — a cheap model classifies/routes, a strong model synthesises. One of the biggest cost levers you have
  • Read the model card: context length, knowledge cutoff, tool-calling support, modality, pricing
  • TTFT (time to first token) vs total latency — with streaming, TTFT is what users feel

In LangChain you branch on capability rather than hard-coded names using model profiles — model.profile exposes what a model actually supports (Part 3 §3.3).

1.5 Core capabilities you must explain

Five mechanisms that every LangChain abstraction is a wrapper over. Knowing the raw behaviour is what lets you debug the wrapper.

  • Function/tool calling — as above; the loop is what agents are made of
  • Structured output — provider-native (constrained decoding), tool-based, or prompted; strongest to weakest guarantee (Part 3 §3.8)
  • Embeddings — text → vector; similarity is geometry (deep dive in the RAG subject)
  • Multimodality — images, audio, PDFs as first-class input
  • Prompt caching — a stable prefix is cached provider-side, cutting cost and TTFT dramatically for long system prompts

1.6 Hallucination — mechanism, not mystery

A model trained to produce plausible continuations will produce a plausible continuation even when it has no grounds for one. That's the whole mechanism.

Four drivers: lossy memory (weights store patterns, not a database — specifics go first), staleness (frozen at training cutoff), no native abstention (optimised to be helpful and fluent, so it fills gaps), and genuine gaps (private or long-tail facts never seen).

1.7 Fine-tune vs prompt vs retrieve

One line to memorise: fine-tune for behaviour, retrieve for knowledge, prompt for everything you can.

PromptingRAGFine-tuning
Best forBehaviour you can describeFacts: large, fresh, private, citableBehaviour you can only show — format, tone, a skill
Update costEdit a stringRe-index a documentRe-train (hours–days)
LatencyBaseline+ retrievalBaseline (cheapest at inference)
CitationsNoNativeNo
Main riskPrompt drift, brittlenessRetrieval missesStaleness, catastrophic forgetting

They compose: fine-tune the generator for format and retrieve for facts is a normal production stack. And sometimes the answer is none of them — a classifier, a SQL query, or fifteen lines of Python.

1.8 Interview focus

Likely interview questions
CoreWhy is my app twice as expensive in another language?

Token inflation. Tokenizers are trained predominantly on English, so non-Latin scripts fragment into far more tokens for the same meaning — often 2–4×. Since cost, context limits, and rate limits are all per-token, everything scales up. Same effect for code, JSON, and UUIDs. Mitigations: measure tokens per language with the actual model's tokenizer, budget context per locale, consider a model with a better multilingual tokenizer, and don't extrapolate cost from English benchmarks.

TrapYou set temperature=0 and still get different JSON. Why?

temperature=0 is near-deterministic, not guaranteed. Floating-point non-associativity, GPU batching, mixture-of-experts routing, and silent model-version updates all introduce variation. If you need stability: pin the model version, set a seed where supported, and — most importantly — validate against a schema instead of asserting an exact string. Use structured output so the shape is enforced rather than hoped for.

Core ⭐Why do LLMs hallucinate, and how do you actually reduce it?

They're next-token predictors over lossily-compressed, frozen knowledge with no built-in abstention — so on gaps, stale facts, or specifics they produce something plausible. Reduce it by climbing the ladder: ground with retrieval, constrain the output (structured/provider-native), verify claims (chain-of-verification or an NLI/entailment check), measure faithfulness with an LLM judge, and give the system a real abstention path. Lowering temperature is not a fix — it reduces variance, not fabrication.

DesignFine-tune, RAG, or prompt — how do you decide?

Split the requirement. Knowledge that's large, changing, private, or must be cited → RAG. Behaviour — format, tone, a classification skill, domain phrasing you can only demonstrate → fine-tuning. Everything you can simply describe → prompting, which is cheapest to iterate. They combine in production. And check whether an LLM is needed at all: for a fixed classification, an encoder model is far faster and cheaper; for aggregation over a table, it's a SQL query.

CoreWho executes a tool call?

Your code does. The model only emits a structured request naming a tool and arguments; the framework routes it, your function runs, and the result goes back as a ToolMessage for the next model call. That's why the security boundary is yours: least-privilege credentials, validation, and approval gates on destructive actions. A hijacked model can request anything — it can only do what your executor permits.

Prompt Engineering
6-category taxonomy, reasoning models, injection, context engineering
Level 1 · Prompt Engineering

From tips to a discipline

This part is built on The Prompt Report (Schulhoff et al.) — a systematic review of 1,500+ papers that catalogues 58 text techniques in 6 categories. Learn the categories, not a list of tricks: it's the difference between reciting "add think step by step" and reasoning about which family of technique a problem needs.

2.1 Anatomy of a prompt

Seven components. Most bad prompts are missing one of them, not badly worded.

2.2 The six categories ⭐

Memorise this structure. It converts a grab-bag of tricks into a framework you can reason from — and it's the single highest-value thing on this page for interviews.

2.3 Zero-shot techniques

No examples — just better instructions. Cheapest family, and often enough.

  • Role / persona prompting — "you are a senior tax accountant". Honest caveat: measured gains are smaller than folklore suggests; it helps tone and vocabulary more than accuracy
  • Style prompting — specify register, length, structure
  • Emotion prompting — "this is important to my career"; real but marginal
  • System 2 Attention (S2A) — have the model rewrite the prompt to strip irrelevant context first, then answer
  • Rephrase and Respond (RaR) — model restates the question before answering, surfacing misreads early
  • Self-ask — model generates and answers its own sub-questions (the bridge to decomposition)

2.4 Few-shot & in-context learning

Showing beats telling — but only if the examples are constructed well. The survey's most actionable finding is that six separate factors govern whether few-shot helps or actively hurts.

2.5 Thought generation

Make the reasoning explicit so errors have somewhere to surface. The most-used family — and the one most often applied where it doesn't belong.

  • Chain-of-Thought — few-shot examples that show the reasoning
  • Zero-shot CoT — "Let's think step by step" (Kojima et al.); no examples needed
  • Step-back prompting — ask the governing principle first, then the specific question
  • Analogical prompting — model generates its own relevant exemplars before solving
  • Contrastive CoT — show correct and incorrect reasoning
  • Thread-of-Thought, complexity-based prompting
When CoT hurts

On simple tasks it adds latency and output tokens for no accuracy gain. On latency-critical paths it's often unaffordable. And on reasoning models it's redundant at best and degrading at worst (§2.9). CoT is a tool for hard multi-step problems on non-reasoning models — not a universal prefix.

2.6 Decomposition

When a problem is too big for one pass, split it. This family is also where prompting starts becoming orchestration — which is where LangChain and LangGraph enter.

  • Least-to-most — solve the easiest sub-problem first, build up
  • Plan-and-solve — plan explicitly, then execute the plan
  • Tree-of-Thoughts — branch, evaluate, backtrack; a search over thoughts
  • PAL / Program-of-Thought — emit code and execute it. The right answer for arithmetic and precise logic, because you're offloading to an interpreter instead of hoping
  • Skeleton-of-Thought — outline, then expand branches in parallel (a latency win)
  • Prompt chaining — sequential prompts, each consuming the last's output → this is literally LCEL (Part 3 §3.11)

2.7 Ensembling

Run it several ways and aggregate. Buys reliability with money.

Self-consistency is the canonical one: sample N chain-of-thought paths at temperature > 0, then take the majority answer — different reasoning routes that converge are more trustworthy than one confident path. Universal self-consistency uses an LLM to pick the most consistent answer when answers aren't directly comparable (free text rather than a number).

The economics are the whole decision: N× the cost and latency for a single answer. Justified for high-stakes, low-volume decisions; rarely justified on a chat hot path.

2.8 Self-criticism

Have the model check its own work — with a large caveat.

  • Self-refine — generate → critique → revise, looped (bound it, or it spins)
  • Chain-of-Verification (CoVe) — draft an answer, generate verification questions, answer those independently, then revise. The independence is what makes it work
  • Self-verification, reversing CoT, cumulative reasoning
Gotcha · "self-critique fixes hallucination"

Models are unreliable judges of their own output — the same flawed reasoning that produced the error often endorses it. Self-criticism helps most when the check is structurally independent: a different model, a tool/interpreter, or retrieved evidence. CoVe works partly because it forces the verification questions to be answered without the draft in view.

2.9 Prompting reasoning models ⭐

A genuinely modern differentiator — and a question that instantly dates a candidate who answers with 2023 advice.

2.10 Automated prompt optimisation

The 2026 framing: prompts are artefacts you optimise against a metric, not strings you tweak by feel.

  • APE (Automatic Prompt Engineer), Active-Prompt, meta-prompting (prompts that write prompts)
  • DSPy — declare the task signature and a metric, and compile the prompt; reported to beat hand-tuning in far less time
  • Prompt management: versioning, A/B tests, decoupling prompts from code (LangSmith Prompt Hub)

2.11 Evaluating prompts

If you can't say how you knew a prompt got better, you were guessing. This is the answer that separates seniors.

  • Build a small labelled set before iterating — 50–200 balanced, realistic cases, including hard and no-answer ones
  • Metrics ladder: exact match / regex / JSON-validity (cheap, deterministic) → LLM-as-judge (scalable) → human (gold)
  • Judge biases: position, verbosity, self-preference — mitigate with a rubric, order swapping, and a judge model different from the generator
  • Is +2% real? Use paired comparison and a bootstrap CI; segment by case type so a flat average doesn't hide a regression
  • Regression-test prompts in CI — a prompt change is a code change
Level 2 · Security & Context

The half everyone skips

Prompting well isn't enough if the prompt can be hijacked, or if the context window is filled without thought. These two topics are where prompt engineering meets systems engineering.

2.12 Prompt injection & jailbreaking

The critical distinction: direct injection comes from the user; indirect injection arrives inside retrieved documents and tool output — and that's the one that bites LLM applications.

2.13 Context engineering

The discipline that supersedes prompt engineering: deciding what enters the window, when, and why.

The shift in framing: context is an allocated budget, not a bucket you fill because it's there. The levers span everything you've learned — retrieval precision and reranking, compression and summarization, tool-output size caps, sub-agent isolation, ordering for attention (edges beat middle), and prompt caching to make a stable prefix cheap.

A concrete benchmark: the deepagents package cut default-turn input tokens by roughly 65% through leaner prompts and tighter tool schemas alone — no model change. That's the size of the prize.

2.14 Interview focus

Likely interview questions
Core ⭐Name the categories of prompting techniques.

Six, per The Prompt Report: zero-shot (precise instructions — role, style, S2A, rephrase-and-respond), few-shot/ICL (examples, with selection strategies), thought generation (CoT, zero-shot CoT, step-back, analogical), decomposition (least-to-most, plan-and-solve, Tree-of-Thoughts, PAL), ensembling (self-consistency), and self-criticism (self-refine, chain-of-verification). Useful because it's diagnostic: format problems → zero/few-shot, reasoning failures → thought generation, complexity → decomposition, inconsistency → ensembling, plausible-but-wrong → self-criticism plus external verification.

Practical ⭐You have 1,000 labelled examples and a context limit. How do you use them?

Select, don't truncate. Use a semantic similarity example selector: embed all 1,000 examples once, embed the incoming input at query time, retrieve the k nearest, and inject only those — turning "similarity" (the strongest of the six exemplar factors) into a mechanism. Also watch order (shuffle to avoid recency bias), label balance (imbalance skews predictions), format consistency, and quality (one wrong exemplar poisons the pattern). If it's still not enough and the task is stable, that's the point at which fine-tuning starts to beat few-shot on tokens.

Modern ⭐How does your prompting change for a reasoning model?

You stop telling it how to think. Reasoning models generate internal chain-of-thought, so explicit "think step by step" is redundant and can degrade output by constraining a search that was already working; heavy few-shot often hurts for the same reason. Instead give goals, constraints, and success criteria, and control cost with the reasoning-effort/thinking-budget setting rather than prompt gymnastics. Also budget for reasoning tokens — they're billed — and note traces come back as a distinct reasoning content block.

TrapWhen does chain-of-thought hurt?

Three cases. On simple tasks it burns latency and output tokens for no gain. On latency-critical paths the cost is often unacceptable. And on reasoning models it's redundant at best, harmful at worst. CoT is for hard multi-step problems on non-reasoning models — treating it as a universal prefix is a 2023 habit.

Security ⭐Direct vs indirect prompt injection — and your defences?

Direct arrives in the user's message. Indirect arrives inside content the system itself pulled in — a retrieved document, a scraped page, a tool result — and it's the agent-specific risk, because that content reaches the model with the developer's implicit trust. Defend in layers: delimit untrusted content and explicitly label it as data, never instructions; keep a clear instruction hierarchy and restate rules after untrusted blocks; scan inputs and outputs; and — the load-bearing one — least-privilege tool credentials plus HITL on destructive actions, so a successful hijack can't do much. Put adversarial cases in your eval set and test injection like a feature.

SeniorHow do you know a prompt change actually improved things?

Measure on a fixed labelled set built before iterating. Use the cheapest sufficient metric (exact match / JSON validity, then LLM-as-judge, then human), compare paired on the same inputs, and report a bootstrap confidence interval — a 2% move on 40 examples is noise. Debias the judge (rubric, swap ordering, different model from the generator) and segment results by case type so a flat average doesn't hide a regression in one slice. Then wire it into CI so a future prompt edit can't silently regress it.

Level 3–4 · Architecture, Models & Messages

What's actually in the box

The package split is the highest-yield trivia in LangChain interviews, and messages changed in ways that break old code quietly.

3.1 What LangChain is for — and isn't

Be able to argue both sides. Interviewers use this to test whether you're a defensive fanboy or an engineer with judgment.

The value: one interface across 1,000+ providers, vector stores and tools; batteries-included components; composition primitives that give you streaming, batching, async, retries and tracing for free.

The cost: an abstraction layer to debug through, version churn (see the box above), and opacity when something goes wrong deep in a chain.

Interview tip · "when would you NOT use LangChain?"

A strong answer: latency-critical single-step calls (the abstraction buys nothing and costs milliseconds), a task that's one provider API call, and anywhere the indirection obscures more than it saves. Teams have publicly reported large latency and error-rate improvements after dropping to plain SDK calls on hot paths. The mature position: use LangChain for the plumbing you'd otherwise rewrite — provider abstraction, retrieval composition, agent harness — and drop to raw SDKs where the value isn't there.

Know which package holds what. This single diagram answers a whole category of interview questions.

Level 5–7 · Prompts, Output & LCEL

Composition

Templates in, validated objects out, and the pipe operator that ties everything together — plus the scoping question every interview asks: LCEL or LangGraph?

3.6 Prompt templates

PromptTemplate (string completion) vs ChatPromptTemplate (message list — use this with chat models). Templates are Runnables, so they pipe straight into a model.

3.7 Few-shot in LangChain

Part 2 §2.4 said similarity is the strongest exemplar factor. Example selectors are how you implement that.

Also available: MaxMarginalRelevanceExampleSelector (similarity + diversity) and LengthBasedExampleSelector (fit a token budget).

3.8 with_structured_output ⭐

The default way to get typed data out of a model — and the two strategies behind it are a favourite interview probe.

3.9 Output parsers — narrower, still useful

Not dead, just scoped. The everyday one is StrOutputParser; the rest matter when structured output isn't available.

  • StrOutputParser — the "just give me the text" tail of nearly every chain
  • JsonOutputParser, PydanticOutputParser, CommaSeparatedListOutputParser, XMLOutputParser
  • get_format_instructions() — how a parser injects format rules into the prompt
  • OutputFixingParser / RetryOutputParser — repair malformed output with a second LLM call (costs a round-trip; bound it)
  • Rule of thumb: with_structured_output when the provider supports it (validated, no parse step); parsers when it doesn't, or for a cheap StrOutputParser tail

3.10 The Runnable interface

One contract, implemented by everything — which is why anything composes with anything.

Every component exposes invoke, batch, stream plus the async variants and astream_events. Prompt templates, models, parsers, retrievers, and your own functions all satisfy it — so a pipeline is just composition, not glue code.

3.11 LCEL — the pipe operator

What LCEL buys you without extra code: streaming, batching, async, parallelism, retries, fallbacks, and tracing. That's the actual argument for using it over hand-rolled function calls.

3.12 LCEL vs LangGraph ⭐

A top-tier 2026 question. The wrong answer is "LangGraph replaced LCEL" — the right one is that they're scoped.

3.13 Interview focus

Likely interview questions
Trap ⭐What changed in LangChain 1.0?

The langchain package was streamlined down to agent essentials — langchain.agents, .messages, .tools, .chat_models, .embeddings — and everything legacy (LLMChain, ConversationChain, AgentExecutor, the old memory classes, MultiQueryRetriever and the old retrievers module, indexing API, hub) moved to langchain-classic. Agents now run on the LangGraph runtime via create_agent, with a middleware system. Messages gained standard content blocks and .text became a property. Python 3.9 was dropped. It's a stability release: no breaking changes promised until 2.0.

Core ⭐LCEL or LangGraph — how do you decide?

By whether the workflow is stateful. LCEL is for stateless linear/DAG composition — prompt → model → parse, RAG stuffing, parallel fan-out with a join — and gives you streaming, batching, async, retries and tracing for free. LangGraph is for anything that loops on state, persists, pauses for a human, or coordinates multiple agents. LCEL isn't deprecated, it's scoped; the 2026 guidance is that LangGraph replaced LCEL for stateful logic specifically. In one app I'd keep the retrieval chain in LCEL and put the agent loop in LangGraph.

Core ⭐with_structured_output vs output parsers?

with_structured_output is the default: you pass a Pydantic/TypedDict/JSON schema and get back a validated object, with the model constrained via ProviderStrategy (provider-native constrained decoding — strongest guarantee) or ToolStrategy (an artificial tool call carrying the schema — portable). Output parsers post-process raw text and matter when the provider lacks structured output, for a cheap StrOutputParser tail, or for repair (OutputFixingParser). Note prompted structured output — "please return JSON" — is no longer supported in agents, because it's a hope rather than a guarantee.

PracticalHow do you make one codebase work across OpenAI and Anthropic?

init_chat_model("provider:model") for a uniform constructor, standard content blocks so reasoning/citations/images arrive in the same shape and your UI doesn't break on a switch, model profiles (model.profile) to branch on real capabilities instead of hard-coding model names, and .with_fallbacks() for failover. Then watch provider-specific defaults — Anthropic's max_tokens is now model-specific, not a portable 1024 — and evaluate per provider, since prompt behaviour genuinely differs.

DebugYour ChatPromptTemplate throws a KeyError on a prompt containing JSON. Why?

Unescaped braces. The template treats {…} as a variable, so literal JSON in your prompt is parsed as a placeholder. Escape them by doubling: {{"ok": true}}. It's a classic silent bug because it only fires when someone puts an example JSON payload in the system prompt.

Level 8 · Tools, Agents & Middleware

The harness matters as much as the loop

In 1.x the agent loop comes from LangGraph and the harness comes from middleware — a catalogue of 19 provider-agnostic components that replace most of what you'd otherwise hand-build. It's the most under-taught part of modern LangChain.

4.1 Defining tools — the docstring is the prompt

The model never sees your implementation. It sees name, docstring, and argument schema — and picks from those alone.

  • Prefer few, well-scoped, non-overlapping tools — overlap is what makes the model dither
  • Negative guidance ("not for X") disambiguates better than more adjectives
  • Keep outputs small — every tool result re-enters the context window
  • ~15 tool calls per pass is a practical ceiling before selection quality degrades
  • ⭐ Too many tools? Don't prune by hand — LLMToolSelectorMiddleware(max_tools=…) narrows the set per call (§4.3)

4.2 create_agent ⭐

Likely interview questions
Trap ⭐How do you implement conversational memory in LangChain in 2026?

Not with ConversationBufferMemory — that's deprecated and lives in langchain-classic. And not with RunnableWithMessageHistory either, which was its official replacement and was itself deprecated in 0.3 as unintuitive. The current answer is persistence via the LangGraph runtime: a checkpointer for thread-scoped history (keyed by thread_id) and a Store for cross-thread/user memory (keyed by namespace), plus SummarizationMiddleware for context compaction. Knowing all three generations — and why each was replaced — is what the question is really testing.

ProdYour agent hangs in production at 3am. How do you debug it?

Start from traces, not code. Check LangSmith for the stuck run: which node, how many model calls, what the last tool returned. Common causes: provider rate-limiting or an outage (429s/retries silently stacking), an unbounded loop, a tool call with no timeout, or context overflow. Immediate mitigations: ModelCallLimitMiddleware to cap runs, timeouts on every tool, .with_fallbacks() to a second provider, and graceful degradation returning a partial answer. Then add the regression case to your eval dataset so it can't recur silently.

Prod ⭐How do you control LLM cost, and where does the money actually go?

Generation dominates — retrieval and embedding are usually noise by comparison. So measure first (usage_metadata on every call, per-route dashboards), then pull levers in impact order: model routing (cheap model classifies/routes, strong model synthesises), semantic caching (hit-rate rises with traffic), provider prompt caching for stable prefixes, shorter context via reranking and compression, output-token caps, and batching. Bound agents with call limits, and set hard per-tenant budgets. Optimising retrieval to save cost is a classic misallocation of effort.

ProdHow do you test an LLM app deterministically in CI?

Three layers. Unit: chains and helpers are plain callables — test them directly, no LLM involved. Integration: stub the model with a fake chat model returning scripted messages/tool calls, and use LLMToolEmulator so agent tests never hit real APIs — that's what makes CI fast, free, and deterministic. Regression: LangSmith datasets with outcome evaluators run as a gate on prompt/model changes. And assert against a schema, not an exact string, since even temperature=0 isn't byte-stable.

SecurityIs dependency security part of your job here?

Yes. A concrete example: CVE-2025-68664 (CVSS 9.3), a deserialization vulnerability in langchain-core's dumps()/dumpd() that affected message history and event streaming — fixed in ≥ 0.3.81. Owning an LLM stack means pinning versions, tracking advisories, and having a patch path — alongside the model-level concerns (indirect prompt injection, least-privilege tool credentials, PII redaction before traces).

6.1 LangChain conceptual

6 questions
CoreWhat is LangChain and what does it cost you?

Value: one interface across 1,000+ providers/vector stores/tools, batteries-included components, and composition primitives that give you streaming, batching, async, retries and tracing for free. Cost: an abstraction layer to debug through, significant version churn, and opacity when something fails deep in a chain. Use it for the plumbing you'd otherwise rewrite; drop to raw SDKs on hot paths.

Senior ⭐When would you NOT use LangChain?

Latency-critical single-step calls (the abstraction buys nothing and costs milliseconds), anything that's genuinely one provider API call, and cases where the indirection obscures more than it saves — teams have publicly reported large latency and error-rate improvements after moving hot paths to plain SDK calls. Also skip it when the task isn't an LLM task at all: a classifier is faster and cheaper for fixed-label classification, and aggregation over a table is a SQL query. Being able to say this without defensiveness is the point of the question.

Trap ⭐What changed in LangChain 1.0? What is langchain-classic?

The langchain package was streamlined to agent essentials (.agents, .messages, .tools, .chat_models, .embeddings); everything legacy — LLMChain, ConversationChain, AgentExecutor, the old memory classes, MultiQueryRetriever and the old retrievers module, indexing API, hub — moved to langchain-classic. Agents run on the LangGraph runtime via create_agent with a middleware system; messages gained standard content blocks; .text became a property; Python 3.9 dropped. Stability release — no breaking changes until 2.0.

TrapLangChain vs LangGraph?

Layers, not rivals. LangGraph is the runtime (graph engine, state, checkpointing, durability); LangChain is the batteries-included layer whose create_agent runs on it. Picking a side reveals a misunderstanding of the stack.

CoreChains vs agents — when do you choose a chain?

A chain is a fixed sequence you author; an agent lets the model choose the control flow. Choose a chain whenever the steps are knowable: it's cheaper, faster, deterministic, testable, and debuggable. Agents buy adaptability to paths you couldn't enumerate, at the cost of latency, tokens, and non-determinism.

CoreWalk me through the packages.

langchain-core (base abstractions, messages, the Runnable interface, minimal deps — pin ≥ 0.3.81 for CVE-2025-68664) · langchain (streamlined agent essentials) · langchain-classic (the 0.x legacy) · langchain-<provider> packages like -openai/-anthropic (preferred over community) · langchain-community (third-party integrations) · langgraph (the runtime) · langsmith (tracing/eval).

6.2 Runnables & LCEL

5 questions
CoreWhat is the Runnable interface and why does it exist?

A uniform contract — invoke, batch, stream, plus async variants and astream_events — implemented by prompts, models, parsers, retrievers and your own functions. It exists so anything composes with anything: a pipeline becomes composition rather than glue code, and every component inherits streaming, batching, async and tracing behaviour automatically.

CoreExplain LCEL. What do you get for free?

| builds a RunnableSequence; a dict literal builds a RunnableParallel whose branches run concurrently. For free you get streaming, batching, async, parallelism, retries, fallbacks, and tracing — that's the actual argument for LCEL over hand-rolled function calls. Add RunnablePassthrough, RunnableLambda, and RunnableBranch for plumbing and routing.

Core ⭐LCEL or LangGraph?

Decided by state. LCEL for stateless linear/DAG composition — prompt → model → parse, RAG stuffing, parallel fan-out with a join. LangGraph the moment the workflow loops on state, persists, pauses for a human, or coordinates multiple agents. LCEL isn't deprecated, it's scoped; LangGraph replaced LCEL for stateful logic specifically. Using LangGraph for prompt | model | parser is over-engineering.

PracticalHow do you add retries and fallbacks?

At chain level: .with_retry(stop_after_attempt=3) for transient failures and .with_fallbacks([backup]) for model/provider failover — both return new Runnables so they compose. Inside an agent, use ModelRetryMiddleware, ToolRetryMiddleware, and ModelFallbackMiddleware. Pair with timeouts and graceful degradation so a failure returns a partial answer rather than a 500.

PracticalHow does streaming work through a chain?

.stream()/.astream() propagate through the whole sequence, and astream_events(version="v3") gives typed events (1.3+). Parsers can emit partial structured output (streaming JSON). The practical gotcha: filter to assistant text — piping raw tool-call JSON to a UI looks broken. Optimise for time-to-first-token, since that's what users perceive.

6.3 Models, messages & prompts

4 questions
CorePromptTemplate vs ChatPromptTemplate; what is MessagesPlaceholder?

PromptTemplate renders a single string (completion-style); ChatPromptTemplate renders a message list with roles — use it with chat models, which is everything modern. MessagesPlaceholder reserves a slot in that list for a variable-length sequence, typically conversation history or an agent scratchpad, so you can inject N prior turns without restructuring the template.

Practical ⭐Few-shot at scale — 1,000 examples, limited context?

Select, don't truncate. Use SemanticSimilarityExampleSelector with FewShotChatMessagePromptTemplate: embed all examples once, embed the incoming input, retrieve the k nearest and inject only those. That operationalises similarity, the strongest of the six exemplar factors. Also mind order (shuffle — recency bias), label balance, format consistency, and quality (one wrong exemplar poisons the pattern). Alternatives: MaxMarginalRelevanceExampleSelector for diversity, LengthBasedExampleSelector to fit a budget.

CoreWhat are standard content blocks and what do they solve?

A provider-agnostic representation of model output — text, reasoning, image, citations, tool calls — exposed via .content_blocks. Before them, OpenAI's "thinking" and Anthropic's "reasoning" had different shapes, so swapping providers broke your UI. They also standardise multimodal input via HumanMessage(content_blocks=[...]). Serialization into content is opt-in (LC_OUTPUT_VERSION=v1 or output_version="v1").

PracticalHow do you make one codebase work across providers?

init_chat_model("provider:model") for a uniform constructor, standard content blocks so output shape is stable, model profiles (model.profile) to branch on capabilities rather than hard-coded names, and .with_fallbacks() for failover. Then account for provider-specific defaults (Anthropic's max_tokens is now model-specific) and evaluate per provider — prompt behaviour genuinely differs.

6.4 Structured output

3 questions
Core ⭐with_structured_output vs output parsers?

with_structured_output is the default — pass a Pydantic/TypedDict/JSON schema, get a validated object back, with no parse step. Parsers post-process raw text and matter when the provider lacks structured output, for a cheap StrOutputParser tail, or for repair (OutputFixingParser). Prompted structured output ("please return JSON") is no longer supported in agents because it's a hope, not a guarantee.

Core ⭐ProviderStrategy vs ToolStrategy?

ProviderStrategy uses provider-native structured output — the schema constrains decoding, so invalid output is essentially impossible. Strongest guarantee, and it can be inferred from the model profile. ToolStrategy emits an artificial tool call carrying the schema — portable to anything that supports tool calling, slightly weaker. A 1.0 win worth mentioning: structured output is now generated inside the agent loop, so it no longer costs an extra LLM call.

DebugThe model returns malformed JSON. Your fixes?

In order: (1) lower the temperature — high temperature is the top cause of broken structure; (2) switch from prompted JSON to with_structured_output with ProviderStrategy so the decoder is constrained; (3) if the provider can't, use ToolStrategy; (4) simplify the schema — deeply nested or ambiguous fields fail more; (5) add OutputFixingParser/RetryOutputParser as a bounded repair path. And test against the schema, not an exact string.

6.5 Tools, agents & middleware

4 questions
CoreHow does the model choose a tool, and how do you improve it?

From the tool name, docstring, and argument schema only — never your implementation. Improve by writing docstrings that state what the tool is and isn't for, using typed Pydantic schemas with per-field descriptions, keeping tools few and non-overlapping with distinct names, and adding few-shot examples for ambiguity. Wrong selection is a prompt bug in the docstring, not a model failure.

Core ⭐What is middleware and which hooks exist?

Composable hooks around the agent lifecycle: before_agent/after_agent, before_model/after_model, wrap_model_call, wrap_tool_call, dynamic_prompt, hook_config — replacing the old pre_model_hook/post_model_hook. Note there is no before_tool/after_tool; tool interception is a wrapper, which is what lets middleware substitute or approve a call rather than just observe it. In practice: SummarizationMiddleware, ModelCallLimitMiddleware, ToolRetryMiddleware, PIIMiddleware, LLMToolEmulator.

Practical ⭐40 tools, wrong selection. Options?

Fix definitions first (precise docstrings, negative guidance, no overlap). Then LLMToolSelectorMiddleware(max_tools=…) to narrow the set per call, or ProviderToolSearchMiddleware to defer to provider-side search. Architecturally, split into sub-agents with small focused toolsets (SubAgentMiddleware). ~15 tool calls per pass is a practical ceiling — a bloated toolset is a design smell.

PracticalHow do you bound an agent's cost and loop count?

ModelCallLimitMiddleware(thread_limit=…, run_limit=…, exit_behavior=…) and ToolCallLimitMiddleware are the 1.x-native answer, alongside LangGraph's recursion_limit, per-run token budgets, and hard spend caps. Also give the loop a real stop condition and return a best-effort answer on exhaustion rather than failing hard.

6.6 Retrieval & memory

4 questions

PracticalHow do you do hybrid search in LangChain?

EnsembleRetriever combining a dense vector retriever with BM25, fused with weighted reciprocal rank fusion. That's the standard fix for exact-term failures — SKUs, error codes, names — which pure embedding search misses. Layer a reranker (CrossEncoderReranker or Cohere) on top for ordering, and ContextualCompressionRetriever to trim what you send.

6.7 Production

5 questions
ProdYour agent hangs at 3am. Debug it.

ProdHow do you cache, and what's the semantic-cache risk?

Three layers: exact-match LLM cache (InMemory/SQLite/Redis), semantic cache keyed by embedding so paraphrases hit, and provider prompt caching for a stable prefix. The semantic-cache risk is staleness: it matches on meaning, not freshness, so after a re-index it happily serves yesterday's answer to a paraphrased question. Bound it with a TTL, a high similarity threshold, and explicit invalidation on re-index — and scope it per tenant so cached answers can't cross a permission boundary.

ProdHow do you keep PII out of prompts, logs and traces?

Critically, apply redaction before traces are emitted, since your observability tool is a copy of production data; LangSmith supports redaction and sampling. Add least-privilege credentials and per-tenant isolation so a leak has limited blast radius.

ProdHow do you test deterministically in CI?

6.9 Prompt engineering Q&A

6 questions
Core ⭐Name the six categories of prompting techniques.

Zero-shot (role, style, S2A, rephrase-and-respond), few-shot/ICL (with selection strategies), thought generation (CoT, zero-shot CoT, step-back, analogical), decomposition (least-to-most, plan-and-solve, Tree-of-Thoughts, PAL), ensembling (self-consistency), self-criticism (self-refine, chain-of-verification). It's diagnostic: format issues → zero/few-shot; reasoning failures → thought generation; complexity → decomposition; inconsistency → ensembling; plausible-but-wrong → self-criticism plus external verification.

CoreWhat is in-context learning, mechanically?

Pattern completion, not training. Examples in the prompt condition the model's next-token distribution toward the demonstrated input→output mapping; no weights change. That's why exemplar format consistency and label distribution matter so much — the model is imitating surface structure as well as semantics — and why a single incorrect exemplar can poison the pattern.

Modern ⭐How does prompting change for a reasoning model?

Stop prescribing how. Reasoning models produce internal chain-of-thought, so "think step by step" is redundant and can degrade output by constraining a working search; heavy few-shot often hurts similarly. Give goals, constraints and success criteria, and control cost via the reasoning-effort/thinking-budget setting. Budget for reasoning tokens — they're billed — and note traces arrive as a distinct reasoning content block.

CoreSelf-consistency — what and what does it cost?

Sample N chain-of-thought paths at temperature > 0 and take the majority answer; independent routes converging is stronger evidence than one confident path. Universal self-consistency uses an LLM to pick the most consistent answer when outputs aren't directly comparable. Cost is the decision: N× tokens and latency — justified for high-stakes low-volume decisions, rarely on a chat hot path.

Security ⭐Direct vs indirect injection, and defences?

Direct arrives in the user turn; indirect arrives in content the system itself pulled in — retrieved documents, scraped pages, tool results — reaching the model with implicit trust. Layer defences: delimit untrusted content and label it as data not instructions; maintain instruction hierarchy and restate rules after untrusted blocks; scan input and output; and — load-bearing — least-privilege tool credentials plus HITL on destructive actions, so a successful hijack can't do much. Put adversarial cases in the eval set.

Senior ⭐How do you know a prompt change improved things?

Measure on a labelled set built before iterating. Cheapest sufficient metric first (exact match / JSON validity), then LLM-as-judge, then human. Compare paired on identical inputs and report a bootstrap CI — a 2% move on 40 examples is noise. Debias the judge (rubric, order swap, judge ≠ generator model) and segment by case type so a flat average doesn't hide a regression. Then wire it into CI so a later edit can't silently undo it.

6.10 System design scenarios

Structure: clarify → data flow → component choices with rationale → prompt strategy → latency/cost budget → eval → failure modes → scale.

7 scenarios
DesignCustomer support assistant

Intent classification (constrained Literal schema) → hybrid RAG over the help centre → drafted reply with citations → escalation on low confidence. LCEL for the retrieval chain, create_agent if it needs tools (order lookup). Middleware: summarization, PII redaction, HITL before customer-facing sends. Eval from historical tickets — intent accuracy, retrieval recall, faithfulness, escalation precision/recall. Keep PII out of traces; cache semantically with per-tenant scoping.

DesignDocument extraction — 100k PDFs → structured records

with_structured_output with ProviderStrategy where supported (constrained decoding beats parsing), else ToolStrategy. Batch with .batch(), cap concurrency, and design for partial failure: per-document status, a dead-letter queue, and bounded repair via OutputFixingParser. Validate with Pydantic constraints so bad extractions fail loudly. Cost model per document up front — at 100k docs, prompt caching of the instruction prefix is a large win.

DesignMulti-provider abstraction

init_chat_model + content blocks (stable output shape) + model profiles (branch on capability) + ModelFallbackMiddleware/.with_fallbacks(). Abstract structured output via strategies rather than provider-specific JSON modes. Evaluate per provider on the same dataset — prompts are not portable in behaviour even when portable in code — and watch differing defaults.

DesignReal-time streaming chat (sub-second TTFT)

Stream tokens and optimise time-to-first-token, not total time. Levers: a fast model on the hot path, prompt caching of the system prefix, semantic cache for repeats, minimal retrieved context (rerank + compress), and skipping retrieval entirely for chit-chat via a cheap router. Manage history with trimming/summarization so the prompt doesn't grow unbounded. Filter streamed events to assistant text.

DesignInternal knowledge assistant with RBAC

Enforce permissions at retrieval with a mandatory metadata filter — never by asking the model not to mention something. Scope caches per permission set so a cached answer can't cross a boundary. Add indirect-injection defence (documents are untrusted), PII redaction before traces, and audit logging of what was retrieved per user. Test with cross-user adversarial cases in the eval set.

DesignPrompt-optimisation workflow for a team of 5

Decouple prompts from code (LangSmith Prompt Hub) with versioning, so changes are reviewable and revertible. A shared labelled dataset seeded from production traces is the source of truth; every change runs the evaluator suite and must beat the baseline on held-out cases with a CI gate. Use pairwise comparison for subjective quality and canary rollout before full deploy. Consider DSPy-style automated optimisation once the metric is trustworthy.

DesignCut LLM spend 70% without losing quality

Measure first — per-route token/cost from usage_metadata. Then, in impact order: model routing (most traffic doesn't need the frontier model), semantic + prompt caching, context reduction (rerank and compress — fewer, better chunks), output-token caps, batching, and bounding agent runs with call limits. Validate each change against the eval set so "cheaper" doesn't quietly mean "worse", and set per-tenant budgets to prevent regressions.
