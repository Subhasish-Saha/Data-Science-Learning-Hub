Level 8 · Tools, Agents & Middleware

The harness matters as much as the loop

In 1.x the agent loop comes from LangGraph and the harness comes from middleware — a catalogue of 19 provider-agnostic components that replace most of what you'd otherwise hand-build. It's the most under-taught part of modern LangChain.

4.1 Defining tools — the docstring is the prompt

The model never sees your implementation. It sees name, docstring, and argument schema — and picks from those alone.

  • Prefer few, well-scoped, non-overlapping tools — overlap is what makes the model dither
  • Negative guidance ("not for X") disambiguates better than more adjectives
  • Keep outputs small — every tool result re-enters the context window
  • ~15 tool calls per pass is a practical ceiling before selection quality degrades
  • ⭐ Too many tools? Don't prune by hand — LLMToolSelectorMiddleware(max_tools=…) narrows the set per call (§4.3)

4.4 Agent patterns & limits

The recurring judgment call: agents are non-deterministic and expensive, so use one only when the path genuinely can't be enumerated.

  • Chains vs agents — a chain is a fixed sequence you wrote; an agent lets the model choose. Prefer a chain when the steps are knowable: cheaper, faster, testable
  • Bounding: ModelCallLimitMiddleware / ToolCallLimitMiddleware plus LangGraph's recursion_limit and your own token budgets
  • Tool errors become ToolMessages (ToolErrorMiddleware or @wrap_tool_call) — never an unhandled crash
  • MCP integration via langchain-mcp-adapters
  • Multi-agent topologies live in the LangGraph subject
Level 9 · Retrieval & RAG

The LangChain retrieval surface

Retrieval theory — chunking, hybrid search, rerankers, evaluation — lives in the RAG subject. Here: how you actually wire it in LangChain, and what moved in 1.0.

4.5 The pipeline in LangChain

  • Loaders: PyPDFLoader, WebBaseLoader, DirectoryLoader, UnstructuredLoader
  • Splitters: RecursiveCharacterTextSplitter (the default), token-based via from_tiktoken_encoder, MarkdownHeaderTextSplitter, SemanticChunker
  • Vector stores: FAISS, Chroma, Qdrant, Weaviate, Milvus, pgvector, Pinecone
  • Retriever: vs.as_retriever(search_type="mmr", search_kwargs={"k": 5})

4.6 Retriever composition

Retrievers are Runnables, so they compose — this is where LangChain earns its keep.

  • EnsembleRetriever — hybrid dense + BM25 with weighted RRF (the standard exact-term fix)
  • ContextualCompressionRetriever + LLMChainExtractor / EmbeddingsFilter — trim retrieved chunks to what's relevant
  • ParentDocumentRetriever — match small chunks, return the enclosing parent
  • SelfQueryRetriever — LLM parses the question into a metadata filter + semantic query
  • Rerankers: CrossEncoderReranker, Cohere rerank
  • ⚠ MultiQueryRetriever and the old langchain.retrievers module now live in langchain-classic

4.7 Building the RAG chain

Deprecated: RetrievalQA and ConversationalRetrievalChain — build with LCEL as above, or wrap the retriever as a @tool and use create_agent for agentic RAG (the model decides whether and what to retrieve).

4.8 Interview focus

Likely interview questions
Core ⭐What is middleware and which prebuilt ones do you reach for?

Composable hooks around the agent lifecycle — before_agent/after_agent, before_model/after_model, wrap_model_call, wrap_tool_call, dynamic_prompt — replacing the old pre/post model hooks. In practice I reach for SummarizationMiddleware (context limits), ModelCallLimitMiddleware (bounding cost — the honest answer to "how do you stop a runaway agent"), ToolRetryMiddleware/ToolErrorMiddleware, PIIMiddleware, ModelFallbackMiddleware, and LLMToolEmulator for tests. The point is you add capability without rewriting the agent graph.

Practical ⭐You have 40 tools and the model keeps picking wrong. Options?

First fix the definitions — precise docstrings stating what each tool is and isn't for, typed schemas with field descriptions, distinct names, and remove overlap (overlap causes dithering). Then use the framework: LLMToolSelectorMiddleware(max_tools=…) to have an LLM narrow the set per call, or ProviderToolSearchMiddleware to defer tools to provider-side search. Architecturally, split into sub-agents each with a small focused toolset (SubAgentMiddleware). Around ~15 tool calls per pass is a practical ceiling, so treat a bloated toolset as a design smell rather than a prompt problem.

TrapIs AgentExecutor how you build agents?

No — deprecated since 0.2 and now in langchain-classic. Use create_agent from langchain.agents, which runs on the LangGraph runtime. Watch the parameter changes: prompt → system_prompt (a string), no pre-bound tool models, custom state must inherit AgentState, runtime data goes in context=, and the streaming node is now "model" not "agent".

CodingWrite a RAG chain in LCEL — where does format_docs go?

Inside the parallel dict, piped after the retriever: {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | model | StrOutputParser(). The retriever returns Document objects, so format_docs flattens them to a string the prompt template can interpolate; RunnablePassthrough forwards the original question unchanged. The dict literal is a RunnableParallel, so retrieval and passthrough run concurrently.
