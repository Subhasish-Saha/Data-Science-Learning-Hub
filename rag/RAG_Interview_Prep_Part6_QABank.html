6.1 Conceptual questions

Testing whether you understand the mechanisms, not just the vocabulary. If you can explain why each thing works, these are free points.

Conceptual · 23 questions
CoreWhat is RAG and why does it exist?

Retrieval-Augmented Generation gives an LLM an "open book" at inference: retrieve relevant text from an external corpus and put it in the prompt so the model answers from evidence, not just parametric memory. It exists to fix five weaknesses of a bare LLM — missing/private knowledge, hallucination, staleness, no source attribution, and the cost of re-training to add facts. (§1.1)

CoreHow are text embeddings trained, and why do they generalize to paraphrases?

Contrastively: mine (query, relevant-passage) pairs at scale, pull each anchor toward its positive and push it from negatives via an InfoNCE loss, using in-batch and mined hard negatives. Because the objective rewards putting meaning-equivalent texts near each other regardless of surface form, synonyms and paraphrases end up as neighbors — which keyword search can't do. (§0.1)

CoreCosine vs dot product vs Euclidean — when does it matter?

Only when vectors aren't normalized. On unit vectors, dot product equals cosine and L2 ranks identically, so most stacks normalize and use dot product (cheapest). Cosine ignores magnitude (usually what you want for text); dot product keeps it; Euclidean measures straight-line distance. The real trap is a metric/normalization mismatch between your embeddings and your index. (§0.2)

RetrievalWhy does pure semantic search fail on SKUs, IDs, and exact numbers?

Embeddings encode meaning, and arbitrary tokens like XR-4432 carry almost no learned semantics, so nearest-neighbor returns topically-similar chunks rather than the exact match. BM25/sparse search matches the literal token and ranks it first. Fix with hybrid search + RRF. (§2.1–2.2)

RetrievalWhat is hybrid search and why RRF for fusion?

Run dense (semantic) and sparse (BM25) retrieval in parallel and merge. Their scores aren't comparable, so weighted-sum fusion needs brittle per-corpus tuning; Reciprocal Rank Fusion instead sums 1/(k+rank) across lists — scale-free, no calibration, and it rewards cross-retriever consensus. It's the robust default. (§2.2)

RetrievalCross-encoder vs bi-encoder — why use both?

A bi-encoder embeds query and doc separately, so the corpus is precomputable and search is fast but ordering is approximate. A cross-encoder reads the pair jointly for much better relevance but must run per candidate at query time. Two-stage pipeline: bi-encoder retrieves ~100 (recall), cross-encoder reranks to ~5 (precision). (§2.4)

Vector DBExplain HNSW and its tuning knobs.

A hierarchical proximity graph: sparse upper layers with long links for coarse navigation, dense lower layers for precision. A query enters at the top, greedily hops toward the nearest node, and descends. Knobs: M (links/node — recall vs memory), efConstruction (build quality), and efSearch (query-time candidate list — the live recall/latency dial). (§1.6)

Vector DBExact vs approximate nearest-neighbor — the tradeoff?

Exact (flat) guarantees the true top-k but is O(N·d) per query — fine to ~10⁴–10⁵ vectors. ANN (HNSW/IVF/PQ) trades a small, tunable recall loss for orders-of-magnitude speed, essential at scale. You can keep a full-precision rescoring pass over ANN candidates to recover most of the lost recall. (§1.6)

ChunkingWhy does chunk size matter and how do you choose it?

Chunk size sets what one embedding must represent. Too big dilutes the vector across topics and wastes context; too small strips context and splits answers across boundaries. Pick empirically — start ~256–512 tokens with ~15% overlap, then measure recall@k on a labeled set for your corpus. There's no universal number. (§1.4)

QueryWhat is HyDE and when does it help or hurt?

HyDE generates a hypothetical answer to the query, embeds that, and retrieves with it — turning query→doc matching into doc→doc matching, which closes the short-query/long-passage gap. Helps on general/zero-shot queries; hurts on specialized corpora where the model's guess is wrong, and always adds an LLM call. (§2.6)

EvalWhat is the RAG triad, and what is faithfulness?

Three checks over query→context→answer: context relevance (is retrieved context relevant?), groundedness/faithfulness (is the answer supported by that context?), and answer relevance (does it address the query?). Faithfulness is measured by decomposing the answer into claims and checking each is entailed by the context. All three fail independently, so you measure all three. (§4.2)

AgenticDifference between Self-RAG and Corrective RAG?

Both add self-evaluation. Self-RAG is one fine-tuned model emitting reflection tokens during decoding (when to retrieve, is a passage relevant, is my sentence supported). CRAG is a modular add-on: a lightweight evaluator grades the retrieved set and triggers a corrective fallback (e.g., web search) when it's poor. Self-RAG bakes judgment in; CRAG bolts a grader + fallback onto any pipeline. (§3.7–3.8)

ArchitectureWhen would you use GraphRAG over vector RAG?

For relationship / multi-hop / "connect the dots" questions and corpus-wide "what are the main themes" queries — where the answer is spread across documents as a network of entities and relations that vector search can't traverse or aggregate. Not for simple fact lookup: extraction and graph maintenance are costly, so vector RAG stays the default. (§3.1)

RetrievalWhat is contextual retrieval?

Before embedding, prepend an LLM-generated sentence that situates each chunk in its document (section, entity, time). Isolated chunks lose the referents that make them findable; the prepended context restores them, sharply improving recall — especially paired with contextual BM25 and a reranker. Cost: a one-time LLM pass per chunk at ingest. (§2.8)

CoreRAG or fine-tuning — how do you decide?

Split knowledge from behavior. Factual, changing, private, or citable knowledge → RAG (re-index to update, citations for free). How the model behaves — format, tone, a skill → fine-tuning. They combine: fine-tune the generator/embedder, RAG for facts. Fine-tune-for-knowledge only when it's small, static, and latency forbids retrieval. (§1.1, §5.6)

CoreWhy do LLMs hallucinate, and does RAG eliminate it?

They predict plausible text from lossy, frozen parametric memory with no built-in "I don't know," so they fabricate on gaps, stale facts, and specifics. RAG reduces this by grounding answers in retrieved evidence and enabling abstention/citation — but doesn't eliminate it: bad retrieval or an ignored context still produces confident errors, which is why you measure faithfulness and add an abstention path. (§0.5, §4.7)

Very commonHow are images stored in a vector database?

Store a vector of the image + metadata, not the pixels. Get the vector either via a multimodal encoder (CLIP maps images and text into one shared space, so text queries retrieve images directly) or by captioning the image with a vision LLM and embedding the caption as text. The raw file stays in object storage (S3/GCS); the chunk's metadata holds a URL/ID pointer. At answer time, fetch the referenced image for a vision LLM or use the caption. (§3.4)

Very commonHow are tables stored / represented in a vector database?

Serialize the table to structure-preserving text (markdown/HTML with column headers kept beside values) at ingestion, then embed and store it like any chunk, tagged as a table. Choose granularity by query type: whole-table chunk, row-level chunks with repeated headers, or an embedded summary with the full table in the parent (small-to-big). For computation/aggregation, don't embed at all — keep the table in SQL and use text-to-SQL, since embeddings can't do arithmetic. Never flatten a table to bare numbers; that destroys the column semantics. (§1.3, §3.3, §3.4)

RetrievalHow does BM25 rank documents (and what do k₁ and b do)?

BM25 sums over the query terms: Σ idf(t) · [f·(k₁+1)] / [f + k₁·(1 − b + b·|D|/avgdl)], where f is term frequency in the doc, |D| its length, avgdl the average, and idf term rarity. k₁ (~1.2–2.0) controls term-frequency saturation (repeated terms give diminishing returns); b (~0.75) controls length normalization (long docs aren't favored for merely repeating a term). It beats raw TF-IDF because TF-IDF's unbounded term frequency over-rewards repetition and long documents. (§2.1)

QueryHyDE vs multi-query — what's the difference?

Both use an LLM to help retrieval, differently. HyDE generates a hypothetical answer and embeds that, turning query→document matching into document→document matching (closes the short-query/long-passage asymmetry). Multi-query generates several paraphrases of the question, retrieves each, and unions/RRF-merges — still query→document, hedging phrasing ambiguity. HyDE bridges vocabulary/shape; multi-query bridges phrasing. Both add latency; you can even combine them. (§2.3, §2.6)

ModernWhat is SPLADE / learned sparse retrieval?

A neural model that outputs a sparse vector over the vocabulary with learned term weights and automatic term expansion (adding related terms the text doesn't literally contain). It keeps BM25's exact-match precision, interpretability, and inverted-index efficiency while gaining semantic recall — hybrid-in-one-model. Use it to avoid running separate dense + sparse systems; ELSER is Elastic's managed version. (§2.1)

ConceptualWhat is self-query retrieval?

The LLM parses the natural-language question into a structured metadata filter plus a semantic query. "Cheap laptops under $800 from this year" becomes filter{price<800, year=2026} + query "laptop" — constraints buried in prose become exact predicates while the topical part stays vector search. Validate the generated filter against your schema and fall back to plain retrieval on parse failure. (§2.7)

ConceptualHow is a sentence embedding pooled from token vectors?

The transformer emits one vector per token; pooling reduces them to one: mean-pooling (average — common for BGE/E5/GTE), [CLS] pooling (the special token, if trained for it), or last-token pooling (decoder-based embedders, since causal attention lets the last token see everything). Use the pooling the model was trained with — mismatch degrades quality, and the pooling must be part of the contrastive training. (§0.1)

6.2 "Design a RAG system for X"

Testing whether you can assemble components into a coherent system with defensible trade-offs. Always: clarify → two pipelines → decisions-with-rationale → budget → eval → failure modes (§5.8). Below, the distinctive decision each scenario forces.

System design · 14 scenarios
DesignCustomer-support assistant: 500K docs, daily updates, sub-2s, RBAC, citations.

Two pipelines. Ingestion: nightly CDC → layout-aware parse → structure-aware chunk → self-hosted BGE embed → upsert into Qdrant with org_id/ACL metadata and version-delete of stale chunks. Serving: embed → hybrid retrieve with a mandatory org filter → RRF → bge-reranker (50→5) → grounded prompt with [Sn] citations → streamed LLM → semantic cache; abstain on weak scores. Budget fits ~2s with streaming. Add golden-set + RAGAS eval and chunk-logging/drift alerts. (worked in §5.7)

DesignLegal / contract search.

Distinctive needs: precision and exact citation to clause. Use structure-aware chunking on clauses/sections with larger chunks (self-contained clauses), parent-document retrieval (match clause, return section), rich metadata (section №, party, date, jurisdiction) for filtering, and hybrid search (legal terms are exact). Reranking is worth the latency; abstention is critical (a wrong legal answer is costly). Emphasize provenance and human-in-the-loop review.

DesignCodebase Q&A ("how does auth work in this repo?").

Code tokenizes densely and has exact identifiers, so: chunk by structure (functions/classes, using an AST-aware splitter), use a code-specialized embedder (Voyage-code / a code model), and lean on hybrid search since symbol names are exact tokens. Attach file path + symbol metadata for citation. Consider multi-hop/agentic retrieval for cross-file questions ("trace this call") and text-to-symbol-graph for relationship queries.

DesignHigh-stakes medical / clinical assistant.

Prioritize faithfulness and abstention over coverage. Strong grounding instruction, mandatory citations, a post-hoc entailment gate (§4.7) that abstains rather than guesses, and conservative thresholds. Domain-tuned embeddings (biomedical), PII handling and access control, full audit logging, and human review for anything actionable. Evaluation weights groundedness heavily; a confident wrong answer is the worst outcome.

DesignMulti-tenant SaaS with strict data isolation.

Isolation is the design center. Shard/namespace the index per tenant (also speeds search), and enforce a mandatory tenant_id filter at retrieval — never rely on the prompt. Scope caches per-tenant so a cached answer can't leak across boundaries. Consider separate collections/indexes for the largest tenants. Test isolation explicitly with adversarial cross-tenant queries in the golden set. (§4.10, §5.2)

DesignReal-time news / financial data (freshness-critical).

Streaming ingestion (not nightly batch): event-driven upsert within seconds, aggressive TTLs, and version-delete so stale prices/headlines vanish. Add recency weighting or a recency metadata filter at retrieval. Semantic caching must have short TTLs and re-index invalidation, or it serves stale answers. Possibly route time-sensitive queries to a live tool/API instead of the index. (§5.3, §4.9)

DesignMixed structured DB + unstructured docs.

Route by query type: a classifier sends computational/analytical questions to text-to-SQL over the DB and semantic questions to vector retrieval over the docs, then the LLM narrates (§3.3). Some questions need both — decompose, gather from each source, synthesize. Guard SQL (read-only, SELECT-only). This "router + two retrievers" is a common real-world shape.

DesignConversational assistant with multi-turn history.

The retrieval query must account for context: rewrite the follow-up into a standalone question using the conversation history ("what about the Pro tier?" → "what is the Pro tier refund window?") before retrieving — otherwise the embedding is ambiguous. Manage history length (summarize old turns), and be careful the history itself doesn't crowd out retrieved context. Query rewriting (§2.6) is the key addition.

DesignUltra-low-latency (sub-500ms) RAG.

Generation dominates, so: aggressive semantic caching, a small fast generation model, minimal context (tight top-k, compression), skip or lighten reranking, prompt caching for the static prefix, and streaming to cut perceived latency. Precompute/warm everything. You trade some quality for speed — measure the quality cost and route only latency-critical queries to the fast path. (§4.8–4.9)

DesignVery high QPS / millions of users.

Scale the serving path horizontally (stateless query nodes behind a load balancer), shard the index, and lean hard on caching (hit-rate rises with traffic). Rate-limit and queue ingestion so it never competes with serving. Watch the LLM provider as a throughput bottleneck and cost center — batch where possible, cache, and consider a self-hosted model at scale. Ingestion and serving scale independently (§5.1).

DesignMultilingual / cross-lingual corpus and queries.

Use a multilingual embedder (multilingual-E5, BGE-M3, Cohere embed-multilingual, LaBSE) that maps all languages into one shared space, enabling cross-lingual retrieval — an English query can match a German passage by meaning. A monolingual model silently tanks recall on non-English content. For hybrid, note BM25 doesn't cross languages (different tokens), so either translate the query, keep per-language sparse indexes, or weight the dense side more. Tag chunks with a lang field, and always measure recall per language — a good average can hide one weak language. (§1.5)

DesignHow do you choose top-k?

Two different k's. For stage-1 retrieval, cast a wide net (~50–100) so the reranker has candidates and recall@k is high — raise it until recall@k plateaus on your golden set. For the final context the LLM reads, keep it small (~3–5): lost-in-the-middle means more chunks become distracting padding, and every chunk costs tokens. So: retrieve wide, rerank + compress, send few. Tune both against measured recall and answer quality, not a fixed guess. (§2.4, §2.10, §4.1)

DesignHow do you evaluate a RAG change in production, not just offline?

Offline metrics (golden set, RAGAS) are a gate, not proof — they're biased proxies. Confirm online, staged: shadow-deploy (run in parallel, log, don't serve), A/B test on outcome metrics (thumbs-up, task success, deflection, latency), canary-ramp 1%→100% with automatic rollback, and use interleaving for sample-efficient retrieval comparisons. Tie the decision to business metrics (resolution rate, CSAT), since a change can lift a proxy metric yet hurt users. (§4.11)

DesignHow do you fine-tune an embedding model?

Contrastive fine-tuning on your data: mine (query, positive) pairs, mine hard negatives (high-ranked-but-wrong passages from a base retriever — random negatives are too weak), train with MultipleNegativesRankingLoss using large batches, small LR, 1–3 epochs, then re-embed the whole corpus and measure recall@k on held-out queries. Do it only when the domain is far from web text, you have (mineable) pairs, and off-the-shelf + reranking has plateaued — it's a re-index-forever commitment. (§1.5)

6.3 Debugging & troubleshooting

The bucket you can't fake — it reveals whether you've actually operated RAG. The meta-skill: localize the failure to a layer (parse / chunk / embed / retrieve / rerank / generate) before proposing a fix, and always "look at what it retrieved" first.

Debugging · 13 questions
DebugAnswers got worse over a month with no code changes.

Data/query/upstream drift, not code. Confirm with the frozen golden set, then check: corpus growth diluting the index, stale/contradictory doc versions (missing deletes), query-mix shift to poorly-covered topics, a silent embedding/LLM API version change, or index fragmentation. Fix per cause; re-run the golden set to confirm recovery. (§4.11)

DebugAnswers are "close but never quite right."

Retrieval is pulling the right neighborhood but not the precise passage — usually oversized chunks diluting the vector or missing overlap splitting the answer. Log and read the top-k, then shrink chunks / add overlap / try parent-document retrieval and re-measure hit rate. (§1.4, §1.9)

DebugThe answer is in the docs but never retrieved.

Check silent truncation first: chunks longer than the embedder's max token length have their tails dropped, so end-of-section content is unretrievable. Also check domain mismatch (general embedder on specialized text) and exact-term queries (need hybrid). Confirm by logging chunk token lengths vs the model cap. (§0.4, §1.4)

DebugRight chunks are retrieved, but the answer is still wrong.

The bug moved to generation/prompt. Print the exact prompt sent to the LLM: is the context actually there and delimited? Is the grounding instruction present? Is temperature low? Is the answer ignoring context in favor of parametric knowledge (tighten "use ONLY context")? Measure answer relevance and faithfulness to pinpoint which. (§1.7, §4.2)

DebugExact product codes / IDs never match.

Dense-only retrieval can't match arbitrary exact tokens. Add BM25/sparse and fuse with RRF; verify the code survives tokenization/chunking; consider a metadata field for exact lookup. Measure recall on ID queries specifically before/after. (§2.1–2.2)

DebugLatency suddenly spiked.

Profile per stage (§4.8) — it's almost never retrieval. Suspects: the LLM provider slowed or you're hitting rate limits/retries; reranking a larger shortlist; cache hit-rate dropped; or index degraded after many inserts (needs rebuild/retrain). Instrument each stage and compare to baseline timings.

DebugAutomated eval says "much better," users disagree.

Likely LLM-judge bias — the new answers are longer or more confidently formatted, and the judge rewarded that (verbosity/formatting bias), or your eval set is synthetic and leaks answers. Debias the judge (rubric, ignore length, different model, position-swap), validate against human labels, and add realistic/hard cases. (§4.6)

DebugAn agent loops and burns tokens on some queries.

Weak stop condition. Add a hard iteration cap with a graceful fallback answer, an explicit sufficiency check ("can you answer now?"), better tool-result formatting, and route truly-unanswerable queries to abstention. Log rounds to find the offending query classes. (§3.6, §3.11)

DebugFaithfulness is high but users still complain.

Faithfulness only checks support by the retrieved context — not whether that context was relevant or whether the answer addresses the question. You're likely faithfully summarizing the wrong-but-real passage (low context/answer relevance). Measure the whole triad; fix retrieval or the prompt, not grounding. (§4.12)

DebugAnything involving tables or numbers is wrong.

Usually parsing: tables were flattened into bare numbers at ingest, losing column semantics. Fix at ingestion — parse tables to markdown/HTML, repeat headers per row-chunk — and route heavily-computational questions to text-to-SQL instead of vector search. (§1.3, §3.3)

DebugA user retrieved another user's private document.

Access control wasn't enforced at retrieval. Add a mandatory permissions/ACL filter to the vector query so forbidden chunks are never candidates, and never rely on the LLM to "not mention" restricted content. Audit the filter, scope caches per-permission, and add cross-user adversarial cases to the eval set. This is a security incident — treat it as one. (§4.10)

DebugBrand-new system, no labeled data — how do you start evaluating?

Cold-start the eval. Generate a synthetic golden set (LLM writes QA pairs grounded in your chunks), hand-review a subset, and add no-answer + adversarial cases. Run reference-free metrics (faithfulness, answer relevancy) on live traffic since they need no ground truth, and — most valuable early — log the retrieved chunks and read them for 10–20 real queries. Add a thumbs feedback loop to harvest real questions into a growing labeled set. Start from strong defaults (hybrid + rerank, ~512-token chunks) and let the accumulating data drive iteration. (§4.5, §1.9)

DebugRetrieval returns contradictory documents. What's going on?

Most often stale versions coexisting because updates appended without deleting the old chunk (§5.3) — fix the freshness pipeline: version-delete superseded chunks, add updated_at, and prefer the latest. If the disagreement is legitimate (two valid sources differ), don't silently pick one — surface both with citations and let the user judge, or add a reconciliation step / recency-and-authority weighting in reranking. Either way, the log of retrieved chunks tells you which case you're in. (§5.3, §4.11)
