Part 6 of 7 · Tasks, Evaluation & Production

Shipping language systems people depend on The task catalogue with its 2026 decision rules, the evaluation level most candidates fail, and the production engineering — serving, drift, PII, reproducibility — plus multimodal and interpretability.

This part is where NLP stops being modelling and becomes engineering. The task catalogue gives you a defensible answer for each family — including the one that comes up most, NER for a brand-new entity type with zero labels (GLiNER or an LLM teacher, then distil into an encoder). Evaluation gets the most space because it is where interviews are lost: token accuracy instead of entity-level F1, ROUGE quoted as if it could see a hallucination, perplexity compared across tokenizers, an LLM judge with no bias controls. Then production: the tiered-cascade pattern that is the highest-leverage cost move in applied NLP, drift detection when labels arrive 30 days late, and the reproducibility hygiene that makes any of it auditable.

6.1 Text classification

The most common NLP task in industry, and the one where a baseline ladder plus a threshold story beats a clever architecture every time.

ShapeOutput layerMetric
BinarySigmoid, one logitPR-AUC, F1 at a chosen threshold
Multi-class (single label)SoftmaxMacro-F1 + per-class
Multi-labelSigmoid per label — not softmaxPer-label F1, micro/macro, subset accuracy, Hamming loss
HierarchicalPer-level heads or a flat head with maskingLevel-wise F1 + consistency rate
Extreme multi-labelLabel embeddings + ANN retrieval over labelsPrecision@k, nDCG@k

Also expect: intent classification with out-of-scope / OOD detection (an explicit other class, energy or max-softmax-probability thresholds), calibration before you threshold, and class imbalance handled with class weights, resampling or focal loss — in that order of preference.

6.2 Extraction and NER in 2026 ⭐

The single most-asked applied question: “NER for a brand-new entity type with zero labels — what do you build this week?” There is a current, defensible answer.

Non-negotiable

Evaluate NER with entity-level F1 — exact boundary and type — using seqeval, broken out per entity type. Token accuracy is inflated by the dominant O class; “98% accurate” on a corpus that is 90% O can be worse than predicting O everywhere. And remember to re-aggregate sub-token predictions into word-level spans first (§3.15).

6.3 Sentiment and ABSA

Document-level sentiment is nearly solved and rarely useful. What businesses actually want is sentiment about a specific thing.

Adjacent tasks: emotion classification, stance detection, toxicity/abuse. For all three, annotator disagreement is signal rather than noise — forcing a majority vote discards genuine ambiguity, so consider soft labels or distributional targets. Lexicon baselines (VADER) are fine to mention, with their ceiling stated honestly.

6.5 Machine translation

The task that produced the transformer — and the task with the most mature evaluation culture, which is why it's worth knowing precisely.

TopicWhat to say
LineageSMT (IBM models, phrase tables, word alignment) → NMT seq2seq + attention → transformer. MT is why attention and then the transformer were invented
TokenizationSubwords are effectively mandatory; shared vs separate source/target vocabularies; SentencePiece for script-agnostic handling
MultilingualOne model, language tags, zero-shot pairs via pivoting; watch the curse of multilinguality
MetricssacreBLEU with its signature (never a bespoke BLEU), chrF/chrF++ for morphologically rich languages, COMET as the human-correlated learned metric, plus LLM-judge adequacy/fluency rubrics
Production issuesDomain adaptation, terminology constraints and glossaries, hallucinated translations (fluent output unrelated to the source), low-resource pairs via back-translation and transfer
The 2026 MT evaluation stack

COMET + LLM-judge adequacy/fluency rubrics + per-language-pair calibration, with chrF for morphology and BLEU reported only for backwards comparability. Saying “I'd report BLEU” alone dates you; saying “sacreBLEU for comparability, chrF for morphology, COMET because it correlates with human direct assessments” does not.

6.6 Question answering

Two shapes with different metrics, and the point where this subject hands off to retrieval.

Extractive QAGenerative QA
OutputA span (start, end) in a passageFree text
ModelEncoder + span headDecoder or enc-dec
MetricEM and token-level F1Grounded correctness + faithfulness; judge rubrics
UnanswerableSQuAD 2.0 framing — the model must abstainExplicit “not in the context” behaviour, trained or prompted

Also know: multi-hop QA, table QA, conversational QA (which needs question rewriting / decontextualisation before retrieval — “what about the second one?” is unretrievable as written), and long-form QA.

Boundary with the RAG subject

Open-domain QA = retriever + reader, and everything about the retriever — chunking, hybrid search, RRF, rerankers, ANN indexes, RAGAS-style evaluation — lives in the RAG subject. This section owns the reader and the metrics.

6.8 Generation-adjacent and multilingual

A short catalogue of tasks that come up as design questions, plus the multilingual issues that need naming.

TaskThe thing to know
Paraphrase / style transferEvaluate semantic preservation and style change separately — one metric can't do both
Grammatical error correctionEdit-level evaluation (M²/ERRANT), not sentence accuracy
Data-to-textFaithfulness to the table is the whole game; hallucinated numbers are the failure
Text-to-SQLSchema linking is the hard part; the metric is execution accuracy, not string match; guardrails against destructive SQL
DialogueTask-oriented (intent + slots + policy) vs open-domain; state management hands off to the LangGraph subject
Controllable generationConstrained decoding, JSON/grammar constraints, plan-then-write
Multilingual: three things to always check

(1) Report per language, never only the macro average — non-Latin scripts pay a token premium, get less pretraining data, and usually carry most of the error. (2) Choose your transfer strategy explicitly: zero-shot cross-lingual (train English, run Hindi, via XLM-R), translate-train, or translate-test — they have different failure modes. (3) Handle language identification, transliteration and code-switching as first-class pipeline stages, not as edge cases.

6.13 Benchmarks and robustness

What the field measures itself with, why those numbers are increasingly untrustworthy, and the behavioural testing that catches what benchmarks miss.

FamilyExamplesStatus
UnderstandingGLUE, SuperGLUELargely saturated — near-ceiling scores stopped discriminating
MultilingualXTREME, XGLUE, MMTEBActive; always read per-language results
EmbeddingsMTEB / MMTEBStandard shortlist; heavily overfit — re-rank on your own data
Knowledge & reasoningMMLU / MMLU-Pro, HellaSwag, GSM8K, MATH, HumanEvalWidely quoted, widely contaminated
Long contextNeedle-in-a-haystack, RULER-style suitesThe right probe for effective context
TruthfulnessTruthfulQAUseful signal, narrow construct
CheckList — behavioural testing for NLP

Three test types worth naming: minimum functionality (does it handle the simplest possible case of a capability?), invariance (perturb something that shouldn't change the label — casing, typos, a name swap — does the prediction hold?), and directional expectation (add a strongly negative clause — does the prediction move the right way?). Add adversarial/contrast sets and counterfactual fairness slices. These catch shortcut learning and dataset artefacts — like NLI models that score well from the hypothesis alone — that no aggregate benchmark will reveal.

Benchmark contamination: detect it with n-gram overlap between the benchmark and your training corpus, canary strings, and performance gaps between a public benchmark and a freshly-collected private set. The practical conclusion — a private, held-out eval set is a competitive asset.

6.16 Serving and performance

Latency budgets, the levers that move them, and the honest observation that a distilled encoder on CPU is often the right production answer.

ConcernWhat to do
Latency budgetDecompose it: network, tokenize, forward pass, post-process. Track p95/p99, not p50 — the tail is what users feel
ThroughputDynamic/continuous batching, length bucketing (don't pad a 12-token input to 512), unpadding

6.18 Privacy, safety and compliance

In any regulated domain this is a scored part of the interview, and the expected answer is architectural rather than aspirational.

AreaThe concrete answer
PII detection & de-identificationNER + rules + validation (checksums for IDs, Luhn for cards); pseudonymisation with a reversible token vault where re-identification is required; retention policy and data residency
Training on user textConsent and lawful basis; keep a training-data manifest so you can answer “is this person's data in the model?” — because you cannot un-train a model on request
MemorisationLMs can regurgitate training data; test with canary strings; differential privacy as a heavier option
Safety classifiersToxicity, self-harm, abuse — with per-subgroup evaluation, because these classifiers are themselves biased
Generative featuresPrompt-injection surface — treat retrieved content as untrusted; detail lives in the LangChain subject
DocumentationModel cards and datasheets for datasets: intended use, out-of-scope use, evaluation slices, known limitations
Fairness, framed correctly

Audit per subgroup on the actual task, using counterfactual pairs (swap the name, swap the pronoun, hold everything else constant). Geometric debiasing of embeddings is a mitigation, not evidence — downstream classifiers can often recover the information it hid. What matters is whether the deployed decision differs for comparable people.

6.21 Long context and interpretability

Two frontier areas where the useful skill is knowing the honest limits.

ClaimThe honest position
“Just put the whole corpus in the context”Cost, latency, attention dilution, and no citation trail. Effective context < advertised context — measure it
“Knowledge editing fixes stale facts”ROME/MEMIT work in narrow demos; edits are brittle, leak into related facts, and don't compose. Retrieval is the maintainable answer
“Attention weights explain the model”Attention is not explanation — weights can be redistributed without changing the output, and information also flows via residuals and the FFN
“A probe shows BERT knows syntax”Probing classifiers may be learning the task themselves; control with random-label and random-model baselines
“LIME/SHAP tell you why”Useful, but unstable on long inputs and sensitive to the perturbation scheme; report variance

Mechanistic interpretability is the direction worth naming: induction heads, circuits, the residual-stream view, sparse autoencoders / learned features, and activation steering. Its practical payoff today is debugging — finding spurious correlations, dataset artefacts (NLI models that score well from the hypothesis alone) and shortcut learning.

“Is NLP just LLMs now?”

No — the boundaries moved. Representation and generation got commoditised; what became the job is problem framing, data quality, evaluation design, latency and cost engineering, and safety. Classical NLP survives as the cheap, deterministic, high-precision layer around the model. That answer works because it is specific about what changed rather than picking a side.

6.22 Interview focus for Part 6

Ten questions across tasks, evaluation and production — the areas where interviews are most often lost.

Tasks, evaluation & production · 10 questions
How do you classify a 50-page document with a 512-token model?

Four options, and I'd measure rather than assume. Truncate — trivially cheap and often fine, because many documents front-load their signal; the essential discipline is to log the truncation rate. Head + tail (first 256 + last 256) — a strong cheap trick for reports and emails where the conclusion is at the end. Chunk and pool — encode chunks and mean/max/attention-pool, using the whole document at k× the compute. A long-context encoder — ModernBERT gives 8k tokens in one pass, which is the 2026 default.

I'd also ask whether the label depends on the whole document at all. Often it depends on one section, in which case retrieve-then-classify beats all four.

⭐ NER for a brand-new entity type with zero labels — what do you build this week?

Day 1–2: GLiNER. It's a compact bidirectional encoder that matches entity-type descriptions against candidate spans, giving genuine open-vocabulary zero-shot NER on CPU — reported to beat both ChatGPT and NER-fine-tuned LLMs zero-shot, with domain variants like GLiNER-BioMed. That's a working system with no labels.

Day 3–5: the teacher loop. Run GLiNER (or an LLM) over unlabelled data, human-verify a stratified sample, fine-tune an encoder on the result, and evaluate on a human-labelled test set only. Add a rules/gazetteer precision layer on top for tickers, IDs and controlled vocabularies. Metric: entity-level F1 via seqeval, per entity type, with the error taxonomy split into boundary / type / spurious / missed — boundary errors usually dominate and respond to a CRF head or a span formulation rather than a bigger model.

Extractive vs abstractive summarization — and how do you catch hallucinations?

Extractive selects sentences: faithful by construction, since every word came from the source, but choppy and redundant. Abstractive generates: fluent and genuinely compressive, but it can state things the source never said. That trade-off is the answer.

Catching hallucinations: ROUGE cannot — it measures n-gram overlap with a reference, so a fluent, invented summary can score well. Use an explicit faithfulness metric: NLI-based (does the source entail each summary sentence? SummaC-style) or QA-based (generate questions from the summary, answer them from the source, compare — QAGS/QuestEval), plus a rubric-bound LLM judge and a human spot-check. For long inputs: map-reduce, refine, hierarchical, or retrieve-then-summarize.

⭐ Micro vs macro F1, and why is token accuracy the wrong NER metric?

Micro pools TP/FP/FN across classes and is dominated by the majority class; macro averages per-class F1 equally. Report macro plus per-class when the rare class is the point — a model can simultaneously show micro-F1 0.94 and macro-F1 0.60. The tell: in single-label multi-class, micro-F1 equals accuracy.

NER: token accuracy is inflated by the dominant O class — on a corpus that is 90% O, predicting O everywhere scores 90%. Use entity-level F1 with exact boundary and type matching via seqeval, broken out per type. And re-aggregate sub-token predictions into word-level spans first, or you're scoring a different task.

BLEU vs ROUGE vs chrF vs BERTScore vs COMET — what do you report?

BLEU is modified n-gram precision with a brevity penalty, corpus-level, translation-oriented — use sacreBLEU with its signature. ROUGE is recall-oriented overlap (ROUGE-1/2 n-grams, ROUGE-L longest common subsequence) and is the summarization convention. METEOR adds stems and synonyms with a fragmentation penalty. chrF is a character n-gram F-score, robust to morphology. BERTScore greedily aligns token embeddings. BLEURT and COMET are learned — COMET is trained on WMT human direct assessments over XLM-R and correlates far better with humans than any n-gram metric.

Per task: translation → chrF + COMET (+ sacreBLEU for comparability); summarization → ROUGE-1/2/L + BERTScore + an explicit faithfulness metric; open-ended/dialogue → surface metrics are near-useless, so rubric-bound LLM judging plus a human-graded anchor set.

⭐ Design an LLM-as-judge evaluation. Name three biases and your control for each.

Design: an explicit rubric with named criteria, a fixed scale with anchor descriptions, a required justification before the score, and pairwise comparison wherever possible — pairwise is materially more reliable than absolute scoring.

Biases and controls: position/order bias → randomise order and average both directions. Verbosity bias → control for length explicitly, or compare at matched lengths. Self-preference (judges favour their own model family) → use a different family as judge. Add language-switching and formatting bias, and sensitivity to the rubric wording.

What makes it evidence: calibrate against a human-labelled slice, report judge–human agreement (κ), and meta-evaluate the judge. Then combine: deterministic metrics for fast regression, judge for open-ended dimensions, human-graded anchor set validating both.

Your model was 0.89 F1 offline and users are complaining. Walk me through the debug.

I'd assume the evaluation is wrong before assuming the model is. In order: (1) leakage — were near-duplicates deduplicated before the split, and was the split grouped by document/user/time? (2) Slices — recompute per class, per language, per length bucket, per customer segment; a 0.89 aggregate can hide 0.3 on the class users care about. (3) Distribution shift — compare production inputs to the test set (length, language mix, vocabulary, OOV rate, truncation rate).

(4) The metric itself — is it the metric the decision needs? Macro vs micro, entity-level vs token-level, threshold set at 0.5 by default. (5) The pipeline around the model — a preprocessing mismatch between training and serving, truncation, a broken language router. (6) Label quality — audit 200 random labels; a 3% error rate caps the ceiling. (7) The complaint itself — collect the actual failing examples; “users are complaining” often means one visible, high-salience error class rather than a broad regression.

How do you detect drift when labels arrive 30 days late?

Distinguish three drifts. Input drift — measurable now with PSI/KL on token or embedding distributions, new-vocabulary rate, new-intent detection. Concept drift — the labels change meaning while the text distribution is unchanged, so input monitoring cannot see it. Performance drift — the thing you care about, arriving 30 days late.

So you need proxies: confidence-distribution shift, abstention rate, unknown/OOV token rate, prediction-mix shift, truncation rate and latency p95. And the strongest signals are downstream user behaviour — edit rate on suggested text, escalation rate, override rate, thumbs-down, time-to-resolution — which arrive in hours and correlate with the real metric. Wrap it in shadow deploys, canaries, a golden-set CI regression suite, and a relabelling flywheel.

Cut the NLP inference bill 10× without losing accuracy.

In this order, measuring at each step. (1) A tiered cascade — rules for the trivially-classifiable, a small encoder for the confident majority, the large model only for the escalated tail, humans for the last 2%. If 90% of traffic never touches the expensive model, average cost drops by roughly an order of magnitude with tail quality preserved. Escalation must be driven by calibrated uncertainty, not a raw softmax score.

(2) Distil the large model's behaviour into the small encoder using it as a teacher. (3) Quantize (~4-bit floor) so the small model runs on CPU. (4) Batch properly — continuous batching, length bucketing, unpadding; and export to ONNX/TensorRT. (5) Cache — exact-match first, then normalised-key, then a semantic cache with a similarity floor and TTL because of the false-hit risk. Then publish a table of macro-F1 vs p95 latency vs $/1M documents at each step, so the trade is visible rather than asserted.

How do you keep PII out of a training corpus and out of logs, and how do you make it reproducible?

PII: a detection pass combining NER, rules and validation (checksums for IDs, Luhn for cards) — rules give you precision on structured identifiers, the model gives recall on names and addresses. Then pseudonymise, with a reversible token vault only where re-identification is genuinely required. Apply it at ingest, before anything is persisted, and again on the logging path — trace redaction is a separate code path from training-data cleaning and both must exist. Add retention limits, data residency, and a training-data manifest, because you cannot un-train a model on request. Test for memorisation with canary strings.

Reproducibility: pin revision= to a commit SHA (never main), pin the tokenizer and library versions, seed everything, and record the exact preprocessing. Track experiments and dataset versions so you have lineage from a prediction back to a model and a data snapshot. Write NLP-specific tests: tokenizer round-trip, label-alignment invariants, schema validation of extracted output, CheckList-style invariance tests, and a no-network unit-test path with a tiny model.
